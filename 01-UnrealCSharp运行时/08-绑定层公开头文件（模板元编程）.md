## 1. 模块职责与架构速览

这一层是"**用宏 + 模板描述一个 C++ 类型/函数如何映射到 C#**"的元编程层。它由三块拼成：

**（1）注册块**（`FClassBuilder` + `TClassBuilder` + `TBindingClassBuilder`）
生成代码里写 `TBindingClassBuilder<T>(NAMESPACE_BINDING).Property(...).Function(...)`，构造期把 `void*` 函数指针写进 `FBindingClassRegister`。`TClassBuilder<T, bIsProjectClass>` 额外注册类型名（`TName<T,T>`）、命名空间（`TNameSpace<T,T>`）、`TTypeInfo<T>`，并在 `!TIsReflectionClass<T>` 时自动注册构造/析构（`TBindingClassBuilder.inl:14-22`）。

**（2）类型描述块**（`TPropertyClass` / `TPropertyValue` / `TPropertyBuilder` / `TArgument` / `TReturnValue`）
四张"类型 → 行为"的特化表，全部以 `std::enable_if_t<条件, T>` 做偏特化选择：

| 表 | 作用 | 关键约定 |
|---|---|---|
| `TPropertyClass<T>` | 取 C# 类型对象 `FClassReflection*`（`Value_Box` / `NewObject` / 泛型实例） | 字符串/容器/结构体各自走专用 Registry |
| `TPropertyValue<T>::Get(...)` | 值搬运：C# 托管对象 ↔ C++ 值 | 两/三个重载：`Get(handle)`（读入）、`Get<TIsReference>(ptr)`（写出/装箱） |
| `TPropertyBuilder<Member>` | 属性 get/set/info 函数指针 | 按"成员指针"与"静态指针"两套各 31 个特化 |
| `TArgument<T>` / `TReturnValue<T>` | 函数参数读入/写回、返回值写出 | 依据 `IN_BUFFER/OUT_BUFFER/RETURN_BUFFER` 三个 `uint8*` |

**（3）缓冲区协议**（`TBufferOffset` + `TOut` + `TTypeInfo::GetBufferSize`）
`TTypeInfo<T>::GetBufferSize()`（`UnrealCSharpCore/.../TTypeInfo.inl:29-39`）= 原生类型 `sizeof(T)`，否则 `sizeof(void*)`。C# 侧生成代码用完全相同的规则**紧凑打包**（`LinearColor.cs:475` InBuffer=20=8+4+8；`LinearColor.cs:483` OutBuffer=8 只含 out 参数），C++ 侧用 `TBufferOffset` 计算输入参数前缀和（正确），用 `TOut` 计算输出参数位置（**错误**，见 F-BIND-001）。

**值语义/引用语义的分工**：`TIsRef<T>`（`UnrealCSharpCore/.../TIsRef.inl:12-39`）决定哪些 `T&` 参数算"可写回的 out 参数"；`TTypeInfo<T>::IsReference()`（`= std::is_reference_v<T>`，`UnrealCSharpCore/.../TTypeInfo.inl:12-15`）决定 `TPropertyValue::Get<IsReference>` 走"别名"还是"拷贝"。两者是**不同的**判定，这一不对称是本报告两条主要发现的根源。

**两个"结构体"trait 的关系（补核，任务点名前提）**：`TIsScriptStruct<T>` 是**纯标记** trait，主模板恒 `false`（`UnrealCSharpCore/Public/Template/TIsScriptStruct.inl:3-7`），只由 `BINDING_SCRIPT_STRUCT` 显式特化为 `true`（`Macro/BindingMacro.h:164-168`）；`TIsUStruct<T>` 是 **SFINAE 探测**，等价于"`&T::StaticStruct` 是否合法"（`UnrealCSharpCore/Public/Template/TIsUStruct.inl:3-13`）。两者判定条件互不相关，**源码层面没有任何互斥约束，可以同时为真**。若某类型同时被 `BINDING_SCRIPT_STRUCT` 注册且拥有 `StaticStruct` 成员，则 `TArgument<T,T>`/`TPropertyValue<T,T>`/`TPropertyClass<T,T>`/`TReturnValue<T>`/`TPropertyBuilder` 会同时匹配两组**模板实参表相同**（`X<T, T>`）的偏特化 → 首次实例化即"偏特化二义"编译错误；`TIsProjectClass`（`Binding/Template/TIsProjectClass.inl:13-28`）与 `TConstructorHelper`（`Binding/Function/TConstructorHelper.inl:26-39`）改用 `if constexpr` 串联（`TIsUStruct` 分支优先），不受影响。抽查了 9 个已注册类型的 UE 5.6 引擎头文件（`FSoftObjectPath` `Runtime/CoreUObject/Public/UObject/SoftObjectPath.h:51`、`FPrimaryAssetType`/`FPrimaryAssetId` `.../PrimaryAssetId.h:23,105`、`FFrameNumber` `Runtime/Core/Public/Misc/FrameNumber.h:17`、`FFrameRate` `Misc/FrameRate.h:20`、`FFrameTime` `Misc/FrameTime.h:15`、`FPolyglotTextData` `Runtime/Core/Public/Internationalization/PolyglotTextData.h:16`、`FVector` `Runtime/Core/Public/Math/Vector.h`、`FDateTime` `Runtime/Core/Public/Misc/DateTime.h`），这些头文件内**均无** `USTRUCT`/`GENERATED_BODY`/`StaticStruct` 声明（5.6 里它们的反射改为在 `.gen.cpp` 里外联生成，例如 `friend struct Z_Construct_UScriptStruct_FPrimaryAssetType_Statics;` 见 `PrimaryAssetId.h:96`），故**未发现真实的同时为真实例**；56 个注册类型未穷举，该风险保留在 §6。

**问题**
`Buffer` 初值为 `OUT_BUFFER`（`TOut.inl:11`）。设 ref/out 参数下标为 `i1<i2<…`，槽位大小为 `s`：

- C# 期望第 k 个 out 参数位于 `Σ_{m<k} s_{i_m}`（紧凑）。
- C++ 实际位置：`P_1 = 0`；`P_{k+1} = P_k + offsets[i_k]`，其中 `offsets[i] = Σ_{j<i} s_j`（**所有**参数，含非 out 参数）。

因此只有在 `Σ_{j<i_1} s_j == s_{i_1}` 时才偶然正确。两个已核实的实例都恰好落在错误一侧：

`FDateTime::GetDate`（三个 `int32`，下标 0/1/2，`offsets=[0,4,8]`）写出顺序：
1. `Index=0`：把 `OutYear` 写到 `+0`，`Buffer += offsets[0] = 0` → **位置不动**；
2. `Index=1`：把 `OutMonth` 写到 `+0`（**覆盖 OutYear**），`Buffer += offsets[1] = 4`；
3. `Index=2`：把 `OutDay` 写到 `+4`（**覆盖 OutMonth**）。

C# 读回结果：`OutYear ← OutMonth 的值`、`OutMonth ← OutDay 的值`、`OutDay ← 未初始化的 stackalloc 栈内存`（该 4 字节从未被写出）。即"三个 out 参数全部错位 + 一个未初始化读"。

`FPolyglotTextData::GetIdentity`（两个 `FString&`，下标 0/1，`offsets=[0,8]`）：`OutNamespace` 与 `OutKey` 的托管句柄都被写到 `+0`，`+8` 保持未初始化；C# 侧 `OutNamespace`、`OutKey` 拿到同一个句柄。（该函数 C# 侧还叠加了一个生成器优先级 bug：`PolyglotTextData.cs:139` 与 `Actor.cs:5447` 写成 `HandleData.GetObject(*(nint*)OutBuffer + 8)`，按 C# 优先级等价于 `GetObject(handle + 8)`，永远查不到句柄 → null；属 C# 生成器问题，仅作旁证。）

**越界写（推断，未找到插件内活实例）**：`Buffer` 累加的是"全参数前缀偏移"，当 out 参数位于若干大体量参数之后、且 out 参数 ≥3 个时，累加值会超过 C# 的 `stackalloc` 出缓冲长度。构造例：`void F(FVector A, FVector B, int32& O1, int32& O2, int32& O3)`（槽位 `8,8,4,4,4`，`offsets=[0,8,16,20,24]`）→ 写出位置 `0, 16, 36`，而 C# 出缓冲只有 12 字节 → 第 3 次写出越过缓冲区尾部 28 字节。插件自带的双 out 场景（`GetDate`/`GetIdentity`）尚未越界。

**建议**
把"步长"改为"刚写出的槽位大小"，与反射路径（`Macro/FunctionMacro.h:116-134`，`OUT_BUFFER += OutPropertyDescriptor->GetBufferSize()`，**只遍历 out 属性**）保持一致：
```cpp
// TOut.inl:36 改为：写出后前进"本参数的槽位大小"，而不是它的起始偏移
if constexpr (TIsPrimitive<T>::Value)
{
    *(std::remove_const_t<std::decay_t<T>>*)Buffer = std::get<Index>(Argument).Set();
    Buffer += sizeof(std::remove_const_t<std::decay_t<T>>);
}
else
{
    *reinterpret_cast<void**>(Buffer) = std::get<Index>(Argument).Set();
    Buffer += sizeof(void*);
}
```
或更直接：保留 `TBufferOffset`，但按"仅 out 参数"的前缀和数组寻址（`OUT_BUFFER + OutOffsets[k]`），并加 `static_assert`/`check(Buffer - OUT_BUFFER <= OutBufferSize)` 类的边界断言。

**验证方式**
1. `grep -n "TBufferOffset<Args0...>" Source/UnrealCSharp/Public/Binding/Function/TOut.inl`（确认步长来源，命中 1 处即 `:36`）；`grep -n "GetBufferSize" Source/UnrealCSharpCore/Public/Binding/TypeInfo/TTypeInfo.inl`（命中 1 处即 `:31-38` 分支内的 `:33`/`:37`）。
2. 用例：C# 调 `FDateTime.GetDate(ref y, ref m, ref d)`，先把三个变量初始化成 `-1`，断言 `y/m/d` 等于 C++ `FDateTime::GetDate` 的真值——修复前 `OutDay` 恒为 `-1`（C++ 从未写出该槽位）。
3. 交叉用例：`FPolyglotTextData.GetIdentity(ref ns, ref key)` 断言两者不同。
4. 可在 `TOut::Get` 内加 `checkf(Buffer - OutBufferBase + SlotSize <= OutBufferSize, ...)`（需要把缓冲长度也传进来）来自动暴露越界组合。

**P0 定级结论**
**维持 P0，且认定为本报告唯一的 P0、确凿无疑**。判据链每一跳都已落到真实源码：① C++ 侧步长取"该参数在**全部参数**中的前缀偏移"（`TOut.inl:36` + `TBufferOffset.inl:41-45`）；② C# 侧出缓冲只按 **out 参数**紧凑打包并按紧凑偏移读回（`DateTime.cs:206-214`、`LinearColor.cs:483-489`、`PolyglotTextData.cs:133-139` 三处实测一致）；③ 二者在"out 参数 ≥ 2 且首个 out 参数之前存在非 out 参数"时必然错位；④ 插件自带两条绑定（`GetDate` 3 个 `int32&`、`GetIdentity` 2 个 `FString&`）正好命中该条件，均为**活跃**路径。实测后果：`GetDate` 三参数全错位并附带 1 个未初始化栈读（`OutDay`），`GetIdentity` 两参数拿到同一个句柄。"越界写"部分仍为**构造例推断**（未找到活实例），不影响 P0 定级；风险面收敛于 `Intermediate/**/*.binding.inl` 是否被纳入编译（见 §6 第 5 条，复核确认这些头当前无 include 点）。

**调用上下文**

**问题**
1. 原始类型 out 参数读回栈垃圾（数值随机）；`double`/`int64` 槽位还会读到相邻栈帧内容。
2. 非平凡类型 out 参数会把垃圾 `nint` 当作托管句柄交给 `HandleData.GetObject`（`Script/Interop/Handle/HandleData.cs`，字典查不到 → 返回 `null`），C# 侧得到 `null` 而非异常，错误被进一步掩盖。

4. 调用方无法区分"成功但结果为空"与"根本没有执行"。

**建议**
1. C++ 侧在对象解析失败时仍完成缓冲区写出（结构体/字符串给 `nullptr` 句柄、原始类型给零值），或至少提供显式的失败标志；把 `TMethodHelper::DefaultReturn()` 那套语义搬过来。

1. 文档化"非平凡 ref/out 参数必须整体重新赋值"，并在托管侧生成 `[Obsolete]`/分析器提示。

### [F-BIND-009] `TArgument::Set()` 的 `IsReference` 模板实参在**当前可达路径**上恒为 `false`（原因是 `TOut` 的 `IsRef()` 门控，而非 `decay`）——`TPropertyValue::Get` 的别名分支在参数路径不可达

- **复核证据**: `Source/UnrealCSharp/Public/Binding/Function/TArgument.inl:52-82`（`:55` `using Type = T;`、`:69-73` `Set()` → `Get<TTypeInfo<Type>::IsReference()>`、`:71-72` `const_cast<std::decay_t<Type>*>(&Value)`）；`UnrealCSharpCore/Public/Binding/TypeInfo/TTypeInfo.inl:12-15`（`IsReference() = std::is_reference_v<T>`）；**decay 与不 decay 的两组基类**：decay 组 `TArgument.inl:100`（指针结构体）、`:112`（字符串）、`:124`（容器）、`:234`（UObject）、`:385`（Optional）→ `IsReference()` = false；**不 decay 组** `TArgument.inl:92-96`（`TCompoundArgument<T, enable_if<!is_pointer_v<remove_reference_t<T>>, T>> : TBaseArgument<T>`），被 `:266-270`（`TIsUStruct`）与 `:134-153`（`TMultiArgument`/`TBindingArgument`/`TScriptStructArgument`）使用 → 对 `T = FGuid&` 得 `Type = FGuid&`、`IsReference()` = **true**；而 `FGuid&` 进不到 `Set()`（`TOut.inl:25` 要求 `IsRef()`，`TIsRef.inl:35-38` 对结构体恒 `false`，见 F-BIND-002）；能进 `Set()` 的类型中，primitive 走 `TBaseArgument<T,true>`（`TArgument.inl:38-41` 的 `Set()` 根本不调 `TPropertyValue`），其余（字符串/容器/多值/指针/Optional）都已 decay → `IsReference()` = false；**返回值路径**确实用到别名分支：`Binding/Function/TReturnValue.inl:31-35`（同一 `TTypeInfo<Type>::IsReference()` 表达式）+ `FRegisterDateTime.cpp:91`（`BINDING_OVERLOAD(FDateTime&(*)(FDateTime&, const FDateTime&), &PlusImplementation)` → `Result = FDateTime&` → `Get<true>`）
- **级别变动**: 无（由 P2 降为 P3，维持 P3）
- **文件**: `Source/UnrealCSharp/Public/Binding/Function/TArgument.inl:69-73`
- **函数**: `TBaseArgument<T, false>::Set()`
- **置信度**: 高

**现状（代码事实）**
```cpp
// TArgument.inl:52-82
template <typename T>
struct TBaseArgument<T, false>
{
	using Type = T;                       // ← Type 就是传进来的 T（是否已 decay 取决于派生类，见下）
	…
	auto Set()
	{
		return TPropertyValue<Type, Type>::template Get<TTypeInfo<Type>::IsReference()>(
			const_cast<std::decay_t<Type>*>(&Value));
	}
```
`TTypeInfo<T>::IsReference()` 定义为 `std::is_reference_v<T>`（`UnrealCSharpCore/Public/Binding/TypeInfo/TTypeInfo.inl:12-15`）。
**更正**："所有 `TArgument` 派生类都先做 `std::decay_t`，因此 `Type` 永不是引用类型"——**不成立**。实际有两组基类：
- **decay 组**（`TCompoundArgument<std::decay_t<T>, std::decay_t<T>>`，`TArgument.inl:112/124/385`；`TBaseArgument<std::decay_t<T>>`，`:100/:234`）：`Type` 非引用 → `IsReference()` = false；
- **不 decay 组**：`TArgument.inl:92-96` 的 `TCompoundArgument<T, std::enable_if_t<!std::is_pointer_v<std::remove_reference_t<T>>, T>> : TBaseArgument<T>` —— `Type` **就是 `T` 本身**。`TArgument.inl:266-270`（`TIsUStruct` 分支）与 `:134-153`（`TMultiArgument`/`TBindingArgument`/`TScriptStructArgument`）都走这一支，于是 `T = FGuid&` 时 `Type = FGuid&`、`IsReference()` = **true**。

因此"`Get<true>` 别名分支在**参数路径**上不可达"这一**结论仍然成立，但原因是另一条**：`Set()` 仅由 `TOut::Get` 在 `IsRef()` 为真时调用（`TOut.inl:25`），而 `IsRef()` 对结构体恒为 `false`（`TIsRef.inl:35-38`，即 F-BIND-002）；能通过 `IsRef()` 的类型要么是 primitive（走 `TBaseArgument<T,true>`，其 `Set()`（`:38-41`）根本不经过 `TPropertyValue`），要么已被 decay（`IsReference()` = false）。
**推论**：该别名分支**不是死代码**——若按 F-BIND-002 的建议把结构体纳入 `TIsRef`，"按引用写回已注册存储"正是结构体 out 参数要走的分支；而它在**返回值路径**已经可达（`TReturnValue.inl:31-35` + `FRegisterDateTime.cpp:91` 的 `FDateTime&` 返回重载）。`TReturnValue.inl:33-34` 与这里是**同一个** `TTypeInfo<Type>::IsReference()` 表达式，并非"真实 `std::is_reference_v`"与别名的两种语义。

**调用上下文**
`TOut::Get`（`TOut.inl:29/33`）→ `Argument.Set()`。因此 out 参数每次都新建一份托管副本（`new FString(...)`、`new TArray(...)`、`new FStruct(...)`）并交给 Registry 管理（`AddStringReference<..., true, ...>` 等）。

**问题**
1. 读代码的人会以为 out 参数会复用/别名已注册对象，实际在这条可达路径上**永远拷贝**（`TPropertyValue<...>::Get<false>` → 例如 `TPropertyValue.inl:287-289` 的 `new std::decay_t<T>(*InMember)`）。真正的不可达理由是 `TOut.inl:25` 的 `IsRef()` 门控（见"现状"更正后的机制），而不是"`IsReference()` 恒 false"；这一点会影响修复方向：**修 F-BIND-002 的同时就会把 `Get<true>` 变成结构体 out 参数的活跃路径**，届时应连带评估"别名 vs 拷贝"的所有权语义（当前 `AddStructReference<false>` 不释放、`<true>` 释放）。
2. 语义上拷贝是必要的（C# 侧把 out 值换成新对象），但每次 out 调用一次深拷贝 + 一次 `IsNeedFree` 释放，属可优化项。
3. `const_cast<std::decay_t<Type>*>(&Value)` 是多余操作（`Value` 本身非 const），暗示作者对 `Type` 的 const 性有误解。

**建议**
显式化意图，避免"看起来像支持别名"的误导：
```cpp
	// 明确：out 参数一律传值（拷贝），不别名
	return TPropertyValue<Type, Type>::template Get<false>(&Value);
```
并对大对象 out 参数（`TArray`/`TMap`/`FString`）改走"原地复用已注册容器"的路径以省一次深拷贝（需要 C# 侧配合：读回时不再替换对象）。同时把 `TArgument.inl:43-46`、`:75-78`、`:104-107`、`:116-119`、`:128-131`、`:238-241`、`:389-392` 那些 `constexpr auto IsRef() const { return TTypeInfo<Type>::Get()->IsRef(); }` 里的 `constexpr` 去掉——`TTypeInfo<T>::Get()` 返回运行期静态对象指针（`TTypeInfo.inl:56-61`），该函数在任何实参下都不可能成为常量表达式（`constexpr` 声明在此属 ill-formed NDR）。

**验证方式**
`grep -n "IsReference()" Source/UnrealCSharp/Public/Binding/Function/TArgument.inl Source/UnrealCSharp/Public/Binding/Function/TReturnValue.inl`；在 `TPropertyValue<FString>::Get<IsReference=true>` 里加 `static_assert(IsReference, "alias path hit")` 观察参数路径是否触发（预期不触发）。
