## 1. 模块职责与架构速览

**职责**：`FPropertyDescriptor` 是 UE `FProperty` 的 C++↔C# 反射包装，负责三件事：
1. `Factory(FProperty*)`（`FPropertyDescriptor.cpp:47`）把任意 `FProperty*` 映射成具体描述符；
2. 提供 C# 侧 P/Invoke 需要的**缓冲区布局信息**（`GetBufferSize`）与**取值/写值**（`Get`/`Set`/`CopyValue`）；
3. 暴露 UPROPERTY 标志、元素大小、名称、类型哈希、`Identical` 等元数据。

**关键结构事实（与任务简报的预期不同，必须先纠正）**：

> **11 个 Primitive 描述符并不是 11 份复制粘贴的实现。**
> 10 个（Byte/Double/Float/Int8/Int16/Int/UInt16/UInt32/UInt64/Int64）是 9 行的**空派生类**，全部继承同一个模板 `TPrimitivePropertyDescriptor<T>`；只有 `FBoolPropertyDescriptor` 有一个 6 行的 `Set` 覆盖。
> 所有 `Get`/`Set`/`CopyValue`/`GetBufferSize`/`DestroyProperty` 行为都来自 `Source/UnrealCSharp/Public/Reflection/Property/TPrimitivePropertyDescriptor.inl`（66 行）。

因此"重复代码"的真实形态是**模板已被使用**，剩余冗余在别处（见 F-PROP-005、F-PROP-006）。

**三层继承**：

```
FPropertyDescriptor                                   (h:20, 抽象接口, cpp:136-206 全空实现)
  └── TPropertyDescriptor<T, auto IsPrimitive>        (TPropertyDescriptor.inl:6)  持有 T* Property / FClassReflection* Class
        ├── TPrimitivePropertyDescriptor<T>           (TPrimitivePropertyDescriptor.inl:7)  IsPrimitive=true
        │     ├── FBoolPropertyDescriptor  final      (FBoolPropertyDescriptor.h:5)  + 自有 Set
        │     └── FByte/FDouble/FFloat/FInt8/FInt16/FInt/FInt64/FUInt16/FUInt32/FUInt64PropertyDescriptor final
        │           └── （另有第 12 个模板派生类：`FEnumPropertyDescriptor`，`EnumProperty/FEnumPropertyDescriptor.h:5`
        │                也 `: public TPrimitivePropertyDescriptor<FEnumProperty>`，但它**覆盖了 `Set`/`Get`/`DestroyValue`**，
        │                见 F-PROP-003 复核证据；不在本次 24 个指定文件内）
        └── TCompoundPropertyDescriptor<T>            (TCompoundPropertyDescriptor.inl:6)   IsPrimitive=false
              └── FStr/FText/FArray/FMap/FSet/FStruct/FObject/... PropertyDescriptor（**共 20 个 final 派生类**，见 F-PROP-007）
```

**工厂机制**（`PropertyMacro.h:3-5`）：

```cpp
#define NEW_PROPERTY_DESCRIPTOR_IMPLEMENTATION(FPropertyType, FPropertyDescriptorType) if (auto Property = CastField<FPropertyType>(InProperty)) return new FPropertyDescriptorType(Property);
#define NEW_PROPERTY_DESCRIPTOR(FPropertyType) NEW_PROPERTY_DESCRIPTOR_IMPLEMENTATION(FPropertyType, FPropertyType##Descriptor)
```

类名由 `##` **记号粘贴**生成——这就是为什么 grep 类名只能命中 3 次（见第 9 节）。注意 `if (auto Property = CastField<...>)` **不检查 `InProperty` 本身是否为 null**（`CastField` 对 nullptr 返回 nullptr，故安全），且工厂末尾 `return nullptr`（`cpp:133`）——调用方必须处理 null 描述符。

## 3. 发现清单

### P1

#### [F-PROP-001] `GetBufferSize()` 三份实现语义不一致，且 Primitive 版缺少空指针检查（"DestroyProperty 之后必崩"——**复核：该崩溃路径当前不可达**）

- **类别**: Bug / 未定义行为 / 一致性
- **严重度**: **P3**
- **复核结论**: 部分确认（偏差：**崩溃路径当前不可达**，原文"DestroyProperty 之后必崩"高估了可达性；三份实现语义不一致的代码事实完全成立）
- **可达性**: 不可达
- **复核证据**: `TPrimitivePropertyDescriptor.inl:58-65`（无 null 检查，逐字吻合）、`TCompoundPropertyDescriptor.inl:50-53`（`return sizeof(void*);`，吻合）、`FPropertyDescriptor.cpp:175-178`（`return 0;`，吻合）、对照 `FPropertyDescriptor.inl:11-24`（有 null 检查，吻合）。
  `DestroyProperty()` 的 4 个真实调用点（grep `DestroyProperty` 全 `Source/` = **8 命中**：`FPropertyDescriptor.h:49` 声明、`FPropertyDescriptor.cpp:171` 基类空实现、`TPropertyDescriptor.inl:22` 与 `TPrimitivePropertyDescriptor.inl:48` 两个 override、`FArrayHelper.cpp:43`、`FMapHelper.cpp:54`、`FMapHelper.cpp:60`、`FSetHelper.cpp:50`）**全部紧跟 `delete <描述符>`**，例如 `FArrayHelper.cpp:43-47`：`DestroyProperty(); delete InnerPropertyDescriptor; InnerPropertyDescriptor = nullptr;` —— **`DestroyProperty()` 与 `delete` 之间不存在任何 `GetBufferSize()` 窗口**，故"置空后再取缓冲区大小"在当前代码里到不了。
  `GetBufferSize()` 本身确实活跃（`FunctionMacro.h:73`、`FunctionMacro.h:132`，grep 全 `Source/` 39 命中），但它拿到的是**尚未销毁**的描述符。
- **级别变动**: 无（维持 P3）。理由：语义分裂与缺少防空是真实的契约缺陷（P3=风格/隐患），但既然崩溃路径不可达，不得按"必崩"定 P1；原 P1 定级系可达性误判所致。
- **文件**: `Source/UnrealCSharp/Public/Reflection/Property/TPrimitivePropertyDescriptor.inl:58`、`Source/UnrealCSharp/Public/Reflection/Property/TCompoundPropertyDescriptor.inl:50`、`Source/UnrealCSharp/Private/Reflection/Property/FPropertyDescriptor.cpp:175`、对照 `Source/UnrealCSharp/Public/Reflection/Property/FPropertyDescriptor.inl:11`
- **函数**: `TPrimitivePropertyDescriptor<T>::GetBufferSize() const`
- **置信度**: 高（三份实现与调用点均已实读）

**现状（代码事实）**

**调用上下文**
- `GetBufferSize()` 真实调用点（grep `GetBufferSize`，Source/ 全 7 模块，共 39 命中，去掉 `FGeneratorCore::GetBufferSize(FProperty*)` 与 `FTypeInfo::GetBufferSize` 两个同名的无关符号后，描述符级调用点为）：
  - `Source/UnrealCSharp/Public/Macro/FunctionMacro.h:73` `IN_BUFFER += PropertyDescriptor->GetBufferSize();`
  - `Source/UnrealCSharp/Public/Macro/FunctionMacro.h:132` `OUT_BUFFER += OutPropertyDescriptor->GetBufferSize(); \`
  - `Source/UnrealCSharp/Public/Binding/Function/TBufferOffset.inl:43`（`TTypeInfo<...>::Get()->GetBufferSize()`，走的是 `FTypeInfo` 虚接口，非本类）
- `DestroyProperty()` 真实调用点：`FArrayHelper.cpp:43`、`FMapHelper.cpp:54`、`FMapHelper.cpp:60`、`FSetHelper.cpp:50`——即**容器内嵌描述符的析构路径**。
- `Super::Property` 的来源：`TPropertyDescriptor.inl:10-14` 构造，由 `PropertyMacro.h:3` 的 `CastField` 保证**构造时非空**。

**问题**
1. **语义分裂**：同名方法在基类返回 `0`、Primitive 返回真实元素大小、Compound 返回 `sizeof(void*)`。调用方（`FunctionMacro.h:73/132`）把它当作"C# 侧入参缓冲区需要多少字节"来累加偏移，而 Compound 描述符的 `CopyValue` 实际 `Malloc` 的是 `ElementSize` 字节（`TCompoundPropertyDescriptor.inl:35-41`）——**两者不同**，说明 Compound 的 `GetBufferSize` 表达的是"缓冲区里放的是句柄指针"，Primitive 的 `GetElementSize` 表达的是"缓冲区里放的是值本身"。这是**隐式约定**，基类签名与注释都没有区分，任何新描述符作者都会写错。
2. **空指针解引用**：`DestroyProperty()` 把 `Property` 置空后（`TPrimitivePropertyDescriptor.inl:54`），`GetBufferSize()` 直接 `Super::Property->...`。同一文件里 `TPropertyDescriptor::DestroyProperty`（`TPropertyDescriptor.inl:22-30`）与 `TPrimitivePropertyDescriptor::DestroyProperty`（`:48-56`）是**逐字节相同的两份实现**，即破坏性的"delete 并置空"被写了两次——说明作者已意识到置空后的风险却只在 `GetElementSize` 里防了一半。

**建议**
```cpp
// TPrimitivePropertyDescriptor.inl
virtual auto GetBufferSize() const -> int32 override
{
	if (Super::Property == nullptr)          // 与 FPropertyDescriptor::GetElementSize 对齐
	{
		return 0;
	}

#if UE_F_PROPERTY_GET_ELEMENT_SIZE
	return Super::Property->GetElementSize();
#else
	return Super::Property->ElementSize;
#endif
}
```
并在 `FPropertyDescriptor.h:51` 给 `GetBufferSize` 加契约注释，明确区分"值缓冲字节数"与"句柄字节数"，或改名为 `GetValueBufferSize` / `GetHandleBufferSize` 二者之一。

**验证方式**
- `grep -n "GetBufferSize" Source/UnrealCSharp` 核对描述符级调用点仅 `FunctionMacro.h:73,132`。
- 在 `TPrimitivePropertyDescriptor::GetBufferSize` 首行加 `check(Super::Property)`，跑任意会走 `FArrayHelper` 析构路径的用例（对含 Primitive 元素的 `TArray` 属性执行 `DestroyProperty` 后再读缓冲区大小）。
- 单测：`FArrayHelper` 销毁后调用 `InnerPropertyDescriptor->GetBufferSize()`，当前应崩，修复后返回 0。

#### [F-PROP-002] `CopyValue()` 三份实现返回三种所有权（nullptr / 入参别名 / 新分配内存），调用方无法判断是否该释放

- **类别**: Bug / 内存/资源泄漏 / 未定义行为
- **严重度**: **P2**
- **复核结论**: 部分确认（偏差："决定最终定级的唯一未验证点"**已证伪**——`AddStringReference` 的第二模板参数 `IsNeedFree=true` 表示**接管并负责释放**，故 Compound 分支的 `Malloc` 所有权有归属，本条维持 P2 契约问题、**不升级为 P1 泄漏**；三份实现语义不一致的代码事实完全成立）
- **可达性**: 活跃
- **复核证据**: 三份实现逐字核对吻合：`FPropertyDescriptor.cpp:166-169`（`return nullptr;`）、`TPrimitivePropertyDescriptor.inl:43-46`（`return const_cast<void*>(InAddress);`）、`TCompoundPropertyDescriptor.inl:33-48`（`FMemory::Malloc` + `InitializeValue` + `CopySingleValue`，`:35/:43/:45` 行号吻合）。
  调用点：grep `CopyValue` 全 `Source/` = **6 命中**（`.h:47` 声明、`cpp:166` 定义、`TCompoundPropertyDescriptor.inl:33`、`TPrimitivePropertyDescriptor.inl:43`、`FunctionMacro.h:129`、`FunctionMacro.h:144`）——"没有第三处调用点"成立。

  **所有权已定性**：`FCSharpEnvironment.h:203-204` 的签名是

- **级别变动**: 无（维持 P2）。理由：所有权有归属 → 不是线性泄漏（不能按 P1）；但"同一虚函数三种所有权语义、且宏内不做任何释放"是真实的契约缺陷（P2）。

**逐类型核对结论（这是本条的实质）**
| 实例化类型 | UE 属性 | 存储 | `InitializeValue` 是否释放旧资源 | 判定 |
|---|---|---|---|---|
| `FBoolProperty` | 位存储（FieldMask/ByteOffset） | 1 bit | 否（POD） | 无泄漏；且该类另有 `Set` 覆盖绕开了 `InitializeValue` |

**因此：其它报告所述"Set 不 DestroyValue → 非平凡类型堆数据泄漏"在 Primitive 描述符中【不成立】**——11 个实例化类型全部是 POD/位存储，`FProperty::InitializeValue` 对它们是 no-op 级别的清零，不涉及内部堆数据。该缺陷的真实生效面**不是** `TCompoundPropertyDescriptor` 这个模板——该模板**根本没有 `Set`**（全文件 54 行，只有 `Get`×4/`CopyValue`/`GetBufferSize`），它的 `Set` 直接落到 `FPropertyDescriptor::Set`（`FPropertyDescriptor.cpp:157-159`，**空函数体**，那个是"静默失效"，见 F-PROP-004）；真实生效面是**下节列出的 20 个具体 Compound 描述符各自的 `Set` 覆盖**（`FStrProperty`/`FTextProperty`/`FNameProperty`/`FArrayProperty`/`FMapProperty`/`FSetProperty`/`FStructProperty`/`FOptionalProperty`/…），它们的 `Set` 里 `InitializeValue` 与 `DestroyValue` 不配对。

**仍然成立的两个问题**
1. **对活体 UObject 内存重复初始化**：`Set` 的 `Dest` 常常不是临时缓冲，而是 UObject 字段本身。证据：
   - `Source/UnrealCSharp/Private/Domain/Interop/FRegisterProperty.cpp:35` `PropertyDescriptor->Set(IN_BUFFER, PropertyDescriptor->ContainerPtrToValuePtr<void>(FoundAddress));`
   - `Source/UnrealCSharp/Public/Macro/FunctionMacro.h:72` `PropertyDescriptor->Set(IN_BUFFER, PropertyDescriptor->ContainerPtrToValuePtr<void>(Params));`
   - `Source/UnrealCSharp/Private/Reflection/Container/FArrayHelper.cpp:137,269`、`FMapHelper.cpp:200,218`、`FSetHelper.cpp:102`、`FOptionalHelper.cpp:91`、`FManagedFunctionDescriptor.cpp:56,61,82`
   对 POD 属性无害；但这意味着"`Set` 的实现必须对已经初始化的内存幂等"这一隐含前提没有写在任何契约里，模板一旦被复用于非 POD（有人把 `FStructPropertyDescriptor` 接到 `TPrimitivePropertyDescriptor` 上）就会立刻变成真实泄漏。
2. **两个 `Set` 实现不一致**：模板版 `InitializeValue` + `CopySingleValue`；`FBoolPropertyDescriptor` 版只有 `SetPropertyValue`。后者**依赖 `FBoolProperty::SetPropertyValue` 自己处理位掩码**（正确），但两者不共享任何公共步骤，任何在模板 `Set` 中新增的逻辑（例如将来加上 `DestroyValue`）都会**静默跳过 bool**。

**建议**
```cpp

```

**补充证据（把这条从"推测"变成"已确认的真实泄漏"）**

|---|---|---|

即：**其它报告所述缺陷在 Primitive 描述符中不成立，但在 Compound 描述符中成立**。修复应落在 **20 个描述符的 `Set` 实现**上（补 `Property->DestroyValue(Dest);`，或先 `Property->DestroyValue(Dest)` 再 `Property->SetPropertyValue(Dest, ...)`）——**但必须按 `Dest` 的活跃性区分**：只有在 `Dest` 已持有活值的 4 个调用点（`FRegisterProperty.cpp:35/64`、`FArrayHelper.cpp:137`、`FOptionalHelper.cpp:91`）才存在泄漏；容器**新增元素**路径（`FArrayHelper.cpp:269`、`FMapHelper.cpp:200`、`FSetHelper.cpp:102`，其 `Dest` 来自 `FScriptArray/FScriptMap/FScriptSet::AddUninitialized`，见引擎 `UnrealType.h:4015-4021` = 裸 `Array->Add(...)`、**不做构造**）上 `Dest` 是未初始化内存，**在那里补 `DestroyValue` 反而会对未初始化内存调用析构（UB / 二次释放）**；`FMapHelper.cpp:218` 的既有键分支在 `:215` 已先 `DestroyValue`，亦不需再补。Primitive 模板的修复（F-PROP-003 建议）属于预防性加固、不修不会造成泄漏（对 11 个 Primitive + `FEnumProperty` 而言）。

## 6. 缓冲区边界与类型宽度

1. **Primitive 路径没有任何 `memcpy`/手工 size 计算**。取值/写值全部走 `FProperty::CopySingleValue`（`TPrimitivePropertyDescriptor.inl:18,33,40`），大小由 `FProperty` 自身决定 → **不存在"size 来自错误常量"的越界风险**。这是 Primitive 描述符最健康的一点。
2. **唯一涉及大小的位置**是 `GetBufferSize()`（`inl:58-65`），返回 `Property->GetElementSize()` 或 `Property->ElementSize`（由 `UE_F_PROPERTY_GET_ELEMENT_SIZE` 宏切换）。两个分支语义等价（UE5.4+ 用函数、更早版本用字段），**宽度来源正确**，但缺 null 检查（F-PROP-001）。
3. **`int64`/`uint64`/`double` 与 C# `long`/`ulong`/`double` 严格对应**：`FInt64Property`→`int64`(8B)、`FUInt64Property`→`uint64`(8B)、`FDoubleProperty`→`double`(8B)，三者都是 8 字节 POD，`CopySingleValue` 按 `FProperty` 的真实大小拷贝。**未发现静默截断**。注意工厂里的注册顺序（`FPropertyDescriptor.cpp:55-63`）是先 `FUInt64`(55) 再 `FInt64`(63)、`FInt8`(57)/`FInt16`(59)/`FInt`(61)——`CastField` 是精确类匹配（非 `IsA` 语义的宽匹配）故顺序无影响，但同一文件 `FClassProperty` 分支（`:69-79`）用 `HasAnyPropertyFlags(CPF_UObjectWrapper)` 在 `FSubclassOf` 与 `FClass` 之间分流，说明作者在需要分支时会显式写出来。
4. **`FBoolProperty` 是位存储**：
   - `Set` 走 `FBoolProperty::SetPropertyValue(Dest, bool)`（`FBoolPropertyDescriptor.cpp:5`），位掩码（`FieldMask`/`ByteOffset`）由 UE 的 `FBoolProperty` 内部处理 —— **实现正确，没有手写 `SetBit`/`GetBit` 的需求**，插件里也没有出现手写掩码。
     **引擎侧已核实（本机 `Engine\Source`）**：`Runtime/CoreUObject/Public/UObject/UnrealType.h:2461-2466`
     ```cpp
     FORCEINLINE void SetPropertyValue(void* A, bool Value) const
     {
         check(FieldSize != 0);
         uint8* ByteValue = (uint8*)A + ByteOffset;
         *ByteValue = ((*ByteValue) & ~FieldMask) | (Value ? ByteMask : 0);
     }
     ```
     即掩码逻辑确实在引擎侧（`:2464` 用 `ByteOffset`、`:2465` 用 `FieldMask`/`ByteMask`），插件侧 `Set` 只需传值 —— **原文结论成立且现已由引擎源码坐实**。
     grep 证据复核：`SetBit|GetBit` 在 `Source/UnrealCSharp/` 下 **0 命中**（原文"无命中于本目录"成立）；全 `Source/` 命中 **9** 处，但全部是 `UnrealCSharpCore` 里与位掩码无关的 `GetBitmaskAttributeClass`/`GetBitmaskEnumAttributeClass`/`GetBitflagsAttributeClass`（`FReflectionRegistry.h:598,600,602` 等），故"无手写位掩码"结论不受影响。
   - `Get` 走 `CopySingleValue`（`inl:18`），`FBoolProperty` 对 `CopyValuesInternal` 有特化处理位展开，因此**不依赖** `GetOffset_ForInternal`。
     **引擎侧已核实**：`FBoolProperty` 确实覆盖 `CopyValuesInternal`（声明 `UnrealType.h:2426`，定义 `Runtime/CoreUObject/Private/UObject/PropertyBool.cpp:422-431`），其实现按 `ByteOffset`/`FieldMask` 逐位搬运：
     ```cpp
     uint8* DestByteValue = (uint8*)Dest + Index * GetElementSize() + ByteOffset;
     uint8* SrcByteValue  = (uint8*)Src  + Index * GetElementSize() + ByteOffset;
     *DestByteValue = (*DestByteValue & ~FieldMask) | (*SrcByteValue & FieldMask);
     ```
     另：`FBoolProperty` 亦覆盖 `InitializeValueInternal`（`UnrealType.h:2428` → `PropertyBool.cpp:439-444`，只清位）与 `ClearValueInternal`（`:2427` → `:432-437`）—— 故 `FProperty::InitializeValue` 对 bool 属性走的是"清位"而不是内存清零。**原文结论成立并已坐实。**
   - **但 `Src` 的宽度是未验证假设**：`FBoolPropertyDescriptor.cpp:5` 的 `*static_cast<bool*>(Src)` 只读 1 字节。`Src` 是 C# 侧写入的 `IN_BUFFER`（`FunctionMacro.h:72`、`FRegisterProperty.cpp:35`）。若 C# 侧把 `bool` 按默认 4 字节 `BOOL` 或 1 字节 `I1` 写入，1 字节读取在**小端**下对 0/1 正确，但对非 0/1 编码（如 `0x00000100`）会读成 `false`。**需在 C# 侧核实**（列入第 10 节未覆盖项）。
5. **`FByteProperty` 带 `Enum` 时的返回值语义**：`Factory` 在 `FPropertyDescriptor.cpp:49` 先匹配 `FByteProperty`，早于 `:93` 的 `FEnumProperty`；UE 中 `TEnumAsByte` 属性就是带 `Enum` 指针的 `FByteProperty`。此时 `FBytePropertyDescriptor` 走 `TPrimitivePropertyDescriptor<FByteProperty>`，`Get`= `CopySingleValue`（原样 1 字节数值）、`Get(...,FMember/FReturn)`= `Class->BoxValue(Src)`（`inl:23,28`），其中 `Class` 来自 `FTypeBridge::GetClass(InProperty)`（`TPropertyDescriptor.inl:12`）。**返回值是 `uint8` 数值本身，不是枚举名/枚举对象**；C# 侧要拿到枚举语义依赖 `FTypeBridge::GetClass` 是否把 `Enum` 映射成了枚举类型 —— `FTypeBridge` 不在本报告覆盖范围内（列入未覆盖项）。**这是一个明确的语义分歧点**：`FEnumPropertyDescriptor`（`FPropertyDescriptor.cpp:93`）与 `FBytePropertyDescriptor`（`:49`）都能表示"C++ 枚举"，走的是两条完全不同的描述符。

## 7. 空指针与临时对象

### 7.1 `GetProperty()` 返回值检查
- `FPropertyDescriptor.inl` 中 **11 个元数据方法全部检查**（`:13,28,39,49,59,67,77,87,97`），返回 0/空值兜底；`Identical`（`cpp:182`）、`DestroyValue`（`cpp:192`）也检查。
- **`TPrimitivePropertyDescriptor<T>` 的 5 个方法全部不检查**（`inl:18,23,28,33,38,40,61,63`）：`Get`×3、`Set`、`CopyValue`（对 Property 无解引用）、`GetBufferSize`、`DestroyProperty`（有检查）。
- **`TCompoundPropertyDescriptor<T>` 同样全部不检查**（`inl:37,39,43,45`）。
- **可空性来源**：`TPropertyDescriptor.inl:10` 构造由 `PropertyMacro.h:3` 的 `CastField` 保证非空，所以**构造后立即使用是安全的**；唯一把它置空的是 `DestroyProperty`（`TPropertyDescriptor.inl:28`、`TPrimitivePropertyDescriptor.inl:54`），因此**唯一可触发的崩溃路径是 "Destroy 之后再用"**（F-PROP-001）。

### 7.2 `ContainerPtrToValuePtr` 返回值检查
`FPropertyDescriptor.inl:37-45`：有 null 检查，且 nullptr 分支返回 `decltype(...){}`（值初始化，即 `nullptr`）。**注意**：调用方直接把它当有效地址用（`FRegisterProperty.cpp:35,49`、`FunctionMacro.h:72,123,132,139,144`、`FArrayHelper.cpp:137` 等），**没有任何一处检查是否为空**；`PointerTypeDescriptor` 之外的描述符若 `GetProperty()` 为空就会返回 nullptr 并被 `Get`/`Set` 直接解引用。

### 7.3 `Get` 返回拷贝还是引用 / 悬垂风险
- `TPrimitivePropertyDescriptor<T>::Get(void* Src, void** Dest)`（`inl:16-19`）与 `Get(void* Src, void* Dest)`（`inl:31-34`）**把值拷进调用方缓冲**（`CopySingleValue`）——无悬垂。
- `Get(..., FMember)`（`inl:21-24`）/`Get(..., FReturn)`（`inl:26-29`）写回的是 `IManagedHandleToObject(Super::Class->BoxValue(Src))`——托管句柄，**生命周期由 C# GC 管理**，不在 `Src`/`Dest` 缓冲里 → 无悬垂，但要求 `Class` 非空（`Super::Class->BoxValue` 未查空；`Class` 来自 `TPropertyDescriptor.inl:12` 的 `FTypeBridge::GetClass`，**其可空性未验证**）。
- **没有发现返回局部变量引用/指针的实现**：`TPrimitivePropertyDescriptor::CopyValue` 返回的是**入参地址**（调用方拥有的活体地址，悬垂风险取决于调用方如何看待它，见 F-PROP-002）；`TCompoundPropertyDescriptor::CopyValue` 返回 `FMemory::Malloc` 的堆地址（不会悬垂，但所有权不明）。**没有一处返回函数内局部变量的地址**。
- 临时对象：`FPropertyDescriptor.inl:44` 的 `decltype(std::declval<FProperty*>()->ContainerPtrToValuePtr<ValueType>(ContainerPtr, ArrayIndex)){}` 是模板元编程表达式（不求值），不产生运行时临时对象。

## 8. 重复代码与模板化合并方案

**先说结论：任务简报里假设的"11 个 Primitive 描述符几乎复制粘贴"在当前代码中已经不存在**。真实状态：

| 项 | 现状 | 合并空间 |
|---|---|---|
| 11 个 `Get`/`Set`/`CopyValue`/`GetBufferSize` | **已被 `TPrimitivePropertyDescriptor<T>` 统一**（`TPrimitivePropertyDescriptor.inl`，66 行覆盖 10 个类） | 已合并，无需再合并 |
| 10 个 `.h` | 各 9 行的空派生声明 | 可用宏再压缩（见下），收益小 |
| 10 个 `.cpp` | 各 1 行的 self-include | **可直接删除**（F-PROP-005） |
| `DestroyProperty` | `TPropertyDescriptor.inl:22` 与 `TPrimitivePropertyDescriptor.inl:48` 重复 | 删除后者（F-PROP-006） |
| `Set` 实现 | 模板一份 + `FBoolPropertyDescriptor.cpp` 一份，步骤分叉 | 抽公共 `SetValueInternal`（F-PROP-003） |
| `GetBufferSize` 的 `#if UE_F_PROPERTY_GET_ELEMENT_SIZE` 块 | 在 `FPropertyDescriptor.inl:16-20`、`TPrimitivePropertyDescriptor.inl:60-64`、`TCompoundPropertyDescriptor.inl:36-40` **各写一遍**（3 份） | 已在基类有 `GetElementSize()`！三处应统一改成调用 `this->GetElementSize()`（它自带 null 检查） |

**推荐的具体合并方案（按收益排序）**

1. **（收益最高、风险最低）三处 `GetElementSize/ElementSize` 的 `#if` 复制改为复用基类方法**
```cpp
// 三处统一为：

{
	if (const auto Property = GetProperty()) { return Property->GetElementSize(); }
	return 0;
}

// TPrimitivePropertyDescriptor.inl:58
virtual auto GetBufferSize() const -> int32 override { return this->GetElementSize(); }

// TCompoundPropertyDescriptor.inl:35（Malloc 与 :37）同样改用 this->GetElementSize()
```
删掉 3 份 `#if UE_F_PROPERTY_GET_ELEMENT_SIZE` 分支（共 6 个编译分支），并**顺带修掉 F-PROP-001 的空指针问题**（基类方法已查空）。风险：`GetElementSize()` 是虚函数（`FPropertyDescriptor.h:54` 非 virtual，实为 `FORCEINLINE`，不虚）——**无虚调用开销**；`TCompoundPropertyDescriptor.inl:35` 位于 `FMemory::Malloc` 参数里，改为 `this->GetElementSize()` 后语义不变。

2. **（收益中、风险低）删除 10 个空 `.cpp` + `TPrimitivePropertyDescriptor::DestroyProperty` 重复实现**（F-PROP-005/006）。零行为变更。

3. **（收益中、风险中）用宏压缩 10 个空 `.h`**——若目标是继续减少文件数：
```cpp
// PrimitivePropertyDescriptions.h（新增，替代 10 个 .h）
#define UE_CSHARP_PRIMITIVE_PROPERTY_DESCRIPTOR(PropertyType)                       \
	class PropertyType##Descriptor final : public TPrimitivePropertyDescriptor<PropertyType> \
	{                                                                              \
	public:                                                                        \
		using TPrimitivePropertyDescriptor::TPrimitivePropertyDescriptor;           \

```
**收益**：10 个文件 → 1 个；`FPropertyDescriptor.cpp:3-12,37` 的 11 行 include 与 `.cpp` 同步消失。
**风险/成本**：① 破坏"类名 = 文件名"的可发现性（IDE 里 `Go to file` 找不到 `FBytePropertyDescriptor.h`）；② 宏内的类定义不能加断点、部分静态分析/IntelliSense 对宏展开类的支持差；③ **收益仅 9 行/文件**，与阅读成本不成比例。**我的建议是不做**——当前 9 行空派生类是"零成本命名锚点"，删除 `.cpp`（方案 2）才是真正的净收益。

4. **（收益高、风险中）不建议**把 `FBoolPropertyDescriptor` 合并进模板（例如给 `TPrimitivePropertyDescriptor` 加 `if constexpr (std::is_same_v<T, FBoolProperty>)` 分支）。`SetPropertyValue` 与 `CopySingleValue` 的语义差异是**真实的类型差异**，用 `if constexpr` 会把位存储的特殊性藏进模板，反而降低可读性。保持独立覆盖，但**共享 `Set` 的前置/后置步骤**（方案见 F-PROP-003）。
