## 1. 模块职责与架构速览

### 1.1 六个注册表的分工

`FCSharpEnvironment`（`FCSharpEnvironment.h:334-354`，13 个裸指针成员：`Domain` + 12 个注册表，其中 `OptionalRegistry` 受 `UE_F_OPTIONAL_PROPERTY` 控制 ⇒ 默认 11 个注册表）全部在 `FCSharpEnvironment::Initialize()`（`FCSharpEnvironment.cpp:57-145`）用 `new` 创建，在 `Deinitialize()`（`:147-269`）按**固定逆序** `delete` 并置空：

```
Optional → Binding → String → Multi → Delegate → Container → Struct → Object → Reference → Class → CSharpBind → Dynamic → Domain
```
（实际顺序见 `FCSharpEnvironment.cpp:177-268`，其中包含 `Dynamic`。）

这个顺序很关键：`StructRegistry` 先于 `ReferenceRegistry` 被销毁，所以 `~FStructReference` 里回调 `RemoveStructReference` 时 `StructRegistry == nullptr`，转发层直接返回 `false`（`FCSharpEnvironment.cpp:561-564`），**析构期不会二次进入注册表**。这一点是正确的，但它是"顺序巧合"而不是设计保证（见 F-REG-005）。

| 注册表 | 键 → 值（正向） | 键 → 值（反向） | 语义 |
|---|---|---|---|
| `FObjectRegistry` | `IManagedHandle → TWeakObjectPtr<const UObject>` | `TWeakObjectPtr<const UObject> → IManagedHandle` | UE 对象 ↔ C# 包装对象（GCHandle） |
| `FStructRegistry` | `IManagedHandle → FStructAddress{结构体类型, 地址, bNeedFree}` | `FStructAddressBase{类型,地址} → IManagedHandle` | UScriptStruct 实例地址 ↔ C# 结构体包装 |
| `FMultiRegistry` | `IManagedHandle → TMultiAddress<T*, bNeedFree>`（6 组） | `void* → IManagedHandle`（6 组） | TWeakObjectPtr / TLazyObjectPtr / TSoftObjectPtr / TSubclassOf / TScriptInterface / TSoftClassPtr |
| `FClassRegistry` | `TWeakObjectPtr<const UStruct> → FClassDescriptor*` 等 7 张表 | — | 反射描述符缓存（按类/按 hash） |
| `FReferenceRegistry` | `IManagedHandle → TSet<FReference*>` | — | 拥有 `new` 出来的 `FReference` 子类对象 |
| `FDynamicRegistry` | 无表 | — | 只挂 2 个全局 hook/delegate |

### 1.2 三条核心数据流

**① C# 包装对象产生（正向注册）**

`FCSharpBind.inl:82` `FoundClass->NewObject()`（经 C# bridge 创建 C# 对象并 `HandleData.Alloc` 分配 GCHandle，见 `Script/Interop/Handle/HandleData.cs:27-44`）→ `FCSharpBind.inl:84` → `FCSharpEnvironment::AddObjectReference`（`FCSharpEnvironment.cpp:527`）→ `FObjectRegistry::AddReference`（`FObjectRegistry.cpp:72`）同时写两张表。

**② 句柄 → UE 对象（反向查找，热路径）**

C# → C++ 每次传对象：`FCSharpEnvironment.inl:51`/`:87` → `FObjectRegistry::GetAddress`（`FObjectRegistry.cpp:34`/`:41`）→ `Get()`。

**③ UE 对象销毁（反向注销）**

`GUObjectArray` 删除监听（`FUObjectListener.cpp:31` 注册、`:46-48` 转发）→ `FCSharpEnvironment::NotifyUObjectDeleted`（`FCSharpEnvironment.cpp:302`）→ `UStruct` 走 `RemoveClassDescriptor`，**其余对象走 `RemoveObjectReference`**（`:312`）→ `FObjectRegistry::RemoveReference(const UObject*)`（`FObjectRegistry.cpp:82`）。

### 1.3 引用（FReference）体系

`FStructReference` / `FBindingReference` / `TContainerReference<T>` / `TDelegateReference<T>` 都是 `FReference` 的子类，构造时只存一个 `IManagedHandle`（`FReference.h:8-11`），**析构时反向调用对应注册表的 `RemoveReference`**：

- `FStructReference.h:14` → `RemoveStructReference(ManagedHandle)`
- `FBindingReference.h:14` → `RemoveBindingReference(ManagedHandle)`
- `TContainerReference.h:15` → `RemoveContainerReference<T>(ManagedHandle)`
- `TDelegateReference.h:15` → `RemoveDelegateReference<T>(ManagedHandle)`

所有权归 `FReferenceRegistry`（`new` 于 `FStructRegistry.cpp:105`、`FBindingRegistry.inl:37` 等），由 `FReferenceRegistry::RemoveReference` 或析构函数 `delete`（`FReferenceRegistry.cpp:13`、`:50`）。**这是一个"删除引用会触发注册表二次删除"的重入设计**，是 F-REG-005 的根因。

## 3. 发现清单

> **排序说明（复核后）**：Finding 编号是跨报告引用锚点，**编号与物理顺序保持稳定不变**；下表分组标题后的括号给出该组**复核后的实际级别构成**。全报告复核后：P0 **0** / P1 **6**（F-REG-001/002/003/004/007/009）/ P2 **2**（F-REG-005/010）/ P3 **10**（F-REG-006/008/011..018）。

### 原 P0 组（复核后：本组无 P0；F-REG-001 = P1）

### [F-REG-001] `FObjectRegistry::RemoveReference(const UObject*)` 在 `TMap::Remove` 之后继续解引用已失效的元素指针，导致释放/注销**另一个对象**的 GCHandle 与引用集合

- **类别**: 未定义行为 / 内存/资源泄漏 / 数据损坏
- **严重度**: **P1**(功能错误：释放/注销**另一个存活对象**的句柄与引用集合)
- **复核结论**: 部分确认（偏差：**P2 定级偏低** —— 机制与全部代码事实成立；但触发不是"隐患"而是**高频必然**：只要 `Object2ManagedHandle` 有 ≥2 个条目且被删条目不在元素数组末位（运行期常态），`:88/:90/:92` 读到的就是**另一条存活条目**的句柄，属于确定性功能错误，故回到 P1；不判 P0 是因为它不写出界、不释放内存，无必然崩溃）
- **可达性**: 活跃
- **复核证据**: `Source/UnrealCSharp/Private/Registry/FObjectRegistry.cpp:82-98` 逐字复核一致；唯一调用者 `FCSharpEnvironment.cpp:538-541`（`:540` 调用 `ObjectRegistry->RemoveReference(InObject)`），其调用者 `FCSharpEnvironment.cpp:302-321`（`:312`），监听器注册在 `FUObjectListener.cpp:29-31`（`:31` `AddUObjectDeleteListener`）、转发在 `:46-49`。**引擎契约证据（强）**：`Runtime/Core/Public/Containers/Map.h:564-565` 文档明写 `Find` 返回的指针 *"is only valid until the next change to any key in the map"*，`Map.h:567-575` 实现为 `return &Pair->Value;`；`Map.h:493-497` `Remove` → `Pairs.Remove(InKey)`；`Set.h:888-918` `RemoveImpl` → `:902 RemoveByIndex`；`Set.h:719-743` `RemoveByIndex` → `:743 Elements.RemoveAt(ElementIndex)`（前移压缩）
- **级别变动**: P2→P1（理由：被删条目不在数组末位时读写的是另一活动对象的句柄，属确定性功能错误而非潜在隐患；原 P0→P2 的降幅过大）
- **文件**: `Source/UnrealCSharp/Private/Registry/FObjectRegistry.cpp:82-98`（失效读发生在 `:88`、`:90`、`:92`，回溯到 `:84` 与 `:86`）
- **函数**: `FObjectRegistry::RemoveReference(const UObject* InObject)`
- **置信度**: 高（容器语义已用本机引擎源码 `Set.h:719-744`、`Map.h:495` 核实；唯一不确定项是该错误句柄在 C# 侧的具体后果，已在"问题"里分档说明）

**现状（代码事实）**

```cpp

{
	if (const auto FoundManagedHandle = Object2ManagedHandle.Find(InObject))   // :84
```

**调用上下文**

唯一调用者：`FCSharpEnvironment::NotifyUObjectDeleted`（`FCSharpEnvironment.cpp:302-321`，`:312` 调用 `RemoveObjectReference(InObject)`）→ `FCSharpEnvironment.cpp:538-541` → 本函数。
`NotifyUObjectDeleted` 由 `FUObjectListener::NotifyUObjectDeleted`（`FUObjectListener.cpp:46-48`）转发，而监听器通过 `GUObjectArray.AddUObjectDeleteListener(this)` 注册（`FUObjectListener.cpp:31`），因此**每一个非 UStruct 的 UObject 销毁都会走这条路径**。另一条经句柄的删除入口已经死掉（见 §4：`FCSharpEnvironment::RemoveObjectReference(const IManagedHandle)` 无任何调用点），所以本函数是对象句柄唯一的正常注销路径。

生命周期阶段：游戏运行期任意时刻（GC、`Destroy()`、世界切换、编辑器 PIE 结束）；线程见 F-REG-008。

**问题**

1. `:86` 的 `Remove` 使 `:84` 得到的指针失效；`:88/:90/:92` 读到的是**相邻条目**的 `IManagedHandle`。`Object2ManagedHandle` 只要有 ≥2 个条目且被删条目不在末尾（实际工程的常态），读到的就是另一个存活对象的句柄。
2. 由此产生的连锁后果（按可观测性排序）：
   - `:88` 把**另一个对象**的 `handle → UObject` 条目删掉 ⇒ 该对象的句柄后在 C# 侧仍可用，但 `GetAddress/GetObject(handle)` 返回 `nullptr`（`FObjectRegistry.cpp:34-51`），C# 侧后续对该对象的任何调用都拿到空对象。
   - `:90` 对**别人的句柄**调用 `GCHandle_Free` ⇒ C# `HandleData.FreeImplementation`（`HandleData.cs:46-78`）把该句柄的引用计数减一；降到 0 时 `OutHandle.Free()` 真正释放 `GCHandle`，于是那个 C# 包装对象可被 GC 回收，而 C++ 侧的映射仍然指向它的句柄 ⇒ 之后 `HandleData.GetObject(handle)`（`HandleData.cs:95-106`）返回 `null`，托管侧拿到空对象。
   - `:92` 对**别人的 owner 句柄**调用 `FCSharpEnvironment::RemoveReference` ⇒ `FReferenceRegistry::RemoveReference` 把该 owner 名下所有 `FReference` 全部 `delete`（`FReferenceRegistry.cpp:48-51`），而每个析构又回调 `RemoveStructReference/RemoveContainerReference/...`，把该对象的结构体/容器/委托引用对象与堆内存一起释放（`FStructRegistry.cpp:126-139`）——这些对象可能仍被 C# 引用。

3. 该函数是"删除时顺便清理"，在没有异常/断言的情况下静默完成，因此现场表现为：随运行时间累积的托管内存增长 + 随机出现的"某个对象突然变成 null" + 稀疏的崩溃，极难复现定位。

**建议**

```cpp
void FObjectRegistry::Deinitialize()
{
	TArray<IManagedHandle> Handles;
	Handles.Reserve(ManagedHandle2Object.Get().Num());
	for (const auto& [Key, Value] : ManagedHandle2Object.Get())
	{
		Handles.Add(Key);
	}

	ManagedHandle2Object.Empty();      // 先清表（保持迭代安全）
	Object2ManagedHandle.Empty();

	for (const auto Handle : Handles)
	{
		FDomain::GCHandle_Free(Handle);
	}
}
```

（若确实需要"二次进入不重复释放"的语义，用一个 `bool bDeinitialized` 或把指针置空来表达，而不是破坏容器键。）
