## 1. 模块职责与架构速览

### 1.1 三层结构

```
C# 侧包装对象 (TArray<T>/TMap/TSet/FString/Script.Delegate…)
   │  构造：TArrayImplementation.TArray_RegisterImplementation(this, GetType())
   │        → HandleData.Alloc(InArray) + HandleData.Alloc(InType)   ← 两个 GCHandle（强）
   │  析构：~TArray() → TArray_UnRegisterImplementation(HandleData.GetHandle(this))
   ▼  P/Invoke
FRegisterArray / FRegisterString / FRegisterDelegate / FRegisterMulticastDelegate (Private/Domain/Interop)
   ▼
FCSharpBind::BindImplementation<T>()                    (Public/Registry/FCSharpBind.inl)
   ▼
FContainerRegistry / FDelegateRegistry / FStringRegistry / FOptionalRegistry   ← 本人负责
   · ManagedHandle2Value : TMap<IManagedHandle, Helper*>          （handle → native helper，拥有指针）
   · Address2ManagedHandle : TMap<void* /*address*/, IManagedHandle>
   ▼  owner 重载时额外注册
FCSharpEnvironment::AddReference(InOwner, new TContainerReference<T>(handle))
   ▼
FReferenceRegistry::ReferenceRelationship : TMap<IManagedHandle /*owner*/, TSet<FReference*>>
   · owner 的 managed handle 消失 → 删除全部 FReference → FReference 析构 → RemoveXxxReference(handle)
```

### 1.2 生命周期关键事实（都有证据）

1. **native 缓冲谁分配**：容器 helper 由 native `new`（`FCSharpBind.inl:97/117/127`、`FArrayPropertyDescriptor.cpp:39/56`）；helper 内部若 `InData==nullptr` 则 `new FScriptArray()`，否则**别名** `InData`（`FArrayHelper.cpp:13-20`）——注意结论：`FReturn` 路径传入的 `InData` 是 `FPropertyDescriptor::CopyValue()` 的**独立堆拷贝**（`TCompoundPropertyDescriptor.inl:33-48`），不是 UObject 属性地址，因此那个 `delete` 是合法释放（详见 F-REG2-001 的撤销说明）。
2. **谁释放**：只有两条路——(a) `FXxxRegistry::RemoveReference(handle)`（`delete helper` + `FDomain::GCHandle_Free`）；(b) 注册表析构时的 `Deinitialize()` 全量清理（`FContainerRegistry.cpp:18-73` 等）。**没有**任何"引用计数/弱引用"机制：`ManagedHandle2Value` 是**裸指针拥有型** `TMap<IManagedHandle, Helper*>`（`TValueMapping.inl:12` → `TManagedHandleMapping.inl:7` → `TMapping.inl:54` 的私有裸 `TMap`）。
3. **谁触发 RemoveReference**：
   - owner-UObject 销毁：`FUObjectListener::NotifyUObjectDeleted` → `FCSharpEnvironment::NotifyUObjectDeleted` → `FObjectRegistry::RemoveReference(UObject*)`（`FObjectRegistry.cpp:82-98`）→ `FCSharpEnvironment::RemoveReference(ownerHandle)`（`FObjectRegistry.cpp:92`）→ `FReferenceRegistry::RemoveReference` 删除 `TContainerReference`/`TDelegateReference` → 各自的 `~FReference` 调用 `RemoveContainerReference<T>` / `RemoveDelegateReference<T>`（`TContainerReference.h:15`、`TDelegateReference.h:15`）。
   - C# 包装对象终结器：`~TArray()`/`~TMap()`/`~TSet()`/生成委托类的 `~Xxx()` → `*_UnRegisterImplementation` → `AsyncTask(GameThread, RemoveXxxReference)`。
   - `FCSharpEnvironment::Deinitialize()`（模块 Shutdown / 热重载）。
4. **`HandleData.Alloc` 用的是强 GCHandle**：`HandleData.cs:39` `GCHandle.Alloc(InObject, bPinned ? Pinned : GCHandleType.Normal)`，并放进静态 `Handles` 字典（`HandleData.cs:11/38`）。→ **被 Alloc 过的 C# 对象是 GC root，永远不会被回收，其终结器永远不会执行**。这一点直接决定了下面 F-REG2-002 的成立。
5. **native 创建包装对象时不走 C# 构造函数**：`ObjectBridge.cs:14` `RuntimeHelpers.GetUninitializedObject(Type)`。所以 native 侧 `Class->NewObject()` 造出来的包装对象**不会**执行 `TArray<T>()` 里的 Register，只由 native 显式 `AddContainerReference` 注册。

### [F-REG2-001] ~~`NewWeakRef(bIsCopy=true)` 把 UObject 属性内存当作 `new` 出来的对象 `delete`，堆损坏~~ → **已证伪撤销**

- **类别**: ~~未定义行为 / Bug~~ → 无（撤销）
- **严重度**: **撤销（非缺陷）**
- **复核结论**: **证伪（撤销，非缺陷）** —— 原主张的前提不成立。`FPropertyArgument::FReturn` 路径的 `Src` **不是** UObject 属性地址，而是 `CopyValue()` 返回的 `FMemory::Malloc` 深拷贝（`TCompoundPropertyDescriptor.inl:35-47` + `PropertyArray.cpp:1150-1182`），helper 取所有权（`bIsCopy → bNeedFreeData=true`）正是设计意图；`delete` 与 `FMemory::Malloc` 在 UE 下**同源**（`ModuleBoilerplate.h:49-73` 的 `REPLACEMENT_OPERATOR_NEW_AND_DELETE`），且 `delete ScriptArray` 会经 `~FScriptArray` → `ForAnyElementType::~ForAnyElementType` 释放元素缓冲（`ScriptArray.h:18-20`、`ContainerAllocationPolicies.h:492-502`），因此**既无堆损坏也无容器缓冲泄漏**

**问题（修正：原判断被证伪）**
原报告认为 `InbNeedFreeData==true` 时 `ScriptArray` 是"UObject 的属性存储或 `FunctionMacro` 栈上的返回值缓冲"，于是 `delete ScriptArray` 会 `delete` 一个非 `new` 指针 → 堆损坏。**这条推理链在源码与引擎两侧都不成立**：
1. `FunctionMacro.h:128-130 / 143-145` 传给 `Get<FReturn>` 的第一实参是 `CopyValue(...)`，而 `FArrayPropertyDescriptor` 派生自 `TCompoundPropertyDescriptor`（`FArrayPropertyDescriptor.h:5`），其 `CopyValue`（`TCompoundPropertyDescriptor.inl:33-48`）返回的是 `FMemory::Malloc(Property->GetElementSize())` 出来的**新堆块**，并已 `InitializeValue` + `CopySingleValue` 完成初始化。
2. `FArrayProperty::CopyValuesInternal`（引擎 `PropertyArray.cpp:1150-1182`）执行的是**深拷贝**（`DestArrayHelper.EmptyAndAddValues(Num)` 重新分配元素缓冲），所以不存在"与 UObject 属性共享内存"的问题。
3. UE 的全局 `operator new/delete` 被 `REPLACEMENT_OPERATOR_NEW_AND_DELETE` 重定向到 `FMemory::Malloc/Free`（`ModuleBoilerplate.h:49-73`，由 UBT 生成的 `PerModuleInline.gen.cpp` 引入，见 `UEBuildModuleCPP.cs:732-751`），故 `FMemory::Malloc` 出来的块用 `delete` 释放**同分配器、合法**。
4. `delete ScriptArray` 还会经 `FScriptArray : TScriptArray<FHeapAllocator> : ForAnyElementType`（`ScriptArray.h:18-20`）调用 `~ForAnyElementType`，其析构体 `FMemory::Free(Data)`（`ContainerAllocationPolicies.h:492-502`）会把元素缓冲一并释放，因此连"容器缓冲泄漏"也不成立。
唯一真实残留见上方"残余事实"（元素**析构函数**未被调用 → 元素内部堆数据泄漏），那是另一种（更轻的）问题，不能支撑原 P0 定级。
对比 TPropertyValue 里的**正确**用法：`Binding/Core/TPropertyValue.inl:858` `new FArrayHelper(Property, new std::decay_t<T>(*InMember), true, true)` —— 那里 `InData` 确实是 `new` 出来的拷贝，`bNeedFreeData=true` 才成立。

```csharp
// (3) C#：不要依赖终结器。要么改用 GCHandleType.Weak（让对象可回收、终结器可运行），
//     要么提供一个显式 Dispose/using 路径并在 TArray<T>/生成委托类上实现 IDisposable，
```
