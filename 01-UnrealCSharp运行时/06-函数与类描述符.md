## 1. 模块职责与架构速览

这一组文件是 **C++ ↔ C# 函数互调的中枢**：所有跨语言函数调用最终都要在这里完成「参数内存的分配 → 从 C# 缓冲搬入 `FProperty` 值 → 调用 UE/C# → 把 out/返回值搬回 C# 缓冲 → 释放参数内存」这一循环。

### 1.1 四个描述符子类与各自的数据流

```
                    FFunctionDescriptor (基类, 持有 TWeakObjectPtr<UFunction> Function)
                    ├─ PropertyDescriptors : TArray<FPropertyDescriptor*>   // 非返回值的全部 CPF_Parm
                    ├─ ReturnPropertyDescriptor                              // CPF_ReturnParm
                    ├─ ReferencePropertyIndexes / OutPropertyIndexes          // 参数索引集合
                    └─ BufferAllocator : TSharedPtr<FFunctionParamBufferAllocator>
                              │
     ┌────────────────────────┼─────────────────────────────┬───────────────────────────┐
     │                        │                             │                           │
FUnrealFunctionDescriptor  FCSharpFunctionDescriptor     FCSharpDelegateDescriptor   (FManagedFunctionDescriptor
(调用 UE 函数)              (UE 调 C#，execCallCSharp)      (C# 委托调 C# 方法)          为二者共用的基类)
PoolBufferAllocator        PoolBufferAllocator           PersistentBufferAllocator
Call0..Call26              CallCSharp(FFrame&)           Execute0/1/2/3/4/6/7
                                                          Broadcast0/2/4/6
```

- **`FUnrealFunctionDescriptor`（`Call0`–`Call26`）**：`FRegisterFunction.cpp` 里 25 个 `*Implementation` 静态函数按「有无 in/out/返回值 + 返回类型是 Primitive 还是 Compound」编号选择 `CallN`。方法内部走 `UObject::ProcessEvent`（`Call0`–`Call7`）或 `UFunction::Invoke` + `FFrame`（`Call8`–`Call15`）；`Call16/18/24/26` 是 RPC 版本，用 `GetFunctionCallspace` 在 `ProcessEvent` 与 `CallRemoteFunction` 之间二选一。
- **`FManagedFunctionDescriptor::Invoke`**：C# 侧函数的统一调用内核。把 `PropertyDescriptors` 逐个转成 `CSharpParams`（primitive 直接传地址；compound 传 `IManagedHandle*`），调用 `FMethodReflection::Runtime_Invoke`，再把返回值和 out 参数写回。
- **`FCSharpFunctionDescriptor`**：UE 的 `UFunction`（native func 被替换为 `UCSharpFunction::execCallCSharp`）被 C# 覆写时使用。`CallCSharp` 负责**在字节码栈上手工重建参数帧**（`InStack.Step` + `FOutParmRec` 链表），是所有路径里唯一显式做了 `DestructorLink` 销毁的。
- **`FCSharpDelegateDescriptor`**：`UDelegateHandler` / `UMulticastDelegateHandler` 的 `ProcessEvent` 里当函数名是 `CSharpCallBack` 时被调用。
- **`FClassDescriptor`**：`UStruct* → FClassReflection* + FunctionHashSet + PropertyHashSet` 的桥。它**不拥有**描述符（描述符由 `FClassRegistry` 的两个 `TMap<uint32, T*>` 拥有），只持有 `TSet<uint32>` 哈希集用于自己的 `Deinitialize` 反向清理。
- **`FClassRegistry`** 用 `GetTypeHash(UFunction*)`（= 指针哈希）作为 `UnrealFunctionDescriptorMap` / `CSharpFunctionDescriptorMap` 的键（`FClassRegistry.h:66,68`）。

### 1.2 生命周期

- 创建：`FCSharpBind::BindImplementation` → `AddFunctionHash<T>(hash, classDescriptor, function, [register])` 存入 `*FunctionHashMap`（**惰性**，此时不创建描述符）→ 第一次真正被调用时 `FClassRegistry::GetOrAddFunctionDescriptor<T>` 才 `AddFunctionDescriptor<T>` → `new T(...)` → 移入 `*DescriptorMap`（`FClassRegistry.inl:35–64`）。
- 销毁：`FCSharpEnvironment::NotifyUObjectDeleted`（`FCSharpEnvironment.cpp:302–321`）—— **`UStruct` 走 `RemoveClassDescriptor`，其它 UObject 走 `RemoveObjectReference`**；⚠️ **修正**：`UFunction` 派生自 `UStruct`（引擎 `Runtime\CoreUObject\Public\UObject\Class.h:2021 class UFunction : public UStruct`），因此 **`UFunction` 也走 `RemoveClassDescriptor` 分支** ——但由于 `UFunction` 从不进入 `ClassDescriptorMap`，该调用实际是**空操作**，函数级描述符表不会因此收缩（详见 F-FN-008）。`FClassRegistry::Deinitialize`（`FClassRegistry.cpp:23-81`）统一 delete 全部描述符。
- `FCSharpFunctionRegister` 是"覆写函数"的看护者：析构时恢复原函数的 `FunctionFlags`/`NativeFunc` 并把动态创建的坑函数从 `Class->FunctionMap` 摘掉（`FCSharpFunctionRegister.cpp:29–71`）。

## 3. 发现清单

### P1

### [F-FN-001] 参数缓冲池复用时既不清零也不析构参数值，销毁时直接 `FMemory::Free`，非平凡类型（FString/FText/TArray/TSet/TMap/对象引用）的内部堆内存永久泄漏

- **类别**: 内存/资源泄漏
- **严重度**: **P1**
- **复核结论**: 确认（代码事实、调用上下文、类别、严重度全部成立；标注的"引擎行为未验证"已由引擎源码核销）
- **可达性**: 活跃（`FUnrealFunctionDescriptor::Call2/3/6/7/10/11/14/15` 与全部 `Execute*/Broadcast*` 都在 C#↔UE 热路径上；五平台 LeanCLR 全部参与编译）
- **复核证据**: 插件侧 —— `Source/UnrealCSharp/Private/Reflection/Function/FFunctionParamBufferAllocator.cpp:27-33`（`~FFunctionParamPoolBufferAllocator` 只 `FMemory::Free(Buffer)`，`:31`）、`:58-74`（Persistent 同，`:70`）；`:35-51` 复用分支（`:39 return Buffers[Count++];`）无 `Memzero`/无析构；`:53-56` `Free(void*)` 只有 `Count--`；`:81-83` Persistent `Free` 空实现。grep `DestroyValue_InContainer`（工具 grep，`Source/**/*.cpp`）**命中 1 次**：`FCSharpFunctionDescriptor.cpp:134` —— 全库唯一显式析构点。**引擎侧（`Engine\Source`）**：`Runtime\CoreUObject\Private\UObject\ScriptCore.cpp:2032-2232` 的 `UObject::ProcessEvent`：`:2150 FMemory::Memcpy(Frame, Parms, Function->ParmsSize);`（参数被**浅位拷贝**进引擎自建的 `UE_VSTACK_ALLOC` 帧，引擎不接管调用方 `Parms` 的所有权）；收尾循环 `:2211-2226` 只对"不落在 `ParmsSize` 区间内"的属性执行 `:2219 P->DestroyValue_InContainer(NewStack.Locals)`，而对 `ParmsSize` 区间内的非 out 属性执行的是 `:2223 FMemory::Memcpy(P->ContainerPtrToValuePtr<uint8>(Parms), P->ContainerPtrToValuePtr<uint8>(NewStack.Locals), P->ArrayDim * P->GetElementSize());` —— **把已构造的值拷回调用方的 `Parms`**，`:2214` 注释原文：*"also copy back constructed value parms here so the correct copy is destroyed when the event function returns"*。即引擎**刻意把析构责任留给调用方**。同一文件另一条脚本执行路径的收尾给出**同向佐证**：`ScriptCore.cpp:1070-1080`（`if (!bUsePersistentFrame)` … `:1073 for (FProperty* Destruct = Function->DestructorLink; …)` / `:1077 Destruct->DestroyValue_InContainer(NewStack.Locals);`），其 `:1072` 注释原文：*"destruct properties on the stack, except for out params since we know we didn't use that memory"* —— **两条路径都只析构 `NewStack.Locals`（引擎自己的帧），从不触碰调用方传入的缓冲**。故的"二难论证"已裁决：**泄漏成立**，`FCSharpFunctionDescriptor.cpp:134` 的手动析构是**正确写法**而非二次析构。
- **级别变动**: 无（P1 维持）
- **函数**: `FFunctionParamPoolBufferAllocator::~FFunctionParamPoolBufferAllocator()`、`FFunctionParamPoolBufferAllocator::Malloc()`、`FFunctionParamPoolBufferAllocator::Free(void*)`、`FFunctionParamPersistentBufferAllocator::~FFunctionParamPersistentBufferAllocator()`
- **置信度**: 高（对"从不析构"这一事实为高；对"泄漏量级"取决于实际参数类型，见下文未验证假设）

**调用上下文**

分配/释放点的全部调用方：
- `FUnrealFunctionDescriptor.cpp:5`（`Factory<FFunctionParamPoolBufferAllocator>`）→ `FUnrealFunctionDescriptor.inl:15,25,35,47,57,69,82,104,116,128,142,157,192,239` 共 14 处 `Malloc`，释放只在 `FunctionMacro.h:147`（`PROCESS_RETURN`）与 `FUnrealFunctionDescriptor.inl:213,260`。
- `FCSharpFunctionDescriptor.cpp:9`（同一 Pool 分配器）→ `FCSharpFunctionDescriptor.cpp:34` `Malloc` / `:138` `Free`（这一对是配平的，且带手动析构）。
- `FCSharpDelegateDescriptor.cpp:6`（`Factory<FFunctionParamPersistentBufferAllocator>`）→ `.inl` 中 11 处 `Malloc`，`Free` 是空实现。
- 参数值的写入点：`FunctionMacro.h:65-92`（`INITIALIZE_VALUE()` → `PropertyDescriptor->InitializeValue_InContainer(Params)` 然后 `Set(IN_BUFFER, ...)`）。

**问题**

三重叠加，任何一条单独看都足以构成泄漏：

1. **复用分支不析构**。`Malloc` 的复用分支（`:37-40`）把上一次调用遗留在缓冲里的 `FString`/`FText`/`TArray`/`TSet`/`TMap`/`FName`（`FName` 是全局部表引用，不泄漏堆但语义仍需初始化）直接交给调用方；`FunctionMacro.h:69` 的 `InitializeValue_InContainer` 会对同一块内存做 placement-new 式重新初始化，**旧值的析构函数永远不被调用**，其内部堆分配（如 `FString` 的字符缓冲、`TArray` 的元素缓冲）就此丢失。UE 的 `FProperty::InitializeValue` 契约是"只能作用于未初始化内存"，`DestroyValue` 必须先行。
2. **销毁时不析构**。描述符析构（`:27-33`、`:66-74`）时缓冲里很可能还留着最后一次调用的参数值（因为 `Free` 不回退内容、`ProcessEvent` 也不销毁调用方提供的 `Parms`），此时 `FMemory::Free` 直接丢掉整块内存 —— 里面的每个非平凡参数值都泄漏。
3. **Persistent 变体把 1+2 放大到极致**：整个 `FCSharpDelegateDescriptor` 一生只有一块 `Params`（`:61`），只在构造时 `Memzero` 一次（`:63`），`Free` 是空函数（`:81-83`）。任何一次 `Execute2/4/6`、`Broadcast2/4/6` 之后留在里面的字符串/数组内部堆，都会在下一次调用被 `InitializeValue_InContainer` 覆盖时泄漏，直到描述符析构再泄漏最后一代。

**建议**

把"清零/析构"的责任从调用点收回到分配器，最省事且与现有 `FCSharpFunctionDescriptor.cpp:126-139` 的写法一致：

```cpp
// FFunctionParamBufferAllocator.h：给分配器一个"按函数析构"的回调
class FFunctionParamBufferAllocator
{
public:
    // 由 FFunctionDescriptor 构造时注入：遍历 Function->DestructorLink 销毁非 OutParm 值
    void SetDestructor(TFunctionRef<void(void*)> InDestructor) { Destructor = InDestructor; }
protected:
    TFunctionRef<void(void*)> Destructor;   // 注意生命周期：应为 TFunction（值捕获）而非 TFunctionRef
};

void FFunctionParamPoolBufferAllocator::Free(void* InMemory)
{
    if (Destructor) { Destructor(Buffers[Count - 1]); }   // 只析构最上面那一块
    Count--;
}

FFunctionParamPoolBufferAllocator::~FFunctionParamPoolBufferAllocator()
{
    for (int32 Index = 0; Index < Count; ++Index) { if (Destructor) Destructor(Buffers[Index]); }
    // 更保守：对全部 Buffers 析构（未配平释放过的块内容可能仍存活）
    for (const auto Buffer : Buffers) { FMemory::Free(Buffer); }
}
```

`Destructor` 的实现可以直接复用 `Function->DestructorLink` 循环（与 `FCSharpFunctionDescriptor.cpp:128-136` 完全相同）。`FUnrealFunctionDescriptor`/`FCSharpDelegateDescriptor` 的 18+11 个调用点则无需改动 —— 把析构放进分配器还能顺带覆盖 F-FN-002 的漏 Free 路径。

**验证方式**

1. 在 `FMemory::Malloc` 处记录 `ParamSize` 与调用栈，用 `-trace=memory` 或 `MallocLeakDetection` 跑一次"每帧调用一个带 `FString` 参数的蓝图函数"的用例（例如蓝图函数 `SetName(FString)`），观察 `FString` 的 `Data` 分配次数与释放次数比值是否随帧数线性增长。

- **严重度**: **P2**

**现状（代码事实）**

释放动作只存在于 `PROCESS_RETURN()` 宏的末尾和两处手写 `Free`：

```cpp

	if constexpr (ReturnType == EFunctionReturnType::Primitive) \
	{ \
		ReturnPropertyDescriptor->Get(...); \
	} \
	else if constexpr (ReturnType == EFunctionReturnType::Compound) \
	{ \
		... \
	} \
	BufferAllocator->Free(Params);      // ← 唯一的自动释放点
```

于是"有返回值"的路径配平，**"无返回值"的路径全部漏释放**：

```cpp
// FUnrealFunctionDescriptor.inl:22-30   Call2 = 纯 IN，无返回值 → 漏 Free

{
```

**调用上下文**

这 11 个 `CallN` 是**最常被调用的形态**：`Call2` 对应"有入参、无返回值"的 UE 函数（C# 侧 `SetXxx(...)` 全是这种），`Call4` 对应"只有 out 参数"的函数（如 `GetAllActorsOfClass` 风格）。调用方：`FRegisterFunction.cpp:58`（`GenericCall2Implementation`）、`:99`（`Call4`）、`:140`（`Call6`）、`:222`（`Call10`）、`:263`（`Call14`）；委托侧：`DelegateHandler.h:79,109,124`、`MulticastDelegateHandler.h:70,85,100`。

**问题**

- 对 Pool 分配器，`Malloc` 的复用以 `Count` 为游标（`FFunctionParamBufferAllocator.cpp:37`）。**从不 `Free` ⇒ `Count` 单调递增**（`uint8`，256 次后回绕），因此：
  - 前 256 次调用每次都走"新分配"分支，`Buffers` 增长到 256 个条目 —— **每个描述符常驻 256 × `ParmsSize` 字节且永不释放**（只有描述符析构才 `FMemory::Free`）。`ParmsSize` 大的函数（带大结构体参数）可达数十 KB，256 倍即数 MB/描述符。
  - 第 257 次调用起 `Count` 回绕，`Malloc` 开始返回 255 次调用前的那块缓冲（见 F-FN-006），此时每 256 次调用就会把一整代未析构的参数值交给 `InitializeValue_InContainer` 覆盖 —— 泄漏从"复用即泄"变成"跨代残留"，且更难复现。
- 对 Persistent 分配器，`Free` 本身是空实现（`FFunctionParamBufferAllocator.cpp:81-83`），因此漏 `Free` **不额外泄漏**，但 `Malloc` 恒返回同一块缓冲（`:76-79`），语义与 Pool 完全不同 —— 两类描述符共用同一套宏、同一套"要不要 Free"的疑问，是**接口设计缺陷**：分配器没有表达"谁来负责回收"的能力，只能靠调用点自觉。
- 由于 `Count` 不回退，池的"池化复用"设计意图在 11/29 个调用点上完全失效（只做到了上限 256 的缓存）。

**建议**

1. 最小改动：把释放收进宏，让所有调用点自动配平 —— 在 `FunctionMacro.h` 增加
   ```cpp
   #define PROCESS_FREE() if (Params != nullptr) { BufferAllocator->Free(Params); }
   ```
   并追加到 `Call2/4/6/10/14` 与 `Execute2/4/6`、`Broadcast2/4/6` 末尾。
2. 更稳的改法：改用 RAII 守卫，让"忘记 Free"在编译期就不可能发生：
   ```cpp
   struct FParamBufferScope
   {
       FParamBufferScope(const TSharedPtr<FFunctionParamBufferAllocator>& InAlloc)
           : Allocator(InAlloc), Params(InAlloc.IsValid() ? InAlloc->Malloc() : nullptr) {}
       ~FParamBufferScope() { if (Params) Allocator->Free(Params); }
       void* Get() const { return Params; }
   private:
       TSharedPtr<FFunctionParamBufferAllocator> Allocator; void* Params;
   };
   ```
   `PROCESS_RETURN()` 里的裸 `Free` 同时删除，避免双重释放。注意 `Params` 目前在宏里被按名引用（`FunctionMacro.h:72,98,139`），改成守卫需要同步改宏为 `Scope.Get()`。
3. 顺带把 `Count` 从 `uint8` 提升为 `int32`（见 F-FN-005）。

**验证方式**

- 静态证据：`Select-String -SimpleMatch 'BufferAllocator->Free'` 在 `FUnrealFunctionDescriptor.inl` 只命中 `:213,:260`，而 `BufferAllocator->Malloc()` 命中 14 处；`FCSharpDelegateDescriptor.inl` 中 `Malloc` **9 处**、`Free` **0 处**（注意不要把"11 个函数"当作"Malloc 次数"：实测分配点为 9）。这是干净的 grep 反证。
- 运行时：断点 `FFunctionParamPoolBufferAllocator::Malloc`，统计 `Buffers.Add` 被执行的次数；对一个每帧调用的 `Call2` 函数，`Buffers.Num()` 会在 256 帧内从 0 涨到 256 并停住（回绕后不再增长），内存常驻峰值 = 256 × `ParmsSize`。

### [F-FN-005] `FFunctionParamPoolBufferAllocator::Free` 忽略 `InMemory` 并盲目 `Count--`，无下溢/归属校验；`Count` 是 `uint8`（255 次后回绕）→ 乱序或少配对释放会让两个活跃调用共享同一缓冲

- **函数**: `FFunctionParamPoolBufferAllocator::Free(void*)`、`FFunctionParamPoolBufferAllocator::Malloc()`

**现状（代码事实）**

```cpp

	uint8 Count;                                  // ← 8 位游标
	decltype(UFunction::ParmsSize) ParamSize;     // = uint16
```

`Count` 同时承担两个语义："当前活跃分配数"与"下一个可用槽位索引"（`Malloc` 的 `return Buffers[Count++]`，`:39`）。

**调用上下文**

所有 `Free` 都在与 `Malloc` 同一函数体内成对出现（`FunctionMacro.h:147`、`FUnrealFunctionDescriptor.inl:213,260`、`FCSharpFunctionDescriptor.cpp:138`），在单线程下是严格 LIFO 的。因此正常流程不会错配。

**问题**

1. **忽略归属**：`Free` 假定"最后分配的一定是正在释放的这块"（LIFO）。若出现乱序释放（例如未来有人用 RAII 守卫且守卫析构顺序与构造顺序不一致，或某个 `CallN` 里嵌套调用了另一个 `CallN` 之后又提前 `return`），`Count--` 之后 `Buffers[0..Count)` 的"存活"假设就错了：某块**仍被外层调用使用**的缓冲会被下一次 `Malloc` 交出去，两个活跃调用写同一块内存 → 参数互相覆盖（静默数据损坏，比崩溃更难查）。
2. **无下溢校验**：`Count` 为 0 时 `Count--` 回绕到 255。此时 `Malloc` 的 `Buffers.IsValidIndex(255)` 在 `Buffers.Num() <= 255` 时为 false，走新分配分支并把 `Count` 加回 0 —— 结果是对**已分配但未跟踪**的状态失去一致（`Count` 与 `Buffers.Num()` 的"存活前缀"关系被破坏），后续 `Free` 可能释放到错误的槽位语义上。
3. **`uint8` 太窄**：配合 F-FN-002（11 个调用点从不 `Free`）只需 256 次调用就回绕；即便修好配对，一个递归/重入较深的调用链（如委托广播里再触发同名函数）理论上也能把活跃数推到 256 以上。

**建议**

改成显式的空闲链表，让 `InMemory` 参与判定，并让类型足够宽：

```cpp
class FFunctionParamPoolBufferAllocator final : public FFunctionParamBufferAllocator
{
private:
	int32 Count = 0;                        // int32，不再回绕
	decltype(UFunction::ParmsSize) ParamSize;
	TArray<void*> Buffers;                  // 全部已分配块，索引即槽位
	TArray<int32> FreeSlots;                // 空闲槽位栈（优化：保持 LIFO 快速路径）

public:
	void* Malloc() override
	{
		int32 Slot;
		if (FreeSlots.Num() > 0) { Slot = FreeSlots.Pop(EAllowShrinking::No); }
		else { Slot = Buffers.Add(FMemory::Malloc(ParamSize, 16)); FMemory::Memzero(Buffers[Slot], ParamSize); }
		++Count;
		return Buffers[Slot];
	}

	void Free(void* InMemory) override
	{
		const int32 Slot = Buffers.IndexOfByKey(InMemory);
		checkf(Slot != INDEX_NONE, TEXT("Free of a pointer not owned by this allocator"));
		checkf(!FreeSlots.Contains(Slot), TEXT("Double free of parameter buffer"));
		FreeSlots.Add(Slot);
		--Count;
	}
};
```
`IndexOfByKey` 是线性查找，但 `Buffers` 通常只有个位数（真正配平后），可接受；若要 O(1)，可用 `TMap<void*, int32>`。

**验证方式**

- 单元测试思路：`Malloc(); Malloc(); Free(第一次); Malloc();` —— 断言第三次 `Malloc` 返回的指针 **不等于** 第二次（当前实现会返回第二次的指针，即仍活跃的那块）。
- 加一个 `checkf(InMemory == Buffers[Count - 1])` 临时断言，跑现有测试与示例工程，观察是否触发（用于确认当前是否真的存在非 LIFO 路径）。

- 至少应在 `Malloc` 的复用分支加 `FMemory::Memzero(Buffer, ParamSize)`（配合 F-FN-001 的析构回调），把"残留旧值"变成"确定的默认值"，把静默数据错误降级为可预期的空值。

1. 断点 `FStructPropertyDescriptor::Get(...FMember)`，记录 `Src` 值与 `AddStructReference` 的对象；对同一函数调用 257 次，检查第 257 次的 `Src` 是否与第 1 次相同（当前实现下必然相同）。
2. C# 侧用例：把一次调用得到的结构体包装器存进静态字段，强制调用同一函数 300 次后再读该字段，观察是否变成新调用的值。

2. `FFunctionDescriptor::GetName()` 返回 `FString`（每次堆分配）。若保留字符串接口，至少该返回 `const FString&`（把名字在 `Initialize` 时缓存一次）或提供 `FName GetFName()`。
3. `FClassRegistry` 侧其实已经有 `TMap<uint32, ...>` 索引，若能按"名字哈希"再建一个索引（`TMap<FName, FCSharpFunctionDescriptor*>`），这个线性扫描可以变成 O(1)。

**建议**

```cpp
// FFunctionDescriptor.h：缓存名字，避免每次构造 FString
protected:
	FName FunctionName;                     // Initialize() 中赋值：FunctionName = Function->GetFName();

public:
	FORCEINLINE FName GetFunctionName() const { return FunctionName; }

// FClassDescriptor.cpp：改按 FName 查找
FFunctionDescriptor* FClassDescriptor::GetFunctionDescriptor(const FName& InFunctionName)
{
	for (const auto FunctionHash : FunctionHashSet)
	{
		if (const auto FunctionDescriptor = ...GetFunctionDescriptor<FCSharpFunctionDescriptor>(FunctionHash))
		{
			if (FunctionDescriptor->GetFunctionName() == InFunctionName) { return FunctionDescriptor; }
		}
	}
	return nullptr;
}
```
（`FCSharpBind.cpp:447` 的调用点相应改为传 `InFunction->GetFName()`；注意那里做的是"名字比较"，语义等价。）

**验证方式**

`Select-String -SimpleMatch 'GetFunctionDescriptor('` 确认只有 1 处外部调用（`FCSharpBind.cpp:447`），改动面小。用 `stat` 或 `TRACE_CPUPROFILER_EVENT_SCOPE` 包住该函数，在一次全量绑定中对比改前/改后的耗时与 `FString` 分配次数。

### [F-FN-015] `FClassDescriptor::Deinitialize()` 不重置 `Class` 成员，`GetClass()` 在反初始化后仍返回旧的 `FClassReflection*`

- **函数**: `FClassDescriptor::Deinitialize()`、`GetClass()`

**现状（代码事实）**

```cpp

{
	const auto FoundClass = Cast<UClass>(Struct);
	...
	for (const auto& FunctionHash : FunctionHashSet) { ...RemoveFunctionDescriptor(FunctionHash); }
```


一旦某条路径先 `Deinitialize` 再 `GetClass()`，这个判空就会失效（返回悬垂指针而非 `nullptr`）。当前 `Deinitialize` 只从析构进入，所以只是隐患。

```cpp

	...
	Class = nullptr;                 // 补上

```
