## 1. 模块职责与架构速览

C# 侧对 UE 反射类型采用**"句柄 + 原生注册表"**的双向映射，而不是直接持有原生指针：

```
C# 包装对象 (FString/UObject/...)  ──HandleData.Alloc(obj)──►  nint Handle (单调递增整数)
        │                                                              │
        │ HandleData.GetHandle(this)                                    │ 作为 key
        ▼                                                              ▼
原生注册表 (FStringRegistry / FReferenceRegistry)  ──►  new FString(...) / UObject*
```

- **句柄分配**：`HandleData.cs:27-44`。每个 C# 对象第一次 `Alloc` 时通过 `ConditionalWeakTable` 分配一个递增句柄，并用 `GCHandle.Alloc(InObject, GCHandleType.Normal)`（**强句柄**）登记。
- **句柄释放**：只有原生侧回调 `HandleData.Free`（`HandleData.cs:24-25`，`[UnmanagedCallersOnly]`）才会 `Free()`。
- **字符串族**：`FString`/`FName`/`FText`/`FAnsiString`/`FUtf8String` 各自的注册函数在原生侧 `new` 一个堆对象存入注册表，C# 侧靠**终结器**调用 `UnRegister` 反向清理。
- **UObject 族**：`Object.cs` 是 `partial class UObject`，包装 `GetClass/GetName/AddToRoot/IsValid` 等，不持有任何原生所有权。

### 2.3 `ToString()` 的 C#↔C++ 封装链与 `IManagedHandle` 0 值语义


### 3.1 "C# 是否让 native UObject 免于 UE GC" 结论

**不阻止。** `HandleData` 侧的 `GCHandleType.Normal`（`HandleData.cs:39`）只是把 **C# 托管包装对象**变成 GC root，与原生 `UObject` 的 UE GC 无关；`Object.cs` 全文（1-57 行）**没有任何** `AddToRoot`/`AddReferencedObjects`/`TStrongObjectPtr` 的自动配对逻辑，只有用户手动调用的 `AddToRoot()`(:44) / `RemoveFromRoot()`(:46)。因此：

- 若原生注册表（`FReferenceRegistry`）中该 `UObject*` 未被 `UPROPERTY`/`AddReferencedObjects` 保护 → **UE GC 回收该对象后，C# 句柄仍指向已释放内存** → 悬垂（P0 级风险，本报告以 F-CS2B-008 记录，原生侧配对证据需跨模块确认，标置信度中）。
- `Object.cs:44 AddToRoot()` 与 `:46 RemoveFromRoot()` 是**成对的公开 API**（用户负责配对），插件自身未自动 `AddToRoot`，所以不构成"AddToRoot 却从不 RemoveFromRoot"的永久 P1 —— **该特定线索不成立**，但形成了"用户忘记配对即永久泄漏"的 API 陷阱（P3 文档级）。

### 3.2 强句柄 → 终结器永不可达（核实已知线索）

```
HandleData.cs:31-39
  var HandleReference = ObjectToHandleReference.GetValue(InObject, _ => new HandleReference { Value = ++Handle, Count = 0 });
  HandleReference.Count++;
  if (!Handles.TryGetValue(HandleReference.Value, out _))
  {
      Handles[HandleReference.Value] = GCHandle.Alloc(InObject, bPinned ? GCHandleType.Pinned : GCHandleType.Normal);   // ← 强句柄
  }
```

`GCHandleType.Normal` = 强（可追踪）句柄，它本身就是一个 **GC root**。`FStringImplementation.cs:17` 传入 `HandleData.Alloc(InString)` 时 `bPinned` 缺省为 `false` → 走 `Normal` 分支。于是：**被 `FString_RegisterImplementation` 登记过的 FString 实例永远可达 → 终结器队列永不包含它 → `FString.cs:12` 的 `~FString()` 永不执行。** 已知线索**成立且适用**于 `FString`/`FName`/`FText`/`FAnsiString`/`FUtf8String`（以及所有经 `HandleData.Alloc` 的包装类型）。

### [F-CS2B-001] 未注册句柄的 `FString.ToString()` 触发原生空指针解引用崩溃（默认构造即触发）

- **类别**: Bug / 未定义行为

- **复核结论**: 确认（行号与代码事实逐字对齐，无偏差）
- **可达性**: 活跃（原生空指针解引用，与脚本后端无关 —— 不经过托管异常协议，LeanCLR 的 `RtResult` 语义不适用）
- **复核证据**: `Source/UnrealCSharp/Private/Domain/Interop/FRegisterString.cpp:42-47` 逐字复核：`:44` `GetString<FString>(InManagedHandle)`、`:46` `IScriptDomain::Get()->NewString(TCHAR_TO_UTF8(**String))` **无判空**；`:23-29` `IdenticalImplementation` 对同一调用做了双重判空 → 漏判成立。`FStringRegistry.inl:20-28`（`:23` Find、`:27` 未命中返回 `nullptr`）。C# 触发链真实行号：`FString.cs:8-10` 默认构造**不注册** → `:43` `ToString()` 传 `HandleData.GetHandle(this)`（未分配时为 0）→ 原生化。`FString` 无 SSO，`**String` 即 `operator*()` 读 `Data.Num()` → 对 `nullptr` 解引用读偏移 → Windows `0xC0000005`。默认构造触发路径 = `FString.cs:8-10` → `FString.cs:43` → `FStringRegistry.inl:27`(nullptr) → `FRegisterString.cpp:46`。

- **文件**: `Script/UE/CoreUObject/FString.cs:8-12,43`；`Script/UE/Library/FStringImplementation.cs:39-41`；`Source/UnrealCSharp/Private/Domain/Interop/FRegisterString.cpp:42-47`

- **置信度**: 高

**现状（代码事实）**

C# 侧默认构造函数**不注册**，句柄保持 0：
```csharp
// Script/UE/CoreUObject/FString.cs:8-14

{

~FString() => FStringImplementation.FString_UnRegisterImplementation(HandleData.GetHandle(this));
```

```csharp
// Script/UE/CoreUObject/FString.cs:42-43
public override string ToString() =>
    FStringImplementation.FString_ToStringImplementation(HandleData.GetHandle(this));   // ← 默认构造时传 0
```

原生侧**只判了 `GetString` 失败的一半**：
```cpp
// Source/UnrealCSharp/Private/Domain/Interop/FRegisterString.cpp:42-47
static IManagedHandle ToStringImplementation(const IManagedHandle InManagedHandle)
{
    const auto String = FCSharpEnvironment::GetEnvironment().GetString<FString>(InManagedHandle);

    return IScriptDomain::Get()->NewString(TCHAR_TO_UTF8(**String));   // ← *String 可能为 nullptr，无任何判空
```

**调用上下文**

`FString` 的句柄只在 `FString_RegisterImplementation`（`FStringImplementation.cs:17`）里通过 `HandleData.Alloc(InString)` 产生，只被带参构造 `FString.cs:14` 调用。故 `new FString()`（`FString.cs:8`）产生的实例 `HandleData.GetHandle(this)` 恒为 **0**（`HandleData.cs:86-92` 在表中找不到即返回 0；且 `HandleData.cs:13,32` 的计数器从 0 起 `++Handle`，**句柄 0 永远不会被分配**）。原生 `GetString<FString>(0)` 在 `ManagedHandle2Value` 中查不到 → `FStringRegistry.inl:23-27` 返回 `nullptr` → `FRegisterString.cpp:46` 对 `nullptr` 取 `**String`。

**问题**

**调用上下文**

- `Tick`(:26-30) 是 `[UnmanagedCallersOnly]`，由 C++ 侧每帧直接调用（同型模式见 `FRegisterAnsiString.cpp` 等注册文件的导出方式），是**托管代码与原生代码的边界**。
- `Send`(:68) 是 `System.Threading.SynchronizationContext` 的 override，由 `await` 的 `SynchronizationContext.Post/Send` 路径与用户直接调用触发。
- 触发路径：**任一非游戏线程**（如 `Task.Run`、`FCSharpCompilerRunnable` 编译线程）调用 `Send` → `:70` 线程不匹配 → `:79-89` 入队 → `:90` 方法返回，`using var` 立即 `Dispose()` → 游戏线程下一帧 `Tick` → `Process`(:38-53) → `Task.Invoke()`(`TaskInfo.cs:14`) → `:22` `WaitHandle?.Set()` → **`ObjectDisposedException`** → 沿 `Invoke` → `Process` → `Tick` 逃逸出 `[UnmanagedCallersOnly]` 方法。

**问题**

1. **进程终止（P0）**：.NET 中异常**不允许**穿过 `[UnmanagedCallersOnly]` 边界。运行时遇到此情况会以不可恢复的方式终止进程（`FailFast` 语义），而非向调用方返回错误。这条路径是**游戏线程每帧执行**的 `Tick`，因此一旦有一次跨线程 `Send`，进程必然在下一次 `Tick` 崩溃。
2. **`Send` 完全丧失同步语义**：`:77-90` **没有任何 `WaitOne()` 调用**。`Send` 的契约是"阻塞调用线程直到回调执行完毕"，当前实现是"入队后立刻返回"。所有依赖 `Send` 返回即代表状态已更新的代码都会读到过期状态 —— 这是**静默的数据竞争**，比崩溃更难排查。已知线索中"同一处还漏了 `WaitOne`"**成立**。
3. **`using var` 的作用域是方法而非"回调完成后"**：`using var` 的 Dispose 点固定在作用域出口(:90)，与队列消费时机(:47-50 的 `Invoke`)完全脱钩。即便补上 `WaitOne()`，`using var` 也必须**放在 `WaitOne()` 之后**才能正确工作 —— 当前写法说明代码在某个版本被删改了等待逻辑而 `using` 未同步调整。
4. **异常被替换（吞异常）**：`TaskInfo.Invoke` 的 `finally`(:20-23) 没有 `catch`。若 `CallBack` 自身抛异常，`finally` 中的 `WaitHandle?.Set()` 再抛 `ObjectDisposedException`，**原异常被新异常替换而丢失**；即便 `Set()` 不抛（同步路径无 WaitHandle 时），原异常仍会逃出 `Tick` 导致终止。详见 F-CS2B-010。

**建议**

### [F-CS2B-010] 任一投递回调抛异常都会终止进程；`TaskInfo.Invoke` 的 `finally` 还会吞掉并替换原异常

- **类别**: 并发/线程安全 / 异常与错误处理
- **严重度**: **P1**（进程终止 + 错误信息丢失 —— 进程终止部分仅 CoreCLR/Mono 成立）
- **复核结论**: 部分确认（偏差：异常替换与连带丢弃机制成立；"进程死亡"同 F-CS2B-009 需按后端区分）
- **可达性**: 潜伏（同 F-CS2B-009：LeanCLR 不终止进程；且 Tick 注册在 LeanCLR 下疑似被条件排除）
- **复核证据**: `TaskInfo.cs:14-24` 逐字核对：`:16-19` `try { CallBack?.Invoke(State); }`、`:20-23` `finally { WaitHandle?.Set(); }` —— **只有 try/finally、无 `catch`** → `Set()` 抛 `ObjectDisposedException` 时**替换**原业务异常，成立。`SynchronizationContext.cs:38-53`：`:47-50` `foreach { Task.Invoke(); }` 无 try/catch、`:52` `PendingTaskList.Clear()` 在异常时被跳过 → `PendingTaskList`（字段，`:36`）残留旧任务，下一帧 `:42 AddRange` 再叠加 → **无界增长 + 反复重放同一批任务**。后端依据同 F-CS2B-009（`FLeanCLRDomain.cpp:99`）：**这一条"队列永久卡死"才是 LeanCLR（异常不终止进程）下的实际后果** —— 非终止型后端把"崩溃"变成了"静默卡死 + 内存增长"。
- **级别变动**: P0→P1（与 F-CS2B-009 同因：进程终止后果受后端限定）
- **文件**: `Script/UE/CoreUObject/TaskInfo.cs:14-24`；`Script/UE/CoreUObject/SynchronizationContext.cs:26-30,38-53`
- **函数**: `TaskInfo::Invoke()` / `SynchronizationContext::Process()` / `SynchronizationContext::Tick(float)`
- **置信度**: 高

**现状（代码事实）**
```csharp
// Script/UE/CoreUObject/SynchronizationContext.cs:38-53
private void Process()
{
    lock (TaskList)
    {
        PendingTaskList.AddRange(TaskList);

        TaskList.Clear();
    }

    foreach (var Task in PendingTaskList)
    {
        Task.Invoke();          // ← :49 无 try/catch：一个任务抛异常，同批次后续任务全部丢失
    }

    PendingTaskList.Clear();    // ← :52 异常时不会执行
}
```
（`Tick` 与 `TaskInfo.Invoke` 代码见 F-CS2B-009。）

**调用上下文**

`Process` 的唯一调用点是 `Tick`(:29)，而 `Tick` 是 `[UnmanagedCallersOnly]`(:26)。`TaskList` 中的任务是 **C# `async`/`await` 的续体**（`Post` 由 `SynchronizationContext` 基础设施在 `await` 完成后调用，`:55-66`）。

**问题**

1. **用户代码异常 = 进程死亡**：任何 `await` 续体（即用户写的 `async` 方法在 `await` 之后的代码）抛出未捕获异常，异常会经 `Invoke` → `Process`(:49) → `Tick`(:29) 穿出 `[UnmanagedCallersOnly]` → 进程终止。而在标准 .NET 语义下，这类异常本应由 `TaskScheduler` 捕获并存入对应的 `Task`（通过 `await` 重新抛出，或进入 `TaskScheduler.UnobservedTaskException`）。**这里完全没有任何捕获层**，把"某个 async 方法出错"升级成了"整个游戏进程崩溃"。这是本文件最严重的可用性问题。
2. **异常替换 → 原始错误信息永久丢失**：`TaskInfo.Invoke` 的 `finally`(:20-23) 在 `CallBack` 抛异常后仍会执行 `WaitHandle?.Set()`；由于该 `WaitHandle` 已被 F-CS2B-009 的 `using` Dispose，`Set()` 抛出的 `ObjectDisposedException` 会**替换**掉原始异常继续传播。结果是调用方只能看到 `ObjectDisposedException`，真正的业务异常被彻底吞掉 —— 任何依赖异常信息定位问题的排查都会失效。
3. **同批次任务被连带丢弃**：`:47-50` 的 `foreach` 无 `try/catch`，前一个任务抛异常时，`PendingTaskList` 中**其余已取出**的任务（`:42` 已从 `TaskList` 移走）全部不再执行，且 `:52` 的 `Clear()` 也不会执行，它们残留在 `PendingTaskList` 中等待下一次 `Process` 的 `AddRange` 追加（导致列表无界增长且语义混乱）。
4. **`PendingTaskList` 的重入风险（次要）**：`PendingTaskList` 是**字段**(`:36`)而非局部变量，`Process` 不是可重入安全的。若某个任务的回调再次触发 `Process`（例如回调里再次泵一帧），`:42` 的 `AddRange` 会污染外层正在 `foreach` 的集合 → `InvalidOperationException`（集合被修改）或任务错乱。

**建议**

```csharp
private void Process()
{
    List<TaskInfo> Batch;
    lock (TaskList) { Batch = new List<TaskInfo>(TaskList); TaskList.Clear(); }   // 用局部变量，消除重入
```

**问题**

- `FMemory::Free` 等价于 operator delete 的**内存回收部分**，但**不调用析构函数** `~FString()`。`FString` 内部持有 `TArray<TCHAR>`（堆分配的字符缓冲）。因此 `:69` 释放的是 `sizeof(FString)` 那 16 字节的壳，**字符数组整块泄漏**。

**建议**

```cpp
    FoundValue->Value = nullptr;
}
```

注意 `UObject` 的正确修法是**让包装唯一化**（原生→C# 封送时复用同一实例），而不是给 `UObject` 加内容哈希。

```csharp

```

**调用上下文**

`Initialize`(:12-17) / `Deinitialize`(:19-24) 是静态入口，按命名与用法推断由 C++ 侧在脚本域启动/关闭（PIE 开始/结束）时调用。`Tick`(:26-30) 通过 `Context?.Process()` 消费队列。

**问题**

- `Context = null` 后 `Tick`(:29) 的 `Context?.` 变为 no-op，**队列中已入队但未执行的任务永远不会被执行**。这些任务的载荷是 C# `async` 方法的续体（`Post` 路径 `:55-66`）。若某个 `async` 方法在 PIE 结束时正 `await` 一个已投递的续体，该 `await` **永不返回**，其 `Task` 永远处于未完成状态 → 后续 `await` 链全部挂死。
- `TaskList`/`PendingTaskList` 是**实例字段**，随 `Context` 一起被丢弃，未清空也未给出任何诊断日志（`:23` 无日志、无断言）。用户侧表现为"PIE 停止后日志停在某一行，没有任何报错"。
- 未对旧的 `Context` 调用任何清理/取消机制，`PendingTaskList` 中残留的 `TaskInfo`（见 F-CS2B-010 的问题 3）也一并丢失。
- 类比：标准 .NET 的 `SynchronizationContext` 没有"关闭"语义，因此这不是"实现不全"，而是**该设计缺少取消语义**——`Deinitialize` 需要一个显式策略（执行剩余任务 / 调用 `TaskScheduler` 取消 / 至少打日志统计丢弃数量）。

**建议**

```csharp
public static void Deinitialize()
{
    var Old = Context;
    Context = null;
    SetSynchronizationContext(null);

    if (Old != null)
    {
        var Dropped = 0;
        lock (Old.TaskList) { Dropped += Old.TaskList.Count; Old.TaskList.Clear(); }
        Dropped += Old.PendingTaskList.Count;
        Old.PendingTaskList.Clear();
        if (Dropped > 0)
        {
            // 打到 UE 日志：PIE 结束时丢弃了 N 个未完成的异步续体
        }
    }
}
```
若要真正正确，应持有一个 `CancellationTokenSource`，在 `Deinitialize` 时 `Cancel()`，让 `await` 侧收到 `OperationCanceledException` 而不是永久挂起。

**验证方式**

PIE 内 `async void Foo() { await Task.Yield(); /* 断点 */ }`，在 `await` 前停止 PIE → 观察断点永不命中且无日志；`Select-String -Path Script\UE\CoreUObject\SynchronizationContext.cs -Pattern "Clear|Cancel"` 在 `Deinitialize` 内 **0 命中**。

- 动态类在**每次 PIE 会话**都会重新生成（`FDynamicClassGenerator` 有对应的 `AddToRoot`/`RemoveFromRoot` 配对，说明类本身会回收），但 rooted 的 UFunction 会把它所属的 `UClass` 一并拖住（`Function->Next`/`InClass->Children` 链表、`FunctionMap` 引用），**跨 PIE 会话累积**：编辑器里反复 Play-In-Editor 会让进程内存持续增长。
- 与 `FRegisterClass.cpp:21-28` 的健壮写法对比：那里已经考虑了"已 root 则 `RemoveFromRoot`，否则 `MarkAsGarbage`"两种状态，说明 rooted 函数的回收是作者已识别的关注点——只是输入绑定这条路径上没有释放点。

**建议**

1. 在 `UInputComponent` 的解绑路径（需先实现，见 F-CS2B-017）中调用 `Function->RemoveFromRoot()`，与 `FRegisterClass.cpp:21-24` 保持一致。
2. 若绑定生命周期等于类的生命周期，考虑不 `AddToRoot`，改为把 `Function` 存进类上的 `TArray<TObjectPtr<UFunction>>`（被 UClass 的 `AddReferencedObjects` 覆盖）或包在 `TStrongObjectPtr` 中，让 UE GC 跟随类一起回收。
3. 至少为 `BindFunction` 加一条注释说明"释放点在哪里"，避免下一位维护者重复此遗漏。

**验证方式**

- grep 证据同上（命中数为 1 且无 `RemoveFromRoot`）。
- 运行时：在编辑器里连续进入/退出 PIE 20 次，用 `obj list class=Function` 或内存快照观察 `UFunction` 数量单调增长。

`OutMethodParamCounts[i]` 是**该方法自己的**参数个数（对所有方法都填了真实值），而 `OutMethodParamNames/Types/Refs` 只包含 `[UFunction]` 方法的参数。两者的契约是"从 `OutMethodParamIndex[i]` 起连续 `OutMethodParamCounts[i]` 项属于方法 i"——对非 `[UFunction]` 方法，这个切片**指向了下一条 `[UFunction]` 方法的参数区**。

具体例：方法列表为 `[普通方法 Foo(a,b,c), [UFunction] Bar(x)]`。则 `ParamCounts = [3, 1]`、`ParamIndex = [0, 0]`、`ParamNames = ["x"]`。原生若按契约读取方法 `Foo` 的参数，会读到 `Bar` 的参数 `x`（或越界），即**为普通方法构造出错误的参数列表**。

标置信度中的原因：若原生只对已确认带 `[UFunction]` 的方法读取参数（先自行过滤），则不会触发；但那样 `OutMethodParamCounts` 就没有存在价值，说明该字段的语义本身含糊。

**建议**

任选其一并写清契约：
1. 让 `OutMethodParamCounts[i]` 与 `OutMethodParamIndex[i]` 语义一致——非 `[UFunction]` 方法的 `Count` 置 0：
```csharp
OutMethodParamCounts[i] = IsUFunction ? OutMethodInfos[i].GetParameters().Length : 0;
```
（需把 `:476` 的赋值移入 `IsUFunction` 分支内。）
2. 或把 `OutMethodParamCounts` 定义改为 "params 明细区的项数"（非 UFunction 恒为 0），并在 C++ 侧同步。
3. 无论哪种，都应在 `GetClassMethodsImplementation` 上写明"index/count 指向扁平明细区"的契约注释。

**验证方式**

用上面的两方法例子（一个普通方法 + 一个 `[UFunction]` 方法）导出元数据，dump `OutBuffer[4]/[6]/[7]/[8]` 四个数组，按 (index,count) 切片验证是否指向正确方法。

### [F-CS2B-029] `GetClass*` 系入口向 `nint* OutBuffer` 写入 3~15 个槽位但无长度校验（unsafe 写 + 跨边界魔术数字）

- **类别**: 安全 / 未定义行为
- **严重度**: **P3**
- **复核结论**: ⚠️部分 —— 严重度由 P2 校正为 **P3**；可达性 活跃
- **文件**: `Script/UE/CoreUObject/Utils.cs:646-676`（15 槽）、`:692-708`（8 槽）、`:721-725`（3 槽）、`:743-771`（14 槽）
- **函数**: `Utils::GetClassDescriptor/GetClassProperties/GetClassFields/GetClassMethods`
- **置信度**: 高（"无长度参数"是代码事实）

**现状（代码事实）**
```csharp
// Script/UE/CoreUObject/Utils.cs:633-676
[UnmanagedCallersOnly]

{
    ...
    OutBuffer[0] = OutTypeDefinition != null ? HandleData.Alloc(OutTypeDefinition) : 0;
    ...
    OutBuffer[14] = OutClassAttributeValues != null ? HandleData.Alloc(OutClassAttributeValues) : 0;   // ← 固定 15 槽
}
```

**调用上下文**

原生侧传入 `OutBuffer` 指针；实际所需容量由 C# 侧**硬编码**决定，跨边界没有任何长度约定参数。

**问题**

- 4 个入口分别固定写入 3/8/14/15 个 `nint`，**均由"原生侧必须按同样数字分配"这一未文档化的约定保证**。一旦任一侧增减字段而另一侧未同步，就是**原生堆越界写**（`nint*` 上的越界写，难以定位、可能静默破坏相邻内存）。
- 这些数字散落在 C# 与 C++ 两侧，没有共享常量或静态断言，属典型"跨语言魔术数字"。
- 另注：这些入口对每个字段都调用 `HandleData.Alloc(...)`（`:646-676` 共 15 次），把句柄交给原生；由于 `HandleData.Alloc` 用 `GCHandleType.Normal`（`HandleData.cs:39`，强句柄），**在原生调用 `HandleData.Free` 之前这些反射对象（`Type`/`string`/数组）被强制保活**。这是有意设计（原生持句柄期间对象必须存活），但也意味着**原生侧漏一次 `Free` 就永久泄漏一个强根**，且没有任何 C# 侧安全网。建议在原生释放处加配对断言（`HandleData.FreeImplementation:46-78` 已有引用计数递减逻辑可观测）。

**建议**

1. 让入口额外接收容量参数并校验：
```csharp
public static unsafe void GetClassDescriptor(nint InTypeHandle, nint* OutBuffer, int InCapacity)
{
    if (InCapacity < ClassDescriptorSlotCount) { /* 报错并返回 */ }
    ...
}
```
2. 或在两侧共享同一常量（C# 侧 `public const int ClassDescriptorSlotCount = 15;`，C++ 侧读取该常量或至少写 `static_assert` 对拍）。
3. 至少在 `Utils.cs` 顶部加注释表，列明 4 个入口各自的槽位含义与数量。

**验证方式**

在原生分配处打印容量、在 C# 入口打印实际写入数，做启动期对拍断言；或静态检查两侧数字是否一致（grep `OutBuffer[1[0-4]]`）。

### [F-CS2B-030] `GetTraceback()` 对 `Frame.GetMethod()`/`DeclaringType` 无判空且每次构造完整 `StackTrace`（开销大）

- **类别**: Bug / 性能
- **严重度**: **P3**
- **复核结论**: ✅确认 —— 严重度 P3 维持；可达性 活跃
- **文件**: `Script/UE/CoreUObject/Utils.cs:72-90`
- **函数**: `Utils::GetTraceback()`
- **置信度**: 中（判空缺失是代码事实；实际触发依赖是否有匿名/动态帧）

**现状（代码事实）**
```csharp
// Script/UE/CoreUObject/Utils.cs:72-90
private static string GetTraceback()
{
    var Traceback = new StringBuilder();

    var Trace = new StackTrace();                       // ← :76 捕获完整栈

    var Frames = Trace.GetFrames();                     // ← :78 文档规定可能返回 null

    foreach (var Frame in Frames)
    {
        Traceback.Append(string.Format("at {0}.{1} in {2}:{3}\r\n",
            Frame.GetMethod().DeclaringType.FullName,   // ← :83 GetMethod() 与 DeclaringType 均可为 null
            Frame.GetMethod().Name,
            Frame.GetFileName(),
            Frame.GetFileLineNumber()));
    }

    return Traceback.ToString();
}
```

**调用上下文**

`GetTraceback` 为 private，仅本文件内使用（调用点未逐一确认，见 §8）。用途显然是异常/失败时的诊断。

**问题**

1. `StackTrace.GetFrames()` 文档明确"可能返回 `null`（无可用帧时）"；`:80` 直接 `foreach (Frames)` → `NullReferenceException`。讽刺的是这是一个**诊断函数**，自身崩溃会掩盖真正的问题。
2. `Frame.GetMethod()` 对某些帧可能返回 `null`；`GetMethod().DeclaringType` 对全局方法/`<Module>` 也可能为 `null` → `:83` 再次 NRE。
3. `Frame.GetMethod()` 被调用 **2 次**（`:83`、`:84`）。
4. `new StackTrace()` 默认捕获文件/行号，代价显著；若在异常路径上高频调用会成为明显开销。`string.Format` 在循环内对每帧做一次格式化 + 分配。
5. Release 下 `GetFileName()` 返回 `null` → 输出 `"in :0"`，**信息误导**（看起来像行号 0 的真实位置）。

**建议**
```csharp
private static string GetTraceback()
{
    var Traceback = new StringBuilder();
    var Frames = new StackTrace(true).GetFrames();
    if (Frames == null) return string.Empty;

    foreach (var Frame in Frames)
    {
        var Method = Frame.GetMethod();
        Traceback.Append("at ").Append(Method?.DeclaringType?.FullName ?? "<unknown>")
                 .Append('.').Append(Method?.Name ?? "<unknown>")
                 .Append(" in ").Append(Frame.GetFileName() ?? "<no-pdb>").Append(':')
                 .Append(Frame.GetFileLineNumber()).Append("\r\n");
    }

    return Traceback.ToString();
}
```
并考虑"仅在 Debug/Editor 下采集"或帧数上限（如只取前 10 帧）。

**验证方式**

在无 PDB 的 Release 下调用确认不抛且输出可辨识；或在 `Frames == null` 分支打断点。

### [F-CS2B-031] `Utils.cs` 的 8~15 个 `out` 参数签名与 LeanCLR 条件编译造成的重复实现（可读性/一致性）

- **类别**: 可优化/可读性
- **严重度**: **P3**

3. 把 LeanCLR 与非 LeanCLR 的属性收集逻辑提取为两个 private 方法，消除函数体内的 `#if` 割裂。

**验证方式**
