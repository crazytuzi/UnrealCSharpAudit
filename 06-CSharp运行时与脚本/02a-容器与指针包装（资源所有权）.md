## 1. 模块职责与架构速览

这 11 个类型是 **UnrealCSharp 暴露给 C# 用户的"UE 容器与指针"API 面**。它们不是普通的数据结构，而是**跨托管的句柄包装**：C# 侧对象只持有"我是谁"的句柄，真正的存储全部在 native 侧。

### 1.1 三层结构

```
[用户 C# 脚本]  ← 直接使用的公开 API
      │  TArray<T> / TMap<K,V> / TSet<T> / TOptional<T> / T*ObjectPtr<T>
      ▼
[Script/UE/CoreUObject/*.cs]      纯句柄包装类（无任何字段存储元素）
      │  每个成员 → HandleData.GetHandle(this) → 传给 Script.Library.*Implementation
      ▼
[Script/UE/Library/*Implementation.cs]   C# 侧桥接层：private static unsafe partial 声明
      │  ★ 注意：这里没有 DllImport —— __XXX_*Implementation 的实体由
      │    Script/SourceGenerator 在编译期生成（负责调用约定、Marshal 等）
      ▼
[Source/UnrealCSharp/Private/Domain/Interop/FRegister*.cpp]
      │  用 FClassBuilder 把一个 C++ 静态函数注册到 C# 的 Script.Library.XXX 类
      ▼
[FCSharpEnvironment] 句柄 → C++ 对象的注册表（GetContainer / GetMulti / GetOptional）
      ▼
[FArrayHelper / FMapHelper / FSetHelper / FOptionalHelper / T*Ptr] 真正的 native 存储
      ▼
[UE 的 FScriptArray / FScriptMap / FScriptSet / FOptionalProperty / UObject]
```

### 1.2 关键设计事实（决定了后续所有发现）

| 事实 | 证据 | 影响 |
|---|---|---|
| **C# 侧无 `DllImport`**，桥接体由 SourceGenerator 生成 | `TArrayImplementation.cs:9` 等全是 `private static unsafe partial` | 任务清单里"缺 `[MarshalAs(UnmanagedType.I1)]`"这类问题**不在手写代码里**；`bool` 宽度由统一约定处理（C++ 一律收 `uint8`，C# 一律显式传 `byte`）——**本模块未发现 bool 宽度 bug** |
| **元素读写用 `byte*` + `stackalloc`**，长度由 C# 的 `sizeof(T)` 决定 | `TArray.cs:80`、`:100`；`BufferMacro.h:21` 的 `RETURN_BUFFER_SIGNATURE` 只有裸指针 | native 侧无长度可校验 → F-CS2A-003 |

### 1.3 资源所有权模型小结

- **分配方**：native 侧（`new FArrayHelper` / `new FScriptArray` / `new TWeakObjectPtr<UObject>` …）由 C++ 构造函数在 C# 构造时触发；C# 侧另分配 1-2 个 `GCHandle`。
- **释放方**：设计上唯一入口是 C# finalizer → native `UnRegisterImplementation` → `AsyncTask(GameThread)` → `RemoveXxxReference` → C++ 析构。**⚠️ 更正（F-CS2A-023）**：该入口**实际不可达** —— C# 对象被 `HandleData.cs:39` 的强 `GCHandle` 永久 root，finalizer 永不执行；即"设计的唯一入口"与"运行的唯一入口"不是同一个，运行期根本没有入口。
- **用户可控性**：**零**。11 个类型中没有一个实现 `IDisposable`（`TFieldPath` 无需实现）；grep `IsDisposed|ObjectDisposedException|ThrowIfDisposed|bDisposed|sealed` 于 `Script/UE/CoreUObject/` 命中 **0**。
- **结论**：这是一套"完全依赖 GC + GameThread Tick"的资源管理模型；而实测表明它**连 GC 这一段也失效**（F-CS2A-023），因此这不是"释放不及时"的设计取舍问题，而是**释放链断裂**的缺陷。对本模块 11 个类型而言，"忘记 Dispose 的后果"应统一读作"**不释放**"。（F-CS2A-005 仍然成立，但严重度描述需按 F-CS2A-023 上修语意。）

## 2. 逐类型分析

### 2.1 `TArray<T>` —— `Script/UE/CoreUObject/TArray.cs`（314 行，已读完 1-314）

**架构**：C# `TArray<T>` 是一个**纯句柄包装类**，本身不含任何元素存储。构造时调用 `TArray_RegisterImplementation(this, GetType())`，由 C++ 侧 `FCSharpBind::Bind<FArrayHelper>(Class, Class->GetGenericArgument(), InManagedObject)` 创建一个 `FArrayHelper`，其中 `new FScriptArray()` 是真正的元素缓冲（`FArrayHelper.cpp:19`）。

**元素读写协议**（这是本类型最关键的设计事实）：

- C# 侧 `TArray_Implementation.cs` 中**没有** `DllImport`。所有 `__TArray_*Implementation` 都是 `private static unsafe partial`（例如 `TArrayImplementation.cs:9`、`:16`、`:23`），由 **C# SourceGenerator 在编译期生成桥接体**。因此 `[MarshalAs]`、调用约定、`bool` 宽度这些问题**不在 C# 侧显式声明**，而由生成器决定。
- C++ 侧签名全部使用 `uint8` 而非 `bool` 传布尔值（`FRegisterArray.cpp:196` `const uint8 bAllowShrinking`、`:224`），C# 侧显式转 `byte`（`TArrayImplementation.cs:133`、`:154`）。**这一对是自洽的**——本模块未发现 `bool` 宽度 bug。
- 值类型 `T` 走 `byte* ValueBuffer`，由 C# `stackalloc byte[sizeof(T)]` 提供；引用类型 `T` 走 8 字节句柄（`sizeof(nint)`）。

**发现的要点**：

1. **索引器完全没有边界检查**，而 C++ 侧在越界时会返回 `nullptr` 并被继续解引用 → 原生崩溃。见 F-CS2A-001（P0）。
2. **`Equals` 按值比较，`GetHashCode` 按句柄** → 违反 .NET 相等性契约，见 F-CS2A-004（P1）。
3. **无 `IDisposable`**，只有 finalizer；释放路径还要跨线程，见 F-CS2A-005（P1）。
4. `foreach` 每次分配迭代器状态机，且每次迭代重新调一次 `Num()` P/Invoke，见 F-CS2A-008（P2）。
5. 无 `IsDisposed` 状态位，无 `ObjectDisposedException` → Dispose/finalize 之后继续调用是**静默 use-after-free**，见 F-CS2A-006（P0/P1）。
6. `stackalloc byte[sizeof(T)]` 的字节数取自**托管** `sizeof(T)`，native 侧写入长度取自**UE 反射** `FPropertyDescriptor::GetSize()`，两者无任何校验或 assert，见 F-CS2A-003（P1）。

### 2.3 `TMap<TKey, TValue>` —— `Script/UE/CoreUObject/TMap.cs`（428 行，已读完 1-428）

### [F-CS2A-003] `stackalloc byte[sizeof(T)]` 的长度来自托管 `sizeof(T)`，native 侧按 UE 反射尺寸写入，二者无任何校验

- **类别**: 未定义行为
- **严重度**: **P1**(功能错误/泄漏)　（若发生错配即为栈破坏，实际可升级为 P0；因未能构造出确定错配的实例，保守定级 P1）

- **可达性**: 活跃

- **级别变动**: 无（P1 维持；未构造出确定性错配实例，不上调 P0）
- **文件**: `Script/UE/CoreUObject/TArray.cs:80`、`:100`、`:108`、`:124`、`:215`、`:289`；`Script/UE/Library/TArrayImplementation.cs:217`；`Source/UnrealCSharp/Private/Domain/Interop/FRegisterArray.cpp:109-119`；`Source/UnrealCSharp/Private/Reflection/Container/FArrayHelper.cpp:89-92`

**调用上下文**

`TArray<T>` 的性能主张建立在"托管 `T` 的布局与 native 元素布局逐字节一致"这一**未断言的隐式契约**上。该契约的双方是：C# 编译期的 `sizeof(T)`，与运行时通过 `FReflectionRegistry::Get().GetClass(InManagedType)` → `Class->GetGenericArgument()`（`FRegisterArray.cpp:16-18`）解析出来的 UE `FProperty`。

**问题**

两侧尺寸不匹配时，native 会**按自己的尺寸写穿 C# 的栈缓冲区**：

- native 更大 → **栈缓冲区溢出**，破坏返回地址/相邻局部变量。`TArray_GetCompoundImplementation`（`TArrayImplementation.cs:215-224`）同样用 `stackalloc byte[sizeof(nint)]` = 8 字节接收，若 native 写入超过 8 字节（例如把整个 struct 塞回）同样溢出。
- native 更小 → 读到栈上未初始化残留字节，**静默产生垃圾值**（比崩溃更难查）。

1. 用户自定义 C# struct 绑定到 UE struct，字段类型/对齐与 native 不完全对应（例如 C# 侧用 `bool` 字段而 native 是 `uint8` 或反之）；

3. LWC（`UE_LARGE_WORLD_COORDINATES`）开关下 `FVector` 为 `double`，而绑定生成物按 `float` 生成。

**建议**

对齐机制本身（由 SourceGenerator 保证 C# 绑定 struct 的 `sizeof` 与 native `FProperty::GetSize()` 一致）无法在本模块内修好，但**可以加廉价的自检**：

### [F-CS2A-004] `TArray<T>` 的 `Equals` 按值比较、`GetHashCode` 按句柄，违反 .NET 相等性契约

- **类别**: Bug
- **严重度**: **P2**(功能错误/泄漏)
- **复核结论**: 部分确认（偏差：级别 P1→P2 —— 契约违反成立，但影响面是"以容器作哈希键时行为异常"这一隐患，不是常规路径上的功能错误）
- **可达性**: 活跃
- **复核证据**: `Script/UE/CoreUObject/TArray.cs:19-41` 逐行核对无误（`:19` `operator ==`、`:32-34` 调 `TArray_IdenticalImplementation`、`:37` `!=`、`:39` `Equals`、`:41` `GetHashCode() => (int)HandleData.GetHandle(this)`）；`Source/UnrealCSharp/Private/Reflection/Container/FArrayHelper.cpp:51-87` `Identical` 确为逐元素 `GetProperty()->Identical`（`:80`）核对无误。对比：`Object.cs:8-24` 的 `UObject.operator ==` 走的是 **native 对象同一性**（`:21` `UObject_IdenticalImplementation` → `FRegisterObject.cpp:16-27` 的 `FoundA == FoundB` 比较 `UObject*`），而 `GetHashCode`（`Object.cs:30`）走**句柄**——因此 `UObject` **同样不自洽**（同一个 `UObject` 的两个不同 C# 包装对象会 `==` 为真但 hash 不同）。本模块的契约违反不是孤例，`UObject` 亦在其中（`UObject.cs` 不在本报告覆盖文件内，此处仅作对照证据）。
- **级别变动**: P1→P2（值/句柄混用只在"容器作哈希键或参与 `Dictionary`/`HashSet`"时暴露，属隐患而非默认路径功能错误）
- **文件**: `Script/UE/CoreUObject/TArray.cs:19-41`
- **函数**: `TArray<T>::operator==` / `TArray<T>::Equals(object)` / `TArray<T>::GetHashCode()`
- **置信度**: 高

**现状（代码事实）**

```csharp
// Script/UE/CoreUObject/TArray.cs:19-41
public static bool operator ==(TArray<T> A, TArray<T> B)
{
    if (A is null && B is null)
    {
        return true;
    }

    if (A is null || B is null)
    {
        return false;
    }

    return ReferenceEquals(A, B) ||
           TArrayImplementation.TArray_IdenticalImplementation(      // :32  逐元素按值比较
               HandleData.GetHandle(A),
               HandleData.GetHandle(B));
}

public static bool operator !=(TArray<T> A, TArray<T> B) => !(A == B);      // :37

public override bool Equals(object Other) => this == Other as TArray<T>;     // :39

public override int GetHashCode() => (int)HandleData.GetHandle(this);        // :41  句柄哈希！
```

其中 `TArray_Identical` 是**逐元素按值比较**（`Source/UnrealCSharp/Private/Reflection/Container/FArrayHelper.cpp:51-87`，用 `InnerPropertyDescriptor->GetProperty()->Identical(ItemA, ItemB)`，`:80`）。

**调用上下文**

`GetHandle` 的实现是 `ObjectToHandleReference` 查表（`Script/Interop/Handle/HandleData.cs:80-93`），而每个 `HandleReference.Value` 来自 `++Handle`（`HandleData.cs:32`），即**每个 `TArray<T>` 实例的句柄都是唯一且单调递增的**。因此：

- 两个内容相同但分别构造的 `TArray<int>`：`==` 返回 **true**，`GetHashCode()` 返回**两个不同的值**。
- 同一实例：`==` true 且哈希相同 → 只有自反情形正确。

**问题**

`Object.Equals`/`GetHashCode` 的契约要求"`Equals` 为 true ⇒ 哈希相等"。这里被破坏，后果是**所有基于哈希的容器静默失效**：

```csharp
var a = new TArray<int>(); a.Add(1);
var b = new TArray<int>(); b.Add(1);

var set = new HashSet<TArray<int>> { a };
set.Contains(b);        // false ← 但 a == b 为 true
set.Add(b);             // 成功，集合里出现两个"相等"的元素

var dict = new Dictionary<TArray<int>, string> { [a] = "x" };
dict[b];                // KeyNotFoundException
dict.TryGetValue(b, out _);   // false
```

用户若把 `TArray` 当 key（或塞进 `HashSet`/`Distinct()`/`GroupBy()`），得到的是**静默的错误结果**，不抛异常。注意这**不是**"句柄 hash 导致查找失败"的常规误用案例——恰恰相反，这里的 `Equals` 是值语义而哈希是引用语义，二者方向不一致才是根因。

另外 `Equals` 用的是 `Other as TArray<T>`：`as` 对**不同类型参数**返回 `null` 而非抛错，所以 `new TArray<int>().Equals(new TArray<string>())` 静默返回 `false`（可接受），但类型不同的两个 TArray 若恰好走 `ReferenceEquals` 也不会误判为相等。

还有一处相关不一致：**`operator ==` 的 `null` 处理与 `Equals` 的语义组合存在陷阱**。`Equals(object Other) => this == Other as TArray<T>` 中，当 `Other` 为 `null` 时 `as` 得到 `null`，再进入 `operator ==`（A = this 非空，B = null）返回 `false`——行为正确，但纯属巧合式正确（依赖 `operator ==` 里那段 `A is null || B is null` 分支）。

**建议**

让哈希与相等语义一致。二选一：

```csharp
// 方案 A（推荐，改动小）：哈希改为按内容，与 == 对齐
public override int GetHashCode()
{
    unchecked
    {
        var Hash = 17;
        var Count = Num();
        for (var Index = 0; Index < Count; Index++)
        {
            Hash = Hash * 31 + (this[Index]?.GetHashCode() ?? 0);
        }
        return Hash;
    }
}
```

方案 A 的问题：每次 `GetHashCode` 都是 O(N) 次 P/Invoke，在 `Dictionary` 里会被反复调用，性能极差；且数组可变，**用作哈希 key 本身语义就是错的**。

```csharp
// 方案 B（推荐，语义更诚实）：改为引用语义，与哈希一致
public static bool operator ==(TArray<T> A, TArray<T> B) => ReferenceEquals(A, B);
// 想比较内容请显式命名，避免 == 被误读为值比较
public bool Identical(TArray<T> Other) =>
    Other is not null && TArrayImplementation.TArray_IdenticalImplementation(
        HandleData.GetHandle(this), HandleData.GetHandle(Other));
```

方案 B 是破坏性 API 变更（现有用户代码里 `arrayA == arrayB` 的语义会变），但对容器类型而言"`==` 是引用相等"是 .NET 主流约定（`List<T>`、`Dictionary<K,V>` 均为引用相等且不重写 `Equals`/`GetHashCode`）。若必须保留值语义 `==`，则至少应**移除** `GetHashCode` 重写并在文档中明确"不可作为哈希 key"，但那样会退化为默认的对象哈希，仍然与 `==` 不一致。

**验证方式**

- 用例（当前应失败，修复后应通过）：
  ```csharp

  var b = new TArray<int>(); b.Add(1);
  Debug.Assert(a == b);                          // 当前通过
  Debug.Assert(a.GetHashCode() == b.GetHashCode()); // 当前失败 → 证明契约被违反
  ```
- grep 统计本插件内是否有把 `TArray` 当 key 的用法：搜索 `Dictionary<TArray`、`HashSet<TArray`、`.Distinct()` 于 `Script/`，命中数见第 5 节死代码表同批 grep。

并且 `AsyncTask` 的目标线程是硬编码的 GameThread（`:36`）——**从 GC finalizer 线程调用它，需要 GameThread 继续 Tick 才会真正回收**。

**调用上下文**

`TArray<T>` 是给用户脚本用的基础容器（`Script/UE/CoreUObject/` 是公开 API 面）。典型用法 `var arr = new TArray<int>()` 出现在每帧的游戏逻辑里，用户得到的对象既不能 `using`（不是 `IDisposable`），也没有 `Dispose()` 可调。

**问题**

释放要跨越三段延迟，任一段卡住就长期泄漏：

1. **GC 决定何时回收** —— finalizer 只在 GC 判定对象不可达后才排队执行。native `FScriptArray` 及其堆分配（`FArrayHelper.cpp:19` 的 `new FScriptArray()` 会在 `Add` 时分配元素数组）在 GC 期间**完全不计入托管堆预算**，因此 GC 没有压力去回收它们。
2. **finalizer 线程排队** —— 只有单个 finalizer 线程，大量容器同时不可达会让队列积压。
3. **GameThread 排空** —— `AsyncTask` 在 GameThread 忙（关卡加载、长 Tick）时延迟执行；**游戏/编辑器关闭过程中 GameThread 停止 Tick 后投递的任务可能永远不会执行**，此时 `RemoveContainerReference` 与 `delete ScriptArray` 都不发生。这不只是"泄漏"，而是**关闭期使用已拆解的 `FCSharpEnvironment`** 的风险路径（`GetEnvironment()` 在 teardown 后取用）。

具体后果：每帧创建临时 `TArray` 的代码（例如把 native 数组取出、转成 C# 数组）会让 native 堆无界增长，`FArrayHelper` 与 `FScriptArray` 双双堆积，最终 OOM 或内存碎片化。这属于《横向维度 2 内存与资源泄漏》的典型命中。

**建议**

1. **给容器类型加 `IDisposable`**，实现标准 Dispose 模式，同时保留 finalizer 作兜底：

```csharp
public class TArray<T> : IEnumerable<T>, IDisposable
{
    private bool bDisposed;

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    private void Dispose(bool bDisposing)
    {
        if (bDisposed) return;          // 重复 Dispose 安全
        bDisposed = true;
        TArrayImplementation.TArray_UnRegisterImplementation(HandleData.GetHandle(this));
        if (bDisposing) { /* 清理托管字段 */ }
    }

    ~TArray() => Dispose(false);
}
```

2. **native 释放改为同步**，至少让 `IDisposable.Dispose()` 路径同步执行，不再依赖 `AsyncTask` 的 Tick：


   取舍：同步分支在非 GameThread 调用时不安全（`FCSharpEnvironment` 假设 GameThread，参见横向维度 3），所以必须保留分支。真正的收益是"用户在 GameThread 里 `using`/`Dispose` 时立即释放"。

3. 在 `FCSharpEnvironment` teardown 前**主动遍历并释放所有容器引用**，而不是指望 finalizer 队列。参考 `HandleData.Clear()`（`Script/Interop/Handle/HandleData.cs:129-145`）已有的集中清理模式。

- 泄漏复现：写一个每帧 `new TArray<int>()` 并 `Add` 1000 个元素的循环，跑 N 帧后统计 `FCSharpEnvironment` 容器引用数；若 `RemoveContainerReference` 的调用计数远小于构造计数即为泄漏。

### [F-CS2A-006] 容器无 `IsDisposed` 状态，释放后继续调用成员是静默 use-after-free

- **类别**: 未定义行为
- **严重度**: **P1**(功能错误/泄漏)
- **复核结论**: 部分确认（偏差：机制成立，但**触发前提被 F-CS2A-023 推翻** —— 对象根本不会被释放，因此"释放后继续调用"这一时序在插件自身路径内不可达；且"句柄复用"经源码核对**不存在**，结论反而更确定）
- **可达性**: 活跃（"无 `IsDisposed` 状态位"这一事实活跃；"释放后再调用"的时序因 F-CS2A-023 而不可达）
- **复核证据**: `TArray.cs:59-312` 全部成员核对无误（无一处置 disposed 检查）；grep `IsDisposed|ObjectDisposedException|ThrowIfDisposed|bDisposed` 于 `Script/UE/CoreUObject/` → **命中 0**；`Source/UnrealCSharp/Private/Domain/Interop/FRegisterArray.cpp:43-107` 的 `return 0`/no-op 兜底分支逐一核对无误（`:51`/`:62`/`:73`/`:84`/`:95`/`:106`）。**关键更正**：`HandleData.cs:32` 用 `Value = ++Handle` 且 `FreeImplementation`（`:72`）只做 `Handles.Remove`，**句柄号单调递增、永不复用** → 因此不存在"取决于句柄复用时序"的情形，而是"**确定性地静默返回 0/忽略**，不存在指向他人对象的串扰"。
- **级别变动**: 无（P1 维持）
- **文件**: `Script/UE/CoreUObject/TArray.cs:59-312`（全部成员）；`Script/Interop/Handle/HandleData.cs:46-78`（`FreeImplementation`）；`Source/UnrealCSharp/Private/Domain/Interop/FRegisterArray.cpp:43-107`（`GetContainer` 为空时的分支）
- **函数**: `TArray<T>::Num/GetSlack/Max/this[int]/Add/...` 全部
- **置信度**: 中（"无 ObjectDisposedException"已确证；具体某次调用是崩溃还是返回默认值取决于 `HandleData` 的句柄复用时序，见下）

**现状（代码事实）**

所有成员都无条件地通过 `HandleData.GetHandle(this)` 取句柄再跨边界调用，**没有一处检查对象是否已释放**。以 `Num()` 与索引器为例：


**调用上下文**

释放路径有两个入口，且都不带状态标记：finalizer（`TArray.cs:17`，由 GC 触发）与 `HandleData.FreeImplementation`（`HandleData.cs:46-78`，由 native 回调 `HandleData.Free`，`:24-25`）。`FreeImplementation` 会 `Handles.Remove(InHandle)` 并 `OutHandle.Free()`（`:72-74`）。

**问题**

`IDisposable` 模式的核心保证是"Dispose 后使用抛 `ObjectDisposedException`"。这里完全没有：

- **读操作**：`Num()` 返回 0、`IsEmpty()` 返回 true、`Max()` 返回 0、`GetSlack()` 返回 0 → 用户的 `for (var i = 0; i < arr.Num(); i++)` 静默变成空循环，**逻辑静默走空分支**。这是"数据损坏"级别的隐蔽性：程序不崩，只是结果错了。
- **`Find`/`FindLast`** 返回 `INDEX_NONE`（`FRegisterArray.cpp:139`、`:150`）→ 与"没找到"不可区分。
- **`Contains`** 返回 `false`（`:161`）。
- **写操作**静默丢弃 → 用户的 `Add` 成功返回但数据没进任何数组。
- **`GetImplementation`**（`:109-119`）在句柄失效时整体跳过（`if` 不成立），**不会写 `RETURN_BUFFER`**，于是 C# 侧 `return *(T*)ValueBuffer;`（`TArray.cs:84`）读出的是 `stackalloc` 的**未初始化栈内存**——读操作返回垃圾值，且可能包含上一个栈帧的敏感数据。

关于"use-after-free"的严格性：`ObjectToHandleReference` 是 `ConditionalWeakTable`（`HandleData.cs:22`），`GetHandle` 在对象已被 GC 后仍可能返回**旧句柄值**（条目随对象存活，但句柄计数器 `Handle` 单调递增 `HandleData.cs:32`，**不复用**）。因此：

- 句柄不会被复用 → 旧句柄不会撞上新容器 → **不会**造成"操作到别的对象"的串扰；
- 但旧句柄在 native 侧已查不到容器 → 落到上面那些静默分支。

**结论修正**：本类型不是"越界写已释放内存"式的经典 use-after-free（因为句柄不复用），而是**更隐蔽的"静默降级为空/垃圾值"**。真正构成 use-after-free 的是 F-CS2A-001（越界读）与 F-CS2A-003（缓冲尺寸错配）。此处定级 P1 而非 P0，因为不直接崩溃。**这一区分是实际验证后的结论，与"预期会 use-after-free"的先验假设不同。**

**建议**

```csharp
// 加入状态位，所有公开成员入口检查
private bool bDisposed;

private void ThrowIfDisposed()
{
    ObjectDisposedException.ThrowIf(bDisposed, this);
}

public int Num()
{
    ThrowIfDisposed();
    return TArrayImplementation.TArray_NumImplementation(HandleData.GetHandle(this));
}
```

取舍：每个成员多一次字段读 + 分支，对热路径的 `Num()`（本来就要跨边界，开销大得多）可忽略。更彻底的做法是让 C++ 侧在查不到容器时**报错而非静默返回 0**（例如 `checkNoEntry()` 或回传一个明确的失败标志），这样即使 C# 侧漏检也能在开发构建期暴露。

**验证方式**

- grep 确认全模块无 disposed 检查：搜索 `ObjectDisposedException|IsDisposed|bDisposed|ThrowIfDisposed` 于 `Script/UE/CoreUObject/` 与 `Script/UE/Library/T*Implementation.cs`，命中数应为 **0**（见第 5 节）。
- 用例：`var a = new TArray<int>(); a.Add(1); /* 手工触发 finalizer 或调用内部释放 */ GC.Collect(); GC.WaitForPendingFinalizers(); Console.WriteLine(a.Num());` → 观察是否静默返回 0 而非抛异常。

1. **崩溃**：`CopySingleValue(Dest, nullptr)` → 读地址 0 → 访问违例，Shipping 直接掉线。
2. **静默垃圾值**（另一条路径）：若 `GetImplementation` 的外层 `if`（`:121`）不成立（句柄失效），native 整体跳过、**不写 `RETURN_BUFFER`**，C# 侧 `return *(TValue*)ReturnBuffer;`（`TMap.cs:275`）读出 `stackalloc` 的**未初始化栈内容**——可能泄漏上一栈帧的数据。这与 F-CS2A-006 是同源问题。

对比：`TMap::Contains`（`TMap.cs:233-254`）走的是同一套 `Get` 但没有读回缓冲，所以**只有它不会崩**——即"用 `Contains` 先判断再取值"是当前唯一安全的用法，但这一点在代码与文档中都没有任何提示。

**建议**

在一处修复即可覆盖全部三个入口。最小改动是 C++ 侧判空（零额外跨边界开销）：

```cpp

        InManagedHandle))
```

**问题**

两个叠加缺陷：

1. **无参构造与带值构造的资源语义不对称**：无参构造产出的对象**没有 native 对应物**，但**依然挂了 finalizer**（`:12-13`），finalizer 会对句柄 0 调 `UnRegister`。这一侧是良性的（`HandleData.FreeImplementation` 有 `if (InHandle != 0)` 守卫，`HandleData.cs:48`；C++ `RemoveMultiReference(0)` 返回 false），但说明这两个构造函数的契约从一开始就不一致——**要么无参构造也该注册一个"空"的 native 指针，要么就不该有 finalizer**。
2. **`Get()` 缺空值检查**：这是致命的那个。native 侧 `GetMulti` 的返回值在**所有失效场景**下都是 `nullptr`——不只是"无参构造"，还包括：
   - finalizer 已跑过（`RemoveMultiReference` 已执行）但托管对象仍被引用；
   - `AsyncTask` 已投递但 GameThread 尚未执行 `UnRegister` 的中间态；
   - 脚本域已关闭。

   代码在这三种情况下**全部**空指针解引用。这与 F-CS2A-002（`TMap` 缺键）是同一类错误：**helper 层用 `nullptr` 表达失败，注册层不检查，直接送进解引用**。

**建议**

1. **native 侧判空**（必须做，成本为零）：

```cpp
            .GetMulti<TWeakObjectPtr<UObject>>(InManagedHandle))
    {
        return FCSharpEnvironment::GetEnvironment().Bind(Multi->Get());
    }

    return InvalidManagedHandle;      // 0 → C# 侧得到 null
```

   `FRegisterSubclassOf.cpp:46-52`、`FRegisterLazyObjectPtr.cpp:47`、`FRegisterSoftObjectPtr.cpp:47`、`FRegisterSoftClassPtr.cpp:47`、`FRegisterScriptInterface.cpp` 需同样处理。

2. **让无参构造注册一个空的 native 指针**，使语义对称：

```csharp

    TWeakObjectPtrImplementation.TWeakObjectPtr_RegisterImplementation(
        this, 0, GetType());          // 传 0 对象句柄，native 端 new TWeakObjectPtr<UObject>(nullptr)
```

   `FRegisterWeakObjectPtr.cpp:15` 的 `GetObject(InObject)` 对句柄 0 返回 `nullptr`，`new TWeakObjectPtr<UObject>(nullptr)` 正是"空弱指针"。这样 `Get()` 走的是已注册容器 → `Multi->Get()` 返回 nullptr → `Bind(nullptr)` → C# 得到 null。**行为正确且不再依赖 `Multi` 判空。**

   取舍：这会给每个"空占位"对象增加一次 native 注册 + 一次 GC 时的 `AsyncTask`，但换来了构造/析构/取值三者语义的一致。若不愿承担这个成本，则至少应把无参构造标为 `[Obsolete]` 并在 XML 注释里写明"未注册，调用 `Get()` 会崩溃"，同时**必须**配合建议 1。

`RemoveAt` 是 `TArray` 的公开 API（`TArray.cs:196`），用户直接调用，参数完全由用户提供。同族的 `InsertZeroed`（`FArrayHelper.cpp:196-199`）与 `InsertDefaulted`（`:201-206`）也**没有**显式 `IsValidIndex` 检查，但它们是直接把下标交给 UE 的 `ScriptArray->InsertZeroed` / `ScriptArrayHelper.InsertValues`（由下层把关）。`RemoveAt` 的危险在于它在调用下层之前**先自己解引用了一次**（`:212` → `:218`）。

**问题**

两条独立的危害，按构建配置分流：

1. **Shipping 构建（`checkSlow` 被编译掉）**：`ScriptArrayHelper.GetRawPtr(InIndex)` 对越界下标（`InIndex == Num()`、负数、或远大于 `Num()` 的值）返回**指向数组分配范围之外的指针**，随后 `DestroyValue(Dest)` 对该地址执行元素析构。对含非 POD 成员的容器（`FString`、`TArray`、`UObject*` 等）意味着**对任意内存调用析构逻辑**——写坏堆。这是"数据损坏"级。
   注：若容器元素是 POD（`CPF_IsPlainOldData | CPF_NoDestructor`），`:214` 的 `if` 会跳过整个析构循环，此时只在 `:222` 的 `ScriptArray->Remove` 处越界——危害降低但不消失。
2. **Debug/Development 构建**：UE 的 `FScriptArrayHelper::GetRawPtr` 内部有 `checkSlow(IsValidIndex(Index))`，会**断言崩溃**。虽然是"安全"的失败方式，但它把"用户传错下标"变成编辑器崩溃，而非可捕获的 C# 异常。

与 F-CS2A-001（`Get` 越界空指针解引用）是**同一类问题的两种表现**：`Get` 因为返回 `nullptr` 而崩溃在 `CopySingleValue`；`RemoveAt` 因为直接算指针而写坏内存。前者崩溃得"干净"，后者是静默内存损坏，**更危险**。

另外注意 C# 侧的越界语义在同一类里**有三种互不相同的行为**：`this[int]` 的 getter 越界 → **崩溃**（F-CS2A-001）；`this[int]` 的 setter 越界 → **静默忽略**（`FArrayHelper.cpp:133-139` 的 `if` 不成立，写操作被丢弃，用户以为写成功）；`RemoveAt` 越界 → **内存损坏/断言**。

**建议**

在 `RemoveAt` 开头加与 `Get`/`Set` 一致的守卫，并让越界成为**可诊断的错误**而不是静默/损坏：

```cpp
void FArrayHelper::RemoveAt(const int32 InIndex, const int32 InCount, const bool bAllowShrinking) const
{
    auto ScriptArrayHelper = CreateHelperFormInnerProperty();

    if (!ScriptArrayHelper.IsValidIndex(InIndex) || InCount <= 0 ||
        InIndex + InCount > ScriptArrayHelper.Num())
    {
        checkNoEntry();      // 或 ensureMsgf(false, TEXT("RemoveAt 下标越界: Index=%d Count=%d Num=%d"))
        return;
    }

    auto Dest = ScriptArrayHelper.GetRawPtr(InIndex);

    if (!(InnerPropertyDescriptor->GetPropertyFlags() & (CPF_IsPlainOldData | CPF_NoDestructor)))
    {
        for (auto Index = 0; Index < InCount; ++Index, Dest += InnerPropertyDescriptor->GetElementSize())
        {
            InnerPropertyDescriptor->DestroyValue(Dest);
        }
    }

    ScriptArray->Remove(InIndex, InCount, InnerPropertyDescriptor->GetElementSize(), __STDCPP_DEFAULT_NEW_ALIGNMENT__);
```

**调用上下文**

`FMapHelper` 持有 `FScriptMap*`（`FMapHelper.cpp:231-239` 的 `GetScriptMap`）与 `FScriptMapLayout`。UE 的 `FScriptMap` **本身就是哈希表**，本可以调用 `FScriptMap::Find`/`FScriptMapHelper::FindMapIndex` 之类的哈希查找（O(1) 均摊）。这里改成"遍历所有桶槽 + 逐键 `Identical`"，把哈希表当数组用。

C# 侧每个公开方法都是一次 P/Invoke，因此每次 `TMap` 查找的代价是：
`1 次托管/原生边界 × (GetMaxIndex 次桶槽遍历 × 1 次 KeyPropertyDescriptor::Identical)`。

**问题**

三重叠乘：

1. **算法复杂度**：`Get`/`Contains`/`Find`/`Set`/`Remove` 全部 O(N)（N 为 `FScriptMap` 的**桶槽总数**，含空槽，通常大于元素数）。`Dictionary`→`TMap` 的迁移在数据量小时无感，数据上千后性能断崖。
2. **`Identical` 的单价高**：对 `FName` 键是字符串比较；对 struct 键是逐字段递归比较；对含 `FString` 的键涉及堆上字符比较。
3. **C# 侧的放大**：`foreach` 每个桶槽 4 次 P/Invoke（`TMap.cs:16` `GetMaxIndex`、`:18` `IsValidIndex`、`:20` `GetEnumeratorKey`、`:20` `GetEnumeratorValue`），而 `GetMaxIndex()` 又是**每次循环重新调用一次**（`TMap.cs:16`）。对一个桶槽数 M、元素数 N 的 map，`foreach` 的开销是 `4M` 次跨边界调用 + `M` 次 `Identical`。

一个经典退化场景：往 `TMap` 里插入 10 万个元素 → 每次 `Add` 若走 `Set`/`Contains` 路径即为 O(N)，总计 O(N²) = 10¹⁰ 次比较，实际表现为"编辑器卡死"。

**建议**

1. **改用 UE 原生哈希查找**。`FScriptMap` 有现成的哈希查找入口（不同 UE 版本命名略有差异，需按 `UEVersion.h` 的兼容宏分支）：

```cpp

    return Index == INDEX_NONE ? nullptr : Helper.GetValuePtr(Index);
```

   取舍：需要在 `FMapHelper` 构造时拿到 `FScriptMapLayout`（已有）以及键的 `GetValueTypeHash` 支持。若某些自定义键类型没有哈希，需回退到线性扫描——建议"哈希可用则哈希，否则回退"并加 `UE_LOG` 提示一次，而不是无条件线性扫描。

2. **C# 侧缓存 `GetMaxIndex()`**：


3. 若要根治 P/Invoke 次数，应改协议：native 侧一次性导出所有键值对到调用方缓冲（`TMap_GetAllEntries`），C# 侧一次拷贝后本地遍历。

**验证方式**

- 基准：构造 1000 / 10000 / 100000 元素的 `TMap<int,int>`，测量单次 `Contains` 耗时；当前应随 N 线性增长，修复后应近似常数。
- 代码审查证据：搜索 `FindMapIndex|GetValueTypeHash|FScriptMapHelper` 于 `Source/UnrealCSharp/Private/Reflection/Container/FMapHelper.cpp`，当前命中数应为 0（证明完全没走哈希路径）。
- 用 `-trace=cpu` 或在 `FMapHelper::Get` 内加静态计数器，统计单次查找的比较次数。

**调用上下文**

`TOptional<T>` 由 `Script/UE/CoreUObject/TOptional.cs` 定义，是 `Script/` 公开 API 面的一部分。用户写法 `opt.Get()`（`TOptional.cs:44`）直接命中，**无需任何前置条件**——不需要未设置状态、不需要越界。

对照 native 侧**做对了**的那一半：`SetImplementation`（`FRegisterOptional.cpp:127-142`）与 `Register2Implementation`（`:62-71`）都显式按 `IsPrimitiveProperty()` 分流：

```cpp

{

}
```

`Get` 路径**缺少这个分流**，是明确的不对称缺陷。

**问题**

`TOptional<int>`、`TOptional<float>`、`TOptional<bool>`、`TOptional<SomeEnum>` 等**最常见的 optional 用法全部不可用**，且失败方式是抛异常或返回无关对象：

```csharp
var opt = new TOptional<int>(7);
var v = opt.Get();      // 期望 7；实际抛 NullReferenceException 或 InvalidCastException
```

只有当 `T` 是**引用类型**（`TCompoundPropertyDescriptor` 路径，`TCompoundPropertyDescriptor.inl:15-18` 转发到虚的 `FMember` 版本，由具体描述符 `Class->BoxValue(Src)` 写出真正的句柄）时才正确。

附带的第二个缺陷：当 optional **未设置**时（或在 `GetOptional` 返回空的失效场景下），`ReturnValue` 保持 `{}`（全 0），`GetImplementation` 返回 0，C# 得到 `null`。对引用类型 `T` 这是"静默返回 null"（用户后续 NRE 且无法区分"未设置"与"值为 null"）；对值类型 `T` 同样是拆箱 `null` 抛 `NullReferenceException`。C# 侧 `Get()`（`:44`）**没有** `IsSet()` 前置检查，也没有 `TryGetValue` 之类的安全入口。

**建议**

两侧任一处修好即可，建议**两侧都修**（native 保证契约，C# 保证错误可诊断）。

方案 A（native 侧统一为句柄语义，与 `Set` 对称）：

```cpp
static IManagedHandle GetImplementation(const IManagedHandle InManagedHandle)
{
    IManagedHandle ReturnValue{};

    if (const auto OptionalHelper = FCSharpEnvironment::GetEnvironment().GetOptional(InManagedHandle))
    {
        if (!OptionalHelper->IsSet())
        {
            return ReturnValue;      // 0 = 未设置
        }

        const auto Value = OptionalHelper->Get();

        if (OptionalHelper->GetValuePropertyDescriptor()->IsPrimitiveProperty())
        {
            // 走装箱路径，产出真正的托管句柄
            OptionalHelper->GetValuePropertyDescriptor()->Get(Value,
                reinterpret_cast<void**>(&ReturnValue));   // 需改为 FMember 重载以触发 BoxValue
        }
        else
        {
            OptionalHelper->GetValuePropertyDescriptor()->Get(Value,
                reinterpret_cast<void**>(&ReturnValue));
        }
    }

    return ReturnValue;
}
```

注意上面两个分支当前代码**完全相同**——这正是问题所在：primitive 描述符的 2 参 `Get` 是裸拷贝，而 `FMember` 重载才是装箱（`TPrimitivePropertyDescriptor.inl:21-24` 的 `*Dest = IManagedHandleToObject(Class->BoxValue(Src))`）。因此正确的修法是让 primitive 走 **`FMember` 重载**：

```cpp
OptionalHelper->GetValuePropertyDescriptor()->Get(Value,
    reinterpret_cast<void**>(&ReturnValue), FPropertyArgument::FMember());
```

方案 B（C# 侧按值类型分流，与 `TArray` 的索引器一致）：`TArray.cs:78-90` 已经示范了正确做法——值类型用 `stackalloc byte[sizeof(T)]` 收裸字节、引用类型收句柄。但 `TOptional` 目前连 `unsafe` 都没用（`TOptional.cs` 无 `unsafe`），改造成本高于方案 A。

同时建议给 C# 侧补安全入口：

```csharp
public bool TryGet(out T OutValue)
{
    if (!IsSet()) { OutValue = default; return false; }
    OutValue = Get();
    return true;
}
```

### [F-CS2A-015] `TOptional.Set(T)` / 带值构造每次调用泄漏一个 `GCHandle`，并永久钉住装箱值

- **类别**: 内存/资源泄漏
- **严重度**: **P1**(功能错误/泄漏)
- **复核结论**: 确认（第 5.2 节第 2 条存疑项的答案：泄漏机制成立）
- **可达性**: 活跃
- **复核证据**: `TOptionalImplementation.cs:19-23`（`:21-22` `HandleData.Alloc(InOptional)` + `HandleData.Alloc(InValue)` + `HandleData.Alloc(InType)`）、`:62-67`（`:66` `__TOptional_SetImplementation(InOptional, HandleData.Alloc(InValue))`）逐行核对无误。`HandleData.cs:27-44` `Alloc` 的语义已读全：`:31-32` 通过 `ConditionalWeakTable.GetValue` 取/建 `HandleReference{Value = ++Handle; Count = 0}`，`:34` `Count++`，`:38-39` 首次才 `GCHandle.Alloc`。因此**值类型 `T` 的每次 `Set` 都会装箱出一个新对象 → 新 `HandleReference` → 新句柄号 → 新 `GCHandle`，且无任何配对释放**（`HandleData.cs:72`/`:74` 的释放只由 native `Free` 驱动，而 C# 侧 0 调用点）。**附带修正**：对**引用类型** `T`（同一对象已在 `Handles` 中）`Alloc` 只做 `Count++`，使 `FreeImplementation`（`:62-67`）的引用计数**永远归不到零** → 即便该句柄本应被释放也释放不掉。两类情形都是泄漏，但**机制不同**。
- **级别变动**: 无（P1 维持）
- **文件**: `Script/UE/Library/TOptionalImplementation.cs:19-23`（带值构造）、`:62-67`（`Set`）；`Script/Interop/Handle/HandleData.cs:27-44`（`Alloc`）、`:46-78`（`FreeImplementation`）；`Source/UnrealCSharp/Private/Domain/Interop/FRegisterOptional.cpp:38-72`、`:127-142`

- **置信度**: 中高（`Alloc` 无配对 `Free` 已由两侧代码确证；"native 侧不存在别的释放路径"是基于 `FRegisterOptional.cpp` 全文 160 行已读完的判断，但未穷举 `IScriptDomain::UnboxValue` 的内部实现是否隐含释放——**该实现未读取**）

**现状（代码事实）**

**调用上下文**

`TOptional<T>.Set(T)` 是公开 API（`TOptional.cs:46`），带值构造 `TOptional(T)` 同样（`:11`）。两者都是用户日常写法。

**问题**

每次调用泄漏的资源量：

1. **一个 `GCHandle`**（`HandleData.Handles` 字典条目永不 `Remove`，`HandleData.cs:72`）。
2. **一个被永久钉住的装箱对象**（强 `GCHandleType.Normal` 根 → 该对象及其全部引用链永生）。
3. `ObjectToHandleReference`（`ConditionalWeakTable`）中的一条条目。

触发路径与放大效应：

```csharp
// 每帧更新一个 optional —— 完全正常的用户代码
for (var i = 0; i < 100000; i++)
{
    opt.Set(i);       // 每次泄漏一个 GCHandle + 一个装箱 int 永久存活
}
```

由于装箱值被强根钉住，**GC 永远无法回收**，托管堆随调用次数线性增长；同时 `Handles` 字典不断扩容。这与"托管语言不会有 native 泄漏"的直觉相反——泄漏的是**托管堆 + GCHandle 表**。

对照：`TArray`/`TMap`/`TSet` 的元素写入走的是 `stackalloc` 裸字节 + 直接 memcpy（`TArray.cs:100-104` 等），**不分配句柄**，所以这三个容器没有本问题。这是 `TOptional` 独有的设计缺陷——它为了支持"装箱 primitive"而绕道句柄，却没有配套回收。

**建议**

1. **native 侧消费后立即释放**（与 `HandleData.Free` 的既有契约一致——`HandleData.cs:24-25` 暴露了 `[UnmanagedCallersOnly] Free`，说明设计上就允许 native 主动释放）：

```cpp
static void SetImplementation(const IManagedHandle InManagedHandle, const IManagedHandle InValue)
{
    if (const auto OptionalHelper = FCSharpEnvironment::GetEnvironment().GetOptional(InManagedHandle))
    {
        if (OptionalHelper->GetValuePropertyDescriptor()->IsPrimitiveProperty())
        {
            OptionalHelper->Set(FDomain::Object_Unbox(InValue));
        }
        else
        {
            auto ManagedHandle = InValue;

            OptionalHelper->Set(&ManagedHandle);
        }
    }

    // 消费完毕：释放调用方临时分配的装箱句柄
    if (const auto ScriptDomain = IScriptDomain::Get())
    {
        ScriptDomain->Free(InValue);
    }
}
```

   `Register2Implementation`（`:38-72`）同样处理。

   取舍：必须确认调用方**确实不再使用**该句柄。`Register2Implementation` 的 `InValue` 只在 `:62-71` 使用一次，`SetImplementation` 的 `InValue` 只在 `:131-140` 使用一次，之后无引用——因此立即释放是安全的。但 `ScriptDomain->Free` 走的是与 native 容器注册相同的 `HandleData.FreeImplementation`（引用计数递减，`HandleData.cs:62-68`），若该装箱对象的句柄曾被 `Alloc` 两次（不会发生于此路径），递减一次不会真正释放——**建议在 `Free` 后加断言确认句柄已从 `Handles` 移除**。

2. **更彻底的方案**：不要为值类型走句柄。让 `TOptional<T>.Set(T)` 像 `TArray` 那样用 `stackalloc` 传裸字节，native 侧直接 `CopySingleValue`。这能同时消除本泄漏与 F-CS2A-014 的句柄/字节歧义——**两个发现是同一个设计缺陷的两面**，一并修复收益最大。

**验证方式**

- 计数用例：在 `HandleData.Alloc`/`FreeImplementation` 内加日志，循环 `opt.Set(i)` 1000 次，比较 `Alloc` 与 `Free` 的次数差。当前差值应为 1000（每次 Set 一进一出）。
- 内存用例：循环 `opt.Set(new string('x', 1000))` 10 万次后调用 `GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect();` 并测 `GC.GetTotalMemory(true)`；若内存不回落即为确认（对象被 GCHandle 钉住）。
- 句柄表增长：打印 `Handles` 字典 `Count`，应随 Set 次数线性增长。

六处逐字一致（`TScriptInterface.cs:19` 参数为 `T InObject`、`TSubclassOf.cs:18` 与 `TSoftClassPtr.cs:19` 参数为 `UClass InClass`）。而带值构造**立即注册一个 native 指针**：

```csharp
// Script/UE/CoreUObject/TWeakObjectPtr.cs:15-17
public TWeakObjectPtr(T InObject) =>
    TWeakObjectPtrImplementation.TWeakObjectPtr_RegisterImplementation(
        this, HandleData.GetHandle(InObject), GetType());
```

```cpp
// Source/UnrealCSharp/Private/Domain/Interop/FRegisterWeakObjectPtr.cpp:12-23
static void RegisterImplementation(const IManagedHandle InManagedObject,
                                   const IManagedHandle InObject, const IManagedHandle InManagedType)
{
    const auto FoundObject = FCSharpEnvironment::GetEnvironment().GetObject(InObject);

    const auto WeakObjectPtr = new TWeakObjectPtr<UObject>(FoundObject);      // :17  native 堆分配

    const auto Class = FReflectionRegistry::Get().GetClass(InManagedType);

    FCSharpEnvironment::GetEnvironment().AddMultiReference<TWeakObjectPtr<UObject>, true, false>(
        Class, InManagedObject, WeakObjectPtr);                              // :21-22  注册进环境
}
```

**调用上下文**

`implicit operator` 意味着**任何**把 `T`（或 `UClass`）传给形参类型为 `TWeakObjectPtr<T>` 的地方都会静默触发一次构造。典型场景是绑定生成的 API：当某个 UE 函数/属性类型是 `TWeakObjectPtr<T>` 时，生成的 C# 绑定会声明对应参数——用户直接传 `SomeActor`，编译器插入隐式转换。

**问题**

三层后果：

1. **每次转换 = 一次 native `new` + 一次 `AddMultiReference`**（`FRegisterWeakObjectPtr.cpp:17`、`:21-22`）。这不是廉价的"包一层"，而是实打实的原生分配与全局注册表写入。
2. **临时对象没有任何确定性释放路径**。承载它的类型**不是 `IDisposable`**（F-CS2A-005 已确证六个包装类均无），所以编译器生成的临时值**无法 `using`、也无法显式 `Dispose`**——用户即便想主动清理也做不到。
3. **释放只能等 GC**，且 native 侧释放还要 `AsyncTask(GameThread)` 再跳一次（`FRegisterWeakObjectPtr.cpp:38-45`）。因此：

```csharp
// 循环里把 UObject 赋给 weak ptr 形参
for (var i = 0; i < 10000; i++)
{
    Consume(SomeActor);     // 每次隐式转换 → 一次 native new TWeakObjectPtr + 一次注册
}
```

   会产生 10000 个 native `TWeakObjectPtr<UObject>` + 10000 个托管包装对象 + 10000 条注册表条目，全部堆积在托管堆与 `FCSharpEnvironment` 中，直到 GC 触发（且 `AsyncTask` 在 GameThread 排空后）才回收。**native 内存压力不参与 GC 决策**，所以 GC 不会因为 native 堆积而提前触发——这与 F-CS2A-005 是同一个根因。

**建议**

1. **把隐式转换改为显式**（API 破坏性变更，但这是最有效的止损）：

```csharp
public static explicit operator TWeakObjectPtr<T>(T InObject) => new(InObject);
```

   取舍：用户代码里现有的隐式转换点需要加显式 cast。但对一个"会产生 native 分配"的操作而言，**隐式是错误的设计选择**——.NET 惯例是只有零成本/无副作用且不丢失信息的转换才做隐式（如 `int`→`long`）。

2. **或让包装类变廉价**：既然 `TWeakObjectPtr<T>` 本质上只是一个 `(ObjectIndex, SerialNumber)` 值对，可以把它做成**不注册的纯托管值类型**，只在真正跨边界时才登记句柄。这样隐式转换就是零 native 成本的。这是更根本的修法，但需要改协议。

3. **无论如何都要实现 `IDisposable`**（F-CS2A-005 的建议 1），否则连"愿意主动清理的用户"都没有手段。

**验证方式**

- 用例：在 `FRegisterWeakObjectPtr.cpp:17` 后加计数器，循环执行 10000 次隐式转换，观察计数增长 10000 且在 GC 前不回落。
- 若要临时规避：把循环体显式写成 `using`-able 形式（当前做不到，正是本发现的要点）。
- grep 证据：搜索 `implicit operator` 于 `Script/UE/CoreUObject/`，命中 6（六处），全部形如 `=> new(...)`。

### [F-CS2A-008] `foreach` 每次分配迭代器状态机，且循环条件每次重发一次 `Num()` P/Invoke

- **类别**: 性能
- **严重度**: **P2**(性能/隐患)
- **复核结论**: 确认
- **可达性**: 活跃
- **复核证据**: `TArray.cs:43-57` 逐行核对无误：`:43-49` 泛型 `GetEnumerator()` 与 `:51-57` 显式 `IEnumerable.GetEnumerator()` **整段逐字重复**（都是 `for (var Index = 0; Index < Num(); Index++) yield return this[Index];`）。对照：`TMap.cs:25-28` 的显式实现**正确地**写成 `return GetEnumerator();`（未重复）—— 同一模块内两处写法不一致，可作为"应改成 TMap 写法"的直接依据。`Num()` 为 P/Invoke（`:66`），故循环条件每次循环一次跨边界调用，成立。
- **级别变动**: 无（P2 维持）
- **文件**: `Script/UE/CoreUObject/TArray.cs:43-57`
- **函数**: `TArray<T>::GetEnumerator()` / `TArray<T>::IEnumerable.GetEnumerator()`
- **置信度**: 高

**现状（代码事实）**

```csharp
// Script/UE/CoreUObject/TArray.cs:43-57
public IEnumerator<T> GetEnumerator()
{
    for (var Index = 0; Index < Num(); Index++)      // :45  每次迭代调用一次 Num()
    {
        yield return this[Index];                    // :47  每次迭代一次索引器 P/Invoke
    }
}

IEnumerator IEnumerable.GetEnumerator()
{
    for (var Index = 0; Index < Num(); Index++)      // :53  与上完全重复的实现
    {
        yield return this[Index];                    // :55
    }
}
```

**调用上下文**

`TArray<T>` 实现了 `IEnumerable<T>`（`TArray.cs:13`），因此用户日常写法 `foreach (var x in arr)` 直接命中。注意 `GetEnumerator()` 的返回类型是**接口** `IEnumerator<T>`，不是具体状态机类型。

**问题**

三处叠加开销：

1. **`yield return` 使 `GetEnumerator` 变成编译器生成的状态机类，每次 `foreach` 都在堆上 `new` 一个**（且 `public` 与显式接口实现各生成一套，代码量翻倍）。用户无法用 `List<T>.Enumerator` 那种 struct 迭代器规避。
2. **`Num()` 在每次循环条件求值时都跨一次托管/原生边界**（`TArray.cs:45`）。对 N 元素数组是 N+1 次 P/Invoke，而长度在循环期间通常不变。正确做法是循环前缓存一次：
   ```csharp
   var Count = Num();
   for (var Index = 0; Index < Count; Index++)
   ```
   当前写法还有**语义隐患**：若循环体内部修改了数组（`RemoveAt`/`Empty`），`Num()` 每次重取会改变迭代边界；虽然 `FArrayHelper::Get` 有边界检查（`FArrayHelper.cpp:125`）不会崩，但会读到"缩短后仍合法"的元素或提前结束，行为与 .NET 契约（枚举期间修改应抛 `InvalidOperationException`）不符。
3. 每个元素 `this[Index]` 又是一次 P/Invoke（`TArray.cs:47` → `:82`）→ **遍历一个 N 元素数组共 2N+1 次跨边界调用**。对比之下，如果 native 侧一次性把整个数组导出到连续缓冲，可以降到 2 次。

**建议**

```csharp
public IEnumerator<T> GetEnumerator()
{
    var Count = Num();                 // 固化长度，与 .NET 契约一致
    for (var Index = 0; Index < Count; Index++)
    {
        yield return this[Index];
    }
}
```

   并删除 `IEnumerable.GetEnumerator()`（`:51-57`）中重复的循环体，改为 `IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();`。

   要根治跨边界开销需要改协议：加一个 `TArray_GetAll`（native 侧 `Memcpy` 整块到调用方缓冲，或对值类型批量写 `byte*`），C# 侧 `CopyTo(T[] array)` / `ToArray()`。这属于协议级改动，收益是数量级的。

**验证方式**

- 用 BenchmarkDotNet 或简单计时：对 10000 元素的 `TArray<int>` 分别测 `for (i<Num())`、`foreach`、以及缓存长度版本，对比 P/Invoke 次数（可用 `TArray_NumImplementation` 加计数器）。
- 观察 GC：`foreach` 前后 `GC.GetAllocatedBytesForCurrentThread()` 差值应约等于状态机实例大小（当前非 0，修复 `GetEnumerator` 的 yield 本身也需要改造成 struct 迭代器才能归零）。

```cpp
// Source/UnrealCSharpCore/Private/Reflection/FReflectionRegistry.cpp:926-950

{
```

`HandleData.Alloc` 用 `ConditionalWeakTable` 按对象缓存句柄并维护引用计数（`Script/Interop/Handle/HandleData.cs:27-44`）：同一 `Type` 实例（`typeof(TArray<int>)` 每次返回同一个 `Type` 对象）反复 `Alloc` 会返回**同一个句柄值**并把 `Count` 递增（`HandleData.cs:34`）；`FreeImplementation` 递减 `Count`，仅在降到 0 时才 `Handles.Remove` + `OutHandle.Free()`（`HandleData.cs:62-74`）。

**调用上下文**

`TArray_RegisterImplementation` 由 **`TArray<T>` 的每一次构造**调用（`TArray.cs:15`）。因此这是用户代码里最高频的路径之一。

**问题**

两个隐患：

1. **句柄引用计数是否配平取决于调用次数奇偶与缓存状态**。首次遇到某个 `T` 时未命中分支**不释放**（句柄由 `FClassReflection` 持有，`FClassReflection` 生命周期即 `FullName2Class` 表的生命周期，通常到进程结束）；之后每次构造走命中分支**释放一次**。由于 `Alloc` 与 `Free` 成对出现（每次构造 Alloc 一次，除首次外每次 Free 一次），计数**大体配平**，但首次那次 Alloc 的 `Count` 永久残留 1。`ConditionalWeakTable` 的条目因此永不被 GC 回收 → `Type` 对象被 `GCHandle`（`HandleData.cs:39`，`GCHandleType.Normal` 是强根）**永久钉住**，`Handles` 字典条目也永不移除。
   后果：**每个被用作容器泛型参数的 `T` 会永久泄漏一个 `Type` 对象 + 一个 `GCHandle` + 一个字典条目**。对 `T` 的数量有限（用户定义的容器类型种类有限）而言，这**不是无界泄漏**，但会使 **collectible `AssemblyLoadContext` 永远无法卸载**（强 GCHandle 是 ALC 卸载的阻断条件之一），与热重载/脚本重载场景冲突。
2. **`Class` 未判空**：`FRegisterArray.cpp:18` 直接 `Class->GetGenericArgument()`。`GetClass` 的 `:949 return nullptr` 路径（句柄无效、或 `IScriptDomain::Get()` 返回空——例如脚本域尚未初始化/已关闭）会导致原生空指针解引用崩溃。

**建议**

1. `FRegisterArray.cpp:14-19` 加判空并给出可诊断的错误：

```cpp
static void RegisterImplementation(const IManagedHandle InManagedObject, const IManagedHandle InManagedType)
{
    const auto Class = FReflectionRegistry::Get().GetClass(InManagedType);

    if (Class == nullptr)
    {
        checkNoEntry();     // 或 ensureMsgf(false, TEXT("TArray 注册失败：无法解析泛型参数类型"));
        return;
    }

    FCSharpBind::Bind<FArrayHelper>(Class, Class->GetGenericArgument(), InManagedObject);
}
```

2. 明确 `Type` 句柄的所有权归属。若期望"构造后即可释放"，应在 C# 侧 `RegisterImplementation` 里改为一次性查询并把结果缓存（`Type` → `FClassReflection*` 的映射本身已由 `FullName2Class` 缓存），避免每次构造都 Alloc/Free 一个句柄：

```csharp
// 每构造一次就 Alloc/Free 一次 Type 句柄是纯开销；改为静态缓存已注册过的 T
private static readonly HashSet<Type> RegisteredTypes = new();
```

3. 若 `FClassReflection` 确实长期持有该句柄，则应在 `GetClass` 的未命中分支之后**不再期望**它被释放，并在注释中写明——当前两条分支的所有权语义不一致且无文档。

**验证方式**

- 泄漏计数：在 `HandleData.Alloc` 与 `HandleData.FreeImplementation` 内加日志，构造 1000 次 `new TArray<int>()`，比较 Alloc 次数与 Free 次数；当前应为 Alloc 2000（数组 1000 + 类型 1000）对 Free 1000（仅数组，且需 finalizer 都跑完）+ 类型命中 999 次 Free。
- ALC 卸载：在 collectible ALC 中构造一次 `TArray<int>` 后卸载 ALC，观察是否 `Unload()` 成功（预期失败或延迟）。
- 空指针路径：在 `IScriptDomain::Get()` 返回空的时机（脚本域关闭后）调用 `new TArray<int>()`，观察是否崩溃。

3. **无法通过基类/接口统一约束**：因为没有共享基类或接口（各类型分别实现 `IEnumerable<T>` 或什么都不实现），"所有包装类型都应实现 `IDisposable`"（F-CS2A-005）这类横向要求无法用类型系统表达，只能靠逐文件改。

### [F-CS2A-023] 容器/包装对象的释放入口由 finalizer 触发，但对象被 `HandleData` 的**强 `GCHandle` 永久 root** → finalizer 永不执行 → native 与托管资源在进程生命周期内**都不释放**

- **类别**: 内存/资源泄漏
- **严重度**: **P1**(功能错误/泄漏)（按 `_CONVENTIONS.md` 定义：这不是崩溃/数据损坏，故 P1；但其**影响面是本模块全部 11 个类型的每一次构造**，且随对象创建速率无界增长，实际危害高于 F-CS2A-005）
- **复核结论**: 新增（`FCSharpEnvironment::RemoveContainerReference` 的实现已读取，该链路已补齐，结论**与乐观假设相反**）
- **可达性**: 活跃
- **级别变动**: 新增（定级 P1 = 泄漏类，非崩溃/数据损坏故不上 P0）
- **文件**: `Script/Interop/Handle/HandleData.cs:27-44`（强 `GCHandle` 的分配点）、`:46-78`（唯一释放点）、`Source/UnrealCSharp/Public/Registry/FContainerRegistry.inl:35-41`（3 参数 `AddReference` 不留 owner）、`:58-82`（`RemoveReference` → `:76 FDomain::GCHandle_Free`）、`Source/UnrealCSharp/Public/Environment/FCSharpEnvironment.inl:168-175`、`Source/UnrealCSharp/Private/Registry/FContainerRegistry.cpp:18-73`（`Deinitialize`）
- **函数**: `HandleData::Alloc` / `HandleData::FreeImplementation` / `FContainerRegistry::TContainerRegistryImplementation::RemoveReference` / `FCSharpEnvironment::RemoveContainerReference`
- **置信度**: 高（形成闭环的每一跳都已 `read` 到；C++ 侧已对 `RemoveContainerReference` / `GCHandle_Free` 做全 `Source/` grep，调用点穷尽）

**现状（代码事实）**

**第 1 跳 —— 句柄是强 GC 根，不是弱引用**：


**同构性**：`FMultiRegistry`（六个指针包装类）、`FOptionalRegistry`（`TOptional`）的 `RemoveReference` 同样只被各自的 `UnRegisterImplementation` 调用（`FRegisterWeakObjectPtr.cpp:38-45`、`FRegisterSubclassOf.cpp:38-44`、`FRegisterLazyObjectPtr.cpp:38-45`、`FRegisterSoftObjectPtr.cpp:38-45`、`FRegisterSoftClassPtr.cpp:38-45`、`FRegisterScriptInterface.cpp:53-60`、`FRegisterOptional.cpp:87-93`），因此**全部 11 个类型**共用这一缺陷。

**问题**

1. **native 侧永久泄漏**：`FArrayHelper` + `FScriptArray` + 其元素缓冲（`FArrayHelper.cpp:19` 的 `new FScriptArray()`，释放点 `:36` 永不执行）、`FMapHelper`/`FSetHelper`（`FSetHelper.cpp:18`/`:43`）、`FOptionalHelper` + `FOptionalProperty` + `FMemory::Malloc(Data)`（`FOptionalHelper.cpp:21`/`:40`）、六个 `new T*Ptr<UObject>`（如 `FRegisterWeakObjectPtr.cpp:17`），全部在进程内累积不回收。
2. **托管侧同样泄漏**：因为是强句柄，`TArray` 等包装对象**自身也永不回收**（连"等 GC"都等不到），每个被创建的容器都是托管堆上的永久对象。
3. **本报告的"资源所有权表"因此需要更正**："释放时机"列**不是**"GC + finalizer 线程 + GameThread 排空**三段延迟**"，真实情况是**这三段都不会发生**；F-CS2A-005 的"无法确定性释放"应读作"**在本插件自身的代码路径内根本不释放**"。
4. §1.2 表里"句柄号单调递增**不复用**"这一条因此有**双重含义**：既排除了句柄复用串扰（该正面结论成立），也说明句柄/对象只增不减（本发现的负面后果）。
