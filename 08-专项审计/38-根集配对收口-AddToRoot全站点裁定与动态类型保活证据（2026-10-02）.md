## 3. 三条引擎侧证据：为什么"补 `RemoveFromRoot`"是错的

| # | 结论 | 权威出处 |
|---|---|---|
| **E1** | 🔴 **外层包不保活其内部对象**：`UPackage::AddReferencedObjects` 只在 **cooker soft-GC** 开关（`bSupportCookerSoftGC`）下遍历 `SoftGCPackageToObjectList`，其后仅 `Super::AddReferencedObjects` ⇒ 运行期**不会**因为"对象在已加载包里"而保活 | `CoreUObject/Private/UObject/Package.cpp:201-216`；`Package.h:438` |
| **E2** | 动态类型由插件存在**裸指针静态容器**里：`static TMap<FString, UEnum*> DynamicEnumMap`、`static TMap<FString, UClass*> DynamicInterfaceMap`（类/结构体同形）—— **不是 `FGCObject`、没有 `AddReferencedObjects`、不构成 GC 引用** | `FDynamicEnumGenerator.h:44`、`FDynamicInterfaceGenerator.h:47`、`FDynamicClassGenerator.h:131`、`FDynamicStructGenerator.h:50` |
| **E3** | 生成入口有**复用守卫**：同名类型第二次生成时**复用**已存在的 UObject（不新建、不重复加根）⇒ root 数**与类型数同阶**，不随域重建 / 生成趟数增长 | `FDynamicEnumGenerator.cpp:90-92`、`FDynamicInterfaceGenerator.cpp:107-109`、`FDynamicClassGenerator.cpp:172-176`、`FDynamicStructGenerator.cpp:90-94` |
| **E4** | 对照：插件**确有一条** FGCObject 保活通道 —— `FReferenceRegistry : FGCObject` + `TArray<TObjectPtr<UObject>> ObjectArray` + `AddReferencedObjects`；但其 `AddReference(UObject*)` 的唯一入口 `FCSharpEnvironment::AddReference(UObject*)` **在动态类型生成路径上没有调用者**（全仓仅定义 2 处 + 声明 1 处） | `FReferenceRegistry.h:5/22-25/29`、`FReferenceRegistry.cpp:59-69`、`FCSharpEnvironment.cpp:658/668` |
| **E5** | 宏实测（本机开发构建）：`WITH_OVERRIDE_BLUEPRINT_NATIVE_EVENT 1`（⇒ 站点 #1 是**活跃代码**）、`WITH_CORECLR 1 / WITH_MONO 0 / WITH_LEANCLR 0` | `Plugins/UnrealCSharp/Intermediate/Build/Win64/x64/UnrealEditor/Development/UnrealCSharp/Definitions.UnrealCSharp.h` |

⇒ 若按 `F-LIFE-004`/`F-LIFE-005` 的字面建议"补齐 `RemoveFromRoot`"：动态枚举/接口会在**下一次 GC** 变成垃圾，而插件的 `DynamicEnumMap`/`DynamicInterfaceMap` 仍持有其**裸指针** ⇒ **悬垂指针 +（若再生成）同名对象命中引擎"原地销毁重建"路径** —— 这是**反向制造**比原登记更严重的缺陷。**本轮据此不做该改动。**

## 5. `F-LIFE-009` 的"决定不做"与触发条件

- **修法候选**：① C# 侧 `UObject` 提供 `IDisposable` 作用域（`RootScope()`）；② 原生侧在句柄 Free 时自动 `RemoveFromRoot`（会与"用户显式加根"语义冲突）；③ Debug 期配对断言/计数。
- **不做的理由**：①③ 都要**新增公开 API / 诊断**，与本库既定口径（不新增公开 API、不加日志/断言）冲突 —— 与 `F-DOM-003`、G7 剩余 4 条同属"决定不做"类。
- **触发重估条件**：① 口径松动（允许新增一个 C# 侧作用域类型或只读诊断计数）；② 出现"用户忘记 `RemoveFromRoot` ⇒ 长会话内存显著增长"的实测报告（需量化，当前无数据）；③ 插件引入 C# 侧资源管理统一约定时。

## 7. 复用价值（给下一轮）

1. 🟢 **"保活是谁"是 root 审计的唯一判据**：`AddToRoot` 是否多余，等价于问"**除 root 外还有没有 GC 引用**"。两个高频错觉：① "对象在已加载的包里就活着"（**错**，E1）；② "静态 `TMap` 里有指针就活着"（**错**，E2 —— 静态容器不是 GC 根，除非它是 `FGCObject` 或元素是 `TObjectPtr` **且** 该容器参与 `AddReferencedObjects`）。
2. 🟢 **"永久 rooted"类登记必须拆成两问**：① 是否**承重**（无其它引用 ⇒ 不能删 root）；② 是否**累积**（看生成入口有没有"名字在表里就复用"的守卫）。`F-LIFE-004/005` 的误判正是把②当成①。
3. 🟢 **三分类模板**（有配对 / 条件 root / 承重无配对）可直接套用到后续任何 `AddToRoot`、`AddReferencedObjects`、`TStrongObjectPtr` 审计。
4. 🟢 **配对闸门要与创建闸门比对**：站点 #1 的配对之所以成立，是因为创建与解根**同在 `#if WITH_OVERRIDE_BLUEPRINT_NATIVE_EVENT` 内**（宏实测 = 1）。审计"配对"时不能只看函数名，要看 `#if` 边界是否一致（本库已有"漏配套版本门控"的同类先例：`F-CS3-004`）。
5. 🟢 **防御性 `RemoveFromRoot` 是安全 no-op**：对未 root 的对象调用它无害 ⇒ 见到"只有 Remove 没有 Add"时优先考虑引擎侧加根（如 `FInheritableComponentHandler`）或历史遗留清理，不要急着当成"配对缺失"。
