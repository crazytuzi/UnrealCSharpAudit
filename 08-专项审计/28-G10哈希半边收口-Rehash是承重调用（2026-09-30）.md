## 1. 结论摘要（先读这一节）

1. 🔴 **本轮的定性结论：`FSetHelper::Add` / `FMapHelper::Set` 末尾那次 `Rehash` 不是"可以省掉的浪费"，而是"`RemoveAt` 的承重调用"。**
   依据（引擎逐行）：`TScriptSet::RemoveAt`（`Set.h:1867-1885`）**在删除前必须沿着哈希桶链走一遍** ——
   `for (FSetElementId* NextElementId = &GetTypedHash(GetHashIndexRef(ElementBeingRemoved, Layout)); …)`。
   元素里的 `HashIndexOffset` 只由 `Rehash` 写（`:1929`），桶数组只由 `Rehash` 分配（`:1902-1913`）。
   ⇒ 不重建哈希，`RemoveAt` 就会按**垃圾桶下标**去解引用（`GetTypedHash` 是 `((FSetElementId*)Hash.GetAllocation())[HashIndex & (HashSize-1)]`）。**这不是"漏命中"，是解引用崩溃。**

2. 🔴 **实测坐实第 1 条**：同一二进制、`G10H_MODE` 环境变量门控三种形态 ——

   | 模式 | 语义 | 结果 |
   |---|---|---|
   | `legacy` | 原样（每次插入整表 `Rehash`） | 🟢 **1799 / 1799、0 failed**（+ 本轮 11 条 = 1810） |
   | `naive` | 删掉 `Rehash`（= 最直觉的"省掉浪费"） | 🔴 **2/2 确定性崩溃**，无 CSV 产出，`0xC0000005`、`coreclr.dll 42.42.42.42424 @ 0x3584ff`（Windows 事件日志 2026-09-30 00:52:14） |
   | `smart` | 只在桶数需要增长时重建（本轮设计的"引擎同款增长规则"） | 🟢 **1810 / 1810、0 failed**，但**未产生任何收益**（见第 4 条） |

   ⇒ **`naive` 的两次崩溃就是"`Rehash` 是承重调用"的活体证据**（对照 `08-…/25` §8.2 那次探针崩溃：同一 `coreclr.dll@0x3584ff` 偏移）。

3. 🔴 **推翻 `08-…/25` §3.2 的一处依据**：该节写"引擎哈希入口**恰对查找值取哈希**，而 `GetValueTypeHash` 不做句柄解析" ⇒ 推出的结论是"换 `FindValueFromHash`/`FindElementIndexFromHash` 会算错桶（静默漏命中 / 解引用句柄）"。
   本轮读 `UnrealType.h:5728-5737` 发现**引擎自己喂的是元素属性**：
   ```cpp
   FORCEINLINE int32 FindElementIndexFromHash(const void* ElementToFind) const
   {
       FProperty* LocalElementPropForCapture = ElementProp;
       return Set->FindIndex(ElementToFind, SetLayout,
           [LocalElementPropForCapture](const void* Element) { return LocalElementPropForCapture->GetValueTypeHash(Element); },   // ← 元素属性
           [LocalElementPropForCapture](const void* A, const void* B) { return LocalElementPropForCapture->Identical(A, B); });
   }
   ```
   ⇒ **"手柄当原生值哈希"这一条对本调用路径不成立**：`GetValueTypeHash(Element)` 的实参是**存储态**（原生值），只有 `EqualityFn` 才接触**查找缓冲**（句柄），而 `Identical` 正是按"B 是句柄"实现的（第 5 条）。
   ⚠️ **但结论方向不变**：`UnrealType.h:5816` 的 **`FScriptSetHelper` 构造是 private**（只能走 `CreateHelperFormElementProperty`，`:5801`），且它算的 layout 与插件自算的一致（`:5811` 用同一 `FScriptSet::GetScriptLayout(Size, Alignment)`），**该辅助类提供不了插件需要的任何新能力**。

4. 🔴 **本轮的第二个不可行点（本轮设计被自己的实验否掉）**：本想"保留哈希正确性、只按引擎同款增长规则省掉多余重建"（= 复刻 `TScriptSet::AddNewElement`，`Set.h:2023-2047`：只在 `HashSize < GetNumberOfHashBuckets(Num())` 时 `Rehash`）。
   **单容器逐个插入的实测（`[G10HDIAG]`）证明该规则对脚本容器根本省不下来**：`GetNumberOfHashBuckets` 的量级是 `Num/2+8` 向上取 2 的幂（`ContainerAllocationPolicies.h:1397-1405` + 常量 `:1378-1382`），而 `TScriptSet::Rehash` **每次都把 `HashSize` 重设成"恰好 N 对应的桶数"**（`Set.h:1904`）⇒ `Num→Num+1` 后需要的桶数**总是**大于上次重建时的值 ⇒ 增长规则**恒为真**。
   ⇒ 实测：`1024` 元素建表 = **1040 次重建 / 约 52.5 万次哈希调用**（`rehash_hashes` 逐档 384 → **476 263** → **733 342**）；`smart` 与 `legacy` 的计数**逐字相同**。

5. 🔴 **第三个不可行点（真正的硬屏障）**：要做到"插入 O(1)"只有一条路 —— 复刻 `AddNewElement` 的**增量挂链**分支（`:2036-2044`：算 `HashIndex = KeyHash & (HashSize-1)`、写 `GetHashIndexRef`/`GetHashNextIdRef`、把 `GetTypedHash(HashIndex)` 指向新元素）。
   它需要**读 `HashSize`、读写 `Hash` 桶数组**，而这两者与 `GetTypedHash` **全在 `TScriptSet` 的 `private:` 段**（`Set.h:2022` 起，成员声明 `:2052-2054`、访问器 `:2056-2059`），而 **`TScriptSet` 自身一个 friend 都没有**（全文件 friend 仅 `:168`/`:1455`/`:1600`/`:1612`/`:1683`，均非它）；
   `FScriptSetHelper` 自身也**没有**暴露桶数或桶数组（`UnrealType.h:5816` private，公开 API 只有 `Rehash()` / `FindElementIndexFromHash` / `AddElement` / `RemoveElement`）。

### 3.2 ❌ "省掉多余重建"不可行 —— 增长规则对脚本容器恒为真

`TScriptSet::Rehash` 每次都令 `HashSize = GetNumberOfHashBuckets(Elements.Num())`（`Set.h:1904`），而 `GetNumberOfHashBuckets(N) = RoundUpToPowerOfTwo(N/2 + 8)`（`ContainerAllocationPolicies.h:1397-1405`，常量 `:1378-1382`：`/2`、`+8`、`≥4`）。
⇒ 每次插入后"所需桶数"都比上次重建时的 `HashSize` 大 ⇒ 复刻 `AddNewElement` 的条件（`Set.h:2030-2035`）**恒真**。

**实测（`[G10HDIAG]`，同一二进制）**

```
[G10HDIAG] num=1 rehashed=0 legacy=0 cond=1 buckets=1     ← 首次插入，条件真 → 建表
[G10HDIAG] num=2 rehashed=1 legacy=0 cond=0 buckets=1     ← 条件假（但整表重建仍在发生，见 §3.3）
```

**规模判据（`keys` 探针，`-game` 全量套件，本轮新增 1024 元素用例驱动）**

| 257 | 256 | 384 | 256 | 384 |
| 1281 | 1280 | **476 263** | 1280 | **476 263** |

⇒ 两者**逐字相同**："增长规则"这一层**没有省掉任何一次重建**；`1040` 次重建 / 约 `52.5` 万次哈希调用就是 1024 元素建表的真实代价（与 `08-…/25` §5 的"Σ1..N = 524 800"上界吻合）。

## 7. 复用价值（给下一轮）

1. 🔴 **"这个 `Rehash` 能不能省"是 G10 哈希半边的第一道判据，答案是"不能"**：`TScriptSet::RemoveAt`（`Set.h:1867-1885`）依赖桶链。**任何"省掉整表重建"的提案都必须先回答"`RemoveAt` 走哪条链"**。
2. 🔴 **第二道判据是"插件的谓词 vs 引擎的谓词"**：`FScriptSetHelper` 的哈希入口喂的是 **`ElementProp->GetValueTypeHash`**（`UnrealType.h:5734`），只有相等谓词接触**查找缓冲**（句柄）。⇒ 下次要评估哈希路径，先分清"**取哈希的那一侧**"与"**比较的那一侧**"，不要再把 `FindIndex` 的形参签名当作"引擎哈希了查找缓冲"的证据（这正是 `08-…/25` §3.2 的错处）。
3. 🔴 **第三道是"私有成员屏障"**：`TScriptSet` 的 `Hash`/`HashSize`/`GetTypedHash` 是 private，而 **`TScriptSet` 自身不声明任何 friend**（`Set.h:2022/2052-2059`；全文件 friend 仅 `:168`/`:1455`/`:1600`/`:1612`/`:1683`，均非它）⇒ **插件侧的一切增量方案都不可实现**；若维护者愿意改引擎源码，那是"引擎侧任务"，与本库口径冲突，须单独裁定。
4. 🟢 **`G10H_MODE` 环境门控 + 单构建多形态**是本次最有效的手法：**同一二进制**跑出 legacy/naive/smart 三组结果，把"崩溃"与"改代码"之间的因果锁死（`naive` 2/2 崩、其余全绿）。配套要求：门控变量必须用 `#ifndef` 包裹，否则 unity 构建下两份 `.cpp` 合一会 `C2374 redefinition`（本轮实测）。
5. 🟢 **"规模判据"必须是单容器**：套件里 257 次插入分散在约 256 个**独立** helper 上（每个容器首次插入都会建表一次）⇒ 按"累计插入"读到的 `rehash_calls` 会**严重低估单容器的 O(N²)**。正确做法就是本轮新增的 `TestSetLarge`/`TestMapLarge`（1024 元素）——**它同时也把"哈希链维护是否正确"变成了永久回归**（`Remove` 全部 1024 个元素后 `Num()==0`）。
6. 🪤 **探针注入点的两条教训**：① unity 构建下探针标识符要带文件前缀（沿用 `08-…/26` §5 的结论）；② 探针若放进"会被后续补丁整段替换"的代码块里，**替换会把探针一起吃掉**（本轮 `FG10HProbe::Rehash` 首次就落在这个坑里，表现为"两种模式计数完全相同"）。
