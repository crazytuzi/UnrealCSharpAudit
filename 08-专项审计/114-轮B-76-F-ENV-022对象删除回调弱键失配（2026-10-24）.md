## 1. 复现（不依赖 PIE）

在工程侧 `UUnitTestSubsystem.Test()` 里把 `TestEnhancedBindingOwnerRelease()` **连调两次**（临时探针，已还原），套件 CSV 直接复现：

```
EnhancedBindingHandleReleasedOnComponentDestroyed, true     ← 第 1 轮
EnhancedBindingHandleReleasedOnComponentDestroyed, false    ← 第 2 轮
```

`EnhancedBindingOwnerHandleAllocated` / `OwnerReferenceKept` 两轮都是 true ⇒ 绑定成功、owner 引用已登记；**只有"对象销毁后释放"这一步第二轮失效**。两次运行里组件地址完全相同（`0x12ABD24C0`，GC 后复用），PIE 第二次失败与之同源 —— C# 域与插件注册表跨 PIE 存活，等价于"同一进程第二次跑"。

## 2. 根因（引擎源码级）

`UObject::ConditionalFinishDestroy()`（`Obj.cpp:1277-1301`）：

```cpp
FinishDestroy();
GUObjectArray.ResetSerialNumber(this);               // :1290  ObjectItem->SerialNumber = 0
GUObjectArray.RemoveObjectFromDeleteListeners(this);  // :1293  → FCSharpEnvironment::NotifyUObjectDeleted
```

`FWeakObjectPtr` 的哈希/相等是 `index ^ serial` / `(index, serial)`（`WeakObjectPtr.h:172-181`、`:353-360`）。删除回调里用 `InObject` 现造的 `TWeakObjectPtr` 是 **`(index, 0)`**，而 `FObjectRegistry::Object2ManagedHandle` 里存的是**插入时的 `(index, S≠0)`** ⇒ 哈希落不到同一个桶，`Find` **必失配**（相等判据里"两边都 invalid 即相等"的兜底也救不了 —— TMap 先比哈希）。

后果是**两个泄漏**（不止测试那一条）：

| # | 泄漏 | 机制 |
|---|---|---|
| ① | owner 自身的 C# 句柄永不释放 | `FObjectRegistry.cpp:120` 的 `GCHandle_Free(ManagedHandle)` 不执行 ⇒ 包装对象（Normal 强句柄）永久驻留，连同其引用图 |
| ② | owner 名下所有 `FReference` 不析构 | `FObjectRegistry.cpp:122` 不执行 ⇒ `FBindingReference` 不析构 ⇒ `RemoveBindingReference` 不执行 ⇒ 绑定句柄留在 `HandleData.Handles`（PIE 第二次红的那条） |

| 主要隐患 | 覆盖陈旧条目时若句柄仍活会误伤（本轮只清"已死句柄"）；按地址读的消费方语义变化 | "add 时反查 owner"依赖的正是根因破坏的映射；双路径删除需幂等，否则双重 `delete`；`FReference` 加成员动 ABI | 裸指针失去弱指针的自动失效 ⇒ 若删除回调漏掉（关停期）会留陈旧条目、`GetObject(悬垂)` 可能返回旧句柄 |

## 6. 剩余问题与隐患

1. **R 的裸指针别名面**：条目在删除回调里移除，正常路径下"移除先于地址复用"；若某对象**没有**收到删除回调（关停期监听器被摘、或 `RemoveObjectFromDeleteListeners` 未覆盖的路径），会留下陈旧地址条目，后续 `GetObject(悬垂指针)` 可能返回旧句柄。目前靠 `Deinitialize()` 清表兜底；未加"进门版本号"之类的二次校验。
2. **A 只清"已死句柄"**：若同地址上残留的是**仍活**的句柄（C# 包装还活着、native 对象已死），A 不处理 —— 此时 `Add` 会覆盖地址条目，旧 handle 之后 `RemoveReference` 因 handle 比对失败而**跳过地址删除**（不会误删新条目），旧 handle 仍要靠引用析构或 `Deinitialize` 回收。
3. **其它弱键面**：`FCSharpBind::OriginalOwnerClass2DummyOwnerClass`、`NotOverrideTypes` 仍是弱指针键，但都不在删除回调路径上（只在绑定期查），本轮未动；若将来在删除回调里查它们，会踩同一坑。
4. **其它地址键面**：`FStringRegistry`/`FDelegateRegistry`/`FStructRegistry` 都是"地址 → 句柄"，它们已有 `GCHandle_IsAlive` 惰性自愈（`FStringRegistry.inl:33-42` 等），**没有** A 这种"Add 时清理"；地址复用 + 引用未析构时仍可能留陈旧条目（优先级低于本轮修的这条）。
5. **判据边界**：两轮都在同一个 `-game` 世界；PIE 的"新世界 + 旧域"没有直接复跑（同一进程两轮的机制等价已证）。Mono/LeanCLR、打包版未跑。
6. **B 的定位**：本轮未采用 —— 它能让测试变绿，但修不了泄漏 ①，且引入"add 时反查 owner"的循环依赖；只有在不能改 `FObjectRegistry` 键类型时才作为退路。
