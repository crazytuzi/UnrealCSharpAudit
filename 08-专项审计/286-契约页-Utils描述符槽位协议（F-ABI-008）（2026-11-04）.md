### 1.3 解析入口的耦合（本轮新增取证）

- C++ 取指针：`GET_UTILS_FUNCTION_POINTER` → `TypeBridgeGetFunctionPointerFn(程序集名, 类全名, 方法名)` —— **只传名字**（`FCoreCLRDomain.cpp:182-188`、`FMonoDomain.cpp:154-160`）。
- C# 解析：`TypeBridge.GetFunctionPointer` → `Type.GetMethod(名字, Static|Public|NonPublic)` —— **只按名字匹配**（`Script/Interop/Bridge/TypeBridge.cs:78-98`）。
- ⇒ 四种失败模式：
  1. 改 C# **参数列表**（2→3）：指针仍解析成功，按旧 ABI 调用 ⇒ **未定义行为**；
  2. 加**同名重载**：`GetMethod` 抛 `AmbiguousMatchException`（`[UnmanagedCallersOnly]` 边界 ⇒ fail-fast）；
  3. **槽位增删/换序**：静默错读（无任何校验）；
  4. **槽位增加超出容量**：descriptor 已满 15 槽 ⇒ 第 16 槽即**越界写**（members 侧的 `Init(InSlotCount + 1)` 同样精确）。
- `IScriptTypes.h:177-180` 的 `ParamCount = 2` **不参与** CoreCLR/Mono 的 Utils 指针解析（该字段只服务 LeanCLR 的 `Class_Get_Method_From_Name` 路径）⇒ 不要误以为它提供了 arity 保护。

## 2. 扩展政策（任何槽位变更必须按此执行）

1. **不改既有方法**：新增/变更槽位一律走**版本化方法**（如 `GetClassDescriptorV2`）＋ 新 `FUNCTION_*` 常量 ＋ 新 `Op(...)` ＋ 新 `typedef`；旧方法与旧路径保留。
2. 若确需扩现有方法：**同时**改四处 —— ① C# 写入表；② C++ `Params[]` 容量；③ C++ 解析下标；④ `Free()` 清单；并用套件（1 991 例，反射加载为每次绑定必经路径）验证。
3. **禁止只加 C# 槽位**（descriptor 15 槽已满）。
4. 整数槽与句柄槽必须按 §1.2 区分。

## 3. 为什么本轮不改代码

| 审计建议 | 撞的规 | 结论 |
|---|---|---|
| ① 把槽位数作为参数传给 C#（改签名） | G7「重命名或改签名既有公开 API」 | 不可行 |
| ② `static_assert` / `Debug.Assert` | G7「新增断言」 | 不可行 |
| ③ `check(InSlotCount == Params.Num() - 1)` | G7「新增断言」 | 不可行 |
| 命名化（两侧定义一个常量集） | 不能阻止漂移；且 B-187 有"命名化被维护者撤回"的先例 | 本轮只写入契约，不施工 |

⇒ 协议当前**没有可观测缺陷**（数值匹配、无越界），所有加固手段都被 G7 封死 ⇒ **维持现状 ＋ 契约**是唯一合规终局。

## 4. 触发条件（出现任一即重新立项）

1. 任何一侧需要增删/重排槽位 ⇒ 必须先按 §2 执行，**不允许顺手加**。
2. 出现 `AmbiguousMatchException`（新增同名重载）或反射加载后类描述符错乱（字段/属性/方法数量对不上）⇒ 立项排查。
3. G7 口径放开"桥接口版本化"或"常量断言" ⇒ 重新评估审计的 ①②③。
4. 平台从 64 位扩展到 32 位（协议隐含 `reinterpret_cast<PTRINT*>` 与 `nint*` 同宽假设）⇒ 复核 `IManagedHandle` 与 `PTRINT` 宽度一致性。
