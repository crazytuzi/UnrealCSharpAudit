## 2. 两条贯穿前提（逐版证据）

### 2.1 C++ 标准：5.0–5.2 = C++17，5.3 起可按 V4 设置默认 C++20

| 版本 | 证据（`Engine/Source/Programs/UnrealBuildTool`） |
|---|---|
| 5.0.3 | `Platform/Windows/VCToolChain.cs:765` 只 `Arguments.Add("/std:c++17")`；`:783` 的 `// Arguments.Add("/std:c++20");` **被注释掉**（注释原文："Will be added when MSVC is feature-complete."） |
| 5.2.1 | `:914` `c++17` 与 `:917` `c++20` **两个分支都在**（可显式选 C++20，但默认仍是 C++17） |
| 5.3.0 起 | 同样两分支；`TargetRules` 的 `BuildSettingsVersion.V4` 起把默认标准推到 **C++20**（"Updates C++ Standard to C++20 (Previously: CppStandardVersion.Cpp17)"） |

⇒ **插件的红线**：源码必须 **C++17 可编**（宿主工程的 `BuildSettingsVersion` 与 `-CppStd` 都可能把它拉回 17）。本轮的 4/5 两类错误正是这条红线的违反。

| 版本 | 头文件路径 |

### 🔴 本轮自己踩的坑（只有 5.0 实编才能发现）

第一版 `#else` 分支我**照抄了 FString 先例的实参形态**：`RemoveAt(Index, false)`。5.0 实编立刻报：

```
Array.h(1665): error C2338: static assertion failed: 'TArray::RemoveAt: unexpected bool passed as the Count argument'
```

**原因**：`TArray` 在 5.0 只有 `RemoveAt(SizeType Index)` 与 `RemoveAt(SizeType Index, CountType Count, bool bAllowShrinking = true)` 两个重载 ⇒ 第二实参位置是 **Count**，传 `false` 会被当成"Count = bool"并被 `static_assert` 挡下。而 FString 的先例之所以能写 `false`，是因为它的 bool 在**不同位置**（`LeftChopInline(Count, bool)`／`RemoveAt(Index, Count, bool)` 的第 3 位）。⇒ 正确写法是 **`RemoveAt(Index, 1, false)`**（Count＝1、不收缩），修后 5.0 编过。
**教训**：**"沿用既有先例"必须连形参位置一起核**；`static_assert` 是引擎给的免费判据，但它只在**目标版本**上才会触发 —— 这也是本轮坚持做 5.0 实编的直接收益（否则这个错误会在维护者那台机器上再弹一次）。

## 5. 登记与残留面

1. **5.0 上增强输入守卫的精度差异**：`HasActionEventBinding` 在 5.0 退化为 (action, trigger) 二元匹配 ⇒ 同一 `UEnhancedInputComponent` 上由**不同对象**绑同一 action+trigger 时，第二个会**被误判为重复**并返回 `InvalidManagedHandle`。**为什么不用派生模板的公开 `Delegate`**：`FEnhancedInputActionEventDelegateBinding<TSignature>` 是按签名实例化的模板，遍历时拿不到 `TSignature`，`static_cast` 到任选实例化都是 UB（引擎自身绑定与用户绑定可能共存于同一数组）⇒ 放弃；**未在 5.0 实机验证该差异的实际发生概率**（需 5.0 工程跑输入用例）。

## 6. 复用价值（方法论）

1. **"本机编得过"只等于"一个版本编得过"** —— 本条的 8 个错误在 5.6/C++20 上**一个都不出现**；审计库（在 5.6 上做）也只提到过其中 2 类（`EAllowShrinking`、`[=, this]`）而**从未编译验证**。⇒ 支持区间写在文档里，就必须有一次**最低版本的真实编译**。
2. **报错先分"语法面"与"API 面"**：`C3791`/`C7585` 是**语言标准**问题（与引擎版本只是间接相关：UE 5.0–5.2 默认 C++17），`C2039`/`C2653`/`C2248` 是**API 可用性/可见性**问题（要逐个查引入版本），`C2665` 是**模板约束**问题（同一签名在 5.0 与 5.6 都"存在"，但可接受的实参值类别不同）。三类的修法完全不同：语法面→**改写成两版通用的写法**（不需要门控）；API 面→门控＋回退；模板面→**改变实参的值类别**（`MoveTemp`）而不是加门控。
3. **门控宏的"支持起点"必须逐 tag 取头文件**：`git show <tag>:<path>` 十秒一条，比"凭印象写 5.3"可靠；本轮正是靠它纠正了两个容易写错的边界 —— `EAllowShrinking` 是 **5.4**（不是"5.5"，那是 `FString::RemoveAt` 的边界，仓库里已有宏），`IsBoundToObject` 是 **5.1**（不是 5.6，5.6 只是把形参类型换成 `FDelegateUserObjectConst` 并**新增**了 `GetUObject`）。
4. **能用"两版通用写法"就不要开门控**：`MoveTemp`、`[this]`、把 init-statement 提出来 —— 三处都**零版本分支**解决了问题；只有"旧版没有等价 API"（`EAllowShrinking`、`IsBoundToObject`/`GetUObject`、`UpdateCanTick` 可见性）才需要 `#if`。
5. **最小检查工程是"最低版本编译"的低成本装置**：一个 4 文件的 `.uproject` ＋ 插件 `Source/` junction，就能在**不改本仓**（产物写在检查工程内）的前提下把插件按 5.0 头文件编一遍；⚠️ 唯一必须处理的差异是 `.uplugin` 里的 **5.5+ UBT 插件模块**（5.0 UBT 不识别）。
6. 🔴 **"沿用既有先例"必须连实参位置一起核**：同为"`EAllowShrinking` ↔ `false`"的兼容分支，`FString` 的 bool 在第 2/3 位、`TArray` 的 bool 在第 3 位（第 2 位是 `Count`）⇒ 照抄先例写出 `RemoveAt(Index, false)` 会被 5.0 的 `static_assert('TArray::RemoveAt: unexpected bool passed as the Count argument')` 当场拦下。**这是本轮 5.0 实编唯一的收益点，也是"必须在目标版本上编"最直接的证明。**
