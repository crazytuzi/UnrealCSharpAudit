## 4. 边界与残余

1. **编码假设仍在**：新管道仍按 **UTF-8** 解码子进程输出。本轮只把 **UI 语言**固定成英文（ASCII），没有处理"子进程按 GBK 输出"的系统（中文 Windows 下 MSBuild 的**非** UI 文案、文件路径含中文时仍可能乱码）。真正根治需要 `ReadPipeToArray` 后按代码页探测（`IsValidUtf8` 再退回 `FANSIToTCHAR`），未做。
2. **`GetDotNet()` 的候选只覆盖常见位置**：不查注册表、不解析 `dotnet --list-sdks`；PATH 里没有、`DOTNET_ROOT`/`%LOCALAPPDATA%` 也没有时仍回落到硬编码值（与原行为一致）。
3. **语言作用域只覆盖两个 dotnet 调用点**：`FCodeAnalysis` 里那次 `dotnet build`（其输出不参与 MSBuild 文案解析）没有包 scope；若将来需要，直接用 `Common/FEnvironmentVariableScope.h` 即可（已在 Core 公共头目录）。
4. **恢复是"写回原值"而非"取消设置"**：UE 没有 unset 环境变量的 API，原值为空时析构会把变量恢复成空串（探针读数 `AFTER=[]`），语义等同"未设置"。
5. **收尾单次读的取舍**：直接子进程退出后管道里剩余字节有界（被管道塞满阻住的写者退不出去），一次 `ReadPipeToArray` 会全部取走；若**后代进程**仍持有写端并继续写，单次读之后的尾部输出会丢 —— 这是换取"无循环、必然返回"的代价（改前是一次 `ReadPipe`，同样会丢）。
6. **通知文案未截图取证**：`ShowCompileResultNotification` 的标题拼接只做了代码级判据（首错行提取函数 + 调用点），UI 实际渲染未截屏。
7. **实编覆盖 Windows / UE 5.6 / UE 5.0 / CoreCLR**；非 Windows 分支（`:` 分隔、`dotnet` 无扩展名）未实跑。
