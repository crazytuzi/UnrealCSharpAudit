**为什么刷新在广播之后（而不是之前）**：`Dynamic.json` 是监听者在 `OnCompile` 里通过 `FCodeAnalysis::Analysis(File)`（同步外部进程）逐文件写出的 ⇒ 编译器必须在广播**之后**读盘刷新，才能读到本次编译的分析产物。顺序因此变成**显式三步**：`Broadcast` →（监听者写 JSON）→ `SetCodeAnalysisDynamicFilesMap`（编译器）→ 判定/生成。

**未新增**：注释 0 / 日志 0 / `throw`·`try-catch` 0 / 公开 API 0 / 引擎接口调用 0（`IsRunningGame()` 与 `FDynamicGenerator::SetCodeAnalysisDynamicFilesMap()` 都是仓内既有调用，前者在 `FEngineListener` ctor 已用）。新增行 `AddedMax` = **82 / 57**（< 110）。

## 2. 语义变化与影响面（必须读）

### 2.1 V1

- **`-game`（editor 二进制）**：不再被 `IsScriptPublishOutdated()` 挡住 ⇒ **会用"存在但可能旧一点"的发布程序集启动**。缺件仍由既有 `IsAssembliesFileExists()`（B-1 的 fail-closed）拦住；`Shared.props` 缺失时该函数本就提前返回 false（不受影响）。
- **交互式编辑器**：`IsRunningGame() == false` ⇒ **条件与改前逐字等价**（无行为变化）。证据：`FEngineListener` ctor 在交互编辑器选择 `OnPostEngineInit` 分支（而非 `OnLoadingPhaseComplete`），说明该判据为假。
- **打包版**：走 `#else` 分支（无此判据）⇒ **不受影响**。
- ⚠️ **残留**：`-game` 不再有任何"发布陈旧"信号 —— 需要"陈旧即失败"的 CI 只能靠外部（改前/改后都不提供，属既有缺口，本轮未改变）。

### 2.2 V2

- **生产者/消费者拆分**：`FEditorListener::OnCompile` 仍负责**生产** `Dynamic.json`（逐文件 `FCodeAnalysis::Analysis`，同步外部进程）；`FCSharpCompilerRunnable` 负责**消费**（刷内存表）。⇒ "顺序未定义"变成"显式三步"。
- **仍存在的边界**：若**监听者完全缺失**（或 `CompilingFileChanges` 为空导致不分析），刷到的是**旧 JSON** ⇒ 仍会 `dynamic=0`。这是"生产者缺失"，**不再是"顺序竞争"**；本轮未构造该场景（登记）。
- **工具栏两处调用保留**（`UnrealCSharpBlueprintToolBar.cpp:24/:53`，属不同生命周期点，未动）。
- **成本**：每次成功编译多一次 JSON 读盘 + 解析（该表 2.5 KB 级，B-8 记录的实测口径 = 12 条）；相对 `dotnet build` 秒级 wall 可忽略（**未单独计时**，登记）。
