## 1. 这两条到底是什么（一句话）

两条的**共同病根都是"静默失效"**：
- **`F-PROP-007`**：`FFieldPathPropertyDescriptor` 零覆写 ⇒ C# 侧 `TFieldPath<T>` 属性**读恒 `null`、写静默丢弃**。上一轮已把它的可达性从"待裁定/不可达"翻转为**活跃**（native 快速返回绕过生成器排除）；本轮按维护者选择走**路线②（补实现）**，让这条路真正可用。
- **`F-PROP2-011`**：稀疏委托在**只读**路径上伪造一个绑到 `nullptr` 的 `Dummy` 委托并落库 ⇒ 引擎侧 `bIsBound` 被永久置真、全局稀疏委托表被污染。本轮拆掉伪造，并把**写路径**（`Set` 与包装层 `Add`）改为走引擎真接口，避免"从静默污染变成静默丢失/硬崩"。

## 3. 逐条核查与设计取舍（含与调查报告的偏差）

### 3.1 生成器**不需要改**（路线② 的一半工作量被前一轮的结论省掉）

`FGeneratorCore::IsSupported(FProperty*)` 的 `:777` `if (bIsGenerateAllModules && Property->IsNative()) return true;` 让 `:888` 的 FieldPath 排除对 native 属性失效；而**导出选择只按"容器种类"二分**（UCLASS → `FProperty_{Get,Set}ObjectPropertyImplementation`，USTRUCT → `…StructProperty…`），与属性类型无关（实测产物：Object 22 695 对 / Struct 20 873 对，零例外）。因此地址解析本来就正确，本轮**一行生成器代码未改、产物未重生成**（避开 `EndGenerator(bIsFull=true)` 的 107 文件静默清扫）。

### 3.2 `FFieldClass::GetName()` **不含前导 `F`** —— 两侧约定必须同向

引擎 `Field.cpp:46-57`：`FFieldClass::FFieldClass(const TCHAR* InCPPName, …)` 里 `check(InCPPName[0] == 'F'); Name = ++InCPPName;` ⇒ `GetName()` 返回 `"Property"` / `"StructProperty"`。生成器写的是 `TEXT("TFieldPath<F%s>")`（`FGeneratorCore.cpp:258`），即**自己补 F**。本轮 `GetClass(const FFieldClass*)` 照此约定写 `FString::Printf(TEXT("F%s"), *InFieldClass->GetName())`，与产物里的 `Script.Reflection.Property.F*` 标记类对齐（实测 6 个类型实参：`FProperty` 38 处、`FArrayProperty`/`FStructProperty` 各 6、`FMapProperty` 4、`FMulticastDelegateProperty` 2、`FField` 1）。

### 3.3 值表示：句柄型包装 + "字段 token"

C# `Script.Reflection.Property.F*` 是 **9 个零成员的标记类**（无句柄、无注册）⇒ 不能直接当值。本轮把 `TFieldPath<T>` 做成**句柄型包装**（照 `TArray<T>`/`TOptional<T>` 范式：ctor 注册 + 终结器注销 + 全部操作走原生导出），并新增一个**字段 token 表**（`FField* ↔ IManagedHandle`，弱句柄、按需重建）让 `Get()` 返回的 `T` 有意义（可 `Set` 回同一路径 ⇒ 往返可用）。token 的 C# 类是**运行时按字段实际类**解析出来的（`FStructProperty` → `FStructProperty` 标记类），因此 `TFieldPath<FProperty>`（基类）与 `TFieldPath<FStructProperty>`（派生）都能正确转型。

### 3.4 所有权与内存（照 `FStringRegistry` 家族）

`FFieldPathAddress : TValueWrapper<FFieldPath*> + TOwnedValue`：
- `Get(FMember)` = **别名**（`IsNeedFree=false, IsMember=true`）：直接指向对象内的 `FFieldPath` 槽，并登记"地址→句柄"以便复用同一包装；
- `Get(FReturn)` = **副本**（`IsNeedFree=true, IsMember=false`）：`Src` 是 `CopyValue`（`Malloc`+`InitializeValue`+`CopySingleValue`）出来的堆块，`RemoveReference` 时 `Value->~FFieldPath(); FMemory::Free(Value)`（与上一轮 `F-PROP2-003` 的修法同形）；
- `Set` 沿用族约定（`InitializeValue` + `SetPropertyValue`），**活值泄漏由上一轮在调用点补的 `DestroyValue` 兜住**（`FRegisterProperty.cpp` / `FOptionalHelper.cpp`）。

### 3.5 `F-PROP2-011`：删伪造必须**同时**改写路径（否则从"静默污染"变"硬崩"）

调查报告逐函数确认：包装层（`FMulticastDelegateHelper` → `UMulticastDelegateHandler`）对"目标为空"是**显式支持**的（`bNeedFree` 自建游离委托），**唯一**无守卫的裸解引用在 `FMulticastDelegatePropertyDescriptor::Set`（`GetMulticastDelegate(Dest)` 后直接 `->Add`）。所以本轮：
1. 删除 sparse 覆写（连带删除该 `.cpp`，23 行 → 0）⇒ 读路径不再写对象状态、不再污染全局稀疏表；**附带收益**：helper 不再持有全局表内部对象的裸指针（原本靠 `Dummy` 把条目永久钉住才掩盖了潜在的 UAF）。
2. `Set` 增加"目标为空"分支（`Property->SetMulticastDelegate(Dest, {单条真实绑定})`）——引擎对稀疏委托**只对已绑定的委托落库**，所以这一支正好是"替换语义"的正确实现；inline 分支行为不变。
3. 包装层 `Add/AddUnique` 增加"物化"分支：游离委托 + 已知属性地址 ⇒ `Property->AddDelegate(ScriptDelegate, nullptr, Address)`。**引擎侧实测可行**：`PropertyMulticastDelegate.cpp:662-679` 在 `Parent == nullptr` 且 `PropertyValue != nullptr` 时用 `FSparseDelegateStorage::ResolveSparseOwner` 从属性地址反推 owner（偏移表在 `Class.cpp:5000-5006` 建表）；inline 侧 `:479-487` 根本不看 `Parent`。唯一硬约束是 `PropertyValue != nullptr`（本分支恒真）。

### 3.6 与调查报告的偏差（3 处）

1. **"只改 `GetMulticastDelegate` 即可"不完整**：调查报告的"最小结论 1+2"已覆盖 `Set` 的守卫；但**包装层 `Add`** 若不改，C# 侧 `obj.MySparseDelegate.Add(...)` 会写进游离委托（引擎不可见）——这是**功能性回归**，故本轮补了第 3 项改动。
2. **`Identical` 不需要改成 `Property->Identical(A, FieldPath, …)` 之外的东西**：`FMulticastDelegateProperty::Identical` 对 `B == nullptr` 安全返回 `A == B`（`PropertyMulticastDelegate.cpp:120-125`），因此"空目标"进入比较路径也不会崩（本轮未改）。
3. **`FReturn` 的 token 解析用 `FField::StaticClass()`（宽类）**：C# 侧 `TFieldPath<T>.Get()` 在引擎里是 `GetTyped(T::StaticClass())`；本轮原生不持有 `T`，改用最宽的 `FField::StaticClass()` 解析（`ResolveField` 的默认实参同值）。后果：若路径指向的字段**不是** `T` 的子类（引擎保证不会），C# 转型会抛 —— 已在 §6 记为未实测项。

1. **已解析路径（非空 `FFieldPath`）的往返未实测**：`Get()` 的字段 token 解析、`Set(token)`、`TFieldPath<T>(T)` 构造都**没有被套件覆盖**（本轮 4 条用例走的是"空路径"语义）。要取得需在 C++ 侧构造一个已解析路径并暴露给 C#——加 `UPROPERTY` 会牵动 proxy 重生成（`EndGenerator(bIsFull=true)` 的 107 文件清扫风险），本轮**未做**。⇒ ⚠️ **范围已收窄（维护者质疑后补做探针）**：「字段类 → C# 类」这一段映射**已实测通过**（§5 探针行：`FProperty`→Handle 36、`FStructProperty`→Handle 44，`Class->NewObject(true)` 成功）⇒ 仍未取得的部分只剩**路径解析（`GetTyped`）+ token 的复用/往返**。
2. **`Identical` / `Reset` 两个导出未被套件覆盖**（无用例）。
3. ✅ **`F-PROP2-011` 的改前/改后对照已取得**（§3.10，维护者质疑后补做）：整组回退 7 个 delegate 文件到 HEAD → 重编 → 跑测 ⇒ **1720 行 / 1 失败**（`SparseDelegateIsBoundFalseWhenPristine = false`，即改前"未订阅的稀疏委托也报已绑定"）。⚠️ 但**"引擎侧污染"本身仍未被直接观测**：本轮的判别式是**经由 C# 可见的 `IsBound()`**（改前因伪造条目而为 true），并未用原生探针去读 `FSparseDelegateStorage` / `bIsBound` 的原始状态；且 11 条用例里只有 1 条是判别式，其余 10 条是写路径回归护栏。

6. **新增导出面未做"装配-原生一致性"校验**：若 C# 侧 `partial` 桥名与原生 `FClassBuilder` 名不匹配，只会在**运行期**表现为 `MethodBridge.GetMethod` 取不到函数（本轮的 4 条用例覆盖了 `Register1`/`IsValid`/`Get` 三条桥，`Register2`/`Set`/`Reset`/`Identical`/`UnRegister` 未验证）。

## 7. 复用价值（给下一轮）

- 🎯 **跨版本兼容可以"用引擎自己的 git 仓库判定"，不必读文档**：本机引擎是 git 仓库（`D:/file/UnrealEngine/5.6`，`release` @ `803688920e03 5.6.0 release`，tag 覆盖 5.0.0/5.0.3 → 5.7.0-preview-1）⇒ 对任一 API 直接 `git show 5.0.3-release:Engine/.../<file> | Select-String <符号>` 就能拿到"5.0 到底有没有、签名是否一致"。本轮据此确认 **`AddDelegate(FScriptDelegate, UObject*, void*)` 与稀疏委托的"未绑定 ⇒ nullptr / 只对已绑定落库"在 5.0.3 就已存在** ⇒ 新代码无需 `UE_F_*` 宏（这条若靠记忆/文档很容易误判成 5.2+ 才有的 API，从而白写一层版本分支）。
- 🔴 **C# 侧发布链是三段式，且 `IsScriptPublishOutdated()` 不看源码时间戳**：`Script/UE/**`（源）→ `dotnet build Script/Script.sln -c Debug`（写 `Content/Script/{UE,Game,Interop}.dll`）→ 编辑器加载。判据只比 **`Script/Shared.props`** 与产物时间戳（`FUnrealCSharpFunctionLibrary.cpp:1275-1303`）⇒ **改 C# 源不会自动重编**。本轮第一次跑测因为人工 touch props 触发了启动期 `SyncCompile`（>25 s），被 harness 的 settle 窗口判为"跑完"而**产出空 CSV（0 行）**—— 处置：先手动 `dotnet build`，再把 props 时间戳压回产物之前。🆕 **判据**：**空 CSV（只有表头）= 套件根本没跑**，不是"0 失败"；先看 `LogUnrealCSharp` 行数是否为 0。
- 🔴 **新增一个 C# ↔ 原生桥要对齐四处**：原生 `FClassBuilder(TEXT("TFieldPath"), NAMESPACE_LIBRARY).Function("Get", …)` ↔ C# 静态类名 `TFieldPathImplementation` ↔ C# `partial` 声明 `private static unsafe partial … __TFieldPath_GetImplementation(...)` ↔ 源生成器按 `命名空间.类::方法` 生成实现。任一处不一致 ⇒ **运行期**才失败（编译期无感）。
- 🎯 **`FFieldClass::GetName()` 无前导 `F`**（`Field.cpp:56-57` 的 `Name = ++InCPPName`），而生成器写 `TFieldPath<F%s>` 自己补 F —— 引用字段类名做映射时必须先确认这一约定，否则会得到 `FFStructProperty` 这种不存在的类型。
- 🎯 **删掉"伪造"必须同时补写路径**：`F-PROP2-011` 的伪造之所以"看起来能用"，是因为它把稀疏委托的写路径也一并糊住了（`Set` 直接解引用、`Add` 写进游离委托）。任何"删除伪状态"的修复都要先枚举**依赖该伪状态**的写路径，否则从"静默污染"直接变成**硬崩**或**静默丢失**。
- **引擎侧 `Parent == nullptr` 可用**：`FMulticastDelegateProperty::{Add,Remove,Clear}Delegate` 允许 `Parent=nullptr` + 合法 `PropertyValue`（sparse 用 `FSparseDelegateStorage::ResolveSparseOwner` 从属性地址反推 owner；inline 忽略 `Parent`）⇒ 包装层**不需要**去别处找 owning UObject。
- 🔴 **归档补丁必须用 raw 字节写，否则"能看不能用"**：PowerShell 的 `git diff ... > x.patch` 默认写 **UTF-16LE（带 BOM）** ⇒ 文件内容看起来正常、`Get-Content` 比对也一致，但 `git apply` 会直接报 `No valid patches in input (allow with "--allow-empty")`。本轮就是因为拿这种补丁回退 delegate 改动才暴露出来（`git apply` 失败、只能手工还原）。**正确写法**：`cmd /c "git diff -- <paths> > x.patch"`（raw 字节），并**必须**用 `git apply --check --reverse <x.patch>` 自检可应用性；上一轮的 `fix-G11-set-semantics.patch` 也按 `git diff 77867446 fca72a8c` 重新导出为 UTF-8。
- 🎯 **C# 侧委托的"可控判据"**：`Script/UE` 产物里的**引擎委托属性**（`UActorComponent.OnComponentActivated`＝稀疏、`UButton.OnClicked`/`UPrimitiveComponent.OnComponentHit`＝内联）可以直接当测试靶子——用 `Unreal.NewObject<T>()` + `IsBound()` + 引擎自身广播（`Activate(true)`）就能覆盖"读 / Add / 赋值 / 引擎回调到 C# 处理器"全链路，**既不需要新增 `UPROPERTY`、也不需要重生成 proxy**；⚠️ 但**要挑非 abstract 的具体类**（`UActorComponent` 是 `UCLASS(abstract)`，`NewObject` 会触发 `FScopedAllowAbstractClassAllocation` 断言 + `SEHException`，编译期完全看不出来）。
- **对照实验的最小形态**：本轮用"临时把新实现改回空实现 + 重编 + 跑测"拿到 `2/4 失败` 的对照，成本约 4 分钟（1 次构建 + 1 次跑测），可证明**新用例是敏感的**（否则新用例可能只是恒真的假绿灯）；delegate 侧同样做法（整组回退 7 文件）拿到 `1/11 失败` ⇒ **判别式 1 条 + 回归护栏 10 条**，两类用例的价值要分开陈述。
