## 2. 引擎 canonical 写法（`FScriptSetHelper`，5.6 `UnrealType.h:5748-5778`）

```cpp
Set->Add(ElementToAdd, SetLayout,
    [Prop](const void* E) { return Prop->GetValueTypeHash(E); },
    [Prop](const void* A, const void* B) { return Prop->Identical(A, B); },
    [Prop, ElementToAdd](void* NewElement)
    {
        if (Prop->PropertyFlags & CPF_ZeroConstructor) FMemory::Memzero(NewElement, Prop->GetSize());
        else Prop->InitializeValue(NewElement);
        Prop->CopySingleValueToScriptVM(NewElement, ElementToAdd);
    },
    [Prop](void* Element)
    {
        if (!(Prop->PropertyFlags & (CPF_IsPlainOldData | CPF_NoDestructor))) Prop->DestroyValue(Element);
    });
```

⇒ 关键规则：**新元素先初始化/清零，再从源拷贝；销毁按 POD/NoDestructor 条件**。

## 3. 为什么直接移植会失败（本轮实验）

C# 侧 `TSet.Add(T)`（`Script/UE/CoreUObject/TSet.cs:101-122`）：

| `T` 类别 | 传入原生缓冲的内容 |
|---|---|
| 值类型（`int` 等） | **原生值本身**（`stackalloc byte[sizeof(T)]; *(T*)buf = InValue`） |
| 引用类型（`UObject` 等） | **托管句柄**（`*(nint*)buf = HandleData.GetHandle(InValue)`） |

而插件的描述符对这层差异是"半转换"的：

- `FObjectPropertyDescriptor::Set(Src, Dest)`：把 `Src` 当 **`IManagedHandle*`** → 取对象 → 写入原生 `Dest`（所以插入这一步是"句柄→原生"）；
- `FPropertyDescriptor::Identical(A, B)`：直接 `Property->Identical(A, B)`（B 仍是**句柄缓冲**）——旧实现是"原生 vs 句柄"的**混合比较**；
- 新实现把同一缓冲交给 `GetValueTypeHash` 求哈希 ⇒ 对 `TSet<UObject>` 哈希的是**句柄整数**，而表里存的是**对象指针** ⇒ 桶不一致 ⇒ 4 条测试同时失败（重复判断/删除/包含全部失真）。

> 这也解释了 B-153 当年"用 `FScriptSetHelper::AddElement` 两次崩溃"：那条路径用 **`CopySingleValueToScriptVM`** 从"句柄缓冲"拷原生值，语义与插件描述符的 `Set` 不等价。

## 4. 正确设计（B-288 实施）

### 4.1 原则

1. **统一在原生值上做 hash/相等/构造**：每次调用先把值缓冲转成一份**原生暂存**（scratch）；
2. scratch 的生命周期与大小/对齐由 `ElementPropertyDescriptor->GetProperty()` 的 `GetSize()/GetMinAlignment()` 决定；
3. 构造/销毁遵循引擎 canonical 规则（§2）；
4. **不新增公开 API**（G7）：scratch 作为 `FSetHelper` 的 `mutable` 私有成员，或函数内 RAII 临时；
5. 不新增日志/断言/异常/注释。

### 4.2 伪代码

```cpp
// 1) 取原生暂存（成员或函数内 RAII）
FProperty* ElementProperty = ElementPropertyDescriptor->GetProperty();
void* Scratch = /* FMemory::Malloc(GetSize(), GetMinAlignment())，或缓存的 mutable 缓冲 */;

// 2) 值缓冲 -> 原生值（对象属性在此完成 句柄->UObject*）
ElementPropertyDescriptor->Set(InValue, Scratch); // 现有 Set 语义正好是"缓冲->原生"

// 3) 哈希 / 相等都只作用于原生值（Scratch 与表内元素）
auto HashFn = [this](const void* E) { return ElementPropertyDescriptor->GetValueTypeHash(E); };
auto EqFn   = [this](const void* A, const void* B) { return ElementPropertyDescriptor->Identical(A, B); };

// 4) 插入（仅缺席时构造）
ScriptSet->FindOrAdd(Scratch, ScriptSetLayout, HashFn, EqFn,
    [ElementProperty, Scratch](void* Dest)
    {
        if (ElementProperty->PropertyFlags & CPF_ZeroConstructor) FMemory::Memzero(Dest, ElementProperty->GetSize());
        else ElementProperty->InitializeValue(Dest);
        ElementProperty->CopySingleValueToScriptVM(Dest, Scratch);  // 原生 -> 原生
    });

// 5) 删除：FindIndex(Scratch) -> DestroyValue -> RemoveAt
// 6) Contains：FindIndex(Scratch) != INDEX_NONE
```

### 4.3 需要确认的点（实施前）

| # | 点 | 处置 |
|---|---|---|
| 1 | `Set` 对**值类型**缓冲是"原生→原生"（直接拷贝）还是也做转换 | 读 `FStructPropertyDescriptor`/primitive `Set` 实现确认；若已是拷贝即可统一 |
| 2 | `CopySingleValueToScriptVM` 在 5.0/5.8 的签名/可用性 | 三档 grep `CopySingleValueToScriptVM`；不可用则改 `CopyCompleteValue` |
| 3 | scratch 缓存的失效面 | 每 helper 一份（`GetSize()/GetMinAlignment()` 固定），无失效问题 |
| 4 | `RemoveAt` 依赖的 HashIndex 一致性 | 插入全部走 `FindOrAdd`（哈希由我们维护）⇒ 一致；`bNeedRehash`/`EnsureRehash` 可退役 |

## 8. B-288 实施记录：scratch 版仍不安全（已回滚）

> 2026-11-17 追加：按 §4 设计实现"值缓冲 → 原生 scratch → 原生值上 hash/相等"，仍失败并出现崩溃，**第二次回滚**。

| 项 | 读数 |
|---|---|
| 改动 | `FSetHelper.h` `+4`（`ValueBuffer` 成员 ＋ `PrepareValueBuffer` 声明）、`FSetHelper.cpp` `+60 −35` |
| 做法 | ctor 按 `GetSize()/GetMinAlignment()` 分配并清零 `ValueBuffer`；每次调用 `DestroyValue(scratch)` → `Set(InValue, scratch)`；`FindOrAdd`/`FindIndex` 用 scratch 的 hash/相等；插入的 `ConstructFn` 仍用 `Set(InValue, InDest)` 保留旧语义 |
| 5.6 构建 | `Succeeded`（74.35 s） |
| §8 / §7 | `PASS` / `CLEAN` |
| **套件** | run#1 **崩溃**（`exit -1073741819` = `0xC0000005`，无 CSV）；run#2 产出 CSV 但 **3 失败**（`SetCompoundAddFalse` / `SetCompoundRemoveTrue` / `SetCompoundContainsTrue`，SHA `520736A8…`） |
| 回滚 | 恢复 `FSetHelper.h/.cpp` 备份 → 强制重编 → 套件 **1 983 / 0 / `A4BFF990…`**（基线恢复） |

**结论（第二次）**：`Set(InValue, scratch)` 在 `TSet<UObject>` 上仍未得到与表内元素一致的"原生值"——失败形态（重复判重失败、按对象删除/包含失败）指向 **描述符 `Set` 的 handle→native 转换结果与元素存储语义不一致**（或 scratch 初始化/销毁在某些元素类型上破坏内存，即那次 AV）。在拿到**逐类型的探针读数**（同一 handle 经 `Set` 后的 native 指针 vs 表内元素指针）之前，**不再盲改**。

**下一步（B-289 门槛）**：先在 C++ 侧加一个**临时探针**（交付前删除），对 `TSet<UObject>` / `TSet<int>` / `TSet<FString>` 三类元素分别打印「handle → Set → native」与「表内元素」的指针/字节，确认转换是否恒等；确认后再决定"修 `Set` 语义 / 引入独立 hash 入口 / 放弃该优化"。
