## 0. 结论摘要

1. **原「复测待办」结案（机制已定，不是"测试面/时序因素"）**：
   `RawMethodHelperOutGetObjectFunction` / `RawMethodHelperOutGetClassFunction` 的失败，
   是 **`nullptr` 实参被换成"已销毁对象的存活托管包装"**。第一层在 C++ 侧
   （`FCSharpBind::Bind(nullptr)` 经弱指针为键的注册表查询命中残留条目），第二层在托管侧
   （强 `GCHandle` 让该包装永不回收）。
2. **与脚本后端无关**（更正原判断「只在 LeanCLR 出现」的隐含前提）：同一探针在 **CoreCLR 6/6**、
   **LeanCLR 24/24** 命中；原观测只是恰好发生在 LeanCLR 会话。**不要**把它记成 LeanCLR 专属。
3. **为什么"同一进程第二次 PIE 才失败"**：残留条目来自**已销毁的已绑定对象**；PIE 停止会拆掉整个世界，
   于是第二轮才有条目可被 `null` 查询命中 —— 与原观测形状完全一致（`Saved/Logs` 该会话 01:00:04 / 01:00:09 两次 PIE）。
4. **附带实测的构建模型问题**（`F-BLD-022`）：切后端时 C# 部署面**不会**跟着重建，
   实测后果是编辑器卡死 60 s 后被 UE 挂起检测判 `Fatal error`。这也顺带裁定
   `09-…/00` §5 里 `F-CS1-026` 的"存疑前提"：**注入逻辑存在，但写 props 的生成器不在启动路径上**（切后端后不跑生成器，产物就一直是旧 flavor；⚠️ 初版措辞"只写一次"已在 §3 更正）。
5. **修法一行，已施工、已验证、已提交（压缩提交 `cd0dfacb`）**（见 `F-REG-019` 的「处置（已执行并提交）」）：`Bind(UObject*)` 与注册表的两个
   `Get*(const UObject*)` 在 `Find` **之前**判空即回 `InvalidManagedHandle` —— fail-closed、静默，符合项目口径
   （**正向 `if` 包裹 + 末尾默认返回**，不用提前 `return`）。
   施工后同一强探针 **CoreCLR 6/6、LeanCLR 9/9 全部不再命中**（施工前分别为 6/6、24/24 命中）。
   提交：**压缩提交 `cd0dfacb216b79a4e831e102612c070164d6ab2a`**（2026-09-17 19:46:35 +0800，父 `1551383b`，**20 文件 +329/−95**；

## 2. [F-REG-019] `nullptr` 实参经弱指针为键的注册表查询命中残留条目 → C# 收到"已销毁对象的存活包装"

- **类别**: 未定义行为 / 功能错误（跨语言语义）
- **严重度**: **P1**（低概率但语义确定错误：C# 侧把 `null` 实参当成一个**非 null 的已死对象**；
  修法一行。原 P0/P1 判据表里"P0 = 崩溃/数据损坏"，本条不崩溃，故不记 P0）
- **文件**:
  - `Source/UnrealCSharp/Private/Registry/FCSharpBind.cpp:42-50`（`FCSharpBind::Bind(UObject*)`）
  - `Source/UnrealCSharp/Private/Registry/FObjectRegistry.cpp:53-58`（`FObjectRegistry::GetObject(const UObject*)`）、`:65-70`（`GetManagedHandle`）
  - `Source/UnrealCSharp/Public/Registry/FObjectRegistry.h:16`＋`:49`（表键类型 = `TWeakObjectPtr<const UObject>`）
  - `Source/UnrealCSharp/Public/Registry/FCSharpBind.inl:56-61`（**判空在下游**，太晚）
  - `Source/UnrealCSharp/Public/Binding/Core/TPropertyValue.inl:470-475`（`UObject*` 的 `Get<false>` → `Bind`）
  - `Source/UnrealCSharp/Public/Binding/Function/TMethodHelper.inl:116-121`（把句柄写进形参槽位）
  - `Script/Interop/Bridge/MethodBridge.cs:63-74`；`Script/Interop/Handle/HandleData.cs:95-106`、`:27-44`
- **函数**: `FCSharpBind::Bind(UObject*)` / `FObjectRegistry::GetObject(const UObject*)` / `Object2ManagedHandle.Find`
- **置信度**: **高**（两个后端均强制复现；机制探针 `ProbeNullBindInvalidAfter` 直接测量）

**现状（代码事实）**

```cpp
// FCSharpBind.cpp:42-50 —— 先查表，判空在下游的 BindImplementation（FCSharpBind.inl:58-61）
IManagedHandle FCSharpBind::Bind(UObject* InObject)
{
    if (const auto FoundManagedHandle = FCSharpEnvironment::GetEnvironment().GetObject(InObject);
        IManagedHandleIsValid(FoundManagedHandle))
    {
        return FoundManagedHandle;          // ← InObject == nullptr 时也会走到这里
    }

    return Bind<false>(InObject);
}

// FObjectRegistry.cpp:53-58
IManagedHandle FObjectRegistry::GetObject(const UObject* InObject)
{
    const auto FoundManagedHandle = Object2ManagedHandle.Find(InObject);   // ← 键是 TWeakObjectPtr<const UObject>
    return FoundManagedHandle != nullptr ? *FoundManagedHandle : InvalidManagedHandle;
}
```

**调用上下文**
`native 形参为 null` → `TPropertyValue<UObject*>::Get<false>`（`TPropertyValue.inl:470-475`）→
`FCSharpEnvironment::Bind`（`FCSharpEnvironment.cpp:454`）→ `FCSharpBind::Bind` →
`FObjectRegistry::GetObject`；返回的句柄被写进 `TMethodHelper` 的形参槽位
（`TMethodHelper.inl:116-121`），托管侧 `MethodBridge.Invoke` 读槽位并 `HandleData.GetObject`
（`MethodBridge.cs:73`）。调用者示例：`FTestMethodHelper::Test()` 的
`UObject* OutObjectValue = nullptr;` + `TMethodBuilder<>::Invoke(this, TEXT("OutObjectValueFunction"), OutObjectValue)`。

**问题**
`FObjectRegistry::Object2ManagedHandle` 是 `TMap<TWeakObjectPtr<const UObject>, IManagedHandle>`。
对象被销毁后条目**不会**被移除，而 `Find(nullptr)` 用"空弱指针"去查表时**可以命中这类残留条目**，
于是 `nullptr` 换出一个**有效句柄**；该句柄在托管侧仍能解到对象 —— 因为
`HandleData` 用强 `GCHandle` 持有包装（`HandleData.cs:39`）。后果：
C# 的 `ref`/`out` 引用类型实参、以及其它经该路径的 `UObject*` 实参，**把 `null` 显示为非 null（且是已死对象）**；
用户代码里的 `obj == null` 判空失效，后续成员访问指向已销毁对象。实测被冒名的对象包括
`ATestBindingPropertyActor`、`ATestMethodHelperActor`、`UTestCoreSubsystem`、`UBlueprintGeneratedClass`。

**为什么表现为"同一进程第二轮/偶发"**
残留条目来自"已销毁的已绑定对象"：PIE 停止拆世界、套件自身 spawn/destroy 都会产生。
第一轮没有条目可命中，第二轮才有；**能否命中取决于残留条目的弱键与空键是否匹配**，
因此表现为低概率偶发（原观测 1/53 会话对；探针 v2 自然命中 5/36）。

**建议**

```cpp
// FCSharpBind.cpp:42 —— 一行守卫（fail-closed、静默）
IManagedHandle FCSharpBind::Bind(UObject* InObject)
{
    if (InObject == nullptr)
    {
        return InvalidManagedHandle;
    }
    ...
}
```

同形守卫加在 `FObjectRegistry::GetObject(const UObject*)` 与 `GetManagedHandle(const UObject*)` 的
`Find` 之前。注意 `FCSharpBind::BindImplementation`（`FCSharpBind.inl:58-61`）**本来就有**同样的判空 ——
"null 视为无效"是既有设计意图，缺陷仅在于**判空发生在查表之后**。
另建议（可单独记 P2）：用 UObject 删除监听在对象销毁时 `RemoveReference`，避免该表随销毁对象单调增长。

**验证方式**
`Saved/Retest/pie_driver.py` + `run-batch.ps1` 复跑；探针版本见 `Saved/Retest/RETEST-REPORT.md` §1

最省事的回归判据：把 `FTestMethodHelper` 的两处 out 断言当哨兵（届时恒为 true）。

## 3. [F-BLD-022] 切换脚本后端时 C# 部署面不会重建（写 props 的生成器不在启动路径上）→ 实测导致编辑器挂起 60 s 后被判 `Fatal error`

- **类别**: 构建/配置（跨后端一致性）
- **严重度**: **P1**（切后端这一操作本身会留下"编译得进去、跑不起来"的错配构建；实测直接卡死编辑器并被
  UE 挂起检测杀掉，且**没有任何可诊断信息**（日志里连一条 `LogUnrealCSharp` 都没有））
- **文件**:
  - `Source/ScriptCodeGenerator/Private/FSolutionGenerator.cpp:115-124`（`Shared.props` 走 4 参重载）
  - 同文件 `:147-164`（`CopyTemplate` 两个重载的写入判定）、**`FSolutionGenerator.h:15-18`**
    （`bReplaceExistingFile` **默认 `true`** ⇒ 默认行为是**每次覆盖**；唯一显式传 `false`（只在缺失时写）的调用点是
    `Game.csproj`，见 `FSolutionGenerator.cpp:97-105`）
  - 同文件 `:190-223`（`ReplaceDefineConstants`：只替换**空占位** `<DefineConstants></DefineConstants>`，
    LeanCLR 时注入 `WITH_LEANCLR;`，非 cook 时注入 `WITH_EDITOR;`）
  - `Source/Compiler/Private/FCSharpCompilerRunnable.cpp:265-314`（`CompileInterop`：产物**不存在**才编）、
    `:316-435`（异步路径 `Compile`：`dotnet build <Game.csproj> -c Release`，无 define 参数；构建体今抽为
    `CompileGame`，见下"API 三态"）
- **置信度**: 高（源码 + 实测：产物 `Script/Shared.props`、`Content/Script/*.dll` 的 mtime 与内容可比对）

**问题**
写 `Script/Shared.props` 的 `FSolutionGenerator::Generator()`（`Shared.props` 那次调用在今 `:115`）**不在编辑器启动路径上** ——
它只由工具栏按钮 / `.Generator`、`.SolutionGenerator` 控制台命令 / **cook 分支**触发（`UnrealCSharpEditor.cpp:167-192`、`:329-403`）。
而 props 里的 `WITH_*` 定义（`ReplaceDefineConstants`）正是"当前 C++ 后端 + 编辑器/cook"的编码。于是**切后端并重启编辑器时，
没有任何东西会跑生成器**，props 保持旧 flavor。于是：
① 先 CoreCLR 后 LeanCLR（或反向）时，C# 部署面仍是**上一个后端的 flavor**；
② 编译触发只认"源比产物新 / 产物不存在 / 显式调用"，**不认"后端变了"**。

> **⚠️ 更正（2026-09-17 收口复核）**：本条初版把根因写成"`Shared.props` 只在**首次生成**时写入（`CopyTemplate` 的

**API 三态与用法（2026-09-17 收口；本节修复后的最终对外形态）**

`FCSharpCompiler`（`FCSharpCompiler.h:16-24`）对外只有三个**语义族**（四个重载），互不重叠，**不应合并**：合并必然产生非法组合
（例如"同步构建 + 立即重载"，或"启动期同步重载"），这些组合在运行期都是崩/死锁。

| 入口（按 `FCSharpCompiler.h:16-24` 的排列） | 执行线程 | 阻塞 | 通知 UI | 构建后重载/激活 | 用途 |
|---|---|---|---|---|---|
| `AsyncCompile()` / `AsyncCompile(FileChanges)` | 编译线程（经队列 `Tasks`） | 否 | 有（进度 + 结果） | 有（`bReloadImmediately` 或动态文件变化时 `Deactivate → fn → Activate`；否则 `MarkOutdated`） | 编辑器常规路径：目录监听、资产变更、蓝图编译 |
| `SyncCompile()` | 调用线程内联 | 是 | **无** | **无**（返回 `bool`） | **启动期专用**：域首次初始化之前修正部署面（⑤）；亦可供未来的 cook/CI 显式调用 |
| `Compile(fn)` | **调用线程内联**（游戏线程调用即为阻塞） | 是 | 有 | 同上（当前唯一调用点传空回调、`bReloadImmediately=false`） | 控制台命令 `UnrealCSharp.Editor.Compile`：**只编译、不重新生成**（与相邻的 `.Generator` 命令分工） |
| `ImmediatelyCompile(bForceCompileInterop)` | 调用线程内联 | 是 | 有 | 有（`bCompileInterop=true` + `bReloadImmediately=true`） | 需"立刻生效"的时机：PIE 前置、内容浏览器操作 |

- **必须区分"入队"与"内联"**：只有 `EnqueueTask()` 那条路（无参 / `FileChanges` 两个重载）是**异步**的；`FCSharpCompiler::Compile(fn)`
  直接调 `FCSharpCompilerRunnable::Compile(...)`（`FCSharpCompiler.cpp:52-61`），**在调用线程同步跑完**——因此它**不能**改名为

**机制（2026-09-17 用临时探针确证；探针跑完已全部还原，工作区无 `[PROBE]` 残留）**

1. `FScriptDomainScope` 的**析构**会 `FScriptDomainFactory::Destroy(Domain)`（`FScriptDomainScope.h:39-45`）⇒ 卸载程序集；该 scope 在 `FDynamicGenerator::Generator()` 里使用（`FDynamicGenerator.cpp:24`）。
2. 编辑器模块 `StartupModule` 的**第一个动作之一**就是 `FDynamicGenerator::Generator()`（`UnrealCSharpEditor.cpp:51`）⇒ **域的首次初始化就发生在那里**，读的是**当时磁盘上**的程序集。探针实录（失败会话，旧位置）：`Initialize` 出现在 props 刷新与构建**之前**；一个会话内共 **3 次 `Initialize` / 2 次 `UnloadAssembly`**。
3. **LeanCLR 不能真正卸载程序集**（CoreCLR 可以）。卸载后再 `load_by_name` 会在同一运行时里叠加"多代"元数据；插件侧另有以 `RtMethodInfo*` 为键、**从不清空**的进程级静态缓存（`FLeanCLRDomain::MethodSlotSizes`、`PInvokeSignatures`；`UnloadAssembly` 只清 `MethodInvokePaths`）。
4. ⇒ 只要**本会话内重建过 C# 程序集**（内容变化），后续初始化就会用到**跨代失效的方法指针**，首次托管调用即在解释器内 AV（`Interpreter::execute` → `get_pinvoke`，`EXCEPTION_ACCESS_VIOLATION 0x5c`）。CoreCLR 因能真正卸载而免疫。
5. ⇒ 结论：**修法必须"在第一次初始化之前"把部署修正**，而不是"事后重编 + 重载"——后者在 LeanCLR 下必然踩上述跨代失效（这正是 step 2/5/syncA 三连崩的原因）。
