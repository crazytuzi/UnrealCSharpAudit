## 1. 热路径架构速览（只讲与性能有关的部分）

插件有**两条完全不同的互调方向**，开销模型完全不同：

**方向 A：C++ → C#（`Invoke`）**
```
C# 生成的属性/方法存根
  → P/Invoke 到 C++（FRegisterXXX 注册的静态函数）
  → FFunctionDescriptor/ContainerHelper 取参
  → FManagedFunctionDescriptor::Invoke            (FManagedFunctionDescriptor.cpp:5)
  → FMethodReflection::Runtime_Invoke              (FMethodReflection.cpp:80)
  → IScriptDomain::Invoke → MethodBridgeInvokeFn   (FScriptDomainImpl.inl:467)
  → C# MethodBridge.Invoke                         (MethodBridge.cs:33)
  → 反射 Method.Invoke
```
每次调用**穿越托管边界 1 次 + 反射调用 1 次 + 3 个 C++ TArray 分配 + C# 侧 2~5 次全局锁**。

> ⚠️ **重要修正**：并非所有 C# → C++ 调用都走这条路。`BINDING_FUNCTION` 注册的 API（`TMap.Add`、`TArray.Get`、`FVector.Size` 等）走的是**另一条独立通道**，全程在栈上、无反射、无字符串查找：
> ```
> C# 生成的存根 → TFunctionBuilder::Invoke (TFunctionBuilder.inl:18)
>               → TFunctionHelper::Call     (TFunctionHelper.inl:19 静态版 / :39 成员版)
>               → 1 次 FCSharpEnvironment::TGetObject 查找 + 栈上的 TArgument 元组
> ```
> 这条路径**是健康的**（见 §6）。哪一类调用走哪条通道，取决于 `Script/SourceGenerator` 生成的代码，**本报告未覆盖该目录**（§8.1）。

**方向 B：C# → C++（覆写回调 / 属性读写）**
```
蓝图或原生代码调用被 C# 覆写的 UFunction
  → UCSharpFunction::execCallCSharp                 (CSharpFunction.cpp:5)
  → FCSharpEnvironment::GetOrAddFunctionDescriptor  (FCSharpEnvironment.inl:31)
  → FCSharpFunctionDescriptor::CallCSharp            (FCSharpFunctionDescriptor.cpp:26)
  → FManagedFunctionDescriptor::Invoke（与方向 A 汇合）
```
注意方向 B **没有** `FindFunctionByName`：函数描述符在 `Bind` 时已按 `GetTypeHash(UFunction*)` 建表并缓存（`FClassRegistry.inl:28-67`），这是**已经做对的地方**。

**对象绑定是独立的第三条热路径**：任何 `UObject*` 从 C++ 流向 C# 都要走 `FCSharpBind::Bind`（缓存命中）或 `BindImplementation`（全量绑定）。全量绑定的成本是「遍历类成员 + 字符串编码」，而 `FCSharpBind::BindImplementation(UStruct*)` 里用了三个 O(N×M) 的嵌套循环（见 F-PERF-009）。

**第四、第五条是引擎级广播**：`GUObjectArray` 的创建/删除监听（每个 UObject 都回调）和 `UClass::ClassConstructor` 替换（每个绑定类的实例构造都回调）。这两条不在"互调"里，但触发频率远高于互调。

## 4. 发现清单

### P1

### [F-PERF-001] C# `TSet<T>.GetEnumerator()` 用元素个数当槽位上界，会漏遍历元素

- **类别**: Bug
- **严重度**: **P1**
- **复核结论**: 确认
- **可达性**: 活跃
- **复核证据**: `Script/UE/CoreUObject/TSet.cs:16` 确实是 `for (var Index = 0; Index < Num(); Index++)`（`:14-23` 全块）；`Script/UE/CoreUObject/TMap.cs:16` 对照确实用 `GetMaxIndex()`（`:14-23`）；`Source/UnrealCSharp/Private/Reflection/Container/FSetHelper.cpp:63-66` = `Num(){ return ScriptSet->Num(); }`、`:73-76` = `GetMaxIndex(){ return ScriptSet->GetMaxIndex(); }`，两者口径确实不同且 `GetMaxIndex` 已暴露；`Source/UnrealCSharp/Private/Domain/Interop/FRegisterSet.cpp:122-129` 证实 `Num`/`GetMaxIndex`/`IsValidIndex`/`GetEnumerator` 四个入口均已注册；`FSetHelper.cpp:184-189` `GetEnumerator` 确实按槽位索引取数据。
- **级别变动**: 无（P1 维持：`foreach` 漏元素是功能错误，不是纯性能）
- **文件**: `Script/UE/CoreUObject/TSet.cs:14-23`（配合 `Source/UnrealCSharp/Private/Reflection/Container/FSetHelper.cpp:63-76`）
- **函数**: `TSet<T>::GetEnumerator()`
- **置信度**: 高

**调用上下文**

**问题**
`FScriptSet` 是稀疏哈希表：元素分布在 `[0, GetMaxIndex())` 的槽位中，`Num()` 只是有效槽位数。把 `Num()` 当上界会在槽位号 ≥ 元素个数时提前终止循环。例：3 个元素落在槽位 0、5、9 时，`Num()==3`，循环只检查槽位 0/1/2，**只能取到 1 个元素**。这不是性能问题而是结果错误，但只要修成 `GetMaxIndex()`，`GetEnumerator` 的开销（见 F-PERF-026）也会一并暴露，所以两条必须一起处理。

public IEnumerator<T> GetEnumerator()
{
    var MaxIndex = GetMaxIndex();          // 循环外取一次，避免每次迭代 P/Invoke
    for (var Index = 0; Index < MaxIndex; Index++)
    {
        if (IsValidIndex(Index))
        {
            yield return this[Index];
        }
    }
}
```
同时把 `GetMaxIndex()` 提到循环外（见 F-PERF-026）。

**验证方式**

3. `RemovedIndexes` 的处理（`OnAsyncLoadingFlushUpdate`，`:371-430`）：`:384` 倒序遍历并 `Add(i)`，因此 `RemovedIndexes` **本身就是降序**；`:426` 正序遍历它逐个 `RemoveAt`（`:428`）时，先删大下标再删小下标，**下标不会失效，这段逻辑是正确的**——原文说的"语义上依赖调用顺序，脆弱"**不成立**。真正的成本问题是：K 次 `RemoveAt` 各自搬移一次尾部 → O(K·N)；且每次 Flush 都会加锁两次（`:379` 拷贝、`:424` 删除）。

**建议**
1. **先判存在再取锁**：`AsyncLoadingObjectArray` 只对"CDO / 非 GameThread 创建的对象"有意义（`:280-298`），但删除路径无法从对象本身知道它当初走的是哪条分支，所以需要真正的结构改动。
2. 把 `TArray<FWeakObjectPtr>` 换成 `TSet<FWeakObjectPtr>`（`TWeakObjectPtr` 有 `GetTypeHash`，`TSet` 的 `Remove` 是 O(1) 平摊）。这是改动最小、收益最直接的一步。
3. 进一步：把 `OnAsyncLoadingFlushUpdate`（`:369-452`）里"遍历 + 收集 + 反向删除"的写法改成单趟 `RemoveAllSwap` 风格的就地压缩（一次 O(N) 完成全部移除），避免 K 次 `RemoveAt`。

**预期收益（复杂度可验证，绝对量未量化）**：对象删除路径从 O(N)+锁 降到 O(1)+锁（方案 2）；Flush 期的批量清理从 O(K·N) 到 O(N)。**具体耗时未量化**（缺 GC 期间对象删除量与该数组规模的实测）。
**风险**：低（`TSet` 语义等价，且顺序无关——原代码也没有依赖顺序）。注意 `FWeakObjectPtr` 作为 key 在对象失效后哈希值会变化：`TWeakObjectPtr` 的 `GetTypeHash` 基于 `(Index, SerialNumber)`，序列号在对象被回收/重用后变化**会导致哈希桶错位、Remove 失败**。所以方案 2 需要**先验证**：用 `ObjectIndex`（`int32`）作为 key 而不是 `FWeakObjectPtr` 本身，或者保留 `TArray` 但改为"标记-压缩"。

**验证方式**
`grep "AsyncLoadingObjectArray" Source/UnrealCSharp/Private/Environment/FCSharpEnvironment.cpp` 实测 **9 处**，其中成员变量 **6 处**（`:149` `Empty()`、`:284`、`:297`、`:318`、`:381`、`:428`）、局部同名变量 3 处（`:376`/`:384`/`:386` 的 `LocalAsyncLoadingObjectArray`）——原文写的"应只有 `:284`/`:297`/`:318`/`:381`/`:428` 五处"漏掉了 `:149`。用 `stat` 观察 GC 期间 `NotifyUObjectDeleted` 的耗时随 `AsyncLoadingObjectArray.Num()` 的变化。

`ClassConstructorMap` 是 `TMap<TWeakObjectPtr<UClass>, UClass::ClassConstructorType>`（`FClassRegistry.cpp:6`）。

**调用上下文**

**问题**

**建议**
```cpp

{
    if (const auto FoundConstructor = ClassConstructorMap.Find(Class);                    // 1 次查找
        FoundConstructor != nullptr && *FoundConstructor != &FClassRegistry::ClassConstructor)
    {
        (*FoundConstructor)(InObjectInitializer);
        break;
    }
    Class = Class->GetSuperClass();
}
```
把 `:231`/`:233` 的 3 次查找收敛为 1 次 `Find` + 1 次解引用。

**预期收益（查找次数可验证，耗时未量化）**：每次实例构造在父类链上减少 **2 次哈希查找/层**（3 次 → 1 次，由 `:231`/`:233` 的源码结构直接可数）。对一个 4 层深的绑定类，从 12 次降到 4 次哈希——**这是查找计数，不是时间测量**；另需注意 `ClassConstructorMap` 的键是 `TWeakObjectPtr<UClass>`（`FClassRegistry.cpp:6`），每次查找都隐含一次 `UClass*`→`TWeakObjectPtr` 转换与一次 `GetTypeHash`，所以"每次查找"的实际成本高于普通指针键。
**风险**：极低。`Find` 返回指针，`*FoundConstructor` 与原 `ClassConstructorMap[Class]` 语义相同（因为 `Contains` 已经保证存在）。注意：不能在 `Find` 得到的指针上再调用 `ClassConstructorMap[Class]`，否则又回到原问题。

**验证方式**

int32 ConsumedIndex = 0;
void SetOutput(const FString& InOutput)
{
    FScopeLock Lock(&CriticalSection);
    PendingOutput.Append(InOutput);
    int32 Index = PendingOutput.Find(TEXT("\n"), ESearchCase::CaseSensitive, ESearchDir::FromStart, ConsumedIndex);
    while (Index != INDEX_NONE)
    {
        ProcessLine(PendingOutput.Mid(ConsumedIndex, Index - ConsumedIndex));
        ConsumedIndex = Index + 1;
        Index = PendingOutput.Find(TEXT("\n"), ESearchCase::CaseSensitive, ESearchDir::FromStart, ConsumedIndex);
    }
    if (ConsumedIndex > 4096)   // 周期性压缩，避免 PendingOutput 无限增长
    { PendingOutput.MidInline(ConsumedIndex); ConsumedIndex = 0; }
}
```

**问题**
每次 C++ → C# 调用：
1. **2 次 `HandleData.GetObject`**（`:37` 取方法、`:39` 取 this）→ 2 次全局 `lock` + 2 次字典查找；每个引用类型参数再多 1 次（`:67`）。

3. **`new object?[N]`（`:45`）**：每次堆分配。
4. **装箱**：每个值类型参数经 `GetValue`（`:150`）返回 `object` → 装箱；返回值的枚举还走 `Convert.ChangeType`（`:116`，内部反射 + 装箱）。

6. `try/catch`（`:35`/`:125`）包住整个方法体，会抑制 JIT 的部分优化。

**建议**
1. **缓存 `ParameterInfo[]` 与参数类型信息**：用 `Dictionary<MethodBase, ParameterInfo[]>`（或 `ConditionalWeakTable<MethodBase, ParameterInfo[]>`）缓存 `GetParameters()` 的结果。在 .NET 7+ 上也可以用 `MethodBase.GetParametersAsSpan()`（无分配）。
2. **缓存委托**：为每个 `MethodBase` 用 `Delegate.CreateDelegate` / `MethodInfo.CreateDelegate` 生成一个 `Func<object, object[], object>`（或用 `System.Linq.Expressions` 编译一个强类型调用器），把 `Method.Invoke` + `object[]` + 装箱整条替换掉。`MethodBridge.Invoke` 的签名是固定的（`(nint, nint, int, nint*)`），完全可以按"参数个数 + 类型签名"缓存一个**已编译的调用器**。
3. **避免 `object[]`**：在 .NET 7/CoreCLR 后端可用 `MethodInvoker`（`MethodBase.Invoke` 的替代，接受 `Span<object>`）或直接走编译委托 + `stackalloc` 的参数暂存。
4. **把 `HandleData.GetObject` 换成无锁读**（见 F-PERF-024），至少先给它加 `[MethodImpl(MethodImplOptions.AggressiveInlining)]`。

**预期收益（粗估）**：每次互调减少 **1 个 `ParameterInfo[]` 分配 + N 个 `ParameterInfo` 分配 + 1 个 `object[]` 分配 + N 次装箱 + 1 次反射调用**；预编译委托后可把 `Method.Invoke` 的开销降低 1–2 个数量级。对 H1 热路径而言这是 C# 侧最大的一项。
**风险**：**中–高**。`Delegate.CreateDelegate` 需要精确匹配签名（含 `ref`/`out`/泛型）；`Method.Invoke` 对 `null` 参数、`Activator.CreateInstance` 默认值（`:53-54`）、`ByRef` 回写（`:79-99`）都有隐含语义，改用委托必须逐条对齐。**建议分两步：先做第 1 步（缓存 `GetParameters()`），风险极低、收益立即可见；第 2 步单独做并按参数个数/类型签名逐类验证。**

**问题**
1. **所有句柄操作共用一把全局 `System.Threading.Lock`**（`:9`）。互调全部发生在 game thread 上，所以实际竞争极少（`TypeBridge.RegisterBinding` 与 `MethodBridge.RegisterBinding` 在启动期），但**无竞争锁仍有 ~20–50 ns 的固定成本**，且它禁止了内联与重排序。
2. **`Handles` 是 `Dictionary<nint, GCHandle>`**：句柄是单调递增的整数（`++Handle`，`:32`），字典查找要做哈希 + 桶探测。同样的语义用一个 `GCHandle[]`/`object[]` **按句柄号直接索引**就是一次数组访问（O(1)、无哈希、缓存友好）。
3. `Alloc` 里 `ObjectToHandleReference.GetValue`（CWT）+ `Handles.TryGetValue`（字典）是**两次哈希查找**，且 CWT 的 `GetValue` 带工厂委托（`:31` 的 lambda 每次调用都要分配闭包？——该 lambda 不捕获外部变量，C# 会缓存为静态单例，**这一项不算分配**；但它仍是委托调用）。
4. `Handles[HandleReference.Value] = GCHandle.Alloc(...)`（`:38`）在已存在时不会更新（外层有 `TryGetValue` 检查），逻辑是对的，但 `TryGetValue` 只为了判断存在性——可以用 `ContainsKey` 或 `TryAdd`（.NET 6+）省一次泛型解包。
5. **`Handles` 只增不减**（只在 `FreeImplementation` `:72` 移除，`Clear` 在 `:141`）。若某条路径漏了 `Free`，字典会持续增长（这是资源问题，不是本报告范围）。

**建议**
1. **用数组槽位表替代字典**（收益最大、改动中等）：
```csharp
private static object?[] SlotObjects = new object?[1024];   // 索引 = 句柄值
private static int NextSlot = 1;                            // 0 保留为 "无效句柄"
// Alloc: 返回 NextSlot++，SlotObjects[slot] = InObject（必要时扩容）
// GetObject: return (uint)InHandle < (uint)SlotObjects.Length ? SlotObjects[InHandle] : null;
```
   这需要把语义确认清楚：当前句柄 id 是**每个对象一个稳定 id**（CWT 保证），并且有引用计数（`HandleReference.Count`，`:34`/`:62-67`）。数组方案要保持"同对象同 id + 计数"，因此仍需保留 `ConditionalWeakTable`（或改用对象头/`GCHandle` 的 `Target` 反查）。**最小改动版本：只把 `Dictionary<nint, GCHandle>` 换成 `GCHandle[] SlotHandles`，`GetObject` 变成一次数组索引 + `.Target`。**
2. **无锁读**：`GetObject`/`GetHandle` 是读操作，写操作（`Alloc`/`Free`）只在 game thread 发生（除 `RegisterBinding` 的启动期）。可以用 `ReaderWriterLockSlim` 替代互斥锁，或者更彻底：**确认所有 `Alloc`/`Free` 都在 game thread** 之后完全去掉锁，只用 `Volatile.Read/Write` + 数组扩容时的双缓冲。
3. `GetObject`/`GetHandle` 加 `[MethodImpl(MethodImplOptions.AggressiveInlining)]`。
4. `TArray<T>.GetHashCode()`（`TArray.cs:41`）实现为 `(int)HandleData.GetHandle(this)` —— 会被 `Dictionary` 内部调用，从而在锁里再取锁。改成缓存句柄到实例字段可避免。

**预期收益（粗估）**：每次互调从 **3–5 次全局锁 + 3–5 次字典/CWT 哈希查找** 降到 **0 次锁（或 1 次 RW 读锁）+ 3–5 次数组索引**；容器遍历（`TArray` N 元素）从 2N 次锁降到 ~0。这是本报告里**调用次数最多的一项**（几乎所有互调与所有容器操作都过它）。
**风险**：**中**。`ConditionalWeakTable` 保证的"同对象同句柄"语义与引用计数必须完整保留，否则 C++ 侧 `FObjectRegistry`/`FContainerRegistry` 的双向映射会失配（`FObjectRegistry.cpp:72-80` 里 `Object2ManagedHandle` 与 `ManagedHandle2Object` 必须成对）。**必须先确认无并发 Alloc/Free**（`grep -rn "HandleData.Alloc\|HandleData.Free" Script/` 之外，C++ 侧 `TypeBridge`/`MethodBridge` 的 `UnmanagedCallersOnly` 入口全部由 game thread 驱动）。

                    if (Method.Name == Name && Method.GetParameters().Length == InParamCount)   // :65  每方法一次 GetParameters
                    {
                        return HandleData.Alloc(Method);                     // :67  全局锁 + 分配
                    }
                }
            }
        }
    }
    return 0;
}
```

**调用上下文**
C++ 侧由 `IScriptDomain` 的"按名字取方法"路径调用（`FClassReflection` 的惰性解析会走 `Utils.GetClassMethods` 而不是它；`GetMethod` 主要服务于需要在运行时按名字解析方法的场景，`grep -rn "GetMethod" Source/UnrealCSharpCore/Public/Domain/Script/IScriptDomain.h` 显示它是接口的一部分）。

**问题**
1. `Type.GetMethods(BindingFlags)` **每次调用都新建一个 `MethodInfo[]`**（反射 API 不缓存）。
2. 循环体内对**每个**方法调 `Method.GetParameters()`（**又是一次数组分配**）只为比较参数个数。
3. 每轮 `Method.Name == Name` 是字符串比较。
4. 全程持有 `HandleData.GetObject` 之后又 `HandleData.Alloc`（2 次全局锁）。

**建议**
1. 用 `Type.GetMethod(Name, BindingFlag)`（按名字直接查）替代手动遍历，再用 `GetParameters().Length` 校验参数个数——把 O(N) 降到"字典查找 + 1 次参数检查"。
2. 或者建一个 `ConditionalWeakTable<Type, Dictionary<(string, int), MethodInfo>>` 缓存，命中则为 0 次反射。
3. `GetParameters()` 的结果可以缓存（与 F-PERF-023 共用一份缓存最好）。

**预期收益（粗估）**：每次调用从 O(N) 反射枚举 + N 次 `GetParameters` 降到 1 次 `GetMethod` + 1 次参数检查（或缓存命中后 0 次）。
**风险**：低（`Type.GetMethod(Name, flags)` 在重载歧义时会抛 `AmbiguousMatchException`，需要 `try/catch` 或改用 `GetMember` 后筛选——这正是原代码手动遍历想避免的问题。**改用缓存方案比改 API 更安全**）。

**验证方式**
`Stopwatch` 对比 `Type.GetMethods` 遍历 vs `Type.GetMethod(Name, flags)` 在 10⁴ 次调用下的耗时。

## 7. 反优化清单 / 被误认为优化的写法（步骤 4 交付物）

### 7.1 为了"省一次拷贝"而牺牲可读性，收益可忽略

1. **`FArrayHelper::Identical` 在 `for` 循环条件里调用 `InA->Num()`**（`FArrayHelper.cpp:74`）
   ```cpp
   for (auto Index = 0; Index < InA->Num(); ++Index)   // 每轮一次 CreateHelperFormInnerProperty
   ```
   看起来像"每次都取最新长度更安全"，实际上既慢又不安全（`Num()` 每次构造 helper）。**这是"看似防御性实则低效"的典型**。建议提到循环外（`FArrayHelper.cpp:63` 已经取过一次 `InA->Num()`，可以复用同一个局部变量）。

2. **`FCSharpBind::BindImplementation` 里的 `Fields.Remove(Field); break;`**（`FCSharpBind.cpp:177`、`:230`、`:300`）
   在遍历 `TSet` 时调用 `Remove`，靠 `break` 立刻跳出内层循环来避免"迭代中修改容器"——**这是把未定义行为藏在一个 `break` 里**。改成 `Fields.Contains(...)`（F-PERF-009）后这个问题自然消失。

3. **`FUnrealCSharpFunctionLibrary::GetFullClass` 把同一个条件表达式写两遍**（`FUnrealCSharpFunctionLibrary.cpp:397-400` 与 `:404-407`）
   大概是为了"避免引入临时变量"。代价是每调用 6 次哈希查找而非 3 次，且两个表达式一旦不一致就会产生难查的 bug。**提取 `const bool bNeedPrefix` 既快又清晰。**

4. **`TArray<T>`/`TMap<K,V>` 为区分值类型/引用类型而把每个方法写 4 份**（`TMap.cs:37-96` 的 `Add` 有 4 个嵌套分支，`:256-379` 的索引器有 4 个分支）
   目的据推测是避免装箱/避免 `object` 中转——**方向正确**，但结果是 IL 体积膨胀 4 倍，损害 JIT 的内联预算（每个方法都超过内联阈值），且 4 份代码必须手工保持同步（`Contains`/`Find`/`Remove`/`Add` 各自重复一遍）。**建议：把 `typeof(T).IsValueType` 分支折叠为一次 `static readonly bool` 判断 + 抽出一个泛型的"写入缓冲"辅助方法**，用 `[MethodImpl(AggressiveInlining)]` 保持内联。收益不是"更快"而是"不再有 4 份必须同步的代码"。

5. **`FArrayHelper::SwapMemory` 与 `FArrayHelper::Swap` 是同一份实现**（`FArrayHelper.cpp:324-332`），两者都导出到 C#（`TArray.cs:306`/`:310`）。这不是优化，是重复。

6. **`FFunctionParamBufferAllocatorFactory::Factory` 为一个无状态的空分配器做 `MakeShared`**（`FFunctionParamBufferAllocator.h:68-70`）
   ```cpp
   static EmptyBufferAllocatorType EmptyBufferAllocator;
   return MakeShared<EmptyBufferAllocatorType>(EmptyBufferAllocator);   // 每次一份 shared ref 控制块
   ```
   已经有 `static` 单例了，却又包装进一个新的 `TSharedRef`。可以返回一个共享的 `static TSharedRef`：
   ```cpp
   static const TSharedRef<FFunctionParamBufferAllocator> Instance =
       MakeShared<EmptyBufferAllocatorType>();
   return Instance;
   ```
   收益极小（每个零参数函数描述符一次），但它**把 `static` 局部变量放在头文件的模板里**，每个 `T`/`EmptyBufferAllocatorType` 组合一份实例，容易引起"以为共享实则多份"的误判。

### 7.2 看起来是热点但实际不是（不要浪费时间）

1. **`FPropertyDescriptor::Factory` 的 27 次 `CastField`**（F-PERF-010）：因为有 `PropertyDescriptorMap` 缓存（`FClassRegistry.h:60`），每个属性只走一次。**不属于帧内热点。**

5. **`FEditorListener::IsCompileRequired` 的 `IterateDirectoryRecursively` 全目录扫描**（`FEditorListener.cpp:603-617`）：只在 `OnPreBeginPIE`（`:207`）调用，**每次 PIE 一次**，不是每帧。设计意图就是"PIE 前检查是否有 C# 文件比程序集新"。**不必优化**（除非把 PIE 启动耗时列为目标，那时可以改成"信任 `OnDirectoryChanged` 收集的 `FileChanges`"，`FEditorListener.cpp:415-464` 已经在收集了）。

### 7.3 需要确认才能判断是否反优化的疑点

1. **`FClassRegistry::ClassConstructor` 里的 `ObjectInitializer.~FObjectInitializer()`**（`FDynamicClassGenerator.cpp:926`）
   ```cpp
   ObjectInitializer.~FObjectInitializer();
   ObjectInitializer.*TAccessPrivate<FObjectInitializer_bIsDeferredInitializer>::Value = true;
   InConstructor();
   ```
   这是**显式析构后再写成员**。它出现在每个实例构造路径上（被 `FClassRegistry.cpp:259` 调用）。从性能角度看，"析构 + 手写私有标记"比"提供一个官方 API"要昂贵且危险。**我把它列入"未覆盖/存疑"**，因为它首先是未定义行为问题（其他报告的范围），其次是性能问题。**更正**：`FObjectInitializer` 的定义现在**可以查到**（引擎源码在 `Engine\Source`），原句"需读 `FObjectInitializer` 定义——本仓库无引擎源码"作废；本报告未再就该析构成本下结论，仍留给未定义行为专项报告。

2. **`FFunctionParamPoolBufferAllocator::Count` 是 `uint8`**（`FFunctionParamBufferAllocator.h:34`）
   `Count` 在 `Malloc` 里 `++`、`Free` 里 `--`。若同一函数的参数缓冲被嵌套复用超过 255 层，`Count` 会回绕。这既是"用窄类型省内存的微优化"带来的隐患，也说明这个池假设了浅嵌套。**位置：`FFunctionParamBufferAllocator.cpp:42/55`。**

3. **`TArray<T>.GetHashCode() => (int)HandleData.GetHandle(this)`**（`TArray.cs:41`）
   把句柄当哈希码是对的（同一对象同一哈希）。但 `GetHandle` 会取全局锁，而 `GetHashCode` 通常在 `Dictionary` 内部被调用（可能已持锁）→ **潜在的自旋/死锁风险取决于 `System.Threading.Lock` 是否可重入**（`System.Threading.Lock` 是可重入的，所以不会死锁，但会有额外开销）。**性能上的问题是"为了一个哈希码取一次全局锁"**，建议把句柄缓存在实例字段。

## 10. 结论摘要

**最重要的三条**：

1. **F-PERF-007 / F-PERF-008（`FMapHelper`/`FSetHelper` 用线性扫描 + 每次插入全表 `Rehash`）是本报告发现的唯一算法复杂度级问题**：C# 侧 `TMap.Contains/Find`、`TSet.Add/Contains` 在插件内部是 O(N)（而非哈希表应有的 O(1)），顺序建 N 元素表是 O(N²)。**复核的最终裁定**：可行性由"可能"升为**确定** —— 引擎确实提供真哈希入口（`FScriptMap::FindValue` `Map.h:2004-2010` → `FScriptSet::FindIndexImpl` `Set.h:1944-1959` 的哈希桶探测；集合侧 `FScriptSet::FindOrAdd` `Set.h:1986+`），"引擎无哈希 API"的说法**不成立**，线性扫描是插件的实现选择；**但"能快多少"仍是未量化**（缺插件侧真实规模/频次实测，且 `GetValueTypeHash` 对 `FString`/结构体键本身有成本）。原文建议里引用的 `FindMapIndexWithKey`（`UnrealType.h:4868-4911`）其实是**线性**扫描，已改正。

2. **F-PERF-024（`HandleData` 用 `Dictionary<nint,GCHandle>` + 全局锁实现句柄表）是调用次数最多的一处**：所有容器操作（`TArray.cs:59-70/82/104/...`、`TMap.cs:31-92/381-426`）、`TypeBridge`/`FieldBridge` 的每个入口都要过它，每次至少 1 次全局锁 + 1 次 `ConditionalWeakTable`/字典哈希查找。**注意 F-PERF-023（`MethodBridge.Invoke` 的反射开销）的"热度"未能验证，见 §8.2-7。**

3. **F-PERF-014 / F-PERF-015 / F-PERF-019（`Encode` 的 77 次线性比较、`GetClassNameSpace`/`GetFullClass` 无缓存、`BeginGenerator` 每资产读一次 JSON）是编辑器启动与代码生成阶段的主力开销**：这三处总调用量在 10⁵–10⁶ 量级，且全部是"低风险、可独立验证"的改动，属于最应该立即动手的一批。

**已排除的误报**：函数参数缓冲已池化（`FFunctionParamBufferAllocator.cpp:35-51`）、对象绑定已有缓存（`FCSharpBind.cpp:42-51`）、类/函数/属性描述符查找已是 O(1) 哈希表（`FClassRegistry.h:56-68`）、C#→C++ 方法指针已在 C# 侧缓存（`MethodBridge.cs:140-148`）、**`BINDING_FUNCTION` 调用路径全栈上零分配（`TFunctionHelper.inl:19-57`）**、类反射解析已懒加载（`FClassReflection.h:86-124`）、字符串封送已用栈缓冲（`TGetUtf8String.inl:6-28`）、P/Invoke 已用 `UnmanagedCallersOnly` 函数指针、**互调/Tick 热路径上没有任何 `UE_LOG`**。

**最大的不确定性（已大幅收敛）**：~~工作区不含 UE 引擎源码~~ —— **该前提已证伪**，UE 5.6 引擎源码在 `Engine\Source`。已把 F-PERF-006/007/008/016 四条从"置信度中"提升为"高"，并改正了其中的错误推断（`FScriptArrayHelper` 字段数 6→5、`FSoftObjectPath` 快路径不拼字符串、`FindMapIndexWithKey` 不是哈希 API、`bIsCompiling` 已是 `std::atomic`）；F-PERF-022 的"12.5 MB"与 F-PERF-009/014/015/019 的各项"总调用量"数字**仍属未量化**，已在正文逐处标明。**当前真正剩余的不确定性不是"引擎 API 未知"，而是"插件侧真实调用频次/规模未测量"。**
