## 0. 结论摘要

1. **释放链条存在且三后端可用**（§1）。释放入口有两类：**原生侧生命周期结束**（32 处 `FDomain::GCHandle_Free`）与 **C# 终结器**（15 个包装类的 `~X()` + 织入器注入的 `[UStruct]`/委托终结器）。
2. 🔴 **实测更正（本轮最重要的一条）**：**"强句柄 ⇒ 终结器永不执行"不成立**（至少对本插件的主力族不成立）。两阶段运行实测：`TArray` 注册 ≥ **276** 次、**注销 364 次**（`TArray_UnRegisterImplementation` 的**唯一调用者就是终结器** `TArray.cs:17`）、`FDomain::GCHandle_Free` **7962** 次。⇒ 原生侧释放点会先把句柄放掉，对象随即不再被钉住、**终结器照常运行**。G1 的"闭环自锁"只在**没有任何原生释放点**的路径上成立。据此，G1 的施工重心应从"全局改弱句柄（D=2 高风险）"改为"**找出真正没有释放点的路径并补齐**"。
3. **本轮已修 3 个确认缺口**（§4，均为"与同族实现不对称"的漏写/历史门控残留）：`F-REG-007`（`FMultiRegistry.inl` 缺 `GCHandle_Free`）、`F-DEL-008`（`FOptionalRegistry::RemoveReference` 缺 `GCHandle_Free`）、`F-RM-004`/`F-DOM-008`（两处 `#if WITH_CORECLR` 门控）。**已提交 `8c54c598`**。
4. **仍开放的缺口按"是否有原生释放点"重排**（§5）：`F-INT2-011`(10b)（C++ 现场新建并直接返回的句柄，从不进注册表）、`F-LEAK-002`（跨语言调用 out 参数句柄）、`F-ENV-002`（`FBindingRegistry` wrapper 被 `bNeedFree` 挡住）、`F-REG2-002`（3 参 `AddReference` 不留 owner）。四者都属"**没有原生释放点**"——与 §2 的实测判据一致。

## 3. 🔴 实测更正：强句柄并没有堵死终结器（本轮新增，带装置）

**装置**：临时探针（已移除）分别计数 `FRegisterArray::RegisterImplementation`（C# ctor）、`FRegisterArray::UnRegisterImplementation`（**唯一调用者是 `TArray.cs:17` 的终结器**）、`FDomain::GCHandle_Free`；跑 `Saved/Retest/run-r1-verify.ps1 -Tag G1-runtime-probe`（编辑器两阶段：PIE#1 → `SetActive 0/1` → PIE#2），归档 `Saved/Retest/out/G1-runtime-probe/G1-runtime-probe.log`。

**结果（本次运行，CoreCLR）**：

| 计数 | 值 |
|---|---|
| `TArray` 注册（C# ctor → 原生） | ≥ **276**（探针每 50 次打一行，末行 `register=276`） |
| `TArray` **注销**（终结器 → 原生） | **364** |
| `FDomain::GCHandle_Free` | **7962** |

**推论**：
1. **终结器在跑**（364 次），且**句柄在大量释放**（7962 次）——原报告的"唯一释放触发者是终结器、而终结器永不执行 ⇒ 闭环自锁"**对这一族不成立**。
2. 机制解释：原生侧的 `RemoveReference`/析构会先调 `GCHandle_Free` → `HandleData.FreeImplementation` 计数归零 → `Handles.Remove` + `OutHandle.Free()` ⇒ 对象**不再被钉住** ⇒ 终结器随后正常排队执行（注销因此还能被观察到）。
3. **更正后的判据**（§2 末）：G1 的真泄漏 = "**有终结器、但没有任何原生释放点**"。按此判据，§5 的四条才是真缺口；而"全局把 `Alloc` 改弱句柄"（`F-LEAK-001`/`F-CS2A-023`/`F-CS2B-002` 的建议 1）**既非必要、也带 D=2 风险**，本轮**决定不做**。

> ⚠️ **本条不推翻的部分**：① `F-LEAK-001`/`F-CS2B-002` 指出的"**字符串**族闭环"仍需按同一判据逐点复核（本报告只实测了 `TArray` 一族；字符串族的原生释放点 `FStringRegistry.inl:76` 存在，形态与容器族相同，但**未单独实测**）；② `F-CS2A-005`/`F-CS2A-023` 的"**无法确定性释放**"（无 `IDisposable`）依然成立 —— 实测只说明"最终会被回收（借道原生释放）"，不说明"用户能确定性释放"。

**构建模型踩坑（本轮实测，供后续轮次复用）**：① `UE.csproj`/`Interop.csproj` **直接编译插件树**（改插件源即可、无需拷贝）；② `Game` 工程对 `Interop` 是**二进制引用**（`Content/Script/Interop.dll`）⇒ 先编 Interop 再编 Game；③ **编辑器运行期间改 C# 会造成 `Game.dll`/`Interop.dll` 版本错配**（实测：错配 ⇒ 25 条 `RawDynamicGet*Property` 失败）；④ `IsScriptPublishOutdated()` **只看 `Shared.props` 与已发布 DLL 的时间戳**、**不看源码** ⇒ 改 C# 源不会自动重编（用 `GeneratorScriptCode` commandlet / `UnrealCSharp.Editor.Compile` / 手工 `dotnet build`）；⑤ 反复构建会留下 **MSBuild 复用节点**占用 `Script/UE/obj/**/UE.dll`，使后续构建**静默失败**（`dotnet build-server shutdown` 或杀节点）。

**机制（已确证）**：3 参 `AddReference`（`FContainerRegistry.inl:35-41`、`FDelegateRegistry.inl:35-41`）只写 `ManagedHandle2Value`，**既不建引用对象、也不留 owner** ⇒ 唯一清理入口 `RemoveReference(handle)` 只能由 **C# 终结器**触发，而 `HandleData.Alloc` 的**强句柄把包装对象钉成 GC root** ⇒ 终结器不排队 ⇒ 条目驻留到域卸载。

##### (1) 先量化"谁在注册"（这是选对修法的前提，本轮实测）

| 来源 | 次数/域周期 | 占比 | 句柄归属 |
|---|---|---|---|
| **C# ctor**（`new TArray/TMap/TSet<T>()` → `FCSharpBind::Bind<FHelper>`） | **309** | **81%** | **用户自己的对象**：C# 引用在，就该活；C# 丢掉，就该回收 |
| 属性读视图（5 个描述符的 `NewWeakRef`） | 43 | 11% | 原生侧 `Class->NewObject()` 造的**一次性视图**，交给 C# |
| 编组（`TPropertyValue.inl`） | 30 | 8% | 同上（含拷贝语义的包装） |

⇒ 结论：**主因不是"临时视图"，而是用户 `new` 出来的包装被强句柄钉死**。这三类的共同点是"**没有原生释放点、生命周期本应由 C# 引用决定**"，因此正确修法是让这些句柄**不再把对象钉住**（而不是加 `IDisposable` 逼用户显式释放）。

##### (2) 解决方案（三层，全部已实现）

| 层 | 改动 | 说明 |
|---|---|---|
| **L1 分配端** | `Script/Interop/Handle/HandleData.cs`：`Alloc(object InObject, bool bPinned = false, **bool bWeak = false**)`，按标志选 `GCHandleType.{Pinned,Weak,Normal}` | 默认仍强句柄 ⇒ **其余全部句柄语义不变** |
| **L2 C# ctor 族** | `TArray/TMap/TSet/FDelegate/FMulticastDelegate` 的 `*_RegisterImplementation` 里，**包装句柄**改 `Alloc(InX, false, true)`；**Type 句柄保持强** | 覆盖 81% 的来源；`Type` 句柄本来就被 `FReflectionRegistry::GetClass` 立即"窃取并释放"，无需弱化 |
| **L3 原生建包装族** | 端到端加 `bIsWeak` 标志：`Op(ObjectBridgeNewObject, …, 1)` → **`2`**（`IScriptTypes.h`）+ `typedef object_bridge_new_object_fn(IManagedHandle, **int32**)` + `IScriptDomain::NewObject(handle, bool bIsWeak = false)`（3 个后端头同步）+ 共享实现 `FScriptDomainImpl.inl` 传标志 + `FClassReflection::NewObject(bool bIsWeak = false)` + C# `ObjectBridge.NewObject(nint, int)` + 5 个描述符的 `NewWeakRef` 改 `Class->NewObject(true)` | 覆盖 11%；三后端**都走共享 `NewObject`**（无任何后端定义 `SCRIPT_DOMAIN_CUSTOM_NEW_OBJECT`，已核实） |

##### (4) 风险与边界（如实列出）

1. **改变了这 5 族（容器/委托）的句柄语义**：包装对象从"进程级常驻"变为"随 C# 引用回收"。对**用户自建容器**这是期望语义；对"**原生侧缓存了句柄、期待其长期有效**"的用法则有风险 —— 本轮已核实这 5 族的原生侧只通过**注册表**（而非托管对象）解析，且 3 参注册**没有地址映射**（不会被 `GetObject(address)` 反查），但**未穷举所有第三方/工程侧插件的用法**。
2. **协议面变更（✅ 维护者已接受，2026-09-22）**：`ObjectBridge.NewObject` 由 1 参变 2 参（op 宏参数计数同步 2、函数指针 typedef 同步 `int32`）⇒ 与**旧版本插件 DLL / 旧 C# 程序集不兼容**；F-ABI-004 的参数个数校验会在不匹配时快速失败（本轮构建 + 三后端运行均无告警）。
3. **仍是"最终回收"而非"确定性释放"**：需要确定性释放的用户仍需 `IDisposable` —— 但本方案把"永不回收"降级为"随 GC 回收"，**不再需要靠用户改代码**。
4. 🆕 **同型缺口（本轮新发现，留给后续）**：`TPropertyValue.inl` 里另有 **18 处 `FoundClass->NewObject()`** 服务于**其他家族**（`TSubclassOf`/`TWeakObjectPtr`/`TLazyObjectPtr`/`TSoftObjectPtr`/`TScriptInterface`/结构体等，见该文件 `:70/85/123/138/178/193/233/248/286/303/346/365/528/545/589/608/1041/1073`）。这些家族的注册表（`FMultiRegistry`/`FStructRegistry`…）**多数带地址映射**，若同样存在"终结器不排队"的闭环，则**不能照搬本方案**（弱化会让地址映射指向已回收对象），需要先决定"地址映射失效时如何重建包装"这一层语义。⇒ ✅ **已测量（2026-09-22 第八刀，见 §5.2）**：闭环**确实存在且量级更大**（3198 注册 / 14 释放 / 残留 3184，其中 **3005 个自持原生堆块**），并已按"是否带地址映射"切成两个子集：**非地址映射 1807 条/周期可安全弱化**、**地址映射 1377 条/周期需先定失效语义**。**仍未改动任何代码。**
5. **未量化**：泄漏的字节量级、稳态收敛值、长会话趋势（需要专项用例 + 内存剖析）。

### 5.4 ✅ 第十刀：`TOwnedValue<Derived>` —— 把"拥有/释放"抽成 CRTP 基类（2026-09-22，已提交 `8c54c598`）

> **对象**：§5.3 里评估过、当时明确"未做"的**清理块去重**。选定形态 = **真 CRTP**：基类持有所有权标志并实现门禁，派生类只实现"怎么放"。

**新增 `Source/UnrealCSharp/Public/Registry/TOwnedValue.inl`（25 行）**

```cpp
template <typename Derived>
struct TOwnedValue
{
	explicit TOwnedValue(const bool InNeedFree) :
		bNeedFree(InNeedFree)
	{
	}

	void Free()
	{
		if (bNeedFree)
		{
			static_cast<Derived*>(this)->FreeImplementation();

			bNeedFree = false;
		}
	}

	bool bNeedFree;
};
```

**三个 wrapper 变成"值 + 拥有能力"两个基类**（多继承）：`TStringAddress<T> : TValueWrapper<T>, TOwnedValue<TStringAddress<T>>`、`TMultiAddress<T,IsType> : TValueWrapper<T>, TOwnedValue<TMultiAddress<T,IsType>>`、`FStructAddress : FStructAddressBase, TOwnedValue<FStructAddress>`；各自的 `bNeedFree` 字段**删除**，改为实现一个 3 行钩子 `FreeImplementation()`，且钩子做成 **`private` + `template <typename> friend struct TOwnedValue;`** ⇒ **唯一公开入口是带门禁的 `Free()`**，避免有人绕过标志直接释放"借来的属性内存"（`FMemory::Free` 到属性地址上）。

#### 5.5.1 🔴 方法学更正：`regs == remain + rel` **判不出覆盖**（引用 §5.2 该判据前必读）

§5.2 用「`regs == 残留 + rel` 逐族成立」推出「本套件内**没有地址被覆盖**的注册」—— **该等式对覆盖不敏感**：覆盖只替换 `Address2ManagedHandle` 的值，**被覆盖句柄的 `ManagedHandle2Value` 条目仍在**（见 5.5.2 的机制），于是覆盖发生时 `regs = remain + rel` 照样成立。
**正确判据：`addrmap == remain − over`**（`over` = 注册时地址映射键**已存在**的次数）。本轮两向都对上：

| 情形 | regs | remain | rel | addrmap | over | 校验 |
|---|---|---|---|---|---|---|
| 无覆盖（基线，含本轮无重复调用那次） | 1221 | 1209 | 12 | 1209 | 0 | `1209 = 1209 − 0` ✅ |
| 有覆盖（追加同址重复调用） | 1229 | 1217 | 12 | **1213** | **4** | `1213 = 1217 − 4` ✅ |

> ⇒ §5.2 的「校验① `regs == 残留 + rel` 逐族成立 ⇒ 没有覆盖」这一句**结论对、依据不成立**（结论另由「`regs == 1219~1220 + rel` 且 addrmap 与 remain 逐值相等」间接支持）。凡引用过该依据的其它结论请按本表重读。

#### 5.6.4 📋 LeanCLR 侧修法方案与取舍（2026-09-23，**仅方案，未实施**）

> **前提**：§5.6.3-4 已定位真因 = `HandleData.ObjectToHandleReference`（`ConditionalWeakTable`）在 **LeanCLR 上不是弱表** ⇒ 每个走过 `HandleData.Alloc` 的包装被永久钉住。修法本质 = **绕开 CWT 完成 object→handle 反查**。
> ⚠️ **先撤回一个不成立的想法**：`Dictionary<nint, GCHandle>` **做不了 object→handle 反查**（按 handle 建键）；而按 object 建键的**强**字典会把包装永久钉死（比现状更糟）且无法清扫（强引用下 `Target` 永不为 null）。

| 方案 | 做法 | 复杂度 / 改动面 | 风险 |
|---|---|---|---|
| **A. 包装类自持 handle 字段** | `GetHandle(obj)` 改读 `obj.Handle`，彻底不用 CWT | **最贵**：手写包装 ~15 个类易改，但 **16 055 个生成类型无共同基类** ⇒ 需改生成器/weaver + **全量重生成** + 三后端回归（估 **2–4 天**） | 大（风险扩散到全部产物） |
| **B. 插件内自建弱表** | 在 `HandleData` 内实现小号 weak table（弱键字典 + 摊销清扫）替换 CWT | **中**：**只动 `HandleData.cs` 一个文件**（~60–100 行），API 与调用点零改动（估 **0.5–1 天含测试**） | 中：清扫正确性；`GetHandle` 是**每次属性读都调的热点**，会变成"哈希 + 摊销清扫" |
| **C. CWT 周期重建（最便宜）** | 缺口是"死对象条目永不消失"，故**定期重建**：锁内 `ObjectToHandleReference = new()`，再把 `Handles` 中**仍存活**（`Target != null`）的条目按原 `Count` 重新 `Add` | **最小**：**5–10 行**，无 API / 生成器改动 | 低-中：O(存活 handle 数) 摊销；需选触发点（每 N 次 `Alloc` 或 tick）并**保留 `Count`**（否则破坏引用计数语义）；**可完全回滚** |

**建议顺序**：① 先用 **C** 验证（预期 LeanCLR 上 `rel/dead/heal` 由全 0 变正），证明"绕开 CWT 即可恢复收益"；② 收益（尤其**长会话峰值**）确证后再做 **B** 作长期形态；③ **A 仅在"必须每对象常量级反查且不接受任何清扫开销"时才值得**；④ **同时把"CWT 在 LeanCLR 上不弱"报给 LeanCLR 上游**（`backend-leanclr`）—— 本质是运行时缺口，插件侧 workaround 是在替 BCL 打补丁。
🔴 **决策前提**：本套修法**只在出货 LeanCLR 时才有价值**（当前 ini = CoreCLR，Windows/Linux/Mac 均 CoreCLR，CoreCLR/Mono 上一切正常）。若 LeanCLR 只是本机试验配置，建议**只做 C 并标注为 LeanCLR 专用 workaround**、不进主线。
