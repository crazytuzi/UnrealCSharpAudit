## Q3 是否**先固化"什么算失败"**，再决定 `Generator`/`ImmediatelyCompile` 是否透传失败

| 字段 | 内容 |
|---|---|
| **问题原文** | 是否**先固化失败判据**（推荐：**产物 manifest 计数/内容差异 ＋ `Generator` 内部返回值**；**不得**用日志行数），再决定是否让 `Generator`/`ImmediatelyCompile` 透传失败（`F-ED2-021` 方案 B 的前置）？（`64` §3.3 Q3；`65` §2.4） |
| **推荐答案（一句话理由）** | **先固化判据** —— `-run=GeneratorScriptCode` 本机**既有 `706 error` / 756 条 `LogBlueprint: Error`** 而**产物正确/确定**（`64` §2.4①(d)）；若直接把"失败"透传到退出码，CI 由**恒绿**变**恒红**，比现状更难用。**实测更正（必须并读 `65` §2.3）**：`64` §2.4⑤ 预测"带参数两态均 exit 0"**不成立** —— 引擎 commandlet 运行器按 `GWarn` 的 error 计数决定进程退出码 ⇒ 真实语义分裂 = **缺参数 = 恒绿（静默成功）／有参数 = 恒红（既有噪声）**，三态语义 =（`Main`=0、error=0 ⇒ `Success` ＋ 退出码 `0`）／（`Main`=0、error>0 ⇒ `Failure - N error(s)` ＋ `1`）／（**`Main`≠0 ⇒ 打印 `Commandlet->Main return this error code: N` ＋ 退出码 `N`**）。⇒ **在判据固化之前，退出码只可用于"参数缺失"这一条判据**（轮 B-26 的修法正是只取这一条）。 |
| **备选与后果** | **维持现状（只保留"参数缺失"判据）**：已修半边（缺参 **exit 0 → 1**，`65` §2.2 判据 A）继续有效，零风险；代价 = "生成是否成功"在 CI 里**完全不可判**，只能人工看产物。**直接透传失败（方案 B 立刻做）**：CI **恒红**，且无法把"既有噪声"与"真失败"分开 ⇒ 比恒绿更糟（`65` §2.4）。**用日志行数当判据**：明确**不得**用（706 error ＋ 756 条 `LogBlueprint: Error` 属既有噪声，与生成是否成功无关）。 |
| **拍板后解锁的条目（级别·S）** | ① **`F-ED2-021` 方案 B**（改 `Generator`/`ImmediatelyCompile` 返回 `bool` ⇒ 覆盖"生成失败"；**公开 API 面变更**：`UnrealCSharpEditor.h` ＋ `FCSharpCompiler.h` 及调用点）⇒ 得到**前置**（判据），开工仍需 CI 侧确认。② **`F-GEN3-012`**（P2·**3.01**）的**方案 B（用既有 `ReturnCode` 做控制流）与方案 C（转发）**：本问给的是"判定什么算失败"的共同底座。③ **死代码批次 C 的 `F-DEAD-029`**（P2·2.00，"依赖图静默丢节点 ⇒ 整类不产出 C# 代码"）：判据固化后，它应当走"**补实现**"而不是"补日志"。 |
| **回填指引（台账要改哪几行、写成什么措辞）** | ① `01` 的 `F-ED2-021` 行（`#L409`）已有"**引擎运行器三态**"与"对 `64` §2.4⑤ 的更正"⇒ **无需重写**，仅在内联补一句"**失败判据 = 产物 manifest 计数/内容差异 ＋ `Generator` 内部返回值；不得用日志行数（2026-10-__ 裁定）**"。② `00` §0.0 T2 表 **第 27 行**（`#L87`）的"**未做**：透传失败（方案 B）⇒ 触发条件 = CI 侧确认 ＋ 先固化判据"后追加该判据的**逐字措辞**（替换"先固化"这一未定表述）。③ `00` §0.1 批次 C 行（`#L199`）把"补 `UE_LOG(Error)`/`ensure`"改为"**补实现优先；确需信号时按裁定过的既有取值域表达**"。④ 若同时拍 Q2：`F-GEN3-012` 行与 `F-CS1-040` 行**共用同一句判据措辞**，避免两条各写一套。 |
| **不拍板的代价** | 退出码**只能用于"参数缺失"这一条判据**（`65` §2.3-2 的实测结论）：`F-ED2-021` 方案 B 永远停在"触发条件未满足"，批次/CI 里"生成失败"仍**不可感知**；`F-GEN3-012` 的方案 B/C 也各缺一块共同底座 ⇒ 同一套"失败"在两个条目里被定义两次甚至互相矛盾。 |

## §复用价值

1. **"卡口径"条目要按"失败信号落在哪"分类，而不是按模块分类** —— 同一批"待裁定"里，`F-ED2-021` 的信号是操作系统既有通道（退出码）、`F-GEN3-012` 是既有 `ReturnCode`、`F-CS4-009` 是既有 Roslyn 诊断、`F-DOM-020` 是既有句柄取值域、死代码批次 C 的"补 `UE_LOG`"才是**真开口**。分类一次，五条各自该走哪条路线就同时定了。
2. **一次性批量裁定 = 先写"例外白名单"，再写"仍需逐例裁定"** —— 白名单只列**已存在**的取值域（列得出文件行号的才算），否则例外会被读成"允许开口"，回到原点。本页 Q2 的写法可直接复用到下一批"卡口径"条目。
3. **判据未固化前，先只取"不依赖判据"的那一条** —— 轮 B-26 只修"缺参返回非 0"，正是因为它不需要回答"生成成功与否"；凡需要判据的修法（方案 B）都应显式登记"前置 = 判据固化"，而不是先做完再补判据。
4. **决策页要给"不拍板的代价"一列，且要能指到台账行** —— 本仓的失序不是"没人做决定"，而是"决定悬空时条目仍显示为待修、下一轮又被重新论证一遍"。把代价钉在具体行号上，悬空状态本身就变成可审计事实。
5. **决策页必须自带"回填指引"** —— 拍板当天就要能把裁定写进台账（改哪一行、写什么措辞、哪些事实必须逐字保留）。不写回填指引，裁定就只存在于这一页里，下一轮的报告照样引用旧口径（`F-DOM-020` 那条已证伪的子断言被引用了多轮就是这个形态）。
