## 1. 逐条复验

### 1.1 `F-GEN-022`（S=2.98）—— 仍成立，但只是"人工一致性"

- **生成端**：`FGeneratorCore::GetFunctionIndex` 把 5 个布尔位拼成 0–31 的索引（`Source/ScriptCodeGenerator/Private/FGeneratorCore.cpp:617-625`），`GetFunctionPrefix` 给出 `Generic/Primitive/Compound`（`:608-615`），两者拼进 P/Invoke 入口名（`FClassGenerator.cpp:646-655`）。
- **运行端**：`FRegisterFunction.cpp:351-376` 注册 **25** 个入口（`GenericCall0/2/4/6/8/10/14/16/18/24/26` ＋ `Primitive|CompoundCall1/3/5/7/9/11/15`）。
- **本轮结论**：25 / 25 两侧**当前一致**，且真实产物只用到 **12** 个索引（复审已统计）⇒ **不是现网缺陷**；风险是"改一位会静默撞上另一个已实现索引（签名相同、编译通过）"。
- **为什么暂缓**：修法只能是**编译期护栏**（共享 `constexpr` ＋ `static_assert`，或生成期自检），收益＝防未来漂移；当前无任何可观测故障，且护栏本身需要跨模块共享头文件（`ScriptCodeGenerator` ↔ `UnrealCSharp`），改动面不小。**登记为"护栏项"，不单独立项。**

### 1.2 `F-CS1-027`（S=2.98）—— 🟢 立项 ①：双路径都删字段、都不扫 IL

- **类路径**：`UnrealTypeWeaver.cs:341-352` 删 `<X>k__BackingField`，随后只重写 `setter`（`:358-454`）与 `getter`（`:456-…`）。
- **结构体路径**：`:560-571` **同形**（删字段 + 重写访问器）——复审当时"结构体路径未读"，本轮已读：**同一缺陷的两条路径**。
- **缺口**：全文件搜 `stfld` / `Constructor` / `BackingField` **0 处**（`UnrealTypeWeaver.cs`）⇒ **构造器里的属性初始化器**（C# 把 `{ get; set; } = 5;` 编译成 ctor 里的 `stfld <X>k__BackingField`）**没有被改写**；字段已被删除 ⇒ 元数据里留下**指向不存在字段的 IL**。
- **后果**：带初始化器的 `[UProperty]` 自动属性 ⇒ 程序集在**加载/JIT 构造器**时失败（`TypeLoadException`/`BadImageFormatException` 一类）；即使不失败，`= 5` 的语义也从未写进原生属性（getter 读原生值 = 0）。复审判"可达性 活跃、仅在带初始化器时产生非法程序集"。
- **修法草案**：删字段**之前**扫描 `Type.Methods`（含 ctors）里的 `stfld/ldfld <BackingField>`：`stfld` 改写为 `call set_X`（初始化器语义并入原生属性）、`ldfld` 改写为 `call get_X`；或"仍被引用则不删字段"（但会保留一份死托管存储，语义不对，**不推荐**）。
- **判据**：
  - **A（静态、可进 CI）**：对一个含 `[UProperty] public int X { get; set; } = 5;` 的类型跑 weaver，断言产物中**不存在**指向被删字段的 `stfld/ldfld`，且 ctor 里出现 `call set_X`；改前 = 命中 ≥1，改后 = 0。
  - **B（端到端、隔离会话）**：临时动态类 ＋ 初始化器 ⇒ 构建 → 加载 → 读回 `X == 5`；改前 = 加载/JIT 失败（或读回 0），改后 = 5。⚠️ **不能进主套件**（非法 IL 会让整趟程序集加载失败），须独立会话/临时工程。
- **风险**：改写 IL 涉及 Cecil 指令重写（已有先例：同一函数的 setter/getter 重写）；范围限定"ctor 里对本类 backing field 的 `stfld`"可控。

### 1.3 `F-BLD-003`（S=2.98）—— 仍成立，但无法验证

### 1.4 `F-PERF-025`（S=2.98）—— 🟢 立项 ②：锁的半边零风险可去

- 现状（逐行实读，HEAD）：
  - `TArray.cs:58-64`：`for (Index < Num()) yield return this[Index];` ⇒ 每次迭代 **2 次 P/Invoke ＋ 2 次 `GetHandle`**（`Num()` 与索引器各一次；`Num()` 见 `:81`）。
  - `TMap.cs:29-38`：`GetMaxIndex()` / `IsValidIndex()` / `GetEnumeratorKey` / `GetEnumeratorValue` ⇒ **4 ＋ 4**。
  - `TSet.cs:29-42`：`Num` / `IsValidIndex` / 索引器 ⇒ **3 ＋ 3**。
- **修法（复审建议，零风险）**：把**循环不变量**提到循环外 —— `var Handle = HandleData.GetHandle(this)` 与上界（`Num` / `GetMaxIndex`）各取一次；`TMap` 的四个私有辅助函数改成**收 `handle` 参数**（不再各自 `GetHandle(this)`）。语义不变：迭代器持有 `this` 引用 ⇒ 包装不会被回收、句柄在遍历期间有效。
- **收益边界（必须先量化再决定是否降级）**：**P/Invoke 数不变**（仍是每元素 2/3/4 次），去掉的是**每元素 2/3/4 次全局锁 + CWT 查找**；`HandleData.Lock` 是进程级 `System.Threading.Lock`（`HandleData.cs:9`），多线程场景下收益远大于单线程。
- **判据**：
  - **A（计数、临时探针）**：在 `HandleData.GetHandle` 计数，`foreach` 10 000 元素：改前 `TArray` 20 000 / `TMap` 40 000，改后 1–2 次（每个 `foreach` 一次）。
  - **B（回归）**：套件 **1 963 / 0**、CSV 与 B-37 基线**逐字节相同**；三个文件的产品/API 面 0 变化。
  - **C（可选）**：单线程 vs 多线程（另一个线程持续 `Alloc/Free`）的 `foreach` wall time 对照 —— 用来证明"锁才是瓶颈"。
- **改动面**：3 个 C# 文件（`TArray.cs` / `TMap.cs` / `TSet.cs`），预计 **±60 行**；不碰 C++、不碰协议、不新增 API。

### 1.5 `F-CS1-005`（S=2.92）—— 仍成立，但"完整修法"不是一轮

### 1.6 `F-PERF-019`（S=2.92）—— 🟡 前提成立、但量级可忽略（建议降级，不写"证伪"）

- **调用点全景（本轮先漏后补，见末尾"自我更正"）**：`FGeneratorCore::BeginGenerator` 有 3 个调用点 ——
