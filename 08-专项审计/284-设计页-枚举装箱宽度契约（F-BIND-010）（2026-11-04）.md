# 设计页：枚举装箱宽度契约（`F-BIND-010`）（2026-11-04）

> **性质**：设计页（**0 代码**）。对象 = `F-BIND-010`（P2 · 潜伏，C 组）。
> **前提回核**：B-246 §6 已登记"审计原文建议的 `sizeof(T)` 修法会**过读**"；本页把根因收敛为**宽度来源有两个**，并给出三条候选与语料配方。
> **结论**：**不建议任何"改读哪种宽度"的一行修法**（两种都各错一半）；要修必须让 C++ 知道"托管侧装箱宽度"，或让协议固定宽度。

---

## 1. 事实（回 HEAD）

| 路径 | C++ 侧宽度 | 托管侧宽度 | 证据 |
|---|---|---|---|
| 托管方法**返回值** → C++ | **1 字节**（硬编码 `uint8`） | C# 代理的底层类型（`Enum.GetUnderlyingType`） | `TPropertyValue.inl:1010`：`*static_cast<uint8*>(FDomain::Object_Unbox(...))`；`MethodBridge.cs:204-212` ＋ `:226-244`（`WritePrimitiveValue` 按 `byte/short/int/...` 写） |
| C# → C++ **参数**（及其 out 参数） | **`sizeof(T)`** | 同上（按底层类型写） | `TArgument.inl:21-31`：`Value(*(std::decay_t<Type>*)IN_BUFFER)`；写入侧同上 |
| C# 代理枚举宽度来源 | —— | UHT `UhtEnum.UnderlyingType`（`UhtEnum.cs:189-195`，默认 `Uint8`） | `ETestEnum.cs:11` = `: byte`（值域 < 256 的 UENUM 被 UHT 报成 Uint8） |
| C++ 实际宽度 | `sizeof(T)`：无固定底层类型的 `enum X {}` = **4**；`enum class X : uint8` = **1** | —— | C++ 语言规则；本工程唯一实例 `ETestEnum`（`TestInterface.h:23-29`，无固定底层类型）⇒ 4 |

⇒ **两个宽度来源**：C++ 的 `sizeof(T)` 与 UHT/C# 的 `UnderlyingType`。二者在"无固定底层类型的小值 UENUM"上必然分叉（4 vs 1），这是本条的根因；`BINDING_ENUM` 注册的枚举走 `TPrimitivePropertyValue`（按 `sizeof` 读）**恰好自洽**，所以只有"未注册"的枚举暴露。

**两个方向、两种症状**：
- 宽枚举（UHT 宽度 > 1）从 C# 返回：C++ 读 1 字节 ⇒ **截断**（审计原文的结论，成立）。
- byte 宽枚举（UHT = 1、C++ = 4）：C# 只写 1 字节，C++ 按 4 字节读 ⇒ **高 3 字节来自缓冲区残留**（`F-BIND-004` 已证"缓冲区不保证清零"）⇒ 可能读到离谱值。**该方向本轮未取实证**，语料见 §4。

## 2. 候选

| 案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A. 生成期宽度 trait**（推荐） | 由 UHT 侧生成器按 `UhtEnum.UnderlyingType` 为每个枚举生成 `TEnumWidth<T>`（或 `TBindingEnum<T>::Width`）特化；`TPropertyValue` 与 `TArgument` 都按该宽度读写 | 生成器改动（`.binding.inl`/`.header.inl` 与 C# 代理两侧）；4 个子模块分支 | 产物变更（所有含枚举的绑定文件）；需覆盖"未导出但参与绑定"的枚举 |
| **B. 协议固定宽度** | 托管侧枚举**一律按 `long`（8 字节）装箱/写缓冲**，C++ 统一读 `int64` 再窄化 | 只改 C#（`MethodBridge.SetValue/WritePrimitiveValue` 的枚举分支）＋ C++ 两处读宽度 | **协议面变更**（两侧必须同版本）；`TArgument`/`TReturnValue`/`TPropertyValue` 都要对齐；跨 5.0–5.8 的 ABI 文档需同步 |
| **C. 契约 + 生成期诊断** | 规定"跨托管边界的 UENUM 必须声明固定底层类型且与 UHT 宽度一致（如 `enum class X : uint8`）"；生成期对 `CppForm == Regular`（无固定底层类型）**且**参与绑定的枚举报诊断 | 0 运行时改动；需要诊断通道（Roslyn `UC_ERROR_0N` 或生成期 fail-closed）与"是否参与绑定"的判定 | 不修老代码；诊断面窄（无法预知运行期返回哪些枚举）；误报风险 |

**倾向**：先做 **C 的语料取证**（§4）确认第二方向的真实症状，再决定 A vs B。若只修"返回路径截断"，A 最小可行子集 = 仅给 `TPropertyValue` 提供宽度；但会留下参数方向的不对称，不建议半修。

## 3. 决策点（需维护者定）

1. 是否接受**生成产物变更**（A 会改所有含枚举的绑定文件；需全量生成 delta 对照）。
2. 若选 **B**，是否接受**协议面变更**（两侧必须同版本；`F-ABI-*` 契约页需更新）。
3. 若选 **C**，诊断放在 **Roslyn 源生成器**（`UC_ERROR_0N` 先例：`F-DEF-010` 的 `UC_ERROR_08`）还是 **C++ 生成期 fail-closed**。

## 4. 语料与判据配方（未跑）

1. **宽枚举（截断方向）**：项目测试头新增 `UENUM() enum EBigEnum { A = 0, B = 300 }`（无固定底层类型）＋ 一个 C# 侧返回该枚举的 `[UFunction]`/绑定方法 ＋ C++ 判据读回值；期望：改前 300 → 44（截断）。
2. **byte 枚举作参数（第二方向）**：把 `ETestEnum` 作为参数的既有绑定调用前，故意用同一参数池槽位写入非零值（或连续调用两个不同方法），观察 C++ 侧收到的值是否被残留污染；期望：若污染成立 ⇒ 第二方向是**现网可达**，优先级应从"潜伏"上调。
3. **对照**：`BINDING_ENUM` 注册的 `ERawTestEnum`（C# `: int`）在两方向都应正确。
4. **套件**：新增判据必须落在既有套件内（CSV 行数会变；同 SHA 不再适用 ⇒ 需登记新基线）。
