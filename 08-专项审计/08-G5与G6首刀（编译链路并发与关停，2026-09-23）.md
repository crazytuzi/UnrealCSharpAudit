### 2.1 前置收口（`F-CMP-003` = `F-ED2-006`；`F-ED2-022` 只取证据面）

* **改前**：`CompileInterop`/`CompileGame` 有 4 条入口 —— worker `DoWork()`（`:146`）、游戏线程 `ImmediatelyDoWork()`（`:154`）、控制台命令 `UnrealCSharp.Editor.Compile` → `Runnable->Compile(…)`（`FCSharpCompiler.cpp:60-69`）、启动期 `SyncCompile()`（`UnrealCSharpEditor.cpp:58`）；两条同步入口**不看 `IsCompiling()`**，与 worker 之间**没有任何互斥**（`F-CMP-003` 的静态结论）。
* **改后**：新增闸门
  ```cpp
  void FCSharpCompilerRunnable::AcquireCompile()
  {
      while (true)
      {
          { FScopeLock ScopeLock(&CriticalSection); if (!bIsCompiling) { bIsCompiling = true; break; } }
          if (IsInGameThread()) { FThreadHeartBeat::Get().HeartBeat(); FTaskGraphInterface::Get().ProcessThreadUntilIdle(ENamedThreads::GameThread); }
          FPlatformProcess::SleepNoStats(0.008f);
      }
  }
  ```
  `Compile()` = `AcquireCompile()` → 清 `bIsPending`（锁内）→ `CompileInternal(…)` → `ReleaseCompile()`；`SyncCompile()` = `AcquireCompile()` → `CompileInterop` + `CompileGame` → `ReleaseCompile()`。
* **🔴 为什么等待必须"泵任务图"**（本刀最容易写错的一处）：若游戏线程在闸门处**只睡不等**或**阻塞在锁上**，worker 侧 `CompileInternal` 结尾派给 `ENamedThreads::GameThread` 的任务就永远没人执行（E5+E7），**F-CONC-003 的互等会从关停期搬进运行期**。故游戏线程分支保留 `ProcessThreadUntilIdle(ENamedThreads::GameThread)`（与 `FEditorListener::WaitForCompile:744` 同一手法）。
* **未照抄审计建议**：`F-CMP-003` 建议「入口加 `if (IsCompiling()) { return false; }`」——**未采纳**：`Generator()` 路径（工具栏/控制台/`DynamicDataSource::Apply/Revert`）在编译在飞时**静默跳过编译**会把"生成后立即重载"的语义变成"产物陈旧且无提示"；改为**等待 + 串行执行**（`F-CMP-003` 建议里的第二条路）。`F-ED2-006`/`F-ED2-022` 建议的 UI 门禁与 `FCanExecuteAction` 接线**本轮未做**（见 §5）。

### 2.2 状态入锁（`F-ED2-008` = `F-CONC-005` = `F-CMP-004`）

* `TQueue<bool> Tasks` **删除**：它的全部用法就是"先 `Empty()` 再 `Enqueue(true)`"（合并请求）与"`IsEmpty()` 当状态读"——**队列元素 `bool` 不携带任何信息**（`F-CONC-008` 自己也指出这一点），语义等价于一个标志位。改为 `std::atomic<bool> bIsPending`，**彻底消除**游戏线程对"仅限消费者线程"的 `Empty()`/`IsEmpty()` 的调用（E2/E3/E4 的整类问题）。
* `OnBeginGenerator()` / `OnEndGenerator()`：`bIsGenerating = …` 后**在 `FScopeLock` 内**写 `bIsPending = false;` 与 `FileChanges.Empty();`；`OnEndGenerator` **额外 `Event->Trigger()`**（生成期间 worker 在 `Event->Wait()`，必须有唤醒源）。`EnqueueTask`×2 也把 `FileChanges.Append` 与标志位放在同一临界区，并补上原本缺失的 `if (Event != nullptr)`（`F-ED2-007` 第 4 点 / `F-ED2-004` 的并入残留）。
* `IsCompiling()` 改为**锁内**判定（`F-ED2-008` 建议的 `mutable FCriticalSection` 方案；**未**用 `const_cast`）：
  ```cpp
  bool FCSharpCompilerRunnable::IsCompiling() const { FScopeLock ScopeLock(&CriticalSection); return bIsCompiling || bIsPending; }
  ```
  调用方全在游戏线程（`FEditorListener` 4 处 + 编译通知 ticker），锁内只有几次原子读/写、**从不跨等待持锁** ⇒ 无递归、无死锁面（§4 的 1704 例回归与三个装置都不见退化）。

### 2.3 原子化（`F-CONC-006` = `F-CMP-012`）

`bool bIsGenerating;` / `bool bIsStopped;` → `std::atomic<bool>`（与既有 `bIsCompiling` 同层）。`bIsStopped` 的可见性直接决定 `Run()` 能否退出（`F-CONC-006` 第 4 点与 `F-CONC-003` 叠加）。

### 2.4 判定窗口闭合（`F-CONC-007`）

* 窗口原本是「worker 已 `Dequeue`、`bIsCompiling` 尚未置位」⇒ 游戏线程 `IsCompiling()` 读到 false ⇒ `OnPreBeginPIE` 跳过 `WaitForCompile` ⇒ **PIE 中脚本域被 `Deactivate/Activate`**。
* 本刀闭合方式**不是**审计建议的"`EnqueueTask` 里直接置 `bIsCompiling = true`"（那会在 `EnableCompiled()==false` 或请求被 `OnBeginGenerator` 丢弃时**永远置真**），而是：**入队只置 `bIsPending`；`bIsPending` 只由"已拿到闸门的执行者"清除** ⇒ `bIsCompiling || bIsPending` 从**入队那一刻**到**编译结束**恒为真，且不存在"置真后无人清"的路径（`ReleaseCompile()` 一定在 `Compile()`/`SyncCompile()` 的出口执行）。

### 3.3 `WaitForCompile`：保留泵图，把输入变有界（`F-ED2-005` / `F-PERF-018` / `F-CONC-021`）

* **`04-…/02` §3.3(g) 的硬约束**（原文）："**如果 `WaitForCompile` 的循环因为任何原因退出（例如被改成带超时后直接 break），`:242` 就会永久等待**" ⇒ 审计给出的 `break` 修法与它自己的 (g) 冲突。

### 3.4 泵/轮询间隔改为具名常量（120 Hz），并更正一个引擎事实（2026-09-23 追加）

> **起因**：维护者指出 `FEditorListener.cpp` 那处 `0.008f` 应当是**具名常量**、由 **120 fps 算出来**，并随后指定**改成类静态变量**，而不是三处各写一个魔法数。
> **改法**：在模块门面 `Source/Compiler/Public/FCSharpCompiler.h` 的 `FCSharpCompiler` 类内增加两个 **`static constexpr` 公有成员**：
> ```cpp
> class COMPILER_API FCSharpCompiler
> {
> public:
> 	static constexpr int32 PollsPerSecond = 120;
>
> 	static constexpr float PollIntervalSeconds = 1.0f / PollsPerSecond;
> ```
> 三处等待/泵循环统一写 `FCSharpCompiler::PollIntervalSeconds` ⇒ **魔法数归零**：`FEditorListener::WaitForCompile`（`FEditorListener.cpp:756`）、`FCSharpCompilerRunnable::AcquireCompile`（`FCSharpCompilerRunnable.cpp:528`）、`FCSharpCompilerRunnable::CompileInternal` 的 worker 有界等待（同文件 `:518-520`）。
> 🔵 **命名依据（本轮回核引擎公开头文件普查，不是口味问题）**：① **时长用复数 `...Seconds`** —— UE `Runtime/Core/Public` + `Runtime/Engine/Public` 共 2381 个头文件里，`...Seconds` 唯一标识符 **124** 个（`DeltaSeconds`、`AccumulatedSeconds`、`BudgetSeconds`、`AsSeconds`…），`...Second` 仅 **21** 个且几乎全是 `...PerSecond` 复合词或 `Millisecond`/`GetSecond`；② **速率用 `...PerSecond` 复合词**（`FramesPerSecond`/`KeysPerSecond`/`PixelsPerSecond`/`DegreesPerSecond`/`RadiansPerSecond`），**`Hz` 在 Core 公开头里 0 命中**（只有散文里的 "FPS"）；③ **不单用 `Rate`** —— 同一批头文件里 `SetPlayRate(float Rate)`、`TurnAtRate(float Rate)` 的 `Rate` 与"秒"无关，语义含糊；④ **与callee 形参同名**：`FPlatformProcess::SleepNoStats(float Seconds)`（`GenericPlatformProcess.h:658`）的形参就是 `Seconds` ⇒ `PollIntervalSeconds` 在调用点与形参风格一致。⇒ 定名 **`PollsPerSecond` + `PollIntervalSeconds`**（初版曾写 `PollRatePerSecond`/`PollIntervalSecond`，按上述四条改为现名）。
> 🔵 **两个名字为什么"一个带 s、一个不带"（刻意的不对称，非笔误）**：它们**不是并列的一对**，而是"**速率**"与"**时长**"两类不同的量，英文构词也不同 —— ① `PollsPerSecond` 是"**被计数的量 + PerSecond**"，量词用**复数**：引擎里 17 个 `...PerSecond` 复合词**全部**用复数（`FramesPerSecond`/`KeysPerSecond`/`PixelsPerSecond`/`MetersPerSecond`/`TicksPerSecond`/`PacketsPerSecond`…）；② `PollIntervalSeconds` 里 `Poll` 是**定语名词**（poll interval = 轮询间隔），英语定语名词用**单数**：引擎同类写法同样全部用单数（`SleepInterval`/`SyncInterval`/`UpdateInterval`/`OcclusionCheckInterval`/`TimeQuotaCheckInterval`）。**决定性对照**：引擎对"帧率"这一个概念本身就同时存在两种写法 —— **`FrameRate`（单数定语，122 处）** 与 **`FramesPerSecond`（复数计数，6 处）** ⇒ 本刀的 `PollIntervalSeconds` ↔ `PollsPerSecond` 正是这一对的中文版。**若要强行对称**只有两条路（均不采纳）：`PollFrequency` + `PollIntervalSeconds`（视觉对称但丢掉了 `PerSecond` 的显式单位）、`PollsPerSecond` + `SecondsPerPoll`（都是 `A Per B` 形，但"时长"就不再走引擎的 `<概念>Seconds` 后缀惯例，与 `DeltaSeconds`/`BudgetSeconds` 不一致）。
> **为什么放在这里、为什么是类静态**：`FCSharpCompiler.h` 是编译模块的公开门面，而 **`FEditorListener.cpp:20` 已经 include 它** ⇒ 编辑模块**零新增 include**（`FCSharpCompilerRunnable.cpp` 新增 1 个同模块 include，无循环：`FCSharpCompiler.h` 只前置声明 `FCSharpCompilerRunnable`）；`static constexpr` 在 C++17 起**隐含 inline** ⇒ **不需要类外定义、不产生导出符号**，即便类本身带 `COMPILER_API` 也无 dllimport 面；命名沿用本库既有风格（类作用域提供 "Compile" 语境，成员名不再重复该前缀 —— 对照 `FCSharpCompileProgress::StagePreparing`）。

### 4.4 装置二：取消探针（G6，`F-CONC-003` / `F-CMP-001`）

* **装置**：`-Mode cancel -FakeSleep 60`。同一个资源事件触发异步编译（假构建 **60 s**），驱动在 **+10 s** 调 `unreal.SystemLibrary.quit_editor()`；宿主测"quit 之后到 `Log file closed`"的时延。
* **结果（21:03–21:04）**：假构建 **11.8 s 被取消**（剩余约 **48 s**）→ 日志 `marker` **1** 行 → **编辑器在 quit 后 3.5 s 退出**（归档 `Saved\Retest\out\G5G6-cancel\`）。

### 4.5 装置三：静默超时探针（G6，`F-CMP-002`）

* **装置**：`-Mode timeout -FakeSleep 150`。异步编译的假构建**睡 150 s 且零输出**；预期 **120 s 静默超时**把它终止，编辑器全程存活。

* **判据**：120.1 s ≈ 静默超时常量 120 s ⇒ 超时路径**确实生效**；而**编辑器没有冻结**（游戏线程不在该构建上等待——它是异步路径），符合 `F-CMP-002` 的修法目标。

* **改法**：重载体抽成局部 lambda `Reload`（= 原任务体 + 新增 PIE 守卫），统一 `FFunctionGraphTask::CreateAndDispatchWhenReady(Reload, …, ENamedThreads::GameThread)`，**并且只在 `!IsInGameThread()` 时等待**（有界轮询，首刀形态）。⇒ 游戏线程同步入口（工具栏 / 控制台 `UnrealCSharp.Editor.Generator` / `OnPostEngineInit` / `DynamicDataSource::Apply/Revert`）**只排队、不等待**，TaskGraph 无法再把 `Deactivate()/InFunction()/Activate()` 就地执行在调用者栈上（事务 `Apply`、`FScopedSlowTask` 帧内、`OnPreBeginPIE` 中途）——**`F-CONC-010` 的重入面消失**（＝审计建议 1 的"投递成普通队列任务、让重载发生在引擎循环的稳定点"）。
* **PIE 守卫（审计建议 3）**：`Reload` 内 `if (GIsPlayInEditorWorld) { MarkOutdated(); return; }`。
  ⚠️ **不能用 `FEditorListener::bIsPIEPlaying`**：该标志在 `OnPreBeginPIE` **开头**就已置真（`FEditorListener.cpp:224`），而此时 PIE 世界还没创建 —— 用它会把"PIE 启动前必须完成的那次重载"也一并跳过（PIE 将跑在旧域上）。`GIsPlayInEditorWorld`（`Runtime/Core/Public/CoreGlobals.h:519`，在 `UEditorEngine::CreatePIEWorldByDuplication` 里置真，`UnrealEngine.cpp:15901/15989`）的语义恰好是"**PIE 世界已在跑**" ✔。
* **语义变化（必须并读）**：① **游戏线程同步入口返回时，重载可能尚未完成**（延后到游戏线程的下一次任务泵）；② **worker 路径（含 PIE 启动前的 `RequestCompile`）仍然等待重载完成** ⇒ "PIE 前一定是新域"不变；③ **PIE 运行期完成的编译不再重载域**（改 `MarkOutdated`；改前会在 PIE 中途 `Deactivate/Activate`）。

### 8.3 🪤 本轮实测到的两个施工陷阱（复用价值）

1. **游戏线程上不能用"轮询 `Task->IsComplete()`"代替等待**：对照实验变体（两个分支都改成轮询）**直接死锁**（`Generator` 命令 8 分钟未返回）—— 队列中的游戏线程任务**只在游戏线程处理任务图时**才执行，轮询循环本身不会去处理它。⇒ 游戏线程只有两条路：`WaitUntilTaskCompletes`（**会就地执行** = 本条要修的重入），或**干脆不等**（本刀的选择）。
2. **`UnrealCSharp.Editor.Generator` 会重入 python 的 slate post-tick 回调**：它弹 `FScopedSlowTask` 模态并 Tick Slate ⇒ 探针驱动里"发命令"的分支被递归回调，实测一路到 `RecursionError: maximum recursion depth exceeded` 并触发几十次嵌套生成（编辑器空转烧 CPU）。⇒ 驱动必须**先把状态推进、再发阻塞命令**（本刀已据此改 `pie_driver_g5g6b.py`，加 `busy` 重入保护 + `generating` 中间态）。
