## 1. 根因细化（对齐条件）

**对齐条件 = `sizeof(T)`（C++ 声明） == UHT `UnderlyingType` 宽度（C# 代理宽度）。**

| 证据 | 读数 |
|---|---|
| C# 侧按代理宽度逐字节写参数 | `Script/UE/Proxy/UMG/Components/Widget.cs:1046-1055`：`SetVisibility(ESlateVisibility)` → `stackalloc byte[1]` ＋ `*(byte*)InBuffer = (byte)InVisibility` |
| C++ 侧参数按 `sizeof(T)` 读 | `TArgument.inl:21-31`（`TBaseArgument<T,true>` 直读 `IN_BUFFER`）＋ `:85-89`（`TPrimitiveArgument`）＋ `:360-366`（枚举特化继承 `TPrimitiveArgument`） |
| C++ 侧托管返回值按 **1 字节**读 | `TPropertyValue.inl:1010`（`*static_cast<uint8*>(FDomain::Object_Unbox(…))`） |
| UE 自身枚举**写了固定底层类型** | `ESlateVisibility : uint8`（`Runtime/UMG/Public/Components/SlateWrapperTypes.h:21`）⇒ `sizeof=1` == 代理 `byte` ⇒ **对齐**（所以 `SetVisibility` 是安全的） |
| 分叉样本：**未写固定底层类型** | `Source/UnrealCSharpTest/Public/UnitTest/Core/TestInterface.h:24` 的 `enum ETestEnum` ⇒ `sizeof=4`、UHT 宽度 `Uint8` ⇒ **不对齐** |

⇒ 两个方向的错位条件：
- **参数方向**：`sizeof(T) != UHT 宽度` ⇒ C# 写 N 字节、C++ 读 `sizeof` 字节（未写固定底层类型的枚举即中招）。
- **返回值方向**：`UHT 宽度 > 1` ⇒ 代理 2/4/8 字节被 C++ 恒读 1 字节（截断）。
- 修法必须共享 **UHT 宽度**（不是 C++ `sizeof`），且要在**两个实例化点**同时生效。

## 2. A 案：生成期宽度 trait

**两个实例化点**（必须都覆盖，否则半修）：
1. **插件侧**绑定包装（`FRegister*.cpp` 与生成的绑定代码）实例化 `TArgument<Enum>`／`TReturnValue<Enum>`；
2. **用户侧** `TMethodBuilder<Enum>`／`TPropertyValue<Enum>::Get`（托管返回值）。

**落点**：`SourceCodeGenerator`（`.inl` 生成器，子模块 4 分支）在导出时**额外生成**一个 trait 头：

```cpp
// UHT/EnumWidth.generated.inl（新增产物；每个导出枚举一行）
template <> struct TEnumWidth<ESlateVisibility>  : std::integral_constant<size_t, 1> {};
template <> struct TEnumWidth<EMyWideEnum>       : std::integral_constant<size_t, 4> {};
```

- **可见性**：`TPropertyValue.inl` / `TArgument.inl`（插件公开头）用 `#if __has_include("UHT/EnumWidth.generated.inl")` 有条件包含（C++17／MSVC 支持；旧版没有该产物时退回现状）。
- **消费**：`TPropertyValue` 的枚举特化按 `TEnumWidth<T>::value` 读；`TArgument` 的枚举特化按同宽度读（而非 `sizeof`）。
- **fallback**：无 trait 的枚举维持现状（1 字节 / `sizeof`）——因此仍需 C 案诊断兜底。
- **改动面**：`SourceCodeGenerator.cs`（+≈30 行，4 分支）＋ 插件 2 个头（各 +2~6 行，含 `#if`）＋ 1 个新产物文件。
- **产物 delta**：新增 `EnumWidth.generated.inl`；现有 1 912 个 `.inl` 中**含枚举参数/返回的绑定文件**会因读取宽度变化而变化 —— **需用 B-257 装置实测**（预估数十~数百个文件）。
- **风险**：`__has_include` 双分支要双测；子模块 4 分支同步；未导出枚举仍靠 C 案。

## 3. B 案：协议固定宽度（不推荐）

- **做法**：C# 侧所有枚举参数/返回值统一按 `long`（8 字节）写；C++ 两个实例化点统一读 `int64` 再窄化到 `T`。
- **改动点**：`Script/Interop/Bridge/MethodBridge.cs`（`SetValue`/`WritePrimitiveValue` 的枚举分支）＋ 生成代码（`Widget.cs` 类代理的逐字节写）＋ `TArgument`/`TPropertyValue` 枚举特化。
- **代价**：**协议面不兼容**（旧 DLL 与新 C++ 不能混跑）；缓冲尺寸从 1 字节变 8 字节，所有含枚举的生成代码都要变 ⇒ 产物 delta 远大于 A；`F-ABI-*` 契约需同步。
- **判据**：新增"宽枚举返回/参数"用例 ＋ 全套件重跑（行数会变，需登记新基线）。

## 4. C 案：契约 ＋ 生成期诊断（0 运行期改动）

- **契约**：跨托管边界的 UENUM 必须**写固定底层类型**（`: uint8` 等），且与 UHT 宽度一致（UE 自身全部满足）。
- **诊断**：对 `CppForm == Regular`（未写固定底层类型）且被导出/参与绑定的枚举报错。通道二选一：
  - Roslyn `UC_ERROR_0N`（C# 侧先例 `UC_ERROR_08`，但 C# 源生成器看不到 C++ 枚举声明）；
  - **C++ 生成期 fail-closed**（`SourceCodeGenerator` 里 `throw new BuildException`，需子模块流程）。
- **优点**：0 运行期风险；**缺点**：不修存量代码，且"是否参与绑定"难精确判定（可能误报）。

---

## 5. 建议

**C 兜底 ＋ A 的最小可行子集**：

1. 先落 **C**：凡未写固定底层类型的 UENUM，一律在生成期报错（或至少登记为"不可跨边界"）；
2. A 的第一阶段**只修返回值方向**（`TPropertyValue` 按 UHT 宽度读）—— 该方向的错位条件明确（UHT 宽度 > 1），且不需要动 `TArgument` 的缓冲布局；
3. 参数方向（`TArgument`）等 C 落地后再评估（未写固定类型的枚举已被诊断挡住，剩下的都是对齐的）。

**不建议 B**：协议不兼容且产物 delta 最大。
