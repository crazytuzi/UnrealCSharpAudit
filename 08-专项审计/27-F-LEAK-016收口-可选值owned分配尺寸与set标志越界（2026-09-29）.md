## 1. 结论摘要（先读这一节）

1. ✅ **机制（修正后的完整表述）**：`FOptionalHelper` 的 owned 分配是 `FMemory::Malloc(ValuePropertyDescriptor->GetSize(), …)`（只给 **value 尺寸**），而引擎的可选值布局在**非 intrusive** 值类型下是"**值 + 紧随其后的 set 标志**"（标志写在 `Data + ValueProperty->GetSize()`，`CalcIsSetOffset()` = `ValueProperty->GetSize()`），且 `InitializeValueInternal` **在构造期**就写那个标志 ⇒ **每次 `new TOptional<T>()` 都在分配块尾之外写 1 字节**。
2. 🔴 **严重度重判（本轮最硬的产出）**：这个越界字节**是否落在分配器真正的块里**取决于尺寸档 ——
   - **4 字节档（`int32`）**：请求 4、分配器块 8 ⇒ 标志落在块内 padding ⇒ **被掩盖**；
   - **1 字节档（`bool`）**：请求 1、块 8 ⇒ 掩盖；
   - **24 字节档（`FVector` 等 UStruct）**：请求 24、块 32 ⇒ 掩盖；
   - **8 字节档（`double` / `int64`）**：请求 8、块 **8** ⇒ 标志写在**块之外**、落进邻居分配 ⇒ **真越界写（堆破坏）**。本轮在**同一二进制**上取得：`FLEAK016_NOFIX=1` 时 **2/2 崩溃**（`0xC0000005`、`coreclr.dll`），且两次崩溃点不同（第 15 次 `int64` 构造之后 / 第 2 次 `int64` 构造之后）——**分配器元数据损坏的典型非确定性**。
3. 🔴 **两处对上一轮登记的更正**（详见 §2.5）：
   - **① `TOptional<FString>` 不越界**：`FString` 有 **intrusive unset 状态**（`Containers/UnrealString.h.inl:208-209`），此时引擎布局**没有尾标志**、`CalcSize()` = `ValueProperty->GetSize()` = **16** = 旧分配 ⇒ **零越界**。上一轮把它算作命中（`16 / 24`），是拿了"**非 intrusive 公式**"当判据。`FName` 同理（`UObject/NameTypes.h:578-579`，值 12 字节）。
   - **② 不是"静默"**：上一轮写"当前被 binned 分配器的 16 字节粒度掩盖 ⇒ 静默"——对 4/1/24 字节档成立，**对 8 字节档不成立**（实测 `FMemory::GetAllocSize` = 8，而引擎需要 16）。
4. ✅ **修复**：`Align(ValuePropertyDescriptor->GetSize() + 1, ValuePropertyDescriptor->GetMinAlignment())`（§3.1）。**安全性可证**：与引擎 `CalcSize()` 在**非 intrusive** 分支**逐字等价**，在 **intrusive** 分支**只多不少**（多 ≤ `minAlign − 1` 字节）⇒ **任何取值下都不会小于引擎的需求**。
5. 🟢 **判据（同一二进制、同一装置、同一用例集）**：改前 **32 行**探针（27 次违规、2 个 `tailOOB=1` 档）→ **崩溃**；改后 **274 行**探针（**违规 0**、`alloc == engineCalc` 全档成立、intrusive 档按预期多分配）→ 套件 **1799 / 0 failed**（19 条新断言全绿）。
6. ⚠️ **未取得**（不得读作"已验证"）：崩溃调用栈（无转储）与"越界字节落到哪个邻居分配"的精确链路；intrusive 档**多分配**的收益/代价量化（有意取舍，§3.1）；Mono/LeanCLR 与打包复测；生成器未跑（原生改动，产物 diff 预期 0，**未实测**）。

**为什么这个式子在任何取值下都安全**：

| 分支 | 引擎 `CalcSize()` | 本轮式子 | 关系 |
|---|---|---|---|
| 非 intrusive（`int`/`bool`/`double`/`int64`/`enum`/无 intrusive ops 的 `USTRUCT`） | `Align(valueSize + 1, minAlign)` | `Align(valueSize + 1, minAlign)` | **逐字相等** |
| intrusive（`FString`/`FName`/`TArray`/`TSet`/`TMap`/有 intrusive ops 的 `USTRUCT`） | `valueSize` | `Align(valueSize + 1, minAlign)` | **≥ `valueSize + 1` > `valueSize`** ⇒ 多分配 ≤ `minAlign − 1` 字节，**安全冗余** |

**三条未采纳的替代修法（各附理由）**：

| 替代 | 为什么不用 |
|---|---|
| `OptionalProperty->CalcSize()`（引擎权威公式） | `UE_F_OPTIONAL_PROPERTY` 自 **5.3** 起就为真（`CrossVersion/Public/UEVersion.h:98`），而本机只有 **5.6** 引擎头 ⇒ `CalcSize()` 在 5.3–5.5 的存在性**无法核实**。本轮无条件式子在没有 intrusive 的版本下与它**逐字等价**、在有 intrusive 的版本下**只多不少** ⇒ 用"不会更小"的式子换取跨版本确定性。（探针里用过 `CalcSize()` 作为**判据**，已按惯例摘除 ⇒ 交付态零新增引擎 API、零新 `UE_F_*` 宏。） |

## 9. 复用价值（给下一轮）

1. **判据要取"引擎自己的权威量"，不要自己按公式推**：本轮更正 #1 的根因就是上一轮用"非 intrusive 公式"当"引擎所需尺寸"。`CalcSize()` / `GetAllocSize()` 都是现成的权威入口 —— 前者给"引擎认为要多少"，后者给"分配器实际给了多少"。
2. **"请求尺寸 vs 块尺寸"是分配类缺陷的第一判据**：`FMemory::GetAllocSize(Data) >= required` 一行就能把"形式越界但被掩盖"与"真越界写"分开。本轮的严重度重判完全建立在这一行上。
3. **探针必须打印类型名**（`GetProperty()->GetClass()->GetName()`）：16 字节的 `FString` 与 16 字节的容器在尺寸上无法区分，只有类型名能把 intrusive/non-intrusive 分开。
4. **同二进制 env 门控 A/B 在"分配/释放"类缺陷上价值最高**：崩溃类缺陷对"重编差异/时序差异"极敏感，一轮构建两次运行消掉了这一层噪声，也让"唯一差异 = 分配尺寸"成为可辩的归因。
5. **崩溃类缺陷的可重复性判据 = "多次运行 + 事件日志 module/offset"，不是"日志尾部行号"**：本轮两次崩溃点不同（n=32 / n=12），若按"最后一行"当判据会误判为"不可复现"。同时**同一 offset 可能跨缺陷复用**（§5.3 的 `0x3584ff`）⇒ offset 只能当"同一类失效"的旁证，不能当某缺陷的指纹。
6. **"修释放"的轮次必须同时核对"分配"**（上一轮留下的方法论）在本轮得到第二次验证：`F-LEAK-012`（释放少析构）与 `F-LEAK-016`（分配少字节）是同一次核对里分出来的两个面，且**后者的严重度比前者高**（前者是泄漏、后者是堆破坏）。
