## 1. 设计与实现

### 1.1 改动对照

| 函数 | 旧（`83e4b90`） | 新（`44fa66d8`） |
|---|---|---|
| `Add` | 全表 `ElementPropertyDescriptor->Identical(Data, InValue)` 扫描 → `AddUninitialized` ＋ `Descriptor->Set(InValue, Data)` → `bNeedRehash = true` | `PrepareValueBuffer`（handle → native）→ `ScriptSet->FindOrAdd(ValueBuffer, Layout, GetKeyHash, EqualityFn, ConstructFn)` |
| `Remove` | 全表扫描 → `EnsureRehash()`（**全表 `Rehash`**）→ `DestroyValue` → `RemoveAt` | scratch → `ScriptSet->FindIndex(...)`；命中才 `DestroyValue` ＋ `RemoveAt` |
| `Contains` | 全表扫描 | scratch → `FindIndex(...) != INDEX_NONE` |
| 哈希/相等谓词 | 描述符 `Identical`（**A = 原生、B = 句柄**，见 [`325`](325-契约页-容器元素原生比较语义（C-IDENT-C-HASH-C-VALUE）（2026-11-17）.md) C-IDENT-1） | `Property->GetValueTypeHash`（C-HASH-1）／`Property->Identical`（两边原生） |
| `bNeedRehash` / `EnsureRehash` | 延迟重哈希机制 | **退役**（全库 grep = **0**） |

**为什么不会再出现 B-288 的三条失败**：`FindOrAdd`/`FindIndex` 的 `EqualityFn` 收到的是"**scratch 与表内元素**"两个原生值，直接走 `FProperty::Identical`；不再经过 `FPropertyDescriptor::Identical` 的句柄转换（那条路径对 native 值恒判不等，实测 0/3）。

### 1.2 构造与析构（`ConstructFn` 保持既有语义）

`FindOrAdd` 的 `ConstructFn` 仍是 `ElementPropertyDescriptor->Set(InValue, Dest)` —— 即"**从入参句柄构造表内元素**"，与旧实现的插入路径**逐字相同**；只有"判等/定位"换成了原生语义。因此：

- 表内元素的构造方式不变（结构体/字符串/对象的既有 `Set` 语义原样保留）；
- 插入时 `AddNewElement` 会用**同一个 hash 回调**链接（必要时 `Rehash`），元数据自插入起就有效 ⇒ `RemoveAt` 前不再需要预重哈希。

### 1.3 scratch 生命周期（C-SCRATCH-1 的落地）

| 阶段 | 实现 |
|---|---|
| 分配 | 构造函数内：`FMemory::Malloc(Descriptor->GetSize(), Descriptor->GetMinAlignment())` ＋ `Memzero`（尺寸为 0 时不分配） |
| 每次使用前 | `Memzero(ValueBuffer, Size)` → `Property->InitializeValue(ValueBuffer)`（**关键**：`Set` 在句柄无效时会早退，此前置初始化保证缓冲区在任何分支下都是**合法默认值**）→ `Descriptor->Set(InValue, ValueBuffer)` |
| 使用后 | `Descriptor->DestroyValue(ValueBuffer)`（此时缓冲区必为"已初始化"状态 ⇒ 不会重演 B-288 的"对未初始化内存析构"AV 候选） |
| 销毁 | `Deinitialize()` 内 `FMemory::Free(ValueBuffer)` |
| 线程 | 与既有契约一致：`FSetHelper` 只在游戏线程使用（[`08-…/307`](307-契约页-Children链线程亲和与RemoveFunction归属（2026-11-17）.md) 同族口径） |

### 3.2 集内性能 A/B（同一装置：`FRegisterSet` 派发层计时，env `UNREALCSHARP_B290_BENCH`，交付前已删）

装置对 `Add`/`Remove`/`Contains` 的**每次调用**累计 `FPlatformTime::Cycles64()` 差值（毫秒级换算），每 256 次落一行（`Contains` 每行一条）。两份二进制分别为"旧实现（`83e4b90` 的 `FSetHelper`）"与"新实现"，其余代码与测试**完全相同**。

| 指标（套件内 `TSet<int>`） | 旧（线性扫描） | 新（哈希） | 变化 |
|---|---|---|---|
| `Add` 累计 **1 280** 次 | **1.059 ms** | **0.286 ms** | **3.7×** |
| `Add` 中段（调用 256→1024，N 从 ~10² 涨到 ~9×10²） | 0.150 → **0.603 ms**（+0.453） | 0.215 → **0.266 ms**（+0.051） | **8.9×** |
| `Add` 末段（调用 1024→1280，N≈10³） | +**0.456 ms** / 256 次 = **1.78 µs/次** | +**0.020 ms** / 256 次 = **0.078 µs/次** | **22.8×** |
| `Remove` **1 024** 次 | **0.565 ms** | **0.066 ms** | **8.6×** |
| `Contains` 大集合（调用 81→83，N=1024） | ≈**2.0 µs/次** | ≈**0.33 µs/次** | **≈6×** |
| 小集合段（调用 0→256，含 2–3 元素集合） | **0.106 ms** | **0.180 ms** | **−0.29 µs/op（回归，见 §3.3）** |

**读数解读**：旧实现的单次 `Add`/`Contains` 随 N 线性增长（末段 1.78 µs/次 ≈ O(N) 扫描 ＋ 每次插入后 `bNeedRehash` 标记，`Remove` 首次还要付一次**全表 `Rehash`**）；新实现基本恒定（0.078 µs/次），差异随 N 放大。与 B-153 的 5 000 次口径（40.648 / 35.627 ms → 0.734 / 0.404 ms）**同向**；本轮未重跑 5 000 次专用基准（见 §6 限制 2）。

### 3.3 小集合固定开销（登记，不作结论）

新实现每次 `Add`/`Contains`/`Remove` 都要：`Memzero` ＋ `InitializeValue` ＋ `Set`（handle→native）＋ `DestroyValue`。对 2–3 元素的集合，这比"2–3 次 `Identical`"更贵 ⇒ 实测 **+0.2~0.3 µs/op**。绝对量级远小于一次 P/Invoke 派发（本装置测得派发＋调用合计 ≈0.4–0.7 µs），且随 N 增大迅速反超。**未做专门优化**（例如按"值类型免 scratch"分流）：那会引入第二条路径与新的类型判定面，与本轮"单一 native 语义"的目标冲突。
