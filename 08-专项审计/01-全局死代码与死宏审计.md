**统计口径说明（重要，关系到全文可复核性）**：
- 命中数 = 在 858 个语料文件里用**大小写敏感**正则 `\b<符号>\b` 统计的总 token 出现次数（含定义行本身）。
- "净引用数 = 命中数 − 定义行数"。净引用数 == 0 → 该符号除自身定义外在整个插件里**零出现**（无 C/C++ 使用、无字符串形式出现、无 `#ifdef/#undef`）。
- **大小写敏感这一点必须强调**：`Select-String` 默认**不区分大小写**，会把 C# 的 `namespace Script.Dynamic`、`ForEach(Str => ...)` 误算成宏 `DYNAMIC`/`STR` 的引用。本报告全部计数均用 `[regex]::Matches`（默认大小写敏感）或 `Select-String -CaseSensitive`，已规避该陷阱。
- 另有 **3 个必须规避的假阳性来源**，本报告在相应章节都做了纠正：① C++ 宏的 token pasting（`##`）会让"按类名 grep"漏判（见 2.2）；② 文件名 ≠ 类名（见 3.2 的 `DefaultSubobject`/`DefaultSubObject`）；③ 扩展方法容器类（见 3.2 的 `CodeAnalysisHelper`）。

### 0.3 架构速览：三个"名字/符号"体系（本报告的核心背景）

本次横向审计发现，这个插件的"死代码判定"之所以容易出错，是因为同一组功能横跨**三套不同的命名体系**：

```
①  C++ 编译期宏体系
    Source/UnrealCSharp/Public/Macro/*.h        (89 个宏, BINDING_*/FUNCTION_*/SIGNATURE_*)
    Source/UnrealCSharpCore/Public/CoreMacro/*.h (476 个宏, CLASS_*/FUNCTION_*/NAMESPACE_*/...)
    → 两者宏名集合交集为 0（见 1.3），但值大量重复（"Binding"/"Dynamic"/"Script"/"Interop"）

②  C++ → C# 的运行时"注册 key"体系（字符串）
    C++  .Function("Name", ptr) / .Property("Name", get, set)   [FRegister*.cpp]
      ↓ FClassBuilder.inl:48-49 拆成 Get+Name / Set+Name；FClassBuilder.cpp:83-91 重载加计数后缀
      ↓ FBindingClassRegister.cpp:113-129 拼成
        "Script.<ImplNS>.<Class>Implementation::__<Class>_<implName>Implementation"
      ↓ .inl:601-633 RegisterBinding() 把全部 key+函数指针推给 C#
    C#   MethodBridge.StringToMethod[<key>] = ptr      (MethodBridge.cs:25)
      ↑ C# 源生成器按 "{namespace}.{class}::{method}" 反查   (UnrealTypeSourceGenerator.cs:903-918)
      ↑ 消费者是 Script/UE/Library/<Class>Implementation.cs 里手写的 __<Class>_<Name>Implementation partial
    → 判定"是否被消费"必须比较「运行时拼出的 key」vs「C# 侧存在的 partial 声明」，
      不能用 .Function("Name") 里的字面量（那是错的判据，见 4.1）

③  C# ↔ C++ 的双向桥接符号体系（字符串）
    C++  IScriptTypes.h 的 Op 表 / CoreMacro/FunctionMacro.h 的 FString(TEXT("..."))
      → 供 Mono/CoreCLR 用反射按名字解析 C# 方法；供 LeanCLR 用平台 invoke 按名字解析
    → 这些名字必须与 C# 侧实际的方法名逐字符一致（本报告据此查出 F-DEAD-004）
```

### 4.1 先纠正一个分析方法问题：C++→C# 的"符号名"是**运行时拼出来的**，不是源码字面量

任务说明已正确指出：`Source/UnrealCSharp/Private/Domain/Interop/*.cpp` **不是** `extern "C"` + `DllImport`，而是注册进 C# 侧 `MethodBridge` 的**名字字典**（`Script/Interop/Bridge/MethodBridge.cs:10` `Dictionary<string, nint> StringToMethod`）。但还有一层更关键的细节必须先讲清楚，否则会得出大量假阳性：

**C++ 侧 `.Function("NewGuid", ...)` 里的 `"NewGuid"` 并不是最终注册的 key。** 真正的 key 由 `FBindingClassRegister::BindingMethod` 在运行时拼出：

```cpp
// Source/UnrealCSharpCore/Private/Binding/Class/FBindingClassRegister.cpp:113-129
void FBindingClassRegister::BindingMethod(const FString& InImplementationName, const void* InFunction)
{
	MethodRegisters.Emplace([=]()
		{
			return BINDING_COMBINE_CLASS(
				        ImplementationNameSpace,
				        BINDING_COMBINE_CLASS_IMPLEMENTATION(GetClass())) +
			        BINDING_COMBINE_FUNCTION(
				        BINDING_COMBINE_FUNCTION_IMPLEMENTATION(GetClass(), InImplementationName));
		},
		InFunction);
}
```
```cpp
// Source/UnrealCSharpCore/Public/CoreMacro/BindingMacro.h:3-9
#define BINDING_COMBINE_CLASS(A, B) FString::Printf(TEXT("%s.%s"), *A, *B)                                    // :3
#define BINDING_COMBINE_CLASS_IMPLEMENTATION(A) FString::Printf(TEXT("%sImplementation"), *A)                 // :5
#define BINDING_COMBINE_FUNCTION(Function) FString::Printf(TEXT("::%s"), *Function)                           // :7
#define BINDING_COMBINE_FUNCTION_IMPLEMENTATION(A, B) FString::Printf(TEXT("__%s_%sImplementation"), *A, *B)  // :9
```
```cpp
// Source/UnrealCSharp/Public/Binding/Class/FClassBuilder.inl:48-49（.Property 会被拆成 Get/Set）
	return Function(BINDING_PROPERTY_GET + InName, GetFunctionPointer.Value.Pointer).
		Function(BINDING_PROPERTY_SET + InName, SetFunctionPointer.Value.Pointer);
```
```cpp
// Source/UnrealCSharpCore/Public/CoreMacro/BindingMacro.h:11-13
#define BINDING_PROPERTY_SET FString(TEXT("Set"))
#define BINDING_PROPERTY_GET FString(TEXT("Get"))
```

即最终 key = `"Script.<ImplNS>.<Class>Implementation::__<Class>_<implName>Implementation"`，其中 `<implName>` = `.Function()` 的第一个参数（`.Property("X")` 则变成 `GetX`/`SetX`）。

C# 侧同构：源生成器 `Script/SourceGenerator/UnrealTypeSourceGenerator.cs:903-918` 按
`key = $"{containingNamespace}.{InOwner.Name}::{method.Name}"` 调 `MethodBridge.GetMethod(ref slot, "<key>")`。
所以**只有 "声明为 `__<Class>_<Name>Implementation` 的 `partial` 方法的 C# 类" 才是真正的消费者**。

> 以「C++ 侧运行时会拼出的 key」是否与「C# 侧存在的 `__<Class>_<Name>Implementation` 声明」配对为准。

**调用上下文**

**问题**
按确定性排序：
1. **跨调用别名（确定）**：函数返回的是同一块 `static` 内存的地址。`void* A = UnboxValue(h1); void* B = UnboxValue(h2);` 之后 `A == B`，`*A` 已被第二次调用覆盖。调用方若缓存指针而不立即取值，就会读到错误数据。这与"返回新分配的缓冲区、由调用方 `Free`"的直觉约定冲突，而**接口（`IScriptDomain.h:35`）没有任何注释说明返回指针的生命周期**。
2. **作用域界定（已核实，避免夸大）**：`SCRIPT_DOMAIN_TYPE` 是宏替换出的**具体类名**（不是模板参数），所以每个具体类各有自己的 `static`——`FCoreCLRDomain::UnboxValue` 一个、`FMonoDomain::UnboxValue` 一个，**不跨后端实例共享**。真正的共享范围是"同一个类 + 同一进程"，即**同一后端的多次调用之间**。第一点仍然是成立的，只是不要说成"跨后端共享"。
3. **并发/重入（中高置信）**：同一后端实例被多线程调用时，两个线程写同一块 `Result` 会造成数据竞争并可能读到对方的值。该实现**没有任何同步**。是否真的存在并发调用（例如异步编译线程与 GameThread 同时走到 `UnboxValue`）属于并发审计的职责，本报告不代答。

**建议**
- **最小改动（推荐）**：把 `static uint64 Result{}` 改为 `thread_local`，至少消除跨线程竞争：
  ```cpp
  thread_local uint64 Result{};
  ```
  这仍不解决"同一线程内两次调用互相覆盖"，但把风险面缩小到"同一线程连续调用"。
- **正确改动**：让所有权明确。要么由调用方提供缓冲区（`void* UnboxValue(IManagedHandle, void* OutBuffer, int32 InSize)`），要么返回按值的小结构（`union { bool b; int8 i8; ... double d; }` 或 `TTuple<int32, uint64>`），从类型上消除指针生命周期问题。
- **文档改动（零成本，必须做）**：在 `IScriptDomain.h:35` 上补注释说明"返回的指针由实现方持有，仅在下一次调用前有效，调用方必须立即取值"，让后续维护者不再踩这个坑。
