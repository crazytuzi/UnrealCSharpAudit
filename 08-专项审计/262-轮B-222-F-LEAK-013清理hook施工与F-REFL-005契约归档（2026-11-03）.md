### 3.3 声明与定义的顺序对齐（维护者指出）

- 维护者指出：新增函数的**声明顺序与定义顺序要一致**。
- 问题：`Reset()` 声明放在头文件第 2 个公开成员（`Generator()` 之后），但定义被追加到了 `.cpp` **文件末尾**（在全部私有函数之后）；而这些文件的既有惯例是"**定义顺序 = 声明顺序**"（`Generator()` → `CodeAnalysisGenerator()` → `Generator(FClassReflection*)` → `Is…` → `GetNameSpace()` → 私有）。
- 处置：4 个 `.cpp` 的 `Reset()` 定义统一移到 `Generator()` 之后、`CodeAnalysisGenerator()` 之前（纯位置移动，`+95/−95`）。
- 顺带修掉一个由此暴露的守卫错位：移动后 `Reset()` 定义一度落在 `#if WITH_EDITOR` **之内**（该守卫原本紧贴 `CodeAnalysisGenerator()`），会把非编辑器定义滤掉 ⇒ 已把 `#if WITH_EDITOR` 一并挪到 `Reset()` 之后（现结构：`Generator()` → `Reset()` → `#if WITH_EDITOR CodeAnalysisGenerator() … #endif`）。
- 复核：`#if/#endif` 计数逐文件配平（18/18、10/10、10/10、8/8）；Editor ＋ Game 双构建 **Succeeded**。

### 3.4 统一入口与清理顺序（维护者指出）

- **入口收敛**：原先三个后端各写 4 行调用（并各拿 4 个生成器头），维护者要求统一走一个入口 ⇒ 新增 `FDynamicGenerator::Reset()`，后端只保留 1 个 include ＋ 1 行调用；facade 内部 4 个调用按空行分隔。
- **顺序**（在 facade 内部）：以 `FDynamicGenerator::Generator()` 的**生成顺序**为准 —— `Enum → Struct → Interface → Class`（类最后生成，因为它要引用枚举/结构体作属性类型、引用接口作实现）。拆除按**反序**：`Class → Interface → Struct → Enum`。
- 现在三个后端的调用块完全一致：

```cpp
// 三个后端（UnloadAssembly 末尾）
FReflectionRegistry::Get().Deinitialize();

FDynamicGenerator::Reset();
```

- 说明：4 个 `Reset()` 只做 unroot ＋ `MarkAsGarbage` ＋ `Empty`，同一帧内不销毁对象（销毁发生在下一次 GC 的同一批），所以顺序**不影响**内存安全；按生成序反序是为了**意图一致**（先拆依赖方，再拆被依赖方），也便于后来者按同一规则维护。
