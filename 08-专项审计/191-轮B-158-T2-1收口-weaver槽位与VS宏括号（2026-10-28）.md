## 1. HEAD 事实（施工前）

### 1.1 `F-CS1-032` —— 四个属性重写点

`Script/Weavers/UnrealTypeWeaver.cs`（HEAD `5b69abc7`）：

```csharp
// 类 setter（:431）
Property.SetMethod.Body.Variables.Add(
    new VariableDefinition(new PointerType(ModuleDefinition.TypeSystem.Byte)));
// …（:438 ilProcessor.Clear() 只清指令、不清变量表）…
ilProcessor.Append(Instruction.Create(OpCodes.Stloc_0));   // :450 硬编码 0 号槽
```

- 四处位置：类 setter `:431/450`、类 getter `:528/533/553/587`、结构体 setter `:650/669`、结构体 getter `:747/752/772/806`（🔴 **行号已漂移**：报告原文记的是 `:377/474/596/693`，HEAD 上整体后移约 54 行）。
- 根因：`ilProcessor.Clear()` 只清**指令**，`Body.Variables` 里手写访问器原有的局部变量仍在 ⇒ 新加的 `byte*` 落在索引 N（N>0），而代码仍写 `Stloc_0`/`Stloc_1`。
- 对照证据：同文件 `ModifyRpcMethod` 做了 `Variables.Clear()`（`:975`）后照用 `Stloc_0`（`:1000`），并在结尾 `ExceptionHandlers.Clear()`（`:1080`）—— 同一份代码里"指令/变量分开清"的写法只有 RPC 路径有。

### 1.2 `F-DEF-004` —— 宏缺括号

```c
// Source/CrossVersion/Public/VSVersion.h:4/6（HEAD）
#define VS2022 _MSC_VER >= 1930 && _MSC_VER < 1950
#define VS2026 _MSC_VER >= 1950
```

唯一用法 `Source/ScriptCodeGenerator/Private/FSolutionGenerator.cpp:472` 的 `#if !VS2026` ⇒ 展开为 `!_MSC_VER >= 1950` = `（!1951）>= 1950` = `0 >= 1950` ⇒ **恒假**（与 `_MSC_VER` 取值无关）。

### 1.3 语料事实

- `Script/Game` 下 **191 处** `[UProperty]`，其中**手写访问器（`get {…}` / `=>`）= 0 处** ⇒ A/B 必须**现造语料**（不能靠跑现成套件）。
- `[UStruct]` 在本绑定里**只能标注在 class 上**（`CS0592`：`UStructAttribute` 的 `AttributeUsage` 只允许 class）；源生成器还要求**文件名 = 类名去掉 `U`/`F` 前缀**（否则 `UC_ERROR_02`）。

## 2. 施工

### 2.1 `F-CS1-032`（`+16/−0`）

四个点各插两行（保持文件既有"每语句间空行"的写法）：

```csharp
Property.SetMethod.Body.Variables.Clear();          // :431 / :658

Property.SetMethod.Body.ExceptionHandlers.Clear();  // :433 / :660
…
Property.GetMethod.Body.Variables.Clear();          // :532 / :759

Property.GetMethod.Body.ExceptionHandlers.Clear();  // :534 / :761
```

- 位置在既有 `Variables.Add(...)` **之前**、`ilProcessor.Clear()` **之前**；`InitLocals`、指令序列、`Stloc_0`/`Stloc_1` 全部不动。
- 清 `Variables` ⇒ 重写后的访问器**只声明 weaver 自己的变量**（buffer 恒为 0 号；非复合 getter 的临时值恒为 1 号）⇒ 硬编码槽位**由构造保证正确**。
- 清 `ExceptionHandlers` ⇒ 手写访问器里原有的 `try/catch` 处理表不会再指向已被 `ilProcessor.Clear()` 摘除的指令（否则 Cecil 写盘时偏移失效）。方法体本来就被整体重写，清空 handler **不丢任何会被执行的语义**。
- ⛔ **被否决的更彻底写法**：改用 `Instruction.Create(OpCodes.Stloc, BufferLocal)` 显式引用变量。它会把手写访问器与**全部 191 处自动属性**的 IL 编码从 `stloc.0`（1 字节）换成 `stloc`（`FE 0E` + 索引）⇒ 全量产物 churn、且失去"自动属性指令面零变化"这条回归判据。**本轮取最小面**：只恢复前提，不动编码。

1. **`InvalidProgramException` 未取得**：对改前/改后两份 `Game.dll` 逐个 `RuntimeHelpers.PrepareMethod` 8 个访问器，**两态均 8/8 "JIT OK"**（`jit-before.txt` / `jit-after.txt`）。CoreCLR 10 x64 的 JIT **不校验**该局部变量签名与栈值的匹配 ⇒ 原文"→ `InvalidProgramException`"在本运行时**不成立**。

## 4. 边界与残余

1. **后端覆盖**：A/B 与 JIT 读数只覆盖 **CoreCLR 10 / Windows x64**；Mono 与 LeanCLR 的验证严格度与局部槽布局未测（登记触发条件：换后端复跑同一探针）。
2. **危害量级**：本机未复现崩溃/截断 ⇒ 本条的真实收益是"**织入产物不再依赖 JIT 的宽容**"，不是"修掉一个可复现的崩溃"。报告原文的 `InvalidProgramException` 属**未验证假设**，已在 `01` 行内与本节更正。
3. **清空 exception handler 的语义**：手写访问器里的 `try/catch` 本来就会被整体重写丢弃（原实现同样丢弃，只是留下悬空 handler）；本轮只是把"悬空"也清掉。
4. **槽位约定仍在**：`Stloc_0`/`Stloc_1` 与 `Variables.Add` 的次序仍是隐式契约，只是**前提被强制成立**；未来若在 `Add` 之外再插变量，需同步复核（已在 `01` 行内登记）。
5. **`F-DEF-004` 的判据是预处理级**，不是"真 VS2022 机器上的 `.sln` 产物"（本机无该工具链）；真机输出未取得。

## 5. 过程事实（装置坑，供后续轮次复用）

1. **MSBuild 常驻节点锁文件 ⇒ 假 A/B**：一次 `-t:Rebuild` 因 `Script/UE/obj/Debug/net10.0/UE.dll` 被 `/nodeReuse:true` 的 MSBuild 工作节点（PID 53888）占用而失败，**删了 Game.dll 却没重建**；随后的普通 build 只是把旧产物复制回来 ⇒ "改后构建"与"改前"**哈希完全相同**（`893E78EF…`），一度误判"修复无效"。处置 = `dotnet build-server shutdown` ＋ `-nodeReuse:false`（/ `MSBUILDDISABLENODEREUSE=1`）；此后 `Game.dll` 哈希变为 `800CB60…`、A/B 才成立。
2. **Fody 只在目标程序集重编译时织入**：只改 `Script/Weavers/UnrealTypeWeaver.cs` 并 `dotnet build` 不会重新织入；必须先 `sync-weaver.ps1`（从插件模板重新生成工程侧副本）**再 touch 一个 Game 源文件**。`sync-weaver.ps1` 的注释里已写明。
3. **源生成器的文件名约束**：`[UClass]`/`[UStruct]` 类型所在文件必须命名为"类名去掉首个 `U`/`F` 前缀"（`UC_ERROR_02`）；`[UStruct]` 只能标 class（`CS0592`）。
