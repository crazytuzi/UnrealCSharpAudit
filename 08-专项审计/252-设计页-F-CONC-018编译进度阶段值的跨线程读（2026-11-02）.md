# 设计页 `F-CONC-018` —— 编译进度阶段值的跨线程读（2026-11-02）

> 分析范围：`F-CONC-018`（P2 · S=2.52 · 活跃）—— 「`FCSharpCompileProgress::GetStage()` 用 `const_cast` 加锁 ＋ 游戏线程每帧轮询」
> 状态：设计完成，**未施工**（结论：**方案 A（`mutable` 锁），1 词**；本轮 0 代码）

## 1. 代码事实（回 HEAD（B-211 交付）复核）

```cpp
// FCSharpCompileProgress.h
FString GetStage() const;          // ← const
void SetStage(const FString&);     // 写方在编译线程
private:
    FCriticalSection CriticalSection;   // ← 非 mutable
    FString Stage;
```

```cpp
// FCSharpCompileProgress.cpp:74 附近
FString FCSharpCompileProgress::GetStage() const
{
    FScopeLock ScopeLock(&const_cast<FCSharpCompileProgress*>(this)->CriticalSection);   // ← const_cast
    return Stage;
}
```

| 事实 | 读数 |
|---|---|
| `const_cast` 的唯一目的 | 在 `const` 成员函数里锁一个**非 `mutable`** 的互斥量 |
| 读方 | 编辑器 UI 每帧轮询（`FEditorListener::WaitForCompile()` 的进度窗，`SCompileProgressDialog::UpdateProgress`） |
| 成本 | 一次 `FScopeLock` ＋ 一次 `FString` 拷贝；B-210 量级估算 ≈100 ns 量级（未单独实测） |
| 并发语义 | 读方拿到的**一定是完整值**（锁保护 `FString` 拷贝），不存在撕裂 —— 这是当前实现的正确性来源 |

⇒ 本条**不是性能问题**（B-210 已改判），而是**两件事**：① `const_cast` 绕过 const 语义（可读性/易被误改成真 UB）；② "`const` 成员函数却改锁状态"这个表达本身在说谎。

## 2. 方案

### 方案 A：`mutable FCriticalSection CriticalSection;`（推荐）
```cpp
-    FCriticalSection CriticalSection;
+    mutable FCriticalSection CriticalSection;
```
```cpp
-    FScopeLock ScopeLock(&const_cast<FCSharpCompileProgress*>(this)->CriticalSection);
+    FScopeLock ScopeLock(&CriticalSection);
```
- 代价：**2 行（1 词 ＋ 1 处去 `const_cast`）**。
- 语义：**完全不变** —— `mutable` 是 C++ 对"逻辑 const、物理可变"的标准表达；锁仍被拿、值仍完整。
- G7：无日志/断言/throw/新公开面；`mutable` 不改变 ABI（成员布局不变）。
- 判据：`grep const_cast FCSharpCompileProgress.*` = **0**；套件同 SHA；编译 0/0。

### 方案 B：双缓冲/原子快照（去锁）
读路径改成读一个 `TAtomic<TSharedPtr<const FString>>` 或"两个 `FString` ＋ `std::atomic<uint32>` 索引"，写方发布新快照。
- 收益：读路径从"拿锁＋拷贝"降到"原子读＋引用计数"，≈100 ns → ≈5–20 ns。
- 代价：`+30/-10` 行；引入所有权/生命周期语义（快照何时释放），且**收益在会话量级上不可测**（每小时 6 µs 级）。
- 结论：**不推荐现在做**（收益 < 复杂度），记录为"将来若进度轮询从每帧变成每对象/每编译多次，再考虑"。

### 方案 C：契约（"允许弱一致读"）
把 `GetStage()` 改成不加锁直接返回 `Stage` 的副本，并在契约里写"允许读到旧值"。
- **不可接受**：无锁拷贝 `FString`（引用计数 ＋ 缓冲区指针）在并发写时是**真实的 UB**（撕裂可能读到已释放缓冲区），不是"弱一致"。⇒ 否决。

### 方案 D：把阶段值改成 `TAtomic<FName>`/枚举
根因是"用 `FString` 表达阶段"（`ParseLine` 从 dotnet 输出解析阶段字符串）。
- 收益：读写天然无锁、无分配。
- 代价：要改 `ParseLine`/`ProcessLine`/`SetStage` 的接口与所有阶段常量；且 `GetCompileProgress()` 的消费者（UI 文案）要跟着映射回字符串。⇒ 记录，不推荐现在做。

## 3. 推荐与判据

- **推荐**：**方案 A**（2 行）。它是"去 `const_cast`"的唯一零风险路径，也让"`const` 函数拿锁"变得名副其实。
- **判据**：`const_cast` 归零；`FScopeLock` 仍在 `GetStage()` 内（并发语义不变）；UBT 5.6 Succeeded；套件 **1 992/0 同 SHA**；§8 PASS。
- **不做的**：方案 B/D（收益不可测、改造面大）；方案 C（真 UB）。

## 4. 触发条件（升级到方案 B/D）

1. 进度轮询从"每帧一次"变成"每对象/每编译多次"（例如将来给多个并行编译各配一个进度条）；
2. 有用例证明 `GetStage()` 的锁在 profiler 中成为可观测热点（当前量级 ≈100 ns × 60 fps ≈ 6 µs/s）。

## 5. 残余

1. "每帧轮询"本身未改：它是 `FEditorListener::WaitForCompile()` 的既有交互（弹窗期间阻塞式刷新），改它要动 UI 语义。
2. 本条与 `F-DEF-003`／`F-DOM-007` 的"需设计"性质不同：它是**纯卫生**（2 行、零语义变化），建议下一轮直接施工，不需要再出决策页。
