## 1. `.gen.cs` → `.g.cs` 的依据（实证，不是"感觉更规范"）

### 1.1 约定是什么

Roslyn 的"生成代码"判定有三条**互相独立**的通道（任一命中即视为生成代码，分析器默认跳过它）：

| 通道 | 内容 |
|---|---|
| 文件名 | `*.g.cs` / `*.g.i.cs` / `*.designer.cs` / `*.generated.cs`，以及 `TemporaryGeneratedFile_*` 前缀 |
| 首部注释 | 文件开头含 `<auto-generated`（如 `// <auto-generated/>`） |
| 特性 | 类型/成员标了 `[GeneratedCode]` |

`.gen.cs` **不在**文件名集合内 —— 这是"`.gen` 不被识别"这一判断的唯一依据；但此前它只是**静态推论**，本轮做了实证。

### 1.2 实证装置（`Saved/Retest/b103-roslyn-gen`）

一个 `net10.0` 类库（`EnableNETAnalyzers=true` / `AnalysisMode=All`），7 个内容等价（仅类名不同、均**无**注释头）的源文件 + 1 个带头文件；判据 = NetAnalyzer 的 `CA1050` / `CA1707` **是否在该文件上报告**（这两条规则的 `ConfigureGeneratedCodeAnalysis` 默认跳过生成代码）。

| 文件 | 首部注释 | 诊断数 | 判定 |
|---|---|---|---|
| `Plain.cs` | 无 | **2**（CA1050 + CA1707） | 普通代码 |
| `B.gen.cs` | 无 | **2** | **未识别为生成代码** |
| `A.g.cs` | 无 | **0** | ✅ 后缀命中 |
| `C.gen.cs` | `// <auto-generated/>` | **0** | ✅ 注释命中（与文件名无关） |
| `D.generated.cs` | 无 | 0 | ✅ 后缀命中 |
| `E.designer.cs` | 无 | 0 | ✅ 后缀命中 |
| `F.g.i.cs` | 无 | 0 | ✅ 后缀命中 |

**包含性控制**（排除"文件根本没参与编译"这一竞争解释）：在同一工程放入 `G_Control.g.cs`（`Undefined_Symbol()`）⇒ **`Build FAILED`、`error CS0103` 指向该文件** ⇒ `.g.cs` **确实参与编译**，上表 0 诊断 = 被当作生成代码跳过，而非未编译。

### 1.3 结论与归因更正

1. **是**"更符合规范/约定"，但准确表述是：`.g.cs` 是 Roslyn 与 .NET 生态（WPF/设计器产物）的**标准生成代码后缀**，`.gen.cs` 是自造后缀、不被识别。
2. **但承重面是注释头**：`C.gen.cs` 证明只要首行有 `<auto-generated/>`，`.gen.cs` 也会被跳过。⇒ 上一轮 [`134`](134-轮B-99-T3第九次选片与立项建议（2026-10-27）.md) §2.8 把"hint 后缀不被识别"列为缺陷主因是**归因偏重**（结论方向不变：`.gen.cs` 确实不合约定）；B-101 交付的**两半是双重保险**：头对任意文件名生效，后缀让 `EmitCompilerGeneratedFiles` 产物名与工具预期一致（部分工具/IDE 只认后缀不读注释）。
3. **顺带更正一处静态推导**：此前曾以"二进制里搜不到 `.designer.cs`"怀疑后缀通道不存在；实证表明后缀通道存在（D/E/F 三个文件同时命中）⇒ 该反证无效（字面量可能不以完整 UTF-16 串存在，但行为存在）。

## 2. `SanitizeFloat` 对齐引擎

### 2.1 引擎里的对应物：`FString::SanitizeFloat`（同名同签名）

| 项 | 引擎（UE 5.6） | 本仓 fork（B-101 后） |
|---|---|---|
| 位置 | `Runtime/Core/Private/Containers/String.cpp.inl:1210-1265`；声明 `UnrealString.h.inl:2281` | `Source/UnrealCSharpCore/Public/Binding/Function/TDefaultArgument.inl:7-73` |
| 签名 | `SanitizeFloat(double InFloat, const int32 InMinFractionalDigits = 1)` | **逐字相同** |
| 截断/补零 | `TrimIndex` / `DecimalSeparatorIndex` / `NumFractionalDigits` / `FractionalDigitsToPad` 四段，`TempString` | **逐字相同**（四个局部量同名同序） |
| 格式化 | `Printf(CHARTEXT(FmtCharType, "%f"))` ⇒ **6 位小数** | `std::stringstream` + `fixed` + **9 位**（B-103 起改为 `Printf("%.9f")`） |
| 负零 | `UE::Core::Private::StripNegativeZero(InFloat)`（= `InFloat += 0.0f`，`String.cpp:57-63`） | 原先**无**；B-103 起 `InFloat == 0.0 ? 0.0 : InFloat` |
| 非数值 | `if (!TempString.IsNumeric()) return TempString;` | **无** |
| 断言 | `check(TrimIndex != INDEX_NONE && DecimalSeparatorIndex != INDEX_NONE)` | **无**（G7） |
| `RemoveAt` | `EAllowShrinking::No` | 版本门控 `UE_F_STRING_REMOVE_AT_E_ALLOW_SHRINKING`（5.0 兼容） |

**为什么不能直接调用引擎函数**（否则对齐就该是"删掉 fork"）：引擎的 `%f` 是 **6 位小数**；本仓有 `SMALL_NUMBER = 1e-8` 的默认值（`FRegisterVector2D.cpp:138`），6 位下会被打成 `0.000000` → 裁剪/补零后变 `"0.0"`，而当前产物是 `0.00000001` ⇒ 直接替换是**行为回归**。插件需要 9 位（`float::max_digits10`），这正是 fork 的存在理由。

### 2.2 本轮对齐的三处（均已落地）

| # | 对齐点 | 做法 | 引擎依据 |
|---|---|---|---|
| 1 | **格式化实现** | `FString::Printf(TEXT("%.9f"), Value)` 取代 `std::stringstream`；删除 `<iomanip>` / `<sstream>` | 引擎实现本身用 `Printf("%f")`；`%.9g` / `%.17g` 是引擎自己的 float/double 格式化先例（`CompactBinarySerialization.cpp:65-66`） |
| 2 | **负零归一** | `const auto Value = InFloat == 0.0 ? 0.0 : InFloat;` | `StripNegativeZero`（`InFloat += 0.0f`）；引擎自动化测试 `FStringSanitizeFloatTest` 断言 `-0.0 → "0"`（`Private/Containers/StringTest.cpp:26-27`）。本仓用显式三目等价表达：不调用 `UE::Core::Private` 私有符号、也不写"看起来像 no-op"的 `+= 0.0` |
| 3 | **精度字面量** | `%.*g` → `%.9g`（与 `%.9f` 同一精度）；不再引用 `numeric_limits` | 引擎 `%.9g`（同上）；`float::max_digits10` 就是 9 |

### 2.3 有据不齐的三处（保留差异）

1. **不直接复用引擎函数** —— 6 vs 9 位（§2.1 的 `1e-8` 实证）；
2. **不加 `IsNumeric()` 早退** —— 对 `inf`/`nan` 的现有输出（原样返回）与引擎一致，加早退只多一个出口，违反本仓"单一出口"；
3. **不加 `check`** —— G7 禁止；`RemoveAt` 的版本门控是 5.0 兼容的既有形态，不能改回引擎的 `EAllowShrinking::No`。

### 2.4 命名对齐

- **与引擎逐字一致**：`TempString` / `TrimIndex` / `DecimalSeparatorIndex` / `NumFractionalDigits` / `FractionalDigitsToPad`（以及形参 `InFloat` / `InMinFractionalDigits`）；
- **新增的两个名（🔁 已于轮 B-105 消除，见 [`140`](140-轮B-105-SanitizeFloat标识符零新名对齐（2026-10-27）.md)）**：`Value` 与 `bIsFixedUnderflow`。后者**引擎无对应概念** —— `FString::SanitizeFloat` 不做"极小值"处理（6 位 `%f` 会把 1e-8 直接压成 0，属"显示用"取舍），引擎里 `underflow` 一词只用于整数容器（`Array.h`/`RingBuffer.h`）。⇒ 保留该名（`bIs*` ＋ 语义自解释）并在报告登记"无引擎先例"。

### 2.4.1 引擎四个版本的实现形态（跨版本对照）

| 项 | UE 5.0 | UE 5.4 | UE 5.6 / 5.8 |
|---|---|---|---|
| 定义 | `Private/Containers/String.cpp:1214`（**非模板** `FString::SanitizeFloat`） | `Private/Containers/String.cpp.inl:1182`（`UE_STRING_CLASS` 模板） | 同左（`:1210` / `:1241`） |
| 负零 | `StripNegativeZero(InFloat)` —— **只在本 .cpp 内声明**（`String.cpp:1205`，无公开头声明） | `UE::Core::Private::StripNegativeZero`（`UnrealString.h:466`，`CORE_API`） | 同左（`UnrealString.h:478`） |
| 格式化 | `Printf(TEXT("%f"))`（6 位） | `Printf(CHARTEXT(ElementType, "%f"))` | 同左 |
| `RemoveAt` | `RemoveAt(..., /*bAllowShrinking*/false)` | `RemoveAt(..., EAllowShrinking::No)`；**同时保留弃用的 `bool` 重载**（`UnrealString.h.inl:453-458`，`UE_ALLOWSHRINKING_BOOL_DEPRECATED`） | 同左（`:483-496`） |
| 断言 / 早退 | `check(...)` ＋ `IsNumeric()` 早退 | 同左 | 同左 |

⇒ 本仓 fork 的两处"兼容写法"都能由此解释：**显式负零三目**（5.0 的 `StripNegativeZero` 不可跨 TU 调用，5.4 才以 `UE::Core::Private` 暴露）；**`RemoveAt` 版本门控**（5.0 只有 `bool` 重载）。

> ✅ **本条已施工（轮 B-104，见 [`139-轮B-104`](139-轮B-104-精度与极小值对齐及RemoveAt门控5.4与UE54实编（2026-10-27）.md) §3）**；⚠️ **更正**：5.4 的 `UE_ALLOWSHRINKING_BOOL_DEPRECATED` 实为**空宏**（`//UE_DEPRECATED(5.4, …)` 被注释）⇒ 旧 `false` 路径在 5.4 上**不会**出弃用告警，本改动的价值是"阈值与首可用版本一致"。**原线索**：`UE_F_STRING_REMOVE_AT_E_ALLOW_SHRINKING` 的阈值是 **5.5.0**（`UEVersion.h:130`），但 **5.4 的 `UnrealString.h.inl:453` 已有 `EAllowShrinking` 重载** ⇒ 在 **5.4 实编点**上本仓走的是**已弃用的 `bool` 重载**（`UE_ALLOWSHRINKING_BOOL_DEPRECATED`；无 `/WX` 故不致命，只会出弃用告警）。可一行把阈值改成 **5.4.0**，但需在 B-30 的 `UE54Check` 实编点复验（本条只记录线索，**未取号、未改**）。

## 5. 未取得 / 边界

1. **对齐只做了"实现与命名"，没有把 fork 换成引擎调用**（§2.1 的 `1e-8` 是硬理由）；若维护者接受 `1e-8 → 0.0` 的行为变化，可另开一轮直接调用 `FString::SanitizeFloat`。
2. `-0.0` 的归一目前**无绑定实证**（产物扫面 0 处负零默认值），判据只到探针层。
3. 全量生成器 manifest 仍未跑（静态扫面替代）；`dotnet build Game.csproj` 的 `MSB4006` 环境问题未变（B-101 §6）。
4. Roslyn 实证用的是 **SDK 10.0.403 自带分析器**；不同 SDK/分析器版本的"是否跳过生成代码"配置可能不同（`GeneratedCodeAnalysisFlags` 由各规则声明），本页只证明**框架层识别**存在且后缀/注释各自生效。
