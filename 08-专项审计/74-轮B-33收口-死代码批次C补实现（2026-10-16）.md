### 4.2 根因与**为什么 `" = null"` 是承重的**

- 因此 `F-DEF-007` 的真实定性是：**不是"元数据默认值被静默丢弃"，而是"签名默认值与体内默认值分工"**；审计原文的"生成 `= null`，与真实默认值不符 ⇒ 语义偏差"**在观测层面不成立**。

## 10. 为什么 `[Localized]` 与 `[FieldNotify]` **不补**（维护者第三次追问的正面回答；v3 补写）

> 维护者问："Localized 和 FieldNotify 为啥不需要补呢"。**答案：不存在"补了会生效"的东西可写 —— 写了不但没用，而且会偏离引擎语义**。下面把两条通道的**可写面**逐一穷举。

### 10.1 `[Localized]`：**引擎自己 5.0 起就只报废弃、不写任何东西**

| 可写面 | 穷举结果 | 证据 |
|---|---|---|
| **property flag（`CPF_*`）** | **没有对应 flag** | `ObjectMacros.h` 的 `EPropertyFlags` 全表无 `Localized`/`CPF_Localized`（4 个引擎一致） |
| **property metadata（`metadata=(Localized=…)`）** | **UHT 不写**：`case EVariableSpecifier::Localized:` ⇒ **只 `LogError("The Localized specifier is deprecated")`**，既不置 flag 也不加 metadata | **UE 5.0** `UnrealHeaderTool/Private/HeaderParser.cpp:3066-3068`；**5.4 / 5.6 / 5.8** `UhtPropertyMemberSpecifiers.cs:189-194`（逐字相同） |
| **运行时消费者** | **全引擎 0 个**读 `"Localized"` metadata 的点（CoreUObject / Engine / Core 三个模块扫过；仅命中 `AssetDataTagMap.cpp` 里一个同名**测试字符串**与 `TextLocalizationManager` 的 `LEETIFYUnlocalized` 命令行开关，均无关） | 见上 |
| **插件的代码生成器** | `Source/SourceCodeGenerator/**` 与 `Source/CodeGenerator` 里**根本没有 `Localized` 这个 token**（0 命中） ⇒ C# 侧也没有可对齐的落点 | `Select-String -Path Source/SourceCodeGenerator -Pattern Localized` ⇒ 0 |
| **本地化的真实机制** | UE5 的本地化走 **`FText` + `LOCTEXT`/`NSLOCTEXT` 命名空间/键**（UHT 为 `FText` 生成 `LocMetadata`），与 `[Localized]` 这个**标注**无关 | `UhtHeaderCodeGenerator*.cs` 的 FText 处理 |

⇒ **"补"只有两种可能，两种都错**：① 写 metadata `Localized=""`（UHT 不写 ⇒ 制造差异，且无消费者）；② 补一个 `CPF_` flag（**不存在**）。**C# 侧 `[Localized]` 特性类保留**（用户可见的标注面；且若将来引擎恢复该语义，插件有地方接），但**生成器侧保持空块** —— 这与 `ObjectMacros.h` 里 `UP::Localized` 说明符**至今仍被登记**（`UPROPERTY` 关键字表）但 UHT 只报废弃，是同一状态。

### 10.2 `[FieldNotify]`：**它不是"标志位"，而是"每个类编译期生成一个虚函数覆写"**

**① 描述符的读取路径（关键：不在 `UClass` 上，在 CDO 的接口上）**

```cpp
// FieldNotification/Public/INotifyFieldValueChanged.h:45
virtual const UE::FieldNotification::IClassDescriptor& GetFieldNotificationDescriptor() const = 0;   // ← 纯虚，接口方法
// Engine/Private/BlueprintGeneratedClass.cpp:515-529
void UBlueprintGeneratedClass::InitializeFieldNotifies()
{
    … if (FieldNotifies.Num() && ImplementsInterface(UNotifyFieldValueChanged::StaticClass()) && ensure(GetDefaultObject(false)))
    {
        TScriptInterface<INotifyFieldValueChanged>(GetDefaultObject(false))       // ← 走 CDO
            ->GetFieldNotificationDescriptor().ForEachField(this, …);             // ← 走上面那个纯虚
    }
}
// FieldNotification/Public/IFieldNotificationClassDescriptor.h:34-38
virtual void ForEachField(const UClass* Class, TFunctionRef<bool(FFieldId)> Callback) const { }   // ← 基类实现 = 空
```

⇒ **可写面穷举**：

| 可写面 | 结果 |
|---|---|
| property flag | ❌ **`CPF_FieldNotify` 在 5.0/5.4/5.6/5.8 的 `ObjectMacros.h` 里都不存在**（`EPropertyFlags` 无该成员；`UP::FieldNotify` 只是 **UPROPERTY 说明符关键字**，`UF::FieldNotify` 是 UFUNCTION 的） |
| property metadata | ❌ UHT 的 `FieldNotifySpecifier`（`UhtPropertyMemberSpecifiers.cs:485-489`）**只置 `PropertyExportFlags \|= FieldNotify`**（UHT 内部代码生成标志），**不写任何运行时 metadata**；运行时也没有任何读它的点 |
| 运行时注册 API | ❌ `FieldNotification` 模块的 `Private/FieldNotificationModule.cpp` 全文 = `IMPLEMENT_MODULE(FDefaultModuleImpl, FieldNotification)`（**空模块**）⇒ **没有**"给某个 `UClass` 注册字段"的接口 |
| 覆写虚函数 | ❌ 要覆盖 `IClassDescriptor::ForEachField` / `GetFieldNotificationDescriptor()`，**必须有一个能写 C++ 虚函数覆写的实例** —— 动态类由引擎无条件 `NewObject<UClass>` 构造（**不是自定义 `UClass` 子类**），vtable = `UClass` 的 ⇒ **运行时无法注入覆写** |

⇒ **要"真正实现"只有两条路，都不是"补一个分支"**：① 让插件把动态类改成**自定义 `UClass` 子类**并覆写该虚函数（改的是动态类构造架构）；② 让插件把动态类造成 **`UBlueprintGeneratedClass`** 并走引擎的 `InitializeFieldNotifies()`（同样等于换掉类构造路径）。两者均属**独立立项**，**触发条件** = 维护者要求"动态 C# 类支持字段通知"。

**② 一个必须说清的边界（避免高估缺口）**：`UBlueprintGeneratedClass::InitializeFieldNotifies()` 说明**蓝图生成的类由引擎直接处理字段通知**。因此对本插件而言：

- **C# 继承自蓝图类（`BP_*_C`）的动态类**：其父链上已有 `UBlueprintGeneratedClass` 的字段通知实现 ⇒ **该场景不是插件缺口**；
- **纯 C# 新建（`[UClass]` 直接继承 C++ 类）且声明 `[FieldNotify]`**：这才是缺口的全部范围 —— 而它撞上的是上面那条"虚函数无法运行时注入"。

### 10.3 与 `[SealedEvent]` 的对照：为什么它"能补"而这两个"不能"

| 属性 | 引擎侧的实体是什么 | 插件侧是否可写 | 结论 |
|---|---|---|---|
| `[SealedEvent]` | **一个 flag**：`FUNC_Final`（`HeaderParser.cpp:6549-6551` / `UhtFunctionParser.cs:459`），且插件里**已有消费者**（`FCSharpBind.cpp:302`） | ✅ `InFunction->FunctionFlags \|= FUNC_Final` | 🟢 **可补、已补** |
| `[Localized]` | **什么都没有**（引擎 5.0 起只报 deprecated） | ❌ 无可写面 | ⚪ **不补（空块即正确）** |
| `[FieldNotify]` | **一个类内虚函数覆写 ＋ 描述符结构体**（编译期宏），值不在 `UClass` 上而在 **CDO 的接口**上 | ❌ 运行时无法注入 vtable 覆写 | ⚪ **不补（登记为"编译期机制"）** |

⇒ **判定准则（可复用）**：**"这个属性在引擎侧最终落成一个可写的存储位吗？"** —— 落成 **flag/metadata** ⇒ 插件能补（`[SealedEvent]`）；落成**代码生成物（宏/虚函数/类型定义）** ⇒ 插件补不了（`[FieldNotify]`）；**什么都没落** ⇒ 补了反而偏离（`[Localized]`）。
