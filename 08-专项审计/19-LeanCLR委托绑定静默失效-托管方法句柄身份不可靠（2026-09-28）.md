
四个候选失败点，逐个的**结构判据**：

| # | 查找 | 结构 | 先验判断 |
|---|---|---|---|
| ① | `GetDelegate<FMulticastDelegateHelper>(handle)` | `TMap<IManagedHandle, …>`（C++ 侧） | 句柄由 `HandleData.Alloc`（C#）给出、C++ 原样存回 ⇒ **与后端无关** |
| ② | `GetObject(InObject)` | `FObjectRegistry` | 后端无关 |
| ③ | `FReflectionRegistry::GetClass(InManagedType)`（`FReflectionRegistry.cpp:929-953`） | 按 `FullName` 缓存；`FullName` 由 `IScriptDomain::GetFullName` 给出 | 若 `Type` 对象驻留则恒命中 |

1. **①②③ 全部为真、只有 ④ 为假**：`helper=1`、`object=1`、`class=1 name=UUnitTestSubsystem`、`method=0`。⇒ 不是句柄失效、不是对象/类没解析出来，**恰好断在"方法身份"这一步**。

3. **同一方法的两次请求句柄相同**（`25133`/`25133`、`25823`/`25823`）⇒ `HandleData` 的对象身份表本身是工作的（`this`=14520、`type`=12576、同一个 `MethodInfo` 两次 `Alloc` 都稳定）；⇒ **不是"CWT 在 LeanCLR 上不工作"，而是"同一个方法存在两个不同的 `MethodInfo` 包装对象"**。
4. **表里的句柄是强句柄**（`ArrayBridge.ArrayGet` → `HandleData.Alloc(Value)`，默认 `bIsWeak=false`）⇒ 描述符期对象一直活着、句柄一直有效 ⇒**不是"句柄已死"**。
5. **为什么 CoreCLR/Mono 不中**：实测两后端全绿。.NET 的 `MethodInfo` **引用相等不受规范保证**（`MemberInfo.Equals` 的语义是 `MetadataToken` + `Module`；CoreCLR 的 `RuntimeMethodInfo` 恰好按 (类型,方法) 缓存/驻留，`Type.GetMethods()` 与 `Delegate.Method` 返回同一实例）。⇒ **这是一个"靠实现细节吃饭"的假设**，在 LeanCLR 上不成立。

> ⚠️ **未取得的细分**（不得读作已证）：本轮只证到"**两个句柄 ⇒ 两个包装对象**"，**未区分**是 `Type.GetMethods()` 每次新建包装、还是 `Delegate.Method` 走另一条包装路径（要区分需在 LeanCLR 侧加托管探针比对 `ReferenceEquals`）。**但这对修法无影响**：两种情形都要求"不要用对象身份当方法身份"。

### 3.4 同型面穷举：全域还有哪些「成员句柄」通道（维护者追问后的补做）

维护者追问"其他地方还有 `IManagedHandle InManagedMethod` 吗？有的话应该都有问题" ⇒ 本轮做了**全域穷举**。判据分两类，只有第一类会复现 `F-RM-016`：

- **A 类（危险）**：native 从**枚举**铸句柄存表，C# 之后拿**新取的包装对象**当键回查 ⇒ 依赖"同一成员 ⇒ 同一包装对象"（LeanCLR 不成立）。

### [F-DEL-022] 每次委托绑定泄漏一个 `MethodInfo` 的强 `GCHandle`（无任何释放点）—— 随 `InMethodInfo` 形参删除而闭合

- **类别**: 内存/资源泄漏（句柄驻留）
- **严重度**: **P3**（量级 = 每次 `Add`/`AddUnique`/`Remove`/`Contains`/`Bind` 各 1 个强 `GCHandle` + 1 条 `Handles` 条目 + 1 条 `ConditionalWeakTable` 条目；**驻留至域卸载** —— 与 `F-REG2-002`/`F-CS2A-023` 同一族，但只在委托注册/绑定路径上触发，非每帧）

- **函数**: `FMulticastDelegateImplementation.FMulticastDelegate_{Contains,Add,AddUnique,Remove}Implementation`、`FDelegateImplementation.FDelegate_BindImplementation`
- **置信度**: **高**（代码事实：`HandleData.Alloc` 无匹配 `Free`；`FMethodReflection::~FMethodReflection` 只释放描述符期铸造的那些句柄）

**现状（代码事实，HEAD）**

```csharp
__FMulticastDelegate_AddImplementation(InDelegate, InObject, HandleData.Alloc(InType),
    HandleData.Alloc(InMethodInfo));        // ← :44-45 HEAD：每次调用为 MethodInfo 新建一个强句柄
```

```cpp
// FRegisterMulticastDelegate.cpp:84 HEAD —— 只用于比较，从不 Free
if (const auto FoundMethod = FoundClass->GetMethod(InManagedMethod))
```

**调用上下文**

C# 公开 API `FOnXxxEvent.Add(UObject, Delegate)` → `FMulticastDelegate_AddImplementation` → native。对照同一行里的 `HandleData.Alloc(InType)`：**它有归属**（`FReflectionRegistry::GetClass(const IManagedHandle)` 命中缓存时 `Free` 掉传入句柄，`FReflectionRegistry.cpp:939`；未命中则由 `FClassReflection` 长期持有 —— 即 `F-CS2A-007` 已裁定的"归属分裂是设计"）⇒ 收支平衡；而 `InMethodInfo` 的句柄**两边都不认领**，且若外部调一次 `Free` 也会被 `HandleReference.Count` 挡住（每次 `Alloc` 都 `Count++`）。

**问题**

`HandleData.Alloc(object, bIsWeak=false)`（`HandleData.cs:41-58`）建的是**强** `GCHandle` + `ConditionalWeakTable` 条目 + `Handles` 字典条目 ⇒ 每次委托绑定都永久钉住一个 `MethodInfo` 包装对象，直到 `HandleData.Clear()`（域卸载；LeanCLR 下即进程级）。**本缺陷由 `F-RM-016` 的"身份比对"设计派生** —— 一旦不再需要句柄身份，这个句柄就没有存在理由。

**建议**（**本轮已随终版闭合**）

删除 `InMethodInfo` 形参与 `HandleData.Alloc(InMethodInfo)`（见 §6.2）⇒ 不再分配、也就无需释放。**未改**：`ManagedMethod` 字段与描述符期铸造的句柄归 `FMethodReflection` 所有（`~FMethodReflection` 里 `ScriptDomain->Free(ManagedMethod)`，`FMethodReflection.cpp:34-42`）—— 那一路径本来就收支平衡。

**验证方式**

- 判别式：临时探针统计 `HandleData.Handles.Count`（或 `Alloc` 调用数与 `Free` 调用数之差）在 N 次 `Add` 前后的增量 —— HEAD 为 **+N（含 1 个方法句柄/次）**，终版为 **+N−N=0**（仅剩 `InType` 的"命中即释放"平衡对）。
- 结构性判据：`git grep "Alloc(InMethodInfo)"` = **0**（终版）。

### [F-RM-017] `FPropertyReflection::ManagedProperty` / `FFieldReflection::ManagedField` 存了成员句柄却**无任何读取者** —— 同型风险（潜伏）

- **类别**: 死代码 / 隐患（同型风险）
- **严重度**: **P3**（**当前不是缺陷**：无消费者 ⇒ 无错误结果；风险在于"将来谁按它反查成员就复现 `F-RM-016`"）
- **文件**: `Source/UnrealCSharpCore/Private/Reflection/FPropertyReflection.cpp:7`/`:20-27`、`Source/UnrealCSharpCore/Public/Reflection/FPropertyReflection.h:27`；`Source/UnrealCSharpCore/Private/Reflection/FFieldReflection.cpp:5`/`:13-20`、`Source/UnrealCSharpCore/Public/Reflection/FFieldReflection.h:19`

- **置信度**: **高**（grep 穷举：这两个字段的全部引用 = ctor 初始化 + 析构 `Free`，**无 getter、无比较、无查表**）

**现状（代码事实）**

```cpp

…
	if (IManagedHandleIsValid(ManagedProperty))               // :20
```

**调用上下文**

`FClassReflection::ParseProperties/ParseFields`（`FClassReflection.cpp`）从 `Utils.GetClassProperties/Fields` 的数组逐元素 `ArrayGet` 取句柄 → 传给两个 reflection 的构造函数。**此后无人读取**（`git grep "ManagedProperty\|ManagedField"` = 16 命中，全部落在上述 ctor/字段/析构；`git grep "GetManagedProperty\|GetManagedField"` = **0**）。

**问题**

**建议**（**本轮未改**，仅登记）

三条路，按库内口径的偏好排序：① **只加注释说明它是"保活用、不得作为成员身份键"**（⚠️ 与库内"不新增注释"口径冲突，故需维护者拍板）；② 若确认保活也不需要（析构 `Free` 只对**同一**对象有意义，而对象被钉住本身并非必需）⇒ **删字段 + 删 ctor 形参 + 删析构分支**（与 `F-RM-016` 同样"消除而非兜底"）；③ 维持现状，仅在本表登记为潜伏。**本轮不动它的理由**：`FPropertyReflection`/`FFieldReflection` 不在本次失败的调用链上，且删字段会牵动 `ParseProperties/ParseFields` 的签名（跨 2 文件 + 与 `Weavers` 无关）；而 `F-RM-016` 的教训恰好说明"能用名字就别用句柄"，故把它留给下一轮按 ② 处理更合适。

**验证方式**

- `git grep "ManagedProperty\|ManagedField" Source/` = 16 命中、`git grep "GetManagedProperty\|GetManagedField" Source/` = **0** ⇒ "无读取者"可复现。
- 若走方案 ②：删除后 UBT **Succeeded** + 两后端 `-game` **1740 / 1740**（该字段不参与任何运行期路径 ⇒ 应逐字节等价）。

## 9. 复用价值（方法论）

1. **「托管对象句柄」≠「元数据身份」**：`HandleData` 给的是**对象身份**（`ConditionalWeakTable` 按引用），而 `MethodInfo`/`FieldInfo`/`PropertyInfo` 的**语义身份**是 `MetadataToken + Module`；ECMA/BCL **不保证**引用相等。凡是要把 C# 侧的成员传过边界再在 native 侧比对的地方，都必须用"名字+元数"或"元数据 token"，**不能**用句柄相等。本轮是本库第一次把这条写进实证。
2. **多后端库的"身份类"假设要单独列清单**：本库已有大量"按名字+元数"的解析（override 绑定、动态生成、`.ctor`），唯独这一条查找用身份 ⇒ **一个跨 5 个调用点的单点假设**。建议后续把"跨边界身份"类假设单独成表（句柄/地址/`FName`/token），逐条标出**各后端是否成立**。
3. **探针模板（可复用）**：对"嵌套 `if` 静默失败"的入口，最省事的实证方式 = 把**每一步条件提为局部量 + 逐条打 `UE_LOG`**，并在"集合查找失败"分支 **dump 整个集合**（本次 384 行 dump 一次性给出"表里存的是 12945 / 请求的是 25823"这一决定性判据）。⚠️ 注意**不要**为了让探针"再算一遍"而重复调用会消费句柄的函数（`FReflectionRegistry::GetClass` 命中缓存时会 `Free` 传入句柄）。
4. **"假绿"用例的识别**：11 条用例里 **3 条**（`*IsBoundFalseWhenPristine` ×2、`MulticastDelegateSetBinds`）在故障态下**照样通过** —— 因为 `no-op` 与"未绑定"的观测值相同、而 `IsBound()` 的判据是 `InvocationList.Num() > 0`。⇒ 回归用例必须**成对**写（"该真时为真"与"该假时为假"各一条），本轮 6 条红 + 3 条假绿正是这条教训的实例。
5. **先数家法再动手（本轮的第二次迭代）**：首版为了"少重复"抽了一个新的私有头 + 全局自由函数，功能上完全正确（3 × 1740/0 + CoreCLR 1740/0），但**与库内写法相悖** —— 库内 **11 处 C++ + 15 处 C#** 的 UTF-8 转换**无一例外全部 inline**，且"**未新增 helper/宏/公开 API**"在既有报告里被当作**优点**记录。⇒ 改法：① 动手前先 `grep` 目标写法的**全部既有实例**并统计形态；② 若"我的抽象"在库里 **0 先例**，默认不引入（本轮的 helper 还有 unity TU 内的**全局重名风险**这一实际代价）；③ **重复 ≠ 坏**：本库刻意容忍 4 个近乎逐字相同的 interop 函数，可读性与"可 grep 出全部转换点"优先。二版 = 6 文件、**零新增文件**，5 个转换点与既有 11 处**逐字同形**。
6. **先问“这条判据还有别的调用者吗？”—— 消除优于兼容**：三轮演进的最后一跃不是技朧问题，而是一个判断—— 当根因是“某个假设不成立”时，先统计该假设的**全部消费者**：`GetMethod(IManagedHandle)` 只有 5 个调用点、`GetManagedMethod()` 只有 1 个 ⇒ **删掉假设本身**比“给它加一层兜底”更小、更彻底（少一个参数、少一个 getter、少一条未来会再踩的路）。**反向提醒**：若该判据有多个消费者（尤其跨模块），则应先定契约再改，不可为一个场景删。
⚠️ **代价必须说清**：删得掉的前提是“身份精确匹配在库内**本就只有这一处**、而其余解析全是名字+元数”（已 grep 穷举）；否则就是“为了统一而丢精度”，应改走 §6.1 的 β 方案。
