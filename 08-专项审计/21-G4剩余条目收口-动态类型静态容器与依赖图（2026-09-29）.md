## 3. 逐条改法

### 3.1 `F-DYN-003` + `F-LIFE-006`（甲）：`ReInstance` 摘掉死键

`FDynamicClassGenerator.cpp` 的 `ReInstance` 在 `RemoveFromRoot()` + `MarkAsGarbage()` 之前摘掉三张以旧类为键的表（**顺序即报告要求**：必须在 `RemoveFromRoot` 之前）：

```cpp
	else
	{
		NamespaceMap.Remove(InOldClass);

		DefaultSubObjectInfoMap.Remove(InOldClass);

		DefaultValueMap.Remove(InOldClass);

		InOldClass->RemoveFromRoot();

		InOldClass->MarkAsGarbage();
	}
```

`FDynamicStructGenerator.cpp` 的 `ReInstance` 同形处理 `NamespaceMap`（其 `DynamicStructMap` 是名字键，属 (乙)，见 §3.2）。

> **为什么删掉是安全的**：这三张表是**反向元数据**（"这个对象属于哪个命名空间"/"它的默认值与子对象信息"），删除**不销毁任何 UObject** —— 对象的存活由 `AddToRoot()`（class `:396`、struct `:249`）与 `RemoveFromRoot()` 决定。旧对象已在同一函数里被 `MarkAsGarbage()`，其三条记录此后**没有任何合法读者**（下一次生成会为新类重建记录）。

### 3.2 `F-LIFE-006`（乙）：反向表在"同名重建"时先摘旧条目

`FDynamicClassGenerator::Generator`（`:174` 之后）与 `FDynamicStructGenerator::Generator`（`:92` 之后）各补一行 `Remove(ClassName)`，紧随 `DynamicXMap[ClassName]` 取值之后、`DynamicXSet.Remove` 之前：

```cpp
		OldClass = DynamicClassMap[ClassName];

		DynamicClassMap.Remove(ClassName);      // 本轮新增

		DynamicClassSet.Remove(OldClass);
```

> **窗口分析（为什么不会短暂"查不到"）**：删除到同一趟稍后 `GeneratorClass` 重新 `Add` 之间，唯一的中间消费者是 `ReInstance` → `FDynamicStructGenerator::ReInstance` 的 `FReflectionRegistry::GetClass(DynamicClass)` 循环（`:372-378`），该函数查的是**反射注册表**（不是本表）⇒ 窗口内无人读 `DynamicClassMap`。`DynamicClassSet.Remove(OldClass)`（原代码就有）走的是完全相同的窗口，属既有模式。
> **收益**：本表项从"指向一个已 `Rename`、迟早被 GC 的旧对象"变为"始终指向当前对象"，同时把"旧名字键无限累积"这一半收敛掉（旧名字下不再留 dangling 项）。

### 3.3 `F-DYN-008`：`SetClass<true>` 的无点路径

`FTypeBridge.inl` 的 `SetClass<IsSoftReference>` 补 `else` 分支：

```cpp
	if constexpr (IsSoftReference)
	{
		if (int32 Index; InPathName.FindLastChar('.', Index))
		{
			…（原样：已完成即立即执行，否则注册 OnCompleted）
		}
		else
		{
			InSetClass();      // 本轮新增
		}
	}
```

> **语义**：`InSetClass()` 即那个 `LoadObject<UClass>(nullptr, *PathName)` + `ObjectProperty->PropertyClass = Class;` 的 lambda。空 / 无点路径下 `LoadObject` 返回 `nullptr` ⇒ `PropertyClass` **仍然是 `nullptr`**，与原行为**一致**；差别在于**执行路径不再静默短路** —— 这正是 F-DYN-008 报告的主诉（"`:202` 的 `FindLastChar` 为 false ⇒ `InSetClass()` 既不立即调用、也不注册 `OnCompleted`"）。
> ⚠️ **边界（不在本轮范围内）**：`LoadObject` **失败**（`FTypeBridge.inl:282-284`）导致 `PropertyClass == nullptr` 的那一半**未修** —— 见 §5。
> **为什么这是修法的正确落点**（而非"顺着 `IsCompleted` 走"）：`:43 return true` 的"未知名字视为已完成"意味着 `IsCompleted` 对**从未成为依赖节点的类型**（含命名空间与节点名不同源的 F-DYN-012 情形）也返回 true ⇒ 那些类型本来就已走 `InSetClass()` 分支。⇒ 走到"无点路径"的是**另一类**输入（`PathName` 为空），本轮把这一类补上，两条路径的语义因此一致。

### 3.4 `F-DYN-010`：依赖图的一次性生命周期

新增 `FDynamicDependencyGraph::Empty()`（`NodeArray.Empty(); NodeMap.Empty();`）与转发 `FDynamicGeneratorCore::Empty()`，并在 `FDynamicGenerator::Generator()` 中**图已被完整消费之后**调用：

```cpp
	FScriptDomainScope([]()
	{
		… 四个生成器 + FDynamicGeneratorCore::Generator();
	});

	FDynamicGeneratorCore::Empty();
```

> **方法名 `Empty`（而非初版的 `Reset`）—— 维护者裁定，三条本仓先例**：① **本仓的 `Reset` 是"照抄引擎 API 名"** —— 插件自有类里唯一叫 `Reset` 的是 `FOptionalHelper::Reset()`（`UnrealCSharp/Public/Reflection/Optional/FOptionalHelper.h:23`），实现只有一行 `OptionalProperty->MarkUnset(Data)`（`FOptionalHelper.cpp:72-75`）＝ `TOptional::Reset()` 的包装；`FArrayHelper::Reset(int32)`（`FArrayHelper.h:54`）同理是 `TArray::Reset` 的包装。本轮的 `FDynamicDependencyGraph` / `FDynamicGeneratorCore` **都是本仓自有类、不镜像任何引擎 API**，不属该惯例。② **本仓自有类清空容器一律用 `Empty`**：同文件的 `FDynamicGeneratorCore::EndCodeAnalysisGenerator()` 就是 `DynamicMap.Empty()`（`:31`）、`Registry/TMapping.inl:24` 是 `Map.Empty()`、容器 Helper 家族一律 `void Empty(…)`（`FArrayHelper.h:56` / `FMapHelper.h:22` / `FSetHelper.h:22`）。③ **语义更精确**：`TOptional::Reset()` 是"标记为未设置"（值回到未设置态、对象仍在），本方法做的是**清空两个容器**；且本类内 `FNode::Completed()`/`Pending()` 才是状态迁移动词，`Empty` 与它们不混淆。
> 📌 **该改名是纯词法改动**：`FDynamicDependencyGraph.h:104`、`FDynamicDependencyGraph.cpp:18`、`FDynamicGeneratorCore.h:33`、`FDynamicGeneratorCore.cpp:82`、`FDynamicGenerator.cpp:39` 共 5 处，**改动面仍为 `+34/−0`**；改后重新构建并重跑了 §4.2 的全部项（见该节的"改名后复跑"行）。

> **落点取舍**：报告首推"在 `EndCodeAnalysisGenerator()` 或 `FDynamicGenerator::Generator()` 收尾处"。本轮选后者 + **放在 `FScriptDomainScope` 之后**，理由：(1) `EndCodeAnalysisGenerator()` 也被**代码分析**路径调用（`FDynamicGenerator::CodeAnalysisGenerator():91`），而那条路径**从未消费图**，在那里清会把"建立中的图"误清；(2) 全量生成是唯一"建图并消费"的路径 ⇒ 在其收尾清理等价于"图的生命周期 = 一趟全量生成"，正是 `OnCompleted` 语义所要求的范围。
> **对文件变更路径的影响**：`FDynamicGenerator::Generator(FileChanges)` 从不建图也从不消费图，它只通过 `SetClass` 间接调用 `IsCompleted`/`OnCompleted`；在该路径上 `NodeMap` 为空 ⇒ `IsCompleted` 走 `:43 return true` ⇒ 与**改前**（上一趟全量生成留下的 `NodeMap` 里通常也查不到该名字）表现一致。
> **消除的两个后果**：① `NodeArray` / `NodeMap` 不再随热重载线性增长（每趟 N 个 `FNode`：`FString` + `TArray<FDependency>` + `TFunction<void()>` + `TArray<TFunction<void()>>`）；② **闭包悬垂捕获结构性消失** —— 旧节点闭包持有的是 `FReflectionRegistry::Deinitialize()` 已 `delete` 的 `FClassReflection*`，图不再跨趟存活即不再有机会调用它。

## 6. 复用价值（给下一轮）

1. **"表 = 复用判据"这一结构性事实决定清理策略**：本仓四个生成器的复用判据全部是"名字在不在表里" ⇒ "清表"与"复用"直接冲突。**任何"清空静态容器"的修法都必须先回答"下次生成怎么复用"**，否则会把泄漏改成资产破坏。
2. **"死指针键"与"名字键"必须切开的判据**：前者指向已 `MarkAsGarbage` 的对象（可安全删）、后者指向仍存活的对象（删了就丢复用依据）。报告用同一个"只增不减"描述两者，是本轮第 0 步的主要更正点。
3. **行号零漂移是一种信号**：某目录若在上几轮提交中未被触碰，则报告行号可直接使用；反之（G12 / G2 轮）必须先做漂移表。判断方式是 `git log <上一轮提交>..HEAD -- <目录>`。
4. **`IsCompleted` 的"未知即 true"是一条隐式契约**：它让"非依赖节点的类型"走立即执行分支；改动图的清理策略时必须把这条契约算进来（否则会以为"清图 = 行为变化"）。
5. **临时探针的探针式选择**：`UE_LOG` + `grep` 取证后整段删除（本库既有做法）；⚠️ **探针若读 `private` 成员会编不过**（本轮 `FDynamicGenerator.cpp` 读 `FDynamicClassGenerator::DynamicClassMap` 触发 11 处 `C2248`）⇒ 探针要么放在能接触到成员的函数体内，要么只取可从公共接口拿到的量。
