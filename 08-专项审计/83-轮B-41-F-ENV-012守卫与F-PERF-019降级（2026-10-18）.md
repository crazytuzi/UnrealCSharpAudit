## 1. Q3 `F-ENV-012`：无效 owner 的 `AddReference`

### 1.1 改动

```cpp
bool FCSharpEnvironment::AddReference(const IManagedHandle InOwner, FReference* InReference) const
{
	if (ReferenceRegistry != nullptr && IManagedHandleIsValid(InOwner))
	{
		return ReferenceRegistry->AddReference(InOwner, InReference);
	}

	delete InReference;

	return false;
}
```

**为什么拒绝时要 `delete`**：所有调用点都是 `AddReference(owner, new FReference(...))` 形式（`TPropertyValue.inl` 等），注册表拒绝接收 ⇒ 该对象无人拥有；不删就从"`{0}` 桶累积"变成"每次调用漏一个 `FReference`"，比原缺陷更差。

**为什么守卫放在 `FCSharpEnvironment` 而不是 `FReferenceRegistry`**：`FReferenceRegistry::AddReference` 的语义是"接管所有权"，把合法性判断放在环境层（唯一入口）与同族 `GetBinding` 等的判空风格一致，且不改注册表的职责。

### 1.3 边界

- **未取得**：`{0}` 桶条目数的运行期 A/B。`GeManagedHandle` 返回无效 owner 需要"成员属性为未登记 `UScriptStruct`"的反射访问才能触发；本轮未埋探针（避免为 P3 条目引入临时日志）。**触发补证** = 出现"无效 owner 注册"的实证。

## 4. 复用价值

1. **"拒绝接收"的守卫要连带处理所有权**：`AddReference(owner, new FReference(...))` 的拒绝路径必须 `delete`，否则守卫本身制造新泄漏。
2. **"每资产一次"的判定必须枚举全部调用点**：`:497`（非每资产）与 `:557`（每资产）在同一次复核里给出相反结论；只看第一个会得出"证伪"的错误定论（B-38 已自更正一次）。
3. **P3 条目的判据可以接受"形态 ＋ 回归"**：`{0}` 桶计数需要专用探针，为一个 P3 守卫引入临时日志不划算 —— 如实登记"未取得"，比强行造判据更可信。
