## 2. 机制

```cpp
// 修复前（:1720）
const auto Output = FUTF8ToTCHAR(reinterpret_cast<const ANSICHAR*>(Bytes.GetData())).Get();

PendingBytes.RemoveAt(0, InLength);

Result.Append(Output);          // 读已释放内存
if (InOnOutput) { InOnOutput(Output); }   // 形参是 const FString&，就地构造 → 同样读已释放内存
```

- `FUTF8ToTCHAR` = `TStringConversion<FUTF8ToTCHAR_Convert>`（引擎 `StringConv.h:1014`），**不可拷贝、不可移动**；转换后的 TCHAR 缓冲就在这个临时对象里（小串在 inline 缓冲，长串在堆上）。
- `Get()` 返回指向该内部缓冲的 `const TCHAR*`，且带 `UE_LIFETIMEBOUND`（`StringConv.h:778`）—— 所以 clang 能静态查出。
- 临时对象在**整条表达式结束**销毁 ⇒ `Output` 立即悬垂；`PendingBytes.RemoveAt()` 之后的任何栈使用都可能覆盖那段缓冲，于是输出内容随机或崩溃。

## 3. 修法

```cpp
// 修复后（:1720）
const auto Output = FString(UTF8_TO_TCHAR(reinterpret_cast<const ANSICHAR*>(Bytes.GetData())));
```

- `UTF8_TO_TCHAR(ptr)` 等价于 `FUTF8ToTCHAR(ptr).Get()`，但它的临时对象活到**整条表达式结束**，而 `FString` 的拷贝正发生在该表达式内 ⇒ 之后只持有值类型 `FString`。
- 这是仓内既有写法（`FRegisterString`／`FRegisterStruct`／`FRegisterName`／`FRegisterText`／`FRegisterMulticastDelegate`／`FRegisterAnsiString`／`FRegisterUtf8String`／`FScriptLog.cpp:18,23`／`FLeanCLRDomain.cpp:723,725` 等 **19 处**）。
- **没有**采用 `FString(Conversion.Get(), Conversion.Length())`：UE 5.4+ 的 `FString(const TCHAR*, int32)` 是 **ExtraSlack** 语义、不是长度；需要「指针＋长度」时必须用 `FString::ConstructFromPtrSize`（插件 `Template/TGetUtf8String.inl` 已在用）。
- 也没有改签名：`InOnOutput` 是 `TFunction<void(const FString&)>`（`FUnrealCSharpFunctionLibrary.h` 声明；`.cpp:1658` 定义），`Result` 是 `FString&` ⇒ 把 `Output` 从 `const TCHAR*` 换成型别 `FString` 后，`Result.Append(Output)` 与 `InOnOutput(Output)` 都照常编译。

## 8. 教训（写入库级约定）

> **对「字符串转换临时对象」这类 C++ 生命周期缺陷，UBT ＋ 套件 ＋ 黑白盒一致性都不构成判据。**
> 今后凡是出现 `XXXToYYY(...)` / `StringCast<...>(...)` / `TStringConversion` 的 **`.Get()` 结果被存进变量**的写法，一律按「悬垂」处理；`Get()` 只在**同一全表达式**内作实参时才算安全。
> 判据只能来自**能静态诊断生命周期的编译器**（clang `-Wdangling`）或人工逐处走查 —— 本机 MSVC 不会给出任何信号。
