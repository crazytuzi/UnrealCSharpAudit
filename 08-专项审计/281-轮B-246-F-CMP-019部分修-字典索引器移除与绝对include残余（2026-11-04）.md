## 4. 残余：绝对 `#include` 半边（转设计）

### 4.1 现状与影响面

- 631 个 `.inl` 的 include 是**绝对路径**（Windows 反斜杠），换机器/换引擎路径即不可解析；`SaveIfChanged` 的"内容相同则跳过"也因此对路径敏感。
- **本工程内无编译期消费者**：`Source/**` ＋ `Intermediate/**` 对 `.header.inl` / `.binding.inl` 的 include 命中 **0**（唯一命中是 `SourceCodeGenerator.cs:63` 的常量定义）。⚠️ 这不等于"其他工程也没有消费者"（C# 动态类的 C++ 桥接可能由外部工程 include），故仍按"产品内容变更"对待。

### 4.2 建议修法（下一轮，需裁定）

```csharp
return classObj.HeaderFile.IncludeFilePath;
```

- **语义**：UHT 已算好的"模块相对路径再剥掉类型目录"（`5.6 UhtModule.cs:248-265`：`ModuleRelativeFilePath` 之后按 `Public/`、`Classes/` 等 `typeDirectory` 再剥一层），引擎自身生成的 `.gen.cpp` 用的就是它（形如 `#include "GameFramework/Actor.h"`）。
- **版本可用性（§7 三步的步 1）**：`IncludeFilePath` 在 **5.1.1 / 5.3.2 / 5.5.4 / 5.8.0** 四个 tag 的 `UhtHeaderFile.cs` 中**均有声明**（`public string IncludeFilePath { get; set; } = String.Empty;`）；**5.0 无 C# UHT**（旧 C++ 实现）⇒ 不适用。
- **风险**：会改变全部 631 个 `.inl`；跨模块 include（如插件类引用 Engine 模块头）能否仍被解析，**只能**在启用导出器的工程里用真编验证 ⇒ 必须先造 ini 装置（并对照 16 231 个 C# 产物是否受影响）。
- **建议**：单独立轮，按"装置 → 生成 → 真编 → 全量比对 → 裁定"推进；未取得真编前不落地。

### 4.3 同族死写（登记，不施工）

`HeaderPath`（本轮后只写不读）与 `Project`（HEAD 起只写不读）＋ `:86-104` 的 9 次目录扫描 ＋ `GetModules(string, Dictionary)` / `GetPlugins(string, Dictionary)` 两个重载 = **纯死写**。按"diff 只含语义改动"本轮未动；建议随死代码批次（`08-…/01` 族）清理，触发条件 = 下一次触碰该文件或做 UHT 启动耗时优化时。
