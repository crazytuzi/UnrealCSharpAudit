## 1. 第 0 步前提回核

### 1.1 `MethodBridge.Invoke` 的形态（`Script/Interop/Bridge/MethodBridge.cs`）

```csharp
        [UnmanagedCallersOnly]                                   // :38  ← 由原生侧直接调用
        public static nint Invoke(nint InHandle, nint InMethod, int InParamCount, nint* InParams)
        {
            try
            {
                if (HandleData.GetObject(InMethod) is MethodBase Method)
                { ... 
                    if (Result is null) { return 0; }                // :111-114  ② 合法 null 返回
                    return HandleData.Alloc(Result);                 // :128      ① 正常返回值
                }
                return 0;                                            // :131      ① void/方法无效
            }
            catch (Exception Exception)                              // :133
            {
                var InnerException = ...;
                Console.Error.WriteLine($"\nUnhandled Exception:\n{InnerException}");   // :142
                return 0;                                            // :148      ③ 异常（与 ①② 同值！）
            }
        }
```
- **唯一出口在 C++ 侧**：`FScriptDomainImpl.inl:476-483` 的 `SCRIPT_DOMAIN_TYPE::Invoke(...)` → `SCRIPT_DOMAIN_INVOKE(IManagedHandle, MethodBridgeInvokeFn, …)`；LeanCLR 另有自定义实现（`FLeanCLRDomain.cpp:150-184`），CoreCLR/Mono 走 `.inl` 默认。
- 消费点：`FMethodReflection::Runtime_Invoke`（`:75-83`）→ `FManagedFunctionDescriptor::Invoke`（`FManagedFunctionDescriptor.cpp:51-53`：哨兵比对 ＋ `IManagedHandleIsValid` 才写返回槽并 `GCHandle_Free`）／`FClassReflection.cpp:750`（返回值丢弃）。

### 1.2 判据路径（不用自造装置）

工程侧 C++ 夹具 **已经**在对 **C# 实现**的函数调 `ProcessEvent`（`Source/UnrealCSharpTest/Private/UnitTest/UnitTestSubsystem.cpp:382-405` 等），而 C# 实现就在 `Script/Game/UnrealCSharpTest/UnitTest/Reflection/CSharpFunction/TestCSharpFunctionActor.cs`。⇒ 只要让其中一个实现**抛异常**，就得到"C++ 调 C# 抛异常"的现成通道（本轮的抛异常夹具是**探针**，交付前已还原）。

### 1.3 一个必须先确认的安全事实

```cpp
// Source/UnrealCSharpCore/Public/Domain/Script/IManagedHandle.h（改前）
static constexpr IManagedHandle InvalidManagedHandle{};                 // = 0
FORCEINLINE bool IManagedHandleIsValid(const IManagedHandle h) { return h != InvalidManagedHandle; }
```
⇒ **有效性判据只排除了 0**。任何"非零哨兵"都会被下游当作**有效句柄**（`Object_Unbox` / `Set` / `GCHandle_Free`）⇒ 哨兵方案**必须同时扩展该判据**，否则是把"静默失败"换成"野句柄崩溃"。

## 2. 决策变更：A 的实测后果（据此改推 A+B）

按口径 A 施工（catch 保留日志后 `throw;`），用同一抛异常夹具跑一趟：

| 判据 | 读数 |
|---|---|
| 进程 | **死亡**：harness 报 `editor exited early (exit code -1073741571)` = `0xC0000409` 家族；事件日志 `Application Error / Faulting module coreclr.dll`、**`Exception code: 0xc00000fd`（栈溢出）** |
| CSV | **无 CSV 产出**（整轮测试结果全部丢失） |
| 日志 | `PROBE-B14 catch-ran ×834`、`LogUnrealCSharp: Error: Unhandled Exception …` **834 条**（栈完全相同） |
| 机制 | **未定位**：异常逃出 `[UnmanagedCallersOnly]` 后没有"一次干净 fail-fast"，而是**重复重入**（834 次）直到栈溢出 ⇒ 🆕 登记为 **`F-CS1-041`**（见 §6） |

**同时得到的另一个新事实**（改变了对本条的定性）：那条 `Console.Error.WriteLine` **本来就已经进 UE 日志**，且带**完整托管栈**：
```
LogUnrealCSharp: Error:
Unhandled Exception:
System.Exception: PROBE-B14
   at Script.UnrealCSharpTest.ATestCSharpFunctionActor.GetBoolValueFunction() in …\TestCSharpFunctionActor.cs
   at System.Reflection.MethodBaseInvoker.InterpretedInvoke_Method(Object obj, IntPtr* args)
   …
```
⇒ F-CS1-006 里"**静默**"的一半（"看不到异常"）**早已不成立**；真正剩下的缺口是"**C++ 侧无法把'抛异常'与'合法 null/void'区分开**"。这正是 B 要解决的，也正是 A 的代价（会话死亡 + 结果丢失）换不来的。

⇒ 维护者据此改推 **A+B**：**日志照旧保留**（不再新增任何日志类型）＋ **异常返回独立哨兵**。

| # | 文件 | 改动 | 依据 |

| 1 | `Script/Interop/Bridge/MethodBridge.cs` | 新增 `public const nint ExceptionHandle = -1;`；`catch` 尾 `return 0;` → **`return ExceptionHandle;`**（`Console.Error.WriteLine` **原样保留**） | 让"异常"从"合法 null/void"里独立出来；日志已存在，无需新增 |

### 3.1 哨兵放哪：两次自我更正后的落点（全局判据 → 消费点 → 函数内局部）

- 初版把 `IManagedHandleIsValid` 扩展为 `h != 0 && h != -1`，理由是"非零哨兵会被下游当有效句柄去 `Object_Unbox`/`GCHandle_Free`"。
- **普查后该理由只覆盖 1 处**：`Invoke` 返回值的**使用方 4 处**（`FManagedFunctionDescriptor.cpp:51`／`TMethodHelper.inl:78`／`FDomain::GetTraceback`／**`FScriptDomainImpl.inl:569`**；**清单经轮 B-16 更正**，原文误把丢弃方 `FClassReflection` 列入、漏了 Core 那处），其中**只有第一处**调用该判据；另两处**连 `0` 都不判**（异常返回 `0` 时今天就照用），全局判据根本保护不到它们。
- 而判据本身在库内 **84 处 / 38 文件**被使用 ⇒ 为一个桥接专用哨兵改动全局语义**不成比例**；维护者复核后改为**在消费点判定**，判据回到 `h != InvalidManagedHandle`。
- **代价对比**：局部判定 = 1 行（消费点条件多一项）；全局判定 = 1 行（判据）+ 38 个文件的语义被牵动。行为等价（哨兵在两种方案里都不会被当有效句柄使用）。
- **第三版（最终，维护者指定）**：哨兵进一步收进 `FManagedFunctionDescriptor::Invoke` 的**函数内局部 `constexpr`**，`IManagedHandle.h` 撤回常量并**回到基线**。理由：C++ 侧今天**只有这 1 个消费点**需要这个名字 ⇒ **零公开面**、零新增 include/依赖边，通用类型头保持"纯类型"。⚠️ **隐含前提（当时写下）**：若出现**第二处**消费点需要判定（§6.6 登记的 `TMethodHelper.inl:78-92`、`FDomain::GetTraceback`），应把常量**搬到公共头**（当时建议 `IScriptTypes.h` 紧随 `method_bridge_invoke_fn:87`），**不要复制字面量**。
- **该触发条件已在轮 B-15 兑现**（[`08-…/53`](53-轮B15收口-失败结果的返回值转换守卫（2026-10-13）.md)）：因 §6.6 的缺口**实测确认会崩溃**，维护者裁定在 `TMethodHelper::Invoke` 与 `GetTraceback` **各加一次判定** ⇒ 消费点从 1 处增至 3 处 ⇒ 常量**升格到 `IManagedHandle.h`**（与 `InvalidManagedHandle` 同居；**判据仍未改**），B-15 同时撤掉本轮的函数内局部常量（同一事实只留一处定义）。

**为什么 `-1` 安全**：C# 侧句柄由 `HandleData.Alloc` 单调分配（`HandleData.cs:41-58`，句柄号**单调递增且不复用**，库内既有结论）⇒ 取值恒为正；`ExceptionManagedHandle = -1` 与之不交。

**产物面**：`IManagedHandle.h` 与判据**都回到基线**（本轮最终版不再改任何共享头）⇒ 产物面与依赖面**零变化**（生成器本就不依赖这些头，实测 `grep` 命中 **0**）。

## 7. 复用价值（方法论）

1. **口径决策必须先测后果再交付**：A 在纸面上是"fail-fast、最响"，实测却是"**834 次重入 + 栈溢出 + 无 CSV**"。先做一次"改后读数"再定稿，避免了把一个"会话必死且丢结果"的行为推给用户。
2. **判据要放在"唯一咽喉"**：托管侧的 `MethodBridge`、`FMethodReflection`、`FManagedFunctionDescriptor` 三处探针**都没抓到**（该路径不走它们），最终在 `FScriptDomainImpl::Invoke`（所有域调用的唯一出口）才拿到读数。
3. **先量爆炸半径，再决定改在哪一层**：初版把哨兵塞进**全局判据** `IManagedHandleIsValid`（库内 **84 处 / 38 文件**），而真正消费 `Invoke` 返回值的只有 **4 处**、其中只有 **1 处**用该判据 ⇒ 收益 1 处、代价 84 处。**结论：桥接专用哨兵应落在消费点，而不是全局判据**（判据保持 `h != 0`）。教训：改全局判据/公共谓词前，先做"使用面 vs 受益面"普查。
4. **探针路径必须写绝对路径**：本轮首版原生探针写成相对路径 ⇒ 读数落在编辑器 CWD（`Engine\Binaries\Win64\Saved\Retest\`），白跑两轮（轮 B-11 已记过同一坑，本轮复发）。
5. **不要用全局替换改语义**：见 §4 的自伤记录；替换必须锚定到语句位置。
6. **"静默"要先复核**：本条被引用了很多轮的"静默失败"，实测发现**日志侧从来不静默**（完整托管栈早已进 UE 日志）⇒ 真正缺的是"返回值不可区分"。凡"静默"类结论，先看有没有既有日志通道。
