## 1. `F-CB-001`：首次运行期实测（原发现明确写"需实测"）

**装置**（临时探针，已移除；日志归档 `Saved/Retest/out/b9-probe/`）：4 个文件各自向同一落盘文件追加一行 —— `FBinding::Register`（注册时的类名/引擎状态）、`FDynamicClassGenerator`（静态金丝雀 + `IsDynamicClass` 调用记录）、两个模块的 `StartupModule`。

**读数（30 次注册、21610 次 `IsDynamicClass` 调用）**：

| 序 | 行 | 内容 |
|---|---|---|
| 1 | `DYNSET-CTOR` | UnrealCSharpCore 的静态 `DynamicClassSet` **先构造** |
| 2–31 | `REG #1..#30 name=… isRunning=0 gEngine=0 gameThread=1` | **30 次类名求值全部在引擎未运行、模块未启动时发生** |
| 32 | `UE-STARTUP` | UnrealCSharp 模块启动 |
| 33 | `CORE-STARTUP` | UnrealCSharpCore 模块启动（**晚于 UE**） |
| 34+ | `DYNCALL class=… result=0` ×21610 | 集合的**首次使用在模块启动之后** |

**结论（三条，全部是实测而非推理）**：
1. 原发现的**机制成立**：静态初始化期就求值类名（`FBinding.cpp` 的 `InClassFunction()`），此时 `GEngine` 尚未构造 ⇒ 依赖"引擎反射在 CRT 静态初始化期可用"这一**未文档化行为**（本机实测可用）。
2. 原发现担心的**跨模块顺序当前是正确的**（CORE 静态先于 UE 静态）—— 这不是"侥幸"，而是**加载器对静态导入的常规行为**（UE 模块的依赖 DLL 先完成静态初始化）；风险只在模块布局改变（单模块合并 / Unity build / 静态库统一链接）时成立。
3. 🔴 **"静默错判"在当前路径上不成立**：注册期**没有任何一次** `IsDynamicClass`/`DynamicClassSet` 访问 ⇒ 即使顺序反转，注册期也不会读到未构造的集合。⇒ 原条第 3 点风险**降级**。
⇒ **处置 = 不改代码，登记为潜伏 + 触发条件**（触发条件：模块布局或注册期路径改变致"注册期调用 `IsDynamicClass`"），并给出**低成本保险建议**（把 `DynamicClassSet` 改为函数内 static 或加"已初始化"标志；本轮**未施工**，因为它针对的是当前不成立的路径）。

## 2. `F-CB-007`：形态修复（4 文件 `+4/−4`）

```cpp
// FBinding.h / FBinding.cpp：返回类型不再暴露数组元素引用
-	FBindingClassRegister*& Register(...);        +	FBindingClassRegister* Register(...);
-	FBindingEnumRegister*&  Register(...);        +	FBindingEnumRegister*  Register(...);
// FClassBuilder.h:67 / TBindingEnumBuilder.inl:34：成员不再是引用
-	FBindingClassRegister*& ClassRegister;        +	FBindingClassRegister* ClassRegister;
-	FBindingEnumRegister*&  EnumRegister;         +	FBindingEnumRegister*  EnumRegister;
```
**为什么安全且充分**：
- **充分**：调用方对这两处**只做 `->` 解引用、从不回写**（`FClassBuilder.cpp:75`、`FClassBuilder.inl:42/59`、`TBindingEnumBuilder.inl`）⇒ 引用性**没有任何语义作用**（全库 `Register*&` 残留 = **0**）。
- **安全**：指针按值保存后，数组扩容只是**移动指针元素**，`FBindingClassRegister` 对象本身仍在堆上 ⇒ 悬垂引用这一类**从构造上消失**（引擎侧 `TArray::Add_GetRef` 返回带 `UE_LIFETIMEBOUND` 的缓冲区元素引用，本层不再把它暴露/存留）。

## 3. A/B 尝试（如实：**未能复现**）

### 3.1 装置
env 门控两处：① `FUNREALCSHARP_B9_SKIP_BASE=1` ⇒ 跳过基类 `FInputBindingHandle` 的注册（构造出原发现描述的"**派生类先注册、基类后注册**"）；② `FUNREALCSHARP_FORCE_REALLOC=1` ⇒ 在 `ClassRegisters.Add_GetRef` 之前 `Shrink()` + `Reserve(Num()+1)`（保证缓冲区**移动**）。

### 3.2 读数
探针时序（`Saved/Retest/out/b9-probe/probe-b9-ab-pre.log` 第 15–20 行）：
```
15: SKIP-BASE
16: REG #4 name=FEnhancedInputActionEventBinding isRunning=0 gEngine=0 gameThread=1
17: FORCED-REALLOC
18: REG #5 name=FInputBindingHandle isRunning=0 gEngine=0 gameThread=1
19: FORCED-REALLOC
```
⇒ **触发条件确实被构造出来了**（派生先、基类后、且嵌套注册前缓冲区被强制移动），但该次运行 **exit 0、CSV 完整、套件全绿** —— **没有崩溃、没有可见破坏**。

### 3.3 🔴 风险模型精确化（本轮对原发现的重要更正）
原发现的表述是"后续 `.Function()` 通过失效引用写入**已释放内存** ⇒ 堆破坏"。实测与代码核对后应改为：

- 该引用指向的是 **`TArray` 缓冲区里的"指针元素"**，不是 `FBindingClassRegister` 对象本身；扩容后**新缓冲区复制了同样的指针值**，而**旧缓冲区的内存内容在被复用/覆写之前仍然保存着同一个指针值**。
- 因此"通过失效引用解引用"这一步**读到的往往仍是正确指针**（⇒ 写入落到正确对象上），只有在**旧缓冲区被别的分配复用并覆写**之后才会读到垃圾 ⇒ 危害需要**两层运气同时失效**（顺序敏感 + 分配器复用了那块内存）。
- ⇒ 这就是它"至今从未触发"的**真正原因**（不是单纯"同 TU 声明顺序救命"），也意味着**修复价值在于消除形态**（本次已做），而**不宣称消除了某个已发生的破坏**。

### 3.4 防护栏（保留在仓库中的判据形态）
- **形态不变式**：全库 `Register*&` = **0**（可用 `Select-String -Pattern 'Register\*&'` 复跑）；
- **回归**：套件与 b8 交付**逐行 0 差异**（1922 / 0）。

## 7. 复用价值

1. **"需实测"的条目要用探针把时序钉死**：`F-CB-001` 争了两轮（"是否真会炸"），本轮用 4 行落盘探针 + 金丝雀一次拿到"静态顺序 / 引擎状态 / 启动顺序 / 集合首次使用点"四个事实 ⇒ 结论从"中置信度推理"变成"实测"。
2. **金丝雀（同 TU 声明顺序 + 落盘）是跨模块静态顺序的廉价判据**：不需要任何框架，一行构造器即可回答"谁先初始化"。
3. **A/B 失败也是产出**：本轮强制重分配**未能**复现故障，反而把风险模型从"写入已释放内存 ⇒ 堆破坏"精确化为"读**指针元素**的陈旧副本 ⇒ 需要两层运气同时失效"——**没有这次失败，报告里就会留一个夸大的结论**。
4. **"配置改了没生效"要先确认机制的层级**：后端选择是**编译期**的（`Build.cs` → 宏），ini 只是它的输入 ⇒ 只改 ini 不重编，观测当然不变；`monitor-editor-modules.ps1` 才是判后端的正确装置。
5. **"未跑的后端"是可关闭的欠债**：本轮把连续 4 轮登记的同一条残留（Mono 未跑）用"改 ini→重编→跑→恢复→重编→对照"一次关掉 ⇒ **跨后端一致性（1922/0 且逐行 0 差异）比"只在 CoreCLR 上绿"强得多**，而成本只有两次增量重编。
