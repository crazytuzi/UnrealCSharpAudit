## 1. ② `F-ENV-001` A1：owner 销毁 ⇒ 清表（判据已取得）

### 1.1 为什么 B-62 的三次装置都不生效

B-62 用「瞬态包组件 / actor-owned 组件 ＋ `K2_DestroyActor` ＋ `UKismetSystemLibrary::CollectGarbage()`」三种组合，`EnhancedBindingComponentCollected` 始终 `false`。本轮定位到两个叠加原因：

| # | 原因 | 证据 |
|---|---|---|
| 1 | **组件没有被标记为 garbage**：`K2_DestroyActor` 只处理 actor 的**已注册**组件；用 `Unreal.NewObject<UEnhancedInputComponent>(OwnerActor)` 创建的组件不是注册组件（也没 `RegisterComponent`），actor 销毁不会带上它 | B-62 §1.2 装置 ② 的 `EnhancedBindingComponentCollected=false` |
| 2 | **`CollectGarbage` 不保证当帧全量 purge**：未标记的对象不在本轮回收集合里；即使标记了，全量 purge 也需显式 `bPerformFullPurge=true` | 本轮改用 `MarkAsGarbage()` ＋ `CollectGarbage(KEEPFLAGS, true)` 后同一条断言翻真 |

### 1.2 新装置（跨帧问题的绕过）

套件的 `Test()` 是**单帧同步**调用（`UTestCoreSubsystem::Test()` → `ProcessTest()` → 各子系统 `Test()` → `EndTest()` 写 CSV），无法在测试内等一帧。因此改用**同步语义等价**的引擎操作：

```cpp
// B63ConsoleCommands.cpp（工程侧）
for (TObjectIterator<UEnhancedInputComponent> It; It; ++It) { (*It)->MarkAsGarbage(); }
CollectGarbage(GARBAGE_COLLECTION_KEEPFLAGS, true);   // 全量 purge：NotifyUObjectDeleted 在同一次调用内触发
```

C# 侧：

```csharp
UKismetSystemLibrary.ExecuteConsoleCommand(GetWorld(), "B63DestroyEnhancedInputComponents");
TestCoreSubsystem.TestEqual("EnhancedBindingHandleReleasedOnComponentDestroyed",
    HasManagedHandle(BindingHandle), false);
```

- 该命令把**进程内全部** `UEnhancedInputComponent` 标记 garbage 并全量 GC —— 只在本测试（套件最后）调用，不影响其它断言；实测 `components=9`。
- 语义等价性：`MarkAsGarbage + CollectGarbage(KEEPFLAGS, true)` 走的就是引擎的销毁路径（`ConditionalFinishDestroy` → `FUObjectDeleteListener::NotifyUObjectDeleted` → `FCSharpEnvironment::NotifyUObjectDeleted`），与"对象自然死亡"的**监听链路完全相同**，差别只在触发方式（显式标记 vs 引用计数归零）。

### 1.3 A/B（同树切换，其余代码不变）

| 变体 | 插件侧 `AddBindingReference` | `EnhancedBindingHandleReleasedOnComponentDestroyed` | 套件 |
|---|---|---|---|
| **A1 关闭**（B-62 之前形态） | `AddBindingReference<…, false>(FoundClass, Object, &binding)`（非 owner，不挂 `FBindingReference`） | **false** ❌ | **1 红**（`B63off`，1 969 行 / 失败 1） |
| **A1 打开**（B-62 交付形态） | `AddBindingReference<…>(InManagedHandle, FoundClass, Object, &binding)`（owner 重载） | **true** ✅ | **0 红**（`B63on` / `B63finalA` / `B63finalB`） |

⇒ 与 B-62 的 `EnhancedBindingHandleReleasedOnRemoveAction`（A2，false→true）合起来，**A1 与 A2 两条清理链各自都有干净 A/B**。

## 2. ③ `F-CS1-005`：反射通道量化（完成 ⇒ 降级出列）

### 2.1 探针设计

- **位置**：`FMethodReflection::Runtime_Invoke`（`FMethodReflection.cpp:75-83`）。它是 `IScriptDomain::Invoke` 的**唯一**调用点；`FManagedFunctionDescriptor::Invoke`（`:70`）也汇到这里 ⇒ 覆盖 `MethodBridge.Invoke` 的全部入口。
- **读数**：总次数、`Cycles64` 累计、`< 10 µs` 桶的次数与均值、单次最大值。
- **为什么不装 profiler**：本机无 `dotnet-trace`/`dotnet-counters`（安装需外网）；`Invoke` 是 `[UnmanagedCallersOnly]`，托管侧不能直调 ⇒ 原生探针是唯一可行路径。
- **第一次尝试的副产品**：以 10 000 次为阈值打点，**整场套件一条都没打出来** ⇒ 先证明"次数 < 10 000"，再改用"退出前由工程侧控制台命令读取累计值"（见 §2.2）。

### 2.2 读数（两次会话一致）

```
B63PROBE components=9 rti_invokes=605 total_ms=316.67 fast=5 fast_avg_ns=2780.0 max_ms=243.37
```

| 指标 | 值 | 说明 |
|---|---|---|
| 调用次数 | **605 / 会话** | 两次独立会话均为 605 |
| 典型单次成本 | **2.78 µs**（`<10 µs` 桶 5 次） | 反射路径本身的量级 |
| 总耗时 | 316.67 ms | **不是** marshalling 成本：其中 **一次 243.37 ms** 的长尾吃掉了绝大部分 |
| 单次最大 | 243.37 ms | 长尾（疑似 JIT/初始化/等待类调用），与 `GetParameters`/`Activator` 无关 |

### 2.3 判读

- **频次极低**：整场 1 962 断言的套件（含 `TestReflectionFunction` / 动态函数 / Blueprint 路径）只穿过 605 次反射调用。
- **收益上界**：即使把 F-CS1-005 点名的开销（`GetParameters()` ＋ `new object[]` ＋ `Activator` ＋ `Method.Invoke`）**全部消除**，上限 ≈ `605 × 2.78 µs` ≈ **1.7 ms/会话**。
- **量级对照**（本库既有降级先例）：`F-GEN-016` 0.223 s（已降级）、`F-RM-013` 9.0–23.1 ms（已降级为 P3）、`F-MACRO-003` 0.26–0.42 ms（已降级）⇒ 本条比"已判非热点"的 `F-MACRO-003` 仍高一个量级，但比 `F-GEN-016` 低两个量级；**放在同一把尺子上 < 2 ms/会话**。

### 2.4 结论

⚫ **降级出列（P2 → P3、不施工）**，登记触发条件：

1. 真实游戏会话的 profiler 显示 `RuntimeMethodInfo.Invoke`（或 `MethodBridge.Invoke`）占 CPU ≥ **1%**；
2. 单帧反射调用 > **1 000 次**；
3. 出现"反射通道成为某功能卡顿主因"的实测。

> **边界**：本轮频次读数来自 `-game` 套件会话（非真实游戏会话），但 605 次是**整场全部测试**的总和（含大量反射/Blueprint 用例），足以说明"它不是每条调用都走的通道"。
