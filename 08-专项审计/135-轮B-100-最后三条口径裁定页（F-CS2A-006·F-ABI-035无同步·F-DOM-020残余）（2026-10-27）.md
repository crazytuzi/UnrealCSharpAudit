### 2.1 `F-CS2A-006`（P1）—— 16 类没有"释放状态"查询；三条路都要开口

**HEAD 事实**

| 事实 | 证据 |
|---|---|
| 16 个包装类全部 `IDisposable`，全部有 `private bool bIsDisposed` 与幂等 `Dispose()` | `TArray.cs:15,21,23,25-35`、`TMap.cs:10,18,22`、`TSet.cs:10,18,22`、`FName.cs:7,15,19`、`FString.cs:7,15,19`、`FText.cs:7,15,19`、`FAnsiString.cs:8,16,20`、`FUtf8String.cs:8,16,20`、`TOptional.cs:8,17,21`、`TFieldPath.cs:8,18,22`、`TScriptInterface.cs:7,15,19`、`TSubclassOf.cs:7,15,19`、`TWeakObjectPtr.cs:7,15,19`、`TLazyObjectPtr.cs:7,15,19`、`TSoftObjectPtr.cs:7,15,19`、`TSoftClassPtr.cs:7,15,19` |
| **没有任何公开读取面**：`grep '\bIsDisposed\b'` 于 `Script/**` ⇒ **0**（64 处命中全部是 `private bool bIsDisposed` 及其读写） | 16 个包装类文件各 1 处 `bIsDisposed`（`TArray.cs:23` 等） |
| 托管侧**能**判活，但入口是 `[UnmanagedCallersOnly]`（C# 不能直调） | `HandleData.cs:24-36` `public static int IsAlive(nint)` |
| `GetHandle` **不能**当"已释放"信号 | `HandleData.cs:60-92` `FreeImplementation` 只删 `Handles` 条目，**不删** `ObjectToHandleReference` ⇒ `GetHandle(this)`（`:94-107`）在 `Dispose` 后**仍返回原句柄** |

**撞哪条**：**E2 的"必须有真实调用方"** —— 这条 API 的消费者天然是**外部用户**，仓内不可能有消费者；这正是 2026-09-28 施工后被撤回的原因（[`08-…/18`](18-G14b收口-三条裁定施工（IDisposable同步卸载·IsDisposed·explicit迁移）（2026-09-28）.md) §0.1）。

**三个选项**

| 选项 | 内容 | 代价 | 判据 |
|---|---|---|---|
| **A（推荐）** | **维持不做**：`Dispose()` 可用，但"释放后调用"仍静默降级；登记触发条件 | 0 | 无（现状即判据） |
| B | **批准公开面**：16 类各加 `public bool IsDisposed => bIsDisposed;` | ≈32 行、16 个公开成员；与"无消费者不做"冲突，需**明确批准** | 对 `TArray<int>`：`Dispose()` 前 `false`／后 `true`；套件与基线同 SHA |
| C | **只给 4 个高频容器类**（`TArray`/`TMap`/`TSet`/`FString`）加，其余不动 | ≈8 行、4 个公开成员；对外契约**不一致**（另 12 类仍查不到） | 同 B（限 4 类） |

**推荐 A 的理由**：① 该状态**已经**由 `Dispose()` 的幂等性保证（重复 `Dispose` 无害）；② "释放后继续调用"的危害在 CoreCLR 下是**静默降级**而非崩溃（`FRegisterArray.cpp:98-107` 一律 `return 0`）；③ 一旦开口，"每类加一个只读属性"会成为先例，把"无消费者不做"的护栏推开；④ 若用户侧真的需要，**A 的触发条件**会把它重新激活（见 §3）。

### 2.2 `F-ABI-035` 无同步半边（P2 · T2 #30）—— 参数池无锁；加锁与既有先例冲突

**HEAD 事实**

| 事实 | 证据 |
|---|---|
| 池分配器持有 `int32 Count` ＋ `TArray<void*> Buffers`，**无锁、无 CS、无线程断言** | `FFunctionParamBufferAllocator.h:21-39`（`:34` `int32 Count`，B-19 已由 `uint8` 改来） |
| `Malloc()` 读 `Buffers.IsValidIndex(Count)` → `Buffers[Count++]`，否则 `Count++` ＋ `FMemory::Malloc` ＋ `Buffers.Add` | `FFunctionParamBufferAllocator.cpp:39-55` |
| `Free()` 只在"栈顶匹配"时 `--Count`（B-19 已修配对半边） | 同上 `:57-63` |
| 分配器由**描述符实例共享**：每个 `FUnrealFunctionDescriptor` / `FCSharpFunctionDescriptor` / `FCSharpDelegateDescriptor` 各持一个 `TSharedRef` | `FUnrealFunctionDescriptor.cpp:5`、`FCSharpFunctionDescriptor.cpp:10/14`、`FCSharpDelegateDescriptor.cpp:6` |
| 同族"加锁"先例**均裁定不做** | `F-PERF-024`、`F-CONC-008`（§1 表） |

**撞哪条**：**线程模型** —— 加锁会落在"**每次 UFunction 调用**"的热路径上；不加锁则依赖"同一描述符不会被并发调用"这一**未证明的约定**。

**三个选项**

| 选项 | 内容 | 代价 | 判据 |
|---|---|---|---|
| **A（推荐）** | **维持不加锁**，登记触发条件 | 0 | 无 |
| B | 加 `mutable FCriticalSection`（头）＋ 2 处 `FScopeLock`（`Malloc`/`Free`） | 4–6 行；每次调用 1 次锁；新增成员（非公开面） | 并发探针：N 线程 × M 次 `Malloc/Free` ⇒ 改前 `Buffers.Num()` 越界/漏配、改后 0 异常；套件同 SHA |
| C | 线程局部池（`TThreadSingleton`／每线程独立 `Buffers`） | 架构改动；内存 = 线程数 × 池大小 | 同 B ＋ 内存读数 |

**推荐 A 的理由**：① **无跨线程实证**（B-19 普查只到"未找到并发调用路径"）；② 与 `F-PERF-024`／`F-CONC-008` 的裁定**直接冲突**（那两条的锁面更大且同样未修）；③ 即便加锁，`Free` 的"栈顶匹配"语义在多线程下仍会退化为"不回收"（不同线程交错入栈）⇒ 锁只能消除 UB，不能消除复用失效。**触发条件**：出现"跨线程调用同一 C# 暴露函数"的实证（如 `AsyncTask`/`ParallelFor` 里调用），或 `F-PERF-024` 的口径被推翻。

### 2.3 `F-DOM-020` 残余（P2 · T2 #24）—— 哨兵只落在 3 个消费点；5 处丢弃方无返回通道

**HEAD 事实**

| 事实 | 证据 |
|---|---|
| 哨兵定义：`static constexpr IManagedHandle ExceptionManagedHandle{-1};`；判据 `IManagedHandleIsValid` **只排除 0** | `IManagedHandle.h:25/27/29-32` |
| 生产者：C# 桥 `catch` 尾返回 `ExceptionHandle`（`-1`） | `MethodBridge.cs:10`（`ExceptionHandle = -1`）＋ `catch` 尾（口径页记 `:144`） |
| **已判 3 处** | `TMethodHelper.inl:90`、`FManagedFunctionDescriptor.cpp:71`、`FDomain.cpp:125`（`GetTraceback`） |
| **丢弃方 3 处（void 语义）** | `FClassReflection.cpp:736`（`InitObject` 的构造调用）、`:750`（`ConstructorObject`）、`:758`（`ConstructorClass`）——`Runtime_Invoke(...)` 返回值全丢 |
| **丢弃方 2 处（void 语义）** | `FDomain.cpp:147`（`InitializeSynchronizationContext`）、`:160`（`DeinitializeSynchronizationContext`） |
| **异常 → 空数组** | `FScriptDomainImpl.inl:549`（`GetClassesWithAttribute` 实现）；消费点 `FDynamicGeneratorCore.cpp:329` |

**撞哪条**：**失败信号口径** —— 三处构造路径与两处 SynchronizationContext 调用**都是 `void`**，没有返回值可承载哨兵；要让它们"可判"必须改 C# 侧返回类型（**ABI/公开面**）。`GetClassesWithAttribute` 返回 `TArray<FClassReflection*>`，"失败"与"无匹配"目前都是空数组，要区分必须加出参或 `bool`（**接口签名变更**）。

**三个选项**

| 选项 | 内容 | 代价 | 判据 |
|---|---|---|---|
| **A（推荐）** | **维持**：5 处丢弃方保持现状；`GetClassesWithAttribute` 的"异常→空数组"登记触发条件；本条按 **"部分已修（桥接侧）＋ 残余决定不做"** 结案 | 0 | 无 |
| B | 只给 `GetClassesWithAttribute` 加"失败可区分"（`bool` 返回值 ＋ 出参，或 `TOut::OutLength` 哨兵） | 接口签名变更（Core 层共享实现 ＋ 4 个后端 override ＋ C# 侧）；≈20–30 行 | 注入 throw ⇒ 改前"空数组、上层当无匹配"、改后"失败可判且产物不落空" |
| C | 全面补状态通道：C# 侧 `Runtime_Invoke` 返回 `uint8`，5 处丢弃方逐处判定 | ABI 变更（`MethodBridge` 签名 ＋ 所有 `Runtime_Invoke` 调用点） | 同 B，覆盖 5 个点 |

**推荐 A 的理由**：① 三处构造路径即便"判到了"，**也没有可做的处置**（对象已分配、构造失败只能丢弃，而丢弃面属 `F-CS2A-006`）；② `GetClassesWithAttribute` 的失败在**当前生成路径上不可达**（字段/类型名都来自同一份 C# 反射）；③ C 会让"每次跨语言调用"多一次返回值检查，而现行哨兵已覆盖**唯一有返回值可判**的路径（`Invoke`）。**触发条件**：出现"异常被上层当空列表 ⇒ **静默漏产物**"的实证（登记路径 `FDynamicGeneratorCore.cpp:329`），或 `Runtime_Invoke` 因其它原因需要改签名。
