## 4. 🔴 轮 B-6 更正：轮 B-5 §3「根因未定位」整节作废

**轮 B-5 的错误结论**：`从未赋值` 的多引用属性读回"非 null 包装、值也非 null"，判断为"该场景下 getter 读到的地址/内容非空，根因未定位"。
**真实原因（一行代码级）**：`ATestBindingPropertyActor` 的构造函数把**全部**多引用属性初始化为非空：

```cpp
// Source/UnrealCSharpTest/Private/UnitTest/Binding/TestBindingPropertyActor.cpp:52-84
ATestBindingPropertyActor::ATestBindingPropertyActor():
	… ObjectValue(this), ClassValue(GetClass()), InterfaceValue(this),
	SubclassOfValue(GetClass()),          // ← 默认 = 自己的类
	WeakObjectPtrValue(this),             // ← 默认 = this
	LazyObjectPtrValue(this),
	SoftObjectPtrValue(this),
	SoftClassPtrValue(GetClass()), …
```
⇒ 我的"从未赋值"判据**从未构造出空值**：读到的当然是**正确的非空值** ✓ 于是
- probe 的 `MULTI-Member empty=0` 是**正确读数**（值确实非空）；
- `?.Get() == null` 为 false 是**正确读数**；
- 6 处描述符守卫"无实测效果"也是**必然**（空值才该触发，而值不空）。
⇒ **不存在"未定位的根因"**；轮 B-5 那 5 条判据（`MultiPropertyUnset…`）**前提不成立、读数作废**，已从交付判据中移除，替换为 §5 的"显式清空"判据（读到时与"从未赋值"是**同一个空值状态**）。
**教训（已入 §7）**：**判据要先用一行代码确认载体的初值**，再谈"应为 null"。

## 6. `F-PROP2-003 (05)` 的可达性更正（本轮第二条产出）

| 事实 | 依据 |
|---|---|
| 类型层面 | `UClass` 与 `TSubclassOf<UObject>` 是不同 C# 包装类型、无隐式互转；`as` 失败只得到 `null` |

## 9. 复用价值

1. **判据的载体初值要用一行代码确认**：本轮最大的时间损失来自"从未赋值"这个想当然的前提 —— 类构造函数里 `SubclassOfValue(GetClass())` 一行就让 5 条判据全部失去意义。
2. **对照实验先于结论**：A/B 两条判据（写 null 后值是否仍旧 / 未赋值是否为空）分别推翻了"陈旧读"与"未定位根因"两个错误结论。
3. **无实测效果的改动不落**：6 处描述符守卫"看起来很对"但读数毫无变化 ⇒ 整块撤回；在载体前提被纠正后回看，这个决定**恰好避免了把无效守卫留进交付**。
4. **同一语义要有两种判空写法**：`== null` 与 `?.Get() == null` 分别测"引用判空"与"值判空"，本轮正是靠两者分开才定位到"包装非 null 但值也为空"与"值本身非空"的差别。
5. **崩溃类现象要登记"计数 + 对照 + 配方"**：4 例全在"重建后首跑"（19 中 4）、非首跑 13 次无 —— 这个配方让轮 B-7 一次循环就复现并拿到转储。**但更要先查库里有没有同签名的既有登记**：本轮 `F-BLD-025` 的返工，就是因为没有先检索 `Fault offset 0x9603a` 这个签名（库里早有专属报告）。
