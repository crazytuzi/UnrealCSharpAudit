## 1. 发现经过（正控怎么把它炸出来的）

### 1.1 为什么必须造正控

`CompileInteropBuild` 的守卫是 `bForceCompileInterop || !FileExists(发布的 Interop.dll)`，而 **`bForceCompileInterop` 没有任何控制台入口**（只有插件工具栏那条 `-forcecompileinterop` 传参路径；`FCSharpCompiler::ImmediatelyCompile` 的默认值是 `false`）⇒ 在普通会话里该分支**只在编辑器启动时跑一次**，落在 `-ExecCmds` **之前** ⇒ 观察不到。

⇒ 本轮**临时**把守卫改成 `if (true)`（只改这一处、只用于正控），于是 `UnrealCSharp.Editor.Generator` 每跑一次就会真的走一遍 Interop 构建。

### 1.2 上一轮"正控失败"的解释（更正我自己的判断）

上一轮（`FBLD023-interopctl`）我把 `Content\Script\Interop.dll` 移走 + 加独占锁，结果是：Interop.dll **mtime 停在上上趟**、日志里**没有 dotnet 输出块**。我当时的结论是"分支没被走到 / 失败没被记录"。

**本轮更正**：那次失败**确实发生了**，只是**发生在编辑器启动期的 `SyncCompile` 里**、落在观测窗口之前，而且那趟的 `Select-String` 检查用错了频道名（`LogUnrealCSharp` 把整段 dotnet 输出当作**一条** `LogUnrealCSharp: Error:` 行的延续）⇒ **"没有输出块"是我的检查方式造成的错觉，不是插件把失败吞了**。这一点已在 `08-…/34` §10.4 更正。

## 2. 机制（逐字落日志）

### 2.1 谁锁的

```
:1108  error MSB3027: Could not copy "obj\Debug\Interop.dll" to
       "..\..\Content\Script\Interop.dll". Exceeded retry count of 10. Failed.
       The file is locked by: "UnrealEditor (48444)"
       [D:\file\UnrealProjects\UnrealCSharpTest\Script\Interop\Interop.csproj]
:1109  error MSB3021: Unable to copy file "obj\Debug\Interop.dll" to
       "..\..\Content\Script\Interop.dll". The process cannot access the file
       'D:\file\UnrealProjects\UnrealCSharpTest\Content\Script\Interop.dll'
       because it is being used by another process.
```

`UnrealEditor (48444)` = **发起这次构建的那个编辑器进程自己**。机制：`Interop.csproj` 的 `<OutputPath>..\..\Content\Script</OutputPath>` 让它**直接写进编辑器加载托管程序集的目录**；编辑器启动时把 `Content\Script\Interop.dll` 加载进 CoreCLR 后**一直持有该文件**（Windows 上托管程序集按文件映射加载、不会主动关闭句柄）。

⇒ **这不是"偶发文件锁"，而是结构性冲突**：只要编辑器活着，Interop 的**发布**就必然失败。这也解释了为什么 MSBuild 要"重试 10 次"（`Microsoft.Common.CurrentVersion.targets(4919,5)` 的 `Copy` 任务带重试）而不是立刻报错。

### 2.2 级联（缺陷本体）

```cpp

{
	CompileNotification->Progress.SetStage(FCSharpCompileProgress::StageFailed);

```

调用方（改前核对）：

| 调用方 | `bCompileInterop` | 后果 |
|---|---|---|
| `ImmediatelyDoWork(bForceCompileInterop)` → `Compile(…, true, …)`（`:174-179`） | **恒 `true`** | 工具栏 Rebuild / 内容浏览器动态源的全量重建**每次都被中止** |

| `FEditorListener.cpp:567/666/672` → `AsyncCompile()` | `true`（`AsyncCompile` 走同一 `true`） | 保存触发的重编译同样被中止 |

**修前那趟的硬判据**：`Interop.csproj` 命中 **96** 次、**`Game.csproj` 命中 0 次**、**`Game.dll` mtime 整趟不动**（停在上一趟的 `00:33:45.078`）⇒ 该趟"重建"**什么都没产出**。

## 3. 施工与判据

### 3.1 改动①：去掉致命级联中止（`CompileInternal`，1 处）

```cpp
// 修后 CompileInternal
if (bCompileInterop)
{
	CompileInterop(bForceCompileInterop);
}
```

- **只删致命 `return`**，不碰 `CompileInteropBuild` / `BuildInterop` / `ShutdownBuildServer`；
- 失败仍**可见**（`BuildInterop` 在返回码非零时 `UE_LOG(LogUnrealCSharp, Error, TEXT("%s"), *InResult)`）；
- `Compile()` 与 `OnCompile` 广播恢复正常 ⇒ 进度不再停在 `StageFailed`；
- ⚠️ 副作用（如实记录）：`InteropPath` 这个局部量随之不再被引用（**已随之删除**，`Select-String` 核查 `InteropPath` 命中 **0**）。

### 3.1b 改动②：把 interop 侧收成单函数（撤掉为"重试"而做的拆分）

> **缘起**：维护者反问 —— **"既然现有代码解决不了（编辑器必然持锁），那还有必要把编译 Interop 流程拆分那么多函数吗"**。核对后确认：**不必**，且拆分**净有害**。

**拆分的唯一受益者是"重试"**。改动前的结构是 `CompileInterop`（门）→ **`CompileInteropBuild`**（守卫 + 首次 + **重试**）→ **`BuildInterop`**（单次构建），后两者的存在意义只有一个：**让"构建"能被调用两次**。而那次重试：

| 事实 | 证据 |
|---|---|
| 重试的前提**恒不成立** | 锁由**当前编辑器进程**持有（`The file is locked by: "UnrealEditor (…)"`），只有重启才释放；`ShutdownBuildServer()` 只清**我们自己派生**的常驻 server |
| 重试**一次都没救回** | 三个装置共 **10 次尝试全部失败**（`FBLD023-selfheal` 4 次 / `-fixed` 4 次 / `FBLD024-collapse-ctl2` 2 次），无一例外 |
| 重试的代价是**固定的** | 单次尝试 = **12.88–13.26 s**（MSBuild 的 `Copy` 重试 10 次）⇒ 重试把"一次注定失败"变成"两次注定失败"，**≈26 s 纯等待换 0 收益** |
| `--disable-build-servers` 在此**是死参数** | 它防"我们自己的 server 占用"，管不了**别的进程**持锁；且该分支要求"已发布的 Interop.dll 不存在"（`ImmediatelyCompile` 的 `bForceCompileInterop` 默认 `false`、只有工具栏 Rebuild 会传 true）⇒ 实际几乎不可达 |

**保留 vs 撤回的取舍**：拆分唯一的"收益"是**结构上与 `CompileGame` 对齐**；代价是 **75 行 + 一个没人看得懂为什么要有的 `_Build` 后缀 + 26 s 白等**。⇒ **撤回拆分**，回到 HEAD 的形状（单函数 `CompileInterop`）**只保留** ` --disable-build-servers`（与 `CompileGame` 同口径的意图、零成本）。

⚠️ **关键区分**：`F-BLD-023` 在 **`CompileGame`** 上的预防层 + 自愈**原样保留** —— 那条链上的锁是**我们自己**（build server）造的，自愈**已实测有效**（探针：`entering retry: shutdown build server` → 重试 30.1 s）；本条讨论的只是 **interop 侧**，那里的锁是**别的进程**持的，自愈从原理上就赢不了。

**改动后的形状**（单函数，`.h` 只留 1 条声明）：

## 4. 残余（如实声明，**本条只修了级联，没修锁**）

1. 🔴 **"编辑器持锁 `Content\Script\Interop.dll`"本身未解决** ⇒ 若 **Interop 源码真的变了**，运行期重建**仍然不会让新 Interop 生效**（编辑器继续用启动时加载的那份）。本轮的修复只保证**不再连累 Game 编译**。方向（留给下一轮，未验证）：构建前把发布产物写到**临时文件**、再用 `MoveFileEx(…, MOVEFILE_REPLACE_EXISTING)` **改名覆盖**（对已打开目标的改名在 Windows 上可行）；或让 Interop 以 `Assembly.Load(byte[])` 方式加载而**不长期持有句柄**。
2. ⚠️ **会白等 ≈13 s，但只在两种情形**（**本节已按 §6.2 更正**：稳态下守卫短路、不会进该分支）：**① 启动期首次**、**② 强制重建（工具栏）** —— 单次 MSBuild 的 `Copy` 重试 10 次（本机实测 **12.88–13.26 s**，收敛前因重试翻倍为 ≈26 s）。可考虑"失败一次后记住本次会话、不再重试"（即 §4 第 3 条的方向 D），但**需先裁定**（会牺牲"用户手动释放后能成功"的可能）。
3. ⚠️ **本轮的正控用了临时代码改动**（守卫 `if (true)`，两次装置各一次）⇒ 该分支在**正式代码里仍不可达**；建议给 `bForceCompileInterop` 一个**正式入口**（控制台命令或设置项），否则这条路径永远只能靠改代码来验证。**另（方向 D，未采纳、待裁定）**：既然"运行期发布必然失败"，可在失败后**记住并顺延到下次启动** —— 启动期那次 `SyncCompile` 在 CLR 加载之前跑，是**唯一能成功**的窗口（本轮实测过一次成功重建）。收益 = 运行期不再付那 13 s；代价 = "运行期改了 Interop 源码 ⇒ 本次会话内新导出的绑定用不上"。
4. **只测 CoreCLR / Win64 / 编辑器 Development**；未复测 Mono（`AndroidScriptDomainType`/`IOSScriptDomainType` 为 Mono）与 LeanCLR、未测打包。
5. **未测"Interop 源码变更 + 重建"的端到端**（需要真的改一份 Interop 源；本轮只测了"发布失败不再连累 Game"）。
