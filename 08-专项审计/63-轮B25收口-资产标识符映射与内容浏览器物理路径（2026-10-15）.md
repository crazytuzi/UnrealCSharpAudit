### 2.1 `F-GEN3-010` ①：只替换 `/Game` **根段**

```cpp
// Source/UnrealCSharpCore/Private/Common/FUnrealCSharpFunctionLibrary.cpp（终形态）
FString FUnrealCSharpFunctionLibrary::GetFileName(const FAssetData& InAssetData, const FString& InAssetName)
{
	const auto GameRoot = FString(TEXT("/Game"));

	auto ModuleName = InAssetData.PackagePath.ToString();

	if (ModuleName == GameRoot || ModuleName.StartsWith(GameRoot + TEXT("/"), ESearchCase::CaseSensitive))
	{
		ModuleName = FString::Printf(TEXT(
			"/%s%s"
		),
		                            FApp::GetProjectName(),
		                            *ModuleName.RightChop(GameRoot.Len()));
	}

	auto DirectoryName = FPaths::Combine(GetGenerationPath(ModuleName), ModuleName);

	return FPaths::Combine(DirectoryName, GetAssetName(InAssetData, InAssetName) + CSHARP_SUFFIX);
}
```
- `"/Game"` 自身与被替换后的等价性：`RightChop(5)` 得空串 ⇒ `/UnrealCSharpTest`（与原行为一致）；
- **顺带消除**的另一半：非 `/Game` 的树（引擎内容 `/Engine/GameplayDebugger`、插件挂载点等）原本也会被全量替换污染（判据 C）；
- `ESearchCase::CaseSensitive` 是**收紧**（原 `Replace` 默认忽略大小写，会把 `/game/...` 也改掉；引擎包根只有 `/Game` 一种拼写）。

### 2.3 `F-ED1-023`：`GetItemPhysicalPath`

// Source/UnrealCSharpEditor/Private/ContentBrowser/DynamicDataSource.cpp（新增，紧接 DeleteItem 之后）
bool UDynamicDataSource::GetItemPhysicalPath(const FContentBrowserItemData& InItem, FString& OutDiskPath)
{
	auto bIsPhysicalPath = false;

	if (const auto InternalPath = InItem.GetInternalPath().ToString(); !InternalPath.IsEmpty())
	{
		const auto DiskPath = InItem.IsFolder()
			                      ? FDynamicHierarchy::ConvertInternalPathToFileSystemPath(InternalPath)
			                      : InternalPath;

		if (IFileManager::Get().DirectoryExists(*DiskPath) || IFileManager::Get().FileExists(*DiskPath))
		{
			OutDiskPath = DiskPath;

			bIsPhysicalPath = true;
		}
	}

	return bIsPhysicalPath;
}

## 8. 复用价值（给下一轮）

1. 🔴 **"报告说'可达性活跃'，要先问'入口的守卫链'**：本条的入口守卫是**设置表**（默认恰好等于四类 ⇒ `else` 分支恒空），一眼看不出来；判据必须**先打入口**（本轮用 `FGeneratorCore::BeginGenerator` ＋ 直接调用被测函数把这条链打了出来）。**"活跃"要能写出"用户怎么做才能到达"**，写不出就是"受限"。
2. **"全量替换 vs 根段替换"是资产路径映射的通用坑**：`Replace("Game", …)` 在**子串**上命中（`Gameplay`/`GameModes`/工程名含 `Game`）—— 判据只需一个**含该子串的目录名**即可翻转（本轮 case A/C 各命中一半：`/Game` 树与 `/Engine` 树）。
3. **"落盘成功但整份 C# 编译失败"是最便宜的 fail-loud 判据**：`dotnet build` 4 个 error 全指向被测产物（§3.2），比任何日志断言都硬；**同一棵树**上"改前 4 错 → 改后 0 错"是**无需回退二进制**的 A/B。
4. **清洗器要复用现成的**：`Encode` 已在库里处理关键字/数字开头/宽字符（E5），命名空间、标识符、文件名三条链上的"非法字符"应共用它 —— 本轮 ② 只加了 12 行。
5. **"内部路径 ≠ 磁盘路径"是内容浏览器类条目的通用前提**：文件项直接是磁盘路径、文件夹项要**派生**（E9/E10），因此 `GetItemPhysicalPath` 必须有**存在性守卫**（§3.4 的自纠就是这条的实证）；同理，判据不能拿**手写的**虚拟路径当输入（会得出"返回了不存在的目录"这种假缺陷/假正常）。
6. 🪤 **装置经验（本轮踩到的三条）**：
   - **`private` ＋ 无导出宏** ⇒ 探针调不动；临时"`private:`→`public:` ＋ 补 `API` 宏"是最小改动（首次构建即因 `LNK2019` 暴露），**还原后必须 grep `TEMP-B25` = 0**；
   - `FGeneratorCore::IsSupported(UPackage*)` 依赖 `SupportedAssetPath`（由 `BeginGenerator` 填）⇒ **不 `BeginGenerator` 就 `written=0`**（本轮第一次跑就是这么失败的：`fileName` 打印正常、`written=0`）；
   - **`GetItemsAtPath` 会原样回显你传入的路径**（数据源按路径 `FindNode` 后建条目）⇒ **手写路径无法验证派生逻辑**，必须从**真实动态类**反推节点路径（本轮从 1 个动态类算出 3 级节点路径）。
7. **同轮并行产出的文档也要"锚在 HEAD"**：[`64`](64-裁定材料-F-INT1-004与口径四项（2026-10-15）.md) 在**工作区含本轮 TEMP 改动**的情况下成文 ⇒ 它在文件头显式声明"全部行号锚在 HEAD `cf27778f`"并给出两处已漂移的例子（`UnrealCSharpEditor.cpp` 守卫 HEAD `:62` ↔ 工作区 `:65`）——**这是"审计库与施工并行"时的正确姿势**。

8. 🔴 **覆写引擎虚函数时，"放在哪里"也是可核查的事实**（本轮维护者指出）：`UDynamicDataSource` 的 20 处 override **是按引擎基类声明顺序排的**，我方初版把新函数插在 `DeleteItem` 之后 ⇒ 破坏了这个约定。**规则**：新增 override 前先 `Select-String` 引擎头把**基类声明顺序**列出来，再插到对应位置（`.h` 与 `.cpp` 同序）；这类"纯位置"改动**同样要重跑受影响条目的判据**（本轮重跑 `b25-cb-post3`，读数逐条相同）。
