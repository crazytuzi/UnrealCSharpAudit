## 1. 静态普查：Default ALC 侧（`Interop.dll`）的静态持有者

`Interop.dll` 由 hostfxr 加载进 **Default ALC**（`UnrealAssemblyLoadContext.Load` 对 `"Interop"` 走 `GetLoadContext(typeof(AssemblyLoader).Assembly)`），因此**只有它里面的静态**才可能把可回收 ALC 钉住。10 个源文件的全部静态：

| 静态 | 类型 | 卸载时的处理 | 判定 |
|---|---|---|---|
| `AssemblyLoader.Context` | `UnrealAssemblyLoadContext?` | `Unload()` 的 `finally` 里置 `null`（`AssemblyLoader.cs:52-57`） | ✅ 已清 |
| `HandleData.Handles` | `Dictionary<nint, GCHandle>` | `Clear()` 逐个 `Free()` ＋ `Clear()`（`HandleData.cs:150-166`） | ✅ 已清（强句柄全释放） |
| `HandleData.ObjectToHandleReference` | `ConditionalWeakTable<object,…>` | `Clear()`；且 CWT 是弱键 | ✅ 不构成强根 |
| `TypeBridge.StringToType` | `Dictionary<string, Type>` | `Clear()` → `StringToType.Clear()`（`TypeBridge.cs:553-556`） | ✅ 已清（**Type 缓存是 ALC 类型的强引用**，这条很关键） |
| `MethodBridge.Bindings` | `MethodBindings`（`Dictionary<string,nint>`） | `Clear()` → 换空快照（`MethodBridge.cs:221-224`） | ✅ 已清（只存裸句柄，无 `MethodInfo`） |
| `LogBridge.ConsoleOut`/`ConsoleError` | `TextWriter?` | `Deinitialize()` 里恢复并置空 | ⚠️ **`Deinitialize()` 从未被 native 调用**（见 §1.1），但持有的是 Default 类型的 writer，不含 ALC 引用 |
| `LogBridge.LogFn` / `bIsLeanCLR` | 函数指针／bool | — | ✅ 非托管引用 |
| `HandleData.Lock` / `Handle` | 锁／计数器 | — | ✅ |

ALC 内部的静态（`Script/UE/CoreUObject/**`：`SynchronizationContext.Context`/`TaskList`、`Utils` 的缓存等）属于**可卸载单元自身**，不构成 ALC 之外的根。

### 1.1 顺带发现（不是本条根因，但属缺陷面）

`LogBridge.Deinitialize()` **没有任何 native 调用点**（全树只有 `LogBridgeInitialize` 的调用：`FScriptDomainImpl.inl:603`）。后果：域卸载后 `Console.Out`/`Console.Error` 仍指向 `LogBridge`、`LogFn` 仍指向已卸载的 native 函数 ⇒ 之后任何 `Console.Write` 会**回调到已卸载的插件代码**。因为 `LogBridge` 在 Default ALC，它**不是** ALC 的根，但这是一个独立的悬挂函数指针面，登记为 **`F-LIFE-015` 的伴生发现**（见 §5）。

## 2. 决定性实验：2 s → 20 s

| 件 | 做法 |
|---|---|
| C# 改动 | 插件 `Script/Interop/AssemblyLoader/AssemblyLoader.cs` 的 `const int TimeLimit = 2000;` → `20000`（`// B240B_PROBE`；项目的 `Script/Interop/Interop.csproj` 直接 `Compile Include="../../Plugins/UnrealCSharp/Script/Interop/**"`，无需改部署副本） |
| 构建 | `dotnet build Script/Interop/Interop.csproj -c Development`（**0 Warning / 0 Error**）→ 产物 `Content/Script/Interop.dll` → 拷到 `Binaries/Win64/Interop.dll`（hostfxr 实际加载的那份） |
| 探针 | 复用 `UnrealCSharp.B240ProbeAlc`（一次 `IScriptDomain::Get()->Deinitialize()`）＋ `UnloadAssembly` 内的 `[b240] unload ms=` 计时注入 |

**读数**：

| 上限 | `Deinitialize()` 总计 | 其中 C# `Unload()` |
|---|---|---|
| 2000 ms | 2005.332 ms | **2002.376 ms**（撞满） |
| **20000 ms** | **20006.027 ms** | **20002.622 ms**（**仍撞满**） |

⇒ **20 s 内数百轮 `GC.Collect()` ＋ `WaitForPendingFinalizers()` 依旧回收不了**：这已经不是"best effort 没等到"，而是**存在 ALC 之外的强根**。同轮也把"GT 被阻塞多久"钉死：**阻塞时长 = 上限本身**（默认每次域卸载 2 s）。

## 4. 下一步（根路径定位，需要装置）

静态普查已把 Default 侧 6 个持有者全部排除 ⇒ 剩下的根**不在静态字段里**，需要用托管堆根路径分析：

1. **开诊断**：`Config/DefaultUnrealCSharpSetting.ini` 的 `bEnableDebug=true`（`FCoreCLRDomain::Initialize` 只在 `IsEnableDebug()` 时设 `DOTNET_EnableDiagnostics=1`；默认 0 ⇒ `dotnet-dump` 无法 attach）。
2. 触发一次卸载（本轮的 `B240ProbeAlc` 探针）后，**进程仍然存活且 ALC 仍被钉住** ⇒ 从容抓取：`dotnet-dump collect -p <pid> -o b241.dmp`（本机已有 `dotnet-dump 10.0.750501`）。
3. `dotnet-dump analyze b241.dmp` 内执行 `dumpheap -type UnrealAssemblyLoadContext` → `gcroot <addr>`，看根路径落在 **Thread／ThreadPool 工作项／静态字段／GCHandle** 哪一类。
4. 若根是"**仍在运行的线程/线程池工作项**"：查 `SynchronizationContext` 的任务链是否有未排空的 continuation（域卸载时 GT 被 2 s 循环占住，`Tick` 不跑）。
5. 若根是"**GCHandle**"：即 `HandleData.Clear()` 之外还有分配点（本库裁定 `Alloc` 单函数，需查是否有 `GCHandle.Alloc` 旁路）。

> 判据（根找到后）：连续两次独立进程卸载后，`Unload()` 的耗时从 **≈2000 ms 掉到 < 100 ms**（回收成功即跳出循环），且 `ContextWeakReference.IsAlive == false` 可由 C# 侧探针读数确认。
