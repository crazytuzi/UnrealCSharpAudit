## 1. 第 0 步前提回核

### 1.1 代码事实（施工前）

```cpp
// Source/UnrealCSharpCore/Private/Reflection/FClassReflection.cpp（施工前）
	FString ArrayGetString(const IManagedHandle InManagedHandle, const int32 InIndex) const
	{
		if (const auto ManagedHandle = ArrayGet(InManagedHandle, InIndex); IManagedHandleIsValid(ManagedHandle))
		{
			const auto Result = ScriptDomain->StringToFString(ManagedHandle);   // 1 次 pinvoke + FString 构造
			ScriptDomain->Free(ManagedHandle);
			return Result;
		}
		return {};
	}
```
| 事实 | 位置 | 说明 |
|---|---|---|
| `Parse*` 的循环上界**每轮重算** | `ParseProperties/Fields/Methods` 的 `for` 条件 | `InManagedReader.ManagedHandle2Int32(InParams[1])` 每轮调用一次 |
| 三个容器**从不 `Reserve`** | `ParseProperties`/`ParseFields`/`ParseMethods` | 元素总数**在循环前就已知**（`InParams[1]`） |
| 名字**两次深拷贝** | `Properties.Add(PropertyName, new FPropertyReflection(PropertyName, …))` 等 | 一次进反射对象、一次进 map 键（`Methods` 更差：键是 `TTuple<FString,int32>`，`FindOrAdd({MethodName, …})` 先构造临时元组再插入） |
| `TMap` **有右值重载** | 引擎 `Containers/Map.h:410`（`Add(KeyType&&, const ValueType&)`）与 `:682`（`FindOrAdd(KeyType&&)`） | ⇒ 键可以 move，无需改任何类型 |
| 查询侧每次构造临时键 | `GetMethod`：`Methods.Find({InName, InParamCount})` | 键类型是 `TTuple<FString,int32>` ⇒ **每次查找 1 次 `FString` 深拷贝** |
| `Methods` 键类型 | `FClassReflection.h:176` | `TMap<TTuple<FString,int32>, TArray<FMethodReflection*>>` |

### 1.2 对审计原文的三点核实

1. 🟢 **`Reserve` 建议成立**（原文"问题 3/建议 3"）：三处都没做，且容量已知 ⇒ 本轮采纳。
2. 🔴 **"`StringToFString` 每次调用都要 `SetNumUninitialized(65536)`" 不准确**：`FScriptDomainImpl.inl:294-334` 的**常态是 1024 字符栈缓冲快路径**（`:300-312`），65536 那条是 **首轮失败后的回退分支**（`:314-329`，仅 >1023 字符才走）⇒ 成员名（短串）根本不进那条路。
3. 🔴 **键改 `FName` 解决不了任何大小写问题**（原文已在"问题 2"自我更正，本轮复核确认）：`FName::IsEqual` 默认 `ENameCase::IgnoreCase`（引擎 `NameTypes.h:760`/`:1483-1487`）⇒ 换键只会把 `GetMethod("Foo")` 的匹配**变得更宽松**，属**语义变更**，本轮**不动**。

## 2. 施工（1 文件 / 3 处，`+36/−19`）

| # | 位置 | 改动 | 依据 |
|---|---|---|---|
| 1 | `ParseProperties` / `ParseFields` / `ParseMethods` 起手 | 计数上提为局部量 ＋ `Properties.Reserve(Properties.Num() + PropertyCount)`（Fields/Methods 同构） | 容量在循环前已知；`Reserve` 取代"1→2→4→…"的反复扩容与再哈希 |
| 2 | 三个 `Add`/`FindOrAdd` | 先构造反射对象（名字进对象），再把名字 **move** 进 map 键：`Properties.Add(MoveTemp(PropertyName), PropertyReflection)`、`Methods.FindOrAdd(TTuple<FString, int32>(MoveTemp(MethodName), MethodParamCount))` | 键由"深拷贝"变"移动"⇒ 每成员少 1 次 `FString` 堆分配；`TMap` 右值重载已在引擎侧确认 |
| 3 | 三处 `for` 条件 | 改用上提后的局部计数 | 去掉每轮一次句柄→int32 转换 |

⛔ **本轮明确不做（各附依据）**：
- **按需解析**（只解析被请求的成员）：C# 侧接口是**整表返回**（`Utils.GetClassMethods` 等），要改就得动跨语言协议 ⇒ 与 `F-INT1-004` 同类，需先裁定。
- **批量化 pinvoke**（把 N 次字符串转换合并成 1 次）：同上需协议变更；且**实测这条路不是热点**（§3.3：4 954 次转换仅占解析 wall 的 5%）。
- **键改 `FName`**：见 §1.2-3（语义变更且不解大小写）。
- **`GetMethod` 的临时键去拷贝**：需要把 `Methods` 的键类型或 `GetMethods()` 的返回类型改掉 = **公开 API 变更**；且实测代价 **0.36 µs/次 × 2 000 次/会话**（§3.4）⇒ 收益不支持这个代价。

## 6. 未取得 / 边界（如实登记）

1. **"其余 ≈95% 的解析耗时在哪"未逐项归因**：本轮只测到"字符串转换占 5%"，没有把 `new` 反射对象、每成员属性容器、`FReflectionRegistry` 查表、`GetClass` 递归分开计时 ⇒ 若后续要优化解析，第一步应是**分解计时**而不是继续抠字符串。
2. **幅度不可信**：进程间方差 2.3×（同模式两轮），本轮的"提升百分比"**不作为结论**；只保留"分配/拷贝次数减少"这一**确定性**陈述。
3. **语料边界**：读数来自 `-game` 套件会话（192 次解析）。**真实编辑器/大工程会话**的解析总量未测（可能按类数线性放大）⇒ "会话级 9–23 ms"只对**本装置**成立。
4. **未构造**能放大差异的压力用例（例如人为解析超大类 `AActor` 多次），因此"Reserve 的收益随元素数增长"只是机制推断。
5. **Mono 的解析读数未测**（交付态只跑了套件；探针矩阵只在 CoreCLR）。
6. **`GetMethod` 的临时键**未修（需公开 API 类型变更）⇒ 已登记为残留，未开新编号（量级 0.36 µs/次）。

## 7. 复用价值（方法论）

1. **"同一二进制 + 环境门控"仍是最省事的 A/B**：本轮 3 次构建就拿到了 2 轮 × 2 模式的矩阵（改前/改后各 2 次）。
2. 🔴 **性能条目必须先冻结"代价口径"再动手**：本轮最有价值的产出不是那 3 处改动，而是**把原判的量化前提测掉了**（字符串只占 5%）——否则会沿着"批量化 pinvoke（要改协议）"这条错误的路走下去。
3. **计数型不变量比时间型读数可靠**：Σ 转换次数（4 954）四次运行**逐项相同**，可用来证明"路径没被改动"；而 Σ 时间在 9–23 ms 之间跳 ⇒ 只做**同轮同向**的比较，不做跨轮百分比。
4. **探针日志是相对 CWD 的**：UE 编辑器/命令让 CWD = `Engine\Binaries\Win64` ⇒ 读数不在工程目录（轮 B-11 已记一次，本轮再次确认）。
5. **"热路径"要靠调用次数证明**：`GetMethod` 每次一次深拷贝听起来很贵，实测 2 000 次/会话、0.36 µs/次 ⇒ 先数次数，再谈优化。
