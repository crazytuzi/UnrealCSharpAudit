## 2. V1 —— 编辑器激活时点后移 / 首次运行（publish 陈旧）是否跳过激活

### 2.1 实测

| 场景 | 读数（`b52-probe.log` 逐字） | 判定 |
|---|---|---|
| **编辑器 · 热启动**（`props` 17:37 < dll） | `[V1] OnPostEngineInit` → `SetActive(1) enable=1 outdated=0 activeBefore=0` → `done active=1` | ✅ **激活发生在 `OnPostEngineInit`，一次成功**（A2/A4/B3 三次一致）；**未见** `OnLoadingPhaseComplete`（编辑器分支不注册它） |

| **`-game`（editor 二进制）· stale** | `LoadingPhaseComplete phase=6/7/8` → `SetActive(1) enable=1 **outdated=1** activeBefore=0` → `done **active=0**`；`props=…889200000000`、`UE.dll=…866500000000`、`Game.dll=…**926000000000**`（19:30）；CSV **3 行**、`LogUnrealCSharp` **0** 行 | 🔴 **真实可达**：激活被跳过 ⇒ **整条 C# 链不启动**、套件静默只剩 2 条 C++ 判据 |

### 2.2 结论与影响面

- **编辑器（交互）**：V1 的"时点后移"是**事实**（`OnPostEngineInit` 而非 `OnLoadingPhaseComplete`），但"publish 陈旧 ⇒ 跳过激活"**被启动期同步编译自动补偿**，**不可构造**。

## 3. V2 —— `OnCompile` 广播的副作用（刷 `CodeAnalysisDynamicFilesMap`）是否承重

### 3.1 A/B（同一驱动器、同一份新动态类文件）

| 状态 | 探针序列（逐字） | 新类是否出现 |
|---|---|---|
| **正常**（`b52-a4`） | `[V2] BroadcastTrue reloadImmediately=0` → `[V2] EditorOnCompile success=1 changes=2` → `[V2] MapRefresh done` → `[V2] Decide loaded=1 reloadImmediately=0 **dynamic=1** changes=2` | ✅ **8.12 s** 后 `find_object("/Script/CoreUObject.HotReloadProbeB52")` 命中、`Dynamic.json` 含该类 |
| **装置**（`b52-b3`，`B52SKIPMAP=1`） | `BroadcastTrue` → `EditorOnCompile success=1 changes=2` → `[V2] MapRefresh SKIPPED by device` → `[V2] Decide loaded=1 reloadImmediately=0 **dynamic=0** changes=2`（后续 2 次编译同样 `dynamic=0`） | ❌ **180 s 不出现**（`v2_found=false`；3 次编译尝试） |

### 3.2 结论

- **承重契约坐实**：`HasDynamicFileChanged` 读的是**内存里的** `CodeAnalysisDynamicFilesMap`；只要监听者不刷新它，**真实变化的动态文件**也会被判成"非动态"⇒ ① 不走 `Deactivate/Activate` 重载；② `else` 分支里的 `InFunction(FileChangesSnapshot)`（`FDynamicGenerator::Generator`）同样解析不出"文件 → 类"，新类**静默丢弃**。
- 也就是说：**"新动态类不重启不出现"这个缺陷的修复，依赖的是"广播的副作用恰好先于判定执行"**，而不是显式依赖 ⇒ 任何让监听者提前返回 / 未注册 / 抛异常的情况都会**静默回退**到修复前的行为（这正是 §3 V2 的原假设，本轮证实）。
- 🟡 **建议（待裁定）**：把 `SetCodeAnalysisDynamicFilesMap()` 从监听者搬到 `CompileInternal` 的 reload lambda（广播**之前**显式调用），使"刷新 → 判定 → 生成"成为**显式顺序**；`FEditorListener::OnCompile` 只保留 `FCodeAnalysis::Analysis()` 的产物写入。或退一步：`HasDynamicFileChanged` 直接读 `Dynamic.json`（代价 = 每次判定一次 IO）。⚠️ 改职责边界 ⇒ 需裁定。

## 4. V3 —— 成功/失败两条广播是否可能乱序

### 4.1 实测序列（三会话一致）

```
[V2] BroadcastTrue  reloadImmediately=0  t=…857.934   ← 图任务内
[V2] EditorOnCompile success=1 changes=2 t=…857.934   ← 同一毫秒
[V2] MapRefresh done
[V2] Decide … dynamic=1 changes=2        t=…857.934+0.2ms
… 后续失败编译：
[V3] BroadcastFalse                      t=…903.889   ← AsyncTask 内（独立时间点）
[V2] EditorOnCompile success=0 changes=0 t=…903.889
```
- `b52-a4`：`true`(52.2 s) → `false`(61.4 s)，时间序；`b52-b3`：三次 `true` 均无 `false` 干扰；`b52-c2`：`true`(53 s) → `false`(?)。
- **未观测到 `false` 早于其前一次 `true`**。

### 4.2 结构论证（为什么"不应"反转）

1. **单执行者闸门** `AcquireCompile()`（`FCSharpCompilerRunnable.cpp:615-639`）把四次编译入口串行化 ⇒ 两次编译不会并发；
2. **工作线程路径显式等待**：`CompileInternal` 在图任务派发后 `while (!Task->IsComplete() && …)` 自旋（`:596-602`）⇒ 该路径上 `true` 必然先于"下一次编译"发生；
3. **游戏线程路径**：`AsyncTask(ENamedThreads::GameThread, …)` 与 `FFunctionGraphTask::CreateAndDispatchWhenReady(…, GameThread)` **进的是同一个游戏线程任务队列**，FIFO ⇒ 后入队的 `false` 不可能越过先入队的 `true`。

⚠️ **边界**：上述第 3 条只对"同一队列"成立。若将来把 `false`（或 `true`）改到别的命名线程／`FTSTicker`／`GameThread_Local`，FIFO 保证即失效 ⇒ 需重新推导。本轮**未**构造反转，也**未**证明"任何实现下都不可能"。
