## 1. HEAD 事实（行号已按 `4564008d` 校正）

### 1.1 被测量函数（`Source/UnrealCSharp/Private/Environment/FCSharpEnvironment.cpp:343-360`）

```cpp
void FCSharpEnvironment::NotifyUObjectDeleted(const UObjectBase* Object, int32 Index)
{
	if (const auto InObject = static_cast<UObject*>(const_cast<UObjectBase*>(Object)))
	{
		if (const auto InStruct = Cast<UStruct>(InObject))
		{
			RemoveClassDescriptor(InStruct);
		}

		(void)RemoveObjectReference(InObject);          // :352  注册表查找/移除（O(1) 哈希）

		{
			FScopeLock Lock(&CriticalSection);           // :355  全局锁

			AsyncLoadingObjectArray.Remove(InObject);    // :357  O(N) 单趟压缩
		}
	}
}
```

- `AsyncLoadingObjectArray` 类型：`TArray<FWeakObjectPtr>`（`Public/Environment/FCSharpEnvironment.h:343`）；`CriticalSection` 在 `:341`。
- 增长点（`NotifyUObjectCreated`，`:317-341`）：**CDO 分支** `:345-351`（每个 CDO 入数组）与**非 game thread 分支** `:358-363`；flush 前只增不减。
- 清理点（`OnAsyncLoadingFlushUpdate`，`:420-480`）：`:430-432` 加锁拷贝 → `:435-470` 倒序收集 → `:476-479` 逐个 `RemoveAt`。
- 频率：`FUObjectListener::NotifyUObjectDeleted`（`Private/Listener/FUObjectListener.cpp:48-50`）→ **引擎每回收一个 UObject 回调一次**（GC / 关卡切换 / PIE 结束）。
- 🔴 **与审计原文的差异**：审计写 `:302-321` 且是 `if (UStruct) … else RemoveObjectReference`；HEAD 为 `:343-360`，且 **`RemoveObjectReference` 对所有对象无条件调用**（不只是非 UStruct 分支）。本轮读数按 HEAD 测。

## 4. 会话外推

| 场景 | D（删除次数/GC） | N（数组规模） | 回调总耗时 | 占 GC wall（110.65 ms） |
|---|---|---|---|---|
| 典型（本机稳态） | 13 652 | 24 | **2.6 ms** | 2.3% |
| 启动期峰值 | 13 652 | 441 | **25.7 ms** | 23.2% |
| 假设大工程 | 13 652 | 1 000 | 57 ms | 52% |
| 假设大工程 | 13 652 | 4 000 | **225 ms** | >100%（即回调本身超过一次 GC 的主体） |
| **越过 0.2 s 的临界** | 13 652 | **≈3 556** | 200 ms | — |

- 审计原文"`AsyncLoadingObjectArray` 数千～数万项"**未被本机复现**：启动峰 **441**、稳态 **24**；要外推到 3 556 需要类/CDO 数量再涨 8 倍，或大量异步加载对象在 flush 前堆积。
- 真实 GC 的 D 通常远小于 13 652（本轮 D 是人为造 12 000 个对象后的上限样本）；D 越小，同样 N 下的总耗时按比例下降。
- 反向看：即使按最不利的 N=441，单次 GC 的回调也只有 25.7 ms，**低于 0.2 s 线**；按规范"低于 0.2 s/会话 ⇒ 降 P3"成立。

## 5. 裁定与修法评估

**裁定：P2 → P3（量化后降级、本体不施工）。**

- 依据：本机 N 峰值 441、稳态 24；单次重 GC 回调 2.6–25.7 ms < 0.2 s；O(N) 扫描 4.1 ns/项，只有在 N 达到 3 556 且 D 保持 13 652 时才越线。
- **触发重估**：`D × (70 + 4.1×N) ≥ 0.2 s`（例如 N=3 000 且 D ≥ 15 000；或 N=10 000 且 D ≥ 4 300），或 profiling 把 `NotifyUObjectDeleted`/`OnAsyncLoadingFlushUpdate` 排进前列，或观测到 `AsyncLoadingObjectArray` 峰值 >3 000。

**修法评估（未采纳）**：

| 方案 | 收益 | 风险/代价 |
|---|---|---|
| `TArray` → `TSet<FWeakObjectPtr>` | `Remove` O(1) 平摊 | 🔴 审计已指出：`TWeakObjectPtr` 的哈希基于 `(Index, SerialNumber)`，对象回收/索引重用后哈希漂移，`Remove` 可能失败 ⇒ 需改键为 `ObjectIndex` 或保留"标记-压缩" |
| flush 改单趟 `RemoveAllSwap` | 把 K 次 `RemoveAt` 的 O(K·N) 降为 O(N) | 不解决删除路径；flush 频率低，收益未量化 |
| "先判存在再取锁" | 省一次锁（13.5 ns） | 需从对象反查它当初走哪条增长分支，结构改动大于收益 |

结论：修法要么动容器键（哈希风险），要么只优化低频率的 flush；在当前量级（<26 ms/GC）下**不值得施工**，保留为触发式条目。
