## 1. 事实（HEAD `08ea0bcf`）

### 1.1 C#→C++ 方向：三条断点

| # | 事实 | 证据 |
|---|---|---|
| ① | `GetPropertyType` **无任何 Delegate 分支** | `EPropertyTypeExtent::Delegate/MulticastDelegate/MulticastInlineDelegate/MulticastSparseDelegate` 在 `Source/**` 的引用数 = **0**（`grep` 全树）；`GetPropertyType` 落到 `return EPropertyTypeExtent::None` |
| ② | `Factory`/`ManagedFactory` **无 Delegate case** | 两个 switch 的 case 列表里都没有这 4 个枚举值（`FTypeBridge.inl`） |
| ③ | **没有可判定的 C# 类型身份** | C# 侧委托类型是**按 C++ 签名一次性生成**的普通类：`Script/Game/Proxy/.../FOnPickUp.cs:12` 是 `public class FOnPickUp`（**无基类、无标记接口**），只在类内声明 `public delegate void Delegate(...)`（`:14`）；`Script/Reflection/Property` 下只有空的 `FMulticastDelegateProperty` 标记类，**没有** `FDelegateProperty`、也没有 `TDelegate<>`/`TMulticastDelegate<>` 泛型包装（机械计数 0） |

### 1.2 即使能判定类型，也缺 `SignatureFunction`

| 事实 | 证据 |
|---|---|
| 引擎两个委托属性类都**必须**挂签名函数才能在 link 后可用 | `UnrealType.h:6014-6015`：`/** Points to the source delegate function ... */ TObjectPtr<UFunction> SignatureFunction;`（`public:` 在下一步之后）；`FMulticastDelegateProperty` 同（`:6073-6074`） |
| `SignatureFunction` 是**公开成员**（可写），但插件里**只有读、没有写** | `SignatureFunction` 全库 **74 处引用，写入点 0**（全部是 `GetFullClass`/`GetClassNameSpace`/`FDelegateGenerator`/`FCSharpDelegateDescriptor`/`UDelegateHandler` 的**读**） |
| 生成侧只能"从 C++ 读签名" | `FDelegateGenerator::Generator(FDelegateProperty*)`（`:26-40`）与 `Generator(FMulticastDelegateProperty*)`（`:397-410`）都以 `InDelegateProperty->SignatureFunction` 为输入；`FGeneratorCore.inl:10-22` 也以它定位模块与生成路径 |
| C# 委托类的"签名"只存在于 IL（嵌套 `Delegate` 的 `Invoke`），插件没有把它变成 `UFunction` 的路径 | `FDynamicGeneratorCore::GeneratorFunction` 只处理 C# `[UFunction]` 方法（`FMethodReflection`），不处理委托类型的 `Invoke` |

> 结论：`Factory` 里"new 一个 `FDelegateProperty` ＋ 赋 `SignatureFunction`"在 C++ 侧**语法可行**，但**语义上无来源** —— 拿不到那个 `UFunction`。

## 2. 判定

| 项 | 结论 |
|---|---|
| 缺陷 | ⚪ **不成立为"映射缺口"**：不是"少一个 case"，而是 **C# 声明面本身不存在**（无法把一个 C# 委托类型唯一对应到某条 `UFunction` 签名） |
| 可达性 | **不可达**（本仓 0 处 C# `[UProperty]`/`[UFunction]` 使用委托类型；且当前命名契约下也无从判定） |
| 本轮处置 | **不施工**；`F-BR-011` 的 Delegate 面记 **不适用/登记** |
| 触发条件 | 维护者要求"动态 C# 类声明委托属性"；或出现 C# 侧委托属性语料（当前 0） |

## 3. 若将来要做：两个方向（供拍板，不在本轮）

| 方向 | 内容 | 规模/风险 |
|---|---|---|
| **A（小，命名契约反查）** | 用 C# 委托类名（`GetClassNameSpace` ＋ `GetFullClass` 同源）反查已存在的 `UFunction`（例如 `…__DelegateSignature`），命中才构造 `FDelegateProperty`/`FMulticastDelegateProperty` ＋ 赋 `SignatureFunction` | ≈20–30 行；**风险高**：依赖生成类名与 C++ 签名函数的命名契约，动态类/跨模块场景可能查不到；查不到时只能静默丢弃（与现状同） |
| **B（大，签名合成）** | 从 C# 委托类型的 `Invoke` 反射签名**合成一个 `UFunction`**（参数/返回值/调用约定），再挂到新建的委托属性上；复用 `FDynamicGeneratorCore::GeneratorFunction` 的属性构造管线 | 远超映射层（需要新的 C# 反射面 ＋ UFunction 生命周期归属裁定）；建议单独立项页 |

**推荐**：**A 不单独做**（命中率不可证、失败即静默）；若确有需求，直接按 **B** 立设计页（含"合成的 `UFunction` 归属谁、何时销毁"）。
