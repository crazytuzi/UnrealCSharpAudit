## 0. 结论摘要

### 0.1 三类读数（`-game` 套件内采集，探针 v3）

| 元素类型 | 元素尺寸 | 入参缓冲内容 | `Set` 后 native | 与表内元素（字节） | hash（native vs 元素） | 引擎 `Property->Identical` | 描述符 `Identical`（native vs native） |
|---|---|---|---|---|---|---|---|
| `TSet<UObject>` | 8 | **托管句柄**（样本 `0x3BA1`） | `UObject*`（样本 `0x0121C692C0`） | **逐字节恒等**（3/3 命中样本） | **相等**（`0x68428F10`） | **true**（3/3） | **false**（0/3） |
| `TSet<int32>` | 4 | 原生值（`0x00000001`） | 原样 | 逐字节恒等（18/18） | 相等（`0x00000001`） | true（18/18） | **true**（18/18） |
| `TSet<FString>` | 16 | **托管句柄**（8 字节，如 `0x61D7`） | 独立原生 `FString`（Data 指针不同、`Num`/`Max` 同为 `0x14`） | **字节不等价**（设计如此） | 内容相等（元素 vs 其原生拷贝：**47/47**） | true（47/47） | false（对象/字符串一侧） |

> 说明：`hashEqN` = 表内与该次 native 值 hash 相等的元素数；样本封顶 48 条/类型，见 §6 限制 1。

### 0.2 判定

1. **门槛结论 = "转换恒等"**（值语义层面）：`Descriptor->Set(handle, scratch)` 产出的原生值，与表内元素在 **hash 与引擎相等谓词**上完全一致（对象/整数连字节都相同）⇒ 按 323 §9 的分支，进入"**再评估修 `Set` 语义 / 独立 hash 入口**"，**不是**"放弃该优化"。
2. **两次失败的根因（前两轮缺的那一格）**：
   - **B-287（直接哈希版）**：`hashRaw ≠ hashNative` —— 对象类 `0x00003BA1`（句柄位）vs `0x68428F10`（指针 hash）；字符串类把 **8 字节句柄当 16 字节 `FString`** 读，实测 hash 退化为 `0x00000000`（空串）。⇒ 插入/查找落在错误桶 ⇒ 4 条 `TSet<UObject>` 用例失败。
   - **B-288（scratch 版）**：hash 已经正确（`hashNative == hashElem`），但只要**相等谓词仍走描述符 `Identical`**，native↔native 就恒判不等（对象 **0/3**）⇒ 重复判定失效 ⇒ `SetCompoundAddFalse` / `SetCompoundRemoveTrue` / `SetCompoundContainsTrue` 三条失败，与 run#2 的失败清单**逐条对应**。
3. **可行修法不需要改 `Set` 语义**：引擎 API 本来就**把 hash 与相等分开传**（`FindIndex`/`FindIndexByHash`/`FindOrAdd`/`Add` 均收 `GetKeyHash` ＋ `EqualityFn`；5.6 `Containers/Set.h:1963/1978/1994/2007`；`FScriptSet : public TScriptSet<…>` `:2115`）。把两个 lambda 换成**引擎原生语义**即可 —— 属**新增独立入口**，不动描述符既有契约。
4. **`FString` 不能做字节比较**：同内容的两个原生 `FString` 缓冲地址不同（本页 §2.3 实测），字节比较必然为假；快路径的相等谓词必须是**值语义**。

## 2. 读数明细

### 2.1 `TSet<UObject>`（`FObjectProperty`，8 字节）

**3 条命中样本（`Add` / `Remove` / `Contains` 各一条）完全同形**：

```
B289 kind=Object op=Add size=8 align=8 elems=2 matchIdx=0 byteEqHit=1 engineEqHit=1 hashEqN=1
     descNativeEq=0 in=A13B000000000000 native=C092C62101000000 elem=C092C62101000000
     hashRaw=0x00003BA1 hashNative=0x68428F10 hashElem=0x68428F10
```

| 读数 | 值 | 含义 |
|---|---|---|
| `in` | `A13B000000000000` = **`0x3BA1`** | C# 传的是**托管句柄**（`IManagedHandle` = `int64`，`TSet.cs:113-120` 用 `HandleData.GetHandle` 取） |
| `native` | `C092C62101000000` = **`0x0121C692C0`** | `FObjectPropertyDescriptor::Set`（`:18-27`）把句柄换成 `UObject*` 后写入 scratch |
| `elem` | 与 `native` **逐字节相同** | 表内元素是同一个对象 ⇒ **转换恒等** |
| `hashRaw` vs `hashNative` | `0x3BA1` vs `0x68428F10` | 对句柄缓冲取 hash = 把句柄当指针做 hash ⇒ **完全错** |
| `hashNative` vs `hashElem` | 相等 | native 值上的 hash 与表内一致 |
| `engineEqHit` | 1 | 引擎谓词在 native↔native 上为 true：`FObjectProperty::Identical`（`PropertyObject.cpp:113`，经 `FObjectPropertyBase::StaticIdentical` `PropertyBaseObject.cpp:123`）——先比指针，同指针直接 true |
| `descNativeEq` | **0** | 插件的 `FObjectPropertyDescriptor::Identical`（`:29-37`）把 **B 参数当句柄**再 `GetObject` ⇒ 对 native 指针恒判不等 |

**新值分支（`matchIdx=-1`）**：`elems=0/1/2` 时不命中属预期（值确实不在集合里），且 `engineEqHit=0` ⇒ 引擎谓词**没有假阳性**。

### 2.2 `TSet<int32>`（`FIntProperty`，4 字节）

```
B289 kind=Int op=Contains size=4 align=4 elems=2 matchIdx=1 byteEqHit=1 engineEqHit=1 hashEqN=1
     descNativeEq=1 in=02000000 native=02000000 elem=02000000 hashRaw=0x00000002 hashNative=0x00000002 hashElem=0x00000002
```

| 读数 | 值 |
|---|---|
| 入参即原生值（无句柄转换） | `in == native == elem` |
| 三个谓词 | `byteEqHit` / `engineEqHit` / `descNativeEq` **全部 1**（18/18） |
| `hashRaw == hashNative` | 值类型没有"句柄 vs 原生"的分裂 ⇒ **B-287 的直接哈希对值类型本来就成立**（这解释了为什么它的失败只集中在 `TSet<UObject>`） |

### 2.3 `TSet<FString>`（`FStrProperty`，16 字节）

**句柄 → native（第 2 条 Add 起有元素可对照）**：

```
B289 kind=Str op=Add size=16 align=8 elems=1 matchIdx=-1 byteEqHit=0 engineEqHit=0 hashEqN=0
     descNativeEq=0 strPairIdent=1 strPairHashEq=1
     in=D7610000000000000000000000000000
     native=00BA652A010000001400000014000000   (Data=0x012A65BA00, Num=0x14, Max=0x14)
     elem=00C7652A010000001400000014000000     (Data=0x012A65C700, Num=0x14, Max=0x14)
     hashRaw=0x00000000 hashNative=0x58803BF3 hashElem=0xFBFD2795
```

| 读数 | 含义 |
|---|---|
| `native` 与 `elem` 的 `Num`/`Max` 相同（`0x14`）、**Data 指针不同** | `Set` 产出的是**独立的原生 `FString` 拷贝**（值等价、**字节不等价**）⇒ 任何 `Memcmp` 判等都会失败 |
| `hashRaw = 0x00000000` | 8 字节句柄按 16 字节 `FString` 读：Data=句柄、Num/Max=0 ⇒ 退化成空串 hash；**若后续两字为脏数据则触发越界读**（见 §6 限制 5） |
| `strPairIdent` / `strPairHashEq` = **47/47** | "元素本体 vs 其原生拷贝"（同内容、不同缓冲）：引擎 `Identical` **true**、hash **相等** ⇒ `FString` 的相等/hash 是**内容语义**（`FStrProperty::GetValueTypeHashInternal` = `GetTypeHash(FString)`，`StrProperty.cpp.inl:157-160`） |

> ⚠️ 套件里**没有** `TSet<FString>` 的重复 `Add`（`UnitTestSubsystem.cs:63-95` 只加 64 个唯一串），所以"重复字符串被正确判重"这一格用**原生对原生**补足；handle 路径的等价性由 `native`/`elem` 的 `Num`/`Max` 同形 ＋ hash/Identical 同源保证。

## 4. 分支判定与设计方向

### 4.1 门槛判定

323 §9 的二元分支取"**转换恒等**"一侧 ⇒ `F-HLP-028` 从"**P3 观察（冻结）**"转为"**可施工候选**"，但仍**不改变级别**（触发条件"万级 TSet"依旧没有证据，见 §6 限制 6）。

### 4.2 方案 A（推荐）：独立 native hash / 相等入口

引擎的哈希 API **本来就把 hash 与相等分开传**：

| API（5.6） | 签名要点 |
|---|---|
| `TScriptSet::FindIndex` `Containers/Set.h:1963` | `(Element, Layout, GetKeyHash, EqualityFn)` |
| `TScriptSet::FindIndexByHash` `:1978` | 同上 ＋ 预计算 hash |
| `TScriptSet::FindOrAdd` `:1994` | 再 ＋ `ConstructFn` |
| `TScriptSet::Add` `:2007` | 再 ＋ `DestructFn`（命中时先析构再构造） |
| `FScriptSet : public TScriptSet<FDefaultSetAllocator, FScriptSet>` `:2115` | `FSetHelper` 现有 `FScriptSet*` 可直接用 |

因此最小改动是：`GetKeyHash = [P](const void* Src){ return P->GetValueTypeHash(Src); }`、`EqualityFn = [P](const void* A, const void* B){ return P->Identical(A, B, 0); }`，值缓冲 → scratch 仍由 `Descriptor->Set` 完成；插入的 `ConstructFn` 捕获入参句柄再 `Descriptor->Set`（保持"从入参构造"的既有语义），`DestructFn` 用 `Descriptor->DestroyValue`。**描述符的 `Identical`/`GetValueTypeHash` 契约一个字都不改**。

### 4.3 方案 B（不推荐）：把描述符 `Identical` 改成对称语义

会同时影响 6+ 个属性描述符与全部既有调用点（B 参数现为**句柄**语义，`FObjectPropertyDescriptor:29-37`、`FStrPropertyDescriptor:49-58` 等），风险面远大于收益；且与 C# 侧"入参是句柄"的既有约定冲突。

### 4.4 施工前必须钉死的五点（建议 B-290 设计页定稿）

1. **scratch 生命周期**：`FMemory::Malloc(GetSize(), GetMinAlignment())` ＋ 清零 ＋ 一次 `Set`；**只对确定被 `Set` 初始化过的 scratch 调 `DestroyValue`**（`Set` 会早退）。
2. **`bNeedRehash`/`EnsureRehash` 退役**：改哈希插入后哈希元数据始终有效，`RemoveAt` 前的全表 `Rehash` 应删除（Remove 由 O(N) 降到 O(1)）；需在报告里给出 `bNeedRehash` 残留 0 的 grep 证据。
3. **字符串/结构体的值语义**：不得出现任何 `Memcmp`；`FString` 的复制成本与现状相同（插入本来就要复制一次）。
4. **三档编译面**：5.0 模块级 `cl`、5.6/5.8 UBT（B-279/B-275 的装置可直接复用）。
5. **回归判据**：6 条 `SetCompound*` ＋ `SetLarge*`（1024 元素）＋ B-153 的微基准口径（5 000 次 `Add`/`Contains` 的 40.648/35.627 ms → 0.734/0.404 ms 参照），并要求 CSV 与 `A4BFF990…` 同 SHA（除**允许**新增的微基准行外）。
