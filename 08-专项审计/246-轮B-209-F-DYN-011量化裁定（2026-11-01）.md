## 1. 算法结构与"重复查找"到底有多密

`FDynamicDependencyGraph::Generator()`（`:87-229`）有两个循环，都是 **同一节点键被反复取值**：

```cpp
NodeArray[NodeMap[Element]] .IsCompleted()      // 第一次
NodeArray[NodeMap[Element]] .Dependencies       // 第二次
NodeArray[NodeMap[Element]] .Generator()        // 第三次
NodeArray[NodeMap[Element]] .Completed()        // 第四次
…
NodeMap.Contains(Type) / NodeArray[NodeMap[Type]] …   // 依赖侧
```

静态数：`NodeMap[Element]` **5** 处、`NodeMap[Type]` **4** 处、`NodeMap[OutNode]` **6** 处、`NodeMap.Contains(Type)` **2** 处 —— 共 **17 个键访问点**，其中第二个循环里 `NodeMap[OutNode]` 在**同一个节点**上被取 6 次。

## 3. 成本分解：图算法自身只占 ~0.2%

| 项 | 估算 | 占 5.09 ms |
|---|---|---|
| 129 次键查找 | 129 × 33.16 ns ≈ **4.3 µs** | 0.08 % |
| 21 次依赖扫描（含 `FDependency::GetType` 建串 + 查找） | ≈ **5 µs** | 0.1 % |
| 容器操作（`TQueue`/`TSet`/`TArray` 栈） | ≈ **1 µs** | 0.02 % |
| **图算法自身小计** | **≈10 µs** | **≈0.2 %** |
| 节点生成器本体（`Node.Generator()` 调用的真实生成） | ≈5.08 ms | ≈99.8 % |

⇒ 「热路径上反复做 `FString` 键查找」在**当前规模下不成立**：真正花时间的是被驱动的**生成器本体**，不是图算法。

## 4. 裁定

| 项 | 结论 |
|---|---|
| 级别 | **P2 → P3**（量化后降级，**本体不施工**） |
| 会话开销 | 图算法自身 **≈10 µs**；含生成器本体 5.09 ms —— 门槛 200 ms ⇒ 低一～两个数量级 |

## 5. 边界（如实登记）

1. **只测 `-game`**：本会话 22 个动态类型。编辑器会话的动态类型通常更多，但图的节点是**动态类型**（不是文件），量级仍是个位到百位。
2. **未构造"深链/成环"负载**：本会话 `deps=21`、无 pending 重扫 ⇒ 第二阶段的"重复依赖扫描"**没有被触发**。该分支的成本只能靠外推（线性于依赖条目数），**未实测**。
3. **17 处包装有极小开销**：`lookups` 计数本身是 `++`（≈1 ns），已包含在 5.09 ms 里；对结论无影响。
