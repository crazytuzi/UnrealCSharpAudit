## 1. 结论摘要（先读这一节）

1. ✅ **容器半已修**：三个 Helper 的 `Deinitialize()` 在"**自有容器**"分支里，先 `Empty(0)`（= 走各自 `Empty` 的**逐元素析构** + 归还元素缓冲）**再** `delete` 外壳。在此之前，`delete` 只释放**外壳**（元素缓冲与元素内层堆全部泄漏）——这正是 `F-LEAK-012` 的原文机制。
2. ✅ **可选值半已修**：`FOptionalHelper::Deinitialize()` 在 `bNeedFreeData` 分支里，先 `OptionalProperty->MarkUnset(Data)`（引擎的 **set-aware 析构**：已设置 ⇒ `ValueProperty->DestroyValue(Data)` 并把标志置假）**再** `FMemory::Free(Data)`。
3. 🟢 **判据是"容器/可选值在释放时刻是否还持有元素"**（同一二进制 A/B，环境变量门控）：
   - 容器：改前 `numBefore=64 numAfter=64 emptied=0` → 改后 **`numAfter=0 emptied=1`**（Array / Map / Set 三类各一行，逐字相同）。
   - 可选值：改前 `setBefore=1 setAfter=1 emptied=0` → 改后 **`setAfter=0 emptied=1`**。
   - 两次运行的套件都是 **1780 / 0 失败**（1 772 基线 + 本轮 8 条新断言）。
4. 🔴 **新登记 `F-LEAK-016`（P1 候选 / 未修）**：`FOptionalHelper` 的 owned 分配是 `FMemory::Malloc(ValuePropertyDescriptor->GetSize(), …)`，而引擎的可选值布局需要 `Align(valueSize + 1, valueMinAlignment)`（值在偏移 0、**set 标志紧随其后**），且 `InitializeValueInternal` **在构造函数里**就写那个标志 ⇒ **每次 `new TOptional<T>()` 都在分配块之外写 1 字节**。实测（探针，已移除）：`TOptional<int>` `allocSize=4 / requiredSize=8`、`TOptional<FString>` `allocSize=16 / requiredSize=24`，一轮套件命中 **7 次**。**为什么不能简单换成 `OptionalProperty->GetSize()`**：`SetValueProperty` 只赋值、不算尺寸（E13），插件这两处构造点都**没有走 link** ⇒ `ElementSize` 不可靠；正确写法是**按引擎公式自己算**。
5. ⏸️ **明确不做 / 登记**：`F-LEAK-016` 的分配修复（需自己的前提核查 + 探针，且要确认对齐语义）；`TPropertyValue.inl` 三处**容器浅拷贝 + deleter** 路径与 `TOptional` 版 `:1085` 的**可达性**（`FScriptArray` 的拷贝构造是 `check(false)`，若可达则在 Development 下断言）—— 见 §8。

**为什么用 `MarkUnset` 而不是 `ValuePropertyDescriptor->DestroyValue(Data)`**：可选值可能是**未设置**状态，此时那块内存不是合法值 ⇒ 直接 `DestroyValue` 会析构未初始化内存。`MarkUnset`（E9）是引擎的**set-aware** 入口：`if (*IsSetPointer) { ValueProperty->DestroyValue(Data); *IsSetPointer = false; }` —— 已设置才析构，并顺手把状态置回未设置（与本类既有的 `Reset()`（`:72-75`）**同一 API**，家法先例 ✓）。

### 3.3 🔴 新登记 `F-LEAK-016`：optional 的 owned 分配少算 set 标志（P1 候选 / **未修**）

**现状（代码事实，HEAD）**

```cpp
// Source/UnrealCSharp/Private/Reflection/Optional/FOptionalHelper.cpp:21（改前=改后，本轮未动）
Data = FMemory::Malloc(ValuePropertyDescriptor->GetSize(), ValuePropertyDescriptor->GetMinAlignment());

InOptionalProperty->InitializeValueInternal(Data);        // ← 这一句就会写 set 标志
```

**引擎契约（E10-E13）**：可选值的**值在偏移 0**、**set 标志在 `Data + ValueProperty->GetSize()`**（`CalcIsSetOffset()`），总尺寸是 `Align(CalcIsSetOffset() + 1, ValueProperty->GetMinAlignment())`（`CalcSize()`）；`FOptionalProperty::HasIntrusiveUnsetOptionalState()` **恒为 false**（`PropertyOptional.cpp:67-71`）⇒ 所有 `TOptional<T>` 都走"值 + 标志"布局。

**问题**：插件只分配 `valueSize` ⇒ `InitializeValueInternal`（`:435-444` 的 `*GetIsSetPointer(Data) = false;`）在**构造期**就写越界 1 字节（对齐到 4/8 时最多 4/8 字节）。**实测（探针，已移除）**：一轮套件 **7 次**命中，`TOptional<int>` `allocSize=4 / requiredSize=8`、`TOptional<FString>` `allocSize=16 / requiredSize=24`。**为什么没炸**：UE 的 binned 分配器按 16 字节粒度给块，1 字节越界落在同一桶内 ⇒ 目前表现为**静默**（这正是本库"静默失败最不可接受"的一类）。

**正确修法（未施工，留给下一轮）**：按引擎公式自己算（**不能**用 `OptionalProperty->GetSize()`：`SetValueProperty` 只赋值不算尺寸、插件这两个构造点都没有 link ⇒ `ElementSize` 不可靠，E13）：

```cpp
Data = FMemory::Malloc(Align(ValuePropertyDescriptor->GetSize() + 1, ValuePropertyDescriptor->GetMinAlignment()),
                       ValuePropertyDescriptor->GetMinAlignment());
```

**为什么不并入本轮**：它是**另一个面**（分配尺寸 vs 释放语义），需要自己的前提核查（4 个 owned 构造点的 `std::decay_t<T>` 尺寸是否与 `FOptionalProperty` 的 `CalcSize()` 一致、对齐取谁）+ 探针 + 改前/改后对照；本轮只登记证据与修法，**不动代码**（不把一个未验证的分配改动混进已验证的释放修复里）。

## 5. 改前 / 改后对照（**同一二进制**，`FLEAK012_NOFIX=1` 门控修复）

## 9. 复用价值（给下一轮）

1. **"清空 ≠ 销毁"是本库容器族的固定缺口形状**：`Empty()`/`Reset()` 早就析构，`Deinitialize()` 才是漏点。凡是"用户 `new` 出来的包装被释放"的路径，都必须走一遍"元素归谁 + 谁来析构"两问；本轮的判据表（容器 17 点 / 可选值 7 点）可直接复用。

5. **修"释放"的轮次必须同时核对"分配"**：本轮的 optional 半边就是"释放少析构 + 分配少几字节"两个面并存的例子（`F-LEAK-012` 与 `F-LEAK-016`）——只修释放会让越界写的现象继续静默存在。
