- 这 6 个点里 **4 个是 `void`**：能表达失败的只有"日志 / 异常 / 断言 / 新公开 API"**四选一**，全部撞 Q2。

- 第 6 点的"漏产物"是**唯一有真实危害**的一条，但它的危害面需要"托管侧抛异常"才会打开 —— 当前语料 **0 命中**（B-16 的触发条件即此）。

### 2.3 选项

| 选项 | 动作 | 代价 | 判据 | 风险 |
|---|---|---|---|---|
| **A（推荐）** | **维持登记**，0 改动 | 0 | —— | 保持现状：异常 ⇒ 静默（4 处）／空数组（1 处）／半构造对象（1 处）。**触发条件已登记**（出现"托管异常导致漏产物/半构造"的实证） |

## 4. Q3 `F-ABI-035` 无同步半边：确认既有裁定，还是推翻？

### 4.1 事实面

```cpp
// FFunctionParamBufferAllocator.cpp（per-descriptor 池；每个 UFunction 一个实例）
void* Malloc()
{
	if (Buffers.IsValidIndex(Count)) { return Buffers[Count++]; }   // 读-判-写，非原子
	Count++;                                                        // 越界后继续涨
	const auto Buffer = FMemory::Malloc(ParamSize, 16); … Buffers.Add(Buffer);
	return Buffer;
}
void Free(void* InMemory)
{
	if (Buffers.IsValidIndex(Count - 1) && Buffers[Count - 1] == InMemory) { Count--; }
}
```

- **回绕半／配对半已在轮 B-19 修掉**（`uint8` → `int32`；`Free` 只在栈顶匹配时回退）；**剩下的只有"无同步"**。
- 现状：`Malloc`/`Free` 无锁、`Count` 无原子、`Buffers`（`TArray`）本身也非线程安全 ⇒ **同一描述符被两个线程同时调用**时才会坏。
- **已有裁定**：⚫ **2026-10-14 维护者裁定「不加锁」**，并发半边按"**已知且接受**"读、保留编号与事实结论、登记触发条件 = 出现"跨线程并发调用同一描述符"的实证。
- 本轮**未取得**任何新的并发证据（B-34/B-35 的会话都是单线程 `-game`）。

### 4.2 若要加锁：三个选项都只能"半解"

| 选项 | 做法 | 为什么是半解 |
|---|---|---|
| B | `Count` 改 `std::atomic<int32>` ＋ CAS 循环 | `Buffers.Add` 仍非线程安全 ⇒ 仍需锁住整个池 ⇒ 等于 A 的反面 |
| C | 每线程独立池（TLS） | 跨线程 `Free` 会落错池 ⇒ 需要"池归属"记录（额外内存/复杂度） |
| D | 拒绝跨线程（`check(IsInGameThread())`） | 撞 Q2（`check` = 断言/日志面） |
| **A（推荐）** | **确认不加锁**（既有裁定不变） | —— |

### 4.3 推荐

**A（确认 2026-10-14 的裁定）**。补充一条**代价表述**供回执引用：热路径（每次托管→原生调用一对 `Malloc`/`Free`）加锁会把"per-descriptor 争用"升级为"全局争用"，而 [`F-PERF-024`](../09-问题清单/05-已完成（P2与P3）.md) 的裁定方向是"**已有的锁都不去动、不要再加新的**"。

> **回执问题**：Q3 = A（确认）/ B / C / D？

## 5. Q4 `F-DEF-010` 修法：A 维持 / B 生成期 skip / C 编译期诊断 / D = C+B

### 5.1 事实面（轮 B-34 已取）

- **当前行为**：C# 子类写 `[UFunction] public override void SealedFunction()` ⇒ 生成期 `FDynamicGeneratorCore::GeneratorFunction()`（`:1086-1150`）**无条件** `NewObject<UFunction>` ＋ `AddFunctionToFunctionMap`（`:1092`/`:1145`），**不查父类同名函数是否 `FUNC_Final`** ⇒ 子类自有函数**遮蔽**父类 final 函数（A/B 实测 `Owner` 翻转子类）。
- **对照 UHT**：原生侧由 UHT 在**编译期**把 `SealedEvent` 翻成 `FUNC_Final`（`UhtFunctionParser.cs:432`）＋ 两条诊断（`UhtFunction.cs:1057-1065`）；**C# 动态类没有编译期这一层**。
- **插件里 `FUNC_Final` 的唯一真实消费面** = `FCSharpBind.cpp:298-302` 的"C# 覆写候选表"过滤 ⇒ 生成期不查 final，就等于只在**绑定期**少一个候选，**不影响遮蔽本身**。

### 5.2 🟢 方案 B 的**探针实测**（本轮真跑的读数，已还原）

探针 = 在 `GeneratorFunction()` 的 `if (Method->IsUFunction())` 之后插入：

```cpp
if (const auto SuperClass = InClass->GetSuperClass(); SuperClass != nullptr)
{
    if (const auto SuperFunction = SuperClass->FindFunctionByName(
            FName(Method->GetName()), EIncludeSuperFlag::ExcludeSuper);
        SuperFunction != nullptr && SuperFunction->HasAnyFunctionFlags(FUNC_Final))
    {
        // B35-PROBE
        continue;
    }
}
```

| 读数 | 基线（无 skip，交付态） | 探针（有 skip） |
|---|---|---|
| 套件行数 | **1961** | **1961** |
| 失败数 | **0** | **2** |
| 失败项 | —— | **正好 2 条**：`BatchCSealedEventForcedChildHasOwnSealedFunction` / `…SealedFunctionOwner`（＝"子类自有函数存在"的那两条） |
| **附带回归** | —— | **0**（`Compare-Object` 对两份 CSV 只报 **4 行**差异 = 2 条判据的两侧 ⇒ **其余 1958 条判据逐条相同**） |
| CSV SHA256 | `409C050E5482A11D89FBE2F0AE45F123A3C9E9E40C64B153AB19BF7303F08F19` | `5CB4278F…`（2 红态） |

⇒ **B 方案：可行、精确、零附带回归**；唯一问题是**静默**（子类方法被无声丢弃，与"没写 `[UFunction]`"不可区分）。

### 5.3 四个选项

| 选项 | 动作 | 改动面 | 失败是否可见 | 判据 | 风险 |
|---|---|---|---|---|---|
| A | **维持登记**（不施工） | 0 | 🔴 否（遮蔽继续发生） | —— | 语义与 UHT 不一致；但**运行期无断言**（引擎侧检索无 `FUNC_Final` 运行期检查）⇒ 后果 = BP/VM 调用解析到子类函数 |
| **B** | **生成期 skip**（探针已验证） | 插件 **1 文件（10 行代码 ＋ 1 空行）**（`FDynamicGeneratorCore.cpp`） | 🔴 否（静默丢弃） | ✅ **已有**：B-34 的 2 条 forced-child 判据**正好翻红**（＝修复生效）＋ 其余 1958 条零变化 | 静默；但与"没标 `[UFunction]`"的既有行为**同形**，可解释 |
| **C（推荐）** | **源生成器编译期诊断**（`UC_ERROR_0N`：子类 `override` 带 `[UFunction]` 且基类同名方法带 `[SealedEvent]` ⇒ 报错） | 插件 `Script/SourceGenerator`（`UC_ERROR_0N` 通道，**Q2 白名单内**） | 🟢 **是**（编译失败，与 UHT 对齐） | ✅ 可做：Roslyn driver 电池 A/B（照 [`08-…/67`](67-轮B27收口-源生成器不抛半边与CodeAnalysis构建闸门（2026-10-15）.md) 的 22 例手法） | 只覆盖"基类也在同一编译里"（C#-declared `[SealedEvent]`）；基类来自其它程序集时不覆盖（但那种基类的 final 来自 C++ UHT，C# 侧本来就无 `[UFunction]` 可覆写） |

> **回执问题**：Q4 = A / B / C / D（若选 C，可顺便回"是否需要 B 作为兜底"）。

## 8. 复用价值

1. **"卡裁定"的行要先做一次出口穷举**：Q1 的 6 个点里有 4 个是 `void` ⇒ "开口与否"其实是"要不要新增失败面"，不是"要不要修 bug"。
2. **"有出口" ≠ "能施工"**：Q1 的第 1 点有既有出口（`InvalidManagedHandle`），但**判据无法构造**（需要一个抛异常的托管构造器，而它会在更早阶段失败）⇒ 在"修法必须先 A/B"的纪律下只能不施工。
3. **探针可以先于裁定**：Q4 的 B 方案在**拍板前**就跑出了"正好 2 条翻转、0 附带回归"的读数 ⇒ 裁定页不必停在纸面推演。
4. **半解要写出来**：Q3 的 B/C 都能被一句"`Buffers` 本身非线程安全"打回原形 —— 裁定页里把"为什么加锁也解决不了"写清，比只写"不加锁"更有说服力。
