## 1. 结论摘要（先读这一节）

1. ✅ **`F-CS2A-012` = `F-PERF-001` 已修**：`TSet<T>::GetEnumerator()` 与 `IEnumerable.GetEnumerator()` 的循环上界由**元素数** `Num()` 改为**桶槽上界** `GetMaxIndex()`，并把非泛型枚举器收敛为 `return GetEnumerator();`（与同目录 `TMap.cs:40-43` 逐字同形）。修法与 [`06-…/02a`](../06-CSharp运行时与脚本/02a-容器与指针包装（资源所有权）.md) 的建议一致，只是**未采纳"把 `GetMaxIndex()` 提到循环外"**（理由见 §3.1，与 `TMap` 的既有形态对齐优先）。
2. 🆕 **新增永久回归判据 2 条**（`SetGetEnumeratorSparseCount` / `SetGetEnumeratorSparseEnumerableCount`）：`Add` 128 → `Remove` 前 60 → `foreach` 计数必须等于 68。改前 **2/2 失败**、改后 **2/2 通过**，两条分别覆盖**泛型**与**非泛型**枚举器。
3. 🔴 **本轮最重要的产出是否掉一条修法**：库内 G10 行给出的"改用引擎哈希入口（`FScriptMapHelper::FindValueFromHash` / `FScriptSetHelper::FindElementIndexFromHash`）"**不能直接施工**。原因是一条被库内任何报告都没记过的**实参语义不对称**：
   - C# 侧对**引用类型**的键/元素写入缓冲的是 **`HandleData.GetHandle(...)` 托管句柄**（`TMap.cs:260-267`、`TSet.cs:72-79`/`:116-124`）；
   - 插件的 **21 个 compound 描述符**正是按"**B 参数是句柄**"实现 `Identical` 的（`FStrPropertyDescriptor.cpp:49-58`、`FObjectPropertyDescriptor.cpp:29-37`、`FStructPropertyDescriptor.cpp:58-67` …）；
   - 但 **`GetValueTypeHash` 全插件只有一处实现、且不做句柄解析**（`FPropertyDescriptor.inl:85-93`）；
   - 而引擎的哈希入口**恰恰对"查找值"取哈希**（`Set.h:1965-1973` → `:1944-1962`；`Map.h:1992` 的引擎原注释 *"We 'know' that the implementation of Find doesn't call GetKeyHash on anything except Key"*）。
   ⇒ 对 `TSet<FString>` / `TSet<UObject>` / `TMap<FName, …>` 这类容器，按原建议改会**算错桶**（`FName`/`FObject` 是读到垃圾值后落错桶 ⇒ **静默漏命中**；`FStr`/`FStruct`/`FOptional` 会**解引用句柄当指针** ⇒ 可能直接崩）。**本轮已用临时探针在运行期观察到该分支的崩溃**（2/2 复现，`coreclr.dll @ 0x3584ff`；移除该分支后 1/1 通过），详见 §8.2。
4. 🟢 **量化已完成**（这正是 §5 第 3 条"收益未量化仍开放"缺的那一环）：1024 元素容器上，**未命中查找 = 1 024 次 `Identical`/次**、命中按位置 64/128/256/512 次；**构建 1024 元素 = 524 800 次哈希调用**（每次插入全表 `Rehash`）⇒ 查找 O(N)、构建 O(N²)。
5. ⏸️ **`F-HLP-016` / `F-HLP-024` 不动**（P2 / 潜伏，`01-…/07` §10.1 的重判已确认"无可达构造点"）。**不采纳"把 `ScriptMapLayout`/`ScriptSetLayout` 零初始化"**：它把"未初始化 ⇒ 早崩"改成"零 layout ⇒ 静默写坏"，与本库"静默失败最不可接受"的判据相反；边界与"将来出现可传空属性的构造点必须三处同改"记入 §3.3。

⇒ 对引用类型键，`GetKeyHash(查找缓冲)` 会把**句柄当原生值**哈希：`FName`（`PropertyName.cpp:111` `GetTypeHash(*(const FName*)Src)`）与 `FObject`（`PropertyObject.cpp:390` `GetTypeHash(GetPropertyValue(Src))`）读到的是垃圾值 ⇒ **落错桶 ⇒ 静默漏命中**；`FStr`/`FStruct`/`FOptional` 走的是**解引用**（`FStructProperty` → `Struct->GetStructTypeHash(Src)`，`PropertyStruct.cpp:160`）⇒ 把句柄整数当指针用，**可能直接崩**。同一处还需**交换相等谓词实参序**（插件全线是 `Identical(存储值, 查找值)`）。

**结论与处置**：本条**不是"改哪几个函数"的问题，而是"要先补一层只读的句柄→原生值解析契约"**（`Identical` 已经各自实现了它，但没有暴露成"哈希可用"的入口）。**本轮不施工**，并把量化（§5）与三条可选设计（§10 第 2 条）留给独立轮次；`F-HLP-021`/`F-HLP-028`/`F-CS2A-010`/`F-PERF-007`/`F-PERF-008` 五条**维持 P2 / 活跃**，处置状态由"未量化"改为"**已量化、前提受阻、待裁定路线**"。

## 5. 量化（临时探针：扫描长度与插入 `Rehash` 代价；探针已移除）

**装置**：在 `FSetHelper` / `FMapHelper` 的**全部线性扫描点**（`Add`/`Remove`/`Contains`；`Get`/`Set`/`Remove`）挂计数器 —— 每次查找累计"`Identical` 调用次数"（= 扫描长度）、每次 `Rehash` 的 lambda 调用次数（= 哈希调用数）、插入次数；并打印扫描长度落在 64/128/256/512/1024 的样本行与每 1024 次查找的汇总行。**驱动用例**（临时，交付前删除）：`TSet<int>` 插入 0..1023 → `Contains` 命中 512 次（键 0..511）→ `Contains` 未命中 512 次（键 100000..100511）→ `Remove(600)`；`TMap<int,int>` 插入 0..1023 → 索引器读取 512 次。

**实测（`-game` 全量套件，`out/G10-probe3/G10-probe3-r01.log`）**

| 观测 | Set | Map |
|---|---|---|
| 插入期扫描长度 vs 元素数 | `num=65 scan=64`、`129/128`、`257/256`、`513/512` | `num=65 scan=64`、`129/128`、`257/256`、`513/512` |
| 查找期（`num=1024`）命中扫描长度 | 64 / 128 / 256 / 512（按键位置） | 64 / 128 / 256 / 512 |
| **查找期（`num=1024`）未命中扫描长度** | **1 024**（连续 10 条样本行 `num=1024 scan=1024`） | 同型（`Get` 未命中 1 024） |
| 累计（lookups=1 024 时） | 94 411 次比较 / avg 92.20 / max 394；inserts 818；**rehashHashCalls 94 980** | 219 819 / avg 214.67 / max 662；inserts 840；**rehashHashCalls 220 387** |
| 累计（lookups=2 048 时，Set 侧） | 618 582 / avg 302.04 / **max 1 023**；inserts 1 447；**rehashHashCalls 541 570** | — |

**读法（三条可复核结论）**

1. **查找是 O(N)**：1024 元素集合的一次**未命中** = **1 024** 次 `Identical`（命中按位置线性分布 64→1024）。⇒ `F-HLP-021`/`028`/`F-PERF-007`/`008`/`F-CS2A-010` 描述的"O(MaxIndex) 线性扫描"实测成立，且**未命中是最坏情形**。
2. **构建是 O(N²)**：`rehashHashCalls` 与"Σ1..N"同量级 —— 1024 元素构建理论值 **524 800**，实测总累计 **541 570**（含套件其余小容器，占比 ≈ 97% 来自这 1024 次插入）⇒ 每次插入都重建整张哈希表（E2）。
3. **收益上界（推算，非实测）**：若哈希路径可用，同一批操作的比较次数应从 ~1024/次降到"冲突链长度 ≈ 1"量级 ⇒ 单点收益 **~10²–10³ 倍**；**但该收益本轮不可兑现**（§3.2 的前提受阻）。

**探针副作用（如实登记）**：带"描述符内省 + 把查找缓冲喂给 `GetValueTypeHash`"的第一版探针**两次运行均在 `coreclr.dll @ 0x3584ff` 崩溃**（`0xC0000005`；Windows 事件日志 20:51:03 与 20:52:20 两条；`Faulting module path = …/Microsoft.NETCore.App/10.0.4/coreclr.dll`）；**去掉该分支（仅保留计数与扫描长度日志）后 1/1 通过**，精简单最终形态 2 次 `-game` 全绿。⇒ 崩溃点落在"**把查找缓冲当原生值做哈希/属性内省**"这一段（该分支含 3 个调用：`IsPrimitiveProperty()`、`GetProperty()->GetClass()->GetName()`、`GetValueTypeHash(…)`；**未逐调用分测**，见 §9）。

## 10. 复用价值（给下一轮）

1. **"查找缓冲 ≠ 原生值"是本库容器族的第一道判据**。凡是要给 `FMapHelper`/`FSetHelper`（以及任何以 `FPropertyDescriptor` 为谓词的路径）**换查找策略**的改动，必须先回答："谓词的 B 参数是裸值还是**托管句柄**？" —— 判据现成：`TPrimitivePropertyDescriptor`（`IsPrimitiveProperty() == true`，12 个 primitive/enum）是裸值，**21 个 compound 覆写 `Identical` 的族**都是句柄。
2. **哈希半边的三条可选路线（供裁定，均已带前置条件）**：
   - **路线 A（全族可用，成本最高）**：新增一个"句柄感知哈希"虚入口（例如 `virtual uint32 GetKeyHash(const void* InKey)`，默认实现为 `GetValueTypeHash`），在 21 个 compound 族里按各自 `Identical` 的解析方式实现（字符串/对象走注册表解析，结构体/Optional 先取原生地址）。⇒ 可全族走哈希；**前置** = 解析必须是**只读且不新建句柄**（否则用例会反向制造 `F-CS2A-024` 那类泄漏），并逐族验证"哈希相等 ⇔ `Identical` 为真"。
   - **路线 B（最小改动，收益只覆盖数值键）**：以 `IsPrimitiveProperty()` 门控 —— 为真时走 `FindElementIndexFromHash`/`FindValueFromHash`，为假时保持线性扫描。⇒ 语义等价（裸值两侧同源）、改动面小；**收益窄**（`FName`/`FString`/`UObject` 键仍 O(N)）。**前置** = 一条"容器已哈希"的一致性判据，因为该路线一旦前提被破坏，失败形态是**静默漏命中**（本库最忌讳）。
   - **路线 C（不推荐）**：在查找入口先把句柄解析成临时原生值再哈希 ⇒ 需要临时存储与析构（`FString`/`FStruct` 都要构造一次），**成本高于线性扫描的常见规模**，且引入新的生命周期面。
   - 无论哪条：**相等谓词实参序必须交换**（引擎是 `(查找值, 存储值)`，插件全线是 `(存储值, 查找值)`）；且**插入路径的语义要与 `TScriptSet::Add` 的覆写语义对照**（E7）。
3. **"先量化再施工"这条库内规则本轮跑通了闭环**：量化结果（1024 次比较/次、524 800 次哈希调用/1024 插入）足以支撑排期判断，而前提核查**同时**发现该修法不可用 ⇒ 若当初直接照建议施工，会得到"性能变好一点、但字符串/对象键容器开始静默漏命中（甚至崩溃）"的**净负结果**。
4. **临时探针的失败也是一等证据**：把查找缓冲喂给 `GetValueTypeHash` 的分支在真实数据上 2/2 崩溃 —— 这类"探针自己崩"的现象，本身就是"该 API 契约不适用于该输入"的活体证据；但**必须**先做归因实验（带/不带该分支的通过率对照），否则会被误读成环境 flake。
5. **日志不是崩溃定位手段**：本机 `-game` 装置在 CSV 出现后强杀进程，归档日志只能保留到某个 flush 点（成功/失败运行分别恒为 1 102 / 1 076 行）⇒ 定位必须靠**产物（CSV）+ 事件日志 + 归因实验**三件套。
