### 1.3 `AddToRoot` 的配对情况（比"容器不清"更要紧）

| 生成器 | `AddToRoot` | `RemoveFromRoot` |
|---|---|---|
| Class | `:404`（`NewObject<UClass>` 后）、`:430`（`UBlueprint`） | `:544`／`:557`（替换路径）、`:910`（ComponentTemplate） |
| Struct | `:255` | `:388`（替换路径） |
| **Enum** | `:203` | **0** |
| **Interface** | `:270` | **0** |

⇒ **动态 UEnum / UInterface 对象一旦创建就永久 Root**；Class/Struct 只在"同名替换"时才解 Root。

### 1.4 没有任何全局清理入口

- 全仓 `FDynamic{Class,Enum,Interface,Struct}Generator::(Reset|Deinitialize|Shutdown)` 在**施工前命中 0**（改造后即本条落地的 4 个 `Reset()`）。
- 域卸载只做反射侧：三个后端都只调 `FReflectionRegistry::Get().Deinitialize();`
  （`FCoreCLRDomain.cpp:264`、`FLeanCLRDomain.cpp:827`、`FMonoDomain.cpp:326`），**不触碰生成器**。
- `FReflectionRegistry::Deinitialize()` 自身也只 `Field2Class.Empty()` ＋ `delete FClassReflection` ＋ `FullName2Class.Empty()`。

### 1.5 关键修正：**同名重注册是"复用"而不是"新建"**

`FDynamicEnumGenerator::Generator()`（`:68-120`）：若 `DynamicEnumMap.Contains(ClassName)` 命中，则**复用同一个 `UEnum*`** 再 `GeneratorEnum(...)` 重注册；接口生成器同构。⇒

- "每次生成都新增一条"**不成立**：同名类型不会增长；
- 真正会累积的是 **① 改名/删除类型（旧名条目与旧对象永久保留）**、**② 域重载后条目不清（跨 PIE 会话保留）**；
- 且因为对象被 `AddToRoot`，**GC 不会回收**它们 ⇒ 既不是"悬垂 key"，也不是"对象被 GC 后串对象"，而是**永久驻留**（原文的"泄漏"方向要按此修正）。

## 2. 影响面（为什么仍值 P2）

1. **进程级只增不减**：编辑器长会话里反复改 C# 动态枚举/接口名，旧对象 + 旧 map 条目永久驻留；`UEnum`/`UClass` 不是轻量对象（含 FName、元数据、CDO 相关）。
2. **跨域不归零**：`UnloadAssembly()` 之后 map 仍在，下一次域初始化会把这些**上一代对象**当作"已存在"复用（`DynamicEnumMap.Contains`）⇒ 行为上"旧类型残留"，而非干净重建。
3. **没有可观测性**：既不统计也不上报（G7 也禁止随手加日志）⇒ 只能靠外部内存快照发现。

## 3. 方案

### 方案 A：四个生成器各加 `static void Reset()`，由 `FDynamicGenerator::Reset()` 统一暴露（已落地）

```cpp
// 四个生成器（FDynamicClass / Enum / Interface / Struct）各加一个静态入口
static void Reset();

// 实现：release 动态对象 + 清空该生成器的全部静态容器
void FDynamicClassGenerator::Reset()
{
	for (const auto Class : DynamicClassSet)
	{
		if (Class != nullptr)
		{
#if WITH_EDITOR
			if (const auto BlueprintGeneratedClass = Cast<UBlueprintGeneratedClass>(Class))
			{
				if (const auto Blueprint = Cast<UBlueprint>(BlueprintGeneratedClass->ClassGeneratedBy))
				{
					Blueprint->RemoveFromRoot();

					Blueprint->MarkAsGarbage();
				}
			}
#endif
			Class->RemoveFromRoot();

			Class->MarkAsGarbage();
		}
	}

	DynamicClassSet.Empty();
	DynamicClassMap.Empty();
	NamespaceMap.Empty();
	DefaultSubObjectInfoMap.Empty();
	DefaultValueMap.Empty();
	ClassConstructorSet.Empty();
}
```

```cpp
// 统一入口（Public/Dynamic/FDynamicGenerator.h/.cpp）
void FDynamicGenerator::Reset()
{
	FDynamicClassGenerator::Reset();

	FDynamicInterfaceGenerator::Reset();

	FDynamicStructGenerator::Reset();

	FDynamicEnumGenerator::Reset();
}
```

调用点（3 个后端各 1 行，紧跟现有反射清理）：

```cpp
FReflectionRegistry::Get().Deinitialize();

FDynamicGenerator::Reset();
```

- **成本**：5 头 ＋ 5 cpp ≈ **+128/−0 行**；3 个后端各 ＋3 行（1 个 include ＋ 1 个调用）。
- **优点**：与"对象被 Root"的既有事实对齐（必须先 unroot 才能回收）；清理点与域生命周期绑定，语义清楚；入口收敛在已有的 `FDynamicGenerator` 门面上，三后端不必各拿 4 个头。
- **风险**：`RemoveFromRoot` + `MarkAsGarbage` 之后，若仍有 `FClassReflection`/`UClass*` 外部引用（如编辑器资产、已生成的 C# 代理缓存）会变成悬垂 ⇒ **必须先确认"域已卸载、无外部持有"**（现有清理顺序：反射先删，再清生成器，符合）。
- **G7**：4 个生成器类虽头在 `Public/Dynamic/` 但**无 `UNREALCSHARPCORE_API` 导出宏**，维护者裁定**不计入公开面**；统一的 `FDynamicGenerator::Reset()` 落在带 `UNREALCSHARPCORE_API` 的门面上，是**唯一的新增导出方法**，按例外记录。

### 方案 B：只在 `FReflectionRegistry::Deinitialize()` 里收口（1 个调用点）

同模块内可直接调用四个 `Reset()`，把"反射 + 动态生成"的清理收在一个入口。
- **优点**：只改 1 处调用点；三个后端零改动。
- **缺点**：语义越界（反射注册表去清生成器）；若将来出现"只重建反射不重建生成器"的路径，会误清。

### 方案 C：不加方法，改在 `FDynamicGenerator::Generator()` 开头清（**不可行**）

生成器按名复用（§1.5），每次 `Generator()` 都新建会导致**每次生成都重建全部动态类型**（CDO/Blueprint 重建开销 + 引用失效）⇒ 排除。

### 方案 D：只清 map，不 unroot（**不彻底**）

对象仍被 Root ⇒ 只回收了 map 的内存（几 KB），对象本体仍驻留 ⇒ 不解决 §2-1。

### 方案 E：契约（0 代码，**不推荐**）

登记"进程内只增不减、跨域不归零"，不修。代价：长会话下不可控；触发重估条件见 §5。

## 5. 维护者裁定与清理时机

1. **G7 口径（已裁定）**：这 4 个类"头在 `Public/` 但无导出宏" —— 维护者裁定**不计入公开面**，方案 A 可以施工；统一入口 `FDynamicGenerator::Reset()` 落在带 `UNREALCSHARPCORE_API` 的门面上，作为**唯一的新增导出方法**按例外记录。
2. **清理时机**：域卸载时清（方案 A/B）**是唯一合理时机**吗？另一种是"编辑器每次 Generator 前做差集清理"（能清"改名遗留"但清不掉"跨域"）—— 需产品口径：**动态类型改名后，旧类型是否应该立刻消失**。
