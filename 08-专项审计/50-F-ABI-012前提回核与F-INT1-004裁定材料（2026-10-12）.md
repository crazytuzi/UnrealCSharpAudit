## 1. `F-ABI-012` 逐条核实

### 1.0 先说一条前提更正（影响该怎么读这一条）

审计原文把可达性记为 **潜伏**、理由是"`FCoreCLRFunctionLibrary.cpp` 在 `#if WITH_CORECLR` 内；**当前 `WITH_CORECLR=0`**"。该前提**已被 2026-10-08 的环境事实更正推翻**（当前配置 `Windows/Linux/Mac → CoreCLR`、`Android/iOS → Mono`、LeanCLR 未启用）⇒ 本条**不是**"未参编的代码"，而是**活后端上的真代码**。本轮据此把它当**活跃项**核 —— 也正因为它活着，才有可能拿到下面的**实物证据**（打包版真跑过）。

### 1.2 断言②：`LIB_HOSTFXR` 无 `#else`

- **代码事实成立**：`Macro.h:85-91` 的 `#if/#elif` 链没有 `#else`（全文仅 7 行，见 §1.1(a)）。

## 2. `F-INT1-004` 裁定材料

### 2.1 现状（代码事实）

```cpp
// Source/UnrealCSharpCore/Public/CoreMacro/BufferMacro.h:1-29（全文）
#define IN_BUFFER InBuffer
#define IN_BUFFER_SIGNATURE uint8* IN_BUFFER          // ← 无长度
#define OUT_BUFFER OutBuffer
#define OUT_BUFFER_SIGNATURE uint8* OUT_BUFFER        // ← 无长度
#define RETURN_BUFFER ReturnBuffer
#define RETURN_BUFFER_SIGNATURE uint8* RETURN_BUFFER  // ← 无长度
#define IN_KEY_BUFFER InKeyBuffer
#define IN_KEY_BUFFER_SIGNATURE uint8* IN_KEY_BUFFER
#define IN_VALUE_BUFFER InValueBuffer
#define IN_VALUE_BUFFER_SIGNATURE uint8* IN_VALUE_BUFFER
```
- **原生侧**：4 个属性实现全部是"无长度"形态 —— `FRegisterProperty.cpp:10-24`（`GetObjectPropertyImplementation`）、`:26-42`（`Set`）、`:44-57`（`GetStruct`）、`:59-…`（`SetStruct`）。
- **C# 侧**：手写包装同样是裸指针 —— `Script/UE/Library/FPropertyImplementation.cs:7`：`private static unsafe partial void __FProperty_GetObjectPropertyImplementation(nint InObject, uint InPropertyHash, byte* ReturnBuffer);`（`__` 实现体由织入器填充）。
- **调用方自定大小**（生成产物，例）：`Script/UE/Proxy/UnrealEd/Classes/ThumbnailRendering/ThumbnailRenderingInfo.cs:161-165` —— `var ReturnBuffer = stackalloc byte[1];` → `FPropertyImplementation.FProperty_GetStructPropertyImplementation(…, ReturnBuffer);` → `return *(bool*)ReturnBuffer;`。
- **织入器按"方法名"定位这 4 个实现**：`Script/Weavers/UnrealTypeWeaver.cs:1137-1151`（`definition.GetType("Script.Library.FPropertyImplementation").Methods.FirstOrDefault(Method => Method.Name == "FProperty_Get…")`）⇒ **改签名会连带改织入器的名字表与 C# 声明**。
- **两侧都没有协议/版本常量**：全库只有 `DOTNET_MAJOR/MINOR/PATCH_VERSION`（`CoreCLR.Build.cs:19-24` 注入）与 .NET 自动生成的 `AssemblyInfo` 版本 ⇒ 想"比对版本"必须**先新增一个版本源**（见 §2.4 路线 B）。

### 2.2 影响面（实测计数）

| 面 | 计数 | 口径 |
|---|---|---|
| 跨边界缓冲签名宏 | **5 个**（IN/OUT/RETURN/KEY/VALUE），**均无长度参数** | `BufferMacro.h` 全文 |
| 原生侧 `*_SIGNATURE` 使用点 | **215**（IN 77／OUT 51／RETURN 65／KEY 7／VALUE 15） | `Source/**`（`*.cpp/*.h/*.inl`）grep |
| 产品侧调用这 4 个属性导出的文件 | **8 925 / 16 230** | `Script/UE/Proxy` + `Script/Game/Proxy` 全量扫描 |
| 产品侧调用点 | **87 670**（Get/Set×Object/Struct 各 22 953／20 882／22 953／20 882） | 同上 |
| 织入器需同步 | 4 个按名查找（外加同类 `_genericCall*` 等查找同族） | `UnrealTypeWeaver.cs:1137-1151` |
| 生成器需同步 | 发射缓冲大小与解引用类型的模板 | `FGeneratorCore::GetBufferSize` / `GetReturn` |

### 2.3 触发条件（决定该不该修）

- 盲写的**必要前提**是"**C# 程序集的生成知识 与 原生二进制的属性布局不一致**"：缓冲大小 = 生成器按 `Property->GetElementSize()`（或非原生取 `sizeof(void*)`）算出的 `N`，写入 = 原生描述符按**同一个属性**拷贝 `N` 字节 ⇒ **同一次生成内 `N ≡ N′`**，不越界。审计自评也写"**仅"栈溢出后果"仍依赖 C# 程序集与 C++ 二进制版本错配**"。
- 现有闸门（都在轮 A/B-1/B-2 建立）：`IsScriptPublishOutdated()`（发布时效性 → 触发重编）＋ `IsAssembliesFileExists()`（缺件 fail-closed）。
- **Live Coding 不构成触发**：它只能改函数体、不能改 `UPROPERTY` 布局；改布局必须整体重编重启，而启动闸会重跑生成/发布。
- ⇒ 真实的错配来源是**人工混装**（把旧 `Content/Script/*.dll` 拷进新构建、或更新插件而不重新生成），不是流水线内的正常路径。

### 2.4 三条路线对照（＋一条收窄变体）

| 路线 | 改什么 | 成本（本轮实测） | 收益 | 风险 / 需要谁拍板 |
|---|---|---|---|---|
| **A 全量加长度** | 5 个缓冲宏 → 加 `uint32 Size`；**215** 处原生签名点；4 个属性实现；C# 手写包装；织入器名单；生成器发射端；**8 925 个产物文件重生成** | 极大（跨模块机械改动 + 全量产物 + 织入器同步，且**必须与产物同轮**，否则新旧混装更糟） | 把"盲写"变成"**有界写**"（可钳制/拒绝） | 一轮巨大的机械改动；口径上还要决定"越界时怎么办"（拒绝？截断？）⇒ **需维护者拍板** |
| **A′ 只改属性路径** | 仅 4 个属性实现 + `FPropertyImplementation.cs` + 织入器 4 处；**产物仍需全量重生成**（8 925 文件里都是这些调用） | 大（省下容器/字符串/委托那 ~211 个签名点，但产物面**不省**） | 覆盖"最现实的发生面"（属性缓冲与元素尺寸的耦合） | 与 A 同为破坏性 ABI 变更；同样需先定"越界语义" |
| **B 加载期互锁** | 新增**版本源**（原生 vs C# 各一份）+ 加载时比对 + fail-closed 分支 | 中（不碰 ABI、产物零变化；但要新增协议常量与守卫） | 把"静默损坏"换成"**可检测**" | ① 现有代码**没有**可用的版本源 ⇒ 得先造；② 编辑器外的对比（打包件里时间戳同源）**不可靠**；③ 失败态 = **C# 完全不可用**，属口径裁定（是否允许 fail-closed 到不可用） |
| **C 维持现状**（＋登记触发条件） | 无 | 0 | 保留 P2 定级与全部事实、把触发条件写清 | 触发需"人工混装"；判据无法在套件里构造（构造它等于人为制造错配）⇒ 收益是"记账准确"而非"消除风险" |

**我方推荐：C**。三条理由：① 触发前提是版本错配，而正常流水线**不产生**错配（生成→编译→发布三件事同源，且有启动期时效性闸门）；② A/A′ 的代价与收益不成比例 —— **215 个签名点 + 8 925 个产物文件**换一个"只能在人工混装时才发生"的越界防护，而且 ABI 一改就**必须**全量重生成，任何漏改都会把"潜在越界"变成"确定不兼容"；③ B 的失败态是"C# 整体不可用"，比"极端情况下越界"更伤可用性，且要先造版本源 ⇒ 属于**策略选择**而非纯技术修复。
**如果维护者要求收**：建议按 **A′ + 明确的越界语义**（例如"尺寸不符即不写、按默认值返回"）一起做，并且**与产物重生成同轮**；B 只在"编辑器内自检"这一窄用途下值得考虑。

## 4. 复用价值（方法论）

1. **"加载器 ↔ 打包配方"要成对读**：只看 `Macro.h` 会得出"名字硬编码"；把 `CoreCLR.Build.cs` 的 `RuntimeDependencies` 一起读，才发现两侧是**同一份三分支约定**。凡"路径/文件名假设"类条目，**必须把 stage 侧一起核**。
2. **两个后端不能合并叙述**：本条把 CoreCLR 的"动态加载"套到 Mono 上就错了 —— Mono 在本仓是**静态链接**（`mono_jit_init` + `mono_aot_register_module` + `dllmap → __Internal`）。凡"加载/解析"类断言，先看该后端**有没有解析这一步**。
3. **有打包产物时，"能不能跑"是可以直接查的**：`Package/**/Saved/*.csv` 里那份 **1701 行 / 0 失败**的 CoreCLR CSV，比任何推演都硬 —— 它同时证明了 hostfxr 找到、域起来、套件执行。
4. **托管后缀不要按"原生库"读**：`.dll` 对 IL 程序集在所有平台都正确；判"后缀硬编码"前先把使用点分类（本仓 9 处全是程序集）。
5. **影响面要先数再谈修法**：`F-INT1-004` 的"改 ABI"在直觉上是"加个参数"，实测是 **215 处签名 + 8 925 个产物文件 / 87 670 调用点** —— 这个数字本身就是裁定材料的主体。
