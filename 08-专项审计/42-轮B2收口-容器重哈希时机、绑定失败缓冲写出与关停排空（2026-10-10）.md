## 2. `F-HLP-022` 残留面（＋ 🆕 `F-HLP-031`）：对已析构键求哈希

### 2.1 机制与引擎依据

`bNeedRehash` 机制（`152b5681` 的"延迟重建"）本身没有问题：插入侧不再全表 `Rehash`，改置 `bNeedRehash = true`；`EnsureRehash()` 是**唯一**的清标志点，且**只**在 `Remove` 里被调用。问题在**它被放的位置**：

```cpp
// 改前（FSetHelper.cpp:176-182 / FMapHelper.cpp:164-172 同形）
	const auto Data = ...->GetData(ValueIndex, ScriptSetLayout);
	ElementPropertyDescriptor->DestroyValue(Data);   // ← 先把元素值析构掉
	EnsureRehash();                                  // ← 再全表 Rehash：对"刚被析构的键"调 GetValueTypeHash
	ScriptSet->RemoveAt(ValueIndex, ScriptSetLayout);
```

引擎侧依据（两面都读过原文）：

| 结论 | 依据 |
|---|---|
| `Rehash` 会遍历**所有 `IsValidIndex` 元素**并调 `GetKeyHash`、**回写**元素内的 `HashIndex` | `Set.h:1899-1941`（`:1920` `IsValidIndex` 判定、`:1927` `uint32 KeyHash = GetKeyHash(Element);`、`:1929` `GetHashIndexRef(Element, Layout) = KeyHash & (HashSize - 1);`） |
| `RemoveAt` **不重算哈希**，只读元素内的 `HashIndex` 摘链 ⇒ 它要求"哈希数组与元素内的 `HashIndex` 一致" | `Set.h:1867-1881`（`:1874` `GetTypedHash(GetHashIndexRef(ElementBeingRemoved, Layout))`） |
| `AddUninitialized` 的注释即官方口径："The set will need rehashing at some point after this call to make it valid." | `Set.h:1887-1897` |

⇒ **`Rehash` 是承重调用（必须发生在 `RemoveAt` 之前），但它同时要求被哈希的元素值仍然存活**。改前的顺序**同时**满足"在 `RemoveAt` 之前"却违反了"值仍存活"——这正是 2026-10-08 对抗复核抓到的残留面（其原话："把全表 Rehash 挪到了删除路径、且放在两次 `DestroyValue` 之后，新增了『对已析构键求哈希』"；"两次 `DestroyValue`"即 `Map` 侧）。

**🆕 `F-HLP-031`（本轮新登记）**：`FMapHelper::Remove` 是**同一处代码的同点同缺陷**（`FMapHelper.cpp:166-172`，key 与 value 各一次 `DestroyValue` 之后才 `EnsureRehash`），此前**没有任何编号登记过它**（台账与 `01-…/07` 均无该行）。⇒ 本轮按库内"新登记不新造机制"的做法补一个编号：**`F-HLP-031`**（类别：未定义行为／内存；严重度 **P2**；可达性 **活跃**；与 `F-HLP-022` 同源同点，建议合并引用）。

### 2.5 为什么这个顺序是承重的（供后续引用）

`Rehash` 与 `RemoveAt` 之间存在一条**双向**约束：`RemoveAt` 需要 `Rehash` **已经跑过**（否则元素内 `HashIndex` 是陈旧的、摘链会走错桶），而 `Rehash` 需要元素值**还没被析构**（否则读已释放的 `FString` 缓冲／`UObject*` 句柄内存）。唯一同时满足两者的位置 = **`DestroyValue` 之前、`RemoveAt` 之前**，也就是本轮落地的位置。
