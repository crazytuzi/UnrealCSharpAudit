两个线程角色：**调用 `Send` 的托管线程**（finalizer / `Task.Run` / 任何用户线程，`ThreadId` 不匹配分支）与**游戏线程**（`Tick` → `Process` → `TaskInfo.Invoke`）。

3. T2：下一帧游戏线程 `Tick` → `Process` → `Task.Invoke()` → `finally { WaitHandle?.Set(); }` **抛 `ObjectDisposedException`**。
4. T3：异常从 `Process` 冒泡到 `Tick`；`Tick` 是 `[UnmanagedCallersOnly]` → 运行时终止进程（编辑器/游戏直接崩，且无 C# 栈可查）。
5. 即使不 Dispose，`Send` 也**从不调用 `WaitOne()`**（`:77-90` 无等待语句），因此「同步 Send」在语义上退化为「异步 Post」，调用方在回调尚未执行时就继续执行 → 见 F-CONC-013。

`FCSharpCompiler::Get()` 的局部静态（`FCSharpCompiler.cpp:29-34`）在首次使用时构造并起线程（`:10`）；析构发生在模块卸载 / 进程静态析构（游戏线程）。`Stop()` 只被 `FRunnableThreadWin::Kill` 调用（引擎侧 `MicrosoftRunnableThread.h:85-88`）。

**问题**
两个线程角色：**游戏线程**（析构 → `Thread->Kill(true)` → `WaitForSingleObject`）、**编译线程**（`Compile()` 内 `WaitUntilTaskCompletes`，等待一个 `ENamedThreads::GameThread` 任务）。
具体交错序列：
1. T0：文件监视器触发编译，编译线程进入 `Compile()` 并在 `SyncProcess`（`FUnrealCSharpFunctionLibrary.cpp:1569-1574` 的 `Sleep(0.01f)` 忙等）里执行 dotnet build（可能数十秒）。
2. T1：编译成功，编译线程在 `:213` 把任务投到**游戏线程队列**，并在 `:242` 阻塞等待（非命名线程 → `TaskGraph.cpp:1509` 的 `FScopedEvent` 纯阻塞，**不会**执行游戏线程任务）。
3. T2：与此同时游戏线程进入模块卸载/退出 → `~FCSharpCompiler` → `Thread->Kill(true)`：先 `Runnable->Stop()`（只置 `bIsStopped`，不打断 build），再 `WaitForSingleObject(Thread, INFINITE)` **阻塞在游戏线程上**。
4. T3：双方互等且都不可能推进——游戏线程被阻塞在 `WaitForSingleObject`，无法回到消息/任务循环去执行 `:213` 投递的任务；编译线程等不到该任务就不会返回 → `Run()` 不退出 → `WaitForSingleObject` 永不返回 → **编辑器/进程挂死（只能杀进程）**。
5. 次级问题（同一处代码）：`Stop()` 不取消进行中的 `SyncProcess`，因此即使没有任务等待，游戏线程也会在 `Kill(true)` 里被阻塞到整个 dotnet build 结束（关闭编辑器要等几十秒）。

**建议**
1. 让 `Compile()` 具备取消能力：给 `FCSharpCompilerRunnable` 增加 `std::atomic<bool> bCancelCompile`，在 `SyncProcess` 的轮询循环里检查（需要给 `SyncProcess` 增加 `TFunction<bool()> InShouldCancel` 参数，`FUnrealCSharpFunctionLibrary.cpp:1569` 的 `while` 条件里判断后 `TerminateProc`）。
2. 把「等待游戏线程任务」改为**有超时**，或改为不阻塞退出：`FTaskGraphInterface::Get().WaitUntilTaskCompletes` 无超时版本，可改用 `FFunctionGraphTask::CreateAndDispatchWhenReady(..., ENamedThreads::GameThread)` 后不等待（把后续状态清理放进任务内），或把整个收尾逻辑改成 `AsyncTask(GameThread, ...)` 而不阻塞。
3. 在 `Stop()` 里设置标志后，`Run()` 的循环条件与 `SyncProcess` 检查点都要看该标志；并在 `~FCSharpCompiler` 里先 `Stop()` 后 `Kill(true)`（当前 `Kill` 内部会调 `Stop`，但显式一点更清楚），同时避免在游戏线程上做无限等待。

```cpp
{

    return false;
```

权衡：不等待会让「重载脚本域」的任务在模块已卸载后执行 → 需在任务内继续保留 `GExitPurge` 与 `UnrealCSharpCoreModule.IsLoaded()` 双重检查（`:223` 已有 `IsLoaded()`），并捕获 `this` 的生命周期问题（见 F-CONC-011）。

4. T3：这一切发生在**未提交的事务栈内**（`FScopedTransaction` 尚未析构、`GUndo` 尚未 StoreUndo），且发生在 `FScopedSlowTask` 对话框的 `EnterProgressFrame` 之间（`UnrealCSharpEditor.cpp:386-388`）。任何在域卸载期间处于「已注册但未失效」的 C# 对象（例如当前蓝图的脚本对象、`HandleData` 表中仍被 UI 持有的句柄）都会悬垂；事务随后回滚/提交时再访问这些对象 → 崩溃或引用错乱。
5. 另一条同类路径：PIE 启动时游戏线程在 `WaitForCompile` 的 `while` 内（`:744`）自泵队列，收尾任务在此被内联执行 → 脚本域在 `OnPreBeginPIE` 中途被卸载重建，而 `FEngineListener::OnPreBeginPIE`（`FEditorListener.cpp:218`）**尚未执行**。
6. 需注意的现实约束（已核实）：因为等待者是命名线程且引擎会自泵/内联执行，这里**不会**造成死锁；风险是重入与生命周期，而不是挂起。

**建议**
1. 让 `ImmediatelyCompile` 走「异步编译 + 显式等待/或延后重载」，不要在调用者栈上重载脚本域：把 `Deactivate/InFunction/Activate` 投递成**普通队列任务**（`FTSTicker` 下一帧 / `AsyncTask` 而非图任务的等待式收尾），让重载发生在引擎循环的稳定点（例如 `FCoreDelegates::OnEndFrame`），而不是事务 Apply / SlowTask 帧内。
2. 如果必须同步，至少在重载前后加状态保护与断言：
```cpp
checkf(!GUndo || GUndo->GetUndoCount() == 0 /* 或在事务外 */, TEXT("Reloading script domain inside a transaction"));
```
更实际的做法是让 `FDeleteFileChange::Apply/Revert` 只请求编译（`FCSharpCompiler::Get().Compile()`）并把文件删除/写回也延迟到事务提交后。
3. 在 `Compile()` 的收尾任务里加 `if (bIsPIEPlaying) { MarkOutdated(); return; }`（配合 F-CONC-007），避免在 PIE 运行期重载域。
权衡：改为异步会让「删除文件 → 立即可见新状态」的交互有一个延迟；可用进度通知（已有 `FSlateNotificationManager` 逻辑）弥补。

```cpp
    }
```

**问题**
两个线程角色：**调用 `Send` 的非游戏线程**（期望同步返回）与**游戏线程**（`Tick` → `Process` 才真正执行回调）。
具体交错序列：
1. T0：一个非游戏线程调用 `Send(cb, state)`（`ThreadId` 不匹配分支）→ 把回调塞进 `TaskList`，随即 `Send` **返回**。
2. T1：调用方按 `Send` 的契约认为 `cb` 已执行完毕，继续执行后续逻辑（例如断言/依赖回调写好的状态）。
3. T2：真正执行要等到游戏线程下一帧 `Tick`（`:26-30`）。若在这之前调用方读取了「应当已被回调更新」的数据，就读到旧值；若调用方拿它做同步栅栏（例如等待一次初始化完成），则语义完全失效。
4. 叠加 F-CONC-002：这一延迟执行最终会因已 Dispose 的 `ManualResetEvent` 抛异常并终止进程——即「不等待」不仅语义错，还把异常留给了后续帧。

**建议**
```csharp

    lock (TaskList) { TaskList.Add(new TaskInfo { CallBack = InCallback, State = InState, WaitHandle = ResetEvent }); }
    ResetEvent.WaitOne();      // 补齐 Send 的同步语义
```

权衡：`WaitOne()` 有死锁风险（若调用者其实在游戏线程但 `ThreadId` 判断失效——`ThreadId` 是非 volatile 的普通 `int`，`:92`，见下）；因此建议 `ThreadId` 与 `Context` 一起做成 `private static volatile`/只读字段，`Initialize()` 后不再变更。

**验证方式**
- grep `Send(` / `override void Send`（仅 `SynchronizationContext.cs:68` 一处定义，`Script/` 内无调用点）。
- 单测：非游戏线程调用 `Send(cb, null)`，紧接断言 `cb` 的副作用已生效 → 必然失败。

2. T1：Windows 的 SEH→`signal` 机制在该线程上调用 `SignalHandler`；处理器内 `FDomain::GetTraceback()` 进入托管运行时并**再次分配内存**（`StringToFString`、`GCHandle_Free`）→ 若内存分配器/日志锁正被崩溃线程自身持有 → **在信号处理器内自死锁**（崩溃报告永远不会输出，进程悬挂）。
3. `GLog->Flush()`（`:26`）会取日志锁并做 I/O：I/O 在信号处理上下文中不是异步信号安全操作；若另一线程正持锁 → 再次死锁。
4. 若托管运行时自身已处于不一致状态（例如崩溃就发生在托管代码里），`Runtime_Invoke` 可能再次触发异常/信号 → 递归处理器。
5. 附带：`signal()` 安装的处理器在 Windows 上语义与 POSIX 不同，且 `SIGFPE/SIGSEGV` 下这样做会干扰引擎自身的崩溃处理（UE 有独立的 crash handler；此处覆盖会改变崩溃行为）。

**建议**
1. 处理器内只做异步信号安全操作：设置 `volatile sig_atomic_t` 标志或写入预分配的环形缓冲，把真正的日志/托管调用留给后续的正常流程（例如下一次 Tick 时检测标志）。
2. 至少要避免进入托管运行时：把 `FDomain::GetTraceback()` 从处理器中移除（可改为记录「托管栈不可用」并 `return`）。
3. 若目的是「崩溃时打印 C# 栈」，应改成注册 UE 的崩溃回调（`FPlatformMisc::SetCrashHandler`/`FCoreDelegates` 的崩溃上报），那是在受控上下文中执行。
4. 加锁保护：`SignalHandler` 中不要调用 `GLog->Flush()`（`UE_LOG` 本身已有缓冲）。
权衡：完全去掉托管栈打印会损失诊断信息；建议只在「非致命信号」（SIGINT/SIGTERM）路径保留，致命信号（SIGSEGV/SIGABRT）改为安全路径。

**验证方式**
- grep `signal(` / `SignalHandler`（`FCSharpEnvironment.cpp:22/127/140`）、`GetTraceback`（`FDomain.cpp:112`、`UnrealCSharp.cpp` 无）。
- 用例：制造一次崩溃（`check(false)` 前的 `*(int*)0 = 0`）观察是否出现卡死而非崩溃窗口；或对进程发 `SIGINT`/`Ctrl+Break` 观察是否挂起。

- **级别变动**: 无（P3 维持）

**现状（代码事实）**
```cpp
// :279（CompileInterop 内）与 :384（Compile 内）
		static auto CompileTool = FUnrealCSharpFunctionLibrary::GetDotNet();
```

**问题**
两个线程角色：**编译线程**（首次调用时执行该函数内静态的动态初始化，MSVC 会插入线程安全守卫与一次加锁）+ **游戏线程**（同一函数理论上也可能被调用——`Compile()` 可被 `ImmediatelyCompile` 在游戏线程直接调用，见 `FCSharpCompiler.cpp:44-50`）。
具体交错序列：游戏线程若抢先执行到该语句，则 `CompileTool` 在游戏线程上初始化（保存的是**当次**的 dotnet 路径快照）；此后即使插件设置里改了 dotnet 路径也不会重新读取——两个线程谁先到谁定值，行为不确定（结合 F-CONC-008 的 CDO 访问问题）。此外，把「读取 UObject 设置」藏进 `static` 初始化器使得真正的问题点更难被发现（调用点看起来只是一次局部静态取用）。

**建议**
- 把 `CompileTool` 提到 `Compile()`/`CompileInterop()` 的参数里（由游戏线程在入队时采集，见 F-CONC-008 的快照建议），或改为非静态局部变量（每次重新读取，代价可忽略：一次 `FString` 拷贝/一次 build 调用）。
- 若确需缓存，缓存应放在 `FUnrealCSharpEditorSetting` 变更时失效的位置（例如 `PostEditChangeProperty` 里清缓存）。

**验证方式**: grep `CompileTool`（`FCSharpCompilerRunnable.cpp:279/291/384/413`、`FCodeAnalysis.cpp:41`）。

#### [F-CONC-024] `FLeanCLRDomain::MethodInvokePaths` 无锁 `TMap`（并发 Invoke / Free / Empty）

- **类别**: 并发/线程安全

- **复核证据**: grep `MethodInvokePaths` 命中 5 处：`Source/UnrealCSharpCore/Public/Domain/LeanCLR/FLeanCLRDomain.h:209`（声明，`TMap<IManagedHandle, TTuple<const leanclr::metadata::RtMethodInfo*, bool>>`）、`Private/Domain/LeanCLR/FLeanCLRDomain.cpp:141`（`Remove`）、`:157`（`Find`）、`:171`（`Add`）、`:831`（`Empty`）——与原文 4 个 cpp 行号完全一致
- **级别变动**: 无（P3 维持）

**现状（代码事实）**
```cpp

	TMap<IManagedHandle, TTuple<const leanclr::metadata::RtMethodInfo*, bool>> MethodInvokePaths;
```

```cpp
			MethodInvokePaths.Remove(InManagedHandle);
```

**问题**
两个线程角色：**执行托管调用的线程**（`Invoke` → `Find`/`Add`）与**执行 `Free`/域卸载的线程**（`Remove`/`Empty`）。

**建议**: 与 `MethodInvokePaths` 相关的读写在入口做线程门禁（`check(IsInGameThread())`），或加 `FCriticalSection`；卸载时先清标志再 `Empty()` 并把在该表上工作的调用挡在门外。

**验证方式**: grep `MethodInvokePaths`（`FLeanCLRDomain.h:209`、`.cpp:141/157/171/831`）；在 `Invoke` 内临时加 `check(IsInGameThread())` 跑 LeanCLR 后端的 PIE 用例。

### 6.1 未发现问题（附 grep 证据，避免"没查"与"没问题"混淆）

- **N-1 资产注册表回调不在非游戏线程**：`FEditorListener.cpp:79/344-350` 与 `ClassCollector.cpp:53-57` 注册的 `OnFilesLoaded/OnAssetAdded/OnAssetRemoved/OnAssetRenamed/OnAssetUpdatedOnDisk` 处理器未做任何线程切换，但其回调线程有引擎保证。引擎证据：`Engine/Source/Runtime/AssetRegistry/Private/AssetRegistry.cpp:85-88`「FEventContext also handles deferring events to the Tick function executed from the GameThread, as we have a **contract that events are only called from the game thread**」，以及 `:4735` `checkf(IsInGameThread(), TEXT("The tick function executes deferred loads and events and must be on the game thread to do so."))`、`:5206-5211`「Finishing the gather is only possible on the game thread」。**结论：这些处理器中直接做 UObject 操作（`FAssetGenerator::Generator`）是安全的**，不构成跨线程 UObject 访问缺陷。
