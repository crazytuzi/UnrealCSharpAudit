### 2.1 `F-REG-001`：先按值拷出句柄，再删表


* **外层由 `IsValid()` 改为 `Address != nullptr`**：`Deinitialize` 遍历时同样受益（每条都释放），且与 `TOwnedValue::Free()` 的门禁（`bNeedFree`）正交。
* **`Deinitialize` 无需改动**：其 `Value.Free()` 与本改动**同时**覆盖"类型有效"与"类型失效、地址仍在"两种形态。
* ⚠️ **未触发的分支**：探针显示"反向映射不匹配"与"结构体类型已 GC"**在本装置中 0 命中** ⇒ 本条的**收益未量化**，只有编译与静态证据（§6 给出触发用例设计）。

## 7. 复核轮（2026-09-24，同轮追加）：维护者复核 + 一处同类缺陷的处置

> **起因**：维护者复核 §2 的改动时提出两点 —— ① `NotifyUObjectDeleted` 的 `Cast` 应直接写进 `if`；② 要求把其余改动一并复核。
> **改动面 = 净 +2/−2**（`FCSharpEnvironment.cpp` 少 2 行、`FStructRegistry.cpp` 换 2 行），**不改变任何语义**，但**②带出一条真缺陷**。

### 7.1 ✅ 采纳：`Cast` 收进 `if`（`FCSharpEnvironment.cpp`）

```cpp
// 改后（与该项目原有写法同形；变量只在块内使用）
		if (const auto InStruct = Cast<UStruct>(InObject))
		{
			RemoveClassDescriptor(InStruct);
		}
```

* `Cast<UStruct>` 返回 `UStruct*`、`RemoveClassDescriptor` 取 `const UStruct*` ⇒ if-init 里推成 `UStruct* const`，隐式加 const 合法；**原有写法本来就是 `if (const auto InStruct = …)`** ⇒ 回到本项目既有形状。

### 7.2 🔴 采纳维护者的另一种修法：把 `FCSharpEnvironment::RemoveReference` **挪到 map 删除之后**

* **问题**：§2.4 把 `FCSharpEnvironment::RemoveReference(InManagedHandle)` 提为**无条件**执行后，该调用**可以重入本函数**，重入链每一跳已落实：
  `本函数` → `FCSharpEnvironment::RemoveReference` → `FReferenceRegistry::RemoveReference`（只清该 handle 名下的引用对象）→ `delete FStructReference` → `FStructReference.h:14` → `FCSharpEnvironment::RemoveStructReference` → **回到本函数** → 走到 `ManagedHandle2StructAddress.Remove(InManagedHandle)`。
  ⇒ **`Find` 得到的 `FoundValue` 变悬垂**，外层再读 `FoundValue->Value` / `FoundValue->Address` 就是**同一类「指针指向 `TMap` 元素、却在 map 变动后继续使用」的失效读**（即 F-REG-001 的根因形态）。
* **owner 来源分析（本轮新增，用于判断重入条件是否可能成立）**：`FStructReference` 的全部内容就是**一个 `ManagedHandle`**（`FStructReference.h:6-16`），由 `FStructRegistry.cpp:111-112` 的 `new FStructReference(InManagedHandle)` 创建 ⇒ 它持的是**被引用者**的句柄；owner 由 `FStructPropertyDescriptor.cpp:79-83` 的 `GeManagedHandle(InAddress, Property)` 求得：
  * 属性属于 `UObject` ⇒ owner = 宿主 UObject 句柄（`FCSharpEnvironment.cpp:589-591`），**不可能**等于结构体句柄；
  * 属性属于 `UScriptStruct` ⇒ owner = **外层**结构体实例的句柄（`:595-596`），与内层不同，**除非同一 `(类型, 地址)` 被先后注册出两个句柄**（模板版与 4 参数版混用、或句柄回收后复用）。
  ⇒ **命中同 key 需要比较刁钻的注册序列，本轮不能声称它是常态**；这也与审计库把 `F-REG-005` 重入链列为"必须实机验证、未取得"的口径一致。
* **最终改法（B，维护者选定）= 把该调用挪到函数末尾**，而不是取副本：
  ```cpp
  		FoundValue->Free();

  		ManagedHandle2StructAddress.Remove(InManagedHandle);

  		(void)FCSharpEnvironment::GetEnvironment().RemoveReference(InManagedHandle);
  ```
  * **外层悬垂**：调用之后**没有任何代码**再碰 `FoundValue` ⇒ **结构上不可能**（比"取副本"更强）。
  * **重入**：重入方 `ManagedHandle2StructAddress.Find(InManagedHandle)` **直接落空**（条目已删）⇒ 整段不执行、**`GCHandle_Free` 恰好一次**。（对比"取副本"方案：重入方仍能命中条目，于是它会再跑一次 `Free()` 与 `Remove`，`GCHandle_Free` 变成两次。）
  * **与同族一致**：`FStringRegistry.inl:77-81`、`FContainerRegistry.inl`、`FDelegateRegistry.inl` 都是"**先删表、后释放**"；B 让本函数与它们同序。
  * **顺序前提已核**：`GCHandle_Free` 仍在 `Remove` 之前（= §2.4 的原始裁定与报告伪代码同序），**未开新窗口**；且引擎自身拆容器也是"先析构值、再收容器"（`PropertyArray.cpp:1188-1195` 的 `EmptyValues` → `DestroyContainer_Unsafe`）。
  * ✅ **"顺序变化会不会让终结器重排"的验证**：C# 侧 `UStruct_UnRegisterImplementation` 是**纯直通**（`Script/UE/Library/StructImplementation.cs:46-49`，函数体只有一行 `__UStruct_UnRegisterImplementation(InObject);`），且全插件树 **`ReRegisterForFinalize` / `SuppressFinalize` / `GC.KeepAlive` 命中 0** ⇒ 换序**不会**把正在执行的终结器重新排队、也不会提前复活包装。
* ⚠️ **A/B 取舍留痕（A = 先取副本，曾短暂实装）**：A 也能消除外层的悬垂读，但**重入仍能命中条目** ⇒ 只能把"读已释放元素"降级，不能消除重入路径本身；且它需要 `auto StructAddress = *FoundValue;` 的副本（**必须用 `auto` 不能 `const auto`** —— `TMap::Find` 返回 `const ValueType*`，而 `TOwnedValue::Free()` 非 const ⇒ 实测报 **C2662**）。⇒ **B 在结构上更强且改动更小，故最终采用 B**。
* ⚠️ **仍未实测**：该重入路径**是否真实发生**（需"同一 `(类型,地址)` 先后注册出两个句柄"的用例）。本轮的结论是"**重入发生时不再有内存不安全，且语义收敛为恰好一次的释放**"，**不是**"证明了重入会发生"。重入本身的语义归属仍属 `F-REG-005`（P2，未实测）。
