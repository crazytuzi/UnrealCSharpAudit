# 设计页 `F-DOM-007` —— Mono 域的初始化幂等与内存释放（2026-11-02）

> 分析范围：`F-DOM-007`（P2 · S=2.15 · 潜伏）—— 「Mono 的域与已加载映像永不释放，且 `Initialize()` 缺少另两个后端都有的重入守卫」
> 状态：设计完成，**未施工**（结论：**幂等守卫可做（方案 B），域释放走契约不施工（方案 C）**；本轮 0 代码）

## 1. 代码事实（回 HEAD（B-211 交付）复核）

| 事实 | 读数 |
|---|---|
| Mono `Initialize()` | `FMonoDomain.cpp:49` 起；**函数体内没有任何 `bIsInitialized`**（全量 grep 确认），JIT 初始化被 `if (Domain == nullptr)` 包住 |
| CoreCLR 的守卫 | `FCoreCLRDomain.cpp:37` `if (bIsInitialized) { return; }`，成功后 `:128` `bIsInitialized = true;` |
| LeanCLR 的守卫 | `FLeanCLRDomain.cpp:41` 同形，成功后 `:86` 置真 |
| **Mono 的 `bIsInitialized` 语义不同** | 它在 `LoadAssembly()` 里赋值：`:309` `bIsInitialized = IsAssembliesFileExists(InAssemblies);` ⇒ **含义是"程序集文件在不在"，不是"初始化成功"** |
| Mono `Deinitialize()` | `:177-187`：`if (!bIsInitialized) return; bIsInitialized = false; UnloadAssembly();` —— **没有 `mono_jit_cleanup`、没有 `mono_domain_unload`** |
| `Initialize()` 调用点 | 仅 **2 处**：`FDomain.cpp:33`、`FScriptDomainScope.h:27` |
| `FScriptDomainScope` 与 `IsInitialized()` | `if (!IsInitialized()) Initialize();` 然后 `if (IsInitialized()) InFunction();` —— **Mono 下这个判定跟着"程序集存在"走**，是既有行为 |

⇒ 两个子问题要分开处置：

1. **幂等**：重复 `Initialize()` 会重跑 `RegisterMonoTrace()` / `RegisterAssemblyPreloadHook()`（在 `if (Domain == nullptr)` **之外**）；JIT 段被 `Domain == nullptr` 挡住，所以危害是"重复注册"，不是重复建域。
2. **释放**：域与映像确实从不释放（`Deinitialize` 只 `UnloadAssembly`）。

## 2. 方案（幂等）

### 方案 A：照抄 CoreCLR 的 `if (bIsInitialized) return;`
**不可直接照抄**：Mono 的 flag 在 `LoadAssembly` 里由"程序集存在"赋值。若在 `Initialize()` 顶部加这个守卫，那么"程序集已存在但域尚未初始化"的首次调用会被**直接挡掉**（flag 初值为 `false`，只有在 `LoadAssembly` 里才会变真 —— 首轮不受影响；但一旦某次 `LoadAssembly` 把它置真而 `Deinitialize` 没复位，后续就会误挡）。

### 方案 B：专用幂等标志（推荐）
```cpp
// FMonoDomain.h
bool bIsInitializeDone{};

// FMonoDomain::Initialize()
if (bIsInitializeDone) { return; }
…原函数体…
bIsInitializeDone = true;

// FMonoDomain::Deinitialize()
…原有内容…
bIsInitializeDone = false;
```
- 代价：`+6/-0` 行（头文件 1、Initialize 2、Deinitialize 1）。
- 关键点：**不碰 `bIsInitialized`** ⇒ `IsInitialized()` 语义、`FScriptDomainScope` 的既有判定完全不变（这一点必须守住，否则会改动"程序集存在 ⇒ 视为可用"的既有约定）。
- 失败路径：若中途 `return`（域创建失败），不置 `bIsInitializeDone` ⇒ 下次调用重试（符合"失败可重试"的直觉）。

### 方案 C：把整个函数体包进 `if (Domain == nullptr)`
- 代价更小，但**语义更粗**：它把"重复注册"与"域已建"绑在一起，而 `RegisterMonoTrace()` 等是否幂等**没有证据**；且会改变"域已建时需要重跑装配"的潜在场景。⇒ 不推荐。

## 3. 方案（释放）

### 方案 D：`Deinitialize()` 里加 `mono_jit_cleanup` / `mono_domain_unload`
- 事实：`mono_jit_cleanup` 是**进程级**清理，会销毁整个 Mono 运行时（本插件还有 CoreCLR/LeanCLR 与 UE 侧托管对象投影，清理顺序无法保证）；`mono_domain_unload` 在 **iOS AOT/静态链接**（`PLATFORM_IOS` 分支已在用 `mono_jit_set_aot_mode` / `mono_aot_register_module`）上不可用。
- 结论：**不做**。加这行代码的失败模式是"编辑器卸载期崩溃"，比"不释放"严重得多。

### 方案 E（推荐）：契约 ＋ 触发条件
在契约页写明：
- Mono 的**域与已加载映像随进程生命周期**，`Deinitialize()` 只解除程序集引用（`UnloadAssembly`），不销毁域；
- 因此 **Mono 后端不支持"编辑器内反复重建脚本域"** 的语义，热重载路径应走进程重启；
- 触发重估的条件：① 出现"长时间编辑会话反复域重建 ⇒ 内存单调增长"的量化实证；② 上游 Mono 提供"安全卸载"的正式 API 且本插件支持区间内可用。

## 4. 判据与触发条件

- **判据（方案 B）**：编译通过；临时探针在 `Initialize()` 内计数，**连续调用两次只进入一次**；`mono_domain_create` 调用次数不变；套件 **1 992/0 同 SHA**（Mono 后端本机不参与编译 ⇒ 只能静态＋编译判据，**运行期判据登记为未取得**）。
- **风险**：Mono 后端**本机不参与编译**（`WITH_MONO 0`）⇒ 任何改动只能做到"静态审查 ＋ 与另外两个后端的同形对照"，不能实编。落地前必须声明这一点。
- **触发条件（升级到释放）**：见方案 E 的两条。

## 5. 残余

1. `IsInitialized()` 在三后端语义不一致（Mono = 程序集存在）—— 与 `F-DEF-003` 的契约条目共享，**不在本条修**。
2. 方案 B 只解决"重复注册"，不解决"域内程序集泄漏"（`UnloadAssembly` 是否真的卸干净未验证）。
3. Mono 的编译面缺口（`WITH_MONO 0`）意味着这条**永远只能静态验证**，这是它与 CoreCLR/LeanCLR 同类修复的根本差别。

## 6. 落地后的两处修正（2026-11-02）

方案 B 已落地（提交 `da0db161`），落地时修正两处：

| 项 | v1 | v2 |
|---|---|---|
| 标志名 | `bIsInitializeDone` | **`bIsInitializeCompleted`** —— 仓内布尔一律 `bIs*`/`bHas*`；`IsCompleted` 在 `FDynamicDependencyGraph::FNode::IsCompleted()` 已有先例。**不用 `bHasInitialized`**：与既有 `bIsInitialized`（语义 = "程序集存在"）只差一个词，最易混读 |
