## 2. 机理（代码事实）

```csharp
// 改前 SynchronizationContext.cs:64-79
private void Process()
{
    lock (TaskList)
    {
        PendingTaskList.AddRange(TaskList);   // 每帧把新任务叠加进来

        TaskList.Clear();
    }

    foreach (var Task in PendingTaskList)
    {
        Task.Invoke();                        // ← 任一任务抛异常即跳出
    }

    PendingTaskList.Clear();                  // ← 被跳过
}
```

```csharp
// TaskInfo.cs:14-24 —— 只有 try/finally（放行 WaitHandle），不吞异常
public void Invoke()
{
    try { CallBack?.Invoke(State); }
    finally { WaitHandle?.Set(); }
}
```

⇒ 异常一跳出 `foreach`，`PendingTaskList` 仍是整批任务（含**已执行过的**）。下一帧：`AddRange(TaskList)` 把新任务接到旧批后面，`foreach` 从头再跑 —— 已执行的重复执行、新任务永远排在抛异常那个任务后面（`task2` 一次都没执行）。本轮实测正是 `task1 ×2 / task2 ×0`。

**两条实际后果**：

1. **套件/真实游戏同一根因、两种表现**：本轮探针走的是套件路径（`TestSynchronizationContextTick` → `FFunction_GenericCall10Implementation` → `Tick`），异常最终被 `MethodBridge.Invoke` 的 catch 捕获并打印，测试函数中止 ⇒ **199 条用例丢失**；真实游戏里 `Tick` 由 native 直接调用，异常会穿出 `[UnmanagedCallersOnly]` ⇒ CoreCLR **fail-fast**（审计旧记录已用 `net10.0` 探针复现过 `TerminateProcess`、`try/catch` 无效、绕过 UE 崩溃上报）。
2. **队列单调膨胀**：每个"抛异常的任务"都会让整批在前面反复重放，`TaskList` 每帧还在追加。

## 3. 修法（E1(b) 授权）

```csharp
// 改后 :71-84
foreach (var Task in PendingTaskList)
{
    try
    {
        Task.Invoke();
    }
    catch (Exception)
    {
    }
}

PendingTaskList.Clear();          // 现在一定执行
```

- **E1(b) 判据**：`Process()` 是 `private`，**唯一调用方**是 `Tick()`（`[UnmanagedCallersOnly]` 边界入口，`SynchronizationContext.cs:52-56`）⇒ 命中 G7 例外白名单第二形态。
- **语义**：单个任务失败不再中止整批、不再重放；与 `Deinitialize()` 既有的 `catch (Exception) { }`（`:37-46`）同形。
- `Post` / `Send` / `TaskInfo.Invoke` 未改动。

## 5. 残余（不在本轮，条目转"部分修"）

1. **`Send` 的异常不回传**：跨线程 `Send` 的 callback 抛异常时，发送方在 `TaskInfo.Invoke` 的 `finally` 里被放行，但**拿不到异常**（.NET 契约要求 `Send` 把异常抛回调用方）。修法要在 `TaskInfo` 里保存异常、在 `Send` 侧 `ExceptionDispatchInfo.Throw()` —— **新增 throw 撞 G7**，需维护者裁定。
2. **`Send` 无超时**：若 `Tick` 不再运行（域非激活/关停中），跨线程 `Send` 会 `WaitOne()` 永久阻塞（与 `F-CS2B-011` 的排空面相邻）。
