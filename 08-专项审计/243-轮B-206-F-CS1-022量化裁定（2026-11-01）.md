## 1. 缺陷口径（原文与代码）

台账原文：「`TypeBridge.GetMethod` 只用『方法名 + 参数个数』匹配重载，且无缓存 → 同参数量重载静默选错」。

```csharp
// Script/Interop/Bridge/TypeBridge.cs:48-75（HEAD 为 B-205 交付树）
[UnmanagedCallersOnly(CallConvs = [typeof(CallConvCdecl)])]
public static unsafe nint GetMethod(nint InHandle, byte* InName, int InParamCount)
{
    …
    foreach (var Method in Type.GetMethods(BindingFlag))          // ← 每次调用重建数组
    {
        if (Method.Name == Name && Method.GetParameters().Length == InParamCount)
        {
            return HandleData.Alloc(Method);                       // ← 首个匹配即返回（静默选错）
        }
    }
    …
}
```

两半：**性能**（无缓存，每次 `GetMethods` + 线性 `GetParameters()`）× **正确性**（同参数量重载取首个）。

## 3. 调用链：为什么是 0

`TypeBridge.GetMethod`（托管）只被 `IScriptDomain::GetMethod` 的实现转发：

```cpp
// FScriptDomainImpl.inl:390-394
return IManagedHandleIsValid(InManagedClass) && TypeBridgeGetMethodFn != nullptr
       ? SCRIPT_DOMAIN_INVOKE(IManagedHandle, TypeBridgeGetMethodFn, InManagedClass, …) : 0;
```

而 `IScriptDomain::GetMethod` 在仓内的**唯一调用点**是：

```cpp
// FScriptDomainImpl.inl:426-445（SetPropertyValue）
const auto Name = FString::Printf(TEXT("%s%s"), *PROPERTY_SET_PREFIX, *InName);   // "set_<Name>"
if (const auto Method = GetMethod(Class, Name, 1); IManagedHandleIsValid(Method)) { Invoke(…); }
```

再往上一跳，`IScriptDomain::SetPropertyValue` 在仓内的**唯一调用点**是 `FPropertyReflection.cpp:45` —— 即 **C++ 反射按名写托管对象属性** 这条路径，属低频 API 面；`-game` 套件的属性写入走的是类型化描述符，不经过它。

⇒ **0 调用是结构性的，不是测量偶然**。

| 项 | 结论 |

| 性能半边 | 0 次/会话 ⇒ **0 ms**，远低于仓内「< 0.2 s/会话 或 < 1 %」门槛（先例：`F-PERF-011`/`003`/`017`/`026`/`027`/`013`/`DYN-009` 共 7 条） |
| 正确性半边 | 「同参数量重载静默选错」需要**该入口被调用**才可能发生；当前 0 调用 ⇒ **不可达** |

| 复测方式 | 复用本轮探针形状（`GetMethodCore` + 计数落盘），但**必须硬编码 `Enabled = true`** 以排除 env 传参假阴性 |

## 5. 边界（如实登记）

1. **只测了 `-game`**。`SetPropertyValue` 的消费方是 C++ 反射按名写，理论上编辑器工具/蓝图可能在编辑器会话里触发；本机编辑器会话未测（需 GUI 会话 + 探针注入）。⇒ 触发条件③ 就是为这一格留的。
2. **未测"同参数量重载是否存在"**。由于 0 调用，`ambiguousCalls` 无从取得；该问题属静态面（同族类型里是否存在 `(Name, ParamCount)` 相同的重载），若将来该路径启用，应先做一次静态排查再决定要不要改成"精确匹配参数类型"。
