## 1. 审计方法

本次审计为**横向（跨模块）专项**，围绕 4 类资源的"分配 ↔ 释放"配对进行。所使用的检索模式（grep 工具 + pwsh `Select-String`）：

**第 1 类 C++ 堆内存**
`new `、`delete`、`FMemory::Malloc`、`FMemory::Realloc`、`FMemory::Free`、`malloc(`、`calloc(`、`realloc(`、`free(`

**第 2 类 托管句柄与跨语言内存**
`GCHandle`、`.Alloc(`、`.Free()`、`mono_gchandle_new`、`mono_gchandle_free`、`mono_string_to_utf8`、`mono_free`、`mono_array_addr`、`Marshal.AllocHGlobal`、`Marshal.FreeHGlobal`、`Marshal.StringToHGlobal*`、`Marshal.PtrToString*`、`Marshal.GetFunctionPointerForDelegate`、`GetDelegateForFunctionPointer`

**第 3 类 OS 资源句柄**
`FPlatformProcess::CreateProc`、`FProcHandle`、`CloseProc`、`CreatePipe`、`ClosePipe`、`ReadPipe`、`GetDllHandle`、`FreeDllHandle`、`LoadLibrary`、`dlopen`、`dlclose`、`IFileManager`、`FileStream`、`StreamReader`、`StreamWriter`、`File.Open`、`MemoryMappedFile`、`File.ReadAllText`

**第 4 类 容器只增不减**
`TMap`、`TSet`、`TArray`、`Dictionary`、`HashSet` + `.Add(`、`.Emplace(`、`.TryAdd(` vs `.Remove(`、`.Empty()`、`.Reset()`、`.Clear()`

1. 任意一次 C++→C# 的 `FString`/`FName`/`FText`/`FUtf8String` 参数或返回值编组（例如 `Actor.GetName()`、`FString` 属性读写、`SetPropertyValue`）；

3. 该包装对象被 `HandleData.Handles` 强引用；
4. 之后只在 `FCSharpEnvironment::Deinitialize()`（模块卸载 / `FStringRegistry::Deinitialize`，`FStringRegistry.cpp:18-113`）时才被一次性清空。

量级：每次字符串编组 = 1 个托管对象 + 1 个 GCHandle + 1 个 native `FString`（含其 TArray 缓冲）+ 2 个 map 条目。在 Tick 中调用 `GetName()` 之类的接口，每帧泄漏一次；60fps 跑 10 分钟 ≈ 36000 次。`Handles` 是企业级强根集合，托管堆不会回收这些对象。

1. 最小改动：`HandleData.Alloc` 对**由 C++ 侧持有**的对象改用 `GCHandleType.Weak`（或 `WeakTrackResurrection`），仅在需要 pin 时用 Pinned；同时把 `HandleData.GetObject` 改为经 `WeakReference` 取目标。这样终结器可运行，`~FString()` 链路恢复。

3. 无论哪种，`FRegisterString::UnRegisterImplementation` 的 `AsyncTask(GameThread)` 需加兜底：引擎退出/`IsEngineExitRequested()` 时同步执行或统一交给 `FStringRegistry::Deinitialize`，否则任务可能永不执行（见 F-LEAK-004）。

**验证方式**
- grep：`RemoveStringReference` 在整个 `Source/` 只有 `FCSharpEnvironment.h:207`、`FCSharpEnvironment.inl:282`、`FRegisterString.cpp:38` 三处 → 证明释放入口唯一。

**问题**
`FScriptArray`/`FScriptMap`/`FScriptSet` 是**只有头部的 POD 描述结构**（分别保存 `Data`/`ArrayNum`/`ArrayMax` 等字段），元素内存是独立的一块分配，元素本身还可能各自持有堆（`FString` 的字符缓冲、嵌套 `TArray` 的 `Data`）。`delete ScriptArray` **并不是"只释放头部"**——`FScriptArray` 继承容器分配器基类，其析构会 `BaseMallocType::Free(Data)`（`ContainerAllocationPolicies.h:682-693`），所以**元素缓冲本身被回收**（"元素堆缓冲泄漏"已证伪）；真正泄漏的是**元素内层堆**：元素未被析构 → 元素各自持有的 `FString` 字符缓冲、嵌套 `TArray`/`TMap` 的 `Data`、结构体内的指针型字段全部泄漏（`FScriptMap`/`FScriptSet` 的对集缓冲同理被基类析构释放，漏的只是 Key/Value 的内层堆）；`FOptionalHelper` 同理：`FOptionalProperty` 的 `Data` 里若已 `MarkSet` 过一个 `FString`/`TArray`，`FMemory::Free(Data)` 会丢掉那个内层分配。

触发路径（很常见，且是"高频返回值"路径）：
1. C# 调用任意绑定函数，该函数在 C++ 侧返回 `TArray<FString>` / `TMap<FString, TArray<int32>>` / `TSet<FName>` / `TOptional<FString>`；
2. `FunctionMacro.h:128-144` 的 `RETURN_VALUE` 宏执行 `CopyValue()` 造出堆副本并交给 Helper；
3. C# 使用完毕（包装对象析构 / 所有者 UObject 死亡）→ Registry `delete` Helper → `delete ScriptArray`；
4. 元素缓冲 + 每个 `FString` 的字符缓冲泄漏，且这块内存**没有任何其它持有者**，永远无法回收。

量级：`TArray<FString>` 长度 N 时，一次调用泄漏 `N * sizeof(FString)` + 每个字符串的 `(len+1)*sizeof(TCHAR)`，再加上 `FScriptArray` 的元素缓冲。在 Tick / 逐帧调用的绑定函数上会线性增长。

**建议**
在各 Helper 的 `Deinitialize` 中，先按元素析构、再释放容器头。以数组为例：

```cpp
void FArrayHelper::Deinitialize()
{
    if (bNeedFreeData && ScriptArray != nullptr)
    {
        if (InnerPropertyDescriptor != nullptr && InnerPropertyDescriptor->GetProperty() != nullptr)
        {
            // 先逐元素 DestroyValue，再释放元素缓冲
            FScriptArrayHelper Helper = CreateHelperFormInnerProperty();
            for (int32 Index = Helper.Num() - 1; Index >= 0; --Index)
            {
                InnerPropertyDescriptor->DestroyValue(Helper.GetRawPtr(Index));
            }
            Helper.EmptyValues(0);      // 释放 Data 缓冲
        }

        FMemory::Free(ScriptArray);     // 头本身来自 CopyValue 的 FMemory::Malloc
        ScriptArray = nullptr;
    }
    ...
}
```
`FMapHelper` / `FSetHelper` 用 `FScriptMapHelper`/`FScriptSetHelper` 的 `EmptyValues` 等价处理；`FOptionalHelper` 用 `OptionalProperty->DestroyValueInternal(Data)`。
注意：当 `InData != nullptr` 且 `bNeedFreeData == false`（宿主内存，如 `FArrayPropertyDescriptor.cpp:39`）时**不得**做上述析构，避免破坏宿主对象——所以要把"数据来源"显式地区分成 `bNeedFreeData` 之外的一个枚举（例如 `EDataOwnership::{Borrowed, HeapCopy}`），现在的 bool 无法区分"堆副本"与"宿主内存"这两种 `bNeedFreeData=false/true` 组合。

**验证方式**
1. 写一个 C++ 绑定函数返回 `TArray<FString>`（长度 1000，元素为长字符串），C# 侧循环调用 1000 次后 `memreport -full` 对比 Tracked 内存；修复前后差值应在 GB 量级。

#### [F-LEAK-014] `SynchronizationContext` 的任务队列在任务抛异常时不清空（每帧累积 + 重复执行），且 `Send` 语义错误

- **类别**: 内存/资源泄漏（并含 并发/线程安全 与 句柄生命周期 问题）
- **严重度**: **P2**
- **复核结论**: ⚠️部分 —— 严重度 P2 维持；可达性 活跃
- **文件**: `Script/UE/CoreUObject/SynchronizationContext.cs:34-53,68-90`、`Script/UE/CoreUObject/TaskInfo.cs:6-22`
- **函数**: `SynchronizationContext::Process()` / `Post` / `Send` / `Tick`

**现状（代码事实）**

```csharp

List<TaskInfo> TaskList = new();
List<TaskInfo> PendingTaskList = new();

private void Process()
{
    lock (TaskList)
    {
        PendingTaskList.AddRange(TaskList);   // ← 叠加式入队
        TaskList.Clear();
    }

    foreach (var Task in PendingTaskList)
    {
        Task.Invoke();                        // ← 中途抛异常则直接跳出
    }

    PendingTaskList.Clear();                  // ← 被跳过 → 整个待处理列表留存
}
```
```csharp
// Script/UE/CoreUObject/SynchronizationContext.cs:68-90
public override void Send(SendOrPostCallback InCallback, object? InState)
{
    if (Thread.CurrentThread.ManagedThreadId == ThreadId) { InCallback(InState); return; }

    using var ResetEvent = new ManualResetEvent(false);   // ← 用 using，方法返回时即 Dispose

    lock (TaskList)
    {
        TaskList.Add(new TaskInfo { CallBack = InCallback, State = InState, WaitHandle = ResetEvent });
    }
    // ← 没有 ResetEvent.WaitOne()：Send 从不等待，语义上退化为 Post
}
```

**调用上下文**
`SynchronizationContext::Tick` 是 `[UnmanagedCallersOnly]`（`:26-30`），由 C++ 每帧调用：`FDomain::Tick`（`Source/UnrealCSharp/Private/Domain/FDomain.cpp:46-52`）→ `IScriptDomain::Tick` → `FScriptDomainImpl.inl:17-23` 的 `SynchronizationContextTickFn`。该函数指针在 `RegisterSynchronizationContextTick`（`FScriptDomainImpl.inl:636-649`）经 `TypeBridge.GetFunctionPointer` 取得（`TypeBridge.cs:92` `Method.MethodHandle.GetFunctionPointer()`）。

**问题**
1. **队列只增不减（异常路径）**：`PendingTaskList.Clear()` 在 `foreach` 之后、且没有 try/finally。任一任务的回调抛出异常，`Clear()` 被跳过，已执行与未执行的任务全部留在 `PendingTaskList`；下一帧 `Process()` 又把新的 `TaskList` 内容 `AddRange` 上去，形成"每帧把历史任务重放一遍"的雪崩：内存线性增长、回调重复执行（副作用叠加，例如重复派发事件）。触发路径：任意一帧中存在一个抛异常的 `Post` 回调。
2. **`Send` 不再是同步语义**：创建了 `ManualResetEvent` 却从不 `WaitOne()`，且用 `using` 在返回时 `Dispose`。于是 (a) 调用方以为已同步完成，实际是异步 → 竞态；(b) `TaskInfo.WaitHandle` 持有的是**已 Dispose 的**事件对象，任务执行时 `TaskInfo.cs:22` 的 `WaitHandle?.Set()` 会对已释放的句柄调用 `Set()` → `ObjectDisposedException`（该异常正是上面第 1 条"任务抛异常"的最可能来源，两者互相放大）。
3. `Tick` → `Process` → `Task.Invoke` 的异常会穿过 `[UnmanagedCallersOnly]` 边界（`SynchronizationContext.cs:29` `Context?.Process()` 无 try/catch）。托管异常跨 `UnmanagedCallersOnly` 边界在 .NET 8+ 行为是终止进程 → 也存在崩溃风险。

**建议**
```csharp
private void Process()
{
    lock (TaskList) { PendingTaskList.AddRange(TaskList); TaskList.Clear(); }

    try
    {
        foreach (var Task in PendingTaskList) { Task.Invoke(); }
    }
    catch (Exception Exception)
    {
        Console.Error.WriteLine(Exception);
    }
    finally
    {
        PendingTaskList.Clear();      // 无论成功失败都清空
    }
}
```
`Send` 要么真正等待（`ResetEvent.WaitOne()`，并把 `using` 改为在 `TaskInfo.Invoke` 里 `Set()` 后由执行方释放），要么直接删除 `WaitHandle` 字段并文档化为异步。

**验证方式**
在 `TaskInfo.Invoke` 里人为 `throw`，观察 `PendingTaskList.Count` 每帧是否递增；或对 `WaitHandle?.Set()` 加断点确认收到 `ObjectDisposedException`。
