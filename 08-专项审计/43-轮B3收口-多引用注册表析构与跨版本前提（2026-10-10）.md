## 2. 机制与安全分析（改一行要先把契约数清）

### 2.1 现状（改前）

```cpp
// Source/UnrealCSharp/Public/Registry/FMultiRegistry.h:30-39（改前）
	private:
		template <typename>
		friend struct TOwnedValue;

		void FreeImplementation()
		{
			FMemory::Free(TValueWrapper<T>::Value);   // ← 只归还内存，不跑析构
			TValueWrapper<T>::Value = nullptr;
		}
```

### 2.2 两个必须回答的问题

**Q1：`IsNeedFree == true` 的那些指针，是不是都由"构造过的堆对象"产生？**（否则补析构 = 对未构造内存调析构）

| 生产者 | 形态 | 判据 |
|---|---|---|
| 6 个 `FRegister*Ptr.cpp`（`SubclassOf`/`WeakObjectPtr`/`LazyObjectPtr`/`SoftObjectPtr`/`ScriptInterface`/`SoftClassPtr`） | `new T...(FoundObject)` ＋ `AddMultiReference<T, true, false>` | 各文件 `:17`（`ScriptInterface` 为 `:20/:22`）逐行读过 |
| 6 个对象属性描述符的 **`FReturn`** 变体 | `AddMultiReference<T, true, false>(Class, Object, CopyValue(...))` | 各 `F*PropertyDescriptor.cpp:45`；`CopyValue` = `TCompoundPropertyDescriptor.inl:33-48`：**`FMemory::Malloc` → `InitializeValue` → `CopySingleValue`** ⇒ **先构造后拷贝**（不是 memcpy） |
| `TPropertyValue.inl` 的 `Get<false>` | `new std::decay_t<T>(*InMember)` ＋ `AddMultiReference<..., true, false>` | `TPropertyValue.inl:147-148` 同行可见 |
| （对照）`IsMember=true` / `IsReference=true` 两路 | `AddMultiReference<..., false, true/false>` | `bNeedFree=false` ⇒ **不会**进 `FreeImplementation`；这些是把**成员地址/引用**登记进来，本轮不动 |

⇒ **Q1 = 是**。所有 `true` 分支都是"已构造的堆对象"，`FreeImplementation` 是它们唯一的归宿。

**Q2：直接 `delete` 还是"显式析构 ＋ `FMemory::Free`"？** —— 后者。理由：① **同仓先例**（`FStringRegistry.h:24-38` 的 `TStringAddress` 就是"`DestroyValue(U*)` 静态模板 ＋ `FMemory::Free`"，逐字同形；`FFieldPathRegistry.h:24-34` 亦为"显式 `~FFieldPath()` ＋ `FMemory::Free`"）；② 保持分配器调用面不变（`new` 由 UBT 的 `PerModuleInline.gen.cpp` 重定向到 `FMemory::Malloc`，`FMemory::Free` 与之匹配 —— 这一条已由原 finding 的证据链闭环）。

### 2.3 改动（8 行，单文件）

```cpp
// Source/UnrealCSharp/Public/Registry/FMultiRegistry.h:34-46（改后）
		template <typename U>
		static void DestroyValue(U* InValue)
		{
			InValue->~U();
		}

		void FreeImplementation()
		{
			DestroyValue(TValueWrapper<T>::Value);   // ← 新增

			FMemory::Free(TValueWrapper<T>::Value);

			TValueWrapper<T>::Value = nullptr;
		}
```

- 对**平凡可析构**类型（`TSubclassOf`/`TWeakObjectPtr`/…，见 §4）该调用是 **no-op**；对非平凡类型它才是本体。
- `bNeedFree` 在 `Free()` 内被置假 ⇒ 不会二次析构；`Value` 在释放后被置 `nullptr` ⇒ 不存在"对已置空指针析构"的路径。

## 3. 判据与读数（探针：释放路径的"内部堆字节"）

### 3.1 探针设计（临时，已移除；插件侧 0 残留）


### 3.2 读数（两轮套件，同一装置）

|---|---|---|

| 其中 `entry > 0`（对象内部有软指针路径） | **78** | **78** |

⇒ 🔴 **两版逐项相同**。这正是本报告最重要的读数：**"补上析构"在当前引擎上不改变任何可观测量** —— 因为那些"内部资源"在当前引擎的存储布局里**根本不在堆上**（§4），析构没有东西可放。

## 4. 🔴 跨版本前提更正（本轮最重要的产出）

### 4.1 结论

| 引擎 | `FSoftObjectPath` 的存储 | 软/弱指针是否含堆成员 | 本条（`FMultiRegistry` 跳过析构）的后果 |
|---|---|---|---|
| **UE 5.6**（当前活跃） | `FTopLevelAssetPath AssetPath;`（`SoftObjectPath.h:465`）＝ **`FName PackageName; FName AssetName;`**（`TopLevelAssetPath.h:190/192`） | **否**（纯 FName） | **无泄漏**（析构无可释放之物） |
| **UE 5.0**（本机亦装有） | `FName AssetPathName;` ＋ **`FString SubPathString;`**（`5.0/Engine/.../SoftObjectPath.h:252-255`） | **是**（含 `FString`） | **每次释放泄漏一个 `FString`** ⇒ 原 finding 的前提在 5.0 上**成立** |

### 4.2 六个类型的逐条依据（当前引擎 = 5.6）

| 注册类型 | 内部成员 | 是否平凡可析构 |
|---|---|---|
| `TSubclassOf<UObject>` | `UClass*` | 是 |
| `TWeakObjectPtr<UObject>` | `FWeakObjectPtr`（对象索引 ＋ 序列号） | 是 |
| `TLazyObjectPtr<UObject>` | `FLazyObjectPtr : TPersistentObjectPtr<FUniqueObjectGuid>`（`LazyObjectPtr.h:150`），载荷 `FUniqueObjectGuid` = **`FGuid Guid;`**（`:135`） | 是 |
| `TSoftObjectPtr<UObject>` / `TSoftClassPtr<UObject>` | `FSoftObjectPtr` → `FSoftObjectPath` → **`FTopLevelAssetPath`（双 FName）** | 是（5.6）／**否（5.0）** |
| `TScriptInterface<IInterface>` | `TObjectPtr<UObject>` ＋ `void*` | 是 |

⇒ 原 finding 正文（[`01-…/02`](../01-UnrealCSharp运行时/02-对象引用结构体注册表.md):729）写的"`TSoftObjectPtr`/`TSoftClassPtr` 持有 `FSoftObjectPath`（**内含 `FString`**，非平凡析构）"是 **UE 5.0 时代的布局**（也与插件支持 5.0–5.6 的多版本语境混淆了），**在 5.6 上不成立**。本轮的 8 行改动因此应读作：**"为 5.0 分支修一个真实泄漏 ＋ 去掉一个隐式前提"**，而不是"修掉 5.6 上的泄漏"。

### 4.3 为什么仍然落地这 8 行（取舍记录）

1. **5.0 分支仍在维护**（本机装 5.0 引擎、仓内有 `UnrealCSharpTest5.0` 与 `CrossVersion` 模块），且库内**已有同类先例**：G8 轮按**头文件依据**落地 5.0 专属兼容修复（`UE_F_SOFT_OBJECT_PATH_GET_ASSET_PATH_NAME`）并如实登记"**5.0 未编译验证**"。
2. **零风险**：对所有 `true` 分支的分配/构造契约已逐点核过（§2.2），对平凡类型是 no-op；4 次 CoreCLR ＋ 1 次 Mono 套件逐行 diff = 0（§5）。
3. **去掉隐式前提**：该释放路径此前"恰好正确"只因为**当前六个类型在当前引擎上平凡**；任何人将来往这张表里加一个非平凡类型（或回到 5.0 布局），泄漏会**静默**发生。补上析构后，正确性不再依赖该前提。

## 6. 未取得 / 残留面 / 触发条件（如实）

1. **UE 5.0 侧只有头文件依据，未编译、未运行**（与 G8 同一边界）：本机无 5.0 的 UBT 产物链；且 `UnrealCSharpTest5.0` 里的插件是**另一子模块快照**（`8f7d871c`），在其中编译本补丁不构成有效证据 ⇒ **"5.0 上每次释放泄漏一个 `FString`"是按存储布局的推理，不是实测**。
2. **结构体路径的残留面原样保留**：`FStructRegistry::FStructAddress::FreeImplementation`（`FStructRegistry.h:38-51`）在 `Value.IsValid()` 为假、或结构体为 POD/`NoDestructor` 时**跳过 `DestroyStruct`**；`FStructRegistry::Deinitialize()`（`FStructRegistry.cpp:21-35`）与其 `RemoveReference` 走**同一个 `Free()`**，因此两面同形。⇒ 该面**本轮未动**（`Value` 失效即拿不到类型信息，且 `Address` 有 `new` 与 `FMemory::Malloc` **两种来源**，统一改 `delete` 前必须先定释放契约 —— 与 2026-10-08 复核的 D=3 判定一致）。
3. **"当前六个类型平凡可析构"是隐式前提**（§4.2）：新增注册类型（或切到 `FSoftObjectPath` 仍含 `FString` 的引擎版本）时，必须复核本表的平凡性；本轮的 8 行已让该路径**不再依赖**此前提，但**探针无法在 5.6 上验证 5.0 的收益**。
4. **探针口径已自我更正**（§3.2）：`GetAssetPathString()` 是按值返回 ⇒ 它不能证明"内部缓冲是否仍被分配"，只能量"当时是否非空"。**本轮没有"5.6 上泄漏 X 字节"的读数，也不应据此写任何泄漏量**。
5. **LeanCLR 未跑**：改动为 COMMON 代码（`FMultiRegistry.h` 无 `#if WITH_*`），但 LeanCLR 切换需要四步纪律（ini → UBT → 编辑器内跑生成器重写 `Script/Shared.props` → `dotnet build`），漏做会产生"只有表头"的假绿 ⇒ 本轮只做 CoreCLR ＋ Mono。
6. **未新增永久判据**（见 §7.2）；`FMultiRegistry` 的另一半（`GetObject` 对死句柄的自愈路径，`FMultiRegistry.inl:30-46`）不在本轮范围。

## 7. 复用价值

1. **"零收益也要如实量化"**：本轮若只看代码 diff 会写成"修好了泄漏"；探针两版读数**逐项相同**（432/432、6020 B）才是真结论。⇒ **凡"补析构/补释放"类改动，必须给出可观测差值；差值为零就照实写"当前引擎零收益"**。
2. **泄漏断言必须回引擎头核存储类型**（本轮方法学的核心）：`FSoftObjectPath` 在 5.0 是 `FName + FString`、在 5.6 是 `FTopLevelAssetPath`（双 `FName`）—— **同一份插件代码，泄漏结论相反**。⇒ 凡跨版本插件（本仓支持 5.0–5.6），**"某个类型里有 FString/容器"这类断言必须带引擎版本与头文件行号**。
3. **探针口径自检**：按值返回的 getter（`GetAssetPathString`/`ToString`）**不能**当作"内部缓冲仍存活"的证据；要量堆，要么取成员地址（需公开成员），要么按分配器查询。本轮把这条写进 [`09-…/02`](../09-问题清单/02-实机与会话验证清单.md) **V-7**，避免后续轮次重复踩。
4. **"照同仓先例改"仍然是最短路径**：`FStringRegistry`/`FFieldPathRegistry` 已有"显式析构 ＋ `FMemory::Free`"的同形实现 ⇒ 本轮 8 行**零新概念、零新 helper**（`DestroyValue` 的命名与形态逐字同前例）。
5. **释放契约的核对面**（可复用的检查表）：① 谁 `new`／谁 `Malloc`；② 有没有 `InitializeValue`/构造；③ 释放门控（`bNeedFree`）覆盖哪些分支；④ 是否有"成员地址"以 `true` 混入（本轮确认**没有**）。
