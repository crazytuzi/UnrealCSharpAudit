## 2. `F-CB-005`：绑定物化产物的归属（✅ 已修）

### 2.1 机制

```cpp
// 改前（FBinding.cpp:10-36）
FBinding& FBinding::Register()
{
	if (!bIsRegister)
	{
		bIsRegister = true;
		for (const auto& Class : ClassRegisters) { Classes.Emplace(Class->operator FBindingClass*()); delete Class; }   // ← 物化产物入数组，注册器被删
		ClassRegisters.Empty();
		for (const auto& Enum : EnumRegisters)   { Enums.Emplace(Enum->operator FBindingEnum*());     delete Enum; }
		EnumRegisters.Empty();
	}
	return *this;
}
```
- 物化点 `FBindingClassRegister::operator FBindingClass*()` = `return new FBindingClass(...)`（`FBindingClassRegister.cpp:47`）⇒ **每次物化都是一个新堆对象**（`FBindingEnum` 同形）；
- `FBinding` 是**函数内静态**（`FBinding::Get()` 的 `static FBinding Binding;`），**有私有默认构造、没有析构** ⇒ 进程内**永不释放**（69 类 ＋ 9 枚举的元数据，含全部 `FString` 数组）。

### 2.2 消费者/生命周期审计（决定"释放点只能挂在哪"）

| 面 | 结论 | 依据 |
|---|---|---|
| 物化产物的消费者 | **全部是"调用时迭代"**，无任何静态缓存：`ScriptCodeGenerator`（`FBindingClassGenerator.cpp:12`、`FBindingEnumGenerator.cpp:9`）、`UnrealCSharpCore`（`FBindingClass.cpp:31/49` 的静态查询、`FLeanCLRDomain.cpp:891`、`FScriptDomainImpl.inl:622`）、运行时查询（`BindingMacro.h:72/193` 的 `IsProjectClass/IsProjectEnum`） | 22 处 `GetClasses()/GetEnums()/FBinding::Get()` 命中逐处读过 |
| 注册侧（`FClassBuilder` 等）是否在析构里用注册器 | **不用**：`FClassBuilder` 只持 `FBindingClassRegister*&`（对数组元素的引用），**没有析构函数**（`FClassBuilder.h:60`；全目录 grep `~FClassBuilder` = 0） | ⇒ 静态析构期 `delete` 物化产物与遗留注册器**不会**触发 UAF |
| ⛔ **被否决的修法**（形态依据，重要） | **不能**把释放挂到 `Deactivate()`（域重建/热重载）路径上：`Register()` 的 **`bIsRegister` 闩**在首次物化后置真，且 `ClassRegisters` 已被 `Empty()`＋`delete` ⇒ **物化产物一旦清空就无法重建**；重新激活（PIE 重启、热重载）会让生成面/绑定查询**变空** ⇒ 只能挂在**静态析构**（模块卸载 / 进程退出） | 代码事实 + `09-…/04` §3.2 对 `F-CB-009` 的"生成器依赖前置生成器副作用"旁证 |

## 3. `F-PROP2-003 (05)`：属性类型不匹配的语义（⏸️ 本体待裁定）

### 3.1 🔴 路径更正：判据实际打到的是"绑定属性"路径，不是描述符

原发现的证据指向 `FClassPropertyDescriptor.cpp:6/13/31` 与 `FSubclassOfPropertyDescriptor.cpp:68`。本轮先按"C# 属性写入"设计判据，落地后核对生成产物与模板，确认**绑定属性的 setter 不走描述符**：

| 路径 | 实现 | 类型不匹配时的行为 |
|---|---|---|
| **绑定属性**（`PropertyActor.ClassValue = x` 与 `__A…_SetClassValueImplementation`） | `TCompoundPropertyBuilder::Set`（`TPropertyBuilder.inl:105-…`）→ `TPropertyValue<UClass*,UClass*>::Get(handle)`（`TPropertyValue.inl:477-480`）→ `FCSharpEnvironment::GetObject<T>`（`FCSharpEnvironment.inl:111-115` 的 **`Cast<T>`**） | 解析失败 ⇒ 返回 `nullptr` ⇒ **赋值 nullptr（清空）** |
| 同上（`TSubclassOf` 属性） | `TPropertyValue<…TSubclassOf…>` → `TMultiPropertyValue::Get(handle)`（`TPropertyValue.inl:157-164`） | 解析失败 ⇒ 返回 `static std::decay_t<T> Default`（**空包装**）⇒ **赋值空包装（清空）** |
| **反射属性**（`FProperty.SetObjectProperty`） | `FRegisterProperty::SetObjectPropertyImplementation:35-39` = **先 `DestroyValue` 再 `Set`** → `FClassPropertyDescriptor::Set` / `FSubclassOfPropertyDescriptor::Set` | 解析失败 ⇒ 写 null（清空）；**且调用方已先销毁** ⇒ 无论如何都留不下原值 |

⇒ 原发现点到的 `Cast<UClass>` 静默**确实存在**（在 `GetObject<T>` 与两个描述符里），但**"清空"这一后果的主要来源是"解析失败与合法默认值不可区分"**，而不是某一个 `Cast` 调用点。

### 3.2 判据与改前读数（`out/b4-pre*`；每场景用**独立新 spawn 的 actor**，避免注册表缓存串场）

| 3 | `ClassPropertyExplicitNullClears` | ✅ true | 显式写 `null` ⇒ 清空（**符合预期**） |

### 3.3 为什么"本体不施工"（不是做不到，而是缺契约）

要让第 2/5 条变成"保持原值"，必须在**赋值之前**区分两种"解析失败"：

1. **句柄无效（0）** = 调用方**显式写 null** ⇒ 应当清空（第 3 条已如此，必须保持）；
2. **句柄有效但解析不出目标类型** = 类型不匹配 ⇒ 应当**不写**（保持原值）。

而现在的取值接口把两者合并成一个返回值：`TPropertyValue<…>::Get(handle)` 返回"值"本身（`nullptr` / `static Default`），**没有"是否解析成功"这一路信号**。⇒ 修法只有两条：

| 方案 | 代价 | 判据可判性 |
|---|---|---|
| **A. 引入"可解析性"谓词**（如给 `TPropertyValue` 特化加 `IsResolvable(handle)`；`FRegisterProperty` 的调用方把 `DestroyValue` 移到该判定之后） | 触及 `TPropertyValue` 的**全部类型特化**面 + 反射 setter 的通用入口 ⇒ 面较大、需回归全量属性用例 | ✅ 第 2/5 条可直接翻转 |
| **B. 维持现状（fail-closed 清空）**，仅把"清空"写成**契约**（并在 C# 侧可见化） | 零代码；但"写入一个类型不匹配的对象 ⇒ 静默清空"仍是**静默数据丢失** | ➖ 第 2/5 条维持 false（作为"当前语义"记录） |

⇒ **请维护者裁定**：(i) 选 A 还是 B；(ii) 若选 A，"可解析性"是加在 `TPropertyValue` 特化上，还是给描述符加一对 `CanSet/Set` API。**裁定落地前不动本体**。

### 3.4 🆕 本轮新登记 `F-REG2-015`：`TSubclassOf` 属性的**陈旧读**

- **现象**（判据 6，改前 false）：把 `TSubclassOf` 属性写成 null 之后，C# 读回**仍是旧包装（非 null）**。
- **根因候选**（代码事实）：读路径 `TMultiPropertyValue::Get(InMember, handle)`（`TPropertyValue.inl:115-131`）先查**地址映射缓存** `GetMultiObject<T>(InMember)`；命中即返回，**不校验缓存包装的值与当前内存是否一致**；而写入路径（`TCompoundPropertyBuilder::Set`）只改内存、**不清缓存** ⇒ 内存被清空后，读回的是陈旧包装。
- **对照**：`UClass` 属性没有地址缓存（读时 `Bind(*Member)` 重新绑定）⇒ 同一场景读回 null ✓（判据 3 通过）。
- **修法草案（未施工，4-6 行）**：地址映射命中后比较"缓存包装的值"与"`*InMember` 当前值"，不一致则摘除该映射并重建包装（与"未命中"分支同形）。
- **归属**：登记为 **`F-REG2-015`**（出处 [`01-…/02-对象引用结构体注册表.md`](../01-UnrealCSharp运行时/02-对象引用结构体注册表.md)，与 `F-REG2-*` 地址映射家族同源）；**待与 §3.3 的裁定同批处理**（两者都在"属性写入 → 读回"这一条链上）。

### 3.5 判据的交付形态

- **保留 3 条**（均通过）：`ClassPropertySetBaseline`、`ClassPropertyExplicitNullClears`、`SubclassOfPropertySetBaseline` —— 作为两个属性"正常读写/显式 null"的**语义基线**；工程侧文件 `Script/Game/UnrealCSharpTest/UnitTest/Binding/BindingPropertyTypeMismatch/UnitTestSubsystem.cs`。

## 7. 复用价值

1. **"归属类"修复必须先做消费者审计，再定释放点**：本轮的否决项（把释放挂到 `Deactivate()`）正是只有把**闩（`bIsRegister`）＋ 注册器生命周期**一起看才会发现的陷阱 ⇒ **"谁 new、谁 delete、何时还能重建"三问缺一不可**。
2. **改前对照要"每个场景独立"**：`TSubclassOf` 的读路径带**地址映射缓存**，同一 actor 连做多个场景会串场（本轮第一版判据就是这样，读数含义不清）⇒ **每个场景一个新 spawn 的 actor**。
3. **"判据打到的路径"必须回生成产物/模板核一次**：原发现指向描述符，而 C# 属性写入实际走 `TPropertyBuilder`/`TPropertyValue` ⇒ **不核路径就会"修了没人走的那条"**。
4. **"必要条件缺失 ⇒ 不施工"是合法结论**：把"解析失败"与"合法默认值"合并返回的接口，无法在不引入新契约的前提下实现"保持原值" ⇒ 本轮把它写成**带两个方案与代价的裁定请求**，而不是硬改一个半成品。
5. **判据可以只交付"能长期绿"的那部分**：必然失败的判据留在报告里（含代码与读数），只让**语义基线**进交付套件 —— 既保住套件全绿，又不把缺陷写成"预期行为"。
