## 1. 前提回核（引擎侧权威契约，E1–E7）

原文的"双删"结论建立在"`TMap::Remove` 会压缩 pair 数组并移动元素"这一前提上。逐条回核如下（全部为 UE 5.6 本机源码）：

| # | 结论 | 权威出处（`Engine/Source/Runtime/Core/Public/Containers/`） |
|---|---|---|
| **E1** | `TSet` 的元素存储是 **`TSparseArray`**，不是 `TArray` | `Set.h:1294` `using ElementArrayType = TSparseArray<SetElementType, typename Allocator::SparseArrayAllocator>;`、`Set.h:1297` `ElementArrayType Elements;` |
| **E2** | `TMap::Remove` → `Pairs.Remove`；`TSet::Remove` → `RemoveImpl` → `RemoveByIndex` → `Elements.RemoveAt(Index)` | `Map.h:493-497`、`Set.h:892-918`（`:902 RemoveByIndex`）、`Set.h:719-744`（`:743 Elements.RemoveAt(ElementIndex);`）、`Set.h:926-934` |
| **E3** | 🔴 **`TSparseArray::RemoveAt` 不移动任何其它元素**：非平凡可析构类型先**原地析构**（`:358`），随后 `RemoveAtUninitialized` 只把该槽位标记为空闲并链进空闲表（`:374-383`）；**没有移位、没有 `Data` 重分配** | `SparseArray.h:351-363`、`SparseArray.h:366-387` |
| **E4** | 唯一会**移动 pair**（进而使 `Find` 指针悬垂）的操作是**新增键**：`AddUninitialized` 先复用空闲槽（`:136`），**仅当空闲链为空**才 `Data.AddUninitialized(1)`（`:147`，可能扩容） | `SparseArray.h:130-152` |
| **E5** | ranged-for 的迭代器持 **`ArrayType& Array`**（容器对象引用）+ 位图迭代器，`operator*` 才 `Array[GetIndex()]` ⇒ 只要**被遍历的那个数组对象本身**没被析构/迁移，迭代状态就有效 | `SparseArray.h:942-1007`（`:1005 ArrayType& Array;`、`:991-994`） |
| **E6** | 引擎**自带**"迭代期容器变化"断言：ranged-for 的 `operator!=` 前 `ensureMsgf(this->Array.Num() == InitialNum, "Container has changed during ranged-for iteration!")`，且该检查在**非 Shipping/Test 构建下开启**（本机编辑器 Development ⇒ 开启） | `SparseArray.h:1047-1065` + `SparseArray.h:22-26`（`TSPARSEARRAY_RANGED_FOR_CHECKS`） |
| **E7** | 插件侧重入链逐跳（HEAD 行号，与原文差 0）：`FObjectRegistry.cpp:122`/`:145` → `FCSharpEnvironment::RemoveReference(handle)` → `FReferenceRegistry.cpp:44-57`；`:50 delete FStructReference` → `FStructReference.h:12-15` → `FStructRegistry::RemoveReference`（`FStructRegistry.cpp:115`）→ `:135` **再次** `FCSharpEnvironment::RemoveReference` → `FReferenceRegistry.cpp:44`（**异键**） | 见左列 |

## 2. 定级与施工

### 2.1 三条失效路径的裁剪表

| 路径 | 触发条件 | 5.6 下是否成立 | 本轮实测 |
|---|---|---|---|
| **① 原文机制**：异键 `Remove` 使外层迭代失效 → 二次 `delete` | 内层删的 pair 下标 < 外层 | ❌ **证伪**（E3/E5：不移位、不重分配、迭代器不持缓冲指针） | 重入 **9 次**（全部异键）、真双删 **0** |
| **② 同键重入**：外层正在遍历的那个 pair 被**原地析构** | 外层键 = 内层键（即某结构体持有**指向自身的** `FStructReference`） | ⚠️ 机制成立（`RemoveAt` 会析构该 pair）**但结构上不可达**：值语义下结构体不可能按值包含自身；`FStructRegistry::AddReference` 的 `InOwner`（宿主句柄）与 `InManagedHandle`（被引用结构体句柄）恒不同源 | `sameKey = 0`（**0 次**） |
| **③ 迭代期新增键**：`Pairs` 扩容 → 外层 `Find` 指针悬垂 | 遍历期间发生 `AddReference`（含重入路径上的新增）**且**空闲链为空 | ⚠️ 机制成立；但 `FReference` 的三族析构（`FStructReference`/`FBindingReference`/`TContainerReference`）**一律只做移除**，无任何新增路径 | `adds=140`、**`add during remove = 0`** |

⇒ 结论：**缺陷本体（可致重复 `delete`）不成立**；残留的是一条**契约违反** —— 代码在 `delete` 回调期间持有 `TMap::Find` 返回的裸指针，而引擎文档明写该指针 *"is only valid until the next change to any key in the map"*（`Map.h:406/423/436/446/468/524/565`）。当前实现下"没有下一次移动"，但这条安全性依赖**未被文档保证的容器实现细节**（5.6 恰好重写过 `TSet`），且③的成立条件（空闲链恰好为空）不可局部证明。

### 2.2 施工：两阶段删除（采纳原文 §建议 (a)）

```cpp
bool FReferenceRegistry::RemoveReference(const IManagedHandle InOwner)
{
	TArray<FReference*> References;

	if (const auto FoundReferences = ReferenceRelationship.Find(InOwner))
	{
		References.Reserve(FoundReferences->Num());

		for (const auto& Reference : *FoundReferences)
		{
			References.Add(Reference);
		}

		ReferenceRelationship.Remove(InOwner);
	}

	for (const auto Reference : References)
	{
		delete Reference;
	}

	return true;
}
```

析构函数同形（先全表收集 → `ReferenceRelationship.Empty()` → 再逐个 `delete`）。**语义边界**：删除的集合、个数与顺序不变；变化只有"**先摘表、后删除**"，因此重入时内层 `Find` 不再命中外层键（旧形态下会命中并重复删除同一批对象 —— 这正是②的入口）。`Empty()` 放在删除之前还有一处附带收益：析构期不再"边遍历边删表"，原来那份安全性（"`StructRegistry` 先于 `ReferenceRegistry` 被销毁 ⇒ 回调短路"）从**销毁顺序巧合**变为**结构性安全**。

- 改动面 **1 文件 `+18/−2`**（`numstat` 实测 `18 2`）；补丁 `Saved/Retest/fix-FREG005-two-phase-remove.patch`（**1 314 B / SHA256 `CE0795F31B716D7560C76A64360750A70CCC2B3EE91EE3C2AD463373F45E6132`**，`git apply --reverse --check` **exit 0**）。
- **口径核查**：未新增注释 / 日志 / `try-catch` / `throw` / `ensure` / 公开 API；未改函数签名、未改任何调用点。
- **风格核查**：TAB 缩进、无行尾空白、无空格缩进、文件纯 CRLF / no-BOM、保留末尾换行（`git ls-files --eol` = `i/lf w/crlf`，与仓内一致）；`for (const auto X : Container)` 为仓内既有写法（同模块 10 处先例）。

## 4. 方法学更正（3 条，第 3 条是**本轮自己的假阳性**）

1. 🔴 **原文机制"删除会压缩/移动元素"证伪**：`TMap`/`TSet` 的 `Elements` 是 `TSparseArray`（`Set.h:1294/1297`），`RemoveAt` 只**原地析构 + 挂空闲链**（`SparseArray.h:351-387`）。凡"容器删除后指针/迭代器是否失效"的判断，**必须先分清 `TArray::RemoveAt`（会移动）与 `TSparseArray::RemoveAt`（不会移动）**——两者语义相反，混用会得出相反的结论（本轮即是）。
2. **原文"迭代器内部状态就是 `&Elements[i]` 指针"不准确**：迭代器持 `ArrayType& Array`（容器**对象**引用），下标另存；因此"数组对象未迁移"时迭代有效。这解释了实测现象，也说明为什么"扩容新增"才是唯一真正的悬垂来源。
3. 🔴 **本轮自己的第一版探针产生了 2 条假阳性**：判据用"曾经出现过的指针集合"（`GFREG005Deleted`），而两阶段装置会**销毁并重建注册表** ⇒ 释放后的 `FReference` 地址被后续分配复用 ⇒ 报出 2 次"double delete"（`0000004267DED320`、`0000004267DE8C00`）。改用"**活指针集合**"（`AddReference` 入集 / `delete` 前出集，出集失败才算双删）后，改前 **0**、改后 **0**。⇒ **双删类判据必须跨代次成立：用"活集合"，不能用"历史集合"。**

## 6. 附带：`F-ENV-011` 的"旧句柄命中新域条目"**未复现**

- **待验前提**：句柄是 64 位纯标量、无域标识；`HandleData` 的计数器 `++Handle` 不因 `Clear()` 重置；若**托管程序集真被重载**（静态量重新起算），旧域句柄值会在新域被逐个复用 ⇒ 域重载后仍在飞的延迟任务（如 `FRegisterStruct::UnRegisterImplementation` 的 `AsyncTask(GameThread, …)`）会**误删新域的无关条目**。
- **判据（本轮新增）**：探针在 `FReferenceRegistry::AddReference` 上记录 **"大 max（>1000）之后出现小值（<100）"** ＝ 计数器重启的证据；另记"值回退"事件（重复 owner 会误报，需人工区分）。
- **结果**：装置 B 全程（含 `SetActive 0` → `SetActive 1` 的**完整环境销毁与重建**）**小值回跳 0 次**；重建后观测到的 owner 句柄仍在 **30k–47k** 区间；累计"值回退"仅 **2 次**，均为**既有 owner 的重复注册**（同值重复，不是新小值）。装置 A 同型（3 次回退、0 次小值）。
- **结论**：**未复现**"计数器重启 ⇒ 旧句柄被复用"。与插件既有笔记一致（`HandleData.Clear()` 不重置计数器）；要给定论仍需在 C# `HandleData` 侧直接埋计数器探针（**留给下一轮**），本轮的 C++ 侧观测只能证明"经引用注册表可见的句柄没有重启形态"。

## 7. 复用价值（给下一轮）

1. 🟢 **"删除会不会移动元素"是容器类判据的分水岭**：`TArray::RemoveAt` 会（移位），`TSparseArray::RemoveAt` 不会（空闲链）—— 而 `TSet`/`TMap` 走的是后者。任何"遍历中删除/重入"的结论，先确定容器类型再下判断。
2. 🟢 **引擎自带迭代期断言可直接当判据**：`TSPARSEARRAY_RANGED_FOR_CHECKS` 在非 Shipping/Test 下为 1 ⇒ Development 构建里 ranged-for 的 `operator!=` 会 `ensureMsgf("Container has changed during ranged-for iteration!")`。本轮 **0 命中**，是免费且可永久沿用的"迭代期容器变化"探针。
3. 🟢 **探针要能把"重入发生"与"重入造成后果"分开**：本轮三件套 = `depth`（发生）+ `sameKey`（危险形态）+ 活指针集合（后果）。只测"深蹲计数"会把"重入 9 次"误读成"9 次危险"。
4. 🟢 **双删判据必须跨代次成立**：装置会销毁/重建注册表 ⇒ 地址复用会让"历史集合"判据假阳性（本轮实测 2 次）。改用"活集合（入集/出集）+ live 收敛到 0"。
5. 🟢 **装置选择决定能不能测到**：同一份代码，`-game` 套件重入 **0** 次、两阶段编辑器装置 **9** 次。凡"跨域/重入/析构顺序"类条目，**必须**用会真正重建环境的装置。
