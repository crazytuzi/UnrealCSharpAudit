# 设计页 `F-REFL-005` —— `GetClass(IManagedHandle)` 的句柄"消费"语义与调用方契约（2026-11-03）

> 分析范围：`F-REFL-005`（P2 · S=2.71 · 活跃）——「`GetClass(IManagedHandle)` 命中缓存时 `Free` 掉传入句柄，导致"同一句柄被释放两次"的调用约定陷阱」
> 复核基线：插件 HEAD `07ea9e7d`（B-220 交付后）
> 状态：**设计完成、0 代码**。结论 = 现有实现是**自洽的"消费"语义**，18 个调用点全部符合；所谓"双重释放"**当前不成立**，本条应改判为**契约/防护**问题

---

## 1. 代码事实（回 HEAD 逐条核对）

### 1.1 被讨论的函数

```cpp
// Source/UnrealCSharpCore/Private/Reflection/FReflectionRegistry.cpp:935-959
FClassReflection* FReflectionRegistry::GetClass(const IManagedHandle InManagedClass)
{
	if (IManagedHandleIsValid(InManagedClass))
	{
		if (const auto ScriptDomain = IScriptDomain::Get())
		{
			const auto FullName = ScriptDomain->GetFullName(InManagedClass);

			if (const auto FoundClass = FullName2Class.Find(FullName))
			{
				ScriptDomain->Free(InManagedClass);          // ← 命中即释放传入句柄

				return *FoundClass;
			}

			const auto Class = new FClassReflection(InManagedClass, ScriptDomain->GetName(InManagedClass));

			FullName2Class.Add(FullName, Class);

			return Class;                                    // ← 未命中：句柄移交给反射对象
		}
	}

	return nullptr;
}
```

### 1.2 未命中路径：句柄所有权**确实转移**给 `FClassReflection`

- 构造：`FClassReflection.cpp:118-122` 把 `InManagedClass` 存进成员 `ManagedClass`。
- 释放：`FClassReflection::Deinitialize()`（`:500` 起）在末尾 `if (IManagedHandleIsValid(ManagedClass)) { ScriptDomain->Free(ManagedClass); }`（`:526-530`）。
- ⇒ **两条路径都释放了一次**（命中：立刻释放传入句柄；未命中：反射析构时释放它持有的那份）⇒ **契约 = "吃掉调用方给的句柄"**，自洽。

### 1.3 调用方：18 个，全部符合"消费"语义

`GetClass(InManagedType)` 在 6 组注册器里共 **18 处**（`FRegisterArray:29`、`FRegisterMap:15`、`FRegisterSet:16`、`FRegisterOptional:16/42`、`FRegisterDelegate:16/51`、`FRegisterMulticastDelegate:16/62/88/112/136`、`FRegisterLazyObjectPtr:19`、`FRegisterScriptInterface:29`、`FRegisterSoftClassPtr:19`、`FRegisterSoftObjectPtr:19`、`FRegisterSubclassOf:19`、`FRegisterWeakObjectPtr:19`）。

- 逐处检查：**没有任何一处**在 `GetClass(...)` 之后再次 `Free(InManagedType)`（本轮 grep 了每处所在函数块）。
- 另有 `GetClass` 的**其他重载**（`TWeakObjectPtr<UField>`／`FString, FString`）不涉及句柄，与本条无关。

### 1.4 句柄从哪来：C# 侧**每次新分配**

```csharp
// Script/UE/Library/TArrayImplementation.cs:14
public static void TArray_RegisterImplementation<T>(TArray<T> InArray, Type InType)
{
	__TArray_RegisterImplementation(HandleData.Alloc(InArray, true), HandleData.Alloc(InType));   // ← 新分配
}
```
其余注册器（`TMap`/`TSet`/`TOptional`/`FDelegate`/`FMulticastDelegate`/…）的 `*_RegisterImplementation` 包装**一律** `HandleData.Alloc(InType)` —— 都是**专供本次调用**的新句柄，不是共享/缓存句柄。
⇒ 命中路径 `Free` 掉它**不会**影响任何其他持有者。

### 1.5 因此：原文的"双重释放"风险，当前**没有可达路径**

- 调用方不二次 Free；
- C# 侧句柄是一次性的；
- 缓存中的反射自己持有一份（另一份句柄，来自首次未命中那次调用）。

**但**：如果将来有人把 `InManagedType` 当成"借用"（例如从某处 `HandleData.GetHandle(type)` 传入共享句柄），命中路径的 `Free` 会**立刻让那个共享句柄失效**，且编译器/运行期都不会报错 —— 这正是原文想表达的"陷阱"，属**契约未文档化 + 无机械防护**。

## 2. 方案

### 方案 A：契约化（0 代码，**推荐**）

在契约页写明三条：

| 条款 | 内容 |
|---|---|
| **C-REFL-1** | `FReflectionRegistry::GetClass(IManagedHandle)` 的语义是**消费**（consume）：无论命中与否，调用方在调用后**不得**再对该句柄调用 `Free`。 |
| **C-REFL-2** | 命中路径释放传入句柄、未命中路径由 `FClassReflection` 持有到析构释放 —— **两条路径各释放一次**，是设计而非缺陷。 |
| **C-REFL-3** | 新增调用方时，句柄**必须来自"专供本次调用"的分配**（C# 侧 `HandleData.Alloc(...)` 形态）；禁止传入共享/缓存句柄。 |

- 成本：**0 行**；G7 零风险。
- 缺点：无机械防护，靠评审。

### 方案 B：改名即契约（`GetClassConsume`）

把方法名改成 `ConsumeClass(IManagedHandle)` 之类，让"消费"写进名字。
- **撞 G7**（重命名既有公开 API，§8.5 仍封死），且要改 **18 处**调用点 + 头文件。
- 收益**仅**在可读性；除非同时改其余两个重载的命名体系，否则名字反而更乱。**不推荐**。

### 方案 C：拆成"借用版" `GetClassBorrow`（不可行）

若提供不消费的版本，未命中路径必须**复制一份句柄**交给反射（否则反射与调用方双持有 → 必然双释放）：需要在 `IScriptDomain` 上新增"复制/持有"原语（三后端各实现）⇒ **新公开面 + 后端改动**，成本远大于收益。**排除**。

### 方案 D：退回"借用"语义（命中不 Free，调用方自己释放）（不可行）

- 未命中路径的反射**已经**持有句柄并在析构时释放 ⇒ 调用方若也释放，就是双释放；若调用方不释放，则命中路径泄漏一个句柄。
- 除非同时改反射的所有权（不再持有句柄），否则无解。**排除**。

### 方案 E：加 `check`/`ensure` 断言防护（**撞 G7**）

在命中路径 Free 前 `check(IsInGameThread())` 或在 `Free` 后置 `InManagedHandle = InvalidManagedHandle` —— 前者是新增断言（G7 禁），后者是形参按值传递、无效。**排除**。
