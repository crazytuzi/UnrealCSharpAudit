## 2. 前提更正（本轮关键）

`TMap.cs:40-69` 的 `GetEnumerator` 早已有分块快路径：

```csharp
if (typeof(TKey).IsValueType && typeof(TValue).IsValueType &&
    KeySize == Unsafe.SizeOf<TKey>() && ValueSize == Unsafe.SizeOf<TValue>())
{
    var Buffer = new byte[EnumeratorChunkSize * PairSize];   // 256 对/块
    while (true)
    {
        var Count = GetPairs(Handle, Index, EnumeratorChunkSize, Buffer, out var NextIndex);
        ... Unsafe.ReadUnaligned<TKey>/<TValue>(...)          // 无逐元素 P/Invoke
    }
}
```

慢路径（`:71-78`）才是"每槽 3–4 次 P/Invoke"：

```csharp
for (var Index = 0; Index < GetMaxIndex(Handle); Index++)   // ① 循环条件里每次重发
{
    if (IsValidIndex(Handle, Index))                        // ②
    {
        yield return new KeyValuePair<TKey, TValue>(
            GetEnumeratorKey(Handle, Index),                // ③
            GetEnumeratorValue(Handle, Index));             // ④
    }
}
```

且慢路径的**主要成本不是 P/Invoke，而是每个键都要新建托管包装**（`FString`/对象/结构体键）⇒ 这是"每元素一次分配"的固有形态，不是调用次数能救的。

## 3. 修法实测（未采纳）

| 改动 | 读数 | 判定 |
|---|---|---|
| `GetMaxIndex(Handle)` 提到循环外（每槽 4 → 3 次 P/Invoke） | **105.060 → 121.648 ms** | 噪声（GC/分配主导）大于效果 ⇒ **回退** |

**为什么不进一步**：要让慢路径也批量化，需原生侧一次返回"键缓冲 ＋ 值缓冲"，C# 侧对**非 blittable 类型**无法自行解码，必须逐类型走描述符 ⇒ 需要新的 interop 协议（`FRegisterMap` ＋ 生成绑定 ＋ 双方契约），规模远大于本条的价值。

**处置**：🟡 **降级 P3、本体不施工**；触发条件 = 出现"万级条目 `TMap` 的每帧 `foreach`"，或 `TMap` 慢路径进 profiling 前列。
