## 1. `D`：UBT 原生库修复

### 1.1 缺什么、从哪来

5.8 的 `Engine\Binaries\DotNET\UnrealBuildTool\` 只有托管 `Blake3.dll` / `SQLitePCLRaw.provider.e_sqlite3.dll`，**缺 5 个原生库**；同一目录的 `runtimes\win-x64\native\` 里**有一份完整拷贝**。

| 文件 | 字节 | SHA256（前 16） | 来源 |
|---|---|---|---|
| `blake3_dotnet.dll` | 379 904 | `ED515032FC106D5F` | `…\UnrealBuildTool\runtimes\win-x64\native\` |
| `e_sqlite3.dll` | 1 795 072 | `4DCBB2AD197D8933` | 同上 |
| `oo2core.dll` | 637 952 | `6F5D41A7892EA6B2` | 同上 |
| `UbaDetours.dll` | 1 212 856 | `CA1580A7174C891E` | 同上 |
| `UbaHost.dll` | 2 183 608 | `6141DC5624C81BF5` | 同上 |

复制到 `…\UnrealBuildTool\` 根（**新增 5 个文件，未改/未删任何现有文件**）。反向操作 = 删除这 5 个文件即可复原。

### 1.2 修复前后

| 阶段 | 现象 |
|---|---|
| 修复前 | 直调 `dotnet UnrealBuildTool.dll` → `DllNotFoundException: Unable to load DLL 'blake3_dotnet'`（`Blake3.Hasher.New()` ← `IoHash.Compute` ← `GlobalSingleInstanceMutex`） |
| 修复后 | UBT 正常启动：`Creating makefile for UE58CheckEditor`、`UHT processed UE58CheckEditor in 5.48 s`、进入编译（见 `b272-ue58-build1.log`） |

`Build.bat` 那条路仍然不可用（它在 "Building UnrealBuildTool" 阶段走 NuGet restore，离线报 `NU1301`）⇒ **必须直调 `UnrealBuildTool.dll`**（配方见 §3.1）。

## 2. 全量构建：为什么没做完

### 2.1 触发原因

`Creating makefile for UE58CheckEditor (Build.version is newer)` ⇒ 5.8 安装的 `Build.version` 比 B-31（2026-10-16）生成的 makefile 新 ⇒ **makefile 失效 ⇒ 引擎模块全量重编**（不是只编插件）。

| 口径 | 读数 |
|---|---|
| 首次尝试（UBA） | 3 775 action；10 分钟只推进到 198（≈6 action/min）；`cl` 并发 **3** |
| 第二次尝试（`-NoUBA` 经典执行器） | 3 574 action；90 秒推进 5（≈3 action/min）；`cl` 并发 **4** |
| B-31 当时（有 Horde 远程） | 4 146 action / 41 分钟（≈100 action/min，`MaxWorkers 576`） |

### 2.2 为什么本地慢

- 引擎 unity blob 体积大（`Module.UnrealEd.*`/`Module.Engine.*` 每个含数十个 cpp）；
- 远程执行是 B-31 能 41 分钟完成的主因，现在 **Horde 不可达**：
  `Unable to get access token for provider 'Horde': Error using the refresh token: Internal Server Error`
  ⇒ `No valid access token obtained for provider 'Horde'. Starting interactive login (browser)`（无法交互）⇒ 退回纯本地。

### 2.3 决定

**停止全量构建**，保留 5.8 检查工程 2026-10-16 的产物（`E:\UnrealEngine\UE58Check\Binaries\Win64\UnrealEditor-UE58Check.dll`、插件各模块 DLL 均在），避免把引擎中间态拖长。
**触发条件（下一轮做全量 5.8 构建的前置）**：① 恢复 Horde/网络；或 ② 给该引擎预置 `InstalledBuild.txt` ＋ 引擎中间产物；或 ③ 换一台空载机器跑 12–20 h。

> 📌 **2026-11-17 补记**：该阻塞已由 [`311`（B-275）](311-轮B-275-UE58全量构建成功（2026-11-17）.md) **解除** —— Horde 服务恢复后 3 567 action / 2 059 s `Result: Succeeded`；但运行期另有**引擎启动断言**（`MemoryImage.cpp:221`，加载项目前），见该页 §3.1。

### 2.4 副作用（必须记录）

1. 引擎 `Engine\Binaries\DotNET\UnrealBuildTool\` **新增 5 个文件**（§1.1）；
2. 被中断的重建刷新了部分引擎二进制时间戳（例：`UnrealEditor-Core.dll` 变为 2026-11-17 12:04）；引擎处于"部分重建"状态，**下次构建仍会重编**（与本轮结论一致）；
3. 停止构建时同时结束了 1 个 **09:05 启动的 `dotnet` 进程**（与本轮构建无父子关系，可能是无关的长驻进程）—— 记录在此，供排查。

## 3. 替代判据：cl 单 TU 探针（5.8 编译面）

### 3.1 配方（复用 B-31，已验证可跑）

```
cd /d "D:\file\UnrealEngine\Release\Engine\Source"      ← 关键：Shared.rsp 里是相对 include
cl.exe @b272-probeN.rsp
```

`b272-probeN.rsp`：

```
@"E:\UnrealEngine\UE58Check\...\UnrealCSharp\UnrealCSharp.Shared.rsp"
/FI"E:\…\UnrealCSharp\Definitions.UnrealCSharp.h"
/I "D:\file\UnrealEngine\Release\Engine\Intermediate\Build\Win64\x64\UnrealEditor\Development\UnrealEd"
/I "D:\…\Plugins\UnrealCSharp\Source"
/std:c++20 /permissive- /Zc:__cplusplus /Zc:preprocessor /utf-8 /W4 /nologo /c /TP /EHsc /MD /bigobj
"…\b272-probeN.cpp"
```

（`vcvars64.bat` 由 `b272-probe.bat` 调用；cl = MSVC **14.52.37025**。）

### 3.2 探针矩阵

| 探针 | 内容 | 结果 | 说明 |
|---|---|---|---|
| **P4** | 最小重现 `TIsStaticEnum` 的 SFINAE 模式（`Test(decltype(StaticEnum<U>())*)`），对普通枚举 `static_assert(!Value)` | **PASS**（0 error） | 5.8 的 `StaticEnum() = delete` 下**仍是 SFINAE 失败、不是硬错误** |
| **P5** | 5.8 fallback 体：`GetGeneratedTypeName` ＋ 两次 `RemoveFromStart` ＋ `FindFirstObjectSafe<UEnum>` | **PASS** | 引擎 API 面兼容（需 `UObject/Class.h` 提供完整 `UEnum`） |
| **P6** | `TStaticEnum<EAxis::Type>::Get()`（**真实 UENUM**，真分支） | **PASS** | `StaticEnum<EAxis::Type>` 特化存在且可用 |
| **P7** | 插件 `Binding/TypeInfo/TStaticEnum.inl`（含 B-270 的 `#include "UObject/ReflectedTypeAccessors.h"`），只带 `CoreMinimal.h`，普通枚举走 fallback ＋ `static_assert(!TIsStaticEnum)` | **PASS** | **无 PCH** 可编译；B-270 的 include 修正在 5.8 成立 |

**探针自身的三次失败（不是缺陷，记录以免误读）**

| 探针 | 失败原因 |
|---|---|
| P1 v1 | 只 include 插件 `.inl`、没有 `CoreMinimal.h` ⇒ `uint8`/`std` 未定义（连带 `StaticEnum` 报 `C2280`，**是假信号**） |
| P1 v2 / P2 | 加上 `CoreMinimal` 后，`TIsStaticEnum`/`TStaticEnum` 全部通过；仅 `TName.inl` 报错 ⇒ `TName.inl` 是**片段头**，依赖 `BindingMacro.h` 的 trait 环境，不能独立 include（**既有结构事实**） |
| P3 | 直接 include `Macro/BindingMacro.h` 仍缺 `TIsTSubclassOf` 等 trait ⇒ 插件头**不是自洽的**，必须按生产 TU 的 include 顺序使用（同上，非本轮缺陷） |

### 3.3 结论

1. **`TIsStaticEnum` 的 5.8 语义正确**：`StaticEnum` 被 `= delete` 时，普通枚举得到 `Value == false`（P4 + P7 的两处 `static_assert` 都是编译期铁证）；
2. **`TStaticEnum` 两条分支在 5.8 都可编译**：fallback（P5/P7）与真分支（P6）；
3. **B-270 的 include 修正（`F-BIND-014`）在 5.8 成立**：插件头只带 `CoreMinimal.h` 即可编译（P7 就是"无 PCH 的空 TU"场景）；
4. **仍未取得**：5.8 下**哪些枚举**会落进 fallback（`StaticEnum` 无特化且未被 `TIsNotUEnum` 排除）—— 需要跑一次 5.8 编辑器/生成器，属运行期语料。
