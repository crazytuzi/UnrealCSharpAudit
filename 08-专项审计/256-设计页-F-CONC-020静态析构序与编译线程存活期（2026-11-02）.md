> 🔴 **对原判的两处修正（回 HEAD 得出）**
> 1. **「跨 TU 静态对象尚未构造就 `AddRaw`」在当前模块依赖下不成立**：`Compiler` 模块依赖 `UnrealCSharpCore`（后者先加载、其静态先初始化）⇒ F3 的 `AddRaw` 落在**已构造**的委托上。原报告的"UB"表述依赖"链接顺序不可知"，但模块加载顺序由依赖图固定，**这条不构成缺陷**（仍如实保留为"依赖模块加载顺序"的约束）。
> 2. **真正的窗口只剩退出期**，且它**依赖"模块/静态对象是否真的析构"**：Windows 上 UE 编辑器默认**不卸载模块 DLL**（`bUnloadModulesOnShutdown` 默认关），进程退出由 OS 终止 ⇒ `FCSharpCompiler` 的函数内静态**根本不会被析构**，F2 的 `Kill(true)` 不执行。**只有**以下路径会让静态析构真的发生：① 显式 `UnloadModulesAtShutdown`/热重载；② 打包版或 `-game` 会话的模块卸载；③ 未来把编译器改成模块持有（方案 C）。⇒ 本条的"潜伏"不是"概率低"，而是**当前配置下析构路径本身不执行**。

## 2. 三个时序窗口（逐一给可达性）

| 窗口 | 时序 | 可达性 | 后果 |
|---|---|---|---|
| **W1 构造期** | 编辑器 `StartupModule` → `FCSharpCompiler::Get()` → `new FCSharpCompilerRunnable` → `AddRaw` 到 Core 模块静态委托 | **构造面可达**，但 Core 模块先加载 ⇒ 委托已构造 | 无缺陷（见 §1 修正 1） |
| **W2 退出期（`OnPreExit` → 模块卸载）** | `FEngineListener::OnPreExit()` → `Deactivate()`（域下发 `Deinitialize`）→ **编译线程仍活着**（上一轮编译可能未结束）→ 线程回调 `FUnrealCSharpCoreModuleDelegates::OnCompile` / 访问已 Deactivate 的域 | **可达但未实证**：需要"退出时编译线程正在跑"这一前提 | 线程访问已销毁的域/委托 ⇒ 崩溃或 UB；`Deactivate()` 本身不等待编译线程 |
| **W3 静态析构期** | `~FCSharpCompiler()` → `Thread->Kill(true)`（等待）→ 删除 `Thread`/`Runnable` | **编辑器默认不可达**（模块不卸载，静态不析构）；热重载/卸载路径可达 | `Kill(true)` 是阻塞等待，若线程卡在 `dotnet build` 会拖住退出；`~FCSharpCompilerRunnable` 已用 `GExitPurge` 守卫缓解 |

## 3. 方案

### 方案 A：契约（不施工，**本轮采用**）
在契约页写明：**编译线程的生命周期由静态对象承担，`OnPreExit` 只负责域、不负责线程**；编辑器默认不卸载模块 ⇒ 该析构路径当前不执行。登记触发条件（见 §5）。
- 代价：**0 行**；G7 零风险。
- 缺点：若将来启用 `UnloadModulesAtShutdown` 或改为模块持有，W2/W3 会变成真窗口，而契约**不会自动拦住**。

### 方案 B：内部 `OnPreExit` 提前停线程（**若要施工，推荐这条**）
在 `FCSharpCompiler` 构造函数里向 `FCoreDelegates::OnPreExit` 注册 private 回调，在退出早期顺序执行 `Runnable->Stop()` → `Thread->Kill(true)`；重复调用（含析构）按 `OnPreExitHandle` 是否仍有效**幂等短路**——句柄由 `OnPreExit()` 自己 `Remove`，不需要额外的 bool 标志。
```cpp
// 形态示意（未施工）
FCSharpCompiler::FCSharpCompiler() : Runnable(nullptr), Thread(nullptr)
{
	Runnable = new FCSharpCompilerRunnable();
	Thread = FRunnableThread::Create(Runnable, TEXT("CSharpCompiler"));
	OnPreExitHandle = FCoreDelegates::OnPreExit.AddRaw(this, &FCSharpCompiler::OnPreExit);
}

void FCSharpCompiler::OnPreExit() { /* if (OnPreExitHandle.IsValid()) { FCoreDelegates::OnPreExit.Remove(OnPreExitHandle); Runnable->Stop(); Thread->Kill(true); } */ }
```
- **G7 合规**：不新增公开 API（`OnPreExit` 为 private、`AddRaw` 句柄为 private 成员）、不新增日志/断言/throw、失败无新出口。
- **跨版本**：`FCoreDelegates::OnPreExit` 已在同仓使用（`FEngineListener.cpp:31`），**5.0 起可用**（§7 判据：同一符号、同一用法）。
- 代价：`FCSharpCompiler.{h,cpp}` 约 **+12/−3 行**。
- 风险：`Stop()` 的语义是"让 `Run()` 退出循环"，`Kill(true)` 再等待；若线程正卡在 `SyncProcess`（`dotnet build`），提前 Kill 会让该次编译的产物处于中间态 —— **需要一次判据**（退出期不产生半写产物）。

### 方案 C：`FCompilerModule` 显式持有（不做）
把 `FCSharpCompiler` 从"函数内静态"改为模块成员（`StartupModule` 创建、`ShutdownModule` `Reset()`）。
- 需要改 `Get()` 的语义并触及 **20+ 调用点**（`UnrealCSharpEditor.cpp` 11 处、`DynamicDataSource.cpp` 4 处、`FEditorListener.cpp` 5 处…），属接口面变更；收益仅在"卸载路径"，**不支持**。

### 方案 D：给 `FCSharpCompiler`/`IScriptDomain` 加公开 `Shutdown()`（不做）
新公开 API ⇒ **撞 G7**；且与方案 B 的收益完全重叠。
