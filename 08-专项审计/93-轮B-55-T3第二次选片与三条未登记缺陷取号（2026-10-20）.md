## 2. 逐条复验

### 2.1 `F-DEL-013`（2.89）—— 仍成立：委托注册表以 UObject 内联属性地址为键

- `FDelegateRegistry.inl:58`：`(InRegistry->*Address2ManagedHandle).Add(InAddress, InManagedHandle);` —— 键是 `FDelegatePropertyDescriptor::NewRef/NewWeakRef` 传进来的 `Property->GetPropertyValuePtr(InAddress)`，即**属性所在 UObject 的内联存储地址**。
- 表里没有任何失效回调 / 版本号：UObject 被 GC 后该地址成为悬垂 key；新对象复用同地址时会 `Add` 覆盖或命中旧条目（串对象）。
- **判定**：机制成立、可达性活跃（10-08 同判）。**处置建议 = 暂缓**：修法要在"裸地址键 → 带 owner/代次的复合键"之间做生命周期设计，与 G1 系列（弱句柄/地址映射）的既有裁定交叉，不是一轮能收口。

### 2.2 `F-CONC-016`（2.89）—— 仍成立：19 个 interop 文件的 `UnRegister` 无条件 `AsyncTask`

- `Source/UnrealCSharp/Private/Domain/Interop/*.cpp` 里 `AsyncTask(ENamedThreads::GameThread` **实测命中 19 个文件**（10-08 报告记 18，多出 `FRegisterFieldPath.cpp`）；形态同 `FRegisterArray.cpp` 的 `UnRegisterImplementation`：finalizer 线程每释放一个包装就投递一个闭包。
- `AssemblyLoader` 自身在游戏线程 `GC.Collect(); GC.WaitForPendingFinalizers();` 时也会绕一圈队列。
- **判定**：P3 性能面成立。**处置建议 = 暂缓**：可做的最小改法是"已在游戏线程则直接执行"，但落点分散在 19 个文件；批量队列（`TQueue` drain）属新装置/新设计，收益需先量化。

### 2.3 `F-HLP-003`（2.88）—— 🟢 立项 ①：描述符包装的释放被绑在"是否拥有属性"上

- **8 个构造点全部传 `bNeedFreeProperty = false`**（底层属性是引擎的，Helper 只借用）：
  - `FArrayPropertyDescriptor.cpp:55-56`（`NewRef`：`false, false`）、`:77-78`（`NewWeakRef`：`bIsCopy, false`）
  - `FMapPropertyDescriptor.cpp:55-56` / `:77-78`、`FSetPropertyDescriptor.cpp:55-56` / `:77-78`
  - `FOptionalPropertyDescriptor.cpp:15`（`false, false`）/ `:33`（`true, false`）
- **但每个 Helper 的构造都无条件 `Factory()` 出一个新描述符包装**：`FArrayHelper.cpp:13`、`FMapHelper.cpp:24-25`、`FSetHelper.cpp` 同形、`FOptionalHelper.cpp:13`。
- **析构只在 flag 为真时才释放**：`FArrayHelper.cpp:57-64`、`FMapHelper.cpp:69-82`（Key＋Value）、`FSetHelper.cpp:65-72`、`FOptionalHelper.cpp:54-63` ⇒ **每条 `NewRef`/`NewWeakRef` 泄漏 1–2 个描述符包装**（有界但不回收，跨对象累积）。
- 🔴 **本轮最重要的更正**：原条目隐含的"把第 4 个实参翻成 `true` 即可"**不可用** —— `TPropertyDescriptor<T,…>::DestroyProperty()` 会 `delete Property`（`TPropertyDescriptor.inl:22-30`，`TPrimitivePropertyDescriptor.inl:48-56` 同形）⇒ 翻 flag 会 **delete 引擎的 `Property->Inner` / `KeyProp` / `ValueProp` / `ElementProp` / `GetValueProperty()`**；`FOptionalHelper` 还会 `delete OptionalProperty`（`:60`）。**正确修法必须把"包装释放"与"底层属性销毁"拆成两件事。**
- **判定**：泄漏成立、修法形态已澄清 ⇒ **立项**（详见 §3.1）。

### 2.4 `F-BIND-010`（2.88）—— 机制仍在，但当前语料不触发

- `TPropertyValue.inl:1010`：`return static_cast<std::decay_t<T>>(*static_cast<uint8*>(FDomain::Object_Unbox(InManagedHandle)));` —— 一律按 1 字节解箱；其余原语走 `sizeof(T)`。
- 触发前提 = **底层类型大于 1 字节的 `UENUM`**；本仓 `UENUM` 语料与 UHT 默认（`uint8`）下不成立 ⇒ 潜伏。
- **处置建议 = 暂缓**：需要先造一个宽底层类型枚举 + 句柄探针，属"先取证再定性"。

### 2.5 `F-MACRO-002`（2.88）—— 仍在，但现存调用点全部绕开

### 2.7 `F-CB-010`（2.88）—— 参数名数量无契约

### 2.8 `F-BR-008`（2.88）—— 🟡 候补 ③：`.sln` GUID 非定宽

### 2.11 `F-DOM-005`（2.82）—— 早退路径不关 host、`Deinitialize` 首行早退

- `FCoreCLRDomain::Initialize()` 在 host 句柄已取到之后仍有 **4 处早退**：`:46-49`（`GetDllHandle` 失败，尚未建 host）、`:72-75`（导出缺失）、`:99-104`（`hostfxr_initialize` 失败）、`:108-113`（`get_runtime_delegate` 失败）—— 后三处会留下"`HostFxrDllHandle` 非空、`HostFxrHandle` 可能非空、但 `bIsInitialized=false`"的中间态；下一次 `Initialize()` 会跳过整个 host 初始化块。
- `Deinitialize()` 首行 `if (!bIsInitialized) return;`（`:136-140`）⇒ 上述中间态**永远不会 `hostfxr_close`**。
- **判定**：事实成立；但"下次初始化彻底跳过运行时"的后果取决于失败点（若 `LoadAssemblyAndGetFunctionPointerFn` 已设，重试可正常走；若未设则后续 `RegisterInterop` 拿空指针）。**处置建议 = 暂缓**：需要先裁定"重试是否复用 host / 失败是否 close"，属状态机设计。

### 2.12 `F-REFL-001`（2.80）—— `Deinitialize()` 不重置 285 个缓存指针

- `FReflectionRegistry::Deinitialize()`（`:876-886`）：`Field2Class.Empty()` → 遍历 `FullName2Class` `delete Class` → `FullName2Class.Empty()`；**`UtilsClass`/`ObjectClass`/… 等 285 个 `FClassReflection*` 成员（`.h:616` 起）一个都不置空**。
- `Initialize()` 末尾（`:634-873`）会经 `GetClass(...)` 重新赋值 ⇒ **`Deinitialize → Initialize` 之间**存在悬垂窗口；若 `Initialize()` 中途失败，悬垂指针会长期保留。
- **处置建议 = 暂缓**：要给出可达性必须构造"域卸载后仍调用反射"的时序（编辑器关闭 / 热重载），属域重载装置轮；且修复形态（统一 `Reset` 285 个成员 vs 惰性校验）需要设计。

### 2.13 `F-GEN2-006`（2.80）—— 去重键不含签名，同名委托被静默丢弃

- `FDelegateGenerator.cpp:41-46`（单播）与 `:411-416`（多播）：`NameSpaceContent = GetClassNameSpace(prop)`、`ClassContent = GetFullClass(prop)`；`if (Delegate.Contains({NameSpaceContent, ClassContent})) return;`。
- 两个**不同**委托属性若落在同一命名空间且 `GetFullClass` 同名（非原生多播的命名空间不含类名时更易发生），第二个不生成。若两者签名不同，C# 侧要么缺类型、要么名字冲突 ⇒ 静默。
- **处置建议 = 暂缓**：把键换成签名（`SignatureFunction` 路径）会让同名不同类型**真的**生成两个同名 C# 类型（编译期冲突），所以修法必须连带命名/去重策略，不是一行改动。

### 2.14 `F-CS4-011`（2.80）—— 🟢 立项 ②（同簇）：替换函数只换末级目录名

- `FSolutionGenerator::ReplacePluginBaseDir`（`:194-203`）：取 `GetPluginBaseDir()` 的**最后一个 `/` 之后**的段，用它替换模板里的 `PLUGIN_NAME`（`UnrealCSharp`）。

- **判定**：成立 ⇒ 与 `F-GEN3-015` 合并为立项 ②（详见 §3.2）。
