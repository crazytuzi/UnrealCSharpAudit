## 1. 模块职责与架构速览

**ScriptCodeGenerator 模块本体是空壳。** `FScriptCodeGeneratorModule::StartupModule()` / `ShutdownModule()` 都是空函数体（`ScriptCodeGenerator.cpp:7-16`），不注册任何委托、不定时器、不挂钩子。整个模块的价值只在于它**编译进了一份静态工具集**（`FGeneratorCore` + 8 个 `F*Generator`），真正的调度在 `UnrealCSharpEditor` 模块里。

**`FGeneratorCore` 的三类职责**：
1. **反射 → C# 类型映射**（`GetPropertyType` / `GetPropertyTypeNameSpace` / `GetBufferCast` / `GetBufferSize` / `GetTypeImplementation` / `GetParamName` / `GetOutParam` / `GetReturn` …）——纯函数，无状态。
2. **可生成性判定与缓存**（`IsSupported` 6 个重载 + `SupportedMap` 缓存 + `IsSkip`）——**有状态静态缓存**。
3. **会话生命周期与清理**（`BeginGenerator` / `EndGenerator` / `AddGeneratorFile` / `DeleteRemainGeneratorFiles` / `GeneratorFiles`）。

**生命周期**：`FGeneratorCore` 全静态成员，**进程级生命周期**，`BeginGenerator` 填充、`EndGenerator` 清空（`FGeneratorCore.cpp:1024-1048`）。若中间抛异常/提前 return 而未走到 `EndGenerator`，静态状态会跨会话残留（详见 F-GENC-005）。

1. `GetOverrideFunctions` 每次返回一份 `TArray<FString>` 的深拷贝；map 里存的就是现成的数组，返回 `const TArray<FString>*`（或 `TArrayView`）即可零拷贝，并在为空时返回一个静态空数组，避免 `TArray<FString>{}` 每次构造。
2. `GetPropertyTypeNameSpace` 的递归 + `Union` 链是"每层新建集合"，且**没有任何缓存**——同一属性在同一次生成里会被 `FClassGenerator` 两次（属性遍历 :175、函数参数遍历 :447）重复计算。注意同文件的 `IsSupported` **有** `SupportedMap` 做记忆化（:860/:901/:926/:957），两套设计的投入不一致。既然 `SupportedMap` 已经用 `TWeakObjectPtr<const UObject>` 作键，类比的 `TMap<TWeakObjectPtr<const FProperty>, TArray<FString>>` 缓存是现成的模板。
3. 顺带：`TArray<FString>` 逐元素拷贝的 `FString` 分配无法避免，但配合 F-GENC-008 的排序改动，可以顺便一次排序 + 缓存。

**建议**
```cpp
// 返回指针，调用方自行判空
static const TArray<FString>& GetOverrideFunctions(const FString& InNameSpace, const FString& InClass);
// 实现里用一个 static const TArray<FString> Empty; 作为兜底
```
`GetPropertyTypeNameSpace` 改为"收集到调用方传入的 `TSet&` 出参"，避免每层返回新集合；并对已计算的 `FProperty*` 加缓存。

**验证方式**
`Select-String -SimpleMatch "GetOverrideFunctions"` 确认 3 个调用点；用 `-trace=memory` 或 Unreal Insights 抓一次全量生成的分配火焰图，观察 `TSet`/`TArray` 分配占比。

名字读作"枚举的**最大**索引"，但值恒为 `0`，且使用方式是把 `0` 传给 `GetDisplayNameTextByIndex` 取**第一个**枚举项（`_MAX` 在 UE 里位于 `NumEnums()-1`，绝不是 0）。也就是说这个名字与它做的事正好相反——读者会以为在取哨兵项 `XXX_MAX`，实际取的是第 0 项（`MetaData` 为空时的兜底默认枚举名）。这属于"代码说的和名字做的不一致"，会让后续维护者误改（例如有人"修正"成 `NumEnums()-1` 就会改变生成结果）。

**建议**
改名并改为常量：
```cpp
// FClassGenerator.cpp 内部（唯一的消费者，不必放 Public 头）
namespace { constexpr int32 EnumDefaultDisplayIndex = 0; }
```
若确实需要跨文件，放在 `Public/` 也应是 `inline constexpr int32 EnumDefaultDisplayIndex = 0;` 而不是宏（有类型、可调试、可被 IDE 跳转）。

**验证方式**
`Select-String -SimpleMatch "ENUM_DEFAULT_MAX_INDEX"`（应 4 命中）；`Select-String -SimpleMatch "ScriptCodeGeneratorMacro.h"`（应只有 `FClassGenerator.cpp:12` 一处 include）。

### [F-GENC-014] 7 处 `for (auto X : UsingNameSpaces)` 按值拷贝 `FString`；`Content +=` 拼接（澄清：UE 的 `FString` 不是 O(N²)）

- **类别**: 性能 / 可优化
- **严重度**: **P3**
- **复核结论**: **确认** —— 7 处按值迭代、2 处引用迭代、`Content +=` 计数、`StringBuilder` 分布全部逐项重跑一致
- **可达性**: **活跃**
- **复核证据**: `grep 'for \(auto UsingNameSpace : UsingNameSpaces\)'` → **7 命中**：`FClassGenerator.cpp:821`、`FStructGenerator.cpp:301`、`FEnumGenerator.cpp:87/216`、`FDelegateGenerator.cpp:347/670`、`FAssetGenerator.cpp:154`（行号与原文逐条一致）；`grep 'for \(const auto& UsingNameSpace : UsingNameSpaces\)'` → **2 命中**：`FBindingClassGenerator.cpp:688/974` ✓。`Content \+=|StringBuilder` 于本模块 → **53 命中**，其中 `StringBuilder` **14 命中且全部在 `FDoxygenConverter.cpp`（:422/426/430/433/440/444/447/451/455/458/464/468/471/474）**、`FGeneratorCore.cpp` 0 命中 → 相减得 `Content +=` **39 命中**，与原文两个数字（14 / 39）完全吻合。关于 `+=` 不是 O(N²) 的澄清成立（`FString::operator+=` → `TArray` 几何增长）。
- **级别变动**: 无（P3 维持：单次拷贝/临时字符串开销，量级上不构成性能问题）
- **文件**: `Source/ScriptCodeGenerator/Private/FClassGenerator.cpp:821`、`FStructGenerator.cpp:301`、`FEnumGenerator.cpp:87/216`、`FDelegateGenerator.cpp:347/670`、`FAssetGenerator.cpp:154`
- **函数**: 各 `F*Generator::Generator(...)` 内的 `using` 块构造循环
- **置信度**: 高（拷贝事实确定）；对"是否值得优化"取决于生成规模，故 P3

**现状（代码事实）**
```cpp
// FClassGenerator.cpp:821-826（FEnumGenerator.cpp:87、FAssetGenerator.cpp:154 等同一写法）
for (auto UsingNameSpace : UsingNameSpaces)      // 821: auto → FString 按值拷贝
{
    UsingNameSpaceContent += FString::Printf(TEXT("using %s;\n"), *UsingNameSpace);
}
```
对照：`FBindingClassGenerator.cpp:688` 与 `:974` 写的是 `for (const auto& UsingNameSpace : UsingNameSpaces)`（**正确**）→ 同一模块内风格不一致。
数量：`for (auto UsingNameSpace : UsingNameSpaces)` **7 命中**，`for (const auto& UsingNameSpace : UsingNameSpaces)` **2 命中**。

**问题与澄清**
1. 按值迭代对每个元素多一次 `FString` 拷贝（引用计数不适用，`FString` 是深拷贝），且元素本身通常不长——单次开销小，但生成一个类有成百上千个属性/参数时会累积。改成 `const auto&` 是零风险修改。
2. **关于 `+=` 在循环里的 O(N²) 判断，我必须纠正任务书的预设**：本模块确实大量用 `Content += ...`（`Content +=` 39 命中，`+=` 总计 84 命中），但 UE 的 `FString::operator+=` → `AppendChars` 会通过 `TArray` 的几何增长策略扩容（`Reserve` 的 slack 计算是几何级），因此**总字符数为 N 的循环 += 是均摊 O(N)，不是 O(N²)**（与 `std::string` 的朴素实现不同）。这里真实的开销是**每次迭代 `FString::Printf` 产生的一次临时分配 + 拷贝**，而非二次复杂度。
3. 模块内**已经**用了更好的模式：`FDoxygenConverter.cpp:422` `TStringBuilder<1024> StringBuilder;` 后面链式 `Append`（:426-474）。也就是说"用 builder 而不是 `Printf` 拼接"在本模块是已验证可行的，只是没有推广到各生成器（全模块 `StringBuilder` 14 命中，**全部集中于 `FDoxygenConverter.cpp`**，`FGeneratorCore.cpp` 0 命中）。

**建议**
- 机械替换 7 处为 `const auto&`。
- 对高频拼接（每个属性一行、每个参数一段）改用 `TStringBuilder<1024>`/`FStringBuilderBase`，`FString::Printf` 换成 `Appendf`；这样 `Content` 只在最后 `ToString()` 一次。

**验证方式**
`Select-String -SimpleMatch "for (auto UsingNameSpace : UsingNameSpaces)"`（应 7）；`Select-String -SimpleMatch "Content +="`（应 39）。优化后用 `stat namedevents` 或简单计时对比一次全量生成的耗时。
