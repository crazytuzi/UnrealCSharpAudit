## 1. 评估方法与评分维度

### 1.1 五个维度（每组候选逐项打分）

| 维度 | 含义 | 分值锚点 |
|---|---|---|
| **A 后果严重度** | 触发之后会发生什么 | 5 = 进程终止 / 堆破坏 / 数据静默损坏；4 = 功能静默错误、或确定性崩溃但需特定操作；3 = 资源泄漏（运行期不可回收 / OOM 风险）；2 = 纯性能 |
| **B 触发概率** | 普通用户命中它的难易 | 5 = 普通用户日常操作即可触发；4 = 正常使用偶尔触发；2–3 = 需要特定配置或数据；1 = 需要外部损坏的构建产物 / 边缘条件 |
| **C 影响面** | 一个修复覆盖多少代码 | 5 = 跨模块、影响整类 API；3 = 单模块；1 = 单文件 |
| **D 修复成本与风险（反向）** | 越小越好修 | 5 = 1 行或几行、低风险；4 = 小范围改动；3 = 中等（需先定契约）；2 = 需要重构；1 = 需要架构级改动 |
| **E 依赖关系** | 是否为其它修复的前置 | **E = 是**（不先修，后续修复会引入新错误或掩盖问题）额外 +0.30，并在 §4 单列 |

> **A 维的一处刻意取舍**：**资源泄漏一律记 3，不记 5**。这直接决定了"强 `GCHandle`"这类"被最多报告独立命中"的单点无法登顶（它是 **P1**，见 §3-G1）—— 因为它的直接后果是长会话内存单调增长，而不是进程消失或数据损坏。我不认为应该为了照顾"引用最多"而把 A 抬到 4：那会让本文件退化成"按引用次数排序"，与 §1.2 的公式目的相反。

### 1.2 综合分公式（可复核）

```
G = (A × B × C) ^ (1/3)          # 几何平均，1.00 ~ 5.00
f_D = 0.85 + 0.03 × D            # D=1 → 0.88；D=5 → 1.00
S = G × f_D + E + g
```

- **E**：前置项 `+0.30`，否则 `0`。
- **g（运行期门控微调）**：`+0.30` = 该缺陷只在 **LeanCLR** 下存在或强化，而当前配置正是 LeanCLR（**活跃路径**）；`0` = 后端无关；`−0.30` = 该缺陷只在 **Mono / CoreCLR** 下存在，而当前配置下不参与编译（**切回该后端即生效**）。
- 取值上限约 `5.00 × 1.00 + 0.30 + 0.30 = 5.60`。
- **为什么用几何平均**：`A×B×C` 的算术积会把三者互相放大（5·5·5=125 而 5·3·5=75，差 40 分），几何平均把量纲压回 1–5，使 A/B/C 之一为低值时**不足以被另外两维掩盖** —— 这正是让"触发概率为 2 的 P0"自然沉底、让"日常必触发但影响面窄"的项浮起来的机制。
- **本文件给出的 A/B/C/D/E/g 可以直接复算**（§2 每组都列出算式）；如果你对某个 B 值有不同判断，S 值与排序会变 —— 这是有意的，**不要把本文件的排序当成唯一解**。

### 1.3 门控规则（本工程的运行期事实，必须先确立）

**事实（两条）**：

1. **本工程五平台全 LeanCLR**：构建产物 `Intermediate/Build/{Win64,Android}/.../Definitions.UnrealCSharpCore.h:19-21` = `WITH_CORECLR 0 / WITH_MONO 0 / WITH_LEANCLR 1`（可实证）。
2. 🔴 **LeanCLR 下托管异常不终止进程**：`FLeanCLRDomain.cpp:834-852` 只解析 `RtMethodInfo*` 经 `Bridge_Invoke` 走解释器，`[UnmanagedCallersOnly]` 是**惰性元数据**；未捕获托管异常由解释器转成 `RtErr::ManagedException` + 全局异常槽（`interpreter.cpp:8368-8376`），**插件只打一条日志、调用方拿到零值**。而 **CoreCLR 下会 `TerminateProcess`**。⇒ 这一条**推翻了旧版"P-01 托管异常屏障 = P0"的前提**。

|---|---|---|
| **LeanCLR 专属缺陷（活跃路径）** | **升档**（`g = +0.30`），并在条目里写明"当前活跃路径" | `F-CS1-001`（`AssemblyLoader.Context` 恒为 null → `HandleData.Clear()`/`TypeBridge.Clear()` 整段被跳过）、`F-DOM-006`（域卸载时句柄表清理路径不可达）、`F-CS2B-027`（`Utils.cs:313` 先索引 `Segments[1]` 后判长度 → **必抛** `IndexOutOfRangeException`） |

## 7. ⚠️「撤销不可结案」与「错误撤销 > 高估」

### 7.1 风险不对称（最重要的方法论之一）

- **高估严重度的代价是浪费工时；错误撤销的代价是缺陷永久漏修。**
- 更糟的是："撤销（非缺陷）"带着**"已裁决"的标签**，因此**后续最不容易再翻出来** —— 它会让缺陷**永久消失在设计视野之外**。
- 由此确立的纪律：把"撤销（非缺陷）"的判定列为**最高抽验优先级**；汇总层重写"非缺陷清单"时**必须逐条核对**。

### 7.2 实测到的三类后果
