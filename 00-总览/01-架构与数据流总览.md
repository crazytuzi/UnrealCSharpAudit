## 第 1 章 一分钟速览

1. **UnrealCSharp 是一个把 C# 变成 UE 一等脚本语言的插件**（`UnrealCSharp.uplugin:5` FriendlyName，版本 1.2.0，作者 crazytuzi）。
2. 它解决的问题是：UE 原生只能用 C++/蓝图写逻辑，C++ 编译慢、蓝图难维护；本插件让**游戏逻辑用 C# 写**，同时仍然完整使用 UE 的反射、GC、编辑器与蓝图体系。
3. **不是"外部进程 + RPC"模式**，而是**同进程内嵌 CLR**：Mono / CoreCLR / LeanCLR 三种运行时都作为动态库被 C++ 模块加载，`Script/Interop/UE.dll` 通过 `DllImport` 反向调用引擎 C++ 导出函数。
4. 用户工作流：装插件 → 编辑器首次加载时由 `ScriptCodeGenerator` 扫描引擎反射数据生成 C# 绑定代码 + 生成 `.sln`/`.csproj` → 用户在 `Script/` 下用 C# 写类 → 保存触发 `FCSharpCompiler`（后台线程跑 `dotnet build`）→ 成功后重新加载程序集并重建脚本域（热重载）。
5. C# 侧写 `[UClass]` 标记的类，插件会在运行时**动态造出真正的 `UClass` + `FProperty` + `UFunction`**，让这些类像原生类一样能被 UE 实例化、被蓝图引用、被 GC 管理。
6. 反向也成立：C++/蓝图里有 `BlueprintImplementableEvent`/`BlueprintNativeEvent` 的函数，可以在 C# 侧 `override`；C++ 调这些 `UFUNCTION` 时会被劫持到托管实现。
7. 劫持机制是**把 UFunction 的 native 函数指针改成 `UCSharpFunction::execCallCSharp`**（`Source/UnrealCSharp/Private/Registry/FCSharpBind.cpp:475`），因此 C++/蓝图/网络复制走的都是 UE 原生调用路径，只是最后一步跳进 C#。
8. 反射元数据在 C++ 侧由 `FReflectionRegistry` 持有（`FReflectionRegistry.h:7`），它把每个托管 `Type` 包装成 `FClassReflection`，把方法包装成 `FMethodReflection`；FProperty/UFunction 与托管侧的名字通过**名字编码**（`FUnrealCSharpFunctionLibrary::Encode`）对齐。
9. C# 侧的元数据在编译期由 **Roslyn SourceGenerator** 和 **Fody Weaver** 两条并行路径注入/生成，另有 `Script/Interop/AssemblyLoader` 负责程序集装载。
10. 三种后端统一在 `IScriptDomain`（`IScriptDomain.h:8`）抽象下，实现类分别是 `FMonoDomain`(520 行) / `FCoreCLRDomain`(312 行) / `FLeanCLRDomain`(889 行)——**LeanCLR 实现体量是 CoreCLR 的约 2.85 倍，抽象并不完全对称**（见 F-ARCH-004）。
11. 模块加载顺序由 `.uplugin` 决定，但**真正的初始化时机不是模块加载完成，而是 `ELoadingPhase::PostDefault` 完成事件**（`FEngineListener.cpp:51-53`）触发的 `FUnrealCSharpCoreModule::Activate()`。
12. `UnrealCSharpCore` 模块是一个**显式状态机**（`Inactive/Active/Outdated`，`UnrealCSharpCore.h:36-45`），"Outdated" 表示 C# 程序集已更新但尚未重载——这是热重载设计的关键状态。
13. `UUnrealCSharpSetting` 支持**按平台**选择脚本后端（`FScriptDomainFactory.cpp:16` 用 `FPlatformProperties::IniPlatformName()` 作 key）。
14. 运行时全局状态高度依赖**函数局部 static 单例**：`FCSharpEnvironment::Environment`(静态成员)、`FReflectionRegistry::Get()` 的 `static` 局部变量、`FCSharpCompiler::Get()` 的 `static`——缺少显式生命周期所有权（见 F-ARCH-006）。
15. 插件不支持在没有编辑器的情况下改绑定：`ScriptCodeGenerator` 与 `Compiler` 都是 `Editor` 类型模块，`SourceCodeGenerator` 是 `Program` 类型（`UnrealCSharp.uplugin:30-53`）。

**差异要点**：
1. **只有 Mono 有 Profiler**（`FMonoProfiler.h` 30 行 / `.cpp` 82 行），CoreCLR 与 LeanCLR 无对应物——`IScriptDomain` 里也没有 profiler 相关方法，说明它是 Mono 专属旁路。
2. **LeanCLR 是"特例分支最多"的后端**：C# 侧源码里出现 `#if WITH_LEANCLR`（`UnrealTypeSourceGenerator.cs:910`），意味着**后端差异泄漏到了生成的 C# 代码中**，而不是被 C# 侧抽象吸收。
3. 函数表驱动：`IScriptTypes.h:107-182` 用 `COMMON_BRIDGE_METHODS` / `NATIVE_BRIDGE_METHODS` / `UTILS_BRIDGE_METHODS` 三个宏列表 + `SCRIPT_TYPES` 展开成函数指针成员（`:177`）。三后端共用同一张表结构，但**表项的填充方式各不相同**（`MethodBridgeRegisterBinding` 在 NATIVE 组 :166，`MethodBridgeInvoke` 在 COMMON 组 :150——注册方向相反）。

> **补正（本工程实际配置 = 五平台全部 LeanCLR，`WITH_CORECLR 0 / WITH_MONO 0 / WITH_LEANCLR 1`）**：
> ③ **LeanCLR 下 C++→C# 不走本机函数指针**——`Bridge_Invoke` 由解释器执行，因此上表"实现类/通道"一栏不能理解为"C++ 侧拿一个托管函数指针直接 call"；`FDomain`/`FMethodReflection::Runtime_Invoke`（`FMethodReflection.cpp:80-88`）看到的仍是统一接口，差异被 `FLeanCLRDomain::Invoke` 吸收。第 4.1 表只描述了 C#→C++ 方向（DllImport vs `delegate*`），本行补充 C++→C# 方向差异。
> ④ **托管异常后果因后端而异**：LeanCLR 下**不终止进程**（`RtResult` 协议，调用方拿到零值），CoreCLR 下会 `TerminateProcess`（fail-fast，`try/catch` 无效）。因此 §3.2 流程二第 [6] 步"最终落到托管侧函数表的 `method_bridge_invoke_fn`"在 LeanCLR 下的准确表述是"经 `Bridge_Invoke` 进入解释器执行，异常以 `RtResult` 返回"，**调用方拿到的零值不会抛异常、也不会被 `check()` 拦下**——这是排查"函数静默返回默认值"类问题的关键前提。
> 以上两条是已核实的地面事实（未再回 LeanCLR 源码逐行复核，故标为补正而非新发现）。
>
> **本表行数口径说明**：本表 `.h` 行数（160 / 142 / 227）为**总行数（含空行）**；`F-ARCH-004` 表的 `.h` 行数（98 / 92 / 144）为**非空行数**（`Measure-Object -Line` 会忽略空行）。两口径**均正确，不是矛盾**（实测裁定；`FMonoDomain.h` 160/98、`FCoreCLRDomain.h` 142/92、`FLeanCLRDomain.h` 227/144）。`.cpp` 的 520 / 312 / 889 在两表中一致，正是因为这三个数本来就按总行数写。

**问题**
后端选择（LeanCLR vs 其他）本应由 C++ 侧 `FScriptDomainFactory`（`FScriptDomainFactory.cpp:22-45`）+ 构建系统 `WITH_*` 宏独自决定；但现在 C# 源码也必须定义 `WITH_LEANCLR` 才能编过，导致：
1. **同一份 `Script/` 产物不能跨后端复用**——切换后端必须重新编译整个 C# 工程。

让 C# 侧只依赖"通道能力"而非"后端名"：把 `#if WITH_LEANCLR` 换成 `#if UNREALCSHARP_INTEROP_PINVOKE` 之类**由能力推导**的符号，或在 `Interop` 工程里统一包装成 `MethodBridge.GetMethod`（LeanCLR 下让 `GetMethod` 内部走 `NativeLibrary.GetExport`），从而让源生成器只产出一条代码路径。取舍：LeanCLR 下多一层间接调用（可忽略），收益是三个后端在 C# 侧真正同构。

**验证方式**
