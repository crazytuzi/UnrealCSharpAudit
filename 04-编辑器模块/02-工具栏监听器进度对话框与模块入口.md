## 1. 模块职责与架构速览

`FUnrealCSharpEditorModule`（`IMPLEMENT_MODULE`，`UnrealCSharpEditor.cpp:397`）是编辑器侧的总装点，在 `StartupModule` 中一次性完成 9 类注册，并把长期存活对象作为**值成员**持有：

```
FUnrealCSharpEditorModule
├── FEditorListener EditorListener            (.h:55, 值成员，非指针)
├── TSharedPtr<FUnrealCSharpPlayToolBar>      (.h:37)
├── TSharedPtr<FUnrealCSharpBlueprintToolBar> (.h:39)
├── TUniquePtr<FAutoConsoleCommand> ×5        (.h:45-53)
├── TStrongObjectPtr<UDynamicDataSource>      (.h:61)
├── FDelegateHandle ×2                        (.h:41,43)
└── FTSTicker::FDelegateHandle TickHandle     (.h:57)
```

三条独立的"编译触发"入口，最终都汇聚到 `FCSharpCompiler` 单例（`FCSharpCompiler.cpp:29-34`），由它背后的 `FCSharpCompilerRunnable` 工作线程执行 `dotnet build`：

1. **工具栏按钮** → `PluginButtonClicked()`（`UnrealCSharpEditor.cpp:248`）→ `Generator()`（314）→ `FCSharpCompiler::Get().ImmediatelyCompile()`（388）→ **在调用线程（游戏线程）同步执行整个构建**。
2. **文件变更 / 蓝图编译 / 资产变更** → `FEditorListener::Compile()`（636）→ `FCSharpCompiler::Get().Compile()`（无参重载）→ `EnqueueTask()` → **异步交给工作线程**。
3. **PIE 启动前** → `OnPreBeginPIE`（188）→ `WaitForCompile()`（676）→ 阻塞游戏线程 + `SCompileProgressDialog` 进度窗轮询。

进度数据的跨线程通路是：工作线程写 `FCSharpCompileProgress`（`FCriticalSection` 保护）→ 游戏线程在 `WaitForCompile` 循环中 `GetCompileProgress()` 拉取 → `SCompileProgressDialog::UpdateProgress()`。**这是拉模型（poll），不是推模型**，这一点决定了 §3.3 的结论。

### [F-ED2-001] `FEditorListener` 对 AssetRegistry 的 5 个 `AddRaw(this,…)` 委托句柄全部丢弃且从不反注册 → 监听器销毁后回调悬空 `this`

- **严重度**: **P0**
- **复核结论**: **确认**（5 处 `AddRaw` 句柄丢弃 + 析构无对应 `Remove` 均为代码事实；`AddRaw` 不跟踪生命周期，与 `AddSP`/`AddWeakLambda` 不同）

**调用上下文**
- `FEditorListener` 是 `FUnrealCSharpEditorModule` 的**值成员**（`Public/UnrealCSharpEditor.h:55`），因此它的 `~FEditorListener()` 在模块对象析构时（模块卸载 / 编辑器关闭）才执行。而 `FAssetRegistryModule` 是引擎级单例，其委托列表的生存期**长于**编辑器模块。
- 反注册缺失的后果是 `FAssetRegistry::OnAssetAdded` 等委托里保留了一个已析构的 `FEditorListener*`。此后任何一次资产新增/删除/改名/磁盘更新都会跳到已释放内存执行 `OnAssetAdded` → `OnAssetChanged` → `FGeneratorCore::BeginGenerator` + `FCSharpCompiler::Get().Compile()`。
- 该调用点在编辑器关闭阶段仍然活跃：内容浏览器与资产注册表在模块卸载之后仍在处理扫描结果与保存的资产事件。

**问题**
1. **必然的 use-after-free**：5 个 `AddRaw` 全部无 Remove。`AddRaw` 不做任何生命周期跟踪（不同于 `AddSP`/`AddWeakLambda`），只是裸指针。
2. **重复注册放大**：`FAssetRegistry::OnFilesLoaded` 在资产注册表**每次完成加载**时都会广播（初始扫描完成、`ScanPathsSynchronous` 重扫完成等），而 `OnFilesLoaded()` 每次被调用都会再 `AddRaw` 一次这 4 个委托。于是：(a) 同一 `this` 在同一个多播委托里被注册 N 次，一次资产变更会触发 N 次 `OnAssetAdded`（N 次代码生成 + N 次编译请求）；(b) 析构后悬空的条目也有 N 份。
3. 与同仓库的正确实现形成鲜明对比：`FClassCollector`（`Source/UnrealCSharpEditor/Private/NewClass/ClassCollector.cpp:47-63` 注册 / `:86-116` 反注册）对**同样这 5 个委托**逐个保存句柄并在析构中 Remove——说明这是 `FEditorListener` 单独的疏漏，而不是"引擎不允许反注册"。

   - **情况 2（非死锁）**：`:242` 由**工作线程**执行（`DoWork()`，`:156-162`）且游戏线程在 `WaitForCompile` 循环里持续 `ProcessThreadUntilIdle(ENamedThreads::GameThread)`（`FEditorListener.cpp:744`）→ 游戏线程会执行该任务。

3. 通过 `Thread->Kill(true)` + `delete Runnable` 强制结束，还可能打断 `SyncProcess` 中的子进程读取线程（`FCSharpCompilerRunnable.cpp:413`），造成 `dotnet` 子进程残留。
4. **（由 F-ED2-004 并入的 P3 残留）** `Exit()`（`FCSharpCompilerRunnable.cpp:102-110`）归还事件池并把 `Event` 置 `nullptr`，而 `EnqueueTask()`（`:125`、`:143`）与 `Stop()`（`:96-99`）**都做了判空，只有 `EnqueueTask` 的两处没有**（不对称）。按上面的时序分析该残留不可达（`Exit()` 之后 `Runnable` 立即被 `~FCSharpCompiler` 删除，`FCSharpCompiler.cpp:17-25`），但属于"关闭期共享状态"的同类问题，建议与情况 3 一起修：`if (Event != nullptr) { Event->Trigger(); }`，或改用 `FEventRef Event{EEventMode::AutoReset};` 成员。

**建议**
- 把单例的销毁提前：在编辑器关闭的确定时点（例如 `FCoreDelegates::OnPreExit` 或 `FUnrealCSharpEditorModule::ShutdownModule`）显式做一次"停止编译线程"的调用，而不是依赖静态析构。

                                              FText* const OutReason) const
{
    const auto Fail = [OutReason](const FText& Reason)
    {
        if (OutReason) { *OutReason = Reason; }
        return false;
    };

    if (bUseRelativePath)
    {

            ? AbsoluteDirectory

        {

                LOCTEXT("Error_InvalidRootPath", "The chosen directory must be within {0}"),

        }

    if (!PlatformFile.DirectoryExists(*AbsolutePath))

            FText::AsNumber(AbsolutePath.Len()),
            FText::AsNumber(PLATFORM_MAX_FILEPATH_LENGTH - ReservedLength)));

    return true;
}

## 3.3 专项：`SCompileProgressDialog` 的跨线程安全（对应任务书 C 段）

**结论：不存在"编译线程直接调用 Slate"的 P0 缺陷。** 该链路的线程安全设计是正确的，证据如下。

**(a) 编译线程从不接触任何 Slate 对象。** `FCSharpCompilerRunnable` 中所有触及 Slate 的位置都做了显式线程跳转：

| 位置 | 目的 | 是否跳游戏线程 |
|---|---|---|
| `FCSharpCompilerRunnable.cpp:325-382` | 创建 "Compiling Scripts" 进度通知 + 注册进度 ticker | ✅ `AsyncTask(ENamedThreads::GameThread, …)` |
| `FCSharpCompilerRunnable.cpp:419-434` | 移除 ticker + `Fadeout()` 通知 | ✅ `AsyncTask(ENamedThreads::GameThread, …)` |
| `FCSharpCompilerRunnable.cpp:441-464` | `ShowCompileResultNotification` → `FSlateNotificationManager::QueueNotification` | ✅ `AsyncTask(ENamedThreads::GameThread, …)` |
| `FCSharpCompilerRunnable.cpp:213-240` | `Deactivate()/InFunction()/Activate()` | ✅ `ENamedThreads::GameThread`（任务参数） |
| `FCSharpCompilerRunnable.cpp:207` | `OnCompile.Broadcast` | ❌ **未跳转**（见 F-ED2-002，但该处理器不碰 Slate） |

**(b) 进度状态是"工作线程写 / 游戏线程读"，且两端都在锁内。**
```cpp
// 写侧（工作线程，经 SyncProcess 的输出回调）
FCSharpCompileProgress.cpp:39-55   SetOutput() → FScopeLock(&CriticalSection)      // :41
FCSharpCompileProgress.cpp:21-37   SetStage()  → FScopeLock(&CriticalSection)      // :23
FCSharpCompileProgress.cpp:57-64   Flush()     → FScopeLock(&CriticalSection)      // :59
// 读侧（游戏线程，FEditorListener.cpp:729）
FCSharpCompileProgress.cpp:66-71   GetStage()  → FScopeLock(&CriticalSection)      // :68
```
`FScopeLock` 是 RAII 锁，四个入口全部覆盖；`CriticalSection` 是 `FCSharpCompileProgress.h:45` 的非 `mutable` 成员（读侧用 `const_cast`，见 F-ED2-012，仅风格问题）。

**(c) `SCompileProgressDialog` 只在游戏线程被创建与更新。** 唯一调用点是 `FEditorListener::WaitForCompile`：
```cpp
690: 			ProgressDialog = SNew(SCompileProgressDialog);      // 游戏线程
...
733: 			ProgressDialog->UpdateProgress(StatusMessage, ElapsedSeconds);   // 游戏线程
```
而 `WaitForCompile` 由 `FEditorDelegates::PreBeginPIE`（`:215`）驱动，是游戏线程委托。

**(d) widget 提前销毁的场景已被正确使用 `TSharedPtr` 处理，不会访问已销毁 widget。** `ProgressDialog` 与 `ProgressWindow` 都是 `WaitForCompile` 的**局部 `TSharedPtr`**（`:682-684`），生命周期完全由该函数栈决定；循环内每次使用前都有 `ProgressDialog.IsValid()`（`:724`）。销毁顺序也是安全的：
```cpp
747: 	if (ProgressWindow.IsValid())
748: 	{
749: 		ProgressWindow->SetContent(SNullWidget::NullWidget);   // 先断开 Content 对对话框的强引用
750:
751: 		ProgressWindow->RequestDestroyWindow();
752:
753: 		TickProgressWindow(ProgressWindow);
754: 	}
```
`:749` 先把窗口内容换成 `SNullWidget`（解除 `SWindow → SCompileProgressDialog` 的强引用），再销毁窗口——这样不存在"窗口还持有 widget 而 widget 已析构"的窗口期。

**(e) `SCompileProgressDialog` 自身无循环引用。** `StatusText`/`ElapsedText`（`SCompileProgressDialog.h:22,24`）由 widget 强引用，同时作为 `ChildSlot` 的子节点被父节点强引用；子节点回指父节点用的是 Slate 内部的弱引用（`SWidget::ParentWidget`），因此**不存在 P1 级的 `TSharedPtr` 循环导致面板永不释放**。`WaitForCompile` 返回时两个局部 `TSharedPtr` 同时释放，widget 与窗口一起回收。

**(f) 残余风险（已单列为发现）**
- `FEditorListener.cpp:686` 的 `FSlateApplication::Get().CanDisplayWindows()` **没有 `FSlateApplication::IsInitialized()` 守卫**，而同文件 `:122` 的析构路径有守卫、`:655-672` 的 `TickProgressWindow` 直接使用 `FSlateApplication::Get().GetRenderer()`（`:672`）——风格不一致，且在无 Slate 的环境（`-nullrhi` / 服务器 / 某些 commandlet 流程）下 `FSlateApplication::Get()` 可能断言失败。**这是本组最接近"P0 崩溃"的未验证点**，但触发需要"无 Slate 环境下走到 `PreBeginPIE`"，正常情况下不可达，故未列为 P0。
- `ProgressDialog` 不是 `TWeakPtr`，但由于它是局部变量而非跨帧缓存，**不需要** `TWeakPtr`。任务书中"是否用 `TWeakPtr`"的担心在此处不成立。

**(g) 编译线程与游戏线程的握手（`:242` `WaitUntilTaskCompletes`）** 是这套设计里唯一需要游戏线程配合的地方：游戏线程必须在等待期间持续泵任务图。`WaitForCompile` 的 `:744` `ProcessThreadUntilIdle(ENamedThreads::GameThread)` 正是为此存在。这也解释了 F-ED2-005 的严重性——**如果 `WaitForCompile` 的循环因为任何原因退出（例如被改成带超时后直接 break），`:242` 就会永久等待**。修复 F-ED2-005 时必须保留"继续泵任务图"的动作。
