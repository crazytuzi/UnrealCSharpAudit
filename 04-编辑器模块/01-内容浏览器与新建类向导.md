## 1. 模块职责与架构速览

两条相对独立的链路，共用一个“动态类”概念。

### 1.1 内容浏览器数据源（只读展示 + 删除/打开）

- `UDynamicDataSource : UContentBrowserDataSource`（`DynamicDataSource.h:42-149`）是插件注册的自定义内容浏览器数据源，名字硬编码为 `"DynamicData"`（`UnrealCSharpEditor.cpp:147`），由编辑器模块用 `TStrongObjectPtr` 持有（`UnrealCSharpEditor.h:61`）。
- 它把 `/Classes_Script` 声明为挂载根：`BuildRootPathVirtualTree()` → `Super::BuildRootPathVirtualTree()` → `RootPathAdded("/Classes_Script")`（`DynamicDataSource.cpp:683-688`，常量见 `CoreMacro/Macro.h:115`；虚拟根 `DYNAMIC_ROOT_VIRTUAL_PATH = "/All/Classes_Script"`，`Macro.h:117`）。
- 目录树的真身在 `FDynamicHierarchy`（`DynamicHierarchy.cpp`）：一棵 `TMap<FName, TSharedPtr<FDynamicHierarchyNode>>` 的树，节点 key 是**脚本目录下的相对路径**（`AddClass` 里 `Path.RightChop(GetFullScriptDirectory().Len())`，`DynamicHierarchy.cpp:200-201`），节点里挂 `TSet<UClass*>`。树的来源是 `FDynamicClassGenerator::GetDynamicClasses()` + 每个类的 `.cs` 文件是否存在（`DynamicHierarchy.cpp:194-195, 229-232`）→ 也就是说**每次重建都要对每个动态类做一次文件系统查询**。
- `FContentBrowserItemData` 的 payload 分两种：`FDynamicFileItemDataPayload`（持 `FName InternalPath` = 磁盘 `.cs` 路径、`TWeakObjectPtr<UClass>`、`FAssetData`）与 `FDynamicFolderItemDataPayload`（只持 internal path）。
- 可写操作只有两个：`EditItem`（用 `FSourceCodeNavigation::OpenSourceFile` 打开 `.cs`，`DynamicDataSource.cpp:523-530`）与 `DeleteItem`（走事务 + `IFileManager::Delete` + 立即重编译，`DynamicDataSource.cpp:547-590`）。重命名/移动/复制/新建文件夹/物理路径等均未实现（§3 F-ED1-023）。

### 1.2 新建类向导

- 入口两条：内容浏览器右键 “New dynamic Class...” → `PopulateAddNewContextMenu` → `FDynamicNewClassContextMenu::MakeContextMenu`；以及工具栏命令 `OpenNewDynamicClass`（`ToolBar/UnrealCSharpPlayToolBar.cpp:50-56`）。两者都汇入 `FDynamicNewClassUtils::OpenAddDynamicClassToProjectDialog`（`DynamicNewClassUtils.cpp:12-48`），创建 `SWindow` + `SDynamicNewClassDialog`。
- `SDynamicNewClassDialog`（1010 行）是一个两页 `SWizard`：第 1 页选父类（“Common Classes” = `FFeaturedClasses` + `FNewClassInfo`，或“All Classes” = `SDynamicClassViewer`），第 2 页填类名/路径/类型（C++/Blueprint）并预算出 `.cs` 目标路径。
- 类名/路径合法性由 `UpdateInputValidity()` 统一判断（`SDynamicNewClassDialog.cpp:864-953`），结果写入 `bLastInputValidityCheckSuccessful`，同时驱动 `SWizard::CanFinish` 与错误提示条。
- 生成动作 = 读插件模板 `Plugins/UnrealCSharp/Template/Dynamic/Dynamic{Actor,ActorComponent,UserWidget,Object}.cs` → 字符串替换（命名空间 using、基类、类名）→ `FUnrealCSharpFunctionLibrary::SaveStringToFile`（UTF-8 无 BOM）→ `FSourceCodeNavigation::OpenSourceFile`。
- “All Classes” 页的数据来自静态的 `FClassCollector`（`ClassCollector.cpp`），它把全编辑器的 `UClass` + AssetRegistry 里的 Blueprint 资产汇总成 `TSet<TSharedPtr<FDynamicClassViewerNode>>`，再摊平成 `TArray` 供 `SListView` 使用。

### 1.3 生命周期速览（关键结论）

- `UDynamicDataSource` 的两个运行时委托用 `AddUObject` 绑定（弱对象），`Shutdown()` 里成对 `Remove`（`DynamicDataSource.cpp:63-67, 96-104`），并在 `Shutdown()` 里 `DynamicHierarchy.Reset()`。这一处是健康的。
- `FClassCollector` 是**静态 `TSharedPtr`**（`SDynamicClassViewer.cpp:7`），没有析构/Reset 路径；它共向 9 个委托源注册了静态回调（构造里 8 个：`ClassCollector.cpp:36/40/43/48/54/57/60/63`，第 9 个 `OnEndFrame` 于 `:142` 动态注册），其中 `FCoreDelegates::OnEndFrame` 的注册**只增不减且句柄被覆盖**（§3 F-ED1-001）。
- Slate 侧：本组的 `.Method(this, &Class::Fn)` 绑定不需要手工 Unbind——UE 5.6 的 `SLATE_EVENT` 裸指针重载走 `CreateSP`（`DeclarativeSyntaxSupport.h:519-530`），而 `TBaseSPMethodDelegateInstance` 存的是 `TWeakPtr`（`DelegateInstancesImpl.h:320`），因此**不会**形成 widget↔delegate 循环引用。凡按“可能会循环引用/可能需要 Unbind”预期去查的点，我逐一核到了引擎实现，未发现真实泄漏（唯一例外是 §3 F-ED1-022 的裸 `this` lambda 捕获，属隐患不属泄漏）。

### P1

### [F-ED1-001] `FClassCollector` 在 `OnEndFrame` 上重复注册且永不注销：请求之后每帧做全量类扫描 + 全量资产查询，委托无限累积

- **类别**: 内存/资源泄漏 + 性能
- **严重度**: **P1**
- **复核结论**: 确认
- **可达性**: 活跃
- **复核证据**: `Source/UnrealCSharpEditor/Private/NewClass/ClassCollector.cpp:131-143`（`RequestPopulateClassHierarchy` 仅按 `GFrameNumber` 防同帧重复，`:142` 无条件 `OnEndFrame.AddStatic`）；`:92-95` 为唯一 Remove 点；`:145-152` 全量扫描；`SDynamicClassViewer.cpp:7,17-20`（静态 `TSharedPtr`，全工程无 `Reset`/析构路径）。grep 复核：模式 `OnEndFrame` 在 `Source/` 递归命中 **5** 处（`ClassCollector.h:73`、`ClassCollector.cpp:21/92/94/142`），与原文数字一致。引擎侧确认「AddStatic 不去重」：`Runtime/Core/Public/Delegates/DelegateSignatureImpl.inl:793-797` = `Super::AddDelegateInstance(FDelegate::CreateStatic(...))`，无查重（查重版为 `AddStaticUnique`），故句柄被覆盖即代表旧的注册永久留存。`FCoreDelegates::OnEndFrame` 每帧广播属引擎主循环常量行为（未在本仓逐行引证，同原文 §5.2）。
- **级别变动**: 无（P1 维持；原文把「注册来源 5 处」「析构里 Remove 数」写错，属非 Finding 项，不影响定级）
- **文件**: `Source/UnrealCSharpEditor/Private/NewClass/ClassCollector.cpp:131`（`RequestPopulateClassHierarchy`）、`:142`（AddStatic）、`:92-95`（析构里的 Remove）、`:145`（`PopulateClassHierarchy`）；`Source/UnrealCSharpEditor/Private/NewClass/SDynamicClassViewer.cpp:7,17-20`

**调用上下文**
`FClassCollector` 构造（`ClassCollector.cpp:31-65`）在用户第一次切到向导的 “All Classes” 页时执行，紧接着就调用 `PopulateClassHierarchy()`（`:33`）并注册 8 个委托（另有 `OnEndFrame` 于 `:142` 动态注册，共 9 个）。首次 `OnFilesLoaded`/`OnDynamicClassUpdated` 到来后 → `RequestPopulateClassHierarchy` → `AddStatic`。引擎每帧 `FCoreDelegates::OnEndFrame.Broadcast()`（`Runtime/Launch` 主循环）→ 调用 `PopulateClassHierarchy`。

**问题**
两层缺陷叠加：
1. **永不注销**：`OnEndFrame` 上的委托在第一次请求后一直存在，所以**此后每一帧**都要跑一遍 `TObjectIterator<UClass>`（大工程数万个 UClass）+ `GetAssetsByPaths(..., true)`（对 `/Game` 等支持路径的全量 AR 查询并复制全部 `FAssetData`）+ `TSet::Array()` 全量拷贝。这是编辑器常驻性的每帧开销。
2. **无限累积**：句柄被覆盖，只有最后一个可被移除；`RequestPopulateClassHierarchy` 每个“有新请求的帧”都会再 `AddStatic` 一份**同一个静态函数**。于是 `PopulateClassHierarchy` 每帧被调用 K 次，K = 会话中发生过请求的不同帧数——工作量随会话时长单调增长（典型 O(帧数) 的每帧重复扫描）。`~FClassCollector` 只能摘掉 1 个，其余仍指向模块内的静态函数，同时静态 `TSharedPtr` 使析构时机推迟到 DLL 卸载（模块热重载/卸载路径上留下的委托指向已卸载模块的代码）。

**建议**
```cpp
// 方案 A（最小改动）：请求时先摘再挂，只保留一个挂载
void FClassCollector::RequestPopulateClassHierarchy()
{
	static auto LastRequestFrame = 0u;
	if (LastRequestFrame == GFrameNumber) { return; }
	LastRequestFrame = GFrameNumber;
	if (OnEndFrameDelegateHandle.IsValid())
	{
```
