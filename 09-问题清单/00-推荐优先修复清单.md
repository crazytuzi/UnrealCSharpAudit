**引擎依据（决定性）**：`Runtime/CoreUObject/Public/UObject/UnrealType.h:4015-4021` 的 `AddUninitializedValues(int32 Count)` = `WithScriptArray([...]{ return Array->Add(Count, ElementSize, ElementAlignment); })` —— **`AddUninitialized*` 只裸分配、绝不构造**。⇒ 在它的产物上调用 `InitializeValue` 是**引擎契约要求的正确行为**；反之对其调用 `DestroyValue` 才是 **UB / 二次释放**。旁证：`UnrealType.h:1434` 的 `InitializeValue` 契约原文 *"this assumes over uninitialized memory"*。

## 4. 修复顺序建议（不是级别顺序）

> 判据：不先做前者，后者的修复会**引入新错误**、**无法验证**、或**掩盖问题**。

| # | 先做 | 后做 | 为什么顺序不能反 |
|---|---|---|---|
| 1 | **P0-4 容器索引/句柄契约**（C# 侧索引器改抛 .NET 异常） | **P0-3 Interop 导出层判空**（native 侧 `Checked()` 样板） | 不是"先有异常屏障才能抛异常"——LeanCLR 下已确证**托管异常不终止进程**（走 `RtResult`、调用方拿零值），屏障不是硬前置；但改 native 侧会把可自诊断的失败与"合法 0 句柄"混为一谈 ⇒ **先定 C# 侧的契约** |
| 2 | **P0-2 对象/委托描述符 Set 判空** | **§2 组的"挂起/悬空委托"族** | 描述符 `Set` 的判空是"输入契约"的统一落点；不先统一，每个族会各写一套判空，覆盖率无法确认（`F-INT2-016` 的 `&In != nullptr` 就是"看起来判了空、其实被优化掉"的实例） |
| 3 | **P0-5 `TOut` 步长 + `F-GEN2-001` 缺括号** | 任何"多返回值 API"的功能验证 | 两者是 **OUT_BUFFER 协议的写端与读端**，**必须同批改**；只修一端时 `GetIdentity`/`GetDate` 这类多 out 场景仍取不到正确值。⚠️ **两者不是同一族**（见 P0-5），需**分别修** |
| 4 | **§2-G1 强 `GCHandle` 释放责任归属** | **§2-G10 容器/注册表"只增不减"+ 裸地址为键** | 很多"只增不减"其实是"**减的责任被交给了永不执行的终结器**"。不先厘清责任归属，会把**责任错位**误判为**真泄漏**，从而给本来正确的释放代码加多余的 `Compact()` |
| 5 | **§2-G4 域代次（generation）机制** | **§2-G10 + P0-2 的跨域部分** | 否则同一批容器要在"无代次"和"有代次"两套结构上各改一遍，第二遍还会引入新的失效判断 |
| 6 | **P0-7 工厂返回值判空**（`FTypeBridge::Factory` / `FScriptDomainFactory::Create`） | **§2-G7 的"启动期汇总校验"** | 工厂的 `nullptr` 语义是"不支持/未编译进来"的唯一表达；不先统一，启动期校验没有可依赖的失败信号 |
| 7 | **§2-G5 编译入口收口**（同步入口绕过 `IsCompiling()` 守卫） | **§2-G5 的竞态修复（`TQueue` 契约）** | 同步入口绕过守卫时会有**两个 `dotnet build` 并发**，会把真正的竞态因果掩盖掉 |
| 8 | **§2-G6 关停期死锁（`Kill(true)` 互等）** | 进程退出路径的任何验证 | 已经互等的进程无法用来验证别的修复 |
| 9 | **P0-11 `F-GENC-001` 4 处反序列化返回值检查** | 产物类缺陷的验证 | 损坏的 `Intermediate/*.json` 会在**第一次保存资产时**崩，先修它才能稳定复现其它生成期问题 |
| 10 | **§1.1 ⚠️ 误修警戒（活值 Dest 4+4 点）** | 任何"统一给 `Set` 加 `DestroyValue`"的批量改动 | 不先钉住这 4 个"不要改"的点，**按旧清单施工会引入比原缺陷更严重的 UB**（对未初始化内存调析构） |

- **P0-8（编辑器委托句柄配对）可以完全独立进行**：它是全清单里"收益/成本"最好的一组（句柄存进容器 + `ShutdownModule` 统一 `RemoveAll`），不阻塞任何其它修复。
