### V-2 `F-ABI-009` —— signal handler（Windows / Linux 分支）

| 项 | 内容 |
|---|---|
| **代码** | `FCSharpEnvironment.cpp`：信号类型表 `:103-120`；注册循环 `:122-144`（`#if PLATFORM_MAC` 用 `sigaction` 并**保存原处理器** `:135`，`#else` 仍是裸 `signal(SignalType, SignalHandler)` `:142`）；恢复路径 `:29`；handler 本体 `:22` |
| **已核实的两个开放面** | ① Windows/Linux **不保存原处理器**（只有 Mac 保存 ⇒ 卸载/退出时无法恢复）；② handler 体内调用 `UE_LOG(LogUnrealCSharp, Error, …)` + `GLog->Flush()` + 托管侧 `FDomain::GetTraceback()`，**均非 async-signal-safe** |
| **前置** | Windows 编辑器一份；Linux 编辑器一份（`F-ABI-011` 也在此列） |
| **步骤** | 1) 触发一次受管崩溃（`SIGSEGV`/`SIGFPE`）观察打印的托管堆栈是否完整；2) 正常退出编辑器，观察是否有残留信号处理器/退出期异常；3) 在同一进程内二次初始化插件（热重载）后崩溃，观察原处理器是否被正确恢复 |
| **期望** | 崩溃时能打印托管堆栈（与 Mac 行为一致）；退出/卸载后**不再持有**被覆盖的处理器 ⇒ 二次崩溃仍能走到引擎自身的崩溃处理 |
| **判定** | 对比 Mac 分支的行为差异是否消失；若仍不一致，则本条维持开放并记录平台 |

> ### ✅ V-2 结论（2026-10-07，本机 Windows，已修复）
>
> 用**临时控制台探针**（`UnrealCSharp.Test.Crash` / `.Abort`，验证后已删除文件）把两个面分开测，结果是**一半成立、一半不成立**：
>
> | 面 | 改前实测 | 判定 |
> |---|---|---|
> | **硬件信号**（`*(volatile int32*)0 = 1`） | 插件处理器**从未被调用**（`LogUnrealCSharp: Error` = 0）；UE 走 **SEH**（`LaunchWindowsStartup.ExceptionHandler`）并产出**完整崩溃报告**（`UEMinidump.dmp` 928 KB + CrashContext 76 KB） | ❌ 报告担心的「崩溃报告失效/卡死」**在 Windows 不成立** —— `signal(SIGSEGV)` 被 SEH 旁路 |
> | **CRT 主动 raise**（`raise(SIGABRT)`） | 处理器**运行了但不返回**：探针在第一次 raise 之后的日志 **0 条**、进程 120 s 仍存活 ⇒ **卡死在信号上下文**（`UE_LOG` 已完成，卡在随后的 `GLog->Flush()`） | ✅ 报告的「崩溃变卡死」**成立** |
>
> **修复**（`FCSharpEnvironment.cpp` `+16/−3`）：① 删掉信号上下文里的 `GLog->Flush()`（实测死锁点）；② 非 Mac 分支补「保存并恢复原处理器」（`static FSignalHandler SignalHandlers[32]` + 安装时存 `signal()` 返回值 + 处理器内 `signal(Signal, Previous…)`，与 Mac 的 `sigaction` 语义对齐；**用定长数组而非 `TMap`**，避免信号上下文里的容器操作）。
>
> **改后实测**：`raise(SIGABRT)` **两次** ⇒ 处理器**正常返回**（探针日志 1 条）、**第二次落到恢复的原处理器** ⇒ **进程正常退出**（66 s）；硬件信号路径**不受影响**（仍走 SEH、仍生成崩溃报告 `UECC-Windows-FC052FF3…`、插件处理器 0 次介入）。`-game` **2 × 1 892 / 0 失败**。
>
> ⚠️ **handler 内仍保留 `UE_LOG` + 托管 `FDomain::GetTraceback()`**（**非 async-signal-safe**，报告建议 2/3 要求彻底移除或加"默认关闭"的开关）。**该路线已评估并否决**（2026-10-07）：① 硬件信号在 Windows 上**根本不进插件 handler**（SEH 旁路）⇒ 该风险不适用；② CRT raise 的信号下确实会卡死，但**卡点具体是 `GLog->Flush()`**（已定点删除）⇒ 剩下的是**未复现的假设性风险**（打断点恰在分配器/日志锁内）；③ 移除 = **失去"崩溃时打印托管堆栈"这一既有功能本身**（`F-ABI-024` 记为**预期行为**），加开关 = 为未复现的风险新增公开配置面。⇒ **保留诊断、不加开关**；改做**零代价加固**：把「恢复原处理器」提到 handler **最前** ⇒ 诊断若再入，由**原处理器**接手（而非递归进自己）。

### V-7 释放路径的「内部堆字节」探针（2026-10-10 轮 B-3 建立；⚠️ **含一条反例教训**）

> 🔴 **为什么单列一条**：`F-REG-006` 这类"释放时跳过析构 ⇒ 内部资源泄漏"的条目，判据看起来应该是"量一量对象内部还剩多少堆字节"。本轮照此做了探针 —— **结果两版读数逐项相同**，并因此发现**该条的泄漏前提与引擎版本绑定**（见 [`08-…/43`](../08-专项审计/43-轮B3收口-多引用注册表析构与跨版本前提（2026-10-10）.md) §4）。

| 项 | 内容 |
|---|---|
| **装置** | 在释放路径（如 `TMultiAddress::FreeImplementation()`）的**同一位置**放两处读数（改前/改后**同一份探针代码**，差别只在有无"补析构"那一行）：① 进入时；② 紧邻 `FMemory::Free` 之前。逐事件把两个数追加到 `Saved/Retest/probe-b3-*.log` |
| **判读** | 两数**相同** ⇒ "补析构"没有释放任何东西（在**该引擎**上无泄漏可消除）；②为 0 而①非 0 ⇒ 析构确实释放了内部资源。**关键：两版读数相同本身就是结论**（不要当成探针失效） |
| **⚠️ 反例教训（本轮踩到）** | 用**按值返回的 getter**（`FSoftObjectPath::GetAssetPathString()`、`ToString()` 一类）去量"内部缓冲是否仍被分配"**是无效口径** —— 它每次都会**重建**一个字符串，改前改后都会给出同样非空的值。本轮据此差点把"零收益"误读成"修复未生效" |
| **✅ 正确做法** | 判定"有没有堆资源可泄漏"**必须回引擎头文件核存储类型与版本**：`FSoftObjectPath` 在 **5.0** = `FName AssetPathName` ＋ **`FString SubPathString`**（`5.0/…/SoftObjectPath.h:252-255`），在 **5.6** = `FTopLevelAssetPath AssetPath`（**双 `FName`**：`SoftObjectPath.h:465` ＋ `TopLevelAssetPath.h:190/192`）⇒ **同一份插件代码，泄漏结论相反** |
| **已知案例** | 轮 B-3（`F-REG-006`）：`out/b3-pre/` 与 `out/b3-post/` 各 **432** 次释放、**78** 次 `entry>0`、合计 **6 020 B**、**432/432 行两数相同** ⇒ 5.6 上零收益、5.0 上才是真泄漏 |
| **能力边界（如实）** | 探针**只能量它读的那个表达式**；对"内部还有别的堆成员"无能为力 ⇒ 必须与**类型成员清单（含引擎版本）**一起给出，二者缺一不可 |

### V-8 归属类泄漏的「created / destroyed」计数探针（2026-10-10 轮 B-4 建立）

> 🔴 **为什么单列一条**：`F-CB-005`（物化产物无所有者）这类"**谁 new、谁没 delete**"的条目，判据不是量字节，而是**数条目** —— 在分配点与释放点各打一条落盘计数，就能把"永不释放"变成可判读的两行字。

| 项 | 内容 |
|---|---|
| **装置** | ① **分配点**：在物化/创建循环末尾追加 `created <名字>=<个数> …`；② **释放点**：在析构器**开头先抓计数**、删除完成后再追加 `destroyed …`（⚠️ 顺序要在 `Empty()` **之前**抓，否则全是 0 —— 本轮第一版就写错了，已改）；③ 一律 `FFileHelper::SaveStringToFile(..., FILEWRITE_Append)` 落盘（不用 `UE_LOG`） |
| **判读** | **改前**：只有 `created` 行（无释放点 ⇒ 无 `destroyed` 行）；**改后**：每轮 `created` 与 `destroyed` 成对且数字相等。**"缺一行"本身就是结论**（不要当成探针没生效） |
| **关键前提** | 释放点必须**真的会被调用到**：本轮用 `-game -AutoQuit`（V-6）保证干净退出 ⇒ **函数内静态的析构器会执行**（2/2 轮各出现一次 `destroyed`），否则读数会误判为"仍未释放" |
| **已知案例** | 轮 B-4（`F-CB-005`）：改前 `created class=69 enum=9`（无 destroy）→ 改后 `created class=69 enum=9` ＋ **`destroyed class=69 enum=9 register=0/0`**；归档 `Saved/Retest/out/b4-post/`（并更正了复核备注里的"约 41 类 + 7 枚举" ⇒ 实测 **69/9**） |
| **能力边界（如实）** | 只量**条目数**，不量字节；**增量泄漏的真实场景是"模块重载/卸载"**（Live Coding、编辑器退出），`-game` 干净退出只能证明"析构会被调用、且数字闭合"，**不能**替代模块卸载场景 |

### V-10 跨模块/跨 TU 静态初始化顺序金丝雀（2026-10-10 轮 B-9 建立）

> 🔴 **为什么单列一条**：`FBinding` 的注册、`FDynamicClassGenerator` 的静态集合分属两个模块，C++ 标准**不保证**其动态初始化顺序（`[basic.start.dynamic]`）；这条只能实测。

| 项 | 内容 |
|---|---|
| **装置** | 在待观测的静态对象**同一 TU 内、紧邻其声明处**放一个文件作用域金丝雀：其构造器向**同一个落盘文件**追加一行（如 `DYNSET-CTOR`）；同时在各模块 `StartupModule()` 追加 `CORE-STARTUP`/`UE-STARTUP`，在注册点追加 `REG #n …` ⇒ **行的先后 = 真实的初始化/启动顺序** |
| **纪律** | ① 一律 `FFileHelper::SaveStringToFile(..., FILEWRITE_Append)`（不用 `UE_LOG`：静态初始化期的日志会被缓冲/丢失）；② **探针函数名按文件取唯一名**（模块启用 Unity build ⇒ 同模块多个 `.cpp` 合并成一个 TU，匿名命名空间同名函数会 `C2084` 重复定义）；③ 取证后**整块移除**并把探针日志归档 |
| **本轮读数** | `DYNSET-CTOR`(1) → `REG #1..#30`(2–31，全部 `isRunning=0 gEngine=0`) → `UE-STARTUP`(32) → `CORE-STARTUP`(33) → 首个 `DYNCALL`(34) ⇒ 静态顺序（CORE 先）与启动顺序（UE 先）**相反**，两者都不是标准保证 |
