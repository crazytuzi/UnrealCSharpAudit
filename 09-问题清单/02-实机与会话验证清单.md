## §1 编辑器会话

### V-1 `F-ED2-005` —— 编译等待的超时分支（路线 A）

| 项 | 内容 |
|---|---|
| **代码** | `FEditorListener::WaitForCompile()`（`Source/UnrealCSharpEditor/Private/Listener/FEditorListener.cpp`）+ 静态成员 `CompileWaitTimeoutSeconds = 600.0`、`PumpTaskGraphWhileCompiling()`（`FEditorListener.h` 静态段落） |
| **为什么不能自动判** | 该函数**只在 PIE 启动路径**被调用（`OnPreBeginPIE` → `IsCompiling()` 为真时），而 `-game` 套件**不产生 PIE** ⇒ 超时分支在套件里不可达 |
| **前置** | ① 能触发一次长编译（清 `Intermediate/`+`Binaries/` 后全量构建，或在 `Script/` 下临时堆大量源文件）；② 编辑器可正常启动 |
| **加速技巧** | 把 `CompileWaitTimeoutSeconds` **临时**改为 `5.0` ⇒ 无需真等 600 s 即可走超时路径；**验证后必须改回 600.0**（并在台账记录该临时改动） |
| **步骤** | 1) 启动编辑器，让编译开始（工具栏触发或启动自动编译）；2) 在编译**尚未结束**时点击 PIE；3) 观察编辑器与进度窗 |
| **期望 —— 改前** | 编辑器**无响应**直到编译结束；`HeartBeat()` 每轮喂狗 ⇒ 引擎挂起检测不触发、无崩溃报告可查；`dotnet build` 若真卡死 ⇒ **永久冻结** |
| **期望 —— 改后** | ① **600 s 内**编译完成：与改前一致（进度窗关闭、PIE 正常启动）；② **超过 600 s**：编辑器**恢复可交互**（进度窗关闭），PIE **以未重编的旧程序集启动**，编译仍在后台继续 |
| **判定标准** | (a) 超时后能否点击菜单/拖动窗口；(b) `FCSharpCompiler::Get().IsCompiling()` 是否仍为真、并**稍后自行变假**（⇒ 证明 GT ticker 的 `ProcessThreadUntilIdle` 仍在为编译线程握手服务，**没有死锁**）；(c) 编译线程最终是否正常结束 |
| **取证** | `Saved/Logs/UnrealCSharpTest.log`（编译结束行）、进程 CPU/线程数、必要时任务管理器确认非挂起 |
| **失败即回归的信号** | 超时后编译**永不结束** ⇒ 说明泵没起作用（等于报告 §2476 的"循环退出即永久等待"）⇒ 立即回退该改动 |

> ### ✅ V-1 结论（2026-10-07，**本机 Windows 编辑器会话，A/B 已做**）
>
> **装置**：一次性 Python 探针（`Content/Python/init_unreal.py`，**验证后已删除、目录也一并删掉**）：每帧回调 + 心跳日志；在 tick 150 **触碰** `Script/Game/UnrealCSharpTest/TestCore/TestCoreSubsystem.cs` ⇒ 由**目录监视器**触发**异步**编译（注意：`UnrealCSharp.Editor.Compile` 控制台命令**在游戏线程同步构建**（`F-ED2-006`），**不能**用它构造"编译中"状态 —— 首次尝试因此不具判别力）；tick 175 请求 PIE（`LevelEditorSubsystem.editor_request_begin_play()`）。**编译是否完成以 `Script/Game/bin/Debug/net10.0/Game.dll` 的 mtime 为证**。
>
> | | **运行 A**：超时 = **0.3 s**（路线 A 生效） | **运行 B**：超时 = **600 s**（等价改前·无界阻塞） |
> |---|---|---|
> | 触碰源文件 | 15:33:01.011（帧 150） | 15:36:05.489（帧 150） |
> | 请求 PIE | 15:33:09.346（帧 175） | 15:36:13.824（帧 175） |
> | **PIE 实际启动** | **15:33:10.258 —— 请求后 0.91 s**（帧 176） | **15:36:22.197 —— 请求后 8.37 s**（帧 176） |

> | 编译完成（dll mtime） | **~15:33:16 ⇒ 在 PIE 启动之后约 7 s** | ~15:36:21 ⇒ 在 PIE 启动之前 |
> | 心跳 | 全程连续（帧 176→190 间隔 0.03–0.04 s） | 请求后帧号几乎不动（175→176 花掉 8.4 s） |
>
> **判定**：① **超时分支确实生效**（A 的阻塞 0.9 s ≪ B 的 8.4 s）；② **PIE 用未重编的旧程序集照常启动**（A 中 PIE 起于编译完成之前）；③ **后台泵有效、无死锁** —— A 里编译在 GT 返回**之后**仍完成（dll mtime 为证），这正是报告 §2476 的硬约束所在；④ 心跳连续 ⇒ 编辑器在 tick 之间保持可响应。

## §2 平台会话（非 Windows / 跨平台）

> 依据：Wave-5 ② 逐条核实后，**P1 里真开放的只剩这两条**（`01-全局问题总表.md` L397/L398）。

### V-2 `F-ABI-009` —— signal handler（Windows / Linux 分支）

| 项 | 内容 |
|---|---|
| **代码** | `FCSharpEnvironment.cpp`：信号类型表 `:103-120`；注册循环 `:122-144`（`#if PLATFORM_MAC` 用 `sigaction` 并**保存原处理器** `:135`，`#else` 仍是裸 `signal(SignalType, SignalHandler)` `:142`）；恢复路径 `:29`；handler 本体 `:22` |
| **已核实的两个开放面** | ① Windows/Linux **不保存原处理器**（只有 Mac 保存 ⇒ 卸载/退出时无法恢复）；② handler 体内调用 `UE_LOG(LogUnrealCSharp, Error, …)` + `GLog->Flush()` + 托管侧 `FDomain::GetTraceback()`，**均非 async-signal-safe** |
| **前置** | Windows 编辑器一份；Linux 编辑器一份（`F-ABI-011` 也在此列） |
| **步骤** | 1) 触发一次受管崩溃（`SIGSEGV`/`SIGFPE`）观察打印的托管堆栈是否完整；2) 正常退出编辑器，观察是否有残留信号处理器/退出期异常；3) 在同一进程内二次初始化插件（热重载）后崩溃，观察原处理器是否被正确恢复 |
| **期望** | 崩溃时能打印托管堆栈（与 Mac 行为一致）；退出/卸载后**不再持有**被覆盖的处理器 ⇒ 二次崩溃仍能走到引擎自身的崩溃处理 |
| **判定** | 对比 Mac 分支的行为差异是否消失；若仍不一致，则本条维持开放并记录平台 |

> ### ✅ V-2 结论（2026-10-07，本机 Windows，已修复）
>
> 用**临时控制台探针**（`UnrealCSharp.Test.Crash` / `.Abort`，验证后已删除文件）把两个面分开测，结果是**一半成立、一半不成立**：
>
> | 面 | 改前实测 | 判定 |
> |---|---|---|
> | **硬件信号**（`*(volatile int32*)0 = 1`） | 插件处理器**从未被调用**（`LogUnrealCSharp: Error` = 0）；UE 走 **SEH**（`LaunchWindowsStartup.ExceptionHandler`）并产出**完整崩溃报告**（`UEMinidump.dmp` 928 KB + CrashContext 76 KB） | ❌ 报告担心的「崩溃报告失效/卡死」**在 Windows 不成立** —— `signal(SIGSEGV)` 被 SEH 旁路 |
> | **CRT 主动 raise**（`raise(SIGABRT)`） | 处理器**运行了但不返回**：探针在第一次 raise 之后的日志 **0 条**、进程 120 s 仍存活 ⇒ **卡死在信号上下文**（`UE_LOG` 已完成，卡在随后的 `GLog->Flush()`） | ✅ 报告的「崩溃变卡死」**成立** |
>
> **修复**（`FCSharpEnvironment.cpp` `+16/−3`）：① 删掉信号上下文里的 `GLog->Flush()`（实测死锁点）；② 非 Mac 分支补「保存并恢复原处理器」（`static FSignalHandler SignalHandlers[32]` + 安装时存 `signal()` 返回值 + 处理器内 `signal(Signal, Previous…)`，与 Mac 的 `sigaction` 语义对齐；**用定长数组而非 `TMap`**，避免信号上下文里的容器操作）。
>
> **改后实测**：`raise(SIGABRT)` **两次** ⇒ 处理器**正常返回**（探针日志 1 条）、**第二次落到恢复的原处理器** ⇒ **进程正常退出**（66 s）；硬件信号路径**不受影响**（仍走 SEH、仍生成崩溃报告 `UECC-Windows-FC052FF3…`、插件处理器 0 次介入）。`-game` **2 × 1 892 / 0 失败**。
>
> ⚠️ **handler 内仍保留 `UE_LOG` + 托管 `FDomain::GetTraceback()`**（**非 async-signal-safe**，报告建议 2/3 要求彻底移除或加"默认关闭"的开关）。**该路线已评估并否决**（2026-10-07）：① 硬件信号在 Windows 上**根本不进插件 handler**（SEH 旁路）⇒ 该风险不适用；② CRT raise 的信号下确实会卡死，但**卡点具体是 `GLog->Flush()`**（已定点删除）⇒ 剩下的是**未复现的假设性风险**（打断点恰在分配器/日志锁内）；③ 移除 = **失去"崩溃时打印托管堆栈"这一既有功能本身**（`F-ABI-024` 记为**预期行为**），加开关 = 为未复现的风险新增公开配置面。⇒ **保留诊断、不加开关**；改做**零代价加固**：把「恢复原处理器」提到 handler **最前** ⇒ 诊断若再入，由**原处理器**接手（而非递归进自己）。
