## 1. 模块职责与架构速览

### 1.1 分层与生命周期

```
FDomain(FTickableGameObject, UnrealCSharp 模块)         ← 唯一长期持有者
  ├─ IScriptDomain::Get()/Set()   静态全局指针 (IScriptDomain.cpp:3-13)
  ├─ FScriptDomainFactory::Create()/Destroy()            ← 后端选择 + 反初始化
  └─ Tick() → IScriptDomain::Tick()

IScriptDomain(纯接口, 30 个纯虚函数, IScriptDomain.h:8-87)
  ├─ FMonoDomain    : Mono    后端 (§Mono)
  ├─ FCoreCLRDomain : CoreCLR 后端 (hostfxr + load_assembly_and_get_function_pointer)
  └─ FLeanCLRDomain : LeanCLR 后端 (LeanCLR VM 内解释执行 + 原生 P/Invoke 注册)

实现复用：FScriptDomainImpl.inl (652 行)
  Mono/CoreCLR  → 全部 30 个方法都来自 .inl（不定义任何 SCRIPT_DOMAIN_CUSTOM_*；
                  CoreCLRDomain.cpp:164-166、FMonoDomain.cpp:184-186 已逐字核对）
  LeanCLR       → 定义 7 个 SCRIPT_DOMAIN_CUSTOM_* 宏（FLeanCLRDomain.cpp:100-106），
                  其中 **5 个对应真实覆写**（UNBOX_VALUE/FREE/INVOKE/
                  GET_CLASSES_WITH_ATTRIBUTE/REGISTER_BINDING）；另 2 个
                  （REGISTER_LOG/REGISTER_SYNCHRONIZATION_CONTEXT_TICK）只是"关闭 .inl 定义"的
                  占位——FLeanCLRDomain.h:189-193 并未声明这两个成员，LeanCLR 用
                  `Class_Get_Method_From_Name(...LogBridge.InitializeLeanCLR)` + `Bridge_Invoke`
                  （FLeanCLRDomain.cpp:69-75）与 `UTILS_BRIDGE_METHODS` 直解（:778）取代之
                  （"覆写 7 个"的措辞不准确）
                  并重定义 SCRIPT_DOMAIN_INVOKE 为 Bridge_Invoke（:99，模板 + RtStackObject 编组）
```

关键事实：**`WITH_MONO` / `WITH_CORECLR` / `WITH_LEANCLR` 是互斥的编译期宏**（`UnrealCSharpCore.Build.cs:269-306` 用同一个字符串做三次相等比较，只可能有一个为 1），编译期取值来自构建时读取的
`Config/DefaultUnrealCSharpSetting.ini`（`UnrealCSharpCore.Build.cs:236-273`）。本测试工程该文件为
`Windows/Linux/Android/Mac/IOS ScriptDomainType=LeanCLR`（`Config/DefaultUnrealCSharpSetting.ini:4-8`），
即**本工程实际编译进的是 LeanCLR 后端，Mono/CoreCLR 的全部代码在该配置下被宏裁掉**。任何"三后端"问题都必须区分"源码级缺陷"与"当前构建实际可达"。
补充的**构建产物硬证据**：`Intermediate/Build/Win64/x64/UnrealCSharpTest/Development/UnrealCSharpCore/Definitions.UnrealCSharpCore.h:19-21`
= `WITH_CORECLR 0 / WITH_MONO 0 / WITH_LEANCLR 1`（另有 Android / Linux / Editor 四份同类产物，取值一致）。因此本报告贯彻口径：
**可达性 = 该发现描述的危险路径在当前配置下是否会被执行**；活跃 = 会执行；潜伏 = 该后端未编译进当前配置，切回该后端即生效；不可达 = 即使切到该后端也到不了（死代码）。

### 1.2 数据流

```
C++ 侧                                    托管侧
FClassReflection::NewObject()  ──► ObjectBridgeNewObject  ──► HandleData.Alloc(Object) ──► nint(序号)
FMethodReflection::Runtime_Invoke() ──► MethodBridgeInvoke ──► MethodBridge.Invoke() (内部 try/catch)
FDomain::GCHandle_Free(h)      ──► HandleDataFree        ──► HandleData.FreeImplementation(h)
字符串：StringBridge.NewString(UTF8*) / GetString(h, char16_t*, n) ；无 mono_string_to_utf8 路径
数组  ：ArrayBridge.ArrayNew(UTF8 全名, len) / ArrayGet ；无 mono_array_addr 路径
```

**重要纠正（避免误报）**：本插件的 C++ 侧**完全没有**使用 `mono_gchandle_new/free`、`mono_string_to_utf8/mono_free`、`mono_array_addr_with_size`。全局 grep（`Source/**/*.{h,cpp,inl}`，排除 `Source/ThirdParty`）显示这些符号只出现在 `Source/ThirdParty/Mono/src/mono/**` 的头文件里；`mono_free` 的唯一调用点是死代码 `FMonoDomain::Free`（见 F-DOM-024）。句柄（GCHandle）与字符串/数组编组**全部在 C# 侧 `Script/Interop`** 完成，`IManagedHandle` 实际是 C# `HandleData.Handles`（`Dictionary<nint,GCHandle>`）的**序号**，不是 `GCHandle` 本身。因此"mono_string_to_utf8 经典泄漏"在本插件中不存在；真正的句柄泄漏点在 C# 表与 C++ 释放路径的配对关系上。

### 2.2 三后端 30/30 对照表实测结果

重跑方法：以 `IScriptDomain.h` 的 30 个纯虚函数为基准，逐条在 `FScriptDomainImpl.inl`（共享实现）、`FMonoDomain`、`FCoreCLRDomain`、`FLeanCLRDomain` 中定位真实行号；Mono/CoreCLR 未定义任何 `SCRIPT_DOMAIN_CUSTOM_*`（`FMonoDomain.cpp:184-186`、`FCoreCLRDomain.cpp:164-166`），故其 30 个实现**必然**来自 .inl；LeanCLR 定义 7 个宏（`FLeanCLRDomain.cpp:100-106`），故 30 个中 5 个为自有实现、25 个来自 .inl。

| 后端 | 共享实现数（.inl） | 自有实现数 | 缺口 / 空壳 / 直接 return | 真实计数 |
|---|---|---|---|---|
| Mono | 30 | 0 | 无 | **30/30** |
| CoreCLR | 30 | 0 | 无 | **30/30** |
| LeanCLR | 25 | 5（UnboxValue `:118-133`、Free `:135-146`、Invoke `:148-188`、GetClassesWithAttribute `:190-250`、RegisterBinding `:854-888`） | 无 | **30/30** |

补充事实（重跑中发现、均为"事实更正"而非新缺陷）：
1. `FLeanCLRDomain` 的桥接成员集由 `COMMON_BRIDGE_METHODS` + `LEANCLR_INTEROP_BRIDGE_METHODS`(2 项) + `UTILS_BRIDGE_METHODS`(6 项) 三组构成（`FLeanCLRDomain.h:199-207`），**不展开 `NATIVE_BRIDGE_METHODS`**。因此 `AssemblyLoaderLoadFromStreamFn`/`LogBridgeSetLogFn`/`LogBridgeInitializeFn`/`TypeBridgeGetFunctionPointerFn`/`MethodBridgeRegisterBindingFn` 在 LeanCLR 后端**根本不存在该成员**（ §2.2 写"恒为 nullptr"，措辞不准确；对 C# `AssemblyLoader.LoadFromStream` 永不被调用的结论无影响，且比"指针为 null"更强。该小节编号为 §2.3）。
