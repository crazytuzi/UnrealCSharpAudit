## 1. 模块职责与架构速览

这 6 组类**不是 UE 的 `FProperty`/`UFunction` 包装**，而是**C# 侧反射元数据（`System.Type`/`MethodInfo`/`FieldInfo`/`PropertyInfo`）在 C++ 侧的镜像描述符**。名字容易误导：

- 它们持有的不是 `UClass*`/`FField*`，而是 `IManagedHandle`（`int64`，见 `IManagedHandle.h:7`），即 C# `GCHandle` 表里的一个编号句柄。因此在**本组文件里不存在"裸 UObject* 未加 UPROPERTY 导致 GC 悬挂"的问题**（详见第 6 节 GC 判定表）。
- `FClassReflection` 是唯一有真实逻辑的类（796 行）；其余 5 个是薄数据类。

数据流（首次访问某个 C# 类的成员时）：

```
调用方 -> FClassReflection::GetProperty/GetField/GetMethod   (FClassReflection.cpp:631/647/663)
      -> EnsureProperties/EnsureFields/EnsureMethods         (FClassReflection.h:94/102/110)
      -> EnsureMemberImplementation(bLoaded, slotCount, &IScriptDomain::GetClassXxx, &ParseXxx)  (cpp:435)
      -> EnsureDescriptor()                                  (cpp:445 -> 407)
      -> IScriptDomain::GetClassDescriptor(ManagedClass, &Params[1])   // 进 C# Utils.GetClassDescriptor
      -> ParseDescriptor()                                   (cpp:129)
      -> IScriptDomain::GetClassProperties(ManagedClass, &Params[1])   // 进 C# Utils.GetClassProperties
      -> ParseProperties()                                   (cpp:205) -> new FPropertyReflection
```

**C# 侧 buffer 契约已逐槽核对通过**（这是本次分析里最重要的"没问题"结论）：C++ 传 `&Params[1]` 作为 `nint* OutBuffer`（`cpp:427/457`），因此 **`InParams[n]` ↔ `OutBuffer[n-1]`**（`InParams[0]` 是 `ManagedClass` 自身）。C# 写 `OutBuffer[0..N]`（`Utils.cs:646-676` 描述符 15 槽、`Utils.cs:692-708` 属性 8 槽、`Utils.cs:721-725` 字段 3 槽、`Utils.cs:743-771` 方法 14 槽），与 C++ 的 `InSlotCount`（`cpp:467=8 / 473=3 / 479=14`）和 `Parse*` 里 `InParams[1..15]` 的下标**完全一致，无 off-by-one**（按 `InParams[n] ↔ OutBuffer[n-1]` 重新逐槽比对 15/8/3/14 槽，全部吻合）。

**关键类关系**：

- `FReflectionRegistry`（`FReflectionRegistry.h:7`，**不是** `FGCObject`/`UObject`，是普通类）拥有所有 `FClassReflection`：`FullName2Class`（`h:1191`，`TMap<FString, FClassReflection*>`）+ `new`（`FReflectionRegistry.cpp:941/966`）+ `delete`（`cpp:873`）。
- `FPropertyReflection`/`FMethodReflection`/`FParamReflection`/`FFieldReflection` 由**各自的 `FClassReflection` 拥有**，`new` 于 `FClassReflection.cpp:248/282/361/370`，`delete` 于 `cpp:487/494/501` 与 `FMethodReflection.cpp:29`。
- 交叉引用均为**裸指针**：`FPropertyReflection::ReflectionType`（h:29）、`FMethodReflection::Return`（h:50）、`FParamReflection::ReflectionType`（h:20）、`FClassReflection::Parent/TypeDefinition/UnderlyingType/GenericArguments/Interfaces`（h:156-172）。生命周期由 registry 单一持有者模型保证（**无 `TSharedPtr`，因此无循环引用**）。
- `FManagedReader`（`FClassReflection.cpp:9-116`）是解析用的轻量视图：`ScriptDomain*` + 静态/成员转换函数，负责把 buffer 槽位转成 bool/int32/FString/FClassReflection*，并在转换后 `Free` 掉托管句柄。

**生命周期**：`FReflectionRegistry::Initialize()`（由各 Domain 的 `Initialize` 调用，`FReflectionRegistry.h:16`）→ 域运行期懒加载 → `FReflectionRegistry::Deinitialize()`（`cpp:867`，由 `FCoreCLRDomain.cpp:242`、`FLeanCLRDomain.cpp:808`、`FMonoDomain.cpp:430` 在域关闭时调用）→ `delete` 所有 `FClassReflection`（其析构 `cpp:124` 会 `Deinitialize()` 释放成员）。

- **方法一路（P0 的主因，成立）**：`Methods` 的键是 `(名字, 参数个数)`。C# 里 `void Bar(int)` / `void Bar(float)` 会落到同一键；**注意键不含 `UFunctionAttribute`**，因此一个普通 C# 方法（无 `[UFunction]`）也能把同名同参数个数的 `[UFunction]` 挤掉——被挤掉的那一个在 `ParseMethods` 里恰好是"唯一解析了 `Return`/`Params` 的版本"（`cpp:343-367` 只在 `bIsUFunction` 分支内解析），而 `ManagedMethod` 对**所有**方法都赋值（`cpp:372`），所以 `TMethodHelper` 拿到的可能是"没有 `Return`/`Params` 的那个"。反射返回顺序不由代码固定，故"谁存活"不可预测。
- **构造函数一路（原文证据 2 的影响被高估）**：构造函数名统一为 `.ctor` 属实（`Utils.cs:437-441/456-466`、`CoreMacro/FunctionMacro.h:5`），但 C++ 侧**三处**调用 `ConstructorObject` 全部使用默认 `InParamCount = 0`（`Source/UnrealCSharp/Private/Registry/FDynamicRegistry.cpp:32`、`Registry/FClassRegistry.cpp:262`、`Environment/FCSharpEnvironment.cpp:448`），`InitObject` 的唯一调用点同样使用默认 0（`Domain/Interop/FRegisterDataTableFunctionLibrary.cpp:29`），而 C# 不允许一个类有两个**零参数**构造函数 → 该键不可能出现重复。因此 `.ctor` 一路**不构成 P0 触发路径**，P0 由上面"方法一路"支撑。

**补验（P0 判定依据）**

1. **C# 生产端不做任何去重**：`Script/UE/CoreUObject/Utils.cs:443-450` 用

2. **构造函数全部名为 `.ctor`**：`Utils.cs:437-441/456-466` 把 `InType.GetConstructors(...)` 与普通方法**拼在同一个数组**里，名字同样取 `MethodBase.Name` → 所有实例构造函数都叫 `".ctor"`（`CoreMacro/FunctionMacro.h:5` `#define FUNCTION_OBJECT_CONSTRUCTOR FString(".ctor")`，`:3` `".cctor"` 对应 `FUNCTION_CLASS_CONSTRUCTOR`）。因此**同参数个数的多个构造函数在 C++ 侧同名同键**，只有最后一个能存活在 `Methods` 里。（**影响边界见上文"触发条件收敛"：C++ 侧只以 `.ctor` + 0 参查询，故这一路不构成实际触发路径**；本项的价值是说明"键不含任何类型信息"这一设计事实。）
3. **C++ 侧唯一的 C# 方法解析入口就是 (名, 参数个数)**：`Source/UnrealCSharp/Public/Binding/Function/TMethodHelper.inl:59`

   即 C++ 侧按 `Args...` 装箱的值，被**按托管侧那个（可能是错的）方法的形参类型**读取。
5. **失败被吞掉**：`MethodBridge.cs:125-137` `catch (Exception Exception) { Console.Error.WriteLine(...); return 0; }` —— 异常不穿越 ABI，只返回 `0`（`InvalidManagedHandle`）。

**触发链（可复现）**：C# `class Foo : UObject { [UFunction] void Bar(int); [UFunction] void Bar(float); }` → `ParseMethods` 里两个 `Bar` 键都是 `("Bar",1)`，后者覆盖前者（并泄漏前者）→ C++ `TMethodHelper<...>::Call(Obj, "Bar", 1.5f)` → `GetParentMethod("Bar",1)` 命中"活下来的那一个" → 若活下来的是 `Bar(int)`，`GetValue(float句柄, typeof(int))` 读到错误解释的位模式 → **要么抛异常被吞成返回值 0，要么静默按 int 处理了一个 float**。`void` 返回时调用方完全无感。

**调用上下文**
首次访问即触发：`FTypeBridge.cpp:13/95` → `GetTypeDefinition()`（`cpp:538`）→ `EnsureDescriptor()`；`FDynamicClassGenerator.cpp:63` → `GetParent()` → `EnsureDescriptor()` → `Parent` 可能是被缓存下来的 nullptr。

**问题**
`EnsureDescriptor` 的语义是"保证已加载"，但实现是"保证只尝试一次"。失败被升格为**永久性事实**（父类不存在、没有属性、没有方法），且调用方大量假设"返回 nullptr = 这个类没有该成员"（`FDynamicClassGenerator.cpp:63`、`FDynamicStructGenerator.cpp:40/109`、`FDynamicInterfaceGenerator.cpp:42/96` 都用 `if (const auto Parent = …)`，把解析失败**当成"没有父类"**处理）→ 生成出的动态 `UClass` 会挂到错误的父类上或丢失继承。
