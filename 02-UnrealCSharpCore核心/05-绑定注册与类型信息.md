## 1. 模块职责与架构速览

这一层是"绑定元数据"的**编译期容器 + 静态初始化期注册表**，不参与任何运行时热路径（Tick/GC/渲染），只在两个阶段工作：

**阶段 A —— 模块静态初始化期（DLL load / CRT static init）**
各绑定文件在文件作用域放一个注册对象，例如 `FRegisterString.cpp:59`：

```cpp
namespace { struct FRegisterString { FRegisterString() { FClassBuilder(TEXT("FString"), NAMESPACE_LIBRARY) ... } }; 
[[maybe_unused]] FRegisterString RegisterString; }   // ← 静态初始化
```

该构造函数 → `FClassBuilder::FClassBuilder(...)`（`FClassBuilder.cpp:11`）→ `FBinding::Get().Register(类名 lambda, 命名空间, IsProjectClass lambda, bIsReflectionClass, TypeInfo lambda)`（`FBinding.cpp:38`）→ 把 `FBindingClassRegister`（`new`，见 `FBinding.cpp:60`）追加进单例里的 `TArray<FBindingClassRegister*> ClassRegisters`（`FBinding.h:44`）。

**阶段 B —— 首次"物化"（materialize）**
`FBinding::Register()`（无参重载，`FBinding.cpp:10-36`）在**第一次**被调用时：
遍历 `ClassRegisters` → `Class->operator FBindingClass*()`（`FBindingClassRegister.cpp:20-58`）→ `new FBindingClass(...)`（第 47 行，值拷贝所有属性/函数/方法）放入 `Classes`，随后 `delete Class`（第 20 行）并 `ClassRegisters.Empty()`（第 23 行）；同一函数把枚举也物化。之后 `bIsRegister` 置真，**再也不会重新物化**。

**关键类关系**

```
FBinding (Meyers singleton, FBinding.cpp:3-8)
 ├─ TArray<FBindingClassRegister*>  →  注册期对象（TFunction 延迟求值，见下）
 │    └─ FBindingTypeInfoRegister / FBindingSubscriptRegister /
 │       TArray<FBindingPropertyRegister|FBindingFunctionRegister|FBindingMethodRegister>
 ├─ TArray<FBindingEnumRegister*>
 ├─ TArray<FBindingClass*>  ← 物化产物（值拷贝，永不释放）
 └─ TArray<FBindingEnum*>
FBindingClass → FBindingTypeInfo(裸 FTypeInfo*) + FBindingSubscript + 值数组
FFunctionInfo* → 指向 TFunctionInfo<...>::Get() 的函数级 static 实例（生命周期 = 模块）
```

**注册期对象全部用 `TFunction`/`TOptional<TFunction>` 延迟求值**（`FBindingClassRegister.h:50-56`、`FBindingFunctionRegister.h:31`、`FBindingTypeInfoRegister.h:19`）：类名、IsProjectClass、TypeInfo、FFunctionInfo 都是 lambda，只在"物化"时才调用。这是本层最重要的设计点（F-CB-001 正是围绕"唯一一个被提前到静态初始化期求值的 lambda"展开）。

**已正确规避的点（避免误报，特此记录）**

1. `FBinding::Get()` 用的是**函数内 static（Meyers singleton）**（`FBinding.cpp:5`），不是文件级全局对象 → 单例自身的构造顺序不是问题；`Classes`/`ClassRegisters` 的首次写入也会触发单例构造。
2. 本层内部**没有任何文件级全局对象**（grep `^(static|TArray|TMap|TSet|FString|bool|int32) ` 在 `Private/Binding` 只命中成员函数定义），注册对象都在消费侧模块。
3. `FBindingTypeInfo`（`FBindingTypeInfo.h:12-47`）与 `FBindingFunction`（`FBindingFunction.h:27-76`）对 `nullptr` 的**每一个**访问器都做了兜底（返回空串/空数组/false），没有裸解引用。
4. `FBindingClass`（`FBindingClass.cpp:19-23`）对元数据做值拷贝，所以 `delete Class`（`FBinding.cpp:20`）之后物化产物依然自洽，不存在悬挂引用。
5. `TTypeInfo<T>::Get()` / `TFunctionInfo<...>::Get()` 的 `static` 局部实例化受 C++11 "magic static" 保护，**单次初始化本身线程安全**。

### [F-CB-001] 绑定注册发生在静态初始化期，且 `FBinding::Register` 会立即求值类名 lambda，触碰引擎与跨模块静态状态

- **类别**: 未定义行为 / 平台兼容
- **严重度**: **P2**
- **文件**: `Source/UnrealCSharpCore/Private/Binding/FBinding.cpp:38-65`（关键点 46 行）
- **复核结论**: ⚠️部分确认（机制成立；原文的"P1 严重度"与"本环境无引擎源码"两处已修正）
- **可达性**: 活跃
- **复核证据**: `FBinding.cpp:46` `const auto Class = InClassFunction();`、`:52` `if (Class == ClassRegister->GetClass())` 经通读全文（112 行）逐字吻合；消费侧 66 处静态对象经 grep `\[\[maybe_unused\]\]`（范围 `Source/UnrealCSharp/Private/Domain/Interop/*.cpp`）= **66** 命中**精确复现**（含 `FRegisterObject.cpp:149`、`FRegisterString.cpp:59`）；`BindingMacro.h:72` 确认为唯一会在静态初始化期触发物化的入口（`TNameSpace::Get()` 内调 `FBinding::Get().Register()`）
- **级别变动**: P1→P2（触发依赖工具链加载顺序，当前由 MSVC 导入表顺序掩盖；且顺序错时表现为"静默算错"而非崩溃）
- **函数**: `FBinding::Register(const TFunction<FString()>&, const FString&, const TFunction<bool()>&, bool, const TOptional<TFunction<FTypeInfo*()>>&)`
- **置信度**: 中（代码事实确定；"是否真会炸"依赖 MSVC 导入表/模块加载顺序。**更正**：本机 UE 5.6 引擎源码确实存在（`Engine\Source`，约 20989 个 `.cpp`），原文"本环境无 UE 引擎源码"的说法已删除；但"`FName`/`GetPrivateStaticClass` 在 CRT 静态初始化期是否可用"取决于运行期模块加载顺序，静态阅读无法判定，故仍维持"中"，卡点见 §5）

**现状（代码事实）**

```cpp

	if (!InIsReflectionClass)
	{
		const auto Class = InClassFunction();          // 46 ← 静态初始化期就求值！
		for (auto& ClassRegister : ClassRegisters)
		{
			if (!ClassRegister->IsReflectionClass())
			{
				if (Class == ClassRegister->GetClass())  // 52 ← 每次比较都重建一个类名 FString

				}
			}
		}
	}
	return ClassRegisters.Add_GetRef(new FBindingClassRegister(InClassFunction, ...));
```

调用方是**文件作用域的静态对象**（静态初始化期执行）：

```cpp

TBindingClassBuilder<UObject>(NAMESPACE_LIBRARY).Function("Identical", ...) ... ;
[[maybe_unused]] FRegisterObject RegisterObject;   // 149
```

`InClassFunction()` 在 `UObject`/`USTRUCT` 类上会一路走到：

```cpp

static auto Get() { return FUnrealCSharpFunctionLibrary::GetFullClass(std::remove_pointer_t<std::decay_t<T>>::StaticClass()); }
// Private/Common/FUnrealCSharpFunctionLibrary.cpp:397-403
   (InStruct->IsNative() || FDynamicClassGenerator::IsDynamicClass(InStruct) || ...)
// Private/Dynamic/FDynamicClassGenerator.cpp:37,237-240
TSet<UClass*> FDynamicClassGenerator::DynamicClassSet;      // 37 ← 文件级静态对象

```

**调用上下文**
- 触发点：插件 `UnrealCSharp` 模块里 66 处文件级 `[[maybe_unused]] FRegisterXxx`（`grep -c '\[\[maybe_unused\]\]'` = 66 命中，如 `FRegisterObject.cpp:149`、`FRegisterString.cpp:59`）——它们在 **DLL 加载（CRT 静态初始化）** 时构造，早于 `StartupModule`。
- 被触碰的下游：`T::StaticClass()`/`StaticStruct()`（UE 反射）、`FUnrealCSharpFunctionLibrary::GetFullClass`（`FString::Printf` + `Encode`）、以及**另一个模块**（UnrealCSharpCore）的文件级静态 `FDynamicClassGenerator::DynamicClassSet`。
- 物化本身（`FBinding.cpp:10-36`）当前不在静态初始化期被触发：`TName<T,T>::Get()`（`TName.inl` 全部分支）**不访问注册表**；只有 `TNameSpace`（`BindingMacro.h:68-76`）会调 `FBinding::Get().Register()`，而 `TNameSpace` 只经 `TTypeInfo::GetNameSpace()`（`TTypeInfo.inl:24`）被生成器/域初始化调用。

**问题**
跨翻译单元、跨 DLL 的动态初始化顺序在 C++ 标准里是未指定的（[basic.start.dynamic]）。这里实际依赖两条**工具链约定**而非语言保证：
1. `UnrealCSharp.dll` 的静态初始化必须在 `UnrealCSharpCore.dll` 的静态初始化之后，否则 `DynamicClassSet.Contains(...)`（`FDynamicClassGenerator.cpp:239`）会操作一个"尚未动态构造"的 `TSet`——当前仅因 MSVC 按导入表先加载被依赖 DLL 而侥幸成立；一旦改成单模块合并/Unity build/静态库统一链接，顺序即失控。
2. 在 `FEngineLoop::PreInit` 之前调用 `StaticClass()`/`GetName()` 需要 UE 的 `FName`/静态类注册已可用；插件把这一整批注册提前到了引擎初始化之前，属于依赖引擎未文档化行为。
3. 反向风险同样存在：`TSet` 的"全零存储"恰好等于空集合，因此**即使顺序错了也可能静默返回 false**（把 `IsDynamicClass` 判成 false → 类名前缀/编码走错分支 → C# 类型名不一致），即"不会崩但会错"，比崩溃更难查。

**建议**
把注册从静态初始化期挪到模块启动期，用 UE 的延迟注册工具，二选一：

```cpp
// 方案 A：模块 StartupModule 里统一注册
// UnrealCSharpCore/Private/UnrealCSharpCoreModule.cpp
void FUnrealCSharpCoreModule::StartupModule() { FBinding::Get().CollectRegistrations(); }

// 方案 B（改动最小）：把消费侧的静态对象换成延迟注册助手
// 例如 FDelayedAutoRegisterHelper(EDelayedRegisterRunPhase::EarliestPossiblePluginsLoaded, []{ FRegisterObject(); });
```

同时（低成本保险）：
- `FBinding::Get()` 里加 `check(IsInGameThread() || GIsInInit)` 之类断言，把"初始化期"显式化；
- `FDynamicClassGenerator::IsDynamicClass` 改成对函数内 static 的访问或加"是否已初始化"标志，避免跨模块静态依赖。

**验证方式**
- `grep -c '\[\[maybe_unused\]\]' Source/UnrealCSharp/Private/Domain/Interop/*.cpp`（66 处 → 确认都在 static init）。
- 在 `FBinding.cpp:46` 前加 `UE_LOG(LogTemp, Warning, TEXT("FBinding::Register @%s"), *FPlatformProcess::GetCurrentProcessName())` + 断点看是否在 `DllMain` 期间命中；或用 `checkf(GIsRunning, ...)`（`GIsRunning` 在引擎 init 后才置真）验证注册时机。
- 把 `UnrealCSharp` 与 `UnrealCSharpCore` 编进同一模块（临时）后运行，观察 `DynamicClassSet.Contains` 的行为差异。

**建议**
不要暴露数组元素引用：

```cpp
// FBinding.h：返回值改为指针（或稳定 handle）
	FBindingClassRegister* Register(...);
// FBinding.cpp：用堆分配保证地址稳定
	FBindingClassRegister* Register = new FBindingClassRegister(...);
	ClassRegisters.Add(Register);
	return Register;
```

或者把 `ClassRegisters` 改为 `TArray<TUniquePtr<...>>` + 返回裸指针，并给 `FClassBuilder::ClassRegister` 加 `check(ClassRegister != nullptr)`。

### [F-CB-011] `SanitizeFloat` 用 `float` 的 `max_digits10` 格式化 `double`，且极小浮点默认值会被静默截断成 `0.0`

四处"看起来像 API 实际无消费者"的代码：`FBindingClass::IsSet`（1 命中 = 定义本身）、`TTypeInfo<void>` 除 `Get()` 外的 5 个虚函数、`FTypeInfo::GetBufferSize`（0 命中定义）、`EFunctionInteract::Override`（只有生成器的 TMap 映射，无产生点）、`EBindingPropertyAccess::ReadAndWrite`（1 命中 = 自身声明，值由 F-CB-013 的算术拼出）。`EFunctionInteract::Virtual` **不是**死代码（`Source/SourceCodeGenerator/SourceCodeGenerator.cs:526` 会产出它，只是当前检入的绑定尚未包含）。

**建议**
- 删除 `FBindingClass::IsSet`（或在生成器/域初始化里真正使用它来跳过未设类型信息的类）；
- `TTypeInfo<void>` 只保留返回 `nullptr` 的 `Get()`，其余成员用 `unreachable()`/删除；
- `FTypeInfo::GetBufferSize` 给一个默认实现（`return sizeof(void*);`）或标 `= 0`；
- `Override` 若确实由 C# 侧 `OverrideAttribute` 机制承担，就在枚举注释里写明并删除生成器里不可达的分支。

**验证方式**
见 §4 的 grep 证据表。

### [F-CB-021] 名字宏对"带 `::` 的限定名"的两种取法：漏传布尔参数会生成非法 C# 标识符

- **类别**: 可读性 / 功能隐患（跨层：宏在 UnrealCSharp 模块，规则由本层的 `TName`/`TNameSpace` 消费）
- **严重度**: **P3**
- **复核结论**: ⚠️部分 —— 严重度 P3 维持；可达性 潜伏
- **文件**: `Source/UnrealCSharpCore/Public/Binding/TypeInfo/TName.inl:19-22`（主模板）、`Source/UnrealCSharp/Public/Macro/BindingMacro.h:41-47,49-76,170-197`
- **函数**: `TName<T,T>::Get()`（宏生成的特化）/ `TNameSpace<T,T>::Get()`
- **置信度**: 中

**现状（代码事实）**

```cpp
// Macro/BindingMacro.h:41-47
#define BINDING_REMOVE_LEFT_NAMESPACE_CLASS_STR(Class)  F_STRING_STR(Class).Left(F_STRING_STR(Class).Find(TEXT("::")))
#define BINDING_REMOVE_RIGHT_NAMESPACE_CLASS_STR(Class) F_STRING_STR(Class).Right(F_STRING_STR(Class).Len() - F_STRING_STR(Class).Find(TEXT("::")) - 2)
// :55-64 / :176-185 —— 有 __VA_ARGS__ 时按第一个参数取左/右段；没有则原样返回 F_STRING_STR(Class)
```
唯一的限定名用例选择了"取右段"：

```cpp
// Source/UnrealCSharp/Private/Domain/Interop/FRegisterWorld.cpp:10
BINDING_ENUM(FActorSpawnParameters::ESpawnActorNameMode, false)   // → TName = "ESpawnActorNameMode" ✓
```

**调用上下文**
`TBindingEnumBuilder.inl:13`（注册键）与 `TBindingEnumGenerator.cpp:19/52/62`（生成的文件名与 `namespace`/`enum` 标识符）都用同一个 `TName<T,T>::Get()`，因此两侧一致；`TNameSpace` 里的 `FBinding::Get().Register().IsProjectClass(TName<T,T>::Get())`（`BindingMacro.h:72`）也以同一字符串为键。

**问题**
- 若将来有人写 `BINDING_ENUM(SomeNS::EMyEnum)`（漏传布尔参数），`TName` 会返回 **"SomeNS::EMyEnum"**，直接生成 `public enum SomeNS::EMyEnum`（非法 C# 标识符）以及文件名带 `::`；没有任何编译期检查能拦住它（C++ 侧字符串合法）。
- 取右段后，外层限定名被丢弃 → 两个不同结构体里的同名枚举会撞名（注册键相同），且 `TName` 与反射侧 `GetFullClass(UEnum*)`（`FUnrealCSharpFunctionLibrary.cpp:473-481`，取的是枚举自身名字）在"外层"信息上不对称。
- `TName` 的键与 `FBinding.cpp:52` 去重键都来自同一个宏，**在已检入的宏用例里写法一致**（`BINDING_CLASS/BINDING_ENUM/BINDING_STRUCT/BINDING_SCRIPT_STRUCT` 共 83 处命中，含 `BindingMacro.h` 里 4 处宏定义；其中唯一的限定名用例已正确传 `false`），所以当前不存在"同一类/枚举注册成两条"的情况（结论见 §6）。

**建议**
- 在 `TName` 的宏特化里加 `static_assert`/`ensure`：名字不含 `::`（或对限定名强制要求显式布尔参数）；
- 用 `constexpr` 工具函数替换两个宏，对 `INDEX_NONE` 情况给出明确分支而不是依赖 `Left/Right` 的负数行为；
- 若需要保留外层名（避免撞名），把嵌套结构改名成 `FActorSpawnParameters_ESpawnActorNameMode` 之类的唯一形式，并同步 C# 侧。

**验证方式**
- `grep -rn "BINDING_ENUM(\|BINDING_CLASS(" Source | grep "::"` → 仅 `FRegisterWorld.cpp:10`（已正确）。
- 临时把该行的 `, false` 去掉，跑一次生成，观察生成的 `.cs` 文件内容/文件名（验证失败模式）。

## 6. 横向维度汇总（规范 §3 要求）

### 6.1 空指针 / 越界 / 未检查返回值

- **本层 `nullptr` 处理良好**：`FBindingTypeInfo`（`FBindingTypeInfo.h:12-47`）与 `FBindingFunction`（`FBindingFunction.h:27-76`）每个访问器都判空；`FBindingTypeInfoRegister.h:15`、`FBindingFunctionRegister.h:23` 在 `TOptional` 为空时传 `nullptr` 而非解引用。
- **发现的越界风险**：生成器 `FBindingClassGenerator.cpp:389/156/85/124` 直接索引 `GetParamNames()[Index]`，唯一保护是 `:339` 的 `IsEmpty()`（F-CB-010）。`FBindingClassGenerator.cpp:48/50/812/814` 也直接 `GetParams()[0]`/`GetReturn()` 解引用——后者只在 `WITH_FUNCTION_INFO`（= `WITH_EDITOR`）成立时才有 `FunctionInfo`，而 `FBindingSubscript::IsSet()`（`FBindingFunction.h:27-30`）只检查 `FunctionInfo != nullptr`；当前 5 个 `BINDING_SUBSCRIPT` 站点（`FRegisterBox2D.cpp:27`、`FRegisterGuid.cpp:55`、`FRegisterVector.cpp:108`、`FRegisterVector2D.cpp:87`、`FRegisterVector4.cpp:70`）都传了 1 个参数名、返回值非 void，因此未触发（置信度 中，属跨模块遗留风险）。
- `TTypeInfo<void>::Get()` 返回 `nullptr`（`TTypeInfo.inl:94-97`）后由 `FBindingFunction::GetReturn()` 透传（`FBindingFunction.h:47-50`）——**调用方需判空**，本层已判。
- `FBinding::Register(...)`（`FBinding.cpp:38-65`）**永不返回 nullptr**（`Add_GetRef` 或已存在元素），无需判空（但见 F-CB-007 的引用失效问题）。

### 6.2 内存与资源泄漏

- 无 `TSharedPtr`/`TUniquePtr`/`AddToRoot`/`GCHandle` 使用（grep 0 命中）；分配点只有两处 `new`（`FBinding.cpp:60/72` 注册器 + `FBindingClassRegister.cpp:47`/`FBindingEnumRegister.cpp:16` 物化产物），`delete` 只覆盖注册器（`FBinding.cpp:20/29`）→ 物化产物永泄漏（F-CB-005）；物化后追加的注册器既不物化也不释放（F-CB-004）。
- `FFunctionInfo*`/`FTypeInfo*` 指向模板函数级 static（`TFunctionInfo.inl:91`、`TTypeInfo.inl:58`），生命周期 = 模块；跨模块卸载时若外部持有这些指针会悬挂（本层不持有外部对象，风险在消费侧）。

### 6.3 线程安全

- 注册与物化**无锁、无线程断言**（F-CB-012）；魔法静态保证 `Get()`/`TTypeInfo<T>::Get()` 首次初始化的线程安全，但 `Classes.Emplace`/`delete`/`ClassRegisters.Empty()` 不保证。
- `TNameSpace`（`BindingMacro.h:72`）在任意线程首次调用都会触发物化，是潜在的"并发首次物化"入口。

### 6.4 异常与错误处理

- 本层不使用异常；无 `try/catch`；无 `check`/`ensure`（grep：`check(`/`ensure` 在 `Private/Binding`+`Public/Binding` 0 命中）——所有错误路径都是"静默降级"（返回空串/空数组/false/丢弃注册），这也是 F-CB-002/F-CB-004/F-CB-008 难被发现的原因。

### 6.5 性能

- 静态初始化期：O(n²) 去重 + 每比较重建类名（F-CB-006）；枚举重复注册（F-CB-008）。
- 生成期：`GetPropertyNames`/`GetFunctionNames` 每次全表扫描 + 按值返回 `TSet`（F-CB-003）。
- 物化期：三组 TArray 值拷贝（F-CB-014）。
- 运行时热路径：本层**不在** Tick/GC 路径上（P/Invoke 注册只在域初始化时读一次 `GetMethods()`），无每帧分配问题。

### 6.6 死代码

见 §4。本层 6 项确认（`FBindingClass::IsSet`、`TTypeInfo<void>` 成员体、`FTypeInfo::GetBufferSize` 声明、`EFunctionInteract::Override`、`EBindingPropertyAccess::ReadAndWrite`、`TDefaultArguments` 恒真守卫），另有 15 项经 grep 确认仍在使用。

- 命名歧义：`FBinding::Register()`（物化，`FBinding.cpp:10`）与 `FBinding::Register(5 参)`（追加，`:38`）语义完全相反却同名，是本报告多处结论需要反复确认的直接原因，建议改名为 `Materialize()`/`AddClassBinding()`。
- `IN`/注释与代码一致性：本层注释极少，未发现"注释与代码不符"的实例（对比：`FBindingClassRegister.cpp:91-97` 的算术虽可用但无注释说明依赖枚举位值，已在 F-CB-013 指出）。

### 6.8 平台兼容
