## 1. 模块职责与架构速览

这一层是"用 C# 定义 UE 类型"这一卖点的运行时实现：**在进程内用 `NewObject` 造出真正的 `UClass` / `UBlueprintGeneratedClass` / `UDynamicScriptStruct` / `UEnum`，再用 `FTypeBridge::Factory` 造出 `FProperty`/`UFunction` 挂到这些类型上**，最后让 UObject 实例与 C# 对象互绑（`FDynamicRegistry::OnPostClassConstructor` → `FCSharpEnvironment::Bind`）。

数据流（自 C# 到 UE 类型）：

1. 代码分析（编辑器）：`CodeAnalysis.cs` 扫描带 `[UClass]/[UStruct]/[UEnum]/[UInterface]` 的声明，写出 `Dynamic.json`（**条目是 `命名空间.类型名`**，`Script/CodeAnalysis/CodeAnalysis.cs:274-353`）与 `DynamicFile.json`。
2. `FDynamicGenerator::SetCodeAnalysisDynamicFilesMap()` 载入文件映射（`FDynamicGenerator.cpp:97-105`），`FDynamicGenerator::CodeAnalysisGenerator()`（`:77-95`）编排 enum → struct → interface → class 全量生成。
3. 依赖图路径：`FDynamicGenerator::Generator()`（`:18-40`）在 `FScriptDomainScope` 内依次调用四个生成器的**无参重载**；它们用 `FDynamicGeneratorCore::Generator(AttributeClass, Fn)` 枚举 C# 侧带该属性的类型，为每个类型建一个 `FNode`（名字 = 裸类型名，回调里捕获 `FClassReflection*`），随后 `FDynamicGeneratorCore::Generator()` → `FDynamicDependencyGraph::Generator()` 做拓扑排序并执行。
4. 单类型生成：`BeginGenerator`（建立 SuperStruct / ClassFlags / ClassConstructor）→ `ProcessGenerator`（`SetFlags` + `GeneratorProperty` + `GeneratorFunction` + `GeneratorInterface`）→ `EndGenerator`（`ClearInternalFlags(Native)` → `Bind` → `StaticLink(true)` → `AssembleReferenceTokenStream()` → `SetClassDefaultObject` → 手动跑一次 `ClassConstructor` 生成 CDO）。
5. 属性/函数：`FDynamicGeneratorCore::GeneratorProperty`（`:889-916`）对每个 `[UProperty]` 调 `FTypeBridge::Factory<true>(ReflectionType, InField, FName(Name), RF_Public)` 后 `AddCppProperty`；`FDynamicGeneratorCore::GeneratorFunction`（`:918-988`）造 `UFunction`，把返回值先挂、参数倒序插入以保证 `ChildProperties` 顺序与 UHT 一致，再 `Bind()`+`StaticLink(true)`，手工挂进 `InClass->Children` 并写 `AddFunctionToFunctionMap`。
6. 软引用推迟：`FTypeBridge.inl:197-222` 的 `SetClass<true>` 用“路径最后一段”的类型名问 `FDynamicGeneratorCore::IsCompleted(Name)`；未完成则注册 `OnCompleted` 回调，等该类型生成完再回填 `PropertyClass`/`InterfaceClass`/`MetaClass`——这正是依赖图存在的意义。（注：`Struct` 分支不走 `SetClass`，它在 `:314` 直接 `LoadObject<UScriptStruct>`。）
7. 重新生成（编辑器）：`Generator(FClassReflection*, EDynamicClassGeneratorType)`（`FDynamicClassGenerator.cpp:141-235`）发现同名类型已存在时，把**旧类改名**为 `DYNAMIC_REINSTANCE*`、造新类、再 `ReInstance()` 用 `FBlueprintCompileReinstancer::ReplaceInstancesOfClass` 迁移实例，最后 `RemoveFromRoot()+MarkAsGarbage()` 旧类。

生命周期关键点（本报告重点）：
- 动态类型对象全部 `AddToRoot()`（class/struct/enum/interface 各一处），**释放路径只存在于 `#if WITH_EDITOR` 的 `ReInstance` 里**（F-DYN-004；与 F-ARCH-005/006 的"永久 root 本身非缺陷"裁决一致）；接口走“原地 `PurgeClass(true)` 重建”而不是造新类（F-DYN-007 **已撤销**：接口 `UClass` 的 `ChildProperties` 为空，`PurgeClass` 的延迟销毁分支不执行）。
- 包/名字：`FDynamicGeneratorCore::GetOuter()` = `UObject::StaticClass()->GetPackage()`，即所有动态类型都建在 **`/Script/CoreUObject`** 包内，UObject 名 = C# 类型名去掉首字母（`FDynamicClassGenerator.cpp:391`、`FDynamicStructGenerator.cpp:247`、`FDynamicInterfaceGenerator.cpp:261`；与 C#/Weaver 侧 `GetPathName()` 完全一致：`Script/Weavers/UnrealTypeWeaver.cs:222-227`、`Script/SourceGenerator/UnrealTypeSourceGenerator.cs:50-53`）。

**问题**

`GetPathName()` 的值来自 C# 侧 `Utils.GetClassDescriptorImplementation`（`Script/UE/CoreUObject/Utils.cs:133-143`）：它**只读类型上直接声明的 `[PathName]`**（`InType.CustomAttributes`，不继承）。给用户类型补 `[PathName]` 的是 IL 织入器：`Script/Weavers/UnrealTypeWeaver.cs:1067-1096`（只挑带 `UClass/UStruct/UEnum/UInterface` 特性的类型）→ `:187-204` 写入 `[PathName("/Script/CoreUObject.<去掉首字母的类型名>")]`。

因此下列情形会让父类解析失败——**而且两条子路径都在 `BeginGenerator` 同一行崩溃**（复核补正：原文只写了"`Parent->GetPathName()` 为空串"这一条，实际还有更常见的"父类反射本身为 nullptr"这条）：

- **子路径 A（父类反射为 nullptr，最常见）**：父类型未被注册进 `FReflectionRegistry` 时，`FClassReflection.cpp:146` 拿到的 `Parent` 就是空（`:37-49` 对未注册句柄返回 `nullptr`），于是 `:162` 的 `if (const auto Parent = ...)` 不成立，`ParentClass` **保持 `nullptr`**，`BeginGenerator` 首行直接解引用空指针。
- **子路径 B（父类反射存在但路径为空）**：`Parent->GetPathName()` 为空串时 `LoadClass<T>(nullptr, TEXT(""))` 返回 nullptr，同样落进首行解引用。

- `[UClass] public partial class UMyThing : MyPlainBase`，而 `MyPlainBase : AActor` 是**没有 `[UClass]` 的普通 C# 基类**。C# 侧对此**不会报错**：`Script/SourceGenerator/UnrealTypeSourceGenerator.cs:420-484` 只在基类名以 `A`/`U` 开头或以 `_C` 结尾时才做名字校验，基类为其它名字时那条 else-if 链没有兜底（`:443-468`）；`[UClass]` 只强制"必须有基类"（`:472-483`）。此时 `MyPlainBase` 既不在 `Dynamic.json` 中（`CodeAnalysis.cs:274-288` 只收录带特性的类），也不会被织入 `[PathName]`，于是 `PathName == ""`。
- 父类型虽带特性，但属于**本次未加载的其它程序集**，或父类型因前面的失败被跳过（图只对"父类也带 `[UClass]`"排序，见 `:63-72`），从而在父类建出来之前就执行了 `LoadClass`。

崩溃点不止一处：即使 `BeginGenerator` 修好，`EndGenerator`（`:340`）与 CDO 构造（`:339-341`）仍会因 `GetSuperClass()==nullptr` 崩溃。

**问题**

> ⚠️ **本段推理已被复核撤销**（前提"接口 `UClass` 的 `ChildProperties` 非空"不成立，详见上方 `复核证据` ②③）。以下正文保留以便追溯，**不得再作为缺陷引用**。

在 `WITH_EDITORONLY_DATA` 构建（编辑器，也就是本插件的主要工作场景）下，`PurgeClass` 把该类**全部 `ChildProperties`（上一轮为接口函数创建的 `FProperty` 参数/返回值链）**挂到 `PropertiesPendingDestruction` 链表上，等待调用方显式销毁（`Class.cpp:6350-6364`）。插件从未调用 `UClass::DestroyPropertiesPendingDestruction()`，于是：

- 每次 C# 热重载，**每个动态接口**泄漏上一轮的整条 `FProperty` 链（含 `FObjectProperty::PropertyClass` 引用、`FString` 元数据）；
- `PropertiesPendingDestruction` 只增不减，节点数随重载次数线性增长；
- 这些字段已不在任何 `ChildProperties` 链上、不被 GC schema 追踪，属"不可回收"的泄漏；编辑器长时间迭代（正是动态 C# 类的工作方式）会持续抬高内存高水位。

同时确认：`PurgeClass` 会清 `CLASS_TokenStreamAssembled`（`Class.cpp:6296` 的 `ClassFlags = CLASS_None`），因此 `EndGenerator` 的 `InClass->AssembleReferenceTokenStream()`（`FDynamicInterfaceGenerator.cpp:188`）能真正重建引用 schema。**这一点不是 bug**（与本层其它"schema 陈旧"猜测相反），特此记录以免误报。

**建议**

```cpp

	Class->DestroyPropertiesPendingDestruction();   // PurgeClass 调用方负责（Class.cpp:6350-6352）
#endif
```
位置建议放在 `FDynamicInterfaceGenerator::EndGenerator`（`:180-229`）末尾：此时 `ReInstance(Class)`（`:135` 之后执行）只改 Blueprint 引脚与编译（`:271-312`），不引用旧 `FProperty`，故安全。取舍：若将来有代码依赖 `PropertiesPendingDestruction` 做字段引用重定向（引擎编译器重编译时会用），必须放在所有引用修复之后；本插件的接口没有 BP 字段重定向需求。

**验证方式**

- grep `DestroyPropertiesPendingDestruction`：插件侧 0 命中；引擎侧在 `Kismet*` / `BlueprintEditorUtils` 中有调用。
- 反复热重载同一接口 20 次，dump `UClass::PropertiesPendingDestruction` 链长度（调试器或临时日志统计 `ChildProperties` 数量对比）。
