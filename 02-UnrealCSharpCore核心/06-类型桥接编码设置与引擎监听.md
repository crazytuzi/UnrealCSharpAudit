## 1. 模块职责与架构速览

`UnrealCSharpCore` 是插件的"反射/桥接内核"，本组 19 个文件构成它的**外围骨架**：

```
                     ┌──────────────────────── UnrealCSharpCore.build.cs ───────────────────────┐
                     │ 编译期读 <Project>/Config/DefaultUnrealCSharp{Editor,}Setting.ini       │
                     │  → 定义 WITH_CORECLR / WITH_MONO / WITH_LEANCLR / WITH_BINDING           │
                     │  → 依赖 CoreCLR|Mono|LeanCLR 模块                                        │
                     └─────────────────────────────────────────────────────────────────────────┘
IModuleInterface ─ FUnrealCSharpCoreModule（UnrealCSharpCore.h:9）
   ├─ EState{Inactive,Active,Outdated} + Activate/Deactivate/MarkOutdated（UnrealCSharpCore.cpp:19-60）
   └─ FEngineListener EngineListener（UnrealCSharpCore.h:43）——模块对象构造即注册引擎委托
        ├─ IPluginManager::OnLoadingPhaseComplete → PostDefault 成功后 SetActive(true)
        ├─ FCoreDelegates::OnPreExit           → SetActive(false)
        └─ 静态 OnPreBeginPIE（由 UnrealCSharpEditor 的 FEditorListener 直接调用）

FUnrealCSharpCoreModuleDelegates（6 个静态多播委托，跨模块事件总线）
   OnUnrealCSharpCoreModuleActive / InActive  ← Activate()/Deactivate() 广播
   OnBeginGenerator / OnEndGenerator          ← UnrealCSharpEditor 广播，Compiler/Editor 订阅
   OnDynamicClassUpdated（WITH_EDITOR）        ← FDynamicClassGenerator 广播
   OnCompile（WITH_EDITOR）                    ← FCSharpCompilerRunnable 广播（工作线程，见 F-BR-009）

FTypeBridge（静态无状态桥）：
   GetClass(FProperty*) ──▶ 27 个具体重载 ──▶ FReflectionRegistry（C# 类型注册表）
   GetPropertyType(FClassReflection*) ──▶ 30 次 IsAssignableFrom 探测 ──▶ EPropertyTypeExtent
   Factory<IsSoftReference>/ManagedFactory ──▶ new F***Property（动态类生成用）
   SetClass<IsSoftReference> ──▶ FDynamicGeneratorCore 依赖图回调（软引用延迟设置 Class）

NameEncode：Encode 把 UE 名字编码成 C# 合法标识符（`_hXX_` / `_h01_` / `_huXXXX_`），
   被 FUnrealCSharpFunctionLibrary::Encode 用于生成 C# 属性名/函数名/命名空间（即绑定键）。
```

关键生命周期：`FUnrealCSharpCoreModule` 是 `FModuleManager` 的单例，`EngineListener` 是其**值成员**（`UnrealCSharpCore.h:43`），因此监听器的构造/析构与模块的加载/卸载严格绑定；`State` 的所有写入都发生在 GameThread（见 §6）。

### [F-BR-002] `GetClass(FProperty*)` 缺 `FUtf8StrProperty`/`FAnsiStrProperty` 分派：专用重载成孤儿，这两类属性静默映射为 `nullptr` —— **已证伪：非缺陷，请从排期移除**

- **严重度**: **撤销（非缺陷）**

### [F-BR-012] `GetAssemblyLoader()` 的"判空"在空指针上调用成员函数：检查被自身解引用抵消

- **类别**: 未定义行为 / 健壮性
- **严重度**: **P3**
- **复核结论**: ⚠️部分 —— 严重度由 P2 校正为 **P3**；可达性 潜伏
- **文件**: `Source/UnrealCSharpCore/Private/Setting/UnrealCSharpSetting.cpp:122-128`
- **函数**: `UUnrealCSharpSetting::GetAssemblyLoader() const`
- **置信度**: 高（代码事实与引擎实现均已核对）；"配置能取到 null"为**中**

**现状（代码事实）**

```cpp
// UnrealCSharpSetting.cpp:122-128
UAssemblyLoader* UUnrealCSharpSetting::GetAssemblyLoader() const
{
	return Cast<UAssemblyLoader>((AssemblyLoader->IsValidLowLevelFast()
		                              ? AssemblyLoader.Get()
		                              : UAssemblyLoader::StaticClass())
		->GetDefaultObject());
}
```

三元表达式的意图显然是"配置的类有效就用它，否则回落到 `UAssemblyLoader` 自己"——但**判空动作本身**是通过被检查的指针完成的。`AssemblyLoader` 是 `TSubclassOf<UAssemblyLoader>`，其 `operator->` / `Get()` 在类指针为空或不是 `UAssemblyLoader` 子类时都返回 `nullptr`：

```cpp
// 引擎 Engine/Source/Runtime/CoreUObject/Public/Templates/SubclassOf.h:108-128
	[[nodiscard]] FORCEINLINE UClass* operator*() const
	{
		if (!Class || !Class->IsChildOf(T::StaticClass()))
		{
			return nullptr;
		}
		...
	[[nodiscard]] FORCEINLINE UClass* Get() const { return **this; }
	[[nodiscard]] FORCEINLINE UClass* operator->() const { return **this; }
```

于是当配置为空时表达式等价于 `((UClass*)nullptr)->IsValidLowLevelFast()`。UE 5.6 的实现恰好自带空判断（`Engine/Source/Runtime/CoreUObject/Private/UObject/UObjectBase.cpp`：`IsValidLowLevelFast` 首行即 `if ((!IsThisNotNull(this, "UObjectBase::IsValidLowLevelFast")) || (UPTRINT)this < 0x100) { UE_LOG(LogUObjectBase, Error, TEXT("'this' pointer is invalid.")); return false; }`，且该函数**非虚**，`UObjectBase.h:178`），因此当前不会崩，但会：

1. 依赖引擎内部实现细节才能"正常工作"（C++ 层面对空指针调用非静态成员函数属 UB）；
2. 每次 `AssemblyLoader` 为空都向 `LogUObjectBase` 打一条 `Error: 'this' pointer is invalid.`，把本应静默回落的默认路径变成错误日志噪音。

**调用上下文**
唯一调用链：`UUnrealCSharpSetting::GetAssemblyLoader()` ← `FMonoFunctionLibrary::GetAssemblyLoader()`（`Source/UnrealCSharpCore/Private/Domain/Mono/FMonoFunctionLibrary.cpp:81-83`）← `FMonoDomain.cpp:343`（Mono 域初始化/程序集加载）。即只有 Mono 后端会走到；`AssemblyLoader` 的 ini 值来自 `UPROPERTY(Config, EditAnywhere, Category = Domain) TSubclassOf<UAssemblyLoader> AssemblyLoader;`（`UnrealCSharpSetting.h:165-166`），构造时默认 `UAssemblyLoader::StaticClass()`（`UnrealCSharpSetting.cpp:22`）。显式在 ini 写 `AssemblyLoader=None`，或写一个已不存在/路径失效的类路径，都会让 `TSubclassOf` 解析为空。

**问题**
"容错分支"（`UAssemblyLoader::StaticClass()`）无法在真正需要它的时候被正确进入判定逻辑：判定条件先解引用了同一个空指针。属于典型的"检查被自身抵消"缺陷。

**建议**

```cpp
UAssemblyLoader* UUnrealCSharpSetting::GetAssemblyLoader() const
{
	// TSubclassOf::Get() 已内含 null 与 IsChildOf 检查，取出来再判空即可
	const auto LoaderClass = AssemblyLoader.Get();
	return Cast<UAssemblyLoader>((LoaderClass != nullptr ? LoaderClass : UAssemblyLoader::StaticClass())
		->GetDefaultObject());
}
```

若想保留"配置类无效时也报错"，应改为显式日志而不是调用空指针成员函数：

```cpp
	if (LoaderClass == nullptr)
	{
		UE_LOG(LogUnrealCSharp, Warning,
		       TEXT("UnrealCSharpSetting.AssemblyLoader is not a valid UAssemblyLoader; falling back to the default."));
	}
```

**验证方式**
在 ini 里写 `AssemblyLoader=None` 并走 Mono 域初始化，检查是否出现 `LogUObjectBase: Error: 'this' pointer is invalid.`（当前会），修完后应只剩自定义 Warning 或无日志；`grep -n "AssemblyLoader" Source/UnrealCSharpCore/Private/Setting/UnrealCSharpSetting.cpp`。

**现状（代码事实）**

```cpp

{

	{
		if (int32 Index; InPathName.FindLastChar('.', Index))    // ← 找不到 '.' 时整个 if 体都不执行

			}

			{
```

**问题**
`InPathName` 不含 `'.'` 时（`FindLastChar` 返回 false）函数**既不设置类也不报错**：属性被创建出来、`AddCppProperty` 成功、却带着 `PropertyClass == nullptr` / `InterfaceClass == nullptr` / `Struct == nullptr` 进入后续序列化与反射（`LoadObject` 与依赖图回调都不会发生）。这与 `GetStatus` 类 API 常见的"返回 bool"不同 —— 该函数返回 `void`，调用方无法察觉失败。含 `'.'` 的路径（如 `/Script/CoreUObject.Vector`、C# weaver 生成的 `/Script/CoreUObject.X`，见 `Script/Weavers/UnrealTypeWeaver.cs:222-227`）能正常工作，因此这是一条**取决于命名格式**的隐式契约。另外 `OnCompleted` 的回调捕获了裸 `FProperty*`（`[PathName, ClassProperty]` 等），若该属性在依赖图完成前被释放（动态类重建/GC），回调会写已释放内存 —— 这一条我**未验证**具体释放路径（见 §5）。

**建议**
把失败显式化：

```cpp
	if constexpr (IsSoftReference)
	{
		int32 Index = INDEX_NONE;
		if (!InPathName.FindLastChar('.', Index))
		{
			UE_LOG(LogUnrealCSharp, Error, TEXT("SetClass: path '%s' has no '.', property class left unset"), *InPathName);
			return;
		}
		...
```

若确实存在"无点路径合法"的场景，则应提供第二条解析分支（例如按最后一个 `/` 切分）。

**验证方式**

以下维度按规范逐项检查，结论为"无问题"的也列出依据。

### 6.1 空指针 / 越界 / 未检查返回值
- **有问题的**：F-BR-001（`Factory` 返回 nullptr 被解引用）、F-BR-003（`LoadObject` 结果被解引用）、F-BR-005（`GetPropertyType(nullptr)`）、F-BR-010（`PathString[0]`/`[Len-1]`）。
- **检查过、无问题的**：`FTypeBridge.cpp` 全部 `GetClass` 重载均有 `if (InProperty != nullptr)`（`:363-604`）；`FClassReflection::IsAssignableFrom(nullptr)` 安全（`FClassReflection.cpp:770-795`）；`FEnumProperty::SetEnum` 可接受 null（引擎 `EnumProperty.h:86-90`）；`GetMutableDefaultSafe<T>()` 是到处使用的判空封装（`FUnrealCSharpFunctionLibrary.h:266`）；`FNameEncode` 无 C 风格缓冲区操作（无 `sprintf`/`strcpy`/`memcpy`，全用 `FString`）。

### 6.2 内存与资源泄漏
- `FEngineListener`：`AddRaw` × 2 与析构中的 `Remove` × 2 严格配对（`FEngineListener.cpp:13/17` 与 `:24/29`），句柄初值为无效（`FEngineListener.h:24/26`，`FDelegateHandle` 默认构造），析构中先 `IsValid()` 再 `Remove` —— **无泄漏、无悬垂注册**。
- `FUnrealCSharpCoreModuleDelegates` 的 6 个静态多播委托：所有订阅方都在各自 `ShutdownModule`/析构中 `Remove`（`FCSharpCompilerRunnable.cpp:34-41`、`UnrealCSharp.cpp:23-32`、`FEditorListener.cpp:135-147`、`DynamicDataSource.cpp:96-103`、`ClassCollector.cpp:69-76`、`UnrealCSharpBlueprintToolBar.cpp:44-46`），未发现只加不减的订阅。
- 本组文件自身不做裸内存分配（`Factory` 里 `new` 出的 `FProperty` 由调用方 `AddCppProperty` 交给 owner 容器管理；`FCSharpBind.inl:93` 传 `nullptr` 作为 owner 的属性由 `FContainerHelper` 负责释放 —— 该所有权链不在本组文件，未深查）。

### 6.3 线程安全
- `FUnrealCSharpCoreModule::State`（`UnrealCSharpCore.h:45`）：全部写入都在 GameThread（`FCSharpCompilerRunnable.cpp:213-240` 用 `FFunctionGraphTask ... ENamedThreads::GameThread`；`FEngineListener` 的引擎委托也在 GameThread；`FEditorListener.cpp:218` 在 PIE 开始时于 GameThread）。**未发现**数据竞争。
- 唯一跨线程点：F-BR-009（`OnCompile` 在工作线程广播）。

### 6.4 异常与错误处理
- 本组文件无 `try/catch`（全插件 `Source/` 亦为 0，见 6.8），错误路径靠返回值 + `UE_LOG`。
- `FTypeBridge` 的失败语义是"返回 nullptr"或"返回 `None`"，但**都不带日志**（F-BR-001/005/013），这是本组最系统的错误处理弱点。
- 本组无 `check`/`ensure`（除 `FTypeBridge.h` 无）→ 不会在 Shipping 因 `check` 崩溃，但也意味着静默失败无法在 Dev 构建暴露。

### 6.5 性能
- `FTypeBridge::GetPropertyType` 每次调用执行最多 30 次 `FReflectionRegistry::Get()`（函数内静态单例，`FReflectionRegistry.cpp:Get()`）与 30 次虚函数 `IsAssignableFrom`（每次沿继承链走并 `EnsureDescriptor()`）；`EnsureDescriptor` 有 `bDescriptorLoaded || bInitializing` 早退（`FClassReflection.cpp:407-414`），因此**不是**每帧热点（调用方仅动态类生成期间），**未列为 Finding**。
- `GetPropertyType` 的 `switch (GetPropertyType(...))` 在 `FDynamicGeneratorCore.cpp:93` 每属性一次，规模可控。
- `FNameEncode::Encode` 使用 `Ret.Reserve(InName.Len() + 4)`，只是预留（`TArray` 会自增长），无重复分配问题；但最坏膨胀约 5 倍（每个字符 → 5 字符），未做长度上限检查 —— 与 F-BR-006 的"非法输入行为未定义"同源，未单列。

### 6.8 平台兼容
- 32/64 位：`EPropertyTypeExtent` 底层类型未指定（`enum class`，编译器选 `int`），从不跨边界传递，无数值宽度假设。
- TCHAR 宽度：`NameEncode` 的 `C > 0x7F` 分支与 `static_cast<unsigned short>` 依赖 16 位 `TCHAR`。已核对 UE 5.6：Windows/Mac/Linux/Android/iOS 均 `PLATFORM_TCHAR_IS_CHAR16 1`（`GenericPlatform`/`UnixPlatform.h:50`/`AndroidPlatform.h:47`/`MacPlatform.h:55`/`IOSPlatform.h:29`），`PLATFORM_TCHAR_IS_UTF8CHAR = USE_UTF8_TCHARS = 0`（`Platform.h:275-281`）→ **当前无问题**；若将来启用 `USE_UTF8_TCHARS`，`ShouldEscape(C)` 的 `isalnum(负值)` 与逐字节"宽字符"编码会双双失效（记录为潜在风险，未立 Finding）。

- `snprintf`/`sprintf`：本组文件 0 处（`FString::Printf` 全部使用 `%s`/`%X`/`%hs` 且参数类型匹配，未发现格式串漏洞；`FCoreCLRLog.cpp:11`/`FLeanCLRLog.cpp:8` 用 `%hs` 传 `char*` 是正确的窄字符写法）。
- RTTI/异常：全插件 `Source/`（去 ThirdParty）`dynamic_cast` 0 处、`try/catch` 0 处，build.cs 也未设置 `bUseRTTI`/`bEnableExceptions` → 与 UE 默认（均关闭）一致，**无冲突**。6 个模块的 `PCHUsage` 也都是 `UseExplicitOrSharedPCHs`（各 build.cs:9/12）。
